## 省略參數的含義

現行 `modules/api.js:390` 與 `modules/ai-protocols/chat-completions.js:47` 沒有傳送思考強度欄位。這表示由模型、供應商與代理服務的預設策略處理，不能推論為關閉，也不能直接標成 low 或 high。

在本機 `workbuddy/deepseek-v4.1-flash` 路徑，8 題完全省略參數的基線請求全部有網關上報的推理 token。因此目前 BDC 若使用這條路徑，省略參數仍會開啟思考。這個結果沒有辨識出預設究竟對應哪個內部強度，不能僅由耗時或推理長度判定檔位。

本次已驗證，在同一 DeepSeek 路徑明確發送 `reasoning_effort: 'none'` 時，16 次主測的上報推理 token 全為 0，並明顯減少正文等待。要在該路徑確實採用快速策略，應在最終 HTTP 請求中明確指定，而非繼續省略參數。

```json
{"reasoning_effort":"none"}
```

上例是要加入完整請求的欄位片段，不是可獨立發送的完整請求。僅在設定物件中新增同名欄位，目前程式也不會自動傳給供應商；需要經共用 API 入口與協議適配器實作。

在提示詞要求簡短回答、調低 temperature、收起思考顯示，都不能代替供應商實際支援的關閉參數。

## 建議採用的任務預設

| 任務 | 建議預設 | 說明 |
| --- | --- | --- |
| 查詞、一般句中詞義 | 快速：明確關閉 | 實測主要意思相同，優先減少等待 |
| 普通段落／文章翻譯 | 快速：明確關閉 | 高檔未顯示穩定品質收益；數字與條件仍要正確保留 |
| 一般單句結構分析 | 標準：低檔，提供深入選項 | 作為速度與解說完整性的產品折衷；高檔在本輪句法細節較完整 |
| AI 助手一般問答 | 標準：低檔，可手動切快速 | 給較長上下文與追問保留一定推理空間；本輪未證明低檔普遍優於關閉，這是產品取捨 |
| 明確的長難句詳解、使用者選擇深入回答 | 深入：高檔 | 接受較長等待，並提高至足夠的生成預算 |

介面可以用「快速／標準／深入」表達使用目的。在已測 DeepSeek 上分別對應 `none/low/high`。只有使用者選擇「跟隨服務端」時才省略欄位；不將省略參數包裝成快速模式。

不必為每次查詞增加一個 AI 分類請求。第一版可直接依現有 taskType 分配，助手由使用者按問題難度手動切換。

## 實作落點

1. 在共用請求設定解析處計算本次策略，讓 `requestAI()` 與 `streamAIResponse()` 共用；由協議適配器輸出各服務實際支援的欄位。功能模組繼續傳任務語義。
2. 普通段落翻譯 `articleParagraphTranslation` 與單句詳解 `articleSentenceTranslation` 必須分開設定，不把所有 `articleAnalysis` 一律設為高檔。
3. 優先次序建議為：本次手動選擇、使用者任務設定、應用程式任務預設。對能力未知的模型，保持明確的「跟隨服務端」狀態，避免聲稱已關閉。
4. 深入模式同時處理生成上限。前次補測出現1100 token截斷後重試，累計12.03秒；應在首次請求就預留適當空間，並按模型驗證，不用單一上限套用所有任務。
5. 在需要辨識生成策略的快取鍵中加入有效檔位，或在使用者選深入時明確重新生成，避免深入分析直接讀到快速版本。
6. 驗收同時檢查最終出站參數、正文首字時間、完整性及供應商可用的推理用量。顯示「關閉」必須有實際能力與驗證依據。

若新增持久化設定，沿用帳戶範圍 AI profile 與同步架構；UI 即時儲存及 `zh-CN/zh-HK` 雙語規則照舊。

## Grok 與其他模型的界限

目前本機 grok2api 的兩個 fast 名稱都映射 FAST app-chat 路徑，該路徑將 `reasoning_effort` 用於控制思考內容輸出，沒有藉此改變實際 mode。即使模型列表宣告支援 none，也不能只憑該宣告在 UI 保證關閉推理。

要在這條 Grok 接入提供真實速度／推理選項，需要選擇已驗證可切換的上游模式或調整代理的實際映射，再重新驗證。僅隱藏回傳思考內容沒有充分依據保證節省推理時間。

其他供應商應按模型與部署實作對應，不對所有 OpenAI 相容服務一律發送 `reasoning_effort: 'none'`。不支援關閉的模型應如實顯示最低強度或跟隨服務端，必要時選用能提供快速模式的模型。

本次只整理優化建議並覆核既有實測，沒有再次發出模型生成請求。
