# AI 供應商憑證保存方案建議

依據會話 386 末段及 docs/research/20261017022406409_BDC接入magpie的AI方案評估.md，需比較的是 A 瀏覽器直連、B 同源反代與 C 憑證留在服務端。

目前沿用使用者暫不做中轉的要求，建議採 A 的本機保存方式；若長期要多裝置或家人共用同一份供應商額度，建議採 C。B 解決連線路徑問題，但原方案仍將金鑰保存在瀏覽器，並未改善金鑰保存位置。

## 現階段保存方式

供應商名稱、無憑證網址、模型及任務映射放在一般設定。個人金鑰只存目前瀏覽器的 secrets 區域，不寫入隨站點公開的 ai-config.js，也不納入一般同步和設定匯出。可提供僅本次使用與記住此裝置兩種選擇。

現有 modules/settings.js 已將一般設定 pen_global_settings 和秘密 pen_global_secrets 分開，但兩者均使用 localStorage；secrets 命名不代表加密。它避免隨靜態檔案向訪客發送金鑰，不能防止同源惡意腳本或 XSS 讀取。換成 IndexedDB 不會消除這項邊界。參考：https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage

特別留意前次討論的 ?key=：modules/sync-core.js 會保留 provider 的 baseUrl、apiUrl、modelsUrl。若把金鑰直接填進這些網址，就可能繞過 secrets 分離並進入同步。應保存無憑證網址及獨立金鑰，僅在發送時按需要組合，並遮蔽錯誤訊息和日誌；仍應優先採用服務支援的標頭認證。

## 長期保存方式

HAPI 等上游供應商金鑰留在 magpie 或受控服務端；BDC 的受驗證後端持有受限 gateway key，瀏覽器僅持有自身登入會話。服務端必須驗證身份、限制可用模型與額度，不能成為匿名即可使用的付費 API 入口。

C 不必綁定 Worker 加 Supabase 的特定組合，可按既有部署與登入能力實現。僅把金鑰藏進後端而不保護呼叫入口，仍會被濫用。

## 建議結論

現在以個人直連為主：非敏感設定可同步，金鑰只留本機，不把金鑰放入網址設定。長期多裝置共用：轉為 C 的服務端持有金鑰。前次紀錄的線上暴露狀態屬歷史檢查，本次不據此宣稱目前網站仍暴露任何金鑰。
