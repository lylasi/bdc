# 文章與筆記儲存粒度及版本策略評估

日期：2026-10-15

狀態：程式核對及方案修訂建議，尚未實作

對應計劃：[文章詳解單詞標記與筆記功能實施計劃](../plan/20261015133427783_文章詳解單詞標記與筆記功能實施計劃.md)

## 1 結論

將文章原文、AI 派生資料和使用者筆記分開保存是合理方向。每次查詞、修改筆記或更改標題便複製整篇文章並永久保留，則不適合作為預設行為。

目前程式的主要問題是寫入及同步粒度過大：小修改會重寫本機整組文章，雲端有變更時會傳送整份應用快照。雲端目前只有最新快照，沒有逐次新增文章歷史。

建議採用「穩定文章 ID、按需保存被引用的原文版本、筆記獨立寫入、雲端分項同步」。原計劃把新增學習資料持續放進單列 JSON，並將歷史壓縮完全延後，容量規劃不足，需要修訂。

## 2 現有程式實際保存甚麼

| 層次 | 現況 | 評估 |
| --- | --- | --- |
| 本機文章 | `saveAnalysisResult()` 優先按 articleId 更新記錄，否則按完全相同原文查找；未找到才新增 | 有穩定 ID 時是更新同一篇，缺少 ID 又改原文時可能多出記錄 |
| 本機寫入 | `saveAnalyzedArticles()` 把整個文章陣列 JSON 化並寫入一個 localStorage key | 小修改也重寫整組，資料變大後成本增加 |
| 雲端資料表 | D1 `snapshots` 每個 user_id 一列 payload | 保存一份最新應用快照；version 是樂觀鎖計數，不是文章歷史 |
| 雲端更新 | POST `/snapshot` 以版本條件 UPDATE 既有列 | 不會因每次修改自動累積歷史列 |
| 同步傳輸 | 正式同步拉取完整快照，合併後有變更才推送完整 payload | 沒有變更不推送；平時輪詢只查版本號 |
| 衝突合併 | articles 採整組較新時間覆蓋 | 即使改的是不同文章，仍可能互相覆蓋，筆記不能直接沿用 |

程式依據：`modules/storage.js:492`、`:595`；`modules/sync-cloudflare.js:183`、`:221`；`modules/sync-core.js:560`；`cloudflare-worker/schema.sql:15`；`cloudflare-worker/src/worker.js:159`。

因此要區分「重新寫入同一份資料」「新增歷史副本」「傳送整份資料」：現況主要發生第一及第三項。

## 3 每種修改應保存甚麼

| 操作 | 建議寫入 | 是否新增原文副本 |
| --- | --- | --- |
| 點開單詞解釋 | 查閱記錄；AI 結果由原有分析／快取層處理 | 同一來源版本首次產生學習記錄時保存一次，之後共用 |
| 編輯筆記 | 覆寫該筆記草稿，提交時保存該筆記修訂 | 否 |
| 新增另一則筆記 | 新筆記與 sourceId、範圍 | 已有該來源版本時不再保存 |
| 收藏／取消收藏 | 詞書成員資料，正文標記由其推導 | 否 |
| 改文章標題、顯示設定或介面語言 | 對應 metadata／設定 | 否 |
| 相同原文重新分析 | 更新分析結果，重用原文雜湊 | 否 |
| 編輯文章文字框 | 保存一份可覆寫的工作草稿，正文仍綁定已渲染來源 | 不按每次輸入建立歷史 |
| 提交修改後的原文，但尚無新學習記錄 | 更新目前文章內容及分析；舊學習資料仍引用舊來源 | 不額外建立新學習來源歷史 |
| 修改後的原文首次產生查閱／筆記 | 保存這個已提交原文版本，讓記錄可以還原 | 有需要才保存，每個內容版本一次 |

首次筆記及來源保存仍須同一交易完成，不能留下沒有原文來源的筆記。內容雜湊相同就重用既有版本；不能只按文章長度或修改時間去重。

## 4 只改一個字，甚麼時候保留兩份是合理的

假設舊文 A 已有筆記，使用者把其中一個字修改後提交成 B，並在 B 再寫一則筆記。A 和 B 都被學習資料引用，保留兩個版本可以準確還原當時的原文和位置。

若直接把 A 的正文改成 B，原來依偏移定位的筆記可能錯位，引用詞義也可能改變。此時保存 B 的完整短文，比首版引入差異重播、版本鏈斷裂恢復等機制更容易驗證。

但以下情況不需要複製原文：

- 修改的是筆記內容，文章本身未變。
- 文字框連續改了十次，最後只提交一次。
- 原文內容未變，只重新生成 AI 分析。
- 同一版本新增多則筆記或多次查詞。

「有必要的內容版本保存一份完整原文」可以接受；「任何操作都新增完整文章歷史」應避免。

## 5 建議的資料邊界

| 資料 | 身分與內容 | 保存策略 |
| --- | --- | --- |
| 文章 | 穩定 articleId、目前來源、標題與 metadata | 同篇文章保持 ID，更新目前狀態 |
| 學習來源 | articleId＋內容雜湊、精確原文及定位映射 | 按引用需要保存，內容不變時共用 |
| 查閱記錄 | sourceId＋句子位置＋規範化詞形 | 更新該筆記錄首次／最近時間 |
| 筆記 | noteId、文字、來源範圍及修訂關係 | 草稿覆寫；提交只新增筆記級修訂 |
| AI 派生資料 | 與來源、模型及提示詞等相容的結果 | 沿用可重建／可清理的資料層，不複製到每則筆記 |

在本機保留計劃中的獨立 IndexedDB，避免清理 AI 快取時丟失筆記。新學習資料逐項寫入；現有 localStorage 文章整組寫入列為後續需要拆分的舊結構，不因增加一則筆記而再寫整個 analyzedArticles。

本機 object store 和雲端資料表不必完全同名；兩端都應維持來源只保存一次、筆記透過 ID 引用的邊界。

### 保留及清理規則

- 不建立未提交的原文歷史；原文及筆記的暫存草稿可覆寫。
- 同一內容版本的多則筆記共用來源，避免重複原文和完整分析結果。
- 保留仍被查閱、筆記、衝突分支、可恢復的刪除記錄或草稿引用的來源。
- 檢查引用時須包含仍保留的歷史修訂，不能只看目前畫面可見的筆記。
- 未被任何保留資料引用的本機來源可列為清理候選；雲端永久刪除仍須有同步與恢復政策，不能直接依本機引用數刪除。
- 筆記的因果關係用於判斷同步衝突；無限保存全部歷史文字並非首版產品目標。歷史內容壓縮與刪除標記回收需要另定安全規則。

這些規則控制不必要的副本，但無法讓持續新增的真實學習資料永遠保持固定容量。

## 6 雲端結構需要修訂

2026-10-15 核對 Cloudflare 官方資料，D1 的單一字串、BLOB 或資料列上限為 **2,000,000 bytes**。目前每位使用者整份應用資料放在一列，因此原文、分析、詞書和新增筆記會共同消耗這個上限；不能將整個資料庫容量當成單一使用者 JSON 的可用容量。[Cloudflare D1 官方限制](https://developers.cloudflare.com/d1/platform/limits/)

未查閱使用者線上資料或瀏覽器實際儲存量，不能據此斷言目前已接近上限；可以確定的是此結構具有硬性容量瓶頸。

### 建議的改造邊界

1. 既有 snapshots 暫保留給原有資料；新增學習資料使用獨立分項儲存。
2. 原文來源每個 sourceId 一筆；查閱每個查閱鍵一筆；筆記修訂每個 revisionId 一筆，所有鍵均包含使用者隔離範圍。
3. 同步上傳本次修改的項目；下載使用變更游標及分頁，首次登入可分頁取得全部學習資料。
4. 以冪等 ID 重試；修訂及來源保持引用完整，資料與同步游標更新須有一致的交易規則。
5. 完整 JSON 保留作備份／匯入格式。備份檔可以完整包含資料，日常同步不必每次傳整份備份。
6. 每筆來源仍須檢查編碼後大小；超大文章另做分塊或物件儲存，不能認為分表後便沒有單筆限制。
7. 既有 snapshots 仍須檢測大小；日後將原有文章分析也拆成逐文章同步，才能一併解決舊資料的整組覆蓋與增長問題。

表結構可採來源、查閱、筆記修訂與同步變更記錄等獨立表；具體 DDL、游標交易及遷移協議應在實作前完成規格。新功能從第一版採分項契約，比先累積大量 articleStudy 後再拆遷更穩妥。

### 是否立即使用差異儲存

目前不建議為短文首版自行實作全文 diff／patch 儲存。先消除不必要複製、按內容去重和改用分項傳輸，收益比較直接。若往後確實支援長篇文稿頻繁修訂，再評估「定期完整快照＋中間差異」，並保留重建及備份驗證機制。

## 7 對原實施計劃的修訂影響

| 原計劃項目 | 修訂建議 |
| --- | --- |
| 原文每版本保存 | 明確限定為已提交且被學習記錄引用的版本，不包含每次輸入或筆記改動 |
| payload.articleStudy | 保留為備份／匯入的邏輯格式；日常雲端保存改為分項資料與協議 |
| 預計無需新增雲端資料表 | 撤回此假設，新增來源／查閱／修訂及同步所需結構 |
| 舊客戶端缺欄位保護 | 舊 snapshot 端點不能操作新學習資料；新舊同步通道分開相容 |
| 全量快照同步 | 新學習資料逐項上傳、按游標分頁下載；舊資料仍依現有通道 |
| 首版先全保留、以後再處理容量 | 首版加入大小量測及按需版本建立；保留資料須有成長評估 |
| 完整版本 10–15 日估算 | 原估算未包含新增分項雲端同步，不能直接作修訂版承諾；完成協議拆解後重估 |

原計劃的標記規則、筆記介面、精確定位、雙語、草稿保存及衝突保留方向仍適用。本次釐清的是資料寫入粒度、原文副本建立條件及雲端容量邊界。

## 8 需補充的驗收

1. 同一原文新增多則筆記及修改筆記多次，來源記錄數保持一份。
2. 文字框連續修改但不提交，不累積學習來源歷史。
3. 同內容重新分析及不同換行格式輸入，依既定規範化規則共用內容版本。
4. 新舊原文各有學習記錄，兩邊引用可還原；未提交編輯不影響目前正文歸屬。
5. 一則筆記更新只提交相關學習項目，不重新上傳全部文章及筆記歷史。
6. 增量下載分頁、重複請求、斷線恢復及兩裝置並發後無缺項、重複或錯誤覆蓋。
7. 刪除／清理流程不刪去衝突、歷史修訂、草稿或可恢復記錄仍需的來源。
8. 對實際序列化大小測量；本機、單筆雲端及舊快照超限均可感知，不顯示假保存成功。
