# AI 供應商六項修正落地決策

- 日期：2026-10-17
- 對應方案：`docs/plan/20261017130932086_D1按使用者同步AI供應商設定完整方案.md`（第 1–16 節）
- 問題來源：`docs/report/20261017213102677_AI供應商方案獨立驗收報告.md`（F1–F6）
- 實作與驗證報告：`docs/report/20261017220515650_AI供應商方案六項問題修正與回歸驗證報告.md`

本次修正以原方案文字為準，不以後附偏差取代需求。以下是實作時需要明確取捨的四點，全部保留原方案的目標（local-first、瀏覽器直連、Key 不進普通 snapshot、預設供應商登入限定）。

## D1. 新裝置的憑證列：以「下載目標」建立，而不是改寫決策表

F1 的根因是同步只枚舉本機已有的憑證列。實作選擇在讀取遠端清單後，為「遠端有、本機完全沒有」的已知供應商建立 `syncMode: 'cloud'`、`version: 0` 的憑證列，再交給既有決策表下載；`decideCredentialAction()` 仍是純函式、語義不變（本機沒有修改且遠端版本較新 → 下載）。

- 保留「本機明確 `local-only` 優先」：只要本機已有憑證列就不會建立下載目標。
- 不把其他供應商的 Key 綁進來：下載**之前**先比對遠端 `binding` 與本機供應商定義；不符就不發出下載請求，只記錄 `binding_mismatch`。
- 遠端 tombstone 不會讓新裝置產生 Key。

替代方案（把「遠端有列但本機無列」直接寫進決策表）會讓純函式同時依賴遠端集合與本機是否存在，較難測試，故未採用。

## D2. F2 用「增量提交 + 指紋守衛」，而不是讓所有寫入共用一把非同步鎖

`updateAIProfile()` 是同步的讀改寫（localStorage 單執行緒），因此：

- 同步只在記憶體副本上作業，提交時用 `updateAIProfile()` 重新讀取最新 profile，僅寫入本次真的改變的憑證列；
- 只有當該列的使用者欄位指紋與同步開始時相同才寫入，否則保留使用者較新的狀態；
- 供應商定義與 `taskModels` 完全不由同步寫入。

沒有把 UI 寫入也改成 async/Web Locks 佇列，原因：會影響 `saveTaskModelSelection()` 等同步呼叫端與既有模組邊界，風險大於收益。跨分頁仍由伺服器版本 CAS 阻止無聲覆蓋。

## D3. 「確認過的版本」只推進自本次同步確認的 mutation

若使用者在同步等待期間又改了一次 Key／刪除供應商，本次同步完成時會把它自己先前那個 mutation 的版本寫入本地；此時把使用者新 `pending` 的 `expectedVersion` 接到剛確認的版本（`advanceConfirmedBase()`），避免馬上出現一個只因「自己剛上傳成功」而產生的假衝突。

限制：只在使用者新 `pending.expectedVersion` 等於舊 `pending.expectedVersion`，且本次同步清空了 `pending`、沒有 conflict 時才推進。別台裝置造成的遠端變更永遠不會被這樣推進，仍走原方案的衝突介面（雲端／本機／稍後）。

## D4. 管理員新增供應商不自動複製個人金鑰

「從我的供應商預填」只帶入服務地址、協議與模型候選，金鑰需重新輸入。理由：把個人 Key 發布成共享 Key 是會讓所有已登入使用者取得該 Key 的行為，必須是明確操作；同時保留「個人供應商不被管理員介面改動」的邊界。

同理，連接成功後的模型一律預設不勾選（即使是單一模型），由管理員逐項確認後才加入草稿；這比「單一模型自動勾選」多一次點擊，但符合「不能把探索到的所有模型直接全站開放」。

## D5. 401／帳戶切換以「工作階段四元組」判定

舊帳戶的延遲回應必須被丟棄，因此以 `(sync endpoint, userId, token, auth generation)` 四項一起比對（`captureAuthSession()` / `isAuthSessionCurrent()`），而不是只看 generation：

- generation 只在登入／登出／換通行碼／帳戶切換時遞增，單看它無法覆蓋「endpoint 設定被改」；
- token 比對可涵蓋同帳戶換通行碼的情況；
- 只有四項都相同時，401／403 才允許改動目前工作階段。

`SESSION_INVALID` 仍保留 user id（讓帳戶 profile 的個人 Key 可用），`SIGNED_OUT` 才清除帳戶 profile；這與先前的 D3 決策一致。

## D6. 部署指南：先清理靜態產物、再發布，且不建議封鎖整個 `ai-config.js`

指南修正為「受控環境清理 → 可執行檢查（`scripts/check-ai-static-config.mjs` 必須 exit 0）→ 才部署前端 → 再撤銷舊 Key」。同時明確寫出前端仍以 ESM 靜態匯入 `ai-config.js`，整檔封鎖會讓應用無法啟動，因此只能確保該檔不含 AI 設定，或改為部署時產生／伺服器注入（需程式修改與回歸）。
