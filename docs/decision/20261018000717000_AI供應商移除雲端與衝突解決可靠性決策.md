# AI 供應商：移除雲端副本、衝突解決與靜態檢查器的可靠性決策

日期：2026-10-18。對應報告：[20261018000717000_AI供應商二次複驗三項問題修正與回歸驗證報告](../report/20261018000717000_AI供應商二次複驗三項問題修正與回歸驗證報告.md)。本決策承接 [20261017220515650_AI供應商六項修正落地決策](20261017220515650_AI供應商六項修正落地決策.md)，處理獨立複驗提出的 R1／R2／R3。

## D1：delete mutation 必須自帶「保留本機副本」意圖

- 決策：憑證列的 pending delete 增加 `keepLocalKey`，由發起操作寫入（`remove-cloud` → `true`；刪除供應商／清空 Key → `false`），並在 `confirm-pending`、`delete-ok`、`delete-not-found` 三條確認路徑一律依此決定是否清空 `apiKey`。
- 理由：原本只用「有沒有 pending delete」判斷，無法區分「只刪雲端副本」與「刪除供應商」，導致使用者按下「移除雲端副本，保留此裝置」後本機 Key 被自己的刪除標記清掉（違反原方案第 9 節）。意圖必須隨 mutation 持久化，才能在回應遺失、404、tombstone 等分支保持一致語意。
- 邊界：**沒有本機 pending 的遠端 tombstone**（別台裝置刪除、或本機 profile 已重建）維持原語意——清空本機 Key 並轉 `local-only`；寧可保守也不要讓已撤銷的雲端 Key 在本機復活。
- 附帶：`bindingVerified` 只在一把 Key 經 PUT 成功上傳後才設為 `true`；DELETE 成功不再順帶標記「已驗證」，避免 `binding_mismatch` 狀態被刪除動作抹掉。

## D2：手動衝突解決與一般同步採同等保護

- 決策：`resolveCredentialConflict()` 視為一般異步同步任務處理：
  1. 進入時捕獲 `captureAuthSession()`（endpoint／userId／token／sessionGeneration）、profile scope key，以及 `conflictBaseline()`（憑證指紋＋version＋syncMode＋衝突列身分）。
  2. `await` 下載後，四項皆需相符才可能提交；任一不符即回傳 `false` 且不寫入（不改 scope、不復活舊 scope、不清新 pending）。
  3. 真正寫入用 `updateAIProfile()` 內的條件寫入再比對一次基線。
  4. 另加資料校驗：回傳版本低於衝突版本 → `conflict_download_stale`；回傳 binding 與目前供應商定義不符 → `binding_mismatch`（不儲存 Key）。
- 理由：一般同步已有指紋合併保護，手動衝突解決卻盲寫；而它是唯一「按鈕 → 網路 → 寫入」的使用者操作，正是最容易被較新本機編輯夾殺的路徑。
- 取捨：過時結果回傳 `false` 而非拋錯，讓呼叫端能區分「使用者自己已改動」與真正失敗；UI 目前僅重新渲染、不加提示，避免在使用者剛存檔時誤報衝突。

## D3：靜態檢查器 fail-closed，未檢查不等於乾淨

- 決策：`scripts/check-ai-static-config.mjs` 的結束碼固定為 0＝實際掃描且無發現、1＝有發現、2＝掃描未完成（目標不存在／不是目錄／不可讀／stdin 為空／目錄內 0 個符合條件的檔案／讀檔失敗）。同時支援 `--stdin`（等價 `--dir -`、`--dir /dev/stdin`）真正讀取管道內容。
- 理由：把 `curl` 輸出接到 `--dir /dev/stdin` 時 `readdir` 失敗被靜默忽略，工具回報 exit 0，等於用成功碼掩蓋「一個位元組都沒檢查」。
- 指南處理：第 7.2 節改為「`mktemp -d` → `curl -fsS -o "$tmp/ai-config.js"` → `--dir "$tmp"` → 清理」，`-f` 讓 HTTP 錯誤直接失敗；另附 `--stdin --name ai-config.js` 版本。兩者都只在 exit 0 時算通過。
- 不變：檢查器仍只輸出檔名／行號／問題類型，不輸出任何值；它仍不是秘密掃描器，也不能取代在供應商控制台撤銷舊 Key。
