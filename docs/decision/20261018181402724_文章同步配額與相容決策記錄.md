## 1. 決策 1：保留上一版分析結果（已定案）

### 決議

- **預設不保留**完整舊結果；每筆記錄只增加：
  - `analysisCount`（分析次數）；
  - `revisions`（最多 5 筆 metadata：`{ at, fingerprint, chars }`）。
- 閱讀記錄只顯示「更新於 X · 分析 3 次」，不提供「還原上一版」按鈕。
- Phase 3（索引 + blob）完成後，提供可選設定 `reading.keepArticlePreviousResult`：
  - 開啟後只保留 **1 份**上一版完整結果；
  - 以獨立 blob 儲存（內容尋址），不塞回記錄本體；
  - 容量面板明確顯示額外佔用；
  - 仍不提供多版本分支，只提供「回到上一版」。

### 理由

1. 使用者的核心痛點是「同一篇變成很多篇」，不是「要保留歷史譯文」。身份修好之後，多數人不需要舊結果。
2. 完整舊結果會讓單篇體積翻倍。以 1.8k 字文章為例，v2 已是 8 KB，再存一份就是 16 KB；500 篇會多出 4 MB。
3. 版本還原需要清楚的 UI（選擇版本、預覽、覆蓋確認），成本高於收益；先做 metadata，保留未來擴充空間。
4. 若真的誤覆蓋，Phase 3 之前仍可從本機備份或雲端快照歷史找回；Phase 3 之後可加「上一版」單一步驟。

### 開啟後的資料流（Phase 3+）

```text
index entry:
  { articleId, docHash, previousDocHash?, ... }

blob store:
  docs[docHash]         = { article, result }   // 最新
  docs[previousDocHash] = { article, result }   // 上一版（可選）
```

- 重新分析且內文有變更時，舊 `docHash` 寫入 `previousDocHash`；
- GC 時 `previousDocHash` 視為被引用，不會被清掉；
- 使用者按「回到上一版」＝把 `previousDocHash` 與 `docHash` 互換，重新渲染；
- 只保留一層，不支援多層版本樹。

## 2. 決策 2：相似文章判定門檻（已定案，含一處修正）

### 決議

- **完全相同的 fingerprint**：不詢問，直接更新原記錄。
- 其餘情況依序檢查：

| 條件 | 門檻 | 說明 |
| --- | --- | --- |
| SimHash 距離 | ≤ 6（64-bit） | 快速篩選；距離越小越相似 |
| 長度比 | 0.7–1.4 | 避免拿短摘錄去比長文 |
| 逐句 Jaccard | ≥ 0.6 | **原本寫逐段，改成逐句**；段落被合併／拆開時仍能命中 |
| 最短重疊 | 至少 5 句或 300 字元 | 太短的文章不提示，避免誤判 |

- 短文章（少於 5 句或 300 字元）：改用更嚴格門檻：
  - SimHash 距離 ≤ 3；
  - 長度比 0.8–1.25；
  - 逐句 Jaccard ≥ 0.8；
  - 否則一律視為新文章。
- 中文為主的文章（CJK 比例 > 0.3）：SimHash 改用「字元 2-gram」而不是英文 3-gram；逐句 Jaccard 不變。
- 顯示給使用者的相似度用逐句 Jaccard，上限顯示 99%；不要顯示 SimHash 距離（一般人看不懂）。

### 為什麼從「逐段」改成「逐句」

段落 Jaccard 對「重新排版」非常敏感：使用者把兩段合併、或把一段拆成兩段，段落 hash 全變，Jaccard 會掉到 0，於是明明只改幾個字卻判定為新文章。句子通常不會因為排版而改變，逐句集合更穩定。

### 誤判與漏判的取捨

- **漏判**（應該是同一篇卻沒提示）：使用者選「另存新篇」就好，成本低。
- **誤判**（不同文章卻提示）：多一次詢問，成本也低；真正的風險是「自動合併」，所以我們**永遠不自動合併**。
- 因此門檻可以稍微寬鬆；但短文章必須嚴格，因為 3 句短文很容易被距離 6 誤判。

### 校準方式

建立 `tests/fixtures/article-similarity/`，至少包含：

1. 原文 vs 修正 1 個錯字 → 應提示；
2. 原文 vs 新增 1 段 → 應提示；
3. 原文 vs 刪除 1 段 → 應提示；
4. 原文 vs 把 3 段合併成 1 段（文字不變）→ 應提示；
5. 原文 vs 同模板但不同內容的新聞簡訊（3 則）→ **不應**提示；
6. 原文 vs 完全不同的文章（同長度）→ 不應提示；
7. 中文原文 vs 中文改寫 → 依 CJK 規則測試；
8. 超短文章（3 句）vs 另一篇 3 句 → 不應提示。

每次調整門檻都跑這組 fixture；門檻常數集中在 `modules/article-identity.js`，不要散在 UI。

## 3. 決策 3：單使用者 blob 配額與 GC

### 3.1 配額要解決什麼

1. **防止病理成長**：重複分析、舊版本、失敗重試都可能留下 blob；沒有上限時，單一使用者可以無限佔用 D1／自建庫。
2. **成本可預期**：D1 免費額度與自架磁碟都有限；50 MB × 使用者數是可控上限。
3. **提早回饋**：與其讓使用者同步到一半收到 413，不如在上傳前就告訴他「還剩多少」。
4. **配額只算文章 blob**：快照索引、詞書、問答、助手不計入，避免容量算法複雜化。

### 3.2 50 MB 的推導

以 v2 結果結構、逐句模式、中文長度約英文 55% 估算（UTF-8 bytes）：

| 單篇原文 | v2 記錄大小 | 500 篇合計 | 50 MB 可容納 |
| --- | ---: | ---: | ---: |
| 1.8k 字元 | 8 KB | 4 MB | 約 6,400 篇（受篇數上限限制） |
| 6k 字元 | 27 KB | 13 MB | 約 1,880 篇 |
| 20k 字元 | 88 KB | 44 MB | 約 580 篇 |
| 50k 字元 | 218 KB | 109 MB | 約 235 篇 |
| 100k 字元 | 436 KB | 218 MB | 約 117 篇 |
| 200k 字元 | 872 KB | 436 MB | 約 58 篇 |

（以上為 ASCII 英文 + 中文譯文的估算；實際會因標點、JSON、模型輸出長度而異。）

解讀：

- 若使用者是「學習文章」型（多數 2k–6k 字），50 MB 可放數百到上千篇，遠超篇數上限。
- 若使用者大量匯入 20k–50k 長文，50 MB 會先於篇數上限觸發；這是合理的，因為長文的分析成本也高。
- 50 MB 也讓 D1 免費 5 GB 理論上可容納約 100 個「用滿」的使用者；自架則只受磁碟限制。
- 若多為 100k 以上的長文，50 MB 只夠約 117 篇；此時應該用單篇上限（見決策 4）而不是放寬配額。

### 3.3 為什麼單 blob 上限是 900 KB

| 單篇 | v2 blob | 900 KB 是否足夠 |
| --- | ---: | --- |
| 20k 字元 | 88 KB | 是 |
| 50k 字元 | 218 KB | 是 |
| 100k 字元 | 436 KB | 是（約 2 倍餘量） |
| 200k 字元 | 872 KB | 勉強，且中文比例高或標註多時會超過 |

- 900 KB 讓單次請求、單列資料、重試單位保持在可控範圍，同時避開 D1 單列 1 MB 的 overhead（**實作前需再確認 D1 單列上限**）。
- 配合單篇 100k 硬上限，本文＋結果最大約 0.5 MB；但 `sentence_analysis`／`phrase_analysis` 沒有全域上限，長文大量標註可累積數 MB，因此另訂：
  - `sentence_analysis` 最多 300 筆；
  - `phrase_analysis` 最多 300 筆；
  - 兩者序列化合計 ≤ 256 KB；
  - 單篇文件（article + result）硬上限 800 KB；
  - 超過時阻止新增標註並提示清理或分段。
- 批次上傳時限制「單批最多 10 個、總量 4 MB」，避免請求 body 過大（`/blobs` 的 `readJson` 上限可放寬到 4 MB）。

### 3.4 GC 30 天的理由

blob 是內容尋址的；只要快照索引還引用它，就不能刪。會被刪的只有「已經沒有被目前快照引用」的 blob。

30 天的用途：

1. **離線裝置**：手機兩三週沒開，回來後仍可能推送舊索引；30 天足夠覆蓋一般使用。
2. **誤刪救援**：使用者刪掉文章後 30 天內，雲端 blob 還在，可透過備份或管理工具救回。
3. **避免頻繁讀寫**：每天掃一次即可；不需要每次 push 都 GC。
4. **成本可控**：即使完全不清，50 MB／使用者的配額已經封頂；GC 主要是回收 churn（重複分析、刪除）。

太短的風險：7 天對長假、出差、舊手機不友善；太長的缺點：未引用 blob 佔用配額最長 90 天，使用者可能提早撞配額。30 天是折衷。

### 3.5 機制

```text
快照 push
  → 解析 payload.articles.index[].docHash
  → 若 index 引用了不存在的 blob → 409 missing_blobs（附 hash 清單）
  → 不逐筆更新 last_seen_at（避免 D1 寫入放大）

每日 GC（Worker cron / selfhost setInterval）
  → 讀目前快照 index 的 hash 集合
  → DELETE FROM article_blobs
    WHERE user_id = ?
      AND created_at < now - 30d
      AND hash NOT IN (目前 index 的 hash)
```

- **配額計算**：`SELECT SUM(bytes) FROM article_blobs WHERE user_id = ?`；上傳前檢查，超過回 `413 quota_exceeded` 並附 `{ used, limit }`。
- **未引用 blob 也計入配額**：簡單且保守；代價是使用者刪文後 30 天內仍佔空間。提供「立即清理未引用」動作（刪除目前快照未引用、且建立超過 24 小時的 blob），讓使用者可主動釋放。
- **idempotent**：相同 hash 重複上傳不重複計費；若內容相同但大小不同（不應發生）以既有為準。
- **缺失保護**：離線裝置推送舊索引時，伺服器檢查 index 的 hash 是否存在；缺失就要求先上傳，避免「索引有、內容沒有」。若該裝置本機也沒有文件（已清快取），則拒絕該筆索引並提示重新分析。

### 3.6 可調參數

| 參數 | 預設 | 環境變數（建議） |
| --- | --- | --- |
| 單使用者 blob 配額 | 50 MB | `MAX_ARTICLE_BYTES_PER_USER` |
| 單 blob 上限 | 900 KB | `MAX_ARTICLE_BLOB_BYTES` |
| 單篇文件上限 | 800 KB | `MAX_ARTICLE_DOC_BYTES` |
| 句子標註上限 | 300 筆 / 256 KB | `MAX_SENTENCE_ANALYSIS` |
| 片語標註上限 | 300 筆 / 256 KB | `MAX_PHRASE_ANALYSIS` |
| 單批上傳上限 | 10 個 / 4 MB | `MAX_ARTICLE_BLOB_BATCH` |
| GC 保留天數 | 30 天 | `ARTICLE_BLOB_GC_DAYS` |
| 立即清理門檻 | 24 小時 | `ARTICLE_BLOB_MIN_AGE_HOURS` |

自架環境可視磁碟調整；Cloudflare Worker 用 `vars`／`secrets` 設定。

## 4. 決策 4：文章篇數與單篇長度上限

### 4.1 篇數上限

索引化之後，篇數本身不再是技術瓶頸：

| 篇數 | 索引大小（約 250 B/篇） | localStorage | 清單效能 |
| --- | ---: | --- | --- |
| 100 | 25 KB | 無壓力 | 即時 |
| 500 | 125 KB | 無壓力 | 即時；搜尋需建立索引 |
| 1,000 | 250 KB | 無壓力 | 需虛擬列表／分批渲染 |
| 5,000 | 1.25 MB | 開始有壓力 | 必須虛擬列表與全文索引 |

建議：

- **軟警示 400 篇**：提示「文章較多，建議清理或使用搜尋」；
- **硬上限 1,000 篇**：超過時拒絕新增分析，要求先刪除或匯出；
- **真正的限制是 50 MB 配額**：1,000 篇 20k 字文章約 88 MB，會先撞配額；這時提示「容量已滿」而不是「篇數已滿」。
- 為什麼不是 500 硬上限：500 對一般使用者足夠，但對「每天匯入新聞」的使用者可能一年就到；1,000 搭配配額更合理，且索引仍很小。
- 若不想做虛擬列表，500 硬上限也可以；差別只是重度使用者的體驗。

### 4.2 單篇長度上限

先看成本（以每段 3 句、concurrency 3、每次請求平均 5 秒估算）：

| 原文長度 | 句數（約） | 段落／請求數（約） | 預估分析時間 | v2 blob |
| --- | ---: | ---: | ---: | ---: |
| 20k 字元 | 223 | 75 | 約 2 分鐘 | 88 KB |
| 50k 字元 | 553 | 185 | 約 5 分鐘 | 218 KB |
| 100k 字元 | 1,105 | 369 | 約 10 分鐘 | 436 KB |
| 200k 字元 | 2,217 | 739 | 約 20 分鐘 | 872 KB |

（實際時間受模型、網路、失敗重試影響，可能更長；費用隨 token 線性增加。）

建議：

- **警示 20k 字元**：提示「文章較長，分析可能需要數分鐘」；
- **硬上限 100k 字元**：超過時不送分析，提示「請分成兩篇」；
- **不建議 200k**：
  - 739 次 AI 請求，任何一次失敗都要重試；
  - 20 分鐘以上的等待，使用者體驗很差；
  - blob 接近 900 KB 上限，中文比例高或標註多時可能超過；
  - 助手上下文也會過長。
- 若真的需要分析長文，正確做法是「分段匯入」而不是放寬單篇上限；未來可做「長文自動分段＋合併」功能。

其他相關限制：

- 助手注入的文章上下文建議截斷到 12k 字元（或最後 N 段），避免模型 context 爆掉；這與分析上限分開。
- 單篇超過 20k 時，分析前顯示預估時間與「可先存檔」提示。

### 4.3 可調參數

| 參數 | 預設 | 說明 |
| --- | --- | --- |
| 篇數軟警示 | 400 | 只提示 |
| 篇數硬上限 | 1,000 | 阻止新增分析 |
| 單篇警示 | 20k 字元 | 提示時間 |
| 單篇硬上限 | 100k 字元 | 阻止送分析 |

## 5. 決策 5：舊客戶端相容策略

### 5.1 先看風險

Phase 3 之後，快照的 `articles` 從「完整 `analyzedArticles`」變成「索引 + blob」。舊版前端（已開著的分頁、快取較久的裝置）會遇到：

1. `applyArticlesPayload` 看到沒有 `analyzedArticles` → 直接跳過，**不會清空本機文章**；
2. 但舊版下一次 push 會把本機完整文章陣列塞回快照；
3. 若伺服器接受，新版的索引會被舊格式覆蓋，blob 也失去引用 → **降級與資料錯亂**。

所以不能「什麼都不做」。

### 5.2 方案比較

| 方案 | 做法 | 舊裝置 | 新裝置 | 伺服器工程 | 風險 |
| --- | --- | --- | --- | --- | --- |
| A. 硬性版本閘門（推薦） | 快照標記 `schema 2`；舊格式 push 回 `409 client_upgrade_required` | 同步失敗，需重新載入／更新 | 正常 | 小 | 舊裝置停止同步，直到更新 |
| B. 伺服器端相容代理 | 伺服器存索引＋blob；舊格式 GET 時組回完整 `analyzedArticles`；舊格式 POST 自動拆成索引＋blob | 可繼續用 | 正常 | 中大（+2–3 天） | 伺服器 CPU／讀取量增加；兩套格式長期維護 |
| C. 雙寫過渡期 | 新前端同時推索引與完整 `analyzedArticles` | 可繼續用 | 正常，但**沒有頻寬收益** | 小 | 兩份資料可能不一致；過渡期結束仍要處理舊裝置 |
| D. 不設閘門 | 伺服器照收舊格式 | 可繼續用 | 被降級覆蓋 | 無 | **不可接受** |

### 5.3 推薦：A + 7 天回滾開關

實作：

1. 快照 payload 增加 `articles.schema: 2`；伺服器在 `snapshots` 或 payload 內記錄目前 schema。
2. 前端 push 帶 `X-BDC-Sync-Schema: 2`。
3. 伺服器若已存 schema 2，收到 schema 1 且含 `payload.articles.analyzedArticles`：
   - 回 `409 client_upgrade_required`；
   - body 附 `{ currentSchema: 2, minClient: '2026.10' }`；
   - 不寫入任何資料。
4. 舊前端會顯示「同步失敗：client_upgrade_required」；使用者重新載入頁面即取得新前端（本專案沒有 Service Worker，不會卡在舊版）。
5. 新前端在同步面板顯示目前 schema 與「所有裝置需更新」提示。
6. 伺服器保留環境變數 `ARTICLES_SCHEMA_MODE=1|2`：
   - 上線後 7 天內可切回 `1` 允許舊格式（降級）；
   - 7 天後移除舊分支。

上線步驟：

1. 先在測試環境用舊快照跑遷移，確認 blob 數與文章數一致；
2. 發布前端與 Worker／selfhost；
3. 所有裝置重新載入；
4. 確認 `/usage` 與同步版本正常；
5. 7 天後關閉 schema 1 分支。

為什麼可以接受「舊裝置暫停同步」：

- 這是個人專案，裝置數量少且由使用者控制；
- 不同步不會丟本機資料，只是雲端暫時不更新；
- 比起長期維護兩套格式，硬閘門的總風險更低；
- 有 7 天回滾開關，真的出問題可切回舊模式。

### 5.4 什麼情況下選 B

只有在以下情況才值得做伺服器端相容代理：

- 使用者無法要求所有裝置同時更新（例如家人共用、多台舊手機）；
- 不能接受任何一台上線後暫時停止同步；
- 願意多花 2–3 天實作與長期維護兩套格式。

B 的實作要點（若要做）：

- 伺服器需要 SHA-256（Worker `crypto.subtle`、Node `node:crypto`）；
- 舊格式 POST：解析 `analyzedArticles` → 逐篇寫 blob + 建索引 → 更新快照；
- 舊格式 GET（依 `X-BDC-Sync-Schema: 1` 或缺少 header 判斷）：讀索引 → 批次讀 blob → 組回 `analyzedArticles` → 回傳；
- 成本：每次舊裝置 GET 要讀取全部文章 blob（D1 rows read），500 篇會很重；只適合過渡期。

### 5.5 決議

- **已定案採用 A**：硬性版本閘門 + 7 天回滾開關 + 明確的發布檢查清單。
- 若之後發現有無法即時更新的裝置，再評估 B，而不是預先做 C（雙寫只會延後問題）。
- **部署順序注意**：伺服器只有在收到第一個 schema 2 push 後才會進入閘門；在那之前舊裝置仍可 push。發布時要同時要求所有裝置重新載入，並在 release note 寫明。

## 7. 驗收與監控

1. 上傳超過 50 MB：回 `413 quota_exceeded`，前端顯示已用／上限與清理入口。
2. 單篇 100k 字元：可分析、可同步；110k：被阻止並提示分段。
3. 第 1,001 篇：被阻止；第 401 篇：只警示。
4. GC 測試：未引用 blob 30 天後刪除；被引用 blob 即使超過 30 天仍保留。
5. 離線裝置推送引用已 GC blob 的索引：回 `409 missing_blobs`，補傳後成功。
6. 舊版前端 push：回 `409 client_upgrade_required`；切回 schema 1 模式可通過；新版資料不被覆蓋。
7. `/usage` 回傳的數字與實際 blob 總和一致。
8. 日誌只記 hash、bytes、user_id，不記文章內容。

## 8. 已定案與實作前驗證

已定案：50 MB、單 blob 900 KB、GC 30 天、400/1,000 篇、20k/100k 字元、硬性 409 閘門。

實作前仍需驗證（不改變決策方向）：

1. D1 單列上限是否確實為 1 MB；若是，900 KB 是否留足 overhead（必要時降到 768 KB 或分塊）。
2. 手動備份／匯出的檔案格式與大小上限（含 docs、gzip）。
3. 舊客戶端閘門的部署順序與 7 天回滾窗口。
4. 若常分析 100k 以上長文，是否改成「分段匯入」而不是放寬上限。

## 9. 評審後追加修正（2026-10-18 18:28）

完整評審見 `docs/report/20261018182830456_文章身份與同步方案評審.md`。以下修正不改變 1–5 的決策方向，但屬於實作前必須納入的範圍：

1. **備份／還原／匯出必須包含 docs**：Phase 3 後快照只有索引；自動備份可只存索引，但手動備份與匯出必須帶文章本文與結果，否則還原後只有清單。格式升版為 `{ format: 2, payload, docs }`，舊格式仍可讀；匯出建議 gzip。
2. **啟動不要下載全部文章**：採「索引常駐、文件快取」；啟動只載入 IndexedDB 已有的 docs，其餘背景下載，開啟文章時單篇 fetch。不要在 `main.js` 阻塞 500 次請求。
3. **tombstone 提前到 Phase 3**：刪除要寫 tombstone（保留 180 天），index 逐項合併；否則離線裝置會把已刪文章復活，或引用已被 GC 的 blob。
4. **合併重複記錄時保留 meta 或改指向 canonical id**：若被合併的 articleId 仍有生詞本，直接刪 meta 會讓詞書的「回到文章」失效。
5. **LAN HTTP 的 hash fallback**：`crypto.subtle` 在 `http://192.168.x.x` 不可用；`docHash` 需有同步的 128-bit fallback，不能退回 32-bit 快取雜湊。
6. **標註上限**：`sentence_analysis`／`phrase_analysis` 各 300 筆、合計 ≤ 256 KB、單篇文件 ≤ 800 KB；否則 1 MB 以下的 blob 上限會被長文標註撐破。
7. **GC 不逐筆更新 `last_seen_at`**：改讀目前 index＋`created_at`，避免每次 push 數百次 UPDATE。
8. **`isLikelyAccidentalWipe` 要認 `articles.index`**：否則 schema 2 下偵測不到本機被清空。
9. **歷史清單不要重新解析全文**：儲存時就寫 `title`／`summary`／`chars`；1,000 篇需虛擬列表。
10. **重新分析要處理既有逐句／片語筆記**：目前 `finalResult` 會把它們丟掉；要合併或明確警告。
