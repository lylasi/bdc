# AI 供應商設定落地偏差決策

- 對應方案：`docs/plan/20261017130932086_D1按使用者同步AI供應商設定完整方案.md`
- 實作報告：`docs/report/20261017174843744_按使用者同步AI供應商設定實作報告.md`
- 日期：2026-10-17

本文件記錄實作時與原方案文字的必要調整。所有調整都保留原需求目標：local-first、瀏覽器直連、預設供應商登入限定、個人供應商完整可用、Key 不進普通 snapshot。

## D1. 模組拆分

原方案列出的檔案以較粗粒度描述（例如把供應商 UI 放在 `features/sync/sync.js`）。實作拆分為：

- `features/sync/ai-provider-settings.js`：供應商設定區塊（由 `sync.js` mount）。
- `features/ai-admin/ai-admin.js`：管理員覆蓋層。
- `modules/ai-settings-sanitize.js`：前後端共用的快照白名單規則（前端用；Worker 另有一份 `snapshot-sanitize.js`）。
- `cloudflare-worker/src/http.js`、`snapshot-sanitize.js`。

原因：`sync.js` 已超過 1600 行；拆分可獨立測試與清理生命週期。`sync.js` 仍是唯一初始化入口。

## D2. 同步解析 API 分成同步與非同步版本

`getProviderConnection`／`resolveAIRequestConfig` 保持同步，供 UI、快取鍵與可用性檢查使用；新增 `resolveAIRequestConfigAsync` 由 `requestAI`／`streamAIResponse` 使用，按需下載 managed 共享 Key。

原因：共享 Key 必須按需取得，而既有呼叫端（OCR、QA、文章）大量使用同步解析；強制全部改 async 會擴大風險。同步版本絕不回傳未下載的 shared Key。

## D3. 401 的處理

方案要求「同步 401 保留個人 Key、清除共享 Key」。實作把 `auth.invalidateSession()` 與明確 `signOut()` 分開：

- `SESSION_INVALID`：移除登入 token 與角色，但**保留 user id**，讓帳戶 profile（個人供應商與 Key）繼續可用；共享 Key、預設列表可用狀態立即清除。
- `SIGNED_OUT`：使用者明確退出，清除該帳戶 AI profile、共享 Key、列表快取與管理草稿。

原因：若 401 同時移除 user id，個人供應商會因 profile 範圍切到訪客而不可用，違反「個人供應商不逐次驗證登入」。保留 user id 只是本機 profile 範圍，不代表登入有效；所有雲端請求仍需 token。

## D4. 無認證供應商不建立憑證列

沒有 Key 的供應商只在普通設定／snapshot 保存 binding，不呼叫 `/ai-credentials`，也不建立空 Key 記錄。伺服器對 `authMode: 'none'` 的 PUT 回 `400 key_not_required`。

原因：符合「不建立空 Key 記錄、不發送空白 Authorization」。

## D5. 個人任務設定的匯入

除了供應商與 Key，`importGuestProviders()` 也會匯入尚未在帳戶設定的任務選擇與個人預設（僅當引用的供應商已存在於帳戶）。這是對方案「登入後明確匯入」的延伸，避免使用者匯入後仍要重設所有任務。

## D6. 快取隔離加入 `keyStamp`

方案要求模型列表快取包含帳戶／供應商／端點／憑證版本。實作額外加入非秘密的 `keyStamp`（每次換 Key 更新），用於 `local-only` Key 更換但同步版本不變的情況。

## D7. Gemini 模型 URL 佔位符

原生 Gemini 的生成 URL 含模型名稱。binding 需要保存可比較的端點，因此使用 `%7Bmodel%7D:generateContent` 佔位符（URL 正規化不會破壞），請求時再替換。Anthropic／Chat Completions 的模型在 body，不受影響。

## D8. 發布事件與 Key 操作

- 管理員發布採用整份列表 + 明確 `keyOps`（preserve/replace/clear），伺服器不信任任何客戶端密文信封。
- `preserve` 在端點改變時回 `400 binding_changed_requires_key`；`clear` 只能在供應商停用時執行。
- 發布摘要使用獨立 `AI_CATALOG_DIGEST_KEY` HMAC，含操作者、baseVersion、設定與 Key 操作。

## D9. 靜態設定遷移

方案要求移除 `ai-config.js` 的 AI 預設。基於「不讀出／輸出秘密、不提交秘密」的約束，本次**沒有直接改寫**使用者私有 `ai-config.js`，而是提供：

- `scripts/migrate-ai-config.mjs`：安全地產生網站根目錄外的私密匯入 JSON 與備份，再把 `ai-config.js` 改寫為只含非 AI 設定；不列印任何 Key。
- 管理員 UI 的「匯入舊版 ai-config.js」：由管理員明確選擇 JSON 後才載入草稿。

原因：自動改寫使用者的本機秘密檔風險過高；部署者需要先確認 TTS／同步等非 AI 設定仍正確，並在供應商端撤銷舊 Key。

## D10. 伺服器端 snapshot 過濾

原方案只描述客戶端與服務端都要排除偽造 managed 定義。實作在 Worker 的 snapshot 讀寫都套用白名單（`snapshot-sanitize.js`），確保舊資料或惡意客戶端都無法把 Key／managed 定義／任務層覆寫存入並回傳。

## D11. 限流

Worker 限流為單 isolate 記憶體滑動視窗，用於降低暴力嘗試與濫用；不是全域配額。方案要求的供應商端限額仍需在供應商控制台設定。

## D12. 介面文案

- 逐任務選擇標題改為「按功能指定模型」（原本的「AI Task → 模型映射」屬技術語言）。
- 無可用供應商時，模型下拉顯示「提示：請先在『我的供應商』新增供應商」並保持停用，而不是空白下拉。
- 既有 `ai-config.js` 的 `AI_PROMPTS`／`EMAIL` 未被任何模組引用；遷移腳本不保留（提示詞已集中在 `modules/prompts/`）。
