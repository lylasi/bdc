# 文章私人直達與刷新恢復範圍

日期：2026-10-28（Asia/Shanghai）。狀態：已實作，19 個文章導航與草稿恢復場景通過。

## 已確認決策

使用者選擇 A：自己的文章可以透過文章 ID 網址直接訪問，支援書籤及同一同步服務、同一帳戶的跨裝置開啟。此次同時討論解決「刷新文章詳解後需要重選文章」的體驗。

原始[架構核對](../research/20261028011154625_文章ID直達網址架構核對.md)已確認穩定 ID、單篇儲存及私人單篇 API 都已存在，欠缺前端 URL 與恢復流程。

## 已確認的折中方案

以 URL 的文章 ID 決定是否自動開篇；普通入口提供續讀選擇。

| 場景 | 建議行為 |
| --- | --- |
| 開啟或切換已保存文章 | 自動把該篇 ID 寫入 URL，例如 `/#a/<articleId>`，使用者毋須手動輸入 |
| 在該篇按刷新 | 依 URL 自動恢復同篇已保存原文及詳解 |
| 使用書籤或在其他裝置開啟帶 ID 網址 | 在相同服務與帳戶下開篇；本機沒有時補讀遠端或等待必要同步 |
| 直接進入普通文章入口 `/#a` | 顯示「繼續閱讀〈上次文章標題〉」入口，同時保留選文及匯入能力；不強制跳轉 |
| URL 指定的文章已刪除、無權限或離線且本機無文 | 提供對應狀態與選文／重試入口，不把另一篇當成指定文章 |

URL 指定文章的優先級高於最近閱讀記錄。最近閱讀只作目前裝置、目前帳戶的便捷入口，不改變跨裝置 ID 直達的契約。

恢復既有文章表示載入已保存內容；持續執行 AI 工作、音訊播放、精確捲動位置等不會由「恢復文章身份」自動成立，若需要須另外界定。

## 現有機制與實作邊界

- `touchOpened()` 已保存本機 `lastOpenedAt`，不改文章 revision 或觸發同步，可供最近閱讀入口使用；見 [article-store.js](../../modules/article-store.js:2011)。同時，建立及遠端套用資料也可能帶入時間，不能僅憑欄位名就保證它等於最後實際閱讀的文章。
- 若入口文案承諾「上次閱讀」，應明確保存目前裝置、目前 scope 的最後開啟文章 ID，或調整遠端套用時對本機閱讀時間的保留；不能只把依現有時間排序的第一篇當成準確答案。該 ID 只作恢復指標，不複製文章全文，也不作跨帳戶身份。
- `currentDraftSnapshot()` 含正文、來源及 `recordId`；`recordHasUnsavedInput()` 可以辨別輸入是否與已保存正文不同；見 [article.js](../../features/article/article.js:3812)。
- 現有輸入事件只更新介面與版本提示，並非每次輸入都保存草稿；見 [article.js](../../features/article/article.js:584)。草稿主要由匯入／切篇／清除等流程寫入；見 [article.js](../../features/article/article.js:3830)。
- 草稿按同步端點及帳戶範圍保存，並有手動恢復入口；見 [article-store.js](../../modules/article-store.js:2034)、[article.js](../../features/article/article.js:4277)。這不等於刷新前的未保存輸入已獲保護。
- 每個 scope 現有草稿只有一筆，並非逐篇保存。現有手動恢復先呼叫 `applyImportedArticle()` 清掉目前 `recordId`，之後再用 `isCurrentArticle(latest.recordId)` 判定接回身份，依靜態流程該條件不能成立；若本輪納入草稿恢復，須連同原文章身份與覆蓋規則一起處理，不能直接宣稱沿用現有入口即可。

## 第二輪決策（已確認）

1. 普通文章入口：採用建議的「繼續閱讀」入口，還是自動打開上次文章？推薦前者；帶 ID 的網址仍然自動恢復指定文章。
2. 未保存的輸入：此次是否同時增加本機草稿自動保存與刷新恢復？推薦納入輕量本機草稿保護，恢復後明確保留「尚未保存／需更新詳解」狀態，不把草稿冒充已保存文章或新分析結果。保存與恢復範圍、覆蓋規則需依使用者選擇再細化。

使用者回覆「好的，就这样按建议实现」，確認普通入口提供續讀選擇，並納入本機草稿自動保存與刷新恢復。
