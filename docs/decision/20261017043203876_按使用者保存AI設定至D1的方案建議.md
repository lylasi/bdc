# 按使用者保存 AI 設定至 D1 的方案建議

## 結論

可以擴充現有 D1，毋須新增另一套資料庫或登入服務。若優先考慮少改動、跨裝置保存，以及雲端故障時已設定裝置仍可使用 AI，建議採用「D1 保存及同步、本機直接呼叫供應商」。這會保留本機金鑰，不屬於之前的 C 方案。若必要條件是金鑰不回傳瀏覽器，則採用 Worker 代呼叫，並接受 Worker / D1 是 AI 服務的依賴。

## 現有程式依據

- `cloudflare-worker/schema.sql` 已有 `users` 與按 `user_id` 保存的 `snapshots`。
- `modules/sync-core.js` 的 `sanitizeAISettings` 已同步供應商網址、名稱、模型及任務映射，但排除 API Key。
- `cloudflare-worker/src/worker.js` 的 `authenticate` 每次查詢 D1 驗證通行碼，目前沒有可離線驗證的短期登入憑證。
- 因此新增的重點是憑證同步、加密與使用者隔離，不是重新建構整套使用者系統。

## 建議的第一階段：D1 保存、本機使用

保留普通設定現有 snapshot 同步流程，另建 `user_ai_credentials` 表，避免同一份供應商設定出現兩套來源。

建議欄位：`user_id`、`provider_id`、`key_ciphertext`、`nonce`、`key_version`、`version`、`updated_at`；以 `(user_id, provider_id)` 作複合主鍵。

- 使用者身分由 Worker 驗證後取得，不接受前端指定任意使用者身分操作資料。
- Worker 使用獨立主密鑰加密 API Key 後存入 D1，主密鑰存 Worker Secret，不與密文放在同一資料表。採用經驗證的認證加密實作，例如 AES-GCM，隨機 nonce，並將使用者與供應商識別綁定為附加認證資料。
- 登入或明確同步時，Worker 解密並透過 HTTPS 將憑證交給已驗證的客戶端。此設計不是端對端加密，也不能阻止本機使用者或受入侵的頁面讀取本機金鑰。
- 本機保留可用設定，AI 請求直接傳到供應商，不逐次讀取 D1。雲端不可用時，已取得設定的裝置可繼續呼叫可達的供應商；新裝置登入、下載及設定變更同步會受影響。
- 憑證更新使用版本檢查；刪除必須明確同步，不能以空字串或登入失敗覆寫本機有效金鑰。退出或切換帳戶時隔離／清除該帳戶的本機憑證，避免跨帳戶沿用。
- 普通 snapshot 中的網址不可攜帶 `?key=...` 等憑證，否則會繞過密文保存設計。
- 直接呼叫供應商仍須滿足其 CORS 和瀏覽器網絡限制；D1 保存不會改變局域網可達性。

## 若堅持 C：Worker 代呼叫

流程為：瀏覽器 → 現有 Worker → 驗證使用者並讀取 D1 憑證 → 解密 → 對應供應商。

瀏覽器只取得供應商識別及「已設定」狀態，不取得 API Key。公網供應商可由 Worker 直接呼叫，毋須一律經過家中 magpie。純局域網端點無法因此直接被公網 Worker 存取，仍需額外連通方案或保留本機直連模式。

此模式除資料表和設定同步外，還須增加模型探索、AI 請求轉發、串流、取消、逾時及錯誤處理，改動量較大。依現有登入設計，D1 故障也會影響驗證；單純快取供應商設定不能消除此依賴。

## 故障邊界與改動範圍

供應商設定與錯誤狀態按使用者及供應商獨立處理。單一供應商失敗不應阻止其他供應商被選用，也不應阻塞詞書、文章等本地功能初始化。第一階段保留手動切換，毋須立即加入自動重試或自動跨供應商切換。

保存及同步模式主要涉及 D1 schema / migration、Worker 憑證 API、設定與 secrets 的本地管理、設定介面和雙語文案，AI 任務呼叫路徑原則上可沿用。屬小至中型改造，仍需驗證帳戶隔離、衝突、刪除、雲端離線及兩種介面語言。Worker 代呼叫屬中型改造，另須驗證串流和各功能的呼叫相容性。

## 官方參考

D1 已自動提供靜態資料加密，但這不會令獲授權 SQL 查詢無法讀取明文欄位，因此與應用層憑證加密是不同保護層。
