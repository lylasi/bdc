# 簡化 AI 接入與故障隔離建議

本建議修訂先前方案 C 的落地方式：保留服務端持有供應商金鑰的原則，取消 Worker、Access、專用 Tunnel 與 magpie 全部串聯為必經路徑的設計。目標是減少部署單元與隔離供應商故障，並非宣稱單機具備高可用。

## 建議架構

在現有 BDC 託管機上，以一個輕量 BDC 服務提供靜態前端與 /api/ai 接口，取代單純靜態檔案服務。瀏覽器使用同源 API。保留既有網站 HTTPS 入口，不為 AI 額外新增一套隧道與網域。

BDC 後端直接連 HAPI 等雲端供應商；magpie 作為可選供應商，與雲端供應商並列。只有 magpie 獨有的模型依賴家中 magpie；HAPI 不繞經 magpie。

同步服務獨立運作，AI 請求不逐次查詢雲端同步服務來驗證身份。後端可使用本地帳戶與可撤銷會話，使 AI 認證不依賴遠端 D1 的即時可用性。這需要實作或調整現有認證，不能把目前 D1 登入直接當作已具備的本地驗證能力。離線教材功能仍由既有 local-first 前端提供；未載入的頁面在網站主機故障時不能保證可用。

## 設定與憑證保存

第一版由管理者在後端設定供應商，瀏覽器只取得名稱、可用模型與狀態。密鑰放在容器掛載的私有設定目錄或受限檔案，位於所有靜態服務目錄及 Git 工作區之外；備份檔亦遵循此邊界。設定更新與備份一併維護。

若之後確實需要從網頁新增或修改金鑰，再增加受管理員權限保護的設定 API，不在第一版引入管理平台或多套秘密管理服務。

## 故障處理

各供應商獨立設定超時、併發與暫時停用狀態。一個供應商不可用時，不阻塞其他供應商請求。模型列表可使用快取或人工配置，避免單一列表請求失敗令全部選項消失。

第一版提供明確的手動切換。自動後備僅在使用者指定的供應商、模型能力與資料傳送範圍內啟用；圖片、結構化輸出與串流能力須匹配。已輸出部分串流時不得靜默重跑；超時重試可能產生額外費用，不能假定上游尚未處理。

## 適用邊界

此方案降低連鎖依賴，但 BDC 主機與共同網絡出口仍是單點。主機故障時，網站新訪問與其 AI API 都會受影響。要承受主機故障，需另一套獨立可用的部署及相應入口切換；這會增加維護成本，應在明確有此可用性要求時再做。

本次僅修訂架構建議，未修改程式、部署服務或遷移憑證。
