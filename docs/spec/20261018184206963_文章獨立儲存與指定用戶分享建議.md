# 文章獨立儲存與指定用戶分享建議

日期：2026-10-18。狀態：使用者已確認；第一階段交由 DeepSeek Harness 實作，分享功能列為第二階段。實作以[文章逐篇儲存與閱讀記錄實施計劃](../plan/20261018184715026_文章逐篇儲存與閱讀記錄實施計劃.md)為準。

建議將文章從使用者的整包同步快照中拆出，改為每篇文章一筆資料，以穩定的使用者 ID 關聯擁有人。這比繼續在快照中保存整份文章索引，更適合逐篇修改、增量同步，以及日後指定用戶分享。

目前 [Cloudflare schema](../../cloudflare-worker/schema.sql:63) 和 [selfhost schema](../../selfhost/schema.sql:15) 都是每位使用者一筆 `snapshots`，完整學習資料寫在 `payload`。兩個後端已有唯一的 `users.user_id`，可以作為文章歸屬的關聯鍵。`label` 是可修改的顯示名稱，不能作為關聯鍵；登入憑證 `token_hash` 也會輪替，不應用於文章身份。

**建議的資料結構**

| 資料表 | 主要欄位 | 用途與交付階段 |
| --- | --- | --- |
| `articles` | `id`, `owner_user_id`, `title`, `body`, `analysis_json`, `source_type`, `source_url`, `revision`, `created_at`, `updated_at`, `deleted_at` | 首期建立。每篇一筆，保存原文及共用分析結果，單篇讀寫 |
| `article_shares` | `id`, `article_id`, `owner_user_id`, `source_revision`, `snapshot_json`, `created_at`, `revoked_at`, `expires_at` | 分享階段建立。固定保存當次分享的標題、原文與允許分享的分析內容 |
| `article_share_recipients` | `share_id`, `recipient_user_id`, `created_at`, `revoked_at` | 分享階段建立。一筆分享可指定多位接收者，組合鍵唯一 |

`articles.id` 使用與標題、網址和內容無關的全域唯一 ID；同一篇重新分析維持 ID，另存新篇或接收者建立個人副本才產生新 ID。`owner_user_id` 關聯 `users.user_id`，並對擁有人及列表排序欄位建立索引。現行 `user_id` 可作穩定帳戶鍵；若日後允許修改登入名稱，另設可修改的 username，保留此關聯鍵不變。

一篇文章的分析結果仍可保存為 JSON，暫時沒有需要把每個段落和句子都拆成資料列。列表查詢只回傳 ID、標題、來源、狀態與時間，開啟文章時才讀取原文和分析，避免列表下載所有內容。單篇大小限制仍需保留，拆表不等於取消容量限制。

個人句子／片語標註、閱讀位置、收藏、生詞本關聯及助手會話屬於使用者自己的學習資料。實作時按 `(user_id, article_id)` 分開管理；可沿用現有個人資料儲存，確有獨立查詢或同步需要時再新增專表。分享快照使用明確欄位清單，不直接複製目前混合了個人詳解的整個 result 或帳戶快照。

**按用戶名稱分享的流程**

介面可以讓擁有人輸入接收者的帳戶名稱，後端先解析成唯一 `user_id`，確認對象後建立分享及接收者關聯。擁有人身份由登入 session 取得；即使請求中帶入其他人的 user_id，也不能據此讀寫對方文章。

首版建議採「指定接收者、唯讀、固定當次內容」：

1. A 選擇文章與 B 的帳戶，預覽分享範圍後送出。
2. 伺服器驗證 A 擁有文章，按指定 revision 原子建立分享快照及接收者關聯；若文章已變更，要求刷新預覽。
3. B 在「收到的文章」看到分享，開啟時驗證接收者權限及分享是否有效。
4. A 之後重新分析或修改原文，不會悄悄改變 B 已收到的版本；再次分享可產生新版本的分享。
5. B 如需修改或自行分析，選擇「儲存為我的文章」，建立 B 擁有的新 ID，另記來源分享 ID。B 的修改不影響 A。

擁有人可以撤回分享或單一接收者的權限。撤回會阻止之後從服務端讀取，但無法收回接收者已儲存的副本或離線內容，介面應明確表達。刪除原文時預設同時撤回相關分享，分享快照按既定保留政策清理；已建立的個人副本獨立保留。

先不加入共同編輯或公開連結。之後如需訂閱作者最新版本，可以新增分享模式；若要多人共同修改，則需要另行設計編輯權限和衝突處理，不能僅把唯讀權限改成可寫。

以上分享首先適用於同一同步服務內的帳戶。不同 selfhost 實例即使出現相同 user_id，也不是同一身份；跨服務分享需要另外的匯出／匯入或協議。

**單篇同步與離線行為**

首期可提供文章列表、單篇讀取、新增、更新、刪除接口。修改和刪除帶 `expected_revision`，伺服器以版本條件原子更新；同時修改同一篇時回報衝突並保留本機內容，讓使用者選擇重新套用或另存副本，不直接以時間較新者靜默覆蓋。不同文章可獨立寫入。

增量同步使用伺服器產生的游標與變更記錄，文章更新、刪除標記及游標寫入需保持一致；不能只依賴裝置時間篩選 `updated_at`。列表分頁需定義一致性邊界，避免同步期間新增或更新造成漏項。過期游標要求重新取得完整清單，並保留尚未上傳的本機修改，防止長期離線裝置帶回已刪除資料。

瀏覽器使用 IndexedDB 逐篇保存資料與待同步操作，仍可離線閱讀及分析；本機資料按同步端點及 user_id 隔離，訪客另設範圍。登出和換帳戶不得把上一帳戶的待同步文章上傳給下一帳戶。備份／匯出包含必要的原文、分析和個人資料，無網路還原也應能開啟。

文章拆出後，原 `/snapshot` 可繼續負責其他學習資料。文章同步有自己的版本與游標，不能再以原 snapshot version 判定整個帳戶是否沒有變更。

**與原計劃的關係及遷移**

此方向建議取代原計劃 Phase 3「整包文章索引 + 內容 hash blob」的主要儲存模式。雜湊可保留作內容校驗或日後去重，但文章身份、擁有權及分享授權以文章 ID 和使用者關係為準。首期不必承擔內容尋址、跨環境 hash 後備和未引用 blob GC 的整套複雜度；若日後文件體積或版本需求增加，再將內容移至獨立版本表或物件儲存。

遷移應先備份，再按使用者逐篇寫入、核對內容與數量，最後切換讀取來源。保留 `(owner_user_id, legacy_article_id)` 等冪等映射以防重試重複匯入，並更新文章生詞本及其他引用。舊資料缺 ID 或有重複 ID 時使用確定的遷移記錄鍵處理，不以內容相同為理由自動合併不同學習記錄。

雲端快照遷移與裝置離線資料補傳要共用同一映射及版本規則。帳戶切換至文章新接口後，服務端必須擋住舊版對文章群組的寫入；不能同時保留兩條互相覆蓋的寫入路徑。其他群組的快照更新不得觸發文章再次匯入。回滾需保全遷移後的新修改，不能只恢復發布前快照。

建議分兩次交付：先完成文章獨立儲存、帳戶隔離、逐篇同步和閱讀記錄 UI；下一次再增加指定用戶分享及收到的文章入口。分享表可以屆時新增，首期先把穩定文章 ID、擁有人和個人資料邊界做好。

驗收重點包括：多篇文章互不覆蓋、跨裝置同篇衝突保留內容、帳戶切換不串資料、遷移可重試且詞書連結完整、離線備份可還原；分享階段另外驗證未授權用戶無法存取、私人資料不隨分享送出、撤回生效和接收者副本獨立。Worker 與 selfhost 使用一致行為；新增介面文字同時完成 zh-CN／zh-HK。
