# 文章閱讀檔案與學習記錄目標方案

日期：2026-10-19  
狀態：依使用者最新目標收斂的建議規格，尚未實作。

## 1. 目標與設計取捨

使用者希望快速讀取文章及已查內容，雲端互動清楚可靠；一篇文章能關聯查過的詞、已加入詞書的詞、短語、句子、個人筆記及 AI 資料，日後可匯出成閱讀筆記；正文標記清楚而不妨礙閱讀，亦可針對不理解的內容分析，資料結構保持簡單。

因此採用「每篇文章有一份閱讀檔案」的產品模型。閱讀檔案是文章、學習條目、詞書關聯及文章資料的組合視圖；不另外保存一份跟它們重複的完整檔案 JSON。

核心取捨：

- 保留已完成的文章 ID 與逐篇文章儲存。
- 單詞、短語、句子採用同一種學習條目；一個引用位置的解析、查閱時間、理解狀態及主要筆記集中保存。
- 個人操作與全文自動解析分開。自動生成的詞義不自動算成「查過」。
- 「已查過」「已收藏」「仍不理解」互相獨立；不以其中一項推定另一項。
- 同一位置再次查閱更新原條目，首版不建立逐次點擊日誌、不記精確查閱次數。
- 使用者沒有要求自動生成 AI 文件；首版將「AI 文件」理解為主動保留的 AI 回答、專題解釋或閱讀總結，與聊天原始消息有來源連結。
- 快速閱讀依賴本機資料；跨裝置完整性依賴按項目同步、可恢復的衝突處理及完整備份。

## 2. 使用者看到的閱讀檔案

打開文章後先顯示原文和已保存的標記。點擊曾查過的詞／句子時直接打開本機解釋；只在缺少資料或主動重新分析時請求 AI。

文章提供一個「本文學習記錄」入口。桌面為側面板，手機為可展開的底部面板，避免在正文中堆疊解釋。

面板用篩選查看：全部、詞與短語、句子、待弄懂、筆記、AI 資料。收藏狀態可作篩選條件。這些是同一份資料的不同視圖，不能各自維護另一份記錄。

每個條目可看到引用、原句、解釋、理解狀態、相關詞書、個人筆記及 AI 追問；可返回原文位置。常用動作是「加入詞書」「仍不懂／已理解」「寫筆記」「問 AI」。

### 2.1 一個完整例子

原文出現 `look forward to`：

1. 在手機選取短語並打開解釋：建立或更新短語學習條目，保存結果及查閱時間。
2. 加入詞書：詞書有詞條，建立它與本條目的關聯；不用複製另一份學習記錄。
3. 標為「仍不懂」：這是使用者的理解判斷，不會因已收藏或查過而自動清除。
4. 寫下「後面接名詞或動名詞」：保存於本條目的個人筆記。
5. 問 AI「為甚麼不能接動詞原形？」：消息連到本條目及當時文章版本。
6. 選擇「保留為 AI 資料」：保存一份可回顧的解釋文件，帶來源消息及條目 ID。
7. 日後點「已理解」：保留查閱、收藏和筆記，只移除待弄懂狀態。
8. 匯出閱讀筆記：該短語、原句、詞義、個人筆記和選定 AI 解釋出現在同一份文件。

## 3. 簡單且明確的資料模型

產品上只需理解三類文章資料，另沿用詞書：

| 類型 | 保存甚麼 | 權威來源 |
| --- | --- | --- |
| 文章 `Article` | ID、原文、來源、版本、全文分析 | 現有文章儲存層 |
| 學習條目 `LearningItem` | 詞／短語／句子引用、已看解釋、查閱時間、理解狀態、主要筆記 | 新的統一學習條目儲存層 |
| 文章資料 `ArticleDocument` | 全篇心得、主動保留的 AI 解釋與總結 | 文件儲存層，每文件一筆 |
| 既有詞書及詞條 | 詞條內容、複習資料、所屬詞書 | 詞書儲存層；與學習條目用 ID 關聯 |

聊天是文章資料的來源，完整會話與消息獨立存於永久儲存。不能把不斷增長的消息陣列塞回文章、某個學習條目，或當成可清理快取。

「三類」是業務模型，不是要求資料庫只能有三張表。消息、待同步操作和詞書關聯可有必要的實體表；首版不另建詞／短語／句子三套資料模型，也不建立完整點擊事件系統或全站知識圖譜。

### 3.1 學習條目的最小契約

以下為概念結構，實作時可沿用專案命名：

```js
{
    id,
    scope,                 // 同步端點＋帳戶，訪客獨立
    articleId,
    contentVersion,        // 原文版本，與同步 revision 分開
    kind: 'word',          // word | phrase | sentence
    anchor: {
        start,
        end,
        quote,
        prefix,
        suffix
    },
    sentence,
    firstViewedAt: null,
    lastViewedAt: null,
    understanding: 'unmarked', // unmarked | needs_review | understood
    explanation: {
        language,
        result,
        generatedAt,
        provenance         // 模型、提示詞/schema 版本等，無密鑰
    },
    note: '',              // 此引用的主要個人筆記
    createdAt,
    updatedAt,
    revision,
    deletedAt: null
}
```

規則：

- 選擇「仍不懂」、寫筆記或直接收藏，都可以建立條目，不要求已完成 AI 查詢。沒有查閱時兩個 viewed 時間保持空。
- 只有有效解釋實際呈現給使用者，才更新查閱時間；快取命中及既有解釋亦算，失敗、背景預取及切走後返回的結果不算。
- 解釋可保存，但不可覆蓋 `note` 或 `understanding`；個人筆記編輯及 AI 更新使用明確的欄位修改操作。
- 相同文章版本＋類型＋精確引用範圍唯一；同一位置再次操作更新原項。不同句境的同詞保留不同條目，可在列表按詞形歸組顯示。
- 查閱事實跟隨原文引用，不跟隨顯示語言。已有解釋保留原來語言；切換 UI 語言不偷偷改寫。首版保留一份主要解釋，新增語言或刷新時明確操作；需要長期比較的版本可另存文章資料。
- 首版每個條目一則主要筆記。沒有筆記時不生成空的筆記文件；日後有多筆記需求再擴充。
- 同一解釋在通用 API 快取中可以有可丟棄副本，但學習條目的已保存內容才是閱讀記錄的權威來源。

### 3.2 詞書關聯只有一個真實來源

用關聯記錄連接 `learningItemId ↔ bookId + entryId`，附新增時間與移除標記。可由兩端查詢，但不另外保存互相可能矛盾的 `isSaved` 布林值。

同一個詞書詞條可關聯多個文章條目，保留多個原句。若出現不同意思，允許新增義項或明確更新；不能因同文字重複就丟掉新來源。

移出詞書只移除有效關聯，保留查閱、難點和筆記。「目前已收藏」由有效關聯推導；「曾經加入過」可由已移除關聯保留的時間得知，無須建立完整事件日誌。

當前詞書仍是 localStorage 整組快照。要完整達到本方案的跨裝置目標，詞條及來源關聯也必須改成按項目保存和同步。可以保留 `modules/storage.js` 對外介面以減少功能層變動，但不能一邊宣稱逐條同步，一邊仍由舊詞書快照任意整組覆蓋。

新增詞條、建立來源關聯及其 outbox 應在共同永久資料庫的同一交易完成；若遷移期間仍跨資料庫，必須有可重試、可核對的未完成操作，不能假裝具有跨庫原子性。

### 3.3 文章資料與 AI 關聯

文章資料至少包含 `id, articleId, kind, title, content, createdAt, updatedAt, revision`。`kind` 區分個人全篇筆記與 AI 文件。AI 文件另帶 `sourceItemIds, sourceMessageIds, contentVersion`；來源多個版本時在各引用上分別保存版本。

會話以穩定 `articleId` 關聯；每條消息固定 `conversationId`，可選帶 `learningItemId` 和原文引用。這樣能從短語看到相關追問，也能從 AI 文件回到原問題。

AI 文件為使用者選擇保留的一份內容快照，來源消息 ID 供追溯。後來聊天修改、刪除或重新生成，不應令已保存文件悄悄改變。相關來源不可用時，仍保留文件與引用文字。

自動組合的閱讀筆記預覽不持久化為另一份主資料；按匯出時生成文件。只有使用者選擇「保存這版總結／另存筆記」時才新增文件。

### 3.4 原文位置與版本

保留摘錄、原句、位置和前後文。全文修改時使用新原文版本，既有記錄仍可追溯到原引用；只有真的改過原文且有記錄引用時才需要保留必要舊版本。查詞、改理解狀態、重分析都不產生全文副本。

新版本中能唯一匹配的引用可重新定位；不確定時提示位置待確認，不把筆記貼到第一個同文字的位置。重新定位也不應抹掉原版本來源。

## 4. 快速讀取與清楚的雲端互動

### 4.1 閱讀路徑

1. 文章列表從本機摘要載入，不先載全部文章的全文及聊天。
2. 打開文章時從 IndexedDB 並行讀該篇原文、輕量學習標記及詞書關聯，立即呈現；不等待雲端回應。
3. 學習條目按 `scope + articleId` 建索引。文章閱讀期間保存記憶體索引，正文不為每個單詞各發一次資料庫或網絡請求。
4. 點曾查過的內容，先讀記憶體／永久記錄；若缺少結果，再查可重建快取，最後才請求 AI。三層有明確優先順序。
5. 長聊天、長 AI 文件按需載入；必要時用可重建的標記摘要避免開文章就讀大量解析正文。
6. 背景同步取得新的記錄後更新受影響標記／條目，不重新渲染整篇，不打斷選字、朗讀或正在輸入的筆記。

新裝置沒有本機文章時，先取得雲端列表和目標文章及其記錄，顯示實際載入狀態；下載後才具備離線能力。不能把尚未下載說成已離線保存。

### 4.2 寫入與同步路徑

```text
使用者操作
    ↓
固定帳戶、文章、原文版本、條目／會話 ID
    ↓
本機交易：保存變更＋寫入待同步操作
    ↓
顯示「已保存到本機」，更新當前畫面
    ↓
背景同步：按項目上傳、取得服務端確認、拉取增量
    ↓
已同步／等待網絡／需要處理衝突
```

同步規則：

- 共用一個同步協調入口，沿用登入與排程；文章、條目、詞書、消息各有明確處理器及游標，功能按鈕不直接散寫雲端請求。
- 每個帳戶範圍只允許一輪協調中的同步；切換帳戶後舊請求不能寫進新範圍。
- 按項目 ID、服務端修訂和冪等操作 ID 同步，不以整組裝置時間決定勝負。
- 本機待上傳的內容不可被背景拉取的舊值覆蓋。服務端確認舊操作時，不能順手清掉使用者剛做的新操作。
- 不同條目直接合併；同一條目兩端分別改筆記與理解狀態，可按有基準版本的欄位變更合併。同一欄位並行修改保留衝突，不無提示丟一邊。
- 查閱時間用最早首次、最晚最近的規則合併；裝置時間不作內容覆蓋依據。
- 同一理解狀態的並行矛盾、AI 解釋更新及個人文字衝突分別處理；不能以「已理解」自動覆蓋另一端的「仍不懂」。
- 新文章、原文版本等依賴需先存在；條目、關聯、消息可排隊重試。操作被重送不應重複建詞條或消息。
- 已刪記錄以刪除標記同步，防止離線裝置復活舊內容；清理時須考慮裝置同步進度。

主介面只需顯示「已保存／待同步／同步失敗或衝突」，具體技術錯誤放詳情。離線時照常本機保存；儲存失敗不得顯示成功。

### 4.3 永久資料和快取

文章、學習條目、詞書關聯、個人筆記、AI 文件、完整會話全部屬永久資料。通用 AI 結果及預取副本才可按 TTL／容量清理。

永久資料使用共同且按帳戶隔離的 IndexedDB 儲存層，可在現有資料庫升級增加 store，不必為了名稱先搬整個資料庫。只在資料確實提交後回報成功。若回退存儲不能滿足寫入／同步契約，要顯示降級及保存失敗資訊，不靜默當成等價成功。

備份完整保存永久資料、關聯及必要原文版本；聊天不能沿用目前每會話最後 50 條的裁剪。同步、備份、給 AI 的上下文長度各自有不同用途，不共用截斷策略。

## 5. 正文標記與理解程度

| 狀態 | 判定 | 建議顯示 |
| --- | --- | --- |
| 未標記 | 沒有主動查閱／個人標記 | 保持乾淨正文及既有點擊能力 |
| 已查過 | 有有效 `firstViewedAt` | 淡色細底線，避免整塊背景 |
| 已收藏 | 有有效詞書關聯 | 浮框和列表顯示收藏圖示；正文可用同一底線的變體 |
| 仍不懂 | 使用者設為 `needs_review` | 稍明顯的暖色／不同線型；在待弄懂列表集中顯示 |
| 已理解 | 使用者設為 `understood` | 取消難點強調，保留查閱和收藏資料 |
| 有筆記 | 筆記非空 | 行旁小圖示或列表入口，不在每個字旁插圖示 |

規則：

- 一個範圍只呈現一種主要正文標記，優先突出仍不懂；完整狀態在浮框／面板顯示，避免疊加多條底線。
- 短語與單詞標記重疊時以目前選取範圍／較大範圍顯示，面板列出重疊項。首版不做複雜多色重疊高亮。
- 不僅依賴顏色；線型、圖示及文字狀態提供其他識別方式。
- 「顯示學習標記」可關閉；只影響呈現，不刪資料。朗讀中的句子高亮與學習底線各自處理。
- 同詞不同句境分開理解；不要因某處 `bank` 已理解，就把其他句境全部判成已理解。
- 查過、收藏、仍不懂都不自動等於某一掌握程度。首版不加入百分比分數或多級熟練度。

手機短語延續上一份評估的「點起詞、點末詞」底部面板。加入、標記仍不懂、寫筆記和問 AI 共用已捕捉的選取引用；保存不等待 AI 補全，成功後可撤銷。

## 6. 閱讀筆記匯出與 AI 分析

### 6.1 不需要 AI 就能匯出

首版以 Markdown 為閱讀筆記輸出，JSON 為完整可還原備份；排版 PDF 可後續加入，不影響資料模型。

預設筆記內容：

1. 文章標題、來源、匯出時間及原文版本。
2. 生詞與短語：查過／收藏的項目、當時詞義、原句、目前理解狀態。
3. 重點句子：使用者操作過的句子及已保存解析。
4. 個人筆記與全篇心得。
5. 待弄懂的問題。
6. 主動保留的 AI 解釋／總結，附來源引用。

原文全文可選附上；原始聊天預設不全部堆入閱讀筆記，可選附錄。完整 JSON 備份始終包含全部永久消息。

相同學習條目在「生詞」與「待弄懂」的分類中出現時，用引用／索引避免重複大段內容。同詞多語境可分組，但每個原句和義項仍保留。曾加入後移除的收藏可選顯示歷史狀態，不能輸出成目前已收藏。

生成時固定本機資料快照，避免讀取途中因同步變化漏項；有未完成下載、衝突或未保存編輯時清楚標示。離線時仍可匯出已有資料，不能宣稱包含尚未下載的另一裝置內容。

### 6.2 AI 分析是可選的進一步整理

提供「分析本文難點」「整理閱讀筆記」兩種明確操作。使用者先確認範圍，可選條目、待弄懂內容、個人筆記和相關問答；按需補充原句或文章上下文。

AI 可解釋疑惑、歸納語法與詞組、提出幾個檢查理解的問題，結果保存為新的文章資料，附所用條目及原文版本。已保存的解釋和個人筆記保持可追溯。

AI 不自動把查過判成不懂、不擅自改為已理解、不自動覆蓋個人筆記或詞書內容。使用者採用某項建議時才更新對應記錄。整理解釋與原始記錄須能區分，匯出時亦有來源說明。

## 7. 實施邊界與遷移次序

第一個可驗收版本應打通完整路徑：本機快速重開 → 主動查閱／難點 → 詞書關聯 → 簡單筆記 → 逐項同步 → 閱讀筆記匯出。不能只完成正文標記而仍讓雲端整組覆蓋或備份截斷。

建議順序：

1. 修復既有可靠性缺口：清快取與聊天分離、完整聊天備份、重分析不丟句子／短語結果、重新打開先讀永久解析。
2. 統一儲存契約及帳戶範圍，完成學習條目、詞書關聯、欄位變更與 outbox；新資料按項目同步。
3. 完成低干擾標記、手機短語面板、理解狀態和主要筆記；支援離線保存與重開。
4. 完成本文學習面板、閱讀筆記 Markdown 匯出及完整 JSON 備份還原。
5. 補上保留 AI 回答為資料、難點分析與閱讀總結；不阻塞基礎閱讀功能。

遷移規則：

- 舊解析保留為可讀內容，不偽造查閱時間或理解狀態；用戶實際打開後再建立可靠記錄。
- 舊詞書的文章 ID／原句能對應時建立來源關聯，不確定時保留引用並標為位置未知。
- 舊聊天按原文 hash 嘗試對應文章；多義對應和無法匹配的會話保留在未關聯資料中，不猜測後刪除。
- 先備份、遷移、核對，再切換主讀寫；遷移可重試，不以長期雙寫維持兩個權威來源。
- 詞書、學習記錄、消息改成獨立同步後，舊 snapshot 路徑不得覆蓋它們；需要與現有文章遷移同類的版本／舊客戶端保護。
- Cloudflare 與 selfhost 共用資料契約和驗證規則，不能只更新一邊。
- 新文案、動態狀態和無障礙標籤同時支援 `zh-CN`／`zh-HK`；教材、原文及歷史內容不隨介面語言轉寫。

本文件收斂了上一份評估的細分建議：首版將查閱狀態、主要解釋及一則個人筆記放進同一學習條目，減少額外實體；長文資料與消息仍獨立，避免單筆無限增長。任何效能數字須在實作後量測，這裏不把尚未測試的毫秒數當承諾。

## 8. 對應目標的驗收標準

| 使用者目標 | 可觀察的驗收結果 |
| --- | --- |
| 快速打開文章 | 已下載文章在斷網下能開，無需先等同步；開一篇不讀全部聊天 |
| 快速重開已查內容 | 點已查詞／句顯示已保存結果，網絡紀錄中無多餘 AI 請求 |
| 雲端不混亂 | 離線修改、兩端不同項修改、重試、切帳戶及舊操作回應均不串資料或漏最新改動 |
| 完整文章關聯 | 從文章找到詞／句／筆記／AI 資料，亦可從詞書來源或消息返回原文引用 |
| 狀態清楚 | 查閱、收藏和仍不懂可獨立存在；切畫面、重整、同步後一致 |
| 不妨礙閱讀 | 正文不插滿卡片，不因同步跳動；標記可關閉，選字和朗讀保持可用 |
| 文字修改可追溯 | 改原文不把筆記貼錯位置，不丟舊引用 |
| 匯出有用且完整 | 單一 Markdown 包含實際操作內容；備份還原後關聯和超過 50 條的會話仍完整 |
| 結構保持簡單 | 三種詞句共用模型；同位置反覆查看不增生副本；預覽與統計由資料推導 |
| AI 可協助但不誤判 | 難點分析可保存和追溯，理解狀態與個人筆記由使用者決定 |
