## 1. 根因

完整分析最後 `saveArticle` 失敗時，`analysisSaveFailures` 會保存當時的 `finalResult` 快照，畫面顯示「重試保存」。

- 單段「刷新」成功時，`persistParagraphResult` 會重讀最新記錄、建立新的 `result` 並用 `saveAnalysis` 落盤；但它不會更新 `analysisSaveFailures` 裡的舊快照。
- 之後按「重試保存」，`retryPendingAnalysisSave` 直接把舊 `failure.result` 交給 `articleStore.saveArticle`；`saveArticle` 會用傳入的 `result` 整份取代記錄，於是把剛刷新的段落結果蓋回舊值。
- 批次重試成功時也有同樣問題：批次用最新記錄合併並落盤，但 `analysisSaveFailures` 快照未同步；只要失敗提示仍在，之後的「重試保存」仍會用過期快照覆蓋批次結果。

## 2. 修法

在 `features/article/article.js` 的 `analysisSaveFailures` 旁新增 helper：

`syncAnalysisSaveFailureParagraph(articleId, contentVersion, index, result)`

- 僅在以下條件成立時更新：
  - `analysisSaveFailures` 有該 `articleId` 的 failure；
  - `failure.contentVersion === contentVersion`（跨版本一律 no-op）；
  - `failure.result.paragraph_analysis` 是陣列；
  - index 合法。
- 只替換對應 index 的段落結果，並用既有 `mergeDetailedAnalyses` 合併該段 `detailed_analysis`。
- 不改 `article`、`contentVersion`、`title`、`sourceType`、`sourceUrl` 等其他欄位。
- 整段包在 `try/catch`，同步失敗只寫內部 warning，不影響已成功的保存流程。

呼叫點：

1. `persistParagraphResult`：`saveAnalysis` 回傳 `saved.ok` 後呼叫。
2. `retryFailedParagraphs` 批次保存成功後：對 `saved.applied`（缺少時退回 `ownedResults.keys()`）逐一以 `ownedResults` 的結果呼叫同一 helper。
3. 「完整保存成功就 `clearAnalysisSaveFailure`」的既有行為未改動。

## 3. 回歸測試

在 `tests/article-reliability.cjs` 情境 18（F3 整篇最後保存失敗）擴充：

1. 讓整篇最後保存交易 abort，確認「重試保存」與未保存提示出現。
2. 對第 2 段按「刷新」，mock 回傳含 `F3-REFRESHED` 的新譯文，等待該段保存成功，且未保存提示仍在。
3. 按「重試保存」，等待成功。
4. 重新載入並開回該文章，斷言：
   - 第 2 段仍是 `F3-REFRESHED`；
   - 第 1 段仍是原本完整分析譯文（非刷新標記）；
   - 沒有未保存提示。

測試載具另修正一點：原本的 abort patch 會攔截「任何完整段落」保存，連刷新也被 abort。改為只 abort 一次完整保存，之後的單段刷新與重試保存可正常落盤；這不改變被測的產品路徑語義。

- helper 依需求只同步 `paragraph_analysis` 與 `detailed_analysis`；快照中的頂層 `chinese_translation` 仍是完整分析當時的舊彙總值。若未來有流程直接消費快照的頂層譯文而非逐段結果，需再評估同步策略。
- `analysisSaveFailures` 僅存在記憶體；頁面重載後本來就不會有「重試保存」，此行為未改。
