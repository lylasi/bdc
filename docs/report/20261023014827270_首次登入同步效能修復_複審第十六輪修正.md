## 1. 問題與根因

### 症狀

`restoreAll()` 的核對迴圈在讀取消息期間（`await readStoredMessages()`）若使用者由帳戶 A 切換到帳戶 B，仍以 A 的記錄完成核對；`allowPartial:true` 時最終回 `{ ok:true }`，UI 因此誤報「還原成功」，實際上結果屬於已離開的 scope。

### 根因

- 修改前 `readStoredMessages()`（`modules/reading-store.js:1674`）在 `readStoreByIndex(...)` 的 `await` 之後沒有像 `getMessages()` 一樣再檢查 `isReadingContextActive(ctx)`，直接回傳 A scope 的記錄。
- `restoreAll()` 核對迴圈（`modules/reading-store.js:2905`）只檢查 `actual.length < expected` 與逐則比對；A 的記錄與備份內容一致，因此 `verifyErrors` 為空。
- 核對迴圈之後、回傳 `ok:true` 之前也沒有再次確認 context；寫入階段（`writeEntity`／`saveArticleVersion`／`getMessages`）同樣有多個 `await`，最後一次寫入完成後才切換帳戶時仍可能走到成功回傳。

## 2. 修改內容

### 2.1 `readStoredMessages()`（`modules/reading-store.js:1674-1694`）

- 入口先檢查 `isReadingContextActive(ctx)`，失效直接回 `null`。
- `readStoreByIndex(...)` 的 `await` 後再次檢查；失效回 `null`，避免把舊 scope 記錄當成核對結果。
- 保留 tombstone 語意：成功時仍回傳含 `deletedAt` 的原始記錄。
- JSDoc 補充 `null`＝stale 的契約。

### 2.2 `restoreAll()` 核對迴圈（`modules/reading-store.js:2905-2910`）

- `const actual = await readStoredMessages(convId, ctx);`
- `if (actual === null) return staleResult();`
- stale 不再被當成「空結果」而只留下 `conversation_messages` 或 `message_mismatch`；`allowPartial:true` 也不會轉成 `partial_restore_failed`。

### 2.3 同一核對函式的其他 `await` 邊界

- 寫入階段結束、進入核對前（`modules/reading-store.js:2861-2865`）：檢查 context，失效回 `staleResult()`，避免後續核對與錯誤碼覆蓋 `stale_scope`。
- 核對迴圈結束、任何成功／失敗回傳前（`modules/reading-store.js:2919-2921`）：再次檢查 context；此時之後已無 `await`，因此切換帳戶後不可能再回 `ok:true`。
- 核對迴圈中的其餘讀取（`getLearningItem`／`getVocabularyEntry`／`linksById`／`getArticleDocument`）皆為同步記憶體查詢，不需要額外 `await` 檢查。

## 3. 回歸測試設計

檔案：`tests/reading-restore-deleted-records.test.mjs`

### 新增 helper：`armVerifyReadHold(expectPuts)`（`:141`）

- 以 `FakeObjectStore.prototype.put` 計數 `messages` store 的寫入；累計到備份消息數（2）後才武裝攔截。
- 武裝後接手下一次 `index('scope_conversation').getAll()` 的 `onsuccess`：以 proxy request 先通知測試（`arrived`），暫不放行 callback。
- 之所以要等最後一則消息 `put` 之後才武裝：寫入階段每寫一則消息前都會呼叫 `getMessages()` 讀同一個索引，太早攔會卡在寫入階段而不是核對階段。
- fake IndexedDB 的交易完成條件與 `onsuccess` 是否被呼叫無關，因此被攔住的讀取交易仍會提交，測試可以安全地在 promise 未解析時切換 scope。

### 測試：`核對讀取期間 A→B 切換：restoreAll 回 stale_scope，不得回 ok:true`（`:273`）

1. 在 scope A 播種 1 個會話 + 2 則消息，`exportAll()` 取得備份。
2. 清空並重建空的 scope A（確保寫入階段的消息查詢讀不到資料，證明攔到的是核對讀取）。
3. `restoreAll(payload, { allowPartial:true })`；等 helper 通知攔到核對讀取，且確認只攔 1 次。
4. 讀取已回來但 promise 尚未解析時執行 `articleStore.reloadScope(B)` + `readingStore.reloadReadingScope(B)`（A→B）。
5. 放行 `onsuccess`，等待 `restoreAll()` 結果。
6. 斷言 `ok:false`、`error:'stale_scope'`；finally 釋放 gate 並切回 scope A，避免污染後續測試。

## 7. 剩餘風險

- `restoreAll()` 的其他路徑（例如 `adoptGuestReadingData()` 先切訪客 scope 再匯出）仍依賴呼叫端自行處理 scope；本次只在還原函式內補檢查，未改變跨 scope 併入流程。
- 攔截測試依賴 fake IndexedDB 的 `FakeObjectStore` 介面與「寫入階段先讀索引」的實作順序；若未來 `restoreAll()` 不再逐則呼叫 `getMessages()`，helper 的武裝條件需同步調整（測試會以「沒有攔到核對讀取」明確失敗，不會默默通過）。
- `writeEntity()` 成功後的最後一次 IDB 交易若橫跨切換，資料仍可能寫入舊 scope；本次確保的是「不再回報成功」與「不跨 scope 核對通過」，未回滾已提交的舊 scope 寫入（local-first 下屬可接受的殘留）。
