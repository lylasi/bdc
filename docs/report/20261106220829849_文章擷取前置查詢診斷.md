## 1. 結論（先看這段）

**已重現的產品缺陷：既有文章預查失敗會阻塞 AI 擷取。截圖不足以判定使用者當時連線失敗的上游原因。**

Codex 審核註記：以下錯誤注入驗證的是客戶端阻塞機制；無認證正式探測只驗證探測當時的端點回應及 CORS，沒有驗證正式帳戶的 SQL 分支或 D1 欄位。不能據此排除使用者當時的服務波動、回應體讀取中斷、代理或瀏覽器因素。

1. `extension/workspace-ui.js:147` 的 `await findExistingPageArticle(page.pageUrl)` 位在 `extract()` 的關鍵路徑上，且**沒有任何 try/catch 或降級**。它一拋錯，同一函式裡的 `runExtensionArticleTask()`（真正呼叫 AI 的那一步）**一次都不會被執行**。
2. 在 0.5.0 基準上，我用六種注入方式讓這一個請求失敗，**六種全部讓 AI 呼叫次數停在 0**（見 §3 表 A）。
3. 截圖那句「無法連線到同步服務」= `errors.cannotReachSync`（`locales/zh-CN.js:429`），只有一個來源：`getAIErrorTranslationKey('sync_unreachable')`（`modules/api.js:372`），而 `sync_unreachable` 只在 `apiRequest` 的 `fetch()`／讀取回應內容拋錯、且那個錯不是「取消／逾時」時產生（`modules/sync-cloudflare.js:280-284`）。
   → **使用者看到的紅色請求 `books?sourceUrl=…` 是「這個請求沒有正常完成」**（實測對應 `net::ERR_FAILED`），不是 500／502／404（那幾種在 0.5.0 會顯示別的文案），也不是逾時（逾時顯示「AI 请求超时」）。見 §3 表 A。
4. 在本地故障注入中，同一 session 的 `/ai-credentials`、`/snapshot` 及不帶 `sourceUrl` 的書單仍正常（表 A 的 S7a）。這證明單一輔助查詢故障可以造成該提示；並不代表使用者當時所有同步端點均正常。
5. 本地真 Worker＋真 SQLite 的路由、認證、CORS、schema、URL 正規化及 SQL 契約檢查通過（§4）。正式唯讀探測僅有未登入回應（§5），不足以驗證正式認證後查詢或排除當時的服務端問題。

**修正方向（經 Codex 審核）**：可恢復的非認證預查失敗允許先取得 AI 預覽，明確提示尚未確認雲端文章；401、403、帳戶失效、端點未設定及使用者取消仍中止。保存仍須雲端去重、關聯和真實回執，不以本地預覽冒充保存成功。

`showError()`（`extension/workspace-ui.js:46-49`）的查找順序：
`errorKeys[code]` → `getAIErrorTranslationKey(code)` → `'extension.workspaceFailed'`。

- `errorKeys` 裡**沒有** `sync_unreachable`，所以 `sync_unreachable` 一定落到 `errors.cannotReachSync` = **「无法连接到同步服务」**（截圖那句）。
- `not_found`／`capture_failed`／`article_not_found`／`internal_error` 都不在 `errorKeys`，也不在 `getAIErrorTranslationKey`，一律落到通用的「操作未完成，已提交的待传项目可在下方重试。」

> 也就是說：**同一支 API、同一個失敗位置，使用者看到的文案完全取決於「錯誤是哪一類」**，而「無法連線到同步服務」這個最容易被誤讀成網路問題的文案，恰好對應「HTTP 完全沒有回應」這一類。

## 6. 仍未確定的上游觸發（需要 3 個 DevTools 事實才能定案）

本地已能證明「失敗的形態」與「造成的後果」，但**這台機器無法取得使用者當下那一次請求為什麼沒有正常完成**。請 Codex（或請使用者回報）補這三項，有助進一步定位：

1. **DevTools Network 那一列的 `Status` 欄原文**：
   - `(failed) net::ERR_FAILED` / `net::ERR_CONNECTION_CLOSED` / `net::ERR_HTTP2_PROTOCOL_ERROR` → 連線層（代理／VPN／廣告或隱私封鎖器／連線被重置）
   - `(failed) net::ERR_BLOCKED_BY_CLIENT` → 本機某個擴充套件或防毒**依 URL 樣式**攔了它（`?sourceUrl=` 這種「URL 裡塞 URL」的樣式，正是部分封鎖清單會當成追蹤／open redirect 攔掉的寫法）
   - `(canceled)` → 是產品自己的 10 秒計時器中止的（那 0.5.0 會顯示「AI 请求超时」，與截圖不符）
   - `403 error code: 1010` / `500` / `502` → 邊緣或 Worker 回的，畫面不該是「无法连接到同步服务」
2. **同一列 `Size` 欄**是 `0 B`／`(failed)` 還是數字（有沒有收到 bytes）。
3. **失敗那頁的網址長度**（`location.href`），以及使用者是否在 VPN／公司代理／校園網路，是否安裝廣告或隱私封鎖擴充套件。

判讀表（對照 §3 表 A）：

| 使用者回報的 Status | 對應結論 | 修正重點 |
|---|---|---|
| `net::ERR_FAILED` 等無回應類 | 連線層問題（本機或網路路徑），但**不該阻塞 AI** | §7 P0（客戶端降級） |
| `net::ERR_BLOCKED_BY_CLIENT` | 本機封鎖器對 `?sourceUrl=` 樣式動刀 | §7 P0 ＋ 考慮把預查改成 POST body 或短鍵（不再把網址塞進 query） |
| `403 error code: 1010` | Cloudflare 邊緣依指紋檔人（但對整個主機一致，與「ai-credentials 200」矛盾，需再確認時間點） | 送 Codex／維運看 Worker 邊緣事件 |
| `500`／`502` | 後端或邊緣錯誤，畫面文案錯誤 | §7 P0 的錯誤分類 ＋ §7 P1（SQL 改成索引查詢，降低 CPU 風險） |

> 附帶觀察：`?sourceUrl=<百分比編碼的完整網址>` 這種「URL 裡塞 URL」的寫法，對各種中間設備（代理、WAF、隱私封鎖清單）都特別容易被當成可疑樣式。若真要長期穩定，建議**不要用 query string 傳整條網址**，改用 POST body 或「短鍵」（例如 `pageUrlKey` 的 SHA-256 前綴）查詢——這同時解掉 §4 P6 的全表掃描問題。

## 7. 最小修正建議（依優先序；不建議由我動產品檔）

### P0-1：預查降級，只有「認證失效」可以中止擷取
`extension/workspace-ui.js:147`（Codex 已在改這一段，以下是給對照用的最小語意）：

```js
// 只有認證問題才中止；其餘（連線、逾時、5xx、404、競態）一律降級
let existingId = '';
try {
    existingId = await findExistingPageArticle(page.pageUrl);
} catch (error) {
    if (['unauthorized', 'stale_session', 'sync_endpoint_missing'].includes(error?.code)) throw error;
    deferredCheck = error?.code || 'check_failed';   // 保存時 client.send() 會再查一次並補 page-link
}
```

依據：保存路徑 `shared/workspace-client.mjs:65` 本來就會再查一次 `GET ?sourceUrl=` 並在必要時 `POST /articles` ＋ `POST /vocabulary/page-link`，所以**擷取階段少做一次預查不會漏資料**，只是「已存在就直接沿用」的捷徑晚一點才生效。

### P0-2：不要用「無法連線到同步服務」講這個請求的失敗
`modules/extension-workspace.js:31-49`：
- 先看 `response.status`／`response.ok`，**再** `response.json()`（目前 `:37` 先 parse，邊緣若回 HTML 會變成沒有 `code` 的 `SyntaxError`，直接掉到最泛用的文案）。
- 失敗碼建議分三類，各自對應不同文案：
  - `sync_unreachable`／`sync_timeout` → 「暫時無法檢查已保存的文章，已先提取；保存時會重試」
  - `4xx/5xx`（`not_found`／`capture_failed`／`internal_error`）→ 明確講「同步服務回報錯誤（HTTP 狀態／錯誤碼）」
  - `401` → 請重新登入
- 另外把預查的 timeout 對齊 `workspace-client` 的 30 秒（`:36` 沒傳 `timeoutMs` → 走 10 秒預設），或直接改成不設逾時以外的獨立小額度，避免「AI 還在跑、輔助查詢先逾時」。

### P1-1：`findPageArticle` 改成索引查詢（Worker；請 Codex 決定由誰動）
`cloudflare-worker/src/page-links.js:7` 目前是「全帳戶文章讀出來在 JS 比對」。最小改法（不動資料形狀）：

```sql
SELECT id, legacy_article_id, source_url, title FROM articles
 WHERE owner_user_id = ? AND deleted_at IS NULL
   AND (source_url = ? OR source_url = ?)      -- 原始 URL / 去 fragment 後的 URL
 ORDER BY updated_at DESC LIMIT 1
```
搭配 `CREATE INDEX ... ON articles(owner_user_id, source_url)`；保留現有 `pageUrlKey` 做最終比對以維持語意。長期建議存一個 `source_url_key` 正規化欄位（含尾斜線政策）。

### P1-2：預查不要「順便寫入」
`modules/extension-workspace.js:46` 的 `POST /vocabulary/page-link` 是一個**寫入**，卻放在「檢查有沒有舊文章」的讀路徑上（每次按擷取都跑）。保存流程（`shared/workspace-client.mjs:91`）已經會補這一步，預查可以只留 GET。

### P2：次要一致性問題（不阻塞，但會咬人）
