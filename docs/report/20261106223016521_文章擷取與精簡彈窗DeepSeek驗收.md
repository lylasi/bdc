## 0. 結論

**本輪交辦的 8 個核心驗收面，在真 MV3 ＋真 Worker／真 SQLite 上全部通過（94/94）。**
上一輪診斷（`docs/report/20261106220829849_文章擷取前置查詢診斷.md`）裡「任何一種預查故障都會整段擋掉 AI」的現象，**在 0.5.1 已不再重現**；而認證類故障仍然正確地擋住 AI。

三件必須分清楚的事（後面 §9 詳述）：

1. **已驗證的是「客戶端阻塞機制」**：本地真 MV3 上，預查失敗不再阻擋 AI；401／403／登出／取消／切帳戶仍會阻擋。這是本輪能負責的結論。
2. **仍未知的是「使用者當時那一次請求為什麼沒有完成」**：那是使用者裝置／網路路徑／中間設備／服務端當下的問題，本輪**沒有**也無法重現。上一輪報告 §6 需要的 3 個 DevTools 事實仍然沒有拿到。
3. **正式服務仍然只確認到**：`GET /vocabulary/books?sourceUrl=…`（無 token）回 `401 {"code":"unauthorized"}` 且帶 `access-control-allow-origin: *`（上一輪 curl 證據）。本輪**沒有**再打正式服務，因此**不能**說「已驗證正式 D1 schema」，也**不能**排除「使用者當時服務端波動」。本輪的修正是讓該預查的非認證故障不再阻擋 AI 預覽。

三個非阻斷觀察（§8，**都不是本輪引進的缺陷**，供 Codex 決定是否處理）：
- 403 會擋 AI，但**不會**登出、**不會**清掉舊預覽（與交辦「403…清舊預覽」的字面對不上；行為本身合理，見 §8.1）。

## 3. A：非認證預查故障**不再**阻擋 AI（上一輪的整段阻塞已解除）

每個情境＝重開面板 →（注入故障）→ 按一次「提取文章」→ 等這次工作結束。

| # | 注入 | AI 呼叫 | 畫面文案 | 有預覽 | 端到端耗時 |
|---|---|---|---|---|---|
| A0 | 不注入（對照） | 1 | 提取完成，请检查标题与正文后保存。 | ✅ | 0.85 s |
| A-斷線 | `route.abort('failed')` → `net::ERR_FAILED`（＝截圖那條紅列） | **1** | 已提取，可先预览；暂时未能检查已保存的文章，保存时会重试。 | ✅ | 0.32 s |
| A-503非JSON | HTTP 503、`text/html`、**無 CORS**（邊緣錯誤頁形態） | **1** | 同上（降級） | ✅ | 0.32 s |
| A-500JSON | HTTP 500 `{"code":"capture_failed"}` | **1** | 同上（降級） | ✅ | 0.32 s |
| A-404 | HTTP 404 `{"code":"not_found"}`（舊版 Worker／路由缺失） | **1** | 同上（降級） | ✅ | 0.32 s |
| A-畸形JSON | HTTP **200** 但 body 是 HTML（非 JSON） | **1** | 同上（降級） | ✅ | 0.32 s |
| A-競態 | GET 回 `{"articleId":"art_race_probe"}`、`POST page-link` 回 404 `article_not_found` | **1** | **提取完成**（＝沒有被當成「已有文章」，也沒有被當成錯誤） | ✅ | 0.34 s |
| A-逾時 | 預查撐 11 s 不回應（誘發預查自己的逾時） | **1** | 同上（降級） | ✅ | **6.32 s** |

判讀：

1. **七種故障全部沒有擋住 AI**，且都拿到完整預覽（正文含 `## Outlook`）。上一輪表 A 的 S1–S6 在 0.5.1 全數失效。
2. **6 秒逾時確實生效**：端到端 6.32 s，明顯小於舊的 10 秒預設（上一輪 S5 得等 10 秒逾時才結束，而且顯示的是「AI 请求超时」）。
3. **「HTTP 非 JSON body 不冒充 network」有兩層證據**：
   - `503 text/html`／`500 JSON`／`404 JSON`／`200 非 JSON` 四種都沒在 `requestfailed` 留下記錄（＝HTTP 回應真的收到了，不是在連線層失敗），只有 A-斷線 留下 `net::ERR_FAILED`。
   - `401 text/html`（§4 B2）仍被判定為認證失敗 → 證明分類用的是 **HTTP status**，不是「body 能不能解析成 JSON」。
4. **競態被正確地當成「沒有既有文章」**：`page-link` 的 404 `article_not_found` 不再中斷流程，畫面回到正常的「提取完成」，保存時 `workspace-client` 會再查一次並補 `page-link`（§5 已驗）。
5. **文案歸因正確**：所有降級情境都不再出現「无法连接到同步服务」(`errors.cannotReachSync`) 或「AI 请求超时」；降級文案明確說「暫時未能檢查已保存的文章，保存時會重試」。

## 4. B/C：認證類故障仍然阻擋 AI（沒有把「認證壞了」也降級）

| # | 情境 | AI 呼叫 | 舊預覽 | 帳戶狀態 | 提取鈕 |
|---|---|---|---|---|---|
| B1 | `401 {"code":"unauthorized"}`（JSON） | **0** | **被清掉** | 未登录账户（已登出） | 停用 |
| B2 | `401` 但 body 是 `text/html`（**非 JSON**） | **0** | **被清掉** | 未登录账户 | 停用 |
| B3 | `403`（例如邊緣 WAF 拒絕） | **0** | 保留（見 §8.1） | 已连接账户（不登出） | 可用 |
| B4 | 使用者主動登出後 | —（按鈕停用，點不到） | 無殘留 | 未登录账户 | 停用 |
| B5 | 切換帳戶（ALICE → BOB）後對同一頁擷取 | **1**（重新擷取） | — | 已连接账户：bob | 可用 |
| C1 | 預查仍在連線時按「停止」 | **0** | 不產生新預覽 | 不變 | 可用 |

重點：

- **B2 是本輪最關鍵的一條**：body 不是 JSON 時，若程式先 `json()` 再判斷 status，就會變成沒有 code 的例外並可能被降級；實測仍然是「擋 AI ＋ 登出」，證明 `response.status` 被保留、沒有被 JSON 解析失敗吃掉。
- **B3**：403 擋住 AI（符合交辦「401／403 不得降級」），但**沒有**清舊預覽、沒有登出（§8.1）。
- **B5**：同一頁在 ALICE 底下已有文章，切到 BOB 後**沒有**沿用別人的記錄，AI 重新跑；BOB 保存後 `bob` 1 篇、`alice` 篇數不變 → 去重是**帳戶範圍**的。
- **C1**：預查被按住時按停止，`env.state.aiCalls` 不變、沒有預覽、畫面顯示「已停止，可重新提取或保存。」；`requestfailed` 留下 `net::ERR_ABORTED`（確實中止而不是放任跑完）。

1. **去重有兩條路徑都成立**：擷取前（D1）與保存前（E1）。E1 特別重要——那正是「預查壞掉」的現實情境：先讓使用者拿到預覽，保存時才補查，仍然不會重複建文章。

## 8. 觀察（不阻斷本輪驗收；沒有一項是本輪改動引進的）

### 8.1 403 會擋 AI，但不清舊預覽、不登出（與交辦字面不同）
實測（`03-403-blocked.png`）：403 時 AI 0 次、畫面顯示「操作未完成，已提交的待传项目可在下方重试。」，但**舊預覽仍在**、帳戶仍顯示「已连接账户：alice」。
- 原因：`modules/extension-workspace.js` 只有 `status === 401` 會 `invalidateSession()`；`workspace-ui.js` 的致命清單雖含 `[401,403]`，但沒有觸發 `AUTH_EVENT`，所以 `preview` 不會被清。
- 我的判讀：**行為本身可接受**（403 多半是邊緣／WAF，不代表 token 失效；保留預覽讓使用者恢復後仍可保存），但這與交辦「401／403…清舊預覽」不一致，請 Codex 明確一下預期語意。若要求 403 也清預覽，最省的做法是在該分支額外清 `preview`（不動 session）。**我沒有改。**

### 8.2 建立本頁詞書後殘留紅字「目标词书不存在或已删除」
`05-save-pending-locked.png` 可見：頁書建立成功、選單也已選中它，但收藏列仍顯示紅字。
- 追查：`capture-ui.js` 的 `selectBook()` → `loadBooks()` 會先用 **storage 快取**的舊書單跑一次 `restoreChoice()`，此時「剛建立的書」還不在清單裡 → `setNotice('captureTargetMissing','error')`；隨後網路回應補上新書、選取恢復，但**這則錯誤沒有被清掉**。
- 是否本輪引進：**不是**。`git show 5b20535:extension/capture-ui.js` 的 `restoreChoice()` 與 `extension/workspace-ui.js` 的 `applyReceipt()` 與現況逐字相同（同樣的快取→restoreChoice 順序）。
- 建議（若 Codex 要做）：`restoreChoice` 成功選中 `previous` 時，一併清掉 `captureTargetMissing` 提示，或把「暫存快取階段」的錯誤延後到最終結果才顯示。

### 8.3 預查仍是「URL 裡塞 URL」，後端仍是全帳戶掃描
本輪修正只讓失敗**不再阻塞**，沒有改變請求形狀與成本：`GET /vocabulary/books?sourceUrl=<整條網址>`、`page-links.js` 仍是「把該帳戶全部文章讀出來在 JS 比對」（上輪 P6：每次 1200 列）。這些屬可評估的效能與協議設計問題，沒有證據確認它們導致了使用者當時的故障。上輪 §7 的 P1-1／P1-2 建議（索引查詢、預查不順便寫入）**仍未做**。

### 8.4 用詞校正：「直接開原文」= 提供按鈕，不是自動開啟
D1 的行為是「沿用既有記錄」＋顯示「在 BDC 打开」按鈕；按下才開 `#a/<articleId>`。本輪驗的是按鈕可開到**同一篇**既有文章（不是首頁、不是新文章），並沒有自動跳轉。
