# 文章身份與同步方案評審

- 時間：2026-10-18 18:28:30 CST
- 範圍：`docs/plan/20261018174933864_文章詳解閱讀記錄互動優化計劃.md`、`docs/plan/20261018180748264_文章身份版本與同步儲存擴展計劃.md`、`docs/decision/20261018181402724_文章同步配額與相容決策記錄.md`

## 1. P0：必須先修

### 1.1 備份／還原／匯出在 Phase 3 會失效

**證據**

- `buildLocalSnapshot()` 目前把完整文章放在 `payload.articles.analyzedArticles`（`sync-core.js:405-431`）。
- 本機備份直接序列化這個 payload（`local-backup.js:60-66`），還原走 `restoreSnapshotLocally(payload)`（`sync.js:1745-1752`）。
- 匯出按鈕把 `payload` 直接變成 JSON 檔（`sync.js:1760-1772`），匯入上限 25 MB（`sync.js:1718`）。
- Phase 3 後 `payload.articles` 只剩 `index`，文章本文與結果在 blob；上述三條路徑都會拿到「有索引、沒有內容」的備份。

**影響**

- 使用者按「建立備份」以為有完整資料，實際無法還原文章。
- 換裝置、清除瀏覽器資料、雲端故障時，沒有可用的離線備份。
- 匯出的 JSON 也不含 blob，無法手動救援。

**建議**

1. 備份格式升版為 `{ format: 2, payload, docs: { [hash]: { article, result } } }`；舊格式仍可讀。
2. 自動備份可以只存索引（節省空間）；**手動備份與匯出必須包含 docs**。
3. 匯出改用 `CompressionStream('gzip')` 產生 `.json.gz`（或至少把上限提高到 100 MB 並警告）；匯入同時支援舊 JSON 與新 gzip。
4. `listBackups()`／`loadBackupPayload()` 改成 async（IndexedDB），`showBackupRestoreModal()` 一併調整。
5. `restoreSnapshotLocally()` 遇到 schema 2 時：先把 docs 寫入 IndexedDB，再寫索引；缺 docs 的索引標記「只有索引，需重新同步」，不要假裝成功。
6. 補測試：備份 → 清空 → 還原 → 每篇文章可開啟；無網路時也能還原。

### 1.2 啟動阻塞與 hydration 模型

**證據**

- `main.js:256` 目前同步呼叫 `loadAnalyzedArticles()`。
- 計畫寫「啟動時 `await loadArticleDocs()`，把文件載入記憶體」。
- 新裝置的 IndexedDB 是空的；若 `loadArticleDocs()` 需要等雲端 blob，啟動會卡在網路。

**影響**

- 500 篇文章 = 500 次 blob 請求；啟動可能數十秒到數分鐘。
- 網路不穩時整個 App 起不來，連其他模組也被拖住。
- 使用者在同步完成前無法看任何文章。

**建議**

採用「索引常駐、文件快取」模型，而不是啟動時全量載入：

```text
state.analyzedArticles = index entries（一定有）
articleDocs (Map 或 IndexedDB) = 已載入的文件
  - 啟動：只載入 IndexedDB 已有的 docs（快、離線可用）
  - 背景：同步時抓缺少的 docs，分批、可續傳、顯示進度
  - 開啟文章：若 doc 不在記憶體/IDB → 顯示「正在下載分析結果」→ 單篇 fetch
  - 目前文章 / 最近開啟優先預取
```

- 所有讀取改走 `getArticleDoc(articleId)`（async）；`showCurrentArticleIfAvailable()` 改成 async，`main.js` 的導航用 `await` 或 fire-and-forget。
- 歷史清單只用索引欄位（title/summary/updatedAt），不需要 docs。
- 全文搜尋在 docs 未齊時只搜尋已載入部分，並顯示提示。
- 若不想做 async getter，退而求其次：啟動只載入本機 docs，缺少的條目在清單顯示「同步中」，點擊時才下載。**不要**在啟動時阻塞下載全部。

### 1.3 Phase 3 缺 tombstone，刪除會被復活

**證據**

- 目前 `applyArticlesPayload()` 以群組 `updatedAt` 決定是否整包套用（`sync-core.js:270-286`）。
- Phase 3 仍沿用群組 LWW，Phase 4 才做 per-article LWW。
- 情境：A 刪除文章 → B 離線期間改了別的文章（`articlesUpdatedAt` 較新）→ B 上線 push → 整包（含已刪文章）覆蓋 A。
- 更糟：被刪文章的 blob 可能在 30 天後 GC；B 推送的索引引用不存在的 blob。

**建議**

把 tombstone 與 index 合併提前到 Phase 3：

- 刪除時寫 `tombstones[articleId] = now`，保留 90–180 天。
- `applyArticlesPayload()` 改成 index 逐項合併（per-article LWW），不再用整組 LWW 跳過。
- 快照 push 驗證 index 引用的 blob 存在；缺失回 `409 missing_blobs`。
- Phase 4 只保留「GC 加固、usage、監控」，不要把 tombstone 留到那時。

### 1.4 單 blob 1 MB 與標註資料衝突

**證據**

- `sentence_analysis` 每個（句子＋上下文）一筆，`phrase_analysis` 每句最多 3 筆（`sync-core.js:151-196`、`article.js:1371-1418`）。
- 兩者都沒有全域上限；1,105 句的 100k 文章，若使用者大量點開句子／片語，累積可達數 MB。
- 100k 文章 v2 本體約 436 KB；加上標註很容易超過 1 MB。
- D1 單列上限需先確認；若為 1 MB，1 MB blob 加列 overhead 可能直接超限。

**建議**

1. 新增全域標註上限（存在 result 內，同步時一併 compact）：
   - `sentence_analysis` 最多 300 筆；
   - `phrase_analysis` 最多 300 筆；
   - 兩者序列化合計 ≤ 256 KB；
   - 超過時淘汰最舊，並顯示「已保留最近 N 筆」。
2. 單篇文件（article + result）硬上限 800 KB；超過時阻止新增標註，提示清理或分段。
3. 單 blob 上限先定 **900 KB**（避開 D1 單列 1 MB 的 overhead）；若確認 D1 上限較高，再調回 1 MB。
4. 若仍要支援更大的文件，把 blob 分塊（例如 512 KB/塊）並在索引記錄 chunk 數；不要直接提高單列大小。
5. 測試：100k 文章 + 300 句 + 300 片語，序列化後 < 800 KB。

### 1.5 合併重複記錄會留下壞掉的生詞本連結

**證據**

- `deleteAnalyzedArticleByIndex()` 會刪除 `articleMeta`（`storage.js:514-520`）。
- 計畫的合併規則：刪除被合併那筆的記錄與 meta，但不刪生詞本。
- 生詞本 id = `articleId`，詞書頁的「回到文章」需要 `getArticleMetaById(activeBook.articleId)`（`vocabulary.js` 的 book-meta banner）。

**影響**

- 使用者在被合併的生詞本裡看不到「回到文章」，或點擊後找不到記錄。
- 詞書本身還在，但失去來源資訊。

**建議**

- 合併時，若被刪除的 articleId 仍有生詞本（`getWordbookById(id)` 存在）：
  - 優先保留 meta（不刪），或
  - 把生詞本的 `articleId` 改指向保留下來的 canonical id，並在詞書顯示合併提示。
- 若選擇保留 meta，容量面板要把「只有 meta、沒有記錄」的條目標為可清理，但不要自動刪。
- 合併確認文案要說明「生詞本會保留，來源連結會指向合併後的文章」。

### 1.6 LAN HTTP 沒有 `crypto.subtle`

**證據**

- `cache.js` 已明確處理 `crypto.subtle` 不可用時的 fallback（`modules/cache.js:59-85`）。
- 專案支援 `python3 scripts/serve.py --lan`，手機以 `http://192.168.x.x:8313` 開啟；這不是 secure context，`crypto.subtle` 不存在。
- 計畫用 `docHash = SHA-256(...)` 作為 blob key。

**影響**

- 區網部署時無法計算 blob key，Phase 3 直接不可用。
- 若退回現有 32-bit FNV fallback，碰撞機率太高，可能把不同文章寫進同一個 blob。

**建議**

- 實作同步的 128-bit fallback（例如兩組 FNV-1a 64-bit，不同 offset/seed，串成 32 hex）；
- 或不要用內容雜湊當 key，改用 `articleId + revision`（伺服器分欄存），完全避開 async crypto；
- `docHash` 只在安全上下文使用 SHA-256；HTTP 時用 128-bit fallback，並在文件中標明「非加密雜湊，只用於去重」。
- 測試：`crypto.subtle` 不存在時仍可建立、上傳、下載 blob。

## 2. P1：設計需補強

### 2.1 全文搜尋與 index-only 矛盾

- 計畫說歷史清單可搜尋「標題＋正文」，但 Phase 3 後索引不含正文。
- 建議：
  - 索引存 `excerpt`（前 200 字）與 `chars`；
  - 同步完成前只搜尋標題＋excerpt；
  - 全文搜尋只在已載入 docs 上做，UI 顯示「尚有 N 篇未下載」；
  - 或背景下載全部 docs 後再啟用全文搜尋（顯示進度）。

### 2.2 歷史清單效能

- `buildArticleHistoryRecords()` 目前每筆都 `parseTitleAndParagraphs()` 解析全文（`article.js:2096-2121`）。
- 1,000 篇時每次開啟清單都要解析數 MB 字串。
- 建議：在儲存時寫入 `title`、`summary`、`chars`、`fingerprint`；清單只讀索引；超過 200 列用虛擬列表或分批渲染。

### 2.3 遷移健壯性

- 舊資料可能沒有 `articleId`（早期記錄）、沒有 `paragraph_analysis`（更舊的結果）、`url:` id 用未正規化的網址。
- 建議：
  - 先寫 IndexedDB、驗證數量，再改 localStorage 索引；失敗就保留舊格式並提示。
  - 無 `articleId` 的記錄用 `local:legacy-<fingerprint>` 補一個，並建立 meta。
  - 無 `paragraph_analysis` 的結果保留 v1 形狀，`compactArticleResult()` 直接回傳原物件，不要硬拆。
  - URL 只在 `sourceType === 'url'` 時正規化；檔案路徑（`sourceType === 'file'`）不要丟進 `new URL()`。
  - 新增 `articleDataVersion`，成功後才寫入；支援重入。
  - 遷移前先做 IndexedDB 備份或匯出檔案，避免 localStorage 已滿時備份失敗。

### 2.4 重新分析會丟掉逐句／片語分析

- `finalResult` 只由 `paragraphAnalyses` 組成，沒有帶入舊的 `sentence_analysis`／`phrase_analysis`（`article.js:1904-1910`）。
- 重新分析同一篇時，使用者過去點開的句子／片語筆記會消失。
- 建議：
  - 若內文未變：合併舊的 `sentence_analysis`／`phrase_analysis`；
  - 若內文有變：保留仍能對上句子／上下文的項目，其餘丟棄並提示；
  - 或在重新分析前明確警告「會清除逐句筆記」。

### 2.5 `isLikelyAccidentalWipe` 要認新格式

- 目前只檢查 `la.analyzedArticles.length`（`sync-cloudflare.js:451-474`）。
- Phase 3 後要同時檢查 `la.articles.index.length`，否則本機被清空時不會自動從雲端還原。
- 補測試：schema 2、index 有文章、其他群組為空 → 觸發還原。

### 2.6 GC 寫入放大

- 計畫「每次快照 push 更新所有 index hash 的 `last_seen_at`」；500 篇就是 500 次 UPDATE／push，會撞 D1 每日寫入限制，也讓同步變慢。
- 建議：
  - 移除 `last_seen_at` 的逐次更新；
  - GC 直接讀目前快照 index，刪除「`created_at` 超過 30 天且不在 index」的 blob；
  - 被 index 引用的 blob 永遠保留；
  - 若一定要記錄最後使用時間，只在新增／變更時更新，不要全量刷。
- Worker 解析 index 時要限制筆數（例如 2,000）與 hash 格式，避免惡意 payload。

### 2.7 批次傳輸與續傳

- 新裝置逐個 GET blob、遷移逐個 POST，500 篇要數百次請求。
- 建議：
  - `POST /blobs/fetch { hashes }` 一次回多篇（例如 10 篇 / 2 MB）；
  - 上傳批次 10 篇 / 4 MB；
  - 每次成功就寫入 IDB 並更新「已同步」清單；
  - 中斷後從清單續傳，不重傳已完成項目；
  - UI 顯示「已同步 120/500」。

### 2.8 其他快照群組仍可能撐爆 2 MB

- 文章移出後，助手會話（每段最多 50 則）、問答集、詞書仍可能很大。
- 建議：
  - 對 `buildLocalSnapshot()` 做總大小檢查；
  - 助手單則訊息與會話數上限；
  - 超過 1.8 MB 時在同步面板警告，而不是等 413。

### 2.9 備份保留策略

- 目前手動備份無上限；計畫改成保留 3 份會直接刪掉舊備份。
- 建議：
  - 只自動淘汰「自動備份」；
  - 手動備份超過 3 份時提示，讓使用者選擇刪除或匯出；
  - 匯出檔名帶時間戳，避免覆蓋。

### 2.10 安全性與驗證

- `/blobs` 需驗證：
  - hash 格式（hex 長度）；
  - 單批數量與總大小；
  - payload 必須是可解析 JSON；
  - 每使用者索引最多 2,000 筆；
  - 每分鐘上傳次數限制。
- 日誌只記 hash／bytes／user，不記內容。
- 客戶端下載 blob 後要驗證 hash（安全上下文）或至少驗證 JSON 形狀。

### 2.11 selfhost 與 Worker 差異

- D1 與 SQLite／Postgres 的 GC SQL、`IN (...)` 參數上限、transaction 行為不同。
- Worker 有 `scheduled`，selfhost 用 `setInterval`；要確保重啟後仍會執行。
- 兩邊都要有 `/blobs`、`/usage`、schema 閘門、批次介面。
- 建議共用一个 API 測試清單，兩邊跑同一組案例。

### 2.12 估時

- Phase 3 原本 3–5 天，加入以下項目後約 **5–8 天**：
  - 備份／還原／匯出格式與 UI；
  - lazy hydration 與 async getter 重構；
  - tombstone 與 per-article merge；
  - 批次 API、進度、續傳；
  - 遷移與回滾測試；
  - Worker＋selfhost 兩邊。
- Phase 0 也不是 0.5 天：身份解析、URL 正規化、fingerprint、測試，約 1 天。

## 3. P2：文件數字與一致性

### 3.1 「精簡 48%」只適用逐句模式

以同一篇 1,832 字元文章實測（ASCII 英文、中文長度 55%）：

| 模式 | v1 | v2 | 節省 |
| --- | ---: | ---: | ---: |
| 標準（無 sentences） | 4,746 字元 | 3,187 字元 | **33%** |
| 逐句（sentences.en/zh） | 8,268 字元 | 4,424 字元 | **46%** |

- 文件中「-48%」應改為「**33–46%，視模式而定**」。
- 100 篇的容量推算也要分模式：
  - 標準模式 100 篇：v1 約 0.95 MB（UTF-16）、v2 約 0.64 MB；加 2 份備份約 2.9 MB。
  - 逐句模式 100 篇：v1 約 1.65 MB、v2 約 0.88 MB；加 2 份備份約 5.0 MB。
- 結論不變（備份仍是最大殺手），但數字要誠實。

### 3.2 其他一致性

- 500 篇索引大小：250 B/篇 → 125 KB，不是 150 KB（已修正一處，附錄也要同步）。
- Phase 3／4 的 tombstone 歸屬要統一（建議移到 Phase 3）。
- 「啟動 `await loadArticleDocs()`」與「lazy hydration」要統一（建議後者）。
- 「全文搜尋」要標明 Phase 3 後只搜尋本地已下載文件。
- `previousResult`（記錄內）與 `previousDocHash`（索引＋blob）要統一成後者。
- 決策 3／4／5 已由使用者確認，文件狀態要改為「已定案」。

## 4. 做得好的地方

- 配額、GC、schema 閘門的設計方向正確，補上上述邊界即可。
