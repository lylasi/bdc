## 1. F1（High）同步收尾不得覆寫不可讀／損壞的後備桶

### 1.1 根因

後備（localStorage）模式的所有「讀桶 → 改 state → 寫回」路徑原本共用寬鬆讀取 `fallbackRead()`：它把任何例外（`SecurityError`／配額例外／非法 JSON／`IndexedDB` 不可用後的降級）都視為「空桶」。

於是同步收尾（`markSynced()` → `persistMeta()` → `fallbackWriteState()`）在桶其實存在、只是這一刻讀不到或解析失敗時，會用記憶體中的整包 payload（`{ scope, ...serializeMeta() }`）覆寫該 key：

- `docs` 與 `outbox` 被一起寫成 `[]` → 使用者的待同步 mutation 永久消失；
- 同一輪 `syncArticles()` 仍回報 `ok: true`（伺服器端 revision 確實已提交），使用者看到「已同步」，但本機帳本已毀。

## 2. F2（Medium）`fallbackReadStrict()` 必須拒絕「outbox 存在但不是陣列」

### 2.1 根因

嚴格讀取先前只驗證 `docs` 是陣列。若桶的 `outbox` 是物件／字串（寫入端或儲存部分損壞），舊行為會：

- `fallbackRead()` 判桶「合法」，`fallbackOutbox()` 再把非陣列 outbox 當成空 outbox → 同步誤判「沒有待確認操作」；
- 回執或收尾把 `outbox` 覆寫成 `[]`，原本可重試的 mutation 永久消失。

即 F1 修好「讀不到」，但仍漏「讀得到、結構卻壞」。

### 2.2 修改位置（現況核對結果）

`modules/article-store.js:325-327`：

```js
if (parsed.outbox != null && !Array.isArray(parsed.outbox)) {
    return { ok: false, error: 'storage_corrupt' };
}
```

- `null`／缺省 `outbox` 仍視為合法空 outbox（相容舊格式桶），符合 `:318-324` 對 `docs` 的既有政策。✅ 存在
- 失敗時所有呼叫端都在寫入前返回（`fallbackWriteState`、`markOpDone`、`markOpsDone`、`advanceOperationBase`），原內容逐位元保留。✅ 語意完整

## 3. F3（Medium）restore 成功、PUT 失敗後必須持久化已確認的 revision

### 3.1 根因

`restore_update` 是「POST /restore + PUT 新正文」的兩段式操作。若 restore 成功（遠端墓碑已清、revision 由 4→5）但 PUT 因 503／斷線失敗：

- 本機 `docs.revision` 與 `outbox.expectedRevision` 仍停在 restore 前的 3；
- 下一輪重試 PUT 或使用者直接刪除時，都用 3 當 `expectedRevision`，遠端以 `article_revision_conflict` 409 回應；
- 這其實是**本機自己的版本基準沒落地**，卻被記成需要使用者處理的 `revision` 衝突（假衝突）。

## 6. 仍存風險

1. **後備模式沒有真正的跨分頁原子性。** `fallbackReadStrict()` → 改記憶體 → `fallbackWrite()` 之間沒有任何鎖或 compare-and-swap；兩個分頁同時收尾／回執時仍是「後寫者勝」。本輪只保證「讀不到就不寫」，不保證「讀到之後沒被別人改」。IDB 模式（`advanceOperationBase` 的同一交易）才有真正原子性。
2. **`restore_update` 新型別的舊版回滾風險（未修）。** `pushOne()`（`modules/article-sync.js`）沒有未知型別的防護：五個已知分支之後的尾端是 `confirmReceipt(...)` + `{ ok:true, skipped:true }`。若使用者回滾到不認識 `restore_update` 的舊版前端（例如快取到舊靜態資源），該 op 會落到這個尾端 → 用 `op.expectedRevision` 確認回執、清掉 outbox、把 doc 標成已同步，**但新正文從未上傳**，遠端停在 restore 後的舊內容，屬靜默資料遺失。目前僅靠 release asset versioning／import map 的版本雜湊降低混版機率。建議後續在 `pushOne()` 對未知 `op.type` 明確回 `markOpFailed('unsupported_op_type')`，讓舊版拒絕而非假成功。
3. **收尾持續失敗會讓每一輪同步都回 `ok:false`。** 這是刻意設計（寧可失敗也不毀帳本），但若 localStorage 長期 `SecurityError`（例如隱私模式），UI 會每輪顯示同步失敗且無自動修復路徑；需使用者清除站點資料或改用 IDB。
4. **F2 只擋 `outbox` 形狀。** 同一層仍接受 `state` 非物件、`docs` 陣列內元素非物件等退化形狀（`docs` 非陣列已被擋）；`generations` 非物件由 `fallbackGeneration()` 個別容錯。屬既有寬鬆度，未在本輪擴大。
5. **deferred 路徑的 `markSynced()` 失敗沒有獨立自動化測試。** `modules/article-sync.js:1088-1105` 的程式碼已核對正確（與正常路徑共用同一 `persistMeta()` 失敗契約），但現有四個新測試只覆蓋正常收尾路徑；deferred 分支需要 `legacy.deferred === true` 與後備桶讀取失敗同時成立，尚無對應測試。
6. **`advanceOperationBase()` 只推進 revision，不推進 `updatedAt`。** restore 後 PUT 失敗時，本機 doc 的 `updatedAt` 仍是本機編輯時間，伺服器是 restore 時間；本輪不影響衝突判定（比對用 revision），但若後續出現以 `updatedAt` 排序／顯示的邏輯需留意。
