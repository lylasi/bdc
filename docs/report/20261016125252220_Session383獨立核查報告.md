## 主要發現

### 1. P1：合併詞書窗口仍可執行詞書名中的腳本（既有漏洞漏修）

位置：`features/vocabulary/vocabulary.js:1084–1092`。

合併窗口把 `book.name` 及 `book.id` 直接插入 innerHTML。本次其他入口加上跳脫，沒有覆蓋這個入口。

復測建立兩本測試詞書，其中一本名稱為 `<img src=/review383-not-found onerror=window.__review383Xss=1>`，開啟詞書頁再開啟合併窗口。結果窗口產生一個 img 元素，`window.__review383Xss` 由 0 變成 1，確認腳本執行。測試只設定本地旗標，沒有傳送資料。

影響：若詞書名包含惡意標記，開啟合併窗口可觸發同源腳本。這是原有問題未修完整，不應表述成這次新增漏洞。建議使用 DOM/textContent 建立資料節點，並同時處理屬性中的 id；驗證所有詞書名輸出入口。

正向對照：通用選項彈窗輸入同類標記時不再產生 img，該處修復有效。

### 2. P2：編號 QA 格式仍會無提示丟失未完成題目（修復不完整）

位置：`features/qa/qa-creator.js:27–29`。

`analyzeQAPairs()` 只要舊格式解析出一組，就立即返回空 warnings，繞過新加入的孤立問題提示。

瀏覽器直接呼叫解析器的結果：

- `Q1: One?\nA1: Yes.\nQ2: Lost?`：只返回第一組，warnings 為空。
- `Q1: One?\nA1: Yes.\nQ2: Lost?\nA2:`：同樣只返回第一組，warnings 為空。
- `One?\nYes.\nLost?`：返回第一組，並有 `qa.orphanQuestionWarning`。

因此原報告 H6「已修復」僅對部分格式成立。建議舊格式解析也追蹤未消耗內容、缺答案及空答案，在保存前提示並讓使用者修正或明確決定是否繼續；不應僅保存後通知。

### 3. P2：文章導入驗證提示被彈窗遮罩壓住（本次新增回歸）

位置：`features/article/article.js:617`；`styles.css` 的 `#message-container`（約 1255 行）及 `.modal-overlay`（約 4081 行）。

本次把空網址的 alert 改成 Toast，但訊息容器 z-index 是 4000，彈窗遮罩是 5000。

復測：文章頁 → 導入文章 → 不填網址 → 點擊抓取。簡體出現「请输入网址」，香港繁體出現「請輸入網址」，但兩種語言的提示均在遮罩下面。對提示中心及關閉按鈕中心執行 elementFromPoint，命中 modal-overlay，提示關閉按鈕不可點擊。

遮罩是半透明，故精確結論是提示被壓暗且不可交互，並非必然完全看不見。建議彈窗內使用內聯驗證訊息，或統一調整訊息宿主與層級；其他彈窗內 alert→Toast 的替換也應巡檢。

### 4. P2：聽寫批改歷史「清空全部」仍沒有反應（既有功能漏測）

位置：`features/dictation/dictation-grader.js:38–47`；內部歷史窗口約 312–323 行亦有相同事件結構。

事件處理器先要求點擊目標位於 `.dg-h-item` 中，否則立即返回；「清空全部」位於 `.dg-h-toolbar`，因此永遠走不到清空分支。

復測寫入一筆測試批改紀錄，開啟歷史並點擊清空全部：紀錄數前後都是 1，沒有確認窗口，按鈕確實沒有 `.dg-h-item` 祖先。

這是原有問題，不是新增回歸；本次雖替換相關確認程式碼，仍未驗證操作能否到達該分支。建議先處理工具列動作，再處理單筆紀錄動作，兩種歷史入口一併驗證。

## 次要發現（靜態確認）

`features/ocr/ocr.js:364–371` 設定「識別失敗／已完成」按鈕文字後，雖排程一秒後還原，但 finally 緊接同步執行 `setBusy(false)`，立即恢復原文字。新增完成態無法如報告所述持續展示。摘要 Toast 的成功／失敗分類改動仍有價值；此項不是說整個失敗提示都不存在。建議完成態與 finally 清理統一設計。

## 對原驗證結論的評估

1. 原流程腳本 `tests/audit-flows.cjs:85–88` 阻斷非 localhost／127.0.0.1 的網路請求，且約 103 行關閉 assistant。這適合測試離線與失敗分支，但不能證明真實 AI、OCR、TTS、助手和 Supabase 同步全流程可用。尚未測試不等於服務故障。
2. 流程腳本捕捉流程異常後記錄 finding，繼續寫出 JSON；正常退出並不表示 findings 為零。安全腳本亦須查看結果，而不是只看 exit code。原報告自身仍記錄部分未修事項，不能將「腳本跑完」解讀為「全部通過」。
3. 原報告關於「CommonJS 模式 node --check 不會報非 async 函式中的 await」的說明不正確。以同一最小語法錯誤分別用 CommonJS 和 module 模式檢查，兩者均 exit 1 且報 SyntaxError。按 ESM 檢查本專案是合理做法，但不應保留錯誤的技術解釋。
4. 真實瀏覽器截圖與測試結果確有產物，沒有依據說原 agent 虛構整個巡檢；問題在於覆蓋與結論強度不匹配。
