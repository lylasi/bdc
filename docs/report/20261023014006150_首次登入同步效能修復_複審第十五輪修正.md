## 二、逐項根因與修改

### R1（Medium）已刪除消息令合法還原誤報失敗

**根因**

1. `restoreAll()` 的核對迴圈（修改前約 `modules/reading-store.js:2871`）用
   `getMessages()` 取得「實際儲存的消息」。
2. `getMessages()`（修改前 `modules/reading-store.js:1640-1658`）是介面查詢，會
   `.filter((msg) => ... && !msg.deletedAt)` 過濾刪除標記。
3. 但 `exportAll()` 匯出消息時**保留** `deletedAt`（`modules/reading-store.js:2702`、
   `2737`）。因此含已刪除會話／消息的合法備份，`writeEntity()` 全部寫入成功，
   核對仍會得到 `actual.length < expected` 與 `message_mismatch`；在
   `allowPartial:true`（備份還原、訪客併入）下被新的 `partial_restore_failed`
   判成失敗，`allowPartial:false` 則回 `verify_failed`。也就是「唯讀查詢語意」
   被誤用在「備份完整性核對」上。

**修改（file:line 為修改後位置）**

1. `modules/reading-store.js:1663-1685`：新增內部 `readStoredMessages(conversationId, ctx)`，
   專供還原核對使用；後備模式讀 bucket 的 `messages`（含 tombstone），IDB 模式用
   `readStoreByIndex(STORE.MESSAGES, 'scope_conversation', [scope, conversationId])`，
   只做 `conversationId` 過濾，**不過濾 `deletedAt`**。讀取失敗回空陣列（fail
   closed，仍會產生核對錯誤，不會假成功）。
2. `modules/reading-store.js:2893-2901`：核對迴圈改用 `readStoredMessages()`；
   `conversation_messages` 與 `message_mismatch` 的判定維持原邏輯。

**測試設計**（`tests/reading-restore-deleted-records.test.mjs`）

- 以 fake IndexedDB 播種會話 + 2 則消息：
  1. `deleteConversation()` → `exportAll()`（斷言備份保留 `deletedAt`）→
     清空 scope → `restoreAll(payload, {allowPartial:true})` 必須回 `ok:true`、
     `verifyErrors` 為空、`counts.messages===2`；
  2. 由儲存端直接讀原始記錄，斷言 2 筆都仍有 `deletedAt`（沒有把 tombstone
     復活），且 `getMessages()` 仍看不到已刪除消息；
  3. 第二個案例只把「單則消息」標記 `deletedAt`（會話仍在），驗證
     `message_mismatch` 不再出現、可見消息只剩一則、原始記錄保留刪除時間；
  4. 第三個案例 `allowPartial:false` 也必須回 `ok:true`。
- 修改前重現：三個案例分別得到
  `partial_restore_failed`（含 `conversation_messages:*`、`message_mismatch:*`）
  與 `verify_failed`。

### R2（Medium）後備消息快取未失效，正常寫入後仍核對失敗

**根因**

1. `writeEntity()` 的 IDB 成功路徑會清 `messagesByConversation` 並更新
   `messagesById`（`modules/reading-store.js:646-650`）。
2. 但 `writeEntityFallback()`（`modules/reading-store.js:622-658`）成功後只呼叫
   `rememberEntity()`，而 `rememberEntity()` 對 message 沒有
   `mapForType`，不會動消息快取。
3. `restoreAll()` 在寫入每則消息前會先 `getMessages()` 找 `existing`（快取空
   陣列）；寫入成功後快取仍是空陣列，核對再次 `getMessages()` 便拿到舊資料，
   導致成功寫入的 `allowPartial:true` 還原被誤判成
   `conversation_messages`／`message_mismatch` → `partial_restore_failed`。

**修改**

1. `modules/reading-store.js:656`：`writeEntityFallback()` 成功後改用既有
   `rememberAppliedEntity()`（`modules/reading-store.js:486-493`），等價於
   `rememberEntity()` + message 快取失效 + `messagesById` 更新。
2. `modules/reading-store.js:699`：後備批次寫入
   （`writeEntitiesAtomically()` 的 `idb_unavailable` 分支）同樣改為
   `rememberAppliedEntity()`。這是同一類快取失效缺口（`appendMessage()` 等
   會走此路徑），一併修正以免同問題在批次寫入復發。

**測試設計**（`tests/reading-restore-fallback.test.mjs`）

- 刻意不提供 `indexedDB`，確認 `initReadingStore()` 回 `fallbackMode:true`。
- 播種會話 + 1 則消息 → `exportAll()` → 移除後備 bucket 並重新
  `initReadingStore()`（同時清空記憶體與消息快取）→
  `restoreAll(payload, {allowPartial:true})` 必須 `ok:true`、
  `verifyErrors` 空、`counts.messages===1`。
- 同一 payload 再還原一次（重複還原／冪等）也必須 `ok:true`，並檢查後備
  bucket 真的留下 1 則消息。
- 修改前重現：首次還原即回
  `partial_restore_failed`（`conversation_messages:*`、`message_mismatch:*`）。

### P3（Medium）訪客併入沒有處理匯出失敗

**根因**

1. `adoptGuestReadingData()`（修改前 `modules/reading-store.js:2914-2926`）依序
   `initReadingStore(guestScope)` → `exportAll()` → `initReadingStore(current)`，
   完全沒有檢查 `payload.ok`，直接讀
   `payload.learningItems.length + ...`。
2. 當訪客 `exportAll()` 失敗（例如後備桶損壞回 `{ok:false,error:'storage_corrupt'}`）
   時 `payload` 沒有陣列欄位，於是在
   `modules/reading-store.js:2921` 拋 `TypeError: Cannot read properties of
   undefined (reading 'length')`，呼叫端拿不到可判讀的錯誤。
3. 切回目前 scope 只靠成功路徑的第三行；若中途新增任何提早 return／throw，
   整個 store 會停在訪客 scope。

**修改（`modules/reading-store.js:2937-2960`）**

1. 以 `let payload = null` + `try { init(guest); payload = await exportAll(); }
   finally { await initReadingStore(current); }`，保證無論成功、回錯或丟例外都
   切回目前 scope。
2. 匯出後先檢查 `payload?.ok !== true`，直接回
   `{ ok:false, error: payload.error || 'export_failed' }`，不再存取陣列。
3. 成功路徑改用 `pickArray()` 計數，避免欄位缺漏時再次拋錯（語意與
   `restoreAll()` 一致）。

**測試設計**（`tests/reading-restore-fallback.test.mjs`）

- 把訪客後備 bucket 寫成無效 JSON（`'{"messages":['`），使訪客
  `exportAll()` 回 `storage_corrupt`。
- 驗證 `adoptGuestReadingData()`：
  1. `assert.doesNotReject`（修改前直接 TypeError）；
  2. 回 `{ ok:false, error:'storage_corrupt' }`，且沒有 `imported`；
  3. `getReadingScope()` 仍是目前帳戶 scope（不是 `::guest`）。
- 另加反向驗證案例：訪客資料正常時仍能併入（`imported===1`、詞書出現在目前
  scope、scope 已切回）。

## 五、剩餘風險

1. **核對只比對存在性與 content／role**：`restoreAll()` 的消息核對現在會看
   含 tombstone 的記錄數與內容，但不比對 `deletedAt` 的時間值本身。若還原
   過程把刪除時間改寫成其他非空值，仍可能通過核對。影響低（本機還原直接
   寫入備份欄位），但屬於已知的核對盲區。
2. **核對讀取失敗採 fail closed**：`readStoredMessages()` 讀取失敗回空陣列，
   會產生核對錯誤而讓還原回報失敗。這是刻意選擇（寧可失敗也不假成功），
   但若 IDB 讀取暫時失敗，合法備份會被判 `partial_restore_failed`，需重試。
3. **`adoptGuestReadingData()` 未進入單頁寫入序列**：它沒有經過
   `runCaptured()`／`runCapturedComposite()`，若與其他 scope 切換並行，仍可能
   交錯。本次只保證「匯出失敗必定切回 current」，未改變既有併發模型（超出
   本輪範圍）。
4. **批次後備寫入的額外修正**：`writeEntitiesAtomically()` 的後備分支一併改用
   `rememberAppliedEntity()`。此變更不改變回傳值，只讓消息快取失效；既有
   `appendMessage`／`deleteConversation` 測試（含 `reading-restore-partial`）
   均通過。
5. **UI 文案無新增**：本次沒有新增使用者可見文字，因此未新增 locale 鍵；
   `audit-i18n` 仍顯示既有 `phonetics.` 缺鍵與既有硬編碼中文，屬既有基線。
