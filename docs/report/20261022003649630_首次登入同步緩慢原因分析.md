# 首次登入同步緩慢原因分析

- 日期：2026-10-22
- 分析工具：Codex CLI（`gpt-6-astra`，reasoning effort `xhigh`）
- 範圍：純程式碼唯讀分析，未修改任何檔案；未取得實際帳戶的 Network 紀錄或 payload 大小
- 後端以 repo 內 `cloudflare-worker/src/` 實作為準，`selfhost/` 共用同一批 handler

## 結論

對「新裝置第一次登入、雲端已有大量資料」的情境，最可能的主因是：

**首次要補齊大量文章與閱讀資料，而前端各階段完全串行，後端 batch API 內又逐筆等待資料庫操作。**

若涉及舊文章遷移（超過 50 篇），另有「匯入後只核對前 50 篇」的缺陷，可能額外產生大量逐篇 create／讀回請求，成為最嚴重的額外瓶頸。

次要原因：本地逐筆 IndexedDB 交易與 O(N²) 陣列掃描、多次全量 JSON 處理、同步完成後仍 `await` 完整本地備份。

固定的 6 秒 debounce、20 秒同步間隔與 AI 憑證等待，**不是**正常首次登入的主要解釋。

若完全沒有本地或雲端資料的新帳戶仍耗時數分鐘，則資料量不足以解釋，應優先量測各請求的實際等待時間、body 下載是否停滯，以及是否停在合併確認狀態。

## 登入後的觸發鏈路

```text
POST /login 成功，或通行碼 GET /me 成功
→ commitSession()
→ emitAuth()
→ 登入回呼 scheduleAutoSync('login')
→ setTimeout(..., 0)
→ doAutoSync()
→ 本地帳戶範圍載入／必要的遷移
→ 文章同步
→ 閱讀同步
→ /snapshot 拉取、合併、必要時推送、套用
→ 顯示同步完成
→ await 建立本地完整備份
→ 釋放 syncInFlight
```

對應程式碼：

- `modules/sync-cloudflare.js:359`
- `features/sync/sync.js:136`
- `features/sync/sync.js:2116`

排程行為：

| 情況 | 排程行為 |
|---|---|
| 未登入開頁，之後手動登入 | 初始化沒有 session，成功登入後通常只排 **1 次 `login`** |
| 已有 session，再次開頁 | 通常只排 **1 次 `init-session`** |
| 登入連結／登入碼流程 | 抑制一般登入排程，改由 `login-link`／`login-link-merge` 排程；也可能等待合併確認 |
| `login`／`init-session` 的排程延遲 | **0 毫秒 timer**，不是固定等 6 秒或 20 秒 |

證據：`features/sync/sync.js:163`、`modules/sync-cloudflare.js:383`、`features/sync/sync.js:2077`。只有 `data:*` 才套用 `max(最後變更＋6 秒, 上次成功＋20 秒)`。

第一個學習資料請求通常是 `/articles?cursor=...`；有舊資料待匯入則先發 `/articles/import`。獨立執行的 `/ai-catalog` 可能更早出現在 Network。

## 五個主要原因

### 1. 首次從游標 0 補齊資料，文章、閱讀、快照完全串行

**證據**

- `features/sync/sync.js:2130`：

  ```js
  await runArticleSyncPhase();
  await runReadingSyncPhase();
  await syncNow(guard.build, guard.apply);
  ```

- `modules/article-sync.js:157`：每頁取得 200 筆變更，再下載正文。
- `modules/article-sync.js:75`：每 50 篇一批，批次之間逐次 `await`，批內又逐篇 `await store.applyRemoteDoc(...)`。
- `modules/reading-sync.js:163`：依序取得 `/reading/changes`、`/reading/batch`、逐項套用。
- `modules/reading-sync.js:306`：固定執行

  ```js
  await pushAll(ctx);
  await pullAll(ctx);
  await pushAll(ctx);
  await pullAll(ctx);
  ```

- 閱讀變更來源是 `seq > cursor` 的歷史紀錄：`cloudflare-worker/src/reading.js:370`。

**影響**

- 新裝置沒有游標與本地 revision，要處理大量既有資料。
- 閱讀資料包含詞書項目、關聯、聊天訊息等，數量可能遠多於文章數；歷史變更也可能多次指向同一實體。
- 下載端有 HTTP 批次，不是每篇一個請求。例如 1,000 篇文章、每篇一筆變更且無遷移時，約需 5 次變更列表＋20 次正文批次請求，全部依次完成。
- 一般文章上傳則逐篇 `await pushOne()`，每輪最多 60 筆：`modules/article-sync.js:328`。
- 後續同步已有游標、revision、空的待傳佇列，只處理少量差異，所以明顯較快。

**建議**

- 首次同步提供「目前實體資料＋一致游標」的初始化接口，避免從頭掃描歷史。
- 批次下載採有限併發，但保留遷移依賴與游標提交順序。
- 對 `hasMore`／剩餘待傳資料明確安排續跑，並顯示階段與已完成筆數。

### 2. 後端 batch 內仍逐筆資料庫操作（DB 層 N+1）

**證據**

- `cloudflare-worker/src/articles.js:158`：

  ```js
  for (const id of ...) {
      const row = await readRow(env, userId, id);
  }
  ```

- `cloudflare-worker/src/reading.js:86` 的 `readBatch()` 也逐 key `await readRow(...)`。
- 寫入更重：`cloudflare-worker/src/reading.js:329` 逐筆 `await applyMutation(...)`；每筆正常寫入含讀實體、讀 mutation、執行 DB batch、再讀回執（同檔 `:165`、`:269`）。

**影響**

- 一個文章 batch 最多串行查 50 次；一個閱讀 batch 最多串行查 200 次。
- 瀏覽器看到「單一請求一直等」，實際上是伺服器累加大量資料庫往返。首次大量下載／遷移上傳時尤其明顯。
- `selfhost` 共用 handler，但 SQLite／PostgreSQL 與 D1 延遲不同：`selfhost/server.mjs:31`。

**建議**

- 批次讀取改用受參數上限約束的集合查詢（分批 `IN (...)`），避免逐筆等待。
- 寫入先批量讀取既有實體與 mutation 回執，再在保留版本檢查、冪等與交易語意下批量提交。
- 這比單純增加前端併發更值得優先處理。

### 3. 舊文章遷移只核對前 50 篇，其餘可能重複上傳及讀回

**證據**

- `modules/article-sync.js:376`：每 100 篇呼叫一次 `/articles/import`。
- `modules/article-sync.js:396`：匯入完成後只呼叫一次

  ```js
  const docs = await fetchDocs(records.map(record => record.articleId));
  ```

- `modules/article-sync.js:59` 的 `fetchDocs()` 會截斷：

  ```js
  const unique = Array.from(new Set(ids)).slice(0, ARTICLE_LIMITS.batchMax);
  ```

  `batchMax = 50`（`shared/article-protocol.mjs:22`），而 `importMax = 100`（同檔 `:24`）。
- 未取得文件的記錄不會 `markOpDone()`。
- 後續 `pushOutbox()` 可能重新逐篇建立；遇到 `409 article_id_exists` 又單篇讀回核對：`modules/article-sync.js:217`。
- `pullDelta()` 不會替這些 pending 記錄解除待傳狀態，因為 `modules/article-store.js:1338` 直接跳過 dirty／pending 項目。

**影響**

- ID、內容一致且匯入成功時，100 篇舊文章的後 50 篇可能額外產生 **50 次 create ＋ 50 次讀回，共 100 個串行 HTTP 請求**。
- 這是可直接從程式碼確認的放大因素，但只適用於有舊文章遷移的情境。
- 匯入接口本身也逐篇查 ID、legacy ID、用量：`cloudflare-worker/src/articles.js:528`。

**建議**

- 匯入後按 50 篇分批核對所有記錄。
- 或讓 import 回應提供可核驗的 ID、revision 與內容摘要，完整解除已成功項目的待傳狀態。
- 用量改為批次計算。

### 4. `/snapshot` 每輪全量讀取、多次 JSON 處理；15 秒不是整輪上限

**證據**

- `modules/sync-cloudflare.js:670` 每輪無條件 `await pullSnapshot()`，再建立本地快照、合併，透過多次 `JSON.stringify()` 比較，必要時整包 POST。
- 伺服器也讀取完整 payload：`cloudflare-worker/src/worker.js:337`。
- 快照包含完整 QA 集合、聽寫設定／評分歷史、非秘密 AI 設定；文章、詞書及聊天已移到其他同步接口：`modules/sync-core.js:386`。
- Worker snapshot POST 上限 2 MiB，這不是實際 payload 大小：`worker.js:76`。

timeout／重試實際行為：

| 路徑 | 設定 |
|---|---|
| 一般快照 GET | 15 秒 |
| 快照 POST | 20 秒 |
| 文章／閱讀一般請求 | 30 秒 |
| 舊文章 import | 60 秒 |
| 快照版本衝突 | 再 GET＋POST 一次；沒有一般 timeout 自動重試 |

見 `modules/sync-cloudflare.js:592`、`:697`。此外，`apiRequest()` 在 `fetch()` 回傳 Response 後就清除 timer，外層 `res.json()` 與剩餘 body 下載不受原 timer 保護（同檔 `:221`）。

**影響**

- 大型 QA／舊快照會增加傳輸、解析、比較與本地寫入成本。
- 首次閱讀遷移可能先額外 GET 一次 `/snapshot`，主流程最後再 GET 一次：`modules/reading-sync.js:293`。
- 缺少 `lastSnapshotVersion` **不是**首次才全量讀取的原因，因為後續同步也全量 GET。
- 文章／閱讀一般錯誤被捕捉後仍繼續下一階段，可能接連等待不同請求超時。

**建議**

- 引入版本條件讀取／分組增量，減少整包 stringify 比較。
- timeout 應涵蓋 body 消費，並另外設定整輪期限。
- 首次遷移已讀過快照時，確認版本仍有效後可重用。

### 5. 本地逐筆交易、陣列掃描與全量備份放大下載後等待

**證據**

- `modules/article-store.js:1367`：每篇開獨立 IndexedDB 交易；完成後呼叫 `replaceRecord()` 與 `emitChange()`。
- `modules/article-store.js:359`：每次都複製整個文章陣列，再 `findIndex()`、`find()`；首次逐篇加入 N 筆可能累計 O(N²) 掃描成本。
- 閱讀實體逐項讀寫；IndexedDB 不可用時，每項讀寫整個 localStorage bucket：`modules/reading-store.js:1799`。
- `modules/local-backup.js:110`：每輪重新匯出完整文章、閱讀資料與快照。
- `modules/local-backup.js:62`：整包 `JSON.stringify()`、`localStorage.setItem()`，並解析既有備份以清理索引。

**影響**

- IndexedDB 等待本身非同步，但逐筆交易會拉長總時間；JSON、陣列掃描、localStorage 會同步占用主執行緒。
- 文章事件目前主要更新數量與狀態，沒有證據顯示每篇都重繪全文：`features/article/article.js:3029`。
- 備份在顯示 `syncDone` 後才 `await backup.createBackup()`，備份完成才釋放 `syncInFlight`：`features/sync/sync.js:2147`。它會造成完成後卡頓或延後下一輪，但不能單獨解釋一直顯示「同步中」；而且每輪都有備份，並非首次專有。

**建議**

- 分批 IndexedDB 交易、用 Map 索引文章、批次更新狀態與 DOM。
- 大型備份改存 IndexedDB，與同步鎖分離，按資料版本決定是否重建。

## 容易誤判的機制

| 機制 | 實際行為與影響 |
|---|---|
| AI catalog／憑證 | 登入觸發 `/ai-catalog`；憑證通常延後 400ms 執行，先讀列表，再逐供應商處理。套用 AI 設定後可能再排一次，但主同步沒有 `await` 它們。會競爭資源，通常不是主流程的直接等待原因。`modules/ai-catalog.js:532`、`modules/ai-credential-sync.js:1168`、`:1195` |
| `guard.stale()` | 比較帳戶與 auth generation；變更就中止／跳過套用，沒有等待或自動重試迴圈。`features/sync/sync.js:214` |
| `pendingMergePaused` | 登入碼流程選「只登入」後，一直暫停自動同步直到確認合併。這是等待使用者決定，不是慢速傳輸。`features/sync/sync.js:718` |
| `syncInFlight`／`queuedWhileInFlight` | 同步期間的 `data:*` 事件可要求追加一輪；結束後以 `data:queued` 排程，才可能受 6 秒／20 秒限制。非本地變更的登入排程在 in-flight 時通常直接返回。`features/sync/sync.js:2093`、`:2161` |
| 子模組重入／頁面失敗 | 文章同步重入會排下一輪；閱讀同步重入共用同一 promise。下載頁完成後才存游標，因此中途失敗下次可能重抓該頁，不是每次全部從頭重試。`modules/article-sync.js:429`、`modules/reading-sync.js:333` |
| realtime 的 5 秒 | 是忽略過密觸發，不是登入後固定等待 5 秒。`features/sync/sync.js:2204` |

## 獨立核對紀錄

主流程另外抽查了關鍵引用，結果與 Codex 分析一致：

- `features/sync/sync.js:2130` 確實為文章 → 閱讀 → snapshot 的串行 `await`。
- `shared/article-protocol.mjs` 的 `batchMax: 50`、`importMax: 100` 與 `fetchDocs()` 的 `.slice(0, batchMax)` 同時存在，確認「每批 100 篇匯入後只核對前 50 篇」的放大缺陷。
- `cloudflare-worker/src/articles.js:158` 與 `reading.js:86` 確實以 `for ... await` 逐筆讀取。
- `cloudflare-worker/src/reading.js` 的 batch 寫入路徑逐筆 `applyMutation`。

## 建議的後續量測

在修 code 前，先用一次真實「新裝置第一次登入」的 Network 紀錄確認瓶頸落點：

1. 各階段耗時：`/articles/changes`、`/articles/batch`、`/articles/import`、`/reading/changes`、`/reading/batch`、`/snapshot`。
2. 是否有大量重複的 `POST /articles`（單篇建立）與 `409` 讀回，驗證第 3 點。
3. `/snapshot` 的 response size 與 `res.json()` 耗時，驗證第 4 點。
4. 前端 Performance 面板中 Long Task 是否集中在文章／閱讀套用與備份。

## 優先順序建議

1. 修正舊文章匯入後只核對 50 篇的截斷缺陷（可直接消除大量串行請求）。
2. 後端 batch 改集合查詢，消除資料庫層 N+1。
3. 首次同步提供增量初始化接口，避免從游標 0 掃描全部歷史。
4. 本地套用改批次交易與 Map 索引。
5. 備份與同步鎖分離、改存 IndexedDB。
