## 1. 必修 1：後備回執不得覆寫另一實例較新的同步狀態

### 1.1 根因

`fallbackApplyReceipts()` 在處理匹配回執時原本寫：

```js
statePayload = { ...(bucket.state || {}), ...serializeMeta(), conflicts };
```

`serializeMeta()` 是**呼叫端記憶體**的整份 state（`cursor`、`migrated`、
`migratedAt`、`lastSyncAt`、`lastError`、`gatePending`、`conflicts`）。
另一個分頁剛把 cursor 推到 73、完成遷移、設定 `gatePending`、記錄同步時間後，
持有舊記憶體的實例只要確認自己文章的回執，就會把這些欄位全部蓋回舊值。
IndexedDB 路徑本來就是交易內讀取 state row，再以
`statePayloadWithConflicts(row, scope, conflicts)` 只換 `conflicts`，兩邊語意不一致。

### 1.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:2478-2488` | 以持久化 `bucket.state` 為 `row`；衝突清單從 `persistedState.conflicts` 讀取（只有持久化 state 沒有 conflicts 時才退回 `meta.conflicts`，與 IDB 路徑一致），刪除匹配文章後以 `statePayloadWithConflicts(persistedState, scope, conflicts)` 寫回 |
| `:2416-2418` | 後備回執改用嚴格讀取（見必修 2），讀取失敗時不進入「沒有變更」分支 |

保留的既有語意：

- 匹配回執仍會清除該文章的 outbox 與衝突；
- 舊代際／被重建取代的回執仍只忽略或 rebase，不清 outbox；
- `scope` 由 `statePayloadWithConflicts()` 補上，不依賴呼叫端記憶體；
- 其他文章的衝突、cursor、遷移狀態、同步時間完全不動。

### 1.3 驗收

| 測試 | 位置 | 內容 |
| --- | --- | --- |
| 單筆 | `tests/article-rebuild-generation.test.mjs:1985` | A、B 兩個模組實例共用 localStorage；B 建立另一篇文章並寫入 cursor 73／`migrated`／`gatePending`／`lastSyncAt`、兩篇文章的衝突；A 的記憶體仍是 cursor 0，確認自己文章的回執後，state 只少了 A 的衝突，其餘欄位與 B 的衝突不變、A 的 outbox 清除、B 的 outbox 保留 |
| 批次 | `:2051` | 同上，A 一次確認兩篇文章（`markOpsDone`）；cursor 91、`migrated`、`gatePending`、`lastSyncAt`、`lastError`、另一篇文章衝突都保留，兩筆匹配 outbox 清除 |

## 2. 必修 2：後備儲存不可讀時不得誤報推送成功

### 2.1 根因

`fallbackRead()` 把任何 `getItem`／`JSON.parse` 例外都轉成
`{ docs: [], outbox: [], state: {} }`。`fallbackApplyReceipts()` 拿到空桶後：

- 找不到文件、也找不到 outbox；
- `matches` 為 false、`changed` 為 false；
- 直接回 `{ ok: true, results, updated, state: null }`。

於是 `markOpDone()` 回 `{ ok:true, stale:true }`，`pushOne()` 把它當成成功，
`pushOutbox` 計入 `pushed`；但本機文件仍是 rev0、outbox 仍在，下一次同步
才是真正的失敗。合法空桶（第一次使用、尚未有資料）與讀取失敗必須分開。

### 2.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:299-323` | 新增 `fallbackReadStrict(scope)`：`getItem` 拋錯→`storage_read_failed`；`raw` 為 `null`／空字串→合法空桶；JSON 解析失敗、非物件、`docs` 不是陣列→`storage_corrupt` |
| `:2416-2418` | `fallbackApplyReceipts()` 改用嚴格讀取；失敗直接回 `{ ok:false, error, results: [], updated: [] }`，不寫入、不改記憶體 |
| `:2499-2501`（既有） | `applyFallbackReceipts()` 對 `ok !== true` 直接回錯誤；`pushOne()` 走既有 `confirmReceipt()`，計入 `failed` 並保留 outbox |

設計取捨：

- **一般讀取路徑不動**：`fallbackRead()` 仍把「尚無資料」視為空桶，啟動、
  首次載入、UI 清單不會因為沒有桶而失敗。
- **合法過期回執仍安全忽略**：合法空桶或桶內沒有匹配操作時，`matches=false`、
  `changed=false`，回 `ok:true, stale:true`，不會誤清 outbox。
- 讀不到就明確失敗，下一輪以同一個 mutation ID 重試；伺服器端冪等（create 的
  `article_id_exists` 核對、PUT／restore 的 mutation ID）讓重試不會重複建立。

### 2.3 驗收

| 測試 | 位置 | 內容 |
| --- | --- | --- |
| 同步路徑＋`getItem` 例外 | `:2125` | 伺服器建立 rev1 後、回應交回 `pushOne` 時讓回執的 `getItem` 拋一次錯；結果 `{pushed:0, conflicts:0, failed:1}`，本機仍 rev0、outbox 保留、無衝突；恢復後同 mutation 重試→`{pushed:1, failed:0, conflicts:0}`、本機 rev1、outbox 清空 |
| 損壞 JSON＋批次讀取例外 | `:2198` | 桶被寫成非法 JSON：單筆 `markOpDone`／批次 `markOpsDone` 都回 `ok:false`、`storage_corrupt`，桶內容不被覆寫；還原合法桶後讓批次 `getItem` 拋一次錯→`storage_read_failed`，文件／outbox 不動；恢復後單筆與批次用同一批 mutation 都成功，rev1、outbox 清空、無衝突 |

## 3. 必修 3：備份還原同 ID 覆蓋墓碑後仍可同步新正文

### 3.1 根因

三條路徑各自正確、組合起來卻卡死：

1. `importDocuments(..., { replace: true })` 對已存在文件一律排 `update`；
2. `pushOne()` 的 update 分支收到 Worker 的
   `409 article_already_deleted` 後，依既有政策記成 `deleted_remote` 衝突；
3. Worker 的 `handleUpdate()` 明確拒絕 `deleted_at IS NOT NULL` 的 PUT。

這個政策對「使用者編輯一篇被其他裝置刪除的文章」是正確的，但備份還原
（`replace: true`、使用者明確要用備份覆蓋）是同 ID 的**復原意圖**：
伺服器墓碑只能先 `POST /articles/:id/restore` 清掉 `deleted_at` 並取得新
revision，才能 PUT 新正文。

### 3.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:2964-2969` | `importDocuments()`：`replace` 備份還原時，若記憶體中的 `existing.deletedAt` 存在→直接排 `restore_update`；另帶 `restoreIntent` 讓交易內用持久化文件補判（記憶體落後另一個分頁剛套用的墓碑） |
| `:1290-1297` | `restoreUpdateType()`：只有明確 `restoreIntent` 且交易內文件是墓碑時，才把 `update`／`create` 升級為 `restore_update`；`delete`／`restore` 不變 |
| `:850`、`:891` | `persistDocWithOp()` 的 localStorage 後備與 IndexedDB 交易都在讀到 `storedDoc` 後才計算 `effectiveType`，文件、摘要、outbox 與代際 ledger 仍同交易／同一同步區塊 |
| `:1239-1244` | `createOutboxOp()` 接受 `restore_update`；後續本機編輯（`type: 'update'`）沿用既有的 `restore_update` 意圖，不會降回普通 update；`delete`／`restore`／重建 `reset` 的優先序不變 |
| `:1278` | `payload` 只對 `delete`／`restore` 設為 `null`；`restore_update` 保留新正文 |

`modules/article-sync.js`

| 位置 | 內容 |
| --- | --- |
| `:248-346` | 新增 `pushRestoreUpdate()`：先 `POST /articles/:id/restore`（`expectedRevision` 取本機／操作基準），再以伺服器回報的 revision PUT 新正文 |
| `:369-371` | `pushOne()` 在 `create`／`update`／`delete` 前分流 `restore_update` |

`pushRestoreUpdate()` 的失敗語意：

| 情況 | 處理 |
| --- | --- |
| restore 200 | 取得目前 revision（通常墓碑 rev3 → rev4），必要時 PUT（rev4 → rev5） |
| 正文已與伺服器一致（回應遺失後重試、別台已還原同一份） | 不再 PUT，直接確認回執，避免無意義推進 revision |
| restore 404 | 沿用 update 的 404：`requeueAsCreate()` 改成建立，下一輪完成；不記衝突、不在同輪無限重試 |
| restore 409 `article_not_deleted` | 另一個裝置已 restore 或先前 restore 已成功但回應遺失：直接以伺服器目前 revision PUT 新正文 |
| restore 409 `article_revision_conflict` 且目前仍是墓碑 | 只用伺服器回報的 revision 再試一次 restore；第二次仍失敗→`markOpFailed`、保留 outbox，下一輪重試 |
| PUT 404 | 同上改成建立 |
| PUT 409（restore 與 PUT 之間又被刪除／改版） | `markOpFailed`、保留 outbox，下一輪重新 restore；**不記成需要使用者處理的資料衝突** |
| 其他 restore／PUT 失敗（配額、權限、5xx） | `markOpFailed`，計入 `failed`，outbox 保留 |
| 確認回執失敗 | 既有 `confirmReceipt()` 回錯誤，不計成功、不清 outbox |

`tests/helpers/article-sync-server.mjs`

| 位置 | 內容 |
| --- | --- |
| `:145-158` | mock `POST /restore` 補上與 Worker 一致的 `article_not_deleted`（已非墓碑且 revision 不同）與同 revision 冪等成功 |
| `:187-190` | mock PUT 對墓碑回 `409 article_already_deleted`，與 `cloudflare-worker/src/articles.js:475` 一致（冪等 mutation 檢查仍在前面） |

設計取捨：

- **一般編輯行為不變**：`saveArticle`／`renameArticle` 不帶 `restoreIntent`，
  即使持久化文件已被別台刪除，仍是 `update` → `deleted_remote` 衝突，
  由使用者選擇（新增測試固定這條路徑）。
- restore 與 PUT 使用兩個 mutation ID：`<op.clientMutationId>:restore` 與
  `op.clientMutationId`。兩者都由同一筆 outbox 操作決定，重試時不變，
  伺服器端可冪等；PUT 的 mutation ID 仍與 `markOpDone` 的回執匹配。
- 還原後的代際不變（沿用墓碑退休後的 generation 2）；revision 由 restore／PUT
  的伺服器回應推進，`markOpDone` 以 `Math.max` 落地。
- `buildOutboxOp`／`rebasePendingOutbox`／`isLegacyPendingOp`／`pushOutbox` 的
  既有語意已檢查：`restore_update` 不是 legacy、rebase 只會保留型別並推進
  `expectedRevision`、統計仍以 `pushOne` 的 `ok`／`conflict` 為準。

## 4. 跨分頁／多實例測試設計

沿用第六～九輪的 `module.registerHooks({ resolve })`：專案模組依 `?tab=<id>`
取得獨立模組圖，`globalThis.indexedDB`、`localStorage`、`fetch` 共用，
模擬「兩個瀏覽器分頁共用儲存、記憶體與 in-flight 請求分開」。

| 測試 | 分頁實例 | 儲存模式 | 用途 |
| --- | --- | --- | --- |
| 必修 1 單筆 | `l1`／`l2` | localStorage 後備 | A 舊 metadata vs B 新 state |
| 必修 1 批次 | `m1`／`m2` | localStorage 後備 | 同上，`markOpsDone` |
| 必修 2 同步讀取例外 | `n1` | localStorage 後備 | 包裝 `fetch`，在 create 回應交回後才讓一次 `getItem` 失敗 |

## 8. 未完成項與仍存風險

1. **（既有缺口，未修）** `persistDocWithMeta()` 的後備分支仍以呼叫端記憶體的
   `{ scope, ...serializeMeta(), ...metaPatch }` 整包寫 state；`markOpFailed()`、
   `deleteArticle()` 的「撤銷未上傳 create」捷徑等路徑仍可能把另一個分頁剛寫入的
   state 蓋回舊值。本輪只修回執路徑（複審指定的 Medium），沒有擴大修改所有
   後備 state 寫入。
2. **（新 outbox 型別）** `restore_update` 是本輪新增的操作型別。目前所有前端
   讀取者都已支援；若使用者把前端回滾到舊版，舊版 `pushOne()` 會落到最後的
   「未知型別直接確認」分支，可能清掉 restore 意圖。專案是靜態 SPA、部署時
   前端一起更新，這個風險只在回滾版本時成立。
3. **（restore 與遠端競態）** restore 成功後、PUT 前遠端又被刪除或改版，本輪
   會保留 outbox、下一輪重新 restore；同一輪最多重試 restore 一次，不會無限
   迴圈，但若遠端持續被刪，該篇文章會逐輪計入 `failed`，直到遠端穩定。
   restore 404 會轉成 create（多一輪），這是沿用 update 404 的既有行為。
4. **（一般編輯政策不變）** 使用者手動編輯一篇被其他裝置刪除的文章仍會得到
   `deleted_remote` 衝突，必須由使用者選擇保留本機或丟棄；本輪沒有提供
   「自動 restore」的 UI 或背景行為。
5. **（localStorage 後備的跨分頁原子性）** `fallbackApplyReceipts()` 的嚴格讀取
   與寫回在同一個同步區塊內、沒有 `await`，但仍不是真正交易；兩個分頁在同一個
   事件迴圈切片外的極端交錯，與其他後備寫入（`fallbackDocWrite`、outbox）風險
   相同。
6. **（未跑 Playwright 巡檢）** 本輪改動集中在 IndexedDB 交易、後備桶、同步
   outbox 與 mock Worker；依約束只執行 node 測試、i18n audit 與 `git diff --check`。
