## 五、與這次選單邊界修正相關的新問題

**沒有發現新的缺陷。** 以下 2 項觀察 + 1 項證據出處說明，請你判斷是否需要處理：

1. **（觀察，低風險）「捲動即關閉」與點擊瞬間 scroll 事件的競態。** build B 新增 `window scroll → closeWordPanelMenu`，若開啟後仍有一個 scroll 事件排隊送達，剛開的選單會立刻被收起。可穩定重現的方式是「未捲動的頁面上用會自動捲動的工具點擊」：`menu-open-short-v4.json` 的診斷欄位記到 `startScrollY:0 → scrollY:285`、`scrollEvents:1`（長標題 2 次）、`hidden:true`、`aria:false`。**人類操作順序（先捲到入口、事件沉澱後再點）8/8 正常開啟**，見 4.2(b)。真機上的風險僅限「慣性捲動尚未停止時點 ⋯」，此時表現是「點了沒反應」；若你認為不可接受，最小改法是把 scroll 監聽改為 rAF 節流後重算位置，或改為只在入口離開 band 時收起。
2. **（觀察，非缺陷）320×260 的可用性偏低。** 該視口 band 只有 144.8px（57→201.8），空詞書選單可用高度 46.8px（不足一個 44px 項目加內距），長標題 89.5px（約 1.5 項），都要在很小的窗口內捲動。這符合「上下限都在操作區內、超長可捲動」的規格，只是操作體感差；若要更好，屬新需求（例如改以上下半屏分頁或全螢幕 sheet），不在本輪修正範圍。
3. **（證據出處說明）** V3 證據 `docs/report/assets/20261107063401314_long-title-v3/empty-menu-and-rename.json` 內的 `inlineMaxHeight` 已是 `141.156px`（＝V4 的 band 算法），且該次執行最後一項命中自身；也就是那份 JSON 是在 V4 定位碼已進樹之後才產生的，不能當作「修前」基線。因此本輪另外做了 `audit-v3-control-v4.cjs` 對照組（第三節），在同一頁、同一尺寸下把 band 扣減還原成 V3 算法，才重現出 `BUTTON.nav-btn` 的症狀並確認修復因果。
