## 新增測試：`tests/extension-compact-assistant.cjs`

真 MV3 + SQLite E2E，按需求覆蓋：

1. **精簡首頁**
   - 首頁只有三個快捷入口，無常駐單詞／原句／上文表單。
   - 無常駐 AI 摘要／結果／收藏／文章擷取區。
   - `#ext-settings-open` 有 title + `aria-label`，可開啟設定 dialog。
   - dialog 內切換語言、AI 思考程度即時寫入 extension storage；重開頁面保留。
   - zh-CN / zh-HK 首頁、設定 dialog 320px 與桌面截圖；無橫向溢出。
2. **懸浮球**
   - 未選字時預設顯示，無障礙名稱正確。
   - `#ext-assistant-enabled` 取消勾選 → storage 即時更新，已開啟網頁即時隱藏。
   - 重新勾選 → 即時恢復；切換語言後懸浮球名稱即時更新。
3. **文章 AI 助手**
   - 無選字點球 → 真 iframe `view=assistant`，開啟時不呼叫 AI。
   - 讀到文章標題與 URL；請求帶原文（`People gather information...`）與 `/test-article?assistant=1`。
   - 真 SSE 串流；連續提問把前一輪問答帶入上下文。
   - `#ext-assistant-stop` 停止 → 重試沿用中斷問題；mock 失敗 → 重試成功且不重複問題。
   - 有草稿時關閉會確認；回收小窗後再點球，草稿與既有對話都恢復。
   - 展開／收回維持同一個 iframe（同 URL、同 ticket，高度改變）；320px 與桌面無溢出。
   - 在助手內登出／切換 Bob：清空 Alice 對話與草稿；Bob 請求上下文不含 Alice 內容。
4. **詞卡助手入口**
   - `#ext-inline-ai` 帶上 `plunge` 與原句；不預先呼叫 AI。
   - 返回後原詞義仍在；原詞書收藏可完成，sentence／source URL 保留，不重跑 AI。
5. **文章右鍵等價流程**
   - service worker 端確認 `bdc-import-article` 已註冊（`chrome.contextMenus.update(id,{})` 成功）。
   - headless 無法點擊瀏覽器原生右鍵選單；改由**可信 lookup frame** 發送同一個
     `BDC_OPEN_WINDOW {view:'article',autoImport:true,ticket}`（與 `contextMenus.onClicked` 共用 `openWorkspace` 入口）。
   - 先把 decoy 分頁帶到前景，證明來源仍由 ticket 綁定，不是 active tab。
   - 驗證 lookup popup URL 帶 `windowTicket`（新票）＋`view=article`＋`import=1`；popup 是獨立視窗。
   - AI 提取、逐段分析、保存；DB `source_url` 是 ticket 綁定的原文；正文不含網頁表單私有值。
   - 完成後**同一個 popup** 導航 BDC `#a/<articleId>`，並載入同一篇正文。
6. **詞書與原文連結**
   - `#ext-open-book`（展開詞卡後可見）→ BDC `#v/book`。
   - `#ext-capture-source a` → 原網頁。
7. **窄版與截圖**
   - 320px / 桌面：首頁、設定、詞卡、助手皆無橫向溢出。
   - 兩語核心 UI 截圖見下節。

## 更新既有測試的新互動

- 登入／模型設定：先開 `#ext-settings-open`（首頁）或 `#ext-inline-settings`（小窗）→ `#ext-settings-dialog`。
- 編輯查詞：`#ext-inline-edit` → `#ext-query-dialog`；原表單 id 不變。
- 原文整頁擷取：`#ext-home-article` 開獨立文章 popup；不再從首頁表單、lookup 下拉或 inline「更多」擷取。
- 文章「在 BDC 打開」：文章 popup 會在同一視窗導航 `#a/<id>`（不是另開分頁）。
- 詞書表單（建立本頁／預設／自訂詞書）仍在 inline「更多」展開的同一個 iframe；文章 popup 只顯示文章區。
- 帳戶切換：在實際使用中的 inline 小窗或文章 popup 內開啟設定 dialog 操作，保留跨帳戶隔離斷言。

以上遷移都保留了原有業務斷言；沒有以放寬條件或直接跳過方式處理。

## 失敗與待主代理處理

### C1. 手動修改查詢仍保留舊來源網址（`tests/extension-capture.cjs`）

- 失敗檢查：`手動修改查詢清除舊來源網址`。
- 現象：由選取詞卡開啟查詞 dialog，修改單詞／原句後提交，`#ext-capture-source a` 仍然存在，
  新結果仍帶著前一次選取頁面的 `sourceUrl`。
- 期望（原有斷言）：手動修改查詢後，不應再宣稱新詞／新句來自上一篇文章。
- 線索（只讀、未改應用）：
  - `extension/lookup.js` 的 `openDialog('ext-query-dialog')` 建立 `querySnapshot`，取消時會把
    `source`／result 還原。
  - 提交時 `#ext-lookup-btn` 只設 `querySubmitted = true` 並關閉 dialog；
    `captureUI.setSource(...)` 沒有被清空，`handleLookup()` 也沒有清除來源。
  - 舊版報告 `docs/report/assets/20261106140441286_page-validation/capture-legacy/results.json`
    顯示同一斷言曾 PASS，因此這是 0.6.0 整合期的行為回歸／待決策點。
- 建議（供主代理判斷）：提交編輯後的查詢時，若文字與開啟 dialog 時的 snapshot 不同，
  清除舊 `source`（或至少不要沿用舊 anchor／sentence 來源），再 `showResult`。
- 目前測試保留此斷言並記為 FAIL，沒有改成「允許保留來源」來繞過。

### 原生右鍵選單的測試邊界

Headless Chromium 無法開啟並點擊瀏覽器原生 context menu，因此本輪：

1. 以 service worker 的 `chrome.contextMenus.update('bdc-import-article', {})` 確認選單 id 已註冊；
2. 以同一個 `openWorkspace()` 入口（可信 lookup frame 的 `BDC_OPEN_WINDOW` + `autoImport:true` + ticket）
   驗證後續完整行為。

這不是把右鍵流程改成另一個功能；`contextMenus.onClicked` 的 handler 與測試入口都呼叫同一個
`openWorkspace(tab, { autoImport: true })`。真正 OS 層右鍵點擊仍建議在非 headless 手動驗一次。
