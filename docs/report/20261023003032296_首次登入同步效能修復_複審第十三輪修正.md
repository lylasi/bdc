## 二、逐項根因、修正與測試

### A（High）全文載入失敗被當成「文章不存在」

#### 根因

`ensureArticleLoaded()`（舊 `modules/article-store.js:1529`）只有兩種結果：全文或 `null`。

- 後備路徑用 `fallbackRead()`：任何讀取例外／JSON 損壞都變成空桶，`null` 與「這篇真的不存在」不可區分。
- IndexedDB 路徑用 `readOne()`：`request.onerror` 直接 `resolve(null)`，交易失敗也被吞成 `null`。

`pushOne()`（舊 `modules/article-sync.js:384-393`）因此把讀取失敗走進 `if (!record)` 的 skip 分支，呼叫 `confirmReceipt()`：

1. 文件被標成 clean；
2. outbox 被移除；
3. 回報 `{ok:true, skipped:true}`，`pushOutbox()` 計入 `pushed`；
4. 實際內容從未上傳，且下一輪已沒有操作可重試。

#### 修正

- `modules/article-store.js:1534` 新增 `ensureArticleLoadedDetailed()`：
  - 真正的「沒有這篇」→ `{ok:true, doc:null}`；
  - 後備讀取失敗 → `{ok:false, error: fallbackReadStrict 的錯誤}`；
  - IDB 讀取失敗 → `{ok:false, error}`；`idb_unavailable` 才切後備並改用嚴格讀取。
- `modules/article-store.js:1603` 的 `ensureArticleLoaded()` 保留為相容包裝（只回全文或 `null`）。
- `modules/article-sync.js:390-409`：`ok:false` 時直接 `return {ok:false, error: ...}`，不 confirm、不 markOpFailed、不清 op。
- `modules/article-sync.js:560-593`：`pushOutbox()` 收集 `errors: [{ articleId, mutationId, error }]`，隨 `pushed` 回傳；`syncArticles()` 的結果因此能帶出錯誤碼。

#### 測試設計（`tests/article-rebuild-generation.test.mjs`「summaryOnly 文件在 IDB get 失敗時…」）

1. `seedRevision3()` 建立遠端 rev3；再保存 `a-v4` 產生待推送 update。
2. 用新的模組實例 `bootTab('k3')` + `reloadScope()` 模擬重新整理，記錄為 `summaryOnly`。
3. `armDocGetFailure()` 包住 `FakeObjectStore.prototype.get`，只讓該文件 key 的下一次讀取注入 request failure。
4. 斷言：
   - `pushed.pushed === 0`、`pushed.failed === 1`、`pushed.errors[0].articleId` 正確；
   - outbox 仍保留同一 mutation、`expectedRevision` 不變；
   - 遠端仍是 rev3／舊正文，本機文件仍 `dirty/pending`；
   - 讀取恢復後下一輪 `pushed === 1`，遠端更新為 rev4、outbox 清空、文件 clean。
5. 反向驗證：暫時讓讀取失敗時 `record = null`（舊行為）→ 測試在 `pushed.pushed !== 0` 失敗；還原後 checksum 一致。

### B（High）備份匯出失敗仍存成「成功備份」並更新簽章

#### 根因

舊 `modules/local-backup.js:202-224`：

```js
try { payload.articleDocuments = await articleStore.exportDocuments(...); }
catch (_) { payload.articleDocuments = []; }
try { payload.reading = await readingStore.exportAll(...); }
catch (_) { payload.reading = null; }
```

- `exportDocuments()` 已經把 `exportDocumentsResult()` 的 `ok:false` 轉成 `[]`，內層 catch 再把例外轉空陣列。
- `readingStore.exportAll()` 的 `{ok:false}` 完全沒有檢查。
- 之後仍 `saveBackupPayload()`、裁剪超過上限的自動備份、寫入 `SIGNATURE_KEY`。
- 下一次自動同步用同一簽章判斷「資料沒變」而跳過重建，等於可用備份被一份沒有文章／閱讀資料的備份覆蓋。

#### 修正

- `modules/local-backup.js:200-227`：
  - `articleStore.exportDocumentsResult()`；`ok !== true` 立即 `return { error }`。
  - `readingStore.exportAll()`；`ok !== true` 立即 `return { error }`。
  - 只有兩者都成功才 `saveBackupPayload()` 與 `writeLastSignature()`。
- `features/sync/sync.js:2292` 的手動備份 UI 也檢查 `{error}`，不再一律顯示「已建立備份」。

#### 測試設計（`tests/local-backup-export.test.mjs`，新檔）

1. 以 fake IndexedDB 建立 scope 與一篇文章，先放兩份既有自動備份、索引、中繼資料與舊簽章。
2. `armStoreReadFailure('docs')` 讓文章匯出 `getAll` 失敗 → 斷言 `{error}`、備份 key 集合、索引、中繼資料、簽章全部不變。
3. `armStoreReadFailure('reading_items', {viaIndex:true})` 讓 `readingStore.exportAll()` 的 scope 索引讀取失敗 → 同樣斷言；錯誤訊息包含 `reading_export_failed`。
4. 第三個測試移除注入，確認成功時會新增備份、更新簽章、payload 含文章文件與閱讀資料（反向驗證）。
5. 反向驗證：暫時把文章／閱讀失敗分支還原成舊的 `[]`／忽略 `ok` → 兩個失敗測試皆失敗；還原後 checksum 一致。

### C（Medium）同代際新 DELETE 接手時 revision 沒交接

#### 根因

`advanceOperationBase()`（舊 `modules/article-store.js:2058-2139`）用 `operationBaseMatches(pending, mutationId, generation)` 同時比對 mutation ID 與代際，不符合就 `{ok:true, applied:false}` 且完全不寫。

情境：

1. restore 已在伺服器把文章推到 rev5；
2. 回應回來前使用者刪除，outbox 換成 M2=`delete`，`expectedRevision` 仍是 rev3；
3. restore 回應送達時 pending 已是 M2，`operationBaseMatches` 回 false；
4. rev5 沒有落地；
5. 下一輪 DELETE 以 rev3 送出，被 409 拒絕並記成使用者衝突。

#### 修正

- `modules/article-store.js:2140-2190`（後備）與 `:2218-2252`（IDB）：
  - 先算 `sameGeneration`（`storedDoc` 不存在或持久化代際 === 本次 generation）。
  - `operationBaseMatches` 失敗時，若 `pending` 存在、`sameGeneration`、且 pending 的代際相符：
    - 只把 `storedDoc.revision` 往前推進到已確認 revision；
    - 只把 `pending.expectedRevision` 往前推進；
    - 不覆寫 pending 的 `clientMutationId`、`type`、payload、`dirty/pending`。
    - 回 `{ok:true, applied:false, rebased:true, revision, doc}`。
  - `pending === null` 或代際不符：維持原本 `{ok:true, applied:false}`，完全不動。
  - 後備與 IDB 兩條路徑語意一致；IDB 版本同時更新摘要。
- `modules/article-sync.js:334-350`：`applied:false` 一律視為 superseded（不 PUT、不 markOpFailed），`rebased:true` 另帶錯誤碼 `revision_base_rebased` 方便除錯；`pushOutbox()` 不計失敗、不計衝突。

#### 測試設計

1. `tests/article-rebuild-generation.test.mjs`「跨操作：restore 回應遲到、使用者 DELETE 接手」：
   - `seedRestoreUpdate()` 建立墓碑 rev4 + 本機 `restore_update`；
   - `afterRestore` hook 暫扣 A 的 restore 回應，確認伺服器已 rev5；
   - 此時 `deleteArticle()`，斷言 DELETE 仍以 rev3 為基準；
   - 放行回應後斷言：文件 rev5、仍是 tombstone、正文未被 restore 舊內容覆寫、代際不變；
   - 新 op 的 `expectedRevision=5`、`clientMutationId`／payload／`createdAt` 不變；
   - 下一輪 DELETE 成功（rev6）、`conflicts=0`、outbox 清空。
2. 「後備桶：同代際新操作接手時 `advanceOperationBase` 同樣只交接 revision」：
   - 直接對 localStorage 後備桶測同代際交接；
   - pending 為 null 時完全不動；
   - 代際不符時完全不動。
3. 反向驗證：暫時在兩條路徑把交接條件改成 `if (true)`（停用交接）→ 兩個測試失敗（expectedRevision 仍是 3／`rebased` 不是 true）；還原後 checksum 一致。

### D（Medium）備份還原忽略文章匯入失敗

#### 根因

`applySnapshotPayload()`（舊 `modules/sync-core.js:357-382`）：

```js
try { await articleStore.importDocuments(...); }
catch (error) { console.warn(...); }
```

- `importDocuments()` 回 `{ok:false,error}` 時沒有檢查；
- 例外被吞掉；
- `restoreSnapshotLocally()` 因此正常結束，UI 顯示「已從備份還原」。

#### 修正

- `modules/sync-core.js:357-404`：
  - 文章文件與閱讀資料都收集失敗到 `errors: [{group, error}]`；
  - 其他群組照常套用；
  - 回傳 `errors.length ? {ok:false, errors} : {ok:true, errors:[]}`。
- `modules/sync-core.js:489-493`：`applyMergedSnapshot()` 不拋出，回傳結果供除錯。
- `modules/sync-core.js:495-507`：`restoreSnapshotLocally()` 在 `ok:false` 時拋出 `Error`，帶 `code='snapshot_restore_failed'`、`errors` 明細；`features/sync/sync.js:2338-2340` 既有 try/catch 會顯示 `sync.restoreFailed`。

#### 測試設計（`tests/snapshot-restore-errors.test.mjs`，新檔）

1. 無 IndexedDB → article-store 走 localStorage 後備；放入損壞桶（`outbox` 是物件而非陣列）。
2. `restoreSnapshotLocally()` 斷言 rejects，`error.code==='snapshot_restore_failed'`、`errors` 含 `articleDocuments: storage_corrupt`。

4. `applyMergedSnapshot()` 斷言不拋出、回 `ok:false`。
5. 桶恢復合法後 `restoreSnapshotLocally()` 成功，文章與後備桶都有內容（反向驗證）。
6. 反向驗證：暫時讓 `applySnapshotPayload()` 一律回 `{ok:true}`（舊吞錯行為）→ 前兩個測試失敗；還原後 checksum 一致。

### E（Medium）單篇推送失敗／衝突仍被完成判斷覆蓋

  - 保持 `syncArticles()` 的 `ok:true`＋`pushed` 計數語意；

## 四、反向驗證紀錄

每項都先暫時回退、確認測試失敗，再還原並比對 SHA-256：

| 項 | 暫時回退方式 | 失敗證據 | 還原後 checksum |
| --- | --- | --- | --- |
| A | `pushOne()` 把讀取失敗當 `record=null` | `pushed.pushed` 實際 1 ≠ 預期 0 | `modules/article-sync.js` 一致 |
| B | 文章失敗轉 `[]`、閱讀忽略 `ok` | 兩個失敗情境都建立備份／更新簽章 | `modules/local-backup.js` 一致 |
| C | 後備與 IDB 交接條件改成 `if (true)`（停用） | 整合測試 `expectedRevision` 3 ≠ 5；後備測試 `rebased` undefined | `modules/article-store.js` 一致 |
| D | `applySnapshotPayload()` 一律回 `{ok:true}` | `restoreSnapshotLocally` 未拋錯、`applyMergedSnapshot` 回 ok:true | `modules/sync-core.js` 一致 |
| E | 移除 `articlePending` 分支 | 回傳 `syncDone` | `features/sync/sync-status.js` 一致 |
| F | 還原分支內 `!articleOk` 判斷失效 | 回 `sync.restoredEmpty` | `features/sync/sync-status.js` 一致 |

另對全部修改檔（含測試）以 `shasum -a 256 -c` 核對，全部 `OK`。

## 五、剩餘風險

1. **A 的錯誤碼粒度**：IDB 讀取失敗目前可能是 `idb_write_failed`／`idb_aborted`／`idb_read_failed`（取決於交易事件順序），測試只斷言有錯誤碼且不為成功，避免綁死底層事件名稱。
2. **C 的交接只處理版本基準**：若新操作是同代際但 `generation` 尚未寫入（升級前舊資料），`(pending.generation||0) === generation` 可能仍成立；若不符則維持不動，下一輪可能仍以舊 revision 送出，但不會誤改資料。這是保守取捨。
3. **D 的閱讀群組失敗**：`restoreSnapshotLocally()` 現在也會因 `readingStore.restoreAll()` 失敗而拋錯。若舊備份的閱讀資料格式只部分相容，使用者會看到「還原失敗」而非靜默部分還原；這是刻意的（必要群組不得假成功），但可能比過去更嚴格。
4. **B 的手動備份 UI 行為變更**：`createBackup('manual')` 回 `{error}` 時現在會顯示建立失敗，不再顯示成功。
