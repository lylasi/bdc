## 二、Findings

### F1｜P1：不同段落同時重試，整份記錄寫入會遺失其中一段結果

- 位置：`features/article/article.js:2350`、`modules/article-store.js:1579`。
- 重現：準備兩段失敗的文章，以持續讀取維持一筆真實 IndexedDB `docs` readwrite transaction；同時重試兩個不同段落，待兩次成功回應及保存排隊後釋放交易。
- 實測：兩段 DOM 均顯示 `done`，但記錄只保留第二段成功結果，第一段仍為失敗；重新載入後第一段成功譯文消失。已重現兩次，包括最後版本的 `article-store.js`。
- 原因與影響：兩個呼叫各自讀取舊記錄、複製整份 `paragraph_analysis`，再保存整份結果。`paragraphClaims` 能處理同段所有權，不能防止不同段落之間的更新遺失。
- 建議：以文章為單位序列化保存，或在提交時原子合併段落變更；加入真實交易排隊的雙段並發回歸。

### F2｜P1：批次保存 await 期間切換文章，舊任務續行仍會覆寫新畫面

- 位置：`features/article/article.js:5260`、`features/article/article.js:5274`。
- 重現：A 有失敗段、B 已成功。阻塞 IndexedDB，批次重試 A，待保存排隊後透過正式文章載入流程切到 B；釋放阻塞並 abort A 的結果寫入交易。
- 實測：切頁後原先為 B 原文、B 譯文及 `done`；A 保存失敗續行後，輸入框仍是 B，段落卻變成 A 原文、`分析失败`、`failed`，並出現「已重试 0 段，仍失败 0 段」。
- 原因與影響：保存前的歸屬檢查沒有涵蓋 `await saveAnalysis()` 之後；即使切頁已取消 job，失敗分支仍呼叫 `renderParagraph()`，後續摘要與進度清理也操作目前畫面。本次證明的是 B 畫面被污染，未證明 B 持久化記錄被改寫。
- 建議：保存完成後再次核對文章、版本、scope、job 及 claim；UI 更新與清理只能由仍持有目前畫面所有權的任務執行。

### F3｜P1：整篇分析保存失敗，仍顯示「已存入閱讀記錄」，重載後結果遺失

- 位置：`features/article/article.js:2641`、`features/article/article.js:2665`、`features/article/article.js:3543`。
- 重現：載入已有失敗結果的文章，修改原文並重新分析；讓正文保存成功、mock 分析成功，只 abort 最後包含完整分析結果的真實 IndexedDB 交易。
- 實測：段落顯示 `done`、失敗數為 0、批次重試隱藏，歷史提示顯示「已存入阅读记录 · 1秒钟前」；重載後成功譯文消失，恢復失敗狀態。
- 原因與影響：保存失敗提示隨後被 `updateHistoryIndicators()` 覆蓋；已有記錄被當作本次分析已成功保存的依據，使用者因此得到錯誤的保存承諾。
- 建議：讓持久化成功與否成為明確狀態，保留未保存結果及可用的保存重試入口，禁止一般歷史指示器覆蓋失敗狀態。
- 備註：此問題已在前次複核報告列為殘留風險；本次以真實交易失敗確認其影響，不視為新引入的回歸，但它直接違反 M1 的保存可靠性要求，仍屬阻斷。

### F4｜P2：成功整篇重分析後，`unsavedParagraphs` 舊標記沒有清除

- 位置：`features/article/article.js:2307`、`features/article/article.js:2660`、`features/article/article.js:3161`。
- 重現：單段重試成功但交易 abort，產生未保存標記；恢復正常寫入，對相同正文完成整篇重分析及保存；同一頁面內重新開啟該文章。
- 實測：重分析後顯示成功、失敗數 0；重新開啟卻變成「未能保存」、`分析失败`、失敗數 1。底層記錄實際已有成功譯文，整頁重載後又恢復成功。
- 原因與影響：清除函式以 `articleId + contentVersion` 找 bucket，但整篇成功路徑只傳 `articleId`。殘留標記覆蓋正確歷史結果，造成假失敗及不必要重試。
- 建議：以正確版本清除已成功提交結果對應的標記，補上「保存失敗→整篇成功→同頁重開→重載」回歸。

### F5｜P2：歷史失敗段切換語言，錯誤原因退化且留下簡體文字

- 位置：`features/article/article.js:2736`、`features/article/article.js:2839`、`features/article/article.js:2419`。
- 重現：開啟含 `provider_auth_failed` 的歷史失敗段，依次切換 `zh-CN → zh-HK → zh-CN`。
- 實測：「失败原因：供应商认证失败，请检查 Key」切至香港繁體後變成「失敗原因：分析失敗」，譯文側仍是簡體「分析失败」；切回簡體也無法恢復原認證錯誤原因。
- 原因與影響：歷史狀態節點缺少 `data-error-code`，失敗譯文節點缺少 `.analysis-failed-inline`，因此 `refreshParagraphDynamicTexts()` 無法正確刷新。除了混合語言，也丟失可操作的錯誤資訊。
- 建議：統一即時與歷史渲染的錯誤 metadata、翻譯節點標記，覆蓋兩個方向的語言切換測試。

### F6｜P2：回答中新增助手會話，停止入口消失，但 `activeAsk` 仍封鎖新會話

- 位置：`features/assistant/assistant.js:976`、`features/assistant/assistant.js:642`、`features/assistant/assistant.js:226`。
- 重現：送出第一題並保持 mock SSE 未完成；停止按鈕出現後按「新增會話」，再送第二題。
- 實測：停止按鈕數量變成 0；第二題留在輸入框，顯示「上一个回答仍在进行中」，provider 請求數仍為 1。釋放舊回應後，它保存於舊會話，新會話仍沒有第二題。
- 原因與影響：新會話清空訊息 DOM，連同停止按鈕一併移除，但沒有處理舊 `activeAsk`。使用者在原請求結束前無法送出，也失去停止入口；未觀察到跨會話資料寫錯。
- 建議：明確處理回答中的會話切換：禁止切換，或取消並完成舊請求的收尾，再切換；保留 token 所有權及 `cancelled` 訊息語義。

## 六、殘留風險與 Phase 2 前置條件

本次未驗證真實 AI／TTS、手機／IME／無障礙、真實長時間 provider timeout、多分頁競態，以及舊客戶端對 `cancelled` 訊息的同步往返。`audit-flows.cjs` 因會寫入工作區報告／截圖而未執行，也沒有宣稱完整專案瀏覽器驗證清單已全部通過。

審核期間其他會話持續修改工作區。HEAD 維持 `5839aa7be4453c70e560e643fbd07610329a6c90`，核心 `article.js`、`assistant.js` 內容未變；共享 `article-store.js` 有外部變更，F1 已在其最後版本重跑並仍可重現。其餘測試結果對應各自執行時版本，不能視為對全部並行 WIP 的最終認證；本報告也不據此歸責其他會話的 diff。

正式進入 Phase 2 前，需要：

1. 關閉 F1–F3 三項 P1 阻斷，恢復保存及切頁一致性。
2. 修復 F4–F6，完成本輪要求的狀態、雙語與助手生命週期驗收。
3. 補入本次六組缺失回歸，固定整合版本後重跑受影響測試並獨立複核。

**目前不可宣告 M1 完成，也不可將現況作為已驗收的 Phase 2 基線。** 音訊 owner 的正式功能仍屬 Phase 2，本次未把它的 skip 誤列為 M1 阻斷；阻斷來自已實際重現的保存可靠性與工作歸屬問題。
