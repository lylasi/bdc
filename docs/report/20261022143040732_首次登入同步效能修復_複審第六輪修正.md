## 1. 問題 1：舊回執（revision 4）在重建後把新代際推回去

### 1.1 根因

`supersededMutations` 是「重建當下 outbox 上那一個 mutation」的黑名單：

- 重建之前就已送出、但回應還沒回來的 mutation（分頁 B 的 PUT）不在清單裡；
- 重建成功、outbox 被清空之後，清單本身也隨操作消失，防護整體失效；
- 另一分頁的記憶體完全不知道重建發生過（沒有任何跨分頁訊號）。

因此 `markOpDone` / `markOpsDone` 只憑「mutation 不匹配」推論出「舊回執只推進 revision」，
於是把 `revision: 4` 寫回剛重建（revision 0）的文件，並把待建立操作 rebase 成
`update` / `expectedRevision 4`；重建完成後才回來則直接把本機推到 4，遠端停在 1。

### 1.2 修正：持久化的「重建代際」

新增持久化欄位 `generation`（文章文件 `<scope>/docs`、摘要 `article_summaries`、outbox 操作三處）：

- 每次「伺服器確認 404 → 改以建立重送」就把文件的代際 +1（`mergeStoredRevision` 的 `resetRevision` 分支）；
- 新建立的 outbox 操作帶著當下的代際（`createOutboxOp`）；
- 所有回執（`markOpDone` / `markOpsDone`，以及 sync 端組出的批次核對）都帶上「它自己所屬操作」的代際；
- 交易內以**持久化文件**的代際為準：
  - 代際不同 → 不得改動 `revision` / `updatedAt`，不得刪除或 rebase 目前的 outbox；
  - 代際相同 → 維持原本語意：匹配就完成確認，不匹配就 rebase 基準（合法舊回執仍可推進 revision、保留新修改）；
- `rebasePendingOutbox` 另外要求「回執代際 = 文件代際 = 操作代際」三者一致，才允許改 `type` / `expectedRevision`。

舊資料沒有 `generation` 一律視為 0（`Number(x) || 0`），只有文件也仍在 0 代際時回執才生效，
因此既有資料不會突然全部被判定過期。

### 1.3 `supersededMutations` 的處置（有界）

由代際機制取代寫入端：`createOutboxOp` 不再累加這個欄位，只**繼承既有（升級前就存在）清單的末 8 筆**
（`LEGACY_SUPERSEDED_LIMIT`），讀取端也只比對末 8 筆。因此它不會隨重建次數無界成長，
同時保留升級前留在 outbox 的舊操作的一次性相容。

## 2. 問題 2：另一分頁保存時，舊記憶體 revision 會復活

### 2.1 根因

`persistDocWithOp` 的交易內雖然讀到持久化 revision 0，但 `mergeStoredRevision` 只做
`Math.max(記憶體 3, 儲存 0) = 3`。它沒有任何資訊可以區分「同一代際的正常並行寫入」與
「上一個代際殘留的記憶體版本」，於是寫回 `type=create / expectedRevision=3`：
建立後遠端 revision 1、本機 3，下一次修改必 409。

### 2.2 修正

`mergeStoredRevision` 先用代際判斷基準：

- `stored.generation > memory.generation` → 採用持久化文件的 `revision`（重建後為 0，建立成功後為 1）
  與新代際，**保留使用者這次的正文／分析／標題**；
- 代際相同 → 維持原本 `Math.max` 語意（避免同代際合法舊回執推進的版本被蓋回）。

文件、摘要、outbox 都在同一個交易、用同一份 `merged` 產生，因此三者基準一致；
`record.revision` / `record.generation` 也會寫回呼叫端的記憶體記錄，
`replaceRecord()` 不會再用交易前的舊值覆蓋。

### 2.3 修改位置

同 1.4 的 `mergeStoredRevision`（`:521-546`）、`persistDocWithOp`（`:607-692`）、
`persistDoc`（`:428-471`）、`persistDocWithMeta`（`:2201-2252`）。

## 3. 跨分頁測試設計

新增 `tests/article-rebuild-generation.test.mjs`（6 個案例）與
`tests/helpers/article-sync-server.mjs`（可暫扣回應的 mock Worker）：

### 3.1 兩個真正的模組實例

Node 的 ESM 快取以解析後 URL 為鍵，因此用 `module.registerHooks({ resolve })`
替「專案內、非 tests/」的模組加上 `?tab=a` / `?tab=b`：

- `article-store`、`article-sync`、`state`、`permanent-db`、`sync-cloudflare`…每個分頁各一份記憶體狀態；
- 子模組沿用父模組的 tab（執行期 `await import('./reading-store.js')` 才不會拿到另一分頁的實例）；
- `globalThis.indexedDB`、`localStorage`、`fetch` 共用 → 完全對應「兩個瀏覽器分頁共用同一份儲存」；
- 測試開頭直接斷言 `tabA.store !== tabB.store`，避免退回單實例假通過。

### 3.2 共用 mock 伺服器

新增 `tests/helpers/article-sync-server.mjs`：只實作 article-sync 會打的路徑
（游標拉取／批次取文件／建立／更新／刪除／舊資料匯入），並提供 `hooks.afterPut`
讓測試可以「伺服器已提交、回應暫扣」。時間戳用嚴格遞增的合成時間，
`updatedAt` 的斷言才有鑑別力（同一毫秒的兩次寫入不會撞在一起）。

### 3.3 案例

| # | 案例 | 驗收對應 |

## 6. 仍存風險與未完成項

1. **（既有缺口，HEAD 已存在，本輪未修）** `markOpFailed()` 經 `persistDocWithMeta()` 會用記憶體內容
   覆寫文件；若上傳失敗發生在本機已保存新正文之後，正文可能被覆回舊內容
   （`modules/article-store.js:2201-2252`；原缺口描述在 `:2096` 附近，行號已因本輪新增程式碼位移）。
   本輪只讓它「代際／版本不前進」不倒退（不會讓防護失效），未改其正文處理。
2. **（既有缺口，HEAD 已存在，本輪未修）** IndexedDB 不可用時，localStorage 匯入後確認回傳
   `idb_unavailable`，outbox／gate 未清（`modules/article-store.js` 的 `applyRemoteDocs`
   `idb_unavailable` 分支，原描述 `:1990` 附近）。需要另一輪把 fallback 路徑的套用／確認補齊。
3. **`supersededMutations` 僅剩相容讀取**：升級前就存在的 outbox 操作若仍在等待上傳，
   其清單最多 8 筆、不再成長；一旦該操作被重建取代（換代際），代際 fence 便接手。
   極端情況（升級前重建、且重建當下沒有記錄到 mutation）仍只能靠代際，別無他法。
4. **代際只在單篇文章層級**：`generation` 不隨遠端 revision 變化，也不會在「伺服器資料被清空但本機
   沒有送出 404 請求」時自動遞增；若遠端被清空而本機從未嘗試上傳，下一次 PUT 會拿到 404 並走
   同一條重建流程（行為不變）。
5. **並行修改風險**：`tests/phonetics.test.mjs` 等既有失敗與本輪無關，但全量 `tests/*.test.mjs`
   目前不是全綠；建議後續單獨修該測試的 import 剝離邏輯，不要誤判成本輪回歸。
6. **未跑瀏覽器巡檢**：本輪改動集中在 IndexedDB 交易與同步回執，已用 fake IndexedDB＋雙實例覆蓋；
   未另外跑 Playwright 的 `tests/article-*.cjs`，因為需要額外的 Playwright 模組與伺服器環境
   （本輪約束只要求 node 測試與 i18n 檢查）。
