## 二、測試方法（與基線的差異）

- 以 `tests/helpers/extension-mv3.cjs` 建立**真正的 MV3 擴充載入**與**真正的 Worker／D1 SQLite 帳戶服務**（ALICE／BOB／ADMIN，含 catalog 發布、snapshot、credential 路由）。
- 目錄（catalog）刻意發布**兩個 managed 供應商，兩者都提供同名模型 `shared-model`**，用來偵測「供應商被移除後是否被靜默換到另一個供應商」。
- 個人供應商**不是**直接寫 localStorage：先以真實 `POST /snapshot` 寫入帳戶 AI 設定，登入後由擴充套件 `pullExtensionAISettings` 套用，再透過產品 UI 的「匯入本機金鑰」流程匯入金鑰（`#ext-import-provider-select` / `#ext-import-key-input` / `#ext-import-key-btn`）。

## 五、缺陷 D69：帳戶 snapshot 只帶 `tasks` 時，用途模型對應被忽略（Low）

**嚴重度**：Low（資料路徑健壯性；官方現行客戶端同時鏡射 `models` 與 `tasks`，正常流程不會觸發；但一旦觸發就是無提示地用錯模型）

**受影響行為**：擴充套件面板的「帳戶預設模型」與「恢復帳戶設定」都依賴 `applyRemoteAISettings` 套用帳戶 snapshot 的用途對應；當 snapshot 的 AI 設定只有 `tasks` 而 `models` 是空物件時，模型對應會被丟棄。

**重現步驟**（真實 Worker／SQLite，非 mock）：

1. 以 BOB token 呼叫 `POST /snapshot`，payload 的 `aiSettings.settings` 只帶：
   ```json
   {"aiSettings":{"updatedAt":"2026-11-06T01:00:00.000Z","settings":{"providers":{},"tasks":{"wordAnalysis":"managed-backup:alt-model"},"thinking":{"wordAnalysis":"medium"}}}}
   ```
   （Worker 端 `sanitizeSnapshotAISettings` 會補上 `"models": {}`，`tasks` 保留；實測寫入後讀回：`"models":{},"tasks":{"wordAnalysis":"managed-backup:alt-model"},"thinking":{"wordAnalysis":"medium"}`）
2. 在擴充套件頁面以 BOB 登入 → 自動 `pullExtensionAISettings` → 若有本機覆寫，先按「恢復帳戶設定」清除。
3. 觀察 `getExtensionAITaskSettings('wordAnalysis')`：`model = managed-backup:shared-model`（目錄預設），`thinking = medium`（帳戶值已生效）。

**預期**：`model = managed-backup:alt-model`（帳戶的用途對應）。
**實測**：`model` 被忽略、`thinking` 生效 → 模型與思考來源不一致，且無任何錯誤或提示。

**根因（唯讀定位，未修改）**：
- `modules/ai-profile-storage.js:532` 與 `extension/modules/ai-profile-storage.js:532`
  ```js
  profile.taskModels = normalizeTaskModelMap(remote.models || remote.tasks);
  ```
  `remote` 來自 `sanitizeAISettings()`，該函式**必定**輸出 `models` 鍵（來源缺省時為 `{}`，空物件在 JS 中為 truthy），因此 `remote.tasks` 永遠不會被讀到。
- 伺服端 `cloudflare-worker/src/snapshot-sanitize.js` 的註解明示 `tasks` 是 `{...models, ...tasks}` 的合併權威來源，客戶端卻優先讀 `models`。

**建議修法（未實作）**：合併兩者或忽略空物件，例如
`normalizeTaskModelMap({ ...(remote.tasks || {}), ...(remote.models || {}) })`
（主站 `modules/ai-profile-storage.js` 為同一份邏輯，需一併調整以維持一致）。

**證據指紋**：缺陷所在 `modules/ai-profile-storage.js` 與打包副本 `extension/modules/ai-profile-storage.js` 同為 `8968bbaed062911835a624367135eff4098c33a21b751c84dc8111a43fae179b`；`modules/ai-settings-sanitize.js` = `6284741710a92240a4358b2a5f39f773cf6ebeb2efebfa6afa0108f654eec705`；伺服端 `cloudflare-worker/src/snapshot-sanitize.js` = `8713f9bd36c060f533b02087cdbb45132ec6d3aaaf9458df0b05a9eda2ac630b`；本項檢查的 `detail` 見 `results.json` 的 D69。

## 六、觀察 O1：跨分頁並行修改會遺失其中一筆，且兩頁都顯示「已保存」（Low）

**嚴重度**：Low（需同時在兩個擴充頁面操作；不會損毀資料，只會遺失一筆選擇；但屬於「假成功」類問題）

**重現步驟**：

1. 在同一個擴充 origin 開兩個頁面（`chrome-extension://<id>/lookup.html` 兩次；等價於 popup + 分頁）。
2. 兩頁都登入同一帳戶，等 AI 面板就緒。
3. 頁面 A 選「文章提取」、頁面 B 選「文章翻譯（段落 / 全文）」。
4. 同一瞬間各自變更模型（`Promise.all` 同時觸發 change）→ 兩個下拉都顯示「已保存」。
5. 讀取 `localStorage` 的 `bdc_extension_ai_preferences_v1:[endpoint, user]`：只有其中一個用途的覆寫存在。

**實測（本輪 6 次啟動）**：

| 啟動 | 遺失回合 |
| --- | --- |
| run A（4 回合） | 4/4（文章提取那一筆） |
| run B（4 回合） | 0/4 |
| run C（8 回合） | 8/8 |
| run D（8 回合） | 8/8 |
| run E（8 回合） | 0/8 |
| run F（8 回合，正式報告那次） | 8/8 |
| 合計 | 44 回合中 36 回合遺失；6 次啟動中有 4 次受影響；受影響的 4 次啟動全部同時出現「兩頁都顯示已保存」 |

排程不同會導致「先讀到舊值的那一頁」覆蓋另一頁，因此有時 0 遺失；這正是非原子讀改寫的典型表現。

**根因**：`modules/extension-ai-preferences.js:41-43` 的註解宣稱
> Read/modify/write is synchronous, so two trusted extension pages cannot lose unrelated task edits.

同一頁內重新渲染是同步的，但**跨頁之間** `getItem` 與 `setItem` 不是原子操作；`storage` 事件只在寫入後非同步送達，無法阻止兩頁同時以同一基準值寫回。

**建議修法（未實作）**：偏好寫入改為帶 revision 的 CAS（寫入前重讀並比對 revision，衝突則重試合併），或在 `storage` 事件到達後偵測自己的 patch 是否仍在，否則重套並提示；至少不要把「已保存」當成跨頁安全。

**證據**：`results.json` 的 `notes`（`cross-page concurrent write: ...`）；本次正式報告那次為 `8/8 rounds lost ... both pages showed the saved notice in 8/8 rounds`。

## 七、觀察 O2：思考降級沒有回饋（Info）

- 實測（D16）：供應商對 `reasoning_effort=high` 回 400，產品自動以「不帶參數」重試成功；`bdc:ai-thinking-fallback` 事件確實發出一次（`{"task":"wordAnalysis","level":"high","provider":"managed-backup","model":"alt-model"}`），但面板仍顯示「高強度」，查詢結果也沒有任何提示。
- 全庫檢索 `bdc:ai-thinking-fallback` 只有 `modules/api.js`（主站）與 `extension/modules/api.js`（擴充）在發事件，**沒有任何 UI 監聽**。
- 面板提示文字已寫「思考程度的實際支持取決於模型」，但使用者仍無法得知該次請求實際沒有套用所選層級。
- 建議（未實作）：在面板顯示一次性提示（例如「此供應商不支援該思考程度，已改用預設」），或把事件接到 `#ext-ai-notice`。

## 八、觀察 O3：恢復帳戶設定後「模型跟隨帳戶、思考跟隨應用預設」的不對稱（Info）

- 實測（D27）：帳戶只設定了 `wordAnalysis` 的模型與 `thinking.wordAnalysis=low` 時，文章擷取按「恢復帳戶設定」後得到 `model=personal-lab:lab-model`（因為解析鏈 `articleCleanup → articleAnalysis → wordAnalysis`），但 `thinking=auto`（應用預設，而非帳戶的 low）。
- 這與主站既有的 `resolveThinkingLookupKeys` 規則一致（只有 `articleWordTranslation／articleWordTooltip／articlePhraseTranslation／articlePhraseAnalysis` 繼承 `wordAnalysis` 的思考），不是本次回歸；但擴充面板把模型與思考放在同一個「用途」下呈現，較容易讓使用者誤解「恢復帳戶設定」兩者會同源。
- 建議（未實作）：面板摘要或提示寫明「思考程度來源」，或讓文章類用途的思考也一併繼承 `wordAnalysis`。

## 九、其他實測發現（非缺陷）

- 移除供應商後，選擇器把當前值標為「（目前值不可用）」並停用該選項，**已保存值不會被改寫**；直接查詞會得到「此供應商已停用或不存在，請重新選擇」，且**沒有**任何送往同名模型另一供應商的請求（D47、D48）。
- 明確選定的模型失敗時不會改用其他模型（D56：只有 1 個請求，無第二名候選）。
- 快取以 endpoint + userId + 模型 + 思考 + promptVersion 分區（D12、D57）；但 managed 快取鍵也包含 catalog version，管理員重新發布目錄後既有快取會失效（本輪因此用「跳過快取重新請求」驗證請求內容，屬既有設計）。
- 偏好保存失敗的兩種情況（`setItem` 拋錯、`setItem` 靜默不落盤）都會顯示「未能保存，請重試」、選單回到已保存值，且不會顯示成功（D32、D33）；恢復後可正常保存（D34）。
- `chrome.storage.local` 僅有 `bdc_capture_books_v1:<scope>` 與 `bdc_extension_ui_locale`，不含偏好、金鑰或 token（D31B、D65）。
- 跨 endpoint 切換時，本機 `local-only` 的個人金鑰會隨舊 profile 清除（既有設計），偏好則保留；回到原 endpoint 後偏好仍在、金鑰需重新匯入（D44、D45；截圖 `controls-zh-CN.png` 可見重新同步後的匯入提示）。
- 小瑕疵（Info）：對某用途按「恢復帳戶設定」後，若該帳戶已無其他覆寫，`localStorage` 仍會留下一個空物件鍵（`bdc_extension_ai_preferences_v1:[...]:{}`），無功能影響。
