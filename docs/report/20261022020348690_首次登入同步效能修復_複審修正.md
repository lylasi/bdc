# 首次登入同步效能修復 — 複審修正

- 日期：2026-10-22
- 前置報告：
  - `docs/report/20261022003649630_首次登入同步緩慢原因分析.md`
  - `docs/report/20261022013327028_首次登入同步效能修復.md`
- 範圍：只修改本輪 5 個問題相關的前端同步／閱讀儲存、Worker handler 與測試；未修改其他 session 的無關檔案，未改 `ai-config.js`，未 git commit／push。

## 摘要

本輪完成 5 項複審修正：

1. **快照快取帳戶污染**：`pullSnapshot()` 在請求入口捕捉 endpoint／user／token／generation，所有等待後、快取讀寫與 fallback 前都驗證同一 session；快取鍵帶 generation。A→B、A→B→A 的遲到回應一律以 `stale_session` 中止，不會以完成時帳戶回填快取。
2. **閱讀批次覆寫本機修改**：遠端批次先做 readonly 預取，但權威的本機 entity／outbox 讀取、三方合併與寫入全部移到同一個 readwrite 交易內，且透過 `serializeWrite()` 與本頁其他寫入共用序列；交易提交成功後才更新記憶體。補讀預取不再改寫任何全域記憶體。
3. **條件快照忽略遷移閘門**：文章／閱讀 `final` 開啟舊資料寫入閘門時，在同一個 DB batch 原子推進 `snapshots.version`。舊版本條件讀取會取得新版本與已移除的舊群組；不帶 `version` 的舊客戶端也看到同一份有效內容。Worker 與 selfhost 共用同一批 handler，契約一致。
4. **大型首次匯入無法續傳**：`pushLegacyMigration()` 改為每個 import 批次成功後立刻按 50 篇核對並持久化完成進度，再處理下一批；`final` 只在全部批次完成後送出。逾時後下一輪只處理尚未完成的 outbox。
5. **匯入預讀過期競態**：批次寫入遇到唯一鍵衝突時，重新讀取該批已存在的 ID／legacy ID，過濾後安全重試；`imported/skipped/ids` 只依實際成功寫入累計，change log 與序號不會為被跳過的項目產生 create。重送同樣資料只會 skipped。

## 逐項修改

### 1. 快照快取 session 隔離

- `modules/sync-cloudflare.js:651`：快取加入 `generation`，快取鍵為 `endpoint::userId::generation`。
- `modules/sync-cloudflare.js:671`：`rememberSnapshot(session, ...)` 只接受入口 session；完成時帳戶已變更就不再寫快取。
- `modules/sync-cloudflare.js:686`：`cachedSnapshot(session, version)` 同時比對 key／generation／版本，且呼叫時 session 必須仍有效。
- `modules/sync-cloudflare.js:703`：公開 `pullSnapshot()` 只捕捉一次 session，交給內部的 `pullSnapshotForSession()`。
- `modules/sync-cloudflare.js:706`：`apiRequest()` 回來、解析 JSON、`notModified` 命中、fallback 與寫快取前都重新驗證；過期即丟 `stale_session`（HTTP 語意 409）。

驗收測試：`tests/snapshot-session-cache.test.mjs`
- A→B：A 的 `/snapshot` 延遲完成後必須 `stale_session`；B 第一次讀取必須是完整 GET（不能帶 A 的 `version=`），B 快取內容必須是 B payload；B 同步不得 POST。
- A→B→A：generation 已改變，舊 A 回應不得被接受；回到 A 後第一次仍完整 GET，第二次才使用 A 自己的條件快取。

### 2. 閱讀批次原子合併

- `modules/reading-store.js:1945`：`loadMissingEntities()` 降級為 readonly 預取，只確認資料可讀，不回寫 `messagesById` 或其他全域狀態。
- `modules/reading-store.js:1985`：`applyRemoteEntities()` 先預取缺失項目，再進入 `serializeWrite()`。
- `modules/reading-store.js:2037`：`applyRemoteEntitiesInTransaction()` 在單一 readwrite 交易內：
  - 一次讀取本 scope 全部 outbox；
  - 讀取每個遠端項目當下最新的本機 entity（message 以 scope 一次讀取）；
  - 用 `planRemoteChange()` 合併並在交易內寫入 entity／outbox；
  - 交易成功後才更新記憶體與衝突標記。
- 交易失敗（含寫入注入失敗）直接回報錯誤，不更新記憶體；`idb_unavailable` 才切換 localStorage 後備，且後備讀寫仍在同一序列內。

驗收測試：`tests/reading-remote-apply.cjs`（真實 Chromium + IndexedDB）
- 暫停缺失 A 的預取讀取，完成 `patchLearningItem('item-b', { note: 'new local note' })`，再放行遠端批次；永久 entity 與 outbox 都保留新筆記，同時合併遠端 `sentence`。
- 注入 `reading_items` 寫入失敗；entity、outbox、記憶體都維持原值，A 沒有部分寫入。

### 3. 遷移閘門推進快照版本

- `cloudflare-worker/src/articles.js:73`、`cloudflare-worker/src/reading.js:66`：新增 `bumpSnapshotVersionStatement()`（`UPDATE snapshots SET version = version + 1 ...`）。
- `cloudflare-worker/src/articles.js:561`：`/articles/import` 提前讀取 `article_state`；空批次或非空批次的 `final` 都把「開啟閘門 + 推進快照版本」放在同一個 `env.DB.batch()`。
- `cloudflare-worker/src/reading.js:440`：`/reading/mutations` 的 `final` 且全部成功時，同一個 batch 更新 `reading_state` 並推進快照版本。
- `selfhost/server.mjs` 與 Worker 共用 `handleArticlesRoute`／`handleReadingRoute`，因此 SQLite／PostgreSQL 與 D1 使用同一契約；沒有另寫一套 selfhost 邏輯。

驗收測試：
- `tests/articles-protocol.test.mjs`：Worker D1 與 selfhost SQLite 各跑一次：舊快照（version 1，含 articles + vocabulary）→ 完成文章 `final` → `GET /snapshot?version=1` 必須回 version 2、`notModified` 不存在、articles 移除、其他群組保留；無 `version` 的舊客戶端看到相同內容；舊客戶端寫回 articles 被 409 擋下。
- `tests/reading-protocol.test.mjs`：Worker D1 與 selfhost SQLite 各跑一次：舊快照含 vocabulary／assistant；建立 `vocabularyEntry` 後以 `delete` + `final` 建立 tombstone 並關閘；`GET /snapshot?version=1` 必須回 version 2、無 vocabulary／assistant、payload 不含 `entry-ghost`；`/reading/batch` 仍看得到墓碑；無 `version` 舊客戶端一致；舊快照寫入被 409 擋下。

### 4. 匯入逐批核對與續傳

- `modules/article-sync.js:365`：抽出 `verifyLegacyRecords()`，按 `ARTICLE_LIMITS.batchMax`（50）核對並以 `markOpsDone()` 持久化。
- `modules/article-sync.js:405`：新增 `runLegacyImportBatches()`；每個 `importChunk` 成功後立刻對該批 records 呼叫 `verifyChunk`，全部完成才 `finalize`。
- `modules/article-sync.js:450`：`pushLegacyMigration()` 改用上述 runner；import 失敗／逾時會直接往外拋，已完成批次的 outbox 已清除；`final` 失敗保留 `gatePending` 供下一輪重試。

驗收測試：`tests/article-import-progress.test.mjs`
- 700 篇、每批 55 秒、整輪 300 秒：第 6 批逾時後，第一輪已確認 500 篇；第二輪只送剩下 200 篇，總 import 呼叫 7 次，沒有重傳已確認 ID；outbox 每完成一個 50 篇核對就嚴格減少；最後 `final` 只呼叫一次並涵蓋全部 700 篇。
- 既有 120 篇回歸 `tests/article-import-batch.cjs` 仍通過：import 3 次（100＋20＋final）、batch 3 次、逐篇 create 0 次、409 0 次。

### 5. 匯入預讀競態

- `cloudflare-worker/src/articles.js:605`：`flush()` 改為重試迴圈：
  - 第一次照原批次寫入；
  - 若 batch 因唯一鍵衝突失敗，重新以 `readExistingIds()`／`readExistingLegacyIds()` 讀取該批；
  - 過濾已由其他請求建立的項目（計入 `skipped`、扣回暫記用量），其餘重建 insert + change + advance 語句後重試；
  - 最多 4 次，非衝突錯誤最終照原樣拋出。
- `imported`／`importedIds` 只在 batch 成功後累計；被跳過的項目不再產生 create change 或前進序號。
- `cloudflare-worker/src/articles.js:557`：預讀仍在請求開始時一次完成，保留原本的批次效能。

驗收測試：`tests/articles-import-race.test.mjs`
- 兩請求屏障：A 先插入 8 篇，B 的預讀在 A 插入前完成但寫入被延後；B 第一批衝突後重讀、跳過 8 篇並補入其餘 8 篇。總數 16、每篇只有 1 筆 create change、A 的內容沒有被 B 覆寫；B 重送只 skipped，不新增資料。
- legacy ID 衝突：B 預讀空集合後 A 先插入同一 legacy ID；B 寫入衝突後重讀、跳過該筆，只保留 A 的內容與 1 筆 create change；重送不新增。
- 覆蓋 `createSqliteDatabase` + `createD1Adapter` 的 Worker 路徑。
- PostgreSQL 以臨時 Docker `postgres:16` + selfhost `DB_DRIVER=postgres` 實測：文章／閱讀 final 後條件快照版本為 3 且舊群組消失；用 trigger 延遲 insert 讓兩個 import 請求都在插入前完成預讀，結果一邊 imported 8、另一邊 imported 8／skipped 8；legacy ID 併發結果為 imported 1 與 skipped 1；共 16 篇文章、17 筆 create change，無重複或覆寫。此為臨時驗證，未新增需 PostgreSQL 的常駐測試。

## 未完成事項與風險

1. **部署前已關閘的舊帳戶**：本輪的版本推進發生在「閘門由 0 變 1」的最後一次 final。若某帳戶在部署前就已經關閘，且某台裝置仍持有部署前載入的舊記憶體快照快取，該裝置的舊版本條件讀取仍可能命中 `notModified`，直到頁面重新載入或快照版本因其他寫入前進。新部署後的關閘流程、以及所有重新載入後的裝置，都不受此影響。若要完全消除此殘留風險，可另做一次性後端遷移，為已關閘帳戶推進版本；本輪沒有修改既有資料。
2. **閱讀預取多一次 readonly 讀取**：`applyRemoteEntities()` 先補讀缺失實體，再於交易內重讀全部項目，換取「等待期間的本機修改不會被舊值覆蓋」與可測試的中斷點。這是本機 IndexedDB 讀取，成本遠低於原本的逐筆交易；但大量批次仍會多一輪 get。
3. **匯入續傳測試是 runner 層虛擬時鐘**：測試直接驅動 `runLegacyImportBatches()` 的批次與逾時，驗證 outbox 進度；實際 `apiRequest()` 的 5 分鐘 deadline 由既有 `sync-cloudflare` timeout／round 邏輯負責，120 篇端到端回歸已覆蓋真實請求路徑。
4. **PostgreSQL 未納入常駐測試**：本次以臨時容器實測通過；repo 內仍只有 SQLite／D1 adapter 測試，沒有 `pg` 依賴與 CI PostgreSQL 服務。SQL 只用標準語法，selfhost 的 `batch()` 在 SQLite／PostgreSQL 都以交易執行。
5. **未改動同步階段仍為串行**：文章 → 閱讀 → 快照的順序與首次初始化游標策略不變；本輪只修復複審列出的 5 項，不包含先前報告的「初始化快照／一致游標」新契約。
