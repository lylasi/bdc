# Kokoro 逐句朗讀延遲實測

- 日期：2026-10-28。
- 問題：文章每句各呼叫一次 Kokoro API，是否會比先前 TTS 慢很多。
- 結論：**直接接入 BDC 現有「本句播完才請求下一句」流程，這次測到的 Kokoro CPU 首音訊等待約 2.9–3.4 秒，會成為明顯句間空白。** 未與實際舊服務在相同輸入、裝置及網絡下作 A/B，不能聲稱比舊服務慢幾倍。
- 狀態：Kokoro 仍是獨立試聽服務，本次沒有把它接入 BDC，也沒有修改播放程式或容器資源配置。

## 一、測試環境與指標

- 主機：前輪已核對的 Apple Silicon、36 GiB 記憶體 Mac。
- 容器：`bdc-kokoro`，CPU 上限 4 核、記憶體上限 6 GiB，已完成預熱。
- 端點：`http://10.10.10.5:8880/v1/audio/speech`。
- 聲線：美音 `af_heart`，`speed=1.0`，MP3。
- 方法：同一用戶端循序呼叫三個句子，再測三句合併段落，分別記錄 HTTP headers、首個非空音訊 body、首 4 KB、完整回應及 ffprobe 音訊時長。沒有故意等待播放完成才發下一次測試；下方總時長為根據資料推算。
- 每個輸入只測一次，沒有控制其他主機工作，結果屬當前環境的樣本，不是統計基準或多用戶併發測試。
- 首音訊 body 不等於實際出聲：瀏覽器解碼與起播緩衝還可能增加延遲。HTTP headers 很快返回亦不代表已有可播放音訊。

| 第一句 | 61 | 2.858 秒 | 2.859 秒 | 3.480 秒 |
| 第二句 | 87 | 3.385 秒 | 3.385 秒 | 4.800 秒 |
| 第三句 | 83 | 3.200 秒 | 3.201 秒 | 4.416 秒 |

## 三、現有 BDC 調度的影響

本次唯讀核對以下程式：

- `features/article/article.js:5014`：文章分句／分段建立朗讀塊。
- `features/article/article.js:5224`：全文亦強制按句播放，不是一次合成全文。
- `features/article/article.js:5268`、`:5285`、`:5310`：完成回調檢查播放狀態、增加重複計數或移到下一塊，再呼叫下一次播放。
- `modules/audio.js:351`：HTTP 音訊由 `onended` 觸發文章的 `onEnd`。
- `modules/audio.js:362`：每次給同一個共用 Audio 元件設定當前 URL，再 `load()`／`play()`。

目前可概括為：

```text
本句播放結束
    → 請求下一句
    → 等待生成及可播放音訊
    → 下一句開始
```

這條路徑沒有下一句預取、雙緩衝佇列或應用層音訊快取。因此若新後端首音訊需約 3 秒，等待會直接出現在句間。舊 HTTP TTS 亦走同一調度，但舊服務可能有不同的生成、串流或快取表現；本次未取得同條件比較。

此外現有 BDC 的 GET `/tts` 與 Kokoro POST `/v1/audio/speech` 仍需適配。不能只修改服務地址就把本次結果當作已整合完成。

## 四、串流與整段請求的觀察

部署實例的 OpenAPI 宣告 `stream` 預設 true；但這次句子與 233 字符段落在首個非空 body 返回時，完整音訊亦已幾乎返回完畢。

尤其合併三句的 `stream=true` 請求，headers 約 0.003 秒就返回，音訊 body 卻到 **7.716 秒**才開始，與完整回應時間相同。因此本次沒有觀察到段落在生成完成前便提早播放的優勢，不能僅靠設定 `stream=true` 宣稱首音訊延遲已解決。

把文字合成為一段可減少請求邊界及句間等待，但會增加第一次起播等待，亦影響逐句高亮、跳句和取消的設計。不能把「整篇送一次」當作所有文章的無條件解法。

## 五、建議接入方式

**優先做有限量預取，而不是一播完才開始下一次合成。**

```text
開始播放第 N 句
    同時生成第 N+1 句並存入暫存
第 N 句結束
    播放已準備好的第 N+1 句
```

這次每句生成時間都短於其播放長度，故單一生成工作的下一句預取有機會遮蔽大部分等待。不是所有情況均有保證：例如很短的上一句、較長的下一句、加速播放、首次語言載入、其他裝置同時請求，都可能需要多緩衝一句或採取回退。

接入時可採：

1. 首次只等待第一句或少量起始緩衝；播放時預取下一至兩句。
2. 同一時間限制一個生成工作，避免多個預取請求爭用這個 CPU 容器。
3. 以文章文字、聲線、速度、模型版本等為鍵快取音訊；重播及上一句可重用。
4. 跳句、取消、文章切換或聲線／速度改動時，取消過期請求並丟棄舊結果。
5. 保留目前的完成、暫停及聽寫狀態語義；Blob 播放或排程不應讓舊回調推進新會話。
6. 預取仍趕不上時，才考慮提高推理效能或合併適量句子；先量測，避免直接堆 CPU 或同時請求整篇。

本次只提供驗證與接入建議，未執行上述產品修改。
