## 2. 必修問題（建議本次修完再複驗）

### P1 · 「更多」選單被全域 `details` 樣式裁切，三個工具入口不可用

**確切重現步驟（1440 與 390 均可重現）**

1. 開啟任一文章詳解，點標題列「本文學習記錄」開啟面板（例：1440×844）。
2. 點底部右側「更多」。
3. 觀察：只有 summary 的箭頭轉向，選單內容完全沒有出現（見 [tools-menu-1440.png](assets/20261028021735583_deepseek-sidebar/tools-menu-1440.png)、[tools-menu-390.png](assets/20261028021735583_deepseek-sidebar/tools-menu-390.png)）。
4. 用滑鼠點「更多」上方 641–787px 區域（選單實際 layout 位置）：`elementFromPoint` 回傳的是清單卡片內的 `reading-quick-actions`／`reading-meaning`；Playwright 真實點擊 `#reading-ai-difficulties` 連續 9 秒被判定 `intercepts pointer events` 而失敗。

**影響**：`備份目前賬戶（JSON）`、`分析本文難點`、`整理閱讀筆記` 三個入口在任何寬度都無法使用；`reading-tools` 的 `open` 狀態仍會切換，使用者只看到箭頭翻轉，沒有任何錯誤提示。

**根因（已定位，非猜測）**

- 全域摺疊區樣式：`styles.css:1371-1377`
  ```css
  details, .ocr-advanced, .dictation-advanced { border: …; background: …; overflow: hidden; }
  ```
  這條規則同時命中 `<details class="reading-tools">`（`features/article/reading-panel.js:139`）。
- 選單：`styles.css:6861` `.reading-tools-menu { position: absolute; right:0; bottom: calc(100% + 8px); … }`，容器 `styles.css:6858` `.reading-tools { position: relative; }`。
- 量測：`.reading-tools` 計算值 `overflow: hidden`、盒子 60×38；選單盒子 202×146（y 641–787）完全落在容器盒子之外 → 被裁成不可見，也一併被排除在 hit test 之外。

**最小建議（已實測可修）**

```css
/* styles.css，緊接 6858 行 */
.reading-tools { position: relative; overflow: visible; }
```

只加 `overflow: visible` 後（未改其他樣式），選單在 1440 與 390 都正常顯示並可點：`分析本文難點` 可開啟 12 列範圍對話框、`備份目前賬戶（JSON）` 可點；見 [fix-tools-visible-1440.png](assets/20261028021735583_deepseek-sidebar/fix-tools-visible-1440.png)、[fix-tools-visible-390.png](assets/20261028021735583_deepseek-sidebar/fix-tools-visible-390.png)。
注意選單 `z-index:1` 在移除裁切後已能壓過清單（實測無需再加 z-index）。

**可選附帶改善**：選單開啟後點擊選單外地區不會收起（只有再點 summary 或選擇項目才關閉），建議補一個 document 點擊／Escape 收起；實測 Escape 會直接關閉整個面板（可接受，但兩者行為不一致）。

### P2 · `<1200px` 子對話框（全篇筆記／AI 範圍）在面板之下、不可操作；Escape 被攔截

**確切重現步驟（390×844）**

1. 開啟面板（底部 sheet）。
2. 點底部「全篇筆記」。
3. 觀察：畫面完全沒有變化（對話框已在 `#app-modal` 內開啟，但被面板整片覆蓋）。見 [child-dialog-note-390.png](assets/20261028021735583_deepseek-sidebar/child-dialog-note-390.png)（截圖時對話框已開啟）。
4. 按 Escape：面板沒有關閉、對話框也沒有關閉（`#app-modal` 沒有 Escape 處理，而面板的 Escape 被 `childDialog()` 提前 return）。再按一次 Escape 仍然沒反應。
5. 只能點面板右上 `×` 關閉面板；面板一關，那個「看不見的」對話框就突然出現且可操作（[p2-stuck-recovery-390.png](assets/20261028021735583_deepseek-sidebar/p2-stuck-recovery-390.png)，`panelHidden=true, modalOpen=true, modalReachable=true`）。

`1024`、`834` 同樣重現（[child-dialog-note-1024.png](assets/20261028021735583_deepseek-sidebar/child-dialog-note-1024.png)）；`1440` 桌面因為對話框（x 440–1000）不與面板（x 1040–1440）重疊而可正常操作，另見下方「通過項」。

**量測證據（1024×844）**

- `#app-modal`：`position: fixed; z-index: 5000`，內容盒 x 232–792。
- 面板：`z-index: 2450`，但 `#app-modal` 位於 `.app-layout`（`index.html:187` 開頭、`index.html:1634` 的 modal 在其中）之內，而 `.app-layout` 是 `position: relative; z-index: 1`（`styles.css:416-419`）→ **形成獨立堆疊層級**，因此 modal 的 5000 只在該層內比較，永遠低於 body 子節點的面板 2450。
- `elementFromPoint` 在對話框三個取樣點分別回傳 `reading-panel-backdrop`／`reading-panel-filters`／`reading-item is-marked`，`insideModal=false`；Playwright 真實點擊「取消」全部超時。

**影響**：手機與平板上，「全篇筆記」與「更多 → 分析本文難點／整理閱讀筆記」全部無法使用（P1 修好後仍然會撞到本項）；且使用者會看到「點了沒反應、Escape 也逃不掉」的假死狀態。桌面不受影響。

**根因行號**

- `index.html:1634`（`#app-modal`）位於 `index.html:187` 的 `<div class="app-layout">` 內。
- `styles.css:416-419`：`.app-layout { position: relative; z-index: 1; }`
- `styles.css:6678`：`.reading-panel { position: fixed; inset: 0; z-index: 2450; }`
- `styles.css:5110-5113`：`.modal-overlay { position: fixed; inset: 0; z-index: 5000; }`（受上面堆疊層限制而失效）
- `features/article/reading-panel.js:66-68`（`childDialog()`）與 `:199-215`（Escape／Tab 處理）：只要 `#app-modal` 不是 hidden，面板 Escape 就被跳過。

**最小建議（擇一，已驗證方案 A 有效）**

- **方案 A（推薦）**：讓主模態脫離 `.app-layout` 堆疊層。例如在 `modules/ui.js` 的 `initModal()` 內加 `document.body.appendChild(dom.appModal);`（或直接把 `#app-modal`／`#article-library-modal` 移到 `<body>` 直屬）。實測把 `#app-modal` 掛到 body 後，390px 的「全篇筆記」可正常命中輸入框與「取消」，並可用滑鼠關閉（[fix-appmodal-visible-390.png](assets/20261028021735583_deepseek-sidebar/fix-appmodal-visible-390.png)）。此改動影響全站模態定位，需回歸設定面板等既有模態。
- 方案 B：不改堆疊，改在開啟子對話框時（`<1200px`）暫時隱藏面板或將面板降到 `.app-layout` 之下（例如 `body:has(#app-modal:not(.hidden)) .reading-panel { z-index: 0 }`），但面板會整個消失於對話框背後，視覺上等於收起。
- 不論哪個方案，建議同時處理「子對話框開啟時 Escape 至少能關掉對話框」，避免再次出現無法逃出的狀態。

> 備註：本項在 `HEAD` 版本已是相同層級設定（`.app-layout` z-index:1、面板 2450），屬**既有問題**，並非本次改版引入；但它是本次驗收清單明確要求「子對話框可操作」的失敗項，且新的「更多」選單把 AI 範圍對話框也放進同一路徑，因此列為必修。

### P3 · 「備份目前賬戶（JSON）」下載錯檔案（未預勾完整備份）

**確切重現步驟（1440，乾淨 context、此前未開過匯出對話框）**

1. 開面板 → 點「更多」→ 點「備份目前賬戶（JSON）」（需先套用 P1 修法，否則點不到）。
2. 開啟的「導出範圍」對話框：`fullBackup=false`、`fullText=false`、`chat=false`，描述為「…0 则对话 · 本篇阅读笔记（不含全文与对话）」（[backup-entry-dialog.png](assets/20261028021735583_deepseek-sidebar/backup-entry-dialog.png)）。
3. 直接按「確認」：下載 `Sidebar-Audit-—-Meeting-Follow-up-reading-notes.md`（2014 bytes 的 Markdown），**不是** JSON 備份。
4. 手動打開「完整 JSON 備份」開關再確認，才會下載 `bdc-full-backup-*.json`（合法 JSON，21 KB）。

**影響**：入口名稱承諾「備份目前賬戶」，實際輸出本篇閱讀筆記；使用者可能以為已備份帳戶而錯過真正備份。

**根因**：`features/article/reading-panel.js:706-715`

```js
const initial = { fullText: !!exportSelection.fullText, chat: !!exportSelection.chat, fullBackup };
…
{ type: 'checkbox', key: 'fullBackup', label: t('article.exportFullBackup'), default: false }  // 714
```

`initial.fullBackup` 有算，但選項的 `default` 被寫死成 `false`，所以 `#reading-export-json`（`reading-panel.js:169-172`，呼叫 `openExportDialog({ source: 'panel', fullBackup: true })`）的意圖在對話框初始化時被丟掉；`runExportChoice` 收到 `fullBackup:false` 便走 Markdown 分支（`reading-panel.js:684`）。

**最小建議**

```js
{ type: 'checkbox', key: 'fullBackup', label: t('article.exportFullBackup'), default: !!initial.fullBackup }
```

（並可考慮從備份入口進入時把 `fullText`／`chat` 兩個選項標為不適用，避免同時勾成「備份＋全文」的語意混亂。）

**比對**：`HEAD` 版本的 `#reading-export-json` 是直接呼叫 `readingExport.exportFullBackupFile()`，不經對話框；本次改為經對話框而漏帶預設值，屬回歸。

## 3. 可選問題（不阻塞，但建議一併處理）

### O1 · 筆記「保存失敗 → 重試」成功後，狀態停在「保存中…」、焦點掉到 body

- 重現：展開卡片 → 注入保存失敗（`__setNoteSaveInterceptorForTests` 回 `{ok:false}`）→ 輸入文字 → 出現「保存失败，请重试 重试」→ 解除注入 → 點「重試」。
- 實際：store 已寫入新筆記，但狀態文字停在 `保存中…`，重試按鈕消失、`document.activeElement` 變成 body（[draft-retry-status.png](assets/20261028021735583_deepseek-sidebar/draft-retry-status.png)、`phase-status-results.json`）。
- 原因：`features/article/reading-panel.js:586` 先捕獲 `statusEl`，`594-609` 在 `await` 之後寫回該節點；但保存成功的 `bdc:reading-change` 會在 await 期間觸發 `renderPanel()`，整個清單（連同該 status 節點與「重試」按鈕）被重建，寫入落在已卸載的節點。點「重試」時焦點正好在該節點內，因此焦點也一起消失。
- 最小建議：`await draft.promise` 之後重新查詢 `panel.querySelector('[data-note-status="…"]')` 再寫入狀態（或讓 `renderList` 重建後統一重套草稿狀態）；若原本焦點在重試／狀態列，重建後把焦點還給同一項。
- 影響級別：資料正確，屬回饋與 a11y 瑕疵；下一次重繪會自行恢復。

### O2 · 「最近查閱」把從未查閱的文件排在最前

- 實測：`sort=viewed` 時前兩張是「AI 資料」「全篇筆記」，之後才是已查閱詞句（`order=[doc_…so31, doc_…uy4, li_…af80, li_…8f6c]`）。
- 原因：`features/article/reading-view.js:36-38`，文件沒有 `lastViewedAt` 時退回 `updatedAt` 當排序鍵，而文件 `updatedAt` 通常晚於詞句的查閱時間。
- 建議：`sort==='viewed'` 時，沒有 `lastViewedAt` 的文件應排最後（或以空字串排序），讓「最近查閱」名副其實；文件仍可在其他排序中依 `updatedAt` 排。

### O3 · 讀取錯誤時篩選計數顯示 0，與標題徽章不一致

- 實測：注入 IndexedDB 讀取失敗後，清單正確顯示「未能读取本机学习记录，请重试。」＋重試，但六個篩選徽章同時變成「全部 0 …」（`features/article/reading-panel.js:405-418`、`:1083-1097`），而標題列徽章仍是 13（`load-error-1440.png`）。
