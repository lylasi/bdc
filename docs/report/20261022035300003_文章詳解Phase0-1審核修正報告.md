## 二、逐項修復說明

### P1-1｜批次保存失敗後失敗段數變成 0、批次重試入口消失

**根因（與審核一致）**

1. 真正的 IndexedDB 交易失敗時，`modules/article-store.js:saveAnalysis` 仍會 `replaceRecord(next)`，把新的成功結果留在記憶體（此行為 HEAD 已存在）。
2. `article.js` 在保存失敗後把段落畫面退回 `failed/save_failed`，但接著 `refreshFailedStateFromRecord()` 只從記憶體記錄重算，得到 0 段失敗。
3. 於是摘要顯示「已重試 0 段，仍失敗 0 段」，批次按鈕 `hidden`／`disabled`，重試入口消失；重載後磁碟又是舊狀態（失敗），形成前後不一致。

**修法（只改 UI 層，不動 store）**

- 新增模組內 `unsavedParagraphs`（key＝`articleId + contentVersion`）追蹤「實際保存失敗」的段落與結果。
- 新增 `failedIndicesForRecord(record)`：失敗段＝`failedIndicesFromResult(record.result)` ∪ 未保存段 index（去重）。
- 單段重試保存失敗、批次保存失敗時 `markParagraphsUnsaved(...)`；任何一次成功保存（單段／批次／全篇分析）都 `clearParagraphsUnsaved(...)`（因為 store 一次寫整份記錄）。
- `refreshFailedStateFromRecord`、`retryFailedParagraphs` 的重試範圍、`recordFailedParagraphs`（歷史列狀態）全部改用同一份 `failedIndicesForRecord`。
- `applyRecordToView` 會把「未保存」段落覆寫成 `failed/save_failed`，所以切回該篇不會突然變成看似可用的譯文。
- 單段成功保存時，若先前有其他未保存段落，會依記錄重新渲染那些段落（store 的整份寫入語義），避免畫面與磁碟不一致。

**未修改 store 的理由**：`saveAnalysis` 的記憶體更新行為是 HEAD 既有行為，且屬另一個工作階段的 WIP 範圍；本次以「UI 使用實際保存結果」修正，符合審核建議，回滾只需還原 `article.js`。

### P1-2｜單段重試被其他段落提前解鎖，舊回應可覆寫新結果並落盤

**根因**

- `updateArticleVersionState()` 只依 stale 狀態無條件把所有 `.retry-paragraph-btn` 設回可用；一段完成就會解鎖另一段仍在請求中的按鈕。
- `isJobWriteTarget(job)` 沒有「同一段落請求世代」概念，晚到的舊回應仍被視為合法寫入者。

**修法**

- 新增 `paragraphClaims`（key＝`articleId + index`）與 claim id，代表「該段落目前的寫入擁有者」。
- `startAnalysisJob` 增加 `index`；`claimParagraphForJob(job, idx)`：
  - 舊擁有者是單段工作 → 直接 `cancelAnalysisJob`（淘汰舊工作）。
  - 舊擁有者是批次工作 → 只撤銷該段 claim，批次其他段落照跑；其晚到回應會被所有權檢查丟棄。
- `isJobWriteTarget(job, index)` 新增同段落世代判斷：`ownsParagraph(job, index)` 不成立就不得寫 DOM、不得保存。
- 批次 `runNext`：若該段已被其他工作接手就跳過（不重複請求、不搶回寫入權）；回應後用 `isJobWriteTarget(job, idx)` 檢查；最終保存只寫仍由批次擁有的段落。
- 單段重試在請求後與保存後都重新檢查 `isJobWriteTarget(job, idx)`。
- 新增 `isParagraphBusy`／`isBatchRetryActive`；`updateParagraphButtonState` 依「stale ＋ 該段忙碌 ＋ 批次忙碌」決定 `disabled`／`aria-busy`；`updateRetryFailedButton` 在批次進行中保持停用。
- `renderParagraph` 的狀態套用改為呼叫 `updateParagraphButtonState`，避免「別段完成 → 這段被 render → 誤開按鈕」。

### P1-3｜助手忙碌鎖設得太晚，初始化期間連送會產生兩個請求

**根因**

- `ask()` 先檢查 `activeAsk`，但建立上下文／會話／讀歷史都是 `await`，`activeAsk` 直到串流前才設定；同步連送時第二次檢查仍是 null。
- `finally` 又無條件 `activeAsk = null`。

**修法**

- `ask()` 拆成外層 wrapper＋`askOwned(token, ...)`：
  - wrapper 在任何 `await` 之前同步設定 `activeAsk = token`；已存在時顯示 `assistant.busy` 並保留輸入。
  - wrapper `finally` 只在 `activeAsk === token` 時解除（只有持有者能解除）。
  - `askOwned` 不再直接清全域鎖；`askOwned` 的早期返回（例如建立會話失敗）由 wrapper 釋放。
- `doSend` 原本的忙碌檢查保留；由於 `ask()` 同步取得鎖，第二次同步送出會在清空輸入前就被拒絕。

### P2-4｜未分析文章被標成已分析；切換歷史殘留錯誤版本提示

**修法**

- `features/assistant/assistant.js:updateContextChip`：只有 `record.result` 存在且正文一致才算已分析；`analysis: null` 一律 `unanalyzed`。
- `features/article/article.js:applyRecordToView` 的無分析分支：`setArticleViewVersion(record.article, { analyzed: false })`＋`clearBatchSummary()`，讓 `analyzedVersion` 清空、banner 不再因舊文章版本而顯示。
- `mountUi()` 建立面板後立即 `updateContextChip(panel)`（locale 重建面板時 chip 不會是空的）。

### P2-5｜切換介面語言後動態失敗狀態與摘要不更新

**根因**

- 狀態文字、失敗原因、重試按鈕、批次摘要都是執行時 `t()` 一次，沒有 `data-i18n`；locale listener 只更新按鈕 aria，沒有重套這些節點。

**修法**

- `applyParagraphStatusUI` 把 `errorCode` 存進 `statusDiv.dataset.errorCode`（狀態與插值資料保留）。
- 新增 `refreshParagraphDynamicTexts()`：重套 `.status-text`、`.para-reason`、逐段重試／刷新按鈕文字、`.analysis-failed-inline`、`.source-language-note`。
- 批次摘要改存 `lastBatchSummary = { done, failed }`，`renderBatchSummaryText()` 在 locale 切換時重套 `t('article.retrySummary', lastBatchSummary)`。
- `initArticle` 的 `bdc:locale-change` 呼叫 `refreshParagraphDynamicTexts()`。
- 版本 banner 本身是 `data-i18n`，locale 切換由 `applyTranslations` 更新；本次補了 zh-CN→zh-HK→zh-CN 雙向斷言。
- 助手 chip：面板在 locale 切換時重建，`mountUi` 立即以目前 locale／文章重算 chip；測試涵蓋「未分析文章 chip」與「無文章 chip」。

### P2-6｜音訊驗收載具不可用

**修法**

- `tests/audio-owner.test.mjs` 的 `document`／`window`／`globalThis` 改用真正的 `createEventTarget` stub：各自維護 listener 集合，`dispatchEvent` 同步呼叫已註冊監聽器，`removeEventListener` 生效。
- 新增常駐自測「事件 stub 本身能註冊與派送」：註冊→派送→移除→再派送，驗證只收到一次；另驗證 window/globalThis 不互相污染。
- P2-T1（`getActiveAudioOwner`）尚未實作，owner 測試**維持 skip**；沒有假裝已完成。

## 七、風險與注意事項

1. **`unsavedParagraphs` 只在記憶體**：key 是 `articleId + contentVersion`。重新載入後以磁碟為準（測試已驗證一致）。若另一個分頁同時成功保存同一篇，標記可能短暫過時；最壞情況只是多顯示可重試入口，不會寫錯資料。
2. **store 的整份寫入語義**：任何一次成功保存都會寫入整份記錄，所以程式在成功後清除全部未保存標記並同步重繪那些段落；若未來 `article-store.saveAnalysis` 改成「失敗即回滾記憶體」，這些 UI 標記會變成多餘但無害。
3. **批次與單段的競爭**：批次進行中若使用者（或程式）對某段再送單段重試，批次會跳過該段；批次最終保存也只寫仍擁有的段落。這避免舊批次覆寫新結果，但該段的摘要「done」數可能不含被接手的那段（仍以記錄實際保存結果顯示）。
4. **`article.js` 仍是大型單檔**：本次只在既有邊界內收斂狀態與所有權，沒有拆檔；請優先 review `paragraphClaims`／`unsavedParagraphs`／`refreshParagraphDynamicTexts` 三個區塊。
5. **新增測試的時序**：13b 依賴 mock 的分次延遲（1600ms／60ms）與「等批次請求已送出」的輪詢；已避免固定 sleep 猜順序，但在極慢機器上仍可能受 CPU 影響。若需再降低 flaky，可把延遲差距拉大。
6. **未修改其他工作階段 WIP**：`modules/article-store.js` 等檔案仍是他人的未提交變更；本報告的測試是在目前混合工作區上執行的，正式驗收仍應固定依賴版本（審核報告第七節第 4 點）。
7. **locale 只影響 UI**：本次沒有轉換文章、譯文、QA、使用者輸入或歷史訊息。
