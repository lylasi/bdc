## 二、R1：移除雲端副本會清空本機 Key

### 原因

`modules/ai-credential-sync.js` 的憑證列只記錄「有一個 delete 待處理」，沒有記錄**這次刪除的目的**。於是三條確認路徑都無條件把 `apiKey` 清成空字串，等同把「只刪雲端副本、此裝置保留」降級成「刪除供應商」：

- `processCredential()` 的 `confirm-pending`（原 438 行）：遠端 tombstone 被視為「本機 Key 也該消失」。
- `processCredential()` 的 `upload-pending` → `delete-ok`（原 538 行）：DELETE 成功即清空 Key。
- 同段的 `delete-not-found`（原 525 行）：雲端列已不存在（404／已被別處刪除）時同樣清空。

原方案第 9 節要求的語意是：「已選保留的本機副本標記為 local-only，不被同一刪除標記回頭清除」；`setProviderKeySyncMode(id,'remove-cloud')`（895 行）與 `removeCloudKey()`（994 行）的註解也明寫「只移除雲端副本」。意圖在寫入時就遺失了。

### 修正

1. `modules/ai-profile-storage.js:224-242`：`normalizePending()` 新增 `keepLocalKey` 欄位（預設 `false`），讓「保留本機副本」的意圖能持久化、跨重新載入存活。
2. `modules/ai-credential-sync.js:936-952`：`remove-cloud` 產生的 delete mutation 標記 `keepLocalKey: true`。
3. 其餘 delete mutation 明確標記 `keepLocalKey: false`，避免語意模糊：
   - `deletePersonalProvider()`（882 行）＝真正刪除供應商。
   - `savePersonalProvider()` 的 `clearKey` 與 `authMode: 'none'` 分支（768、793 行）＝使用者主動清空 Key。
   - `resolveCredentialConflict(id,'local')` 且本機無 Key（1084 行）＝同步刪除。
4. 三條確認路徑改為依意圖處理：
   - `confirm-pending`（461 行）：先取出 `keepLocalKey`，tombstone 時只切換為 `local-only`，僅在意圖為「真刪除」時清空 `apiKey`。
   - `delete-ok`（562 行）：清空與否同上；同時**只有 PUT 成功**才把 `bindingVerified` 設為 `true`（原本 delete 成功也會標記為已驗證，屬同類盲寫）。
   - `delete-not-found`（562 行前後）：同上。
5. `apply-remote-delete`（473 行）維持原語意：**沒有本機 pending 的 tombstone** 代表別的裝置真的刪了，本機照樣清空並轉 `local-only`；並補上註解說明為何與 R1 不同。`download` 分支遇到 tombstone 亦然。

### 行為矩陣（皆有回歸案例）

| 情境 | 雲端結果 | 本機 Key | 本機 syncMode |
| --- | --- | --- | --- |
| remove-cloud → DELETE 200 | 已刪 | 保留 | local-only |
| remove-cloud → DELETE 404（別處已刪） | 已刪 | 保留 | local-only |
| remove-cloud → 回應遺失，下次同步以 tombstone+mutationId 確認 | 已刪 | 保留 | local-only |
| 刪除整個供應商 → DELETE 200 | 已刪 | 清空 | local-only（provider 已移除） |
| 其他裝置刪除 → 本機無 pending 的 tombstone | 已刪 | 清空 | local-only |

## 三、R2：衝突解決的非同步下載覆蓋較新本機 Key／接受舊會話結果

### 原因

`resolveCredentialConflict()`（原 921-991 行）在 `await downloadOne()`（949 行）之後直接 `updateAIProfile()`（955 行），只檢查「這一列還在不在」。一般同步路徑已有 `captureAuthSession()`／`isAuthSessionCurrent()`／`createSessionGuard()`／`commitCredentialChanges()` 指紋合併，手動衝突解決卻完全沒有，於是：

- 重現 A：下載期間使用者存了新 Key → 舊雲端 Key 覆蓋新 Key，並清掉新的 pending。
- 重現 B：下載期間登出再登入同帳戶 → 舊工作階段把結果寫進重新建立（且已有新 Key）的 profile。

同一函式的 `choice === 'local'` 與 `remoteDeleted` 分支雖然是同步寫入、本身沒有 await 窗口，但仍缺少「這一列是否還是我看到的那一列」的條件寫入。

### 修正（`modules/ai-credential-sync.js:960-1092`）

1. 新增 `conflictBaseline(credential)`（176 行）：把「使用者按下按鈕時看到的狀態」序列化為基線——憑證指紋（apiKey／syncMode／binding／pending mutation）＋`version`＋`syncMode`＋衝突列（`remoteVersion`／`remoteDeleted`／`remoteLastMutationId`）。
2. `resolveCredentialConflict()` 進入時捕獲：`captureAuthSession()`、`profileKeyForScope(activeScope)`、`conflictBaseline()`。
3. 下載完成後 `operationIsCurrent()`（987 行）一次驗證四件事，任一不符即 `return false`，**完全不寫入**：
   - endpoint／userId／token／sessionGeneration 與捕獲時一致（`isAuthSessionCurrent`）；
   - 目前仍為登入狀態；
   - 目前 profile scope key 與捕獲時相同（不會把結果寫回舊 scope）；
   - 該憑證列的基線未變（使用者沒有存新 Key、沒有換 pending、衝突仍是同一個）。
4. 只有 `operationIsCurrent()` 通過才進行資料校驗，再做**條件寫入** `guardedWrite()`（995 行）：在 `updateAIProfile()` 的讀-改-寫區塊內再次比對基線，符合才套用；被跳過時不 `notify()`、不清 pending、不復活舊 scope。
5. 回傳值語意：套用成功 `true`、被判定過時 `false`（UI 需區分失敗與過時）、真正的資料錯誤才拋錯。
6. 額外校驗（原方案第 8 節「採用雲端版本亦應核對 binding」）：
   - 回傳 `version` 低於衝突記錄的 `remoteVersion` → `conflict_download_stale`（不寫入、衝突保留）。
   - 回傳 `binding` 與目前供應商定義不一致 → `binding_mismatch`，只記錄 `bindingVerified=false`／`lastError`，**不存這把 Key**（避免把 Key 送往不是它綁定的端點）。
   - 回傳為 tombstone → 視為採用「雲端已無此 Key」，切 `local-only` 並清空 Key（與 R1 不同：這裡是使用者明確選擇採用雲端版本）。
   - 下載成功才把 `bindingVerified` 設為 `true`，並補 `keyStamp`。
7. 其他衝突路徑檢查結論：`choice === 'local'` 與 `remoteDeleted` 分支改走同一個 `guardedWrite()`；一般同步路徑本來就走 `commitCredentialChanges()` 指紋合併，未發現其他「await 後盲寫」的憑證入口（`uploadPending`／`downloadOne` 的結果一律經由該 commit 落地）。

## 四、R3：靜態掃描命令沒有讀 stdin 卻報成功

### 原因

`scripts/check-ai-static-config.mjs` 只支援目錄：`walk()` 對 `readdirSync` 失敗直接 `return`（原 93 行），`main()` 仍以「沒有 findings」結束（原 119 行 → `ok:true, exit 0`）。指南第 149 行把 `curl` 的回應接到 `--dir /dev/stdin`，實際上一個位元組都沒檢查。

### 修正

`scripts/check-ai-static-config.mjs`（改寫）：

1. 明確 stdin 模式：`--stdin`、`--dir -`、`--dir /dev/stdin`、`/dev/fd/0` 等價（50-52 行），以 `fs.readFileSync(0)` 讀取並當成 `ai-config.js` 掃描（`--name` 只影響報告顯示）。stdin 為 TTY（沒有管道）→ `stdin_missing`；讀不到 → `stdin_read_failed`；空內容 → `stdin_empty`。三者皆 `exit 2`。
2. 目錄模式改為 fail-closed：不存在 → `target_missing`；不是目錄 → `target_not_directory`；無法列出 → `target_unreadable`；掃描期間任何 `readdir`／讀檔失敗 → 收集到 `scanErrors` 並以 `scan_failed` 結束；**掃到 0 個檔案 → `no_files_scanned`**。以上全部 `exit 2`，不再以「沒有掃到」冒充乾淨。
3. 結束碼文件化：0＝實際掃描且無發現、1＝有發現（只輸出檔名／行號／類型，不輸出值）、2＝沒有完成掃描。
4. JSON 報告新增 `scanned`、`scanErrors`、`error`、`message`，讓「到底檢查了幾個檔案」可被機器驗證。

`docs/release/20261017174843744_AI供應商設定同步部署與遷移指南.md`：

- 7.1 第 4 步補上 0／1／2 結束碼語意表（141 行）。
- 7.2 第 2 步（159 行起）改成真正可執行的命令：`mktemp -d` → `curl -fsS ... -o "$tmp/ai-config.js"`（`-f` 讓 4xx/5xx 直接失敗，不會把錯誤頁當設定檔）→ `node scripts/check-ai-static-config.mjs --dir "$tmp"` → 清理；並附 `--stdin --name ai-config.js` 的管道版本。兩者都只有 `exit 0` 才算通過，`exit 2` 明確標示為「未檢查完成」。

## 七、程式驗收與正式部署的分界

**本輪已完成（程式層）**：R1／R2／R3 的行為修正、靜態檢查器 fail-closed、部署指南命令修正、19 個永久回歸案例、四個必跑驗證命令全數通過。

**本輪未執行（正式環境）**：

- 未部署前端、未執行 `wrangler deploy`、未對正式 D1 執行 migration 或 catalog 發布。
- 未操作任何真實供應商 Key，未輪換或撤銷舊共享 Key。
- 未遷移私有 `ai-config.js`。只以檔名／行號層級輸出確認：本機私有檔目前仍含 legacy AI 匯出（`legacy-ai-export:*`），代表第 7.1 節的遷移在該環境尚未完成；實際遷移與部署仍需依指南在受控環境執行。
- 未做新的視覺驗收：瀏覽器腳本以 route 白名單載入本機檔案、`ai-config.js` 一律替換為 `ai-config.example.js`、Worker／供應商全為 mock，且不載入完整 CSS，只證明功能互動。

**剩餘限制**：

1. R1 的情境以「本機仍保有 pending delete」為前提。若使用者在 pending 尚未落地前手動清除本機 profile（或換裝置登入），後續只會看到遠端 tombstone，無法與「別處真的刪除」區分——此時仍採保守語意（清空本機 Key），與 `apply-remote-delete` 一致。
2. R2 的基線比對以「這台裝置的 localStorage 狀態」為準。多分頁同時對同一列操作時，後寫入者會依 `updateAIProfile()` 的讀-改-寫與基線比對被判為過時並回傳 `false`；UI 目前對 `false` 只重新渲染、不顯示額外提示（避免在使用者自己剛編輯過時誤報「其他裝置已修改」）。若後續需要更明確的回饋，應新增 `zh-CN`／`zh-HK` 成對文案後再改。
3. 靜態檢查器是靜態文字檢查，不是秘密掃描器，也不能取代在供應商控制台撤銷舊 Key。
4. 瀏覽器回歸在首次啟動 Chrome 時若受 sandbox 限制失敗，需以既有授權方式重跑；本輪該命令一次成功，沒有任何一項是「假設通過」。
