## 1. 必修 1：移除及還原沒有隔離同代際延遲回執

### 1.1 根因

`deleteDoc()` 只把代際 ledger 寫成 `max(文件, ledger, 記憶體)`：文件被完整 pull 移除時，
屏障數值不變，代表「上一條生命週期」沒有被結束。之後用同 ID 備份還原，採用的是
**同一個代際**（例如 gen1 / rev0 / create / expected0）；上一條生命週期暫扣的回執
（B 的 gen1 PUT 已提交 rev2、A 重試同一 mutation 收到冪等成功並清空 outbox）
因此仍能匹配，把還原文件改成 `gen1 / rev2 / update / expected2`，而遠端其實不存在。

### 1.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `modules/article-store.js` | `:536-588` `deleteDoc()` | 新增 `options.onlyIfClean`、`options.retireGeneration`；交易內多讀 outbox（見第 3 節） |
| `:557-564` | `retireGeneration === true && storedDoc` 時 ledger 寫入 `max(文件, ledger, 記憶體) + 1`（代際只能前進） |
| `:513-533` `fallbackRemoveDoc()` | localStorage 後備的同一套規則：讀 bucket 內文件／outbox／ledger 後同步寫回，沒有 await 插隊 |
| `:553`、`:570` | 交易失敗（`idb_unavailable`）切換後備時走同一個 `fallbackRemoveDoc()` |
| `:2182-2207` `reconcileFullList()` | 遠端已無此篇時傳入 `retireGeneration: true` |

設計取捨：

- 只有「交易內仍存在持久化文件」才 +1。另一個分頁若已經移除同一篇（交易序列化後
  `storedDoc` 為 `null`），不會再重複推進，避免 ledger 被多分頁灌高。
- `retireGeneration` **只用在遠端移除**。使用者主動刪除仍走
  `deleteArticle()` → `persistDocWithOp(tombstone, 'delete')`，tombstone 與 delete outbox
  同一個代際，回執語意不變（新增測試 `完整 pull 不得刪掉另一分頁剛建立的刪除 tombstone`
  固定這條路徑）。
- 被移除的 ID 之後若被遠端重新建立並下載，`applyRemoteDocs()` 仍採
  `max(localDoc, ledger)`，沿用新的代際。

### 1.3 驗收（`tests/article-rebuild-generation.test.mjs:1107`）

完整複審時序：A 404 重建到 gen1 → 建立成功 rev1 → B 保存並送出 PUT（伺服器提交
rev2、回應暫扣）→ A 重試同一 mutation（mock Worker 依 `clientMutationId` 回冪等成功）
清空 outbox → 匯出 gen1/rev2 備份 → 遠端清空＋`resetRequired` → 完整 pull 移除文件
（斷言 ledger = 2）→ 還原為 gen2/rev0/create/expected0。
單筆 `markOpDone`、批次 `markOpsDone`、以及放行 B 真正的 PUT 回應，都不得改動
revision／`updatedAt`／outbox；之後建立到遠端 rev1、更新到 rev2，衝突 0。

## 2. 必修 2：原樣還原本版本備份，首次更新 409

### 2.1 根因

`mergeStoredRevision()` 只有「持久化／ledger 代際 **大於** 記憶體代際」時才重設版本
基準。還原新格式備份時兩邊同為 gen1，於是把備份的 `revision 2` 繼承下來，建立
操作變成 `create / expectedRevision 2`。`POST /articles` 不使用 expectedRevision，
伺服器建到 rev1，本機仍停在 rev2；下一次更新送出 `expectedRevision 2` 必定
`article_revision_conflict`（複審重現 `pushed.conflicts = 1`）。

### 2.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:621-635` `mergeStoredRevision()` | 新增「重新建立」分支：`type === 'create' && !storedDoc && hasPendingOp !== true` → `revision: 0`、`generation: max(stored, memory)` |
| `:751-758` | localStorage 後備的 `persistDocWithOp()` 把 `type`、`hasPendingOp` 傳入合併 |
| `:794-801` | IndexedDB 交易內同樣傳入（`hasPendingOp` 取自交易內讀到的既有操作） |
| `:771-773` | outbox 一律加入交易（即使 `skipOutbox` 不寫操作），確保合併時讀得到既有操作 |

規則說明：

- 本機沒有持久化文件、也沒有等待中的操作，代表上一條生命週期的遠端版本已無意義；
  建立一定從 0 開始。等待中的操作仍存在時不套用（保留它已確認／待重送的基準）。
- 新格式備份（`generation: 1 / revision: 2`）與沒有 `generation` 的舊備份都走同一條
  規則；`generation` 不會因此倒退（取 ledger 與記憶體較高者）。
- 第 1 項的 ledger 前進在「完整 pull → 還原」路徑也會讓版本歸零；本項另外覆蓋
  **沒有 ledger 的裝置**（跨裝置還原備份）與其他「文件已不存在」的建立路徑。

### 2.3 驗收

| 測試 | 位置 | 內容 |
| --- | --- | --- |
| 新格式備份 | `:1322` | 來源裝置留下 gen1/rev2；遠端清空；換到沒有 ledger 的新裝置還原 → `revision 0 / create / expected 0` → 建立 rev1 → 更新 rev2，衝突 0 |

## 3. 一併修（既有 High）：完整 pull 刪掉另一分頁剛保存的未同步正文

### 3.1 根因

`reconcileFullList()` 只用呼叫端記憶體判斷 `dirty / pending`。A 停在 pull 回應時，
B 已保存新正文（持久化文件 dirty、outbox 有操作），但 A 的記憶體仍是 clean 的舊版本；
`deleteDoc()` 無條件刪除文件與摘要（outbox 反而留著），`dropRecord()` 也把記憶體記錄
移除。接著 `pushOutbox()` → `pushOne()` 找不到文件，直接 `markOpDone()` 把操作確認掉，
同步回報 `pushed 1 / failed 0`，正文與 outbox 一起消失。

### 3.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:500-507` `docHasLocalPending()` | 文件 dirty／pending 或仍有 outbox 操作即視為本機未同步 |
| `:536-588` `deleteDoc()` | 交易 store 增加 `STORE_OUTBOX`；同一交易讀 `[docs, ledger, outbox]`，`onlyIfClean` 且有未同步狀態時回 `{ ok: false, skipped: true, doc }`，不刪任何東西 |
| `:513-533` `fallbackRemoveDoc()` | 後備桶用同一條規則（同步讀寫，中間沒有 await） |
| `:2194-2216` `reconcileFullList()` | 傳入 `onlyIfClean: true`；被跳過時把交易內讀到的最新持久化文件合併回記憶體（`mergeRecordsIntoMemory`），並在有任何刷新時 `emitChange()` |

`modules/article-sync.js` 不需修改：記憶體已補回該篇（含最新正文），`pushOne()` 找得到
記錄，PUT 404 時走既有重建流程，正文取自持久化文件；不會再把操作誤判為完成。

### 3.3 驗收（`:1409`）

A 的同步暫扣在完整清單回應；B 保存 `b-v4` 後放行。斷言文件、摘要、outbox 都保留
（正文 `b-v4`、`dirty`、`pending`），A 的記憶體補回 `b-v4`，該輪 `pushed.pushed === 0`；
下一輪 PUT 404 → 重建為 `create / expected 0 / payload b-v4`，再下一輪建立成功
（遠端 rev1、正文 `b-v4`、outbox 清空、衝突 0）。

另外新增 `:1486` 的 tombstone 保護測試：B 剛建立的本機刪除（tombstone＋delete outbox）
不會被 A 的完整 pull 移除，代際與操作都不變，之後 DELETE 仍能成功送出。

## 7. 未完成項與仍存風險

1. **（既有缺口，未修）** `markOpFailed()` 經 `persistDocWithMeta()` 仍以呼叫端記憶體
   內容寫文件；上傳失敗若發生在本機剛保存新正文之後，正文可能被覆回舊內容。本輪只
   確認代際／版本不倒退（`persistDocWithMeta` 已採 ledger）。
2. **（既有缺口，未修）** IndexedDB 不可用時：
   - `applyRemoteDocs()` 仍回 `idb_unavailable`；匯入後確認／gate 未清；
   - `markOpDone()`／`markOpsDone()` 沒有 localStorage 後備實作，後備模式下來自同步的
     回執會失敗。因此第 13 案（後備）只驗證代際／revision／outbox 的交易語意，回執
     隔離以 IndexedDB 路徑（第 12 案）覆蓋。
3. **（既有行為，未擴大處理）** `restoreArticle()` 在遠端已不存在時仍送 `/restore`，
   伺服器 404 會變成衝突（`pushOne()` 只對 `update` 的 404 走重建）。本輪保證還原後
   代際不倒退，但沒有把 restore-404 改走 create。
4. **ledger 長期容量**：`article_generations` 每篇「曾被重建／被遠端移除」的 ID 留一列，
   不會回收（同 ID 可能被備份還原，沒有安全的前綴清理方式）。每次遠端移除只 +1，
   同一分頁不會重複推進（交易內已看不到文件），但長期仍隨文章 ID 數成長。
5. **localStorage 後備的跨分頁原子性**：`fallbackRemoveDoc()` 的讀改寫中間沒有 await，
   屬既有後備模型的限制；兩個分頁在同一個事件迴圈切片外的極端交錯仍可能覆蓋，
   與其他後備寫入（`fallbackDocWrite`、outbox）風險相同。本輪只保證與 IndexedDB
   路徑相同的判斷規則。
6. **`retireGeneration` 對本機 tombstone 的影響**：已被伺服器永久清除、且本機已同步
   完成的 tombstone 會被完整 pull 移除（既有行為），移除時 ledger 再 +1；之後若用
   備份「復原」，會以更新的代際重新建立，不影響同步正確性。
7. **未跑 Playwright 巡檢**：本輪改動集中在 IndexedDB 交易與同步回執，已用 fake
   IndexedDB＋雙實例＋真實 mock Worker 流程覆蓋；依約束只執行 node 測試與 i18n 檢查。
