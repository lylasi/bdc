## 六、新觀察（本輪新增，皆非阻擋）

### 1. F2 同類風險仍在其他路由（既有問題，非本分支回歸）

F2 的根因是「`try` 內 `return handleX(...)` 沒 `await`」。本輪確認 `await` **只補在 `/articles`**（`worker.js:512`）；同型的 `/reading`、`/ai-credentials`、`/admin/users`、`/ai-catalog` 仍無 `await`。我用 DB 故障注入（`env.DB.prepare` 對特定 SQL 拋錯，記憶體 SQLite）實測：

| 路由 | 正常 | DB 故障時 |
| --- | --- | --- |
| `GET /reading/capabilities` | 200 | **reject（無 JSON 500）** |
| `GET /reading/changes` | 200 | **reject** |
| `GET /ai-credentials` | 200 | **reject** |
| `GET /ai-catalog` | 200 | **reject** |
| `GET /articles` | 200 | `500 {"code":"internal_error"}` ✅ |
| `/admin/users` | 200 | 注入點未命中其寫入路徑，**未能實證**；原始碼同型（無 `await`） |

- **為何不阻擋 0.3.0**：這四條路由在 `git diff` 中**未被本分支改動**（只有 `/articles` 多了 `await`），是既有行為、非回歸；0.3.0 自己的路由面（`/vocabulary/books`、`/vocabulary/default`、`/vocabulary/page-link`、`/captures`）雖也未 `await`，但 `handleVocabularyCaptureRoute`（`captures.js:166-188`）與 `handleCaptureBookWrite`（`capture-books.js:94`）**各自有 try/catch**，DB 故障會回 `{"code":"capture_failed"}` 500，封套正確。
- **建議（後續一輪，一行修法）**：`return await handleX(...)` 套用到 `/reading`、`/ai-credentials`、`/admin/users`、`/ai-catalog`，並補一項「route 內部拋錯必回 JSON 500」的回歸測試。（P3）

### 2. 同網址再存的觀感問題已被 UI 修正吸收

`saveArticle()` 成功後 `applyReceipt()` 會 `preview = null`、隱藏預覽並記下 `savedArticleId`（`extension/workspace-ui.js:95-108`）；再次按「AI 提取本頁文章」會走既有文章入口（第 50–53 項）。因此上一輪「第二次保存＝沿用、新編輯被丟棄」的使用者可達路徑已被關閉，只剩 client API 層的 `D5` 文件化行為。

### 3. 跨分頁待傳會覆蓋正在編輯的預覽（P4，F1 的鏡像情境）

`showPending()` 的條件是 `!currentJob && !busy && state.source?.pageUrl`，未考慮「已有可編輯但尚未保存的預覽」；若另一分頁／裝置同時寫入同頁待傳，會取代使用者正在編輯的內容（artifact `debug.cross-tab-pending-probe` 已記錄，**只做記錄、未列入需求斷言**）。需同時操作同一頁才會發生，建議下一輪把條件改為 `!preview`，或先提示再取代。

### 4. 另外 2 項低優先項（沿用上一輪，仍未處理）

- `page-link` 回執的 `articleId` 未與先前 `GET ?sourceUrl` 的值做相等比對（兩者走同一個 `findPageArticle`，實務風險極低）。
- `cancel()` 內 `assertSession`，登出後無法從 UI 清掉本機待傳（不影響資料正確性）。
