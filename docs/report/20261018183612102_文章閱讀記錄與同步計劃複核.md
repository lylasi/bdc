# 文章閱讀記錄與同步計劃複核

審閱日期：2026-10-18。對象為會話 400 所提出、並於前次評審後修訂的計劃。

方向合理，但現稿不宜直接整批實作。閱讀記錄的搜尋、目前文章標示、重新命名與刪除復原值得保留；文章身份、結果精簡及同步擴展仍有可能覆蓋或遺失資料的規則缺口。應先完成閱讀記錄交互及切換安全，再分開交付資料遷移與同步改造。

前次修訂已補上句子／片語標註、手動備份包含文件，以及將逐篇合併和刪除標記提前至 Phase 3。以下聚焦修訂後仍未解決的問題。嚴重程度以對應功能發布前是否必須修正為準。

**P0：沿用目前文章 ID 缺少來源切換條件，可能用新文章覆蓋舊文章。**

位置：擴展計劃 2.1、互動計劃 6.4；[文章庫載入流程](../../features/article/article.js:2812)、[依 ID 儲存結果](../../modules/storage.js:595)。

現稿首先判定「currentId 存在且記錄仍在 → 沿用」。但文章庫載入會更換輸入及來源，沒有清除目前文章 ID。使用者開啟 A，再從文章庫匯入 B，直接分析，就可能把 B 寫入 A，並沿用 A 的專屬生詞本。OCR、網址及其他全文替換入口也需要逐一核對。

應明確區分「編輯已載入文章」與「匯入另一篇文章」。只有前者可優先沿用目前 ID；新匯入先解除舊綁定，再依來源與內容尋找記錄。另存新篇必須明確繞過舊 ID。僅將 `id` 加到 `buildArticleMetaInput()` 並不足夠。

驗收補項：開啟 A → 分別以文章庫、OCR、網址匯入 B → 分析，A 的內容和詞書連結均不被改動；開啟 A 後修改一段再分析，才更新 A。

**P0：結果精簡會刪掉只存在頂層的單字詳解。**

位置：擴展計劃 3.1；[按需載入單字詳解](../../features/article/article.js:3161)。

現稿將頂層 `detailed_analysis` 視為逐段結果的重複資料，準備刪掉後再重建。然而目前點擊單字取得的新詳解只合併到 `current.result.detailed_analysis`，並未寫回 `paragraph_analysis`。直接 compact 會遺失這些已取得的詳解；保留 `sentence_analysis` 和 `phrase_analysis` 仍無法補救。

應先將頂層獨有項目遷移到統一的詞彙標註結構，或保留無法從段落重建的項目，再調整所有新增詳解的寫入端。驗收使用真實結果形狀：段落詳解為空、頂層有按需取得的單字詳解，經 compact、同步、hydrate 後仍完整可讀。33–46% 的節省來自模擬樣本，不能當作所有資料的保證。

**P0：渲染 token 只能防畫面覆寫，不能防舊請求污染另一篇文章。**

位置：互動計劃 6.7；[句子與片語儲存](../../features/article/article.js:1374)、[單字詳解儲存](../../features/article/article.js:3178)、[主分析流程](../../features/article/article.js:1763)。

句子、片語、單字詳解都可能在回應到達時才讀取目前輸入和 `currentArticleId`。A 的請求未完成就切到 B，回應可能寫進 B。現稿只要求每次寫 DOM 前核對 token，並沒有阻止儲存。主分析的可變全域 abort controller、後續任務排程與 finally 清理也要一起處理，否則舊流程仍可能影響新流程。

每次請求應固定攜帶 `{ runId, articleId, contentRevision, controller }`，派發後續工作、寫資料、更新 UI、執行 catch/finally 時都驗證所屬工作。非目前文章的結果可取消或存回原記錄，但不可按回應時的目前文章決定歸屬；同一篇文章已改版時也不能套用舊結果。

驗收補項：主分析、重試及詞／句／片語請求延遲回來時，切換、重新分析或刪除文章均不產生跨文章寫入，也不復活已刪除記錄。

**P0：GC 的 30 天從建立時計算，不能提供刪除後 30 天保留。**

位置：擴展計劃 4.3、4.4、3.2；決策記錄的 GC 規則。

現稿刪除「建立超過 30 天、且目前索引未引用」的 blob。一篇 60 天前建立、今天才刪除的文章，下一次 GC 就符合刪除條件。這和「刪除後 30 天回收」不同；立即清理使用建立超過 24 小時的條件，也有相同問題。

保留期應從失去有效引用開始計算，例如記錄 `unreferencedAt`，或先標記再延遲清理。有效引用需要包含目前 `docHash`、`previousDocHash`，以及仍保留的備份所依賴的文件；刪除前還需防止與索引發布並發造成誤刪。

另外，自動備份只保存索引、依賴正式資料庫中的文件，並不天然具備還原能力。舊文件被替換、清理或遺失後，索引仍在但內容已不在。應讓備份保存完整文件，或以不可變文件及引用保留機制保證備份有效期內不被 GC。遷移流程的備份雖寫着「遷移前」，卻列在改寫 localStorage 之後，需改為第一個強制成功步驟。

驗收補項：今天刪除一篇建立超過 30 天的文章，明天執行 GC 仍可按承諾還原；保留上一版及舊備份後執行 GC，兩者仍能完整恢復。

**P1：HTTPS 與區域網 HTTP 使用不同 docHash 演算法。**

位置：擴展計劃 4.3。

HTTPS 用 SHA-256，HTTP 後備用兩組 FNV64，同一份文件在兩種環境會產生不同識別值，造成重複上傳、配額浪費和不必要的版本差異；也沒有明確定義下載驗證方式。

應統一序列化規則、UTF-8 位元組與雜湊演算法，沒有 Web Crypto 時使用同一演算法的實作。伺服器應驗證提交的 hash 與內容相符，並禁止同一 hash 被不同內容覆寫。若一定要多演算法，需設計帶演算法識別的格式及遷移規則，不能當成透明後備。

驗收補項：同一文件在 HTTPS 與 LAN HTTP 得到相同 hash，往返同步不產生副本；錯配 hash 的上傳遭拒。

**P1：逐篇合併尚未完整定義相同時間、刪除及 metadata 的處理。**

位置：擴展計劃 4.4；[現有文章 metadata 套用](../../modules/sync-core.js:269)。

以 `updatedAt` 決勝、相同時比較 `docHash`，無法決定「相同時間、相同內容 hash、不同標題」哪筆勝出。刪除只判定 tombstone 時間嚴格大於更新時間，兩者同時會留下文章。刪除標記 180 天後清除，也不能阻止更久未上線的裝置重新帶回舊資料。

需要定義完整且與合併輸入順序無關的排序規則、同時刪除的勝負，以及過期裝置重新同步時的重建規則。另需決定索引中的 title／source 和獨立 `articleMetas` 誰是權威來源；正文改成逐篇合併，而 metadata 維持整組覆蓋，仍可能失去改名或來源。現稿快照範例使用 `metas`，現行名稱則是 `articleMetas`，也需說明映射。

驗收補項：交換 local/remote 合併順序結果一致；同時改名、同時刪改、離線超過 180 天重新連線，都符合明確政策。

**P1：降級開關不是資料安全的回滾，409 的舊版行為亦描述錯誤。**

位置：決策記錄 5.3、擴展計劃 4.5；[pushSnapshot](../../modules/sync-cloudflare.js:434)。

將 `ARTICLES_SCHEMA_MODE` 改成 1 允許舊格式寫入，等於重新開放舊快照覆蓋新索引。只恢復遷移前快照，則會遺失上線後新增的內容。回滾應先暫停寫入，備份最新完整 v2 資料，再執行保留新資料的反向轉換；若無可靠反向轉換，應採向前修復並保留版本閘門。

目前 `pushSnapshot()` 對所有 409 都直接回傳 `{ conflict: true }`，不讀錯誤 body。舊前端不會如計劃所述顯示 `client_upgrade_required`。新設計的 `missing_blobs` 也需要獨立處理。應在前置版本加入錯誤碼分流，或明確接受舊版只能顯示一般衝突提示，不能將未存在的提示當作驗收結果。

**P1：D1 上限的推導有事實錯誤。**

位置：擴展計劃 4.3、配額決策記錄。

Cloudflare 官方目前列出的字串、BLOB 或資料列上限是 **2,000,000 bytes**，不是計劃使用的 1 MB。900 KB 可以是產品保守上限，但「為避開 D1 單列 1 MB」不能作為依據。免費方案的單一資料庫上限是 **500 MB**，5 GB 是帳戶合計；若所有使用者共用一個資料庫，不能直接用 5 GB ÷ 50 MB 推算容量。[官方 D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

應修正決策依據，區分產品配額、資料庫限制和實測安全餘量；這不代表需要立即提高已選定的配額。

**P1：原始交互目標仍有缺口，應在首期補齊。**

位置：互動計劃 5.2–5.4、6.3、6.6；擴展計劃 2.6。

| 缺口 | 影響 | 建議 |
| --- | --- | --- |
| 預設按最近更新，沒有最近開啟 | 剛讀過但未修改的舊文章仍埋在底部 | 增加本機 `lastOpenedAt`，優先提供最近閱讀或繼續閱讀入口；閱讀行為不必每次觸發內容同步 |

**P2：整理文件矛盾後再估時。**

擴展摘要仍把逐篇合併與 tombstone 放 Phase 4，正文與路線圖已改成 Phase 3；重複整理要求刪 meta，但孤兒清理與詞書連結又要求保留；互動計劃採標題覆寫，擴展資料模型卻優先 meta.title。這些要先統一，否則不同實作者會做出不同結果。

手動備份自動淘汰至 3 份、標註超額淘汰，也不應混入一般 UI 優化：需明確區分可重新生成的快取與使用者主動保存的資料，清理前提供可理解的政策及匯出途徑。單篇 800 KB 上限和「100k 原文加 600 筆標註仍小於 800 KB」亦不能同時無條件保證，需定義實際超額行為。

建議交付順序：

1. **閱讀記錄與切換安全**：完成搜尋、最近閱讀、目前文章、草稿保護、刪除復原，以及身份切換和非同步結果歸屬。沿用現有儲存格式即可交付可見改善。
2. **本機儲存與備份**：單獨驗證結果精簡的無損性、IDB 遷移、失敗恢復及離線完整還原，再發布。相似文章提示可獨立安排，不應成為改善歷史清單的前置條件。
3. **索引與 blob 同步**：合併規則、GC 引用、雜湊、版本閘門及回滾政策定案後再實作，Worker 與 selfhost 同步驗收。

現有短工期估算涵蓋的內容已擴大到資料遷移、雙後端與相容性處理，應按上述交付邊界重新估算。第一期驗收要直接涵蓋「快速回到剛才讀的文章」「切換不丟草稿」「刪除可復原」，並在 zh-CN、zh-HK 與手機尺寸下確認；後續各期再加入對應資料完整性測試。

本次結論基於計劃與現有程式碼的靜態核對，以及官方 D1 限制查證；尚未以實作或瀏覽器測試驗證計劃中的行為。
