# AI 思考強度按任務設定：sol61 複核問題修正報告

日期：2026-11-02
範圍：修正 sol61 複核提出的 8 項問題；未重寫功能、未 commit、未 push。

## 一、逐項修正

### 1) unsupported 思考記憶 key 太粗（High）

- `modules/api.js`
  - `thinkingTargetKey()` 改為 `provider|format|apiUrl|model|level`。
  - `isThinkingUnsupportedFor(resolved, level)` 與 `markThinkingUnsupported(resolved, level)` 均帶入實際送出的等級；只拒絕 `none` 不會再讓同模型的 `high` 被跳過。
  - `AUTH_EVENT` 的 `SIGNED_OUT`、`ACCOUNT_CHANGED`、`SESSION_INVALID` 與 `bdc:ai-catalog-change` 都會呼叫 `resetThinkingFallbackMemory()`，清空 unsupported 與 notified 記憶。
- 測試：`tests/ai-protocol-integration.test.mjs`
  - 供應商只拒絕 `none` 時，之後 `high` 仍會送出。
  - 同一 provider 換 endpoint 後會重新嘗試該等級。

### 2) Gemini 思考預算與截斷（High）

- `modules/ai-protocols/gemini.js`
  - Gemini 2.5 的 `maxOutputTokens = thinkingBudget + max(caller maxTokens, 1024)`；呼叫端未給 `maxTokens` 時答案保留 1024。
  - 保留 `low/medium/high` 及 `none` 的預算映射。
- `modules/api.js`
  - 抽出並匯出 `isLengthFinishReason()`，接受 `length`、`max_tokens`、`MAX_TOKENS`（大小寫不敏感）。
  - `requestAI()` 的截斷重試改用此判斷，Anthropic `stop_reason='max_tokens'` 與 Gemini `finishReason='MAX_TOKENS'` 都會觸發既有的一次加倍重試。
- 測試：
  - Gemini 2.5 high 的 `maxOutputTokens > thinkingBudget`，且等於 budget + max(caller, 1024)。
  - Anthropic / Gemini 的截斷原因會觸發第二次請求並加倍 `max_tokens` / `maxOutputTokens`。

### 3) LWW 合併仍可能丟失 thinking（Medium）

- `modules/sync-core.js`
  - 新增 `mergeAISettingsThinking(winner, loser)`。
  - 選出 `aiSettings` 勝出者後，把落敗方 `settings.thinking` 的鍵合併進勝出者；同名鍵以勝出者為準，兩邊都空則不輸出 `thinking`。
  - `updatedAt` 與群組 LWW 語意維持不變。
- 測試：`tests/ai-sync-regressions.test.mjs`
  - local 較新但沒有 thinking、remote 較舊有 thinking：保留 remote thinking。
  - remote 較新但沒有 thinking、local 較舊有 thinking：保留 local thinking。
  - 同名鍵以勝出者為準；兩邊都空不輸出 thinking。

### 4) Gemini 2.5 Pro 的 none（Medium）

- `modules/ai-protocols/gemini.js`
  - `gemini25ThinkingBudget()`：`gemini-2.5-pro`（含 preview 名稱）的 `none` 映射為 `thinkingBudget: 128`；`gemini-2.5-flash` 維持 `0`。
  - 程式註解說明 Pro 的 128 是「最低強度」而非真正關閉。
- 測試：`tests/ai-units.test.mjs`
  - `gemini-2.5-pro` 與 `gemini-2.5-pro-preview-06-05` + `none` → 128。
  - `gemini-2.5-flash` + `none` → 0。

### 5) 結構化 422 錯誤無法觸發降級（Medium）

- `modules/api.js`
  - `isThinkingParameterError()` 以安全 `JSON.stringify` 處理 `payload.detail`、`payload.errors`、`payload.error` 等物件／陣列，避免 `[object Object]`。
  - 仍只接受 HTTP 400／422。
- 測試：`tests/ai-protocol-integration.test.mjs`
  - `detail: [{ loc: ['body','reasoning_effort'], msg: 'Extra inputs are not permitted' }]` 會觸發一次不含思考參數的重試，且 `maxTokens` 恢復原值。

### 6) 助手「跟隨設定」重試沒有固定首次有效模式與模型（Medium）

- `features/assistant/assistant.js`
  - 新增 `features/assistant/request-plan.js` 的 `resolveAssistantRequestPlan()`：首次送出時把 `auto` 解析成實際等級（`resolveThinkingLevel('assistant').level`）並凍結當時 model spec。
  - `requestSnapshot` 同時寫入 `thinking` 與 `model`；重試直接沿用 snapshot，不再重新解析個人設定。
  - 首次與重試都以 `{ thinking, model }` 明確傳給 `onceCompletions()`／`streamCompletions()`。
  - `getAssistantModelSpec(modelOverride)` 在有 override 時直接回傳該 spec，不再經 `getTaskModelSelection()` 重挑；面板下拉與任務設定行為不變。
- 測試：`tests/ai-units.test.mjs`
  - 首次 `auto` 只解析一次，快照寫入 high + model。
  - 重試即使面板／任務設定已改變，仍使用快照的 thinking 與 model。
  - 明確等級不會呼叫任務設定解析。
  - 由於助手 UI 依賴完整 DOM，本次以純規劃函式測試＋程式路徑註解驗證，未跑完整瀏覽器助手流程。

### 7) 快取鍵與實際請求策略不一致（Medium）

- `modules/api.js`
  - `analyzeParagraph`、`analyzeWordInSentence`、`analyzeSentence`、`analyzeSelection` 的主要與 fallback `requestAI()` 都傳入同一個 `thinking`。
  - `getWordAnalysis`、`getWordPronunciations` 的 `fetchAIResponse()` 也傳入同一個 `thinking`。
  - 快取註解說明：結果仍以「要求等級」寫入，實際回應可能來自渠道降級為 auto。
- 測試：`tests/ai-protocol-integration.test.mjs`
  - 以 mock fetch 驗證 `analyzeWordInSentence` 與 `getWordAnalysis` 的 `reasoning_effort` 與 API 解析出的 thinking 等級一致（high／medium）。

### 8) 降級事件可能永遠不發（Low）

- `modules/api.js`
  - `thinkingUnsupportedTargets`（已拒絕，後續直接用 auto）與 `thinkingFallbackNotified`（已發過事件）分成兩個 Set。
  - 只有實際降級後的請求成功時才標記 notified 並發 `bdc:ai-thinking-fallback`。
  - 若首次降級重試失敗，不會標記 notified；下一次因 unsupported 記憶直接使用 auto 且成功時，會補發一次事件。
  - 串流路徑也套用相同語意。
- 測試：`tests/ai-protocol-integration.test.mjs`
  - 第一次 400 降級後重試得到 401（失敗）→ 不發事件。
  - 第二次因記憶直接 auto 成功 → 事件只發一次，level 為原本要求的 high。

## 三、仍存在的風險

1. **能力記憶仍是 session 內狀態**：重新載入頁面後，每個 provider／endpoint／model／level 會重新探測一次。若供應商在同一 session 內改變行為但沒有 auth／catalog 事件，記憶可能暫時過期。
2. **Gemini 輸出上限可能過大**：`thinkingBudget + answer reserve` 可能超過某些模型／網關的 `maxOutputTokens` 上限；目前沒有按模型查表夾限，需靠供應商回報錯誤。
3. **Gemini 2.5 Pro 的 none 不是真正關閉**：固定為 128 最低預算；UI 既有提示已說明部分渠道會降級。
4. **LWW 的 thinking 採鍵級復活**：勝出方若刻意清空某些任務，落敗方仍有舊值時會保留舊值；這是本次指定語意，無法用單一 snapshot 表達「刪除」。
5. **錯誤字串比對仍偏寬**：`max_tokens` 等關鍵字可能讓其他 400／422 token 上限問題也觸發一次不含思考的重試；結果通常安全，但該次會失去推理能力。
6. **助手只驗證純規劃函式**：未在真實瀏覽器逐個 panel mode 驗證重試；snapshot 僅存在記憶體，重新載入後重試會回到一般解析路徑。
7. **快取可能延後生效**：降級後以要求等級寫入的快取，會在 TTL 內優先命中；渠道之後恢復支援時，未必立刻重新送出該等級。
8. **未對真實供應商 live 驗證**：所有協議測試皆為 mock fetch；Gemini／Anthropic 的實際配額與錯誤格式仍建議抽樣驗證。
