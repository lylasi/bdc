## 摘要

本輪完成 4 項必要修正：

1. **preflight 後重新讀取操作會覆蓋未核對快照（Medium）**：`pushLegacyMigration()` 改成有界多輪核對——每次核對後重新讀 outbox，把核對等待期間才出現的未確認快照再核對一次；伺服器確認不存在的快照會先以交易清除，才允許用目前內容重新匯入。任何仍在變動、尚未核對的快照一律安全延後，不送 `final`、不清 gate、不改走逐篇上傳。匯入後的核對也改成比對「持久化的實際送出快照」，不再比對核對當下的本機內容，避免同一類等待期間修改造成假衝突。
2. **本機儲存用舊 outbox 覆蓋剛提交的 importSnapshot（Medium）**：`persistDocWithOp()` 把 outbox 的讀取、合併、寫入全部放進文章文件的同一個 IndexedDB readwrite 交易；並以交易內已提交文件的 revision 為下限，保留等待期間完成的確認。localStorage 後備也改成讀取、合併、寫入在同一個沒有 `await` 的同步區段完成。`recordImportSubmission()` 與新增的 `clearImportSnapshots()` 都加上交易內版本比對，不覆蓋、不誤刪另一份尚未核對的快照。
3. **flush 釋放 skipped 預占容量後仍回傳舊配額錯誤（Medium）**：`/articles/import` 的預檢失敗、flush 未被阻擋時，重新讀取已提交用量並重驗目前項目；容量足夠就繼續匯入同一請求，不再回傳 flush 前的 409。
4. **稀疏陣列指紋與 JSON 不一致（Low）**：`sortedJson()` 按 JSON.stringify 的陣列語意逐格輸出，空洞／undefined／function 都是 `null`；`Array(1)` 與其 JSON 往返 `[null]` 指紋一致，不同順序仍不同。

## 逐項修改

### 1. Medium — preflight 後重新讀取不得覆蓋尚未核對的舊快照

- `modules/article-sync.js:431`：新增 `snapshotNeedsVerification()`。只有「有 mutation ID、且快照內容與目前 payload 不同（delete 一律）」的操作才需要先核對；內容相同的重送只會被伺服器 skip，核對仍會成功。
- `modules/article-sync.js:508`：`verifySubmittedSnapshots()` 額外回報 `missing`（伺服器沒有這篇），不再只是略過。
- `modules/article-sync.js:660`：`pushLegacyMigration()` 的 preflight 改為最多 3 輪：
  - 每輪只核對尚未 resolved／conflicted／missing、且 `snapshotNeedsVerification()` 的操作；
  - 核對後一定重新讀取 outbox（`:676`），把等待期間被修改、因而新出現的未確認快照納入下一輪；
  - 核對失敗仍立即停止本輪並記錄錯誤（`:669`）。
- `modules/article-sync.js:682`：伺服器已確認不存在的快照，先透過新的 `store.clearImportSnapshots()` 以交易清除（`:684`），再重新讀取 outbox；若清除前又出現新快照，回報 `deferred` 不動它（`:695`）。這是「重新核對或安全延後」的實際落地，也避免舊快照內容不同時被永久誤判成另一筆未確認提交。
- `modules/article-sync.js:706`：建立匯入清單時，仍帶著未核對且有差異快照的操作放進 `deferred`，不匯入、不推送。
- `modules/article-sync.js:779`：匯入後的 `verifyChunk` 改為重新讀取 outbox，使用 `op.importSnapshot`（實際送出的內容與 mutation ID）核對，不再使用核對當下的本機 record；等待期間的新修改會由 `markOpsDone()` rebase 保留。快照遺失時回報 `legacy_snapshot_missing`，不假裝成功。
- `modules/article-sync.js:758`：`recordImportSubmission()` 若在交易內發現已有另一份未核對快照，會回報 `deferred`；`importChunk` 只送出已寫入快照的項目，並把實際送出的 `records` 交給 runner 核對。
- `modules/article-sync.js:604`／`:805`／`:826`：`runLegacyImportBatches()` 支援只核對實際送出的子集合；只要有任何項目被安全延後，就不送 `final`、不清 `gatePending`，直接回報 `deferred`。
- `modules/article-sync.js:871`：`syncArticles()` 收到 `legacy.deferred` 時停止本輪的 legacy 推送（仍記錄同步時間），下一輪重新核對；不會讓 `pushOutbox()` 用 `expectedRevision: 0` 逐篇送出而產生假衝突。

驗收測試：
- `tests/article-import-progress.test.mjs:539`：A／B 屏障。A、B、C 先匯入但回應遺失；先改 A，第二輪 preflight 只核對 A；在 `/articles/batch` 暫停等待期間修改 B 正文、刪除 C；釋放後重新核對 B／C 的舊快照並 rebase。最終 outbox 清空、衝突 0、伺服器上 A 分析／B 正文／C 墓碑都是最新值，沒有重新 import、沒有逐篇 create。
- `tests/article-import-progress.test.mjs:600`：直接驗證 `recordImportSubmission()` 不會用不同 mutation／內容的快照覆蓋舊快照（回報 `deferred`）；同一份快照重試仍幂等；`clearImportSnapshots()` 版本不符時不清除，版本相符才清除且保留 outbox 操作。
- `tests/article-import-progress.test.mjs:665`：舊快照存在但伺服器沒有這篇、期間又改了分析；本輪先核對出 missing、清除快照、再以目前內容匯入成功，無衝突、gate 關閉。
- 反證：暫時把 `MAX_PREFLIGHT_PASSES` 改成 1，A／B 測試失敗（B／C 留在 outbox、最新內容沒到遠端）；暫時停用 missing 快照清除，`舊快照在伺服器不存在` 測試失敗（回報 `deferred:true`）。

### 2. Medium — 文章儲存不得用舊 outbox 覆蓋剛提交的 importSnapshot

- `modules/article-store.js:508`：重寫 `persistDocWithOp()`。IndexedDB 路徑現在於同一個 `[docs, summaries, outbox]` readwrite 交易內：
  1. 讀取已提交文件與既有 outbox 操作（`:534`）；
  2. 以 `mergeStoredRevision()` 取交易前 record 與已提交文件 revision 的較大值（`:541`）；
  3. 以這個合併結果建立文件與新 outbox 操作（`:547`，`createOutboxOp()` 會保留既有 `importSnapshot` 與較高的 `expectedRevision`）；
  4. 全部寫入後才提交。
  交易成功後把合併後 revision 寫回呼叫端持有的 record（`:567`），避免後續 `replaceRecord()` 用舊版本覆蓋記憶體。
- `modules/article-store.js:493`：新增 `mergeStoredRevision()`。這是「保留期間已確認 revision」的交易內下限。
- `modules/article-store.js:512`：localStorage 後備改成在同一個同步區段讀 bucket、找既有 doc／op、合併、寫入，中間沒有 `await`，不會被另一份 async 工作插入。
- `modules/article-store.js:869`：把原本會自己讀 outbox 的 `buildOutboxOp()` 拆成同步的 `createOutboxOp()` 與讀取 wrapper；交易內直接使用已讀到的 `existing`，消除「交易外讀、交易內寫」的窗口。
- `modules/article-store.js:688`／`:704`／`:719`：`recordImportSubmission()` 加上 `importSnapshotMatches()`／`importSnapshotAction()`。已有不同快照時回報 `deferred`，不覆蓋；同一份快照重試維持幂等；操作已不存在或不再是 legacy create／update 也回報 `deferred`。
- `modules/article-store.js:789`：新增 `clearImportSnapshots()`，交易內比對 mutation ID（有 `submittedAt` 也比對）才移除快照；期間若出現新快照則回報 `deferred`。

驗收測試：`tests/article-import-progress.test.mjs:702`。以 fake IndexedDB 的 hook 在文章儲存的 outbox 讀取之後、提交之前插入 `recordImportSubmission()`：
- 分析修改：快照成功保留，payload 是最新分析，snapshot 的 mutation ID 與目前操作不同；
- 刪除：outbox 為 delete 且保留原匯入快照；
- 重新載入後同步：先核對舊快照、rebase 到 revision 1，再把最新分析與刪除送到遠端；衝突 0、outbox 清空。
- 反證：暫時把既有操作改回「交易外讀取、交易內寫入」，測試立即失敗（`剛提交的 import 快照被文章儲存覆蓋`）。

### 3. Medium — flush 釋放 skipped 容量後以最新用量重驗目前項目

- `cloudflare-worker/src/articles.js:884`：`handleImport()` 的逐篇預檢失敗時，先 `flush()`；flush 未被阻擋就重新 `readUsage()`，再對目前這篇重跑 `checkQuota()`。容量足夠就繼續本次請求的匯入，不再回傳 flush 前的 409。
- flush 內原有的「重試前重讀用量」與「全部 blocked 都是重複項目時重算用量」維持不變（`cloudflare-worker/src/articles.js:766`、`:840`、`:844`）。

驗收測試：`tests/articles-import-race.test.mjs:831`。重現原情境：實際只剩 1,000 bytes；B 先暫記 900-byte 重複項目，再處理 200-byte 新文章；另一個請求在 B 的批次送出前先建立該重複 ID（實際只佔 1 byte）。同一請求回 200、`imported:1`、`skipped:1`、ids 只有新文章；用量、2 筆 create change、`next_seq=3` 都正確；重送只 skipped，不新增資料或序號。
- 反證：暫時把 quota 失敗分支改回「flush 未 blocked 仍回傳 flush 前的 quota」，測試回 409 `article_quota_exceeded`、imported 0。

### 4. Low — 稀疏陣列指紋按 JSON 序列化語意

- `modules/article-sync.js:379`：陣列改為逐格 `sortedJson(value[index])`；空洞讀到 `undefined`，和 undefined／function 一樣輸出 `null`，與 `JSON.stringify` 的 `[null]` 一致。物件鍵排序邏輯不變，不同陣列順序仍產生不同字串。
- `modules/article-sync.js:399`：把內容指紋函式具名為 `articleContentKey()` 並匯出，供測試直接驗證；`docContentKey()` 與核對流程共用同一份實作。

驗收測試：`tests/article-import-progress.test.mjs:78`。`Array(1)` 與 `JSON.parse(JSON.stringify(...))` 的 `[null]` 指紋相同；`Array(3)` 與 `[null,null,null]` 相同；`[1,2]` 與 `[2,1]` 不同。
- 反證：暫時改回 `value.map(...).join(',')`，測試失敗（`[]` vs `[null]`）。

## 未完成事項與風險

1. **preflight 最多 3 輪、其餘安全延後**：若使用者在三輪核對期間持續修改不同文章，本輪會回報 `deferred` 並在下一次自動同步重試；不會丟資料，但該輪不會推送 legacy 變更。這是刻意的有界策略，避免無限追趕持續變動的 outbox。
2. **跨分頁同時寫快照**：`recordImportSubmission()` 與 `clearImportSnapshots()` 都會在交易內比對 mutation ID／`submittedAt`；偵測到較新的快照就延後，不會覆蓋或誤刪。但同一瀏覽器多分頁同時匯入仍可能多等一輪，未另外建立跨分頁鎖。
3. **revision 下限只加在 `persistDocWithOp()`**：這是本輪 importSnapshot 交錯的直接路徑。`persistDoc()`（例如只更新 lastOpenedAt）與 `persistDocWithMeta()`（衝突 metadata）仍是原本的單次寫入；跨分頁同時確認舊回執時，理論上仍有極窄的 revision 回退窗口，不在本輪 4 個問題範圍內。若後續要全面消除，應把同一交易內 revision／pending 合併套到所有文件寫入路徑。
4. **Worker 修正只在預檢失敗路徑多讀一次用量**：正常匯入不增加查詢；接近配額時會多一次 `readUsage()`，可接受。PostgreSQL 交易語意未重新實測（本輪未設定 `BDC_TEST_PG_URL`；相關 6 項 skip）。
5. **既有 phonetics 測試失敗**：全量 Node 測試唯一失敗是 `tests/phonetics.test.mjs` 的 vm import 語法問題，與本輪修改檔案無關；未擅自修改其他 session 的 phonetics 模組。
6. **UI 驗收**：本輪沒有新增或修改使用者可見文字，`zh-CN`／`zh-HK` 鍵集合仍一致（各 1987 鍵）；沒有新增 locale key。
