## 二、六項修復的逐項複核

### P1-1 批次保存失敗後失敗數變 0、重試入口消失 — 成立

- `features/article/article.js:2289-2344` 以 `unsavedParagraphs`（key 為 `articleId + contentVersion`）記錄「實際保存失敗」的段落；`failedIndicesForRecord` 把記錄層失敗與未保存段去重合併，`refreshFailedStateFromRecord` 讓畫面與按鈕共用同一來源。
- 單段保存失敗：`features/article/article.js:4807-4820` 先保存再更新畫面，失敗時登記未保存並以 `save_failed` 重繪。
- 批次保存失敗：`features/article/article.js:5260-5284` 保存失敗時保留未保存標記、把成功段退回失敗、重算失敗數與批次入口。
- 成功保存後：`features/article/article.js:4821-4831`、`5270-5271` 清除未保存標記並同步重繪其他段落，避免「畫面成功、記錄失敗」。
- 測試：`tests/article-reliability.cjs:696-796` 以真正的 `IDBObjectStore.put` 交易 abort（非容量預檢）重現，覆蓋摘要、按鈕可見/可用、逐段重試、重載、恢復寫入後遞減。

### P1-2 單段被提前解鎖、舊回應覆寫 — 成立

## 五、殘留風險與條件

1. **程序條件**：計劃建議的第二次獨立審核未完成（助手工作階段無進度），本報告不能替代其結論。
2. **全篇分析保存失敗**：`saveArticle` 失敗仍只走既有 toast 與歷史狀態，沒有登記成逐段「未保存」；本次只修了單段／批次重試路徑。若要求「所有保存失敗都可在重載後重試」，這仍是缺口。
3. **`status: 'cancelled'` 跨版本**：舊客戶端可能把停止的半段當完整回答；回滾時不得把 cancelled 改寫成 complete。
4. **測試邊界**：真實 timeout、真機、IME、螢幕閱讀器、真實 AI／TTS、真實同步後端與跨版本往返未執行。
5. **混合工作區**：`article-store`、`reading-store`、sync、Worker、selfhost 仍有其他工作階段的未提交變更；正式驗收與提交前應固定依賴版本，只挑本次檔案。
6. **`unsavedParagraphs` 僅在記憶體**：重新載入以磁碟為準（測試已驗證一致）；多分頁同時保存時可能短暫多顯示重試入口，不會寫錯資料。
7. **`article.js` 仍為大型單檔**：本次只收斂狀態與所有權，未拆檔。
