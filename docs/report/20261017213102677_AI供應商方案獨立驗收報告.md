日期：2026-10-17。範圍：目前工作區實作，對照 `docs/plan/20261017130932086_D1按使用者同步AI供應商設定完整方案.md` 原方案，並核對實作報告與偏差決策。沒有修改產品程式、私人設定或正式服務。

## 驗收結論

**主要架構已完成，但尚未按完整方案通過驗收。** 獨立重跑的既有測試均通過；補充瀏覽器案例卻重現六項問題，其中新裝置 Key 下載和同步期間資料遺失直接影響核心需求。建議先修正下列問題，再執行正式資料遷移及發布。

## 已確認問題（按處理優先度）

### F1／P1：新裝置不會下載已同步的個人 Key

- 位置：`modules/ai-credential-sync.js:428`、`modules/ai-profile-storage.js:475`。
- 原因：同步已建立 `remoteMap`，但待處理集合只有 `Object.keys(profile.credentials)`；新裝置從普通 snapshot 取得供應商定義後，本機沒有憑證列。套用 snapshot 也不會建立供下載使用的憑證狀態。
- 重現：空白帳戶 profile → 套用包含 `personal-test` 的遠端設定 → 模擬 `/ai-credentials` 回傳其 version 1 憑證 → 執行同步。
- 實際：只請求 `/ai-credentials`，沒有請求 `/ai-credentials/personal-test`；`credentialCount=0`，狀態卻為 `synced`。新裝置仍無法使用該供應商。
- 修正要求：對已存在且 binding 相符的遠端供應商建立可下載狀態，處理遠端憑證；保留本機明確 `local-only` 的優先權，不能把其他供應商的 Key 綁過來。補上全新裝置首次登入測試。

### F2／P1：同步完成會覆蓋期間新存的供應商，單一分頁也會發生

- 位置：`modules/ai-credential-sync.js:423`、`modules/ai-credential-sync.js:445`。
- 原因：在非同步網路請求前載入整份 profile，完成後原樣整份寫回；UI 保存沒有參與同一把鎖，也沒有對 profile revision 做提交檢查／合併。
- 重現：上傳供應商 A 的 Key，延遲 PUT 回應 → 同一分頁保存新供應商 B → 放行 A 的成功回應。
- 實際：B 保存後存在，A 同步完成後 B 消失（`before=true, after=false`）。這比實作報告描述的「多分頁最後寫入者勝出」範圍更大。
- 修正要求：提交時重讀最新 profile，只合併仍符合該次 mutation／revision 的憑證變更；或讓所有 profile 讀改寫遵循一致的序列化機制。測試保存、換 Key、刪除及任務修改與同步交錯。

### F3／P1：舊帳戶的延遲 401 會登出新帳戶

- 位置：`modules/ai-catalog.js:246`。相同模式亦見 `modules/ai-credential-sync.js:405`、`:460`；初始化 `/me` 的回調也需要一併檢查。
- 原因：收到 401 後先呼叫全域 `auth.invalidateSession()`，沒有先確認回應仍屬目前 auth generation／帳戶。後面的成功路徑 generation 檢查保護不到錯誤分支。
- 重現：A 下載 managed Key 的請求延遲 → 明確登出 A → 登入並驗證 B → A 的請求回 401。
- 實際：B 從 `loggedIn=true` 變成 `false`，錯誤為 `managed_login_required`。
- 修正要求：所有非同步回應，包括 401／403、例外及 finally 更新，都先檢查原帳戶、endpoint、auth generation，再修改目前會話。

### F4／P1：直接切換帳戶仍繼承上一帳戶的共享 Key 與驗證期限

- 位置：`modules/ai-catalog.js:433`、`:453`、`:236`；`modules/sync-cloudflare.js` 的 `ACCOUNT_CHANGED` 事件。
- 原因：catalog 只在 `SIGNED_OUT`／`SESSION_INVALID` 清 Key。`ACCOUNT_CHANGED` 僅刷新，既有 `verified`、expiresAt、credentialCache 仍有效；快取命中也只比較 catalogVersion。
- 重現：A 驗證並取得共享 Key → 不先登出，直接登入 B → B 的 catalog 刷新模擬網路失敗。
- 實際：目前使用者為 B，但 `status=verified, usable=true, oldKeyRetained=true, reusedOldKey=true`。B 的新目錄驗證未成功，卻沿用 A 的存取時段及 Key。
- 修正要求：帳戶／endpoint 改變時同步鎖定 managed 狀態、清 Key、推進 generation；新帳戶驗證成功前不得恢復。亦須涵蓋跨分頁 token／userId 更新。

### F5／P2：管理員「取得模型」會直接擴大全站開放模型列表

- 位置：`features/ai-admin/ai-admin.js:649`、`:651`。
- 原因：探索結果直接取代 `provider.models`，而該欄就是發布用白名單；未分開「發現的模型」與「管理員確認開放的模型」。
- 重現：原白名單只有 `allowed-model` → 取得模型返回它及 `expensive-new-model` → 直接發布。
- 實際：發布 payload 包含兩個模型，沒有逐項確認新增模型。也會清掉原先模型的能力標記。這違反方案「不能把探索到的所有模型直接全站開放」。
- 修正要求：保留既有白名單，新模型預設未勾選；探索只更新候選列表，發布使用明確確認的集合。
- 相關未完成需求：管理員表單沒有共用個人的兩欄／自動辨識流程；新供應商固定為 `openai-chat`，協議仍須手選，開放模型是文字區而非方案所述選取流程。

### F6／P2：舊版個人任務模型選擇在遷移時被刪除

- 位置：`modules/ai-profile-storage.js:649`、`:672`。
- 原因：遷移複製供應商與 Key，但沒有把 `settings.ai.models`／`tasks` 的個人供應商引用放入新 profile，隨後刪除舊欄位。
- 重現：舊設定有供應商 `mine`、個人 Key，以及 assistant／qaChecking 指向 `mine:m1` → 執行遷移。
- 實際：供應商 `mine` 保留，但新 `taskModels={}`，舊 tasks 已移除。原本逐任務選擇無法恢復。
- 修正要求：安全地保留已遷移個人供應商的模型引用，不能轉成不受限制的 managed 定義；保存與讀回成功後才刪除舊映射。原方案明確要求保留既有任務選擇。
