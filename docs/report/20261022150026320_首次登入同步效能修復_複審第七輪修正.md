## 1. 問題 1：第二次重建可能重用上一個代際

### 1.1 根因

第六輪的 `mergeStoredRevision()` 在 `resetRevision` 分支使用：

```js
generation: Math.max(storedGeneration, memoryGeneration + 1)
```

且合併基底是呼叫端記憶體 `...record`。複審重現的狀態是：

- 分頁 B 記憶體：`generation 0 / revision 3`；
- 持久化文件：`generation 1`（分頁 A 已完成第一次重建）；
- 被確認 404 的操作（分頁 A 後來送出的 PUT）：`generation 1`。

於是 `max(stored=1, memory+1=1) = 1`，沒有產生新代際；同時 `...record` 把 B 的舊正文
（`body-3`）寫回文件。第二次重建仍停在 generation 1，A 那筆 generation 1 的回執
便重新通過 fence，把 revision 推到 2，而遠端其實不存在。

### 1.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:577-607` `mergeStoredRevision()` | 重建代際改為 `max(持久化文件代際, ledger 代際, 被確認 404 的操作代際, 記憶體代際) + 1`；不再用「記憶體 + 1」推算 |
| `:610-625` `contentFromStoredDoc()` | 新增：重建時正文／分析／標題／來源／時間以持久化文件為準，保留另一分頁剛保存的最新內容 |
| `:750-760` `persistDocWithOp()` | 交易內同時讀文件、outbox、ledger，把 `operationGeneration`（目前 outbox 操作的代際）傳入 merge；操作身分（`resetFromMutationId`）不符時仍回 `requeue_deferred`，作為「重複處理」的判別 |

「重複處理同一次 404」與「新的重建」的區分方式：

- 同一次 404 重送時，outbox 已被第一次重建換成新的 `create` 操作（新 mutation ID），
  交易內的操作身分核對會回 `requeue_deferred`，不會再次遞增代際；
- 真正的新重建（目前 outbox 操作仍是送出 404 的那一筆）才會以該操作的代際為基準 +1。

### 1.3 驗收（新測試 `tests/article-rebuild-generation.test.mjs:571`）

- B 停在 pull 等待、A 第一次重建到 generation 1 → 建立成功 → 保存 `a-v6` 並送出 PUT
  （伺服器已提交、回應暫扣）；
- 遠端再次消失後放行 B，B 用舊記憶體處理 404；
- 斷言第二次重建為 `generation 2 / revision 0`，正文是 `a-v6`（不是 B 的 `b-v4`），
  outbox 是 `create / expectedRevision 0 / generation 2`；
- 以 `markOpsDone` 與 `markOpDone` 分別投遞 generation 1 的舊回執（含放行真正的
  `afterPut` 回應）：文件 revision／`updatedAt`／outbox 都不變；
- 之後建立成功（遠端 revision 1），再更新到 revision 2，無衝突。

## 2. 問題 2：刪除待建立文章的捷徑會倒退代際

### 2.1 根因

`deleteArticle()` 的「尚未上傳的 create 直接撤掉」捷徑：

- 只用交易外的 `readOutbox()` 與呼叫端記憶體 `record` 判斷；
- tombstone 由舊記憶體 `toDoc(tombstone)` 寫入；
- 直接刪除目前 outbox。

當 B 的記憶體是 `generation 1`、持久化文件／摘要／outbox 已是 `generation 2` 時，
捷徑把文件與摘要寫回 generation 1，並刪掉 generation 2 的 create；之後放行
generation 1 的舊 PUT 回應，`markOpDone` 因代際相同而把 revision 推高。

> 重現條件補充：若 B 的清單只有摘要（`summaryOnly`），`deleteArticle()` 會先
> `ensureArticleLoaded()` 從儲存補全文，反而拿到新代際而掩蓋問題。因此回歸測試
> 必須先讓 B 保持「已開啟過的全文記錄」（本輪測試以 `ensureArticleLoaded()` 建立）。

### 2.2 修正

| 位置 | 內容 |
| --- | --- |
| `:1563-1586` `pendingCreateTombstone()` | 以持久化文件＋目前操作＋ledger 決定是否可撤銷 create：必須是非 legacy `create`、持久化 revision 為 0、操作代際等於目前有效代際 |
| `:1593-1690` `deleteArticle()` | 捷徑改為在同一個交易內讀 `[docs, article_summaries, outbox, article_generations]`；tombstone 內容取自持久化文件、代際取 `max(doc, ledger)`，並同步寫 ledger／摘要、刪 outbox |
| `:1602-1627` 後備分支 | localStorage 桶用同一套 `pendingCreateTombstone()` 規則，寫入 tombstone、ledger、移除 outbox，不再使用舊記憶體 tombstone |
| `:1657` | 只有 ledger 低於文件代際時才補寫，維持「只前進」 |
| `:1316-1334` `ensureArticleLoaded()` | 補上 fallback 讀取分支，讓後備模式重新載入後仍能取得全文（否則捷徑與一般編輯在後備模式會找不到全文） |

### 2.3 驗收（`:707`、`:800`）

- IndexedDB：A 第一次重建（gen 1）→ B 重新載入並保持全文 → A 完成建立 → A 再次重建
  到 gen 2（create 尚未送出）→ B 用記憶體 gen 1 直接刪除：
  - 文件／摘要／ledger 都保持 `generation 2`、revision 0，outbox 被安全撤銷；
  - 以 `markOpsDone`／`markOpDone` 投遞 gen 1 回執，tombstone 不變；
  - 復原後以 `create` 建立成功，再更新成功。
- localStorage 後備：兩次重建到 gen 2 後，用 gen 1 的分頁刪除；斷言桶內文件、
  `generations[id]` 都是 2，outbox 不含該篇，重新載入後仍是 2。

## 3. 問題 3：完整 pull 移除文件後還原同一 ID 失去代際屏障

- `reconcileFullList()` → `deleteDoc()` 同時刪除文件與摘要，代際消失；

- 重建前暫扣的 generation 0 回執於是重新匹配，把還原後的 create rebase 成

## 4. 問題 4：截取末 8 筆會解除升級前的舊回執防護

### 4.1 根因

`LEGACY_SUPERSEDED_LIMIT = 8`：

- 讀取端 `ignoresRebuiltReceipt()` 只比對 `slice(-8)`；
- 寫入端 `createOutboxOp()` 只繼承末 8 筆。

升級前清單若已有 9 筆，第一筆不在末 8 筆內，於是它與文件同為 generation 0 時
不再被視為過期，回執可把 `revision 0 / create` 推成 `revision 40 / update / expectedRevision 40`。

### 4.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:653-657` `ignoresRebuiltReceipt()` | 改為完整 `includes()`，不再截斷 |
| `:1135-1138` `createOutboxOp()` | 繼承時完整複製整份舊清單（`[...inherited.supersededMutations]`），不截斷 |
| `:1128-1139` | 新流程仍只在「同一代際的既有操作」上繼承，且從不 append，因此清單不會無界成長 |

### 4.3 驗收（`:1026`）

- 直接寫入既有 outbox：9 筆 `supersededMutations`、generation 0、`create / expectedRevision 0`；
- 以第一筆（不在末 8 筆）呼叫 `markOpDone`：文件 revision／`updatedAt`、outbox 類型與
  基準都不變；
- 保存一次後清單仍完整 9 筆且順序不變；
- 以第一筆＋第二筆呼叫 `markOpsDone`：同樣不變；
- 再保存一次，清單仍是 9 筆（證明新流程不累加）。

## 8. 未完成項與仍存風險

1. **（既有缺口，HEAD 已存在，本輪未修）** `markOpFailed()` 經 `persistDocWithMeta()`
   仍以呼叫端記憶體內容寫文件；若上傳失敗發生在本機已保存新正文之後，正文可能被
   覆回舊內容。本輪只確保它的代際／版本不會倒退（`persistDocWithMeta` 已採用 ledger，
   `modules/article-store.js:2412-2460`）。
2. **（既有缺口，HEAD 已存在，本輪未修）** IndexedDB 不可用時：
   - `applyRemoteDocs()` 仍回 `idb_unavailable`，匯入後確認／gate 未清；
   - `markOpDone()`／`markOpsDone()` 沒有 localStorage 後備實作，後備模式下來自同步
     的回執會失敗。本輪只補了 `ensureArticleLoaded()` 與刪除捷徑的後備語意。
3. **（既有行為，本輪未擴大處理）** `restoreArticle()` 在遠端文章已不存在時仍送出
   `/restore`，伺服器回 404 會變成衝突（`pushOne()` 只對 `update` 的 404 走重建）。
   本輪已保證還原後的代際不會倒退，但沒有把 restore-404 改走 create；若需要，建議
   另一輪把 `restore` 的 404 也納入重建流程。
4. **DB schema 升級**：`bdc-articles` 由 v3 升到 v4（新增 `article_generations`）。其他
   仍開著舊版資料庫的分頁會由 `onversionchange` 關閉連線；升級後需要重新載入頁面才能
   使用新 store。沒有其他資料轉換；舊文件的 `generation` 會在第一次寫入、回執、
   套用遠端文件或刪除時補寫 ledger。
5. **ledger 不會清除**：每篇「曾被重建過」的文章（含之後被移除的 ID）在
   `article_generations` 留一列。列數受文章 ID 數限制，但永久刪除後不會回收；目前
   沒有安全的前綴清理方式（同 ID 可能被備份還原），暫不清理。
6. **備份格式新增 `generation`**：舊版應用讀到新備份時會忽略未知欄位；新應用讀到
   舊備份（沒有 `generation`）時以 ledger 接手。跨裝置且兩邊 ledger 都為 0 時，
   仍以 0 起算（沒有其他來源可判定代際）。
7. **未跑 Playwright 巡檢**：本輪改動集中在 IndexedDB 交易與同步回執，已用 fake
   IndexedDB＋雙實例覆蓋；依約束只執行 node 測試與 i18n 檢查。
8. **既有測試失敗**：`tests/phonetics.test.mjs:47` 與本輪無關，已在乾淨 HEAD 重現。
