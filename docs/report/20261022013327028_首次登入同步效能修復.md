# 首次登入同步效能修復

- 日期：2026-10-22
- 依據：`docs/report/20261022003649630_首次登入同步緩慢原因分析.md`
- 範圍：純前端靜態 SPA（`modules/`、`features/sync/`）＋ Cloudflare Worker ＋ selfhost（SQLite／PostgreSQL）
- 未修改 `ai-config.js`；未執行 git commit／push

## 摘要

本次依報告優先順序完成五項修復，全部保持 local-first 與既有同步語意：

1. **文章匯入後核對截斷**：`importMax=100`、`batchMax=50` 的落差已消除。匯入後按 `batchMax` 分批核對全部記錄，並以批次交易完成 `markOpsDone`。以 120 篇舊文章實測：`/articles/import` 3 次（100＋20＋final）、核對 `/articles/batch` 3 次（50＋50＋20）、**逐篇 `POST /articles` 0 次、409 0 次**（修復前後半段會多出約 70 次 create＋讀回）。
2. **後端 batch DB N+1**：`/articles/batch`、`/reading/batch` 改為分組 `IN (...)` 集合查詢（以 D1 bound parameter 上限 100 為準分批）；`/articles/import` 的既有 ID／用量查詢改為一次預取＋增量維護；`/articles/usage` 改 SQL 聚合；閱讀 mutation 先批次預取實體與 ledger 回執，寫入仍逐筆保留 claim／版本檢查與交易語意。
3. **`/snapshot` 全量處理與 timeout**：新增 `?version=` 條件讀取（舊後端不認得參數時照常回完整 payload，自然 fallback）；前端在同一帳戶記憶體快取最近一次快照的 JSON 字串，未變更時不重新下載（命中時重新 parse 一份新物件，避免呼叫端改寫快取）；`syncNow` 不再重複全量 `JSON.stringify`；`apiRequest()` 的 timeout 現在涵蓋 body 下載（先緩衝再回傳 Response），並可用 `beginSyncRound()/endSyncRound()` 限制整輪期限（預設 5 分鐘，`SYNC.syncRoundMs` 可覆寫）。
4. **本地套用成本**：文章下載改批次 IndexedDB 交易（一批 50 篇一個交易），記憶體清單以一次 O(N) 合併＋Map 索引更新；`findRecord()` 不再每次掃描整個陣列。閱讀下載同樣改批次交易（IndexedDB 一個交易、localStorage 後備一次讀寫整個 bucket），同一頁重複 key 先去重。
5. **備份與同步鎖分離**：同步完成後才以 `setTimeout(0)` 建立備份，不再 `await` 佔用 `syncInFlight`；自動備份以「頁面 session ID＋文章／閱讀寫入世代＋快照群組時間戳」簽章去重，並限制同時只有一個自動備份在跑；備份裁剪改讀中繼資料，不再為每一包備份重新解析 payload；備份匯出改為唯讀（`hydrate:false`），避免在鎖外用較早的讀取結果覆寫同步剛更新的記憶體。

## 風險與注意事項

1. **整輪期限**：預設 5 分鐘（`SYNC.syncRoundMs` 可調）。文章／閱讀階段逾時只讓該階段失敗（游標已逐頁提交，下一輪續傳）；快照階段逾時會顯示自動同步失敗，但本機資料不受影響。極大型首次同步可能跨多輪完成。
2. **快照條件讀取**：只在記憶體快取仍對應同一版本時使用；重新載入頁面後第一次仍是完整 GET（沒有跨 session ETag）。快取只保留 JSON 字串（上限 8 MiB，超過即不快取、退回完整讀取），命中時重新 parse，避免 `lwwMerge` 或套用流程改寫巢狀群組而污染下一次結果。舊後端忽略 `?version=`，行為與修復前相同。
3. **`apiRequest` 現在會緩衝完整 response body**：目前沒有任何同步呼叫端使用串流；大型回應會多一份 buffer 記憶體，但可確保 timeout 涵蓋下載。
4. **備份簽章**：包含每次頁面載入的隨機 session ID，因此跨頁面載入的第一次自動同步一定會重建一次備份（避免世代歸零造成誤判）；同一頁面內沒有資料變更時才跳過。若某個資料變更沒有更新 `dictationUpdatedAt`／`vocabularyUpdatedAt`／`qaUpdatedAt`／`assistantUpdatedAt` 或文章／閱讀寫入世代，理論上可能漏掉一次自動備份（手動備份不受影響）。
5. **`/articles/import` 用量**：改為請求開始時快照＋增量維護；與另一台裝置並發匯入時，仍可能超出配額少許（與修改前同一類競態，非本次新增）。
6. **本地套用批次交易**：`applyRemoteDocs` / `applyRemoteTombstones` / `markOpsDone` 仍不支援 localStorage 後備（與修改前 `applyRemoteDoc` 相同）；IndexedDB 不可用時回報 `idb_unavailable`。
7. **閱讀合併順序**：同一頁重複 key 會去重（保留最後一筆），因為 `/reading/batch` 回傳的是「目前」實體；若未來後端改為回傳歷史版本，此去重需要重新檢視。
8. **後端 SQL 相容性**：`IN (...)` 分批上限以 D1 的 100 個 bound parameter 為準（owner 佔 1～2 個，其餘 90 個給 ID）；selfhost SQLite／PostgreSQL 均支援，且已用真實 selfhost 測試覆蓋。
9. **測試檔調整**：`tests/reading-reliability.test.mjs` 只調整並發屏障的攔截範圍（同時攔 `get` 與 `all`），斷言與測試意圖不變。
