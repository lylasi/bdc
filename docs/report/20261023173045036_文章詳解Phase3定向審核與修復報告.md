## 一、審核方式與限制

第一次完整 Phase 3 審核與一次窄範圍重試都因 Codex 工作階段停滯而取消。依使用者指示重試後，改為兩個定向審核：

1. **P3-T1 續作／checkpoint**：只審 `features/article/article.js` 的分析續作路徑、`modules/article-store.js` 的 `saveAnalysis()` 與 `tests/analysis-checkpoint.cjs`。
2. **P3-T2～T5 與渲染／探針**：只審快取治理、分詞、locale 狀態保留、句尾渲染與 perf probe，不要求跑完整回歸。

兩次都成功回覆並提出具體代碼位置。限制如下：

- Codex 回覆時處於 Plan Mode，無法寫入檔案；本報告由協調方依回覆內容落盤。
- 這是定向審核，不是完整 Phase 3 的形式化簽核；未涵蓋文章模組全部歷史程式碼。
- 修復後由協調方逐項重跑斷言，不單獨採信實作方回報。

## 三、關鍵修復說明

### 3.1 續作失敗與最終保存（T1-F1／F2／F4）

- `results` 是續作與最終保存的唯一真相；失敗段不得因為「已有結果陣列」而被當成成功。
- `finalizing` 是取消的禁區：只要最終保存已開始，取消不得再排入 `cancelled` 寫入。
- `saveAnalysis()` 的成功語義收緊為「持久化成功」；記憶體不再領先磁碟。

### 3.2 快取兩層合併（C-F5／F6）

- IDB 是較持久、較可信的一層；同鍵時不應被 localStorage 的過期時間反向覆蓋。
- 清理失敗必須可觀測： `ok:false`、`removed:0`、`pendingRemoval>0`，且不更新 24 小時節流時間。

### 3.3 locale 狀態（A-F1／R-F4）

- 快速連切時，第二次 capture 可能發生在 DOM 已重建、內容尚未 restore 的空窗；因此必須把「待還原快照」一起合併，而不是只信任當前 DOM。
- 備註輸入框的選取範圍與草稿同等重要；restore 時先聚焦再 `setSelectionRange`。

### 3.4 句尾渲染與探針（P-F2／F5／F6）

- `splitText()` 同時完成「截斷原節點」與「插入新節點」，是唯一能保證尾段仍在 DOM 的做法。
- 探針不得改變產品行為，但也不得記錄錯誤狀態：取消就是 `cancelled`，第一輪就必須有本回合的規模。

## 五、剩餘風險

1. **checkpoint 寫入放大**：初次分析與續作都每 1.2 秒寫整份 JSON；長文的 checkpoint 成本仍未單獨量測。
2. **最終保存期間取消的顯示語義**：記錄以最終保存結果為準，畫面可能已顯示取消；尚未加 UI 說明。
3. **HTML 字串預先包字路徑**：`replaceOutsideTags` 仍使用舊 ASCII regex；表格／舊分析 HTML 路徑的連字號與重音詞可能先被切斷。
4. **locale restore 的串流邊界**：助手串流最多等 6 秒 settle；面板 scroll 依賴最後一次 render，快速重繪可能退回頂部。
5. **發布步驟未執行**：部署前仍需 `node scripts/update-release-map.mjs`；本輪未 commit／push／deploy。
