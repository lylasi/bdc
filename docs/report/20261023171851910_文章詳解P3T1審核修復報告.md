## F1（高）：續作失敗段未保存，最終仍標 complete

### 根因

`resumeAnalysis()` 的 `runNext()` 只在 `outcome.ok === true` 時 `results.set(idx, result)`：

- `outcome.ok === false` 只呼叫 `renderParagraph`，失敗結果沒有進入 `results`。
- `catch` 分支同樣只 render，沒有 `results.set`。

最終保存只把 `results` 的索引寫回 `paragraph_analysis`，因此失敗段仍是舊的 `null`；`analysisRunStats()` 看不到失敗，`failed=0`，`status` 被寫成 `complete`，重開後 `isIncompleteAnalysisRun()` 為 false，續作入口消失。

### 修法

`features/article/article.js` `resumeAnalysis()`：

- 成功與失敗都先組出 `result` 再 `results.set(idx, result)`。
- 失敗用 `outcome.result || paragraphPipeline.failedParagraphResult(outcome.errorCode)`。
- `catch` 用 `paragraphPipeline.failedParagraphResult(error?.code || 'provider_error')`。
- 失敗結果同樣排程進度 checkpoint。
- 最終保存依完整 `paragraph_analysis` 重算 `analysisRunStats()`；有失敗時 `status=partial`。
- 最終保存成功且為 `partial` 時直接顯示續作 banner，不必等重新載入。

### 測試

新增「情境 F1」：

- 10 段先完成前 5 段 checkpoint，重新載入後續作。
- mock 讓續作第 2 段（index 6）回 500。
- 斷言 `analysis_run.status=partial`、`failed>0`、該段 `failed=true` 且有 `errorCode`。
- 重新載入後失敗段仍顯示 `failed`，續作 banner 顯示 9/10，續作按鈕可見。

修復前紅燈：`status=complete`、`failed=0`、失敗段仍是 `null`、重開後顯示 `pending` 且無續作入口。修復後全綠。

## F2（中）：最終保存期間取消可把 complete 蓋成 cancelled

### 根因

`cancelAnalysisCheckpoint(cp)` 只跳過 `cp.finalSaved`，沒有檢查 `cp.finalizing`。`writeAnalysisCheckpoint()` 又對 `requested === cancelled` 繞過 `finalizing/finalSaved` 檢查，因此最終保存交易還在進行時按取消，會排入一筆 `cancelled` checkpoint；交易提交成 `complete` 後，這筆 checkpoint 再把記錄覆蓋成 `cancelled`。

### 修法

`features/article/article.js`：

- `cancelAnalysisCheckpoint()`：`cp.finalSaved || cp.finalizing` 直接回傳 resolved `null`，不排入 cancelled。
- `writeAnalysisCheckpoint()`：只要 `cp.finalizing || cp.finalSaved` 一律 skip；分析中途取消仍會寫 cancelled，因為那時 `finalizing` 尚未成立。
- 最終保存失敗時仍會把 `finalizing` 復位，取消路徑得以保留既有「取消保留已完成段」行為。

### 測試

新增「情境 F2」：

- 攔截 `IDBObjectStore.put`，在 `analysis_run.status=complete` 的 docs 寫入後，用同一交易持續發出 `get` 保持交易開啟，製造「最終保存交易已開始但尚未返回」。
- 等 `window.__finalPutSeen` 後按清除（`cancelActiveRun`），再釋放交易。
- 斷言交易完成後 `analysis_run` 仍是 `complete`，且三段譯文仍在。

修復前紅燈：記錄被寫成 `status=cancelled`。修復後綠燈。

## F3（中）：續作進度只在最後保存，部分完成後切換／刷新會丟失

### 根因

`resumeAnalysis()` 的 `results` 只在全部段落跑完後才透過 `queueAnalysisSave` + `articleStore.saveAnalysis` 保存一次。續作中途重新載入、切換文章或取消時，已完成的續作段只存在記憶體，重開後必須重跑。

### 修法

在 `features/article/article.js` 新增續作專用的稀疏進度 checkpoint：

- `createResumeProgressCheckpoint()`：捕獲 job、articleId、contentVersion、`articleStore.captureArticleContext()`、`runMeta`、`total`，並以 `checkpointEpoch` 作為回合世代。
- 每段成功／失敗後 `scheduleResumeCheckpoint()`，debounce 1200ms；同一 checkpoint 的寫入由 `chain` 序列化，同一時間最多一個寫入。
- `writeResumeCheckpoint()` 走既有 `queueAnalysisSave(articleId, contentVersion, ...)` → `articleStore.saveAnalysis(..., { ctx, expectContentVersion, silent: true })`。
- 以最新記錄的 `paragraph_analysis` 為基底，只覆蓋本 job `results` 有、且未被其他工作接手的索引；不碰其他段。
- `analysis_run` 以合併後完整段落透過 `analysisRunStats()` 重算 `completed/failed`，狀態寫 `running`；取消 flush 寫 `cancelled`。
- 保存前檢查 `readingActions.articleVersion()` 與記錄內容版本；保存後再檢查一次版本；`ctx` 為 job 啟動時捕獲，帳戶切換後由 store 阻擋。
- 最終保存前先 `await flushResumeCheckpoint()`，再設 `finalizing=true`；最終保存仍為非 silent 的 `complete/partial`。
- `cancelAnalysisJob()`／`cancelAnalysisJobs()` 透過 `job.progressCheckpoint` 呼叫 `cancelAnalysisJobProgress()`，取消／切換時 best-effort flush 已完成的續作段。
- 最終保存成功設 `finalSaved=true`，後續取消與排隊 checkpoint 不得覆蓋。
- 最終保存失敗時復位 `finalizing/finalStatus`，保留既有 running/cancelled 進度。

### 測試

擴充「情境 F3」：

- 10 段先前完成 5 段；續作時只延遲最後一段，讓前 4 個續作段完成。
- 等待續作進度 checkpoint 落盤：`completed=9`、index 5～8 有新結果、index 9 仍為 `null`。
- 按清除取消：斷言 flush 後 `status=cancelled`、`completed=9`、4 段新結果仍在。
- 重新載入：4 段新結果仍在、`completed=9`、banner 顯示 9/10。
- 再次續作：只送出最後一段請求，完成後 `status=complete`、`completed=10`，已完成段不重做。

修復前紅燈：進度只到最終保存，沒有 9/10 checkpoint，重新載入沒有續作入口。修復後全綠（含取消 flush）。

## F4（中）：checkpoint 持久化失敗仍在記憶體替換記錄

### 根因

`modules/article-store.js` `saveAnalysis()`：

```js
const persisted = await persistDocWithOp(next, 'update', ...);
...
replaceRecord(next);
if (!persisted.ok) return { ok: false, error: persisted.error, record: next };
```

`replaceRecord(next)` 在 `persisted.ok` 判斷之前。checkpoint 寫入失敗時，記憶體記錄仍被換成「已含 5 段結果」的版本；切走再打開會看到「已保存 5/10 段」的續作 banner，但磁碟其實沒有。

### 修法

- 只有 `persisted.ok === true` 才 `replaceRecord(next)`。
- 失敗回傳 `{ ok: false, error, record }`；`record` 保留本次嘗試內容供呼叫端除錯／重試，但不進入 store 記憶體。
- `saveArticle()` 行為未改（除非測試證明必要；本次未證明需要改）。

### 測試

新增「情境 F4」：

- 強制 running／cancelled 且有完成段落的 docs 寫入持續 abort（checkpoint 與取消 flush 都失敗）。
- 完成 5 段後：
  - 記憶體記錄仍為 0 段、`analysis_run.completed=0`。
  - 先切到別篇再切回：不得出現「已保存 5/10」banner，記錄仍 0/10。
  - 重新載入：仍 0/10、5 段譯文不在記錄中、不得顯示 5/10 banner。
- checkpoint 失敗提示在切換前仍可見。

紅燈證據：為確認斷言真的能抓到舊行為，暫時把 `saveAnalysis()` 還原成「先 `replaceRecord` 再檢查 `persisted.ok`」單獨跑 F4，得到 5 項失敗，包含：

```text
FAIL F4 切回後不得出現已保存 5/10 的續作 banner
  {"visible":true,"status":"已保存 5/10 段",...}
FAIL F4 切回後記錄仍是 0/10（不是 5/10）
  {"status":"cancelled","completed":5,...}
```

還原修復版後 F4 全綠。

## 殘留風險

1. **非佇列寫入者的競態**：續作 checkpoint 以「讀最新記錄 → 合併 → 寫回」保存；單詞／句子詳解等直接呼叫 `saveAnalysis()` 的流程不經過 `queueAnalysisSave`。若剛好交錯，理論上仍可能覆蓋同一次讀取之後才寫入的頂層詳解。此競態與主分析 checkpoint 相同，屬既有架構風險，本次未擴大處理範圍。
2. **帳戶切換時的 best-effort**：續作 checkpoint 使用啟動時捕獲的 `ctx`；換帳戶後 `saveAnalysis()` 會以 stale context 擋下，因此最後幾段進度可能不落盤。這是刻意以「不寫到新帳戶」優先。
3. **最終保存期間取消**：F2 的保護會讓取消在 `finalizing` 期間不寫 cancelled，也不顯示「取消保留已完成段」提示；結果以最終保存的 `complete/partial` 為準。
4. **F4 不再樂觀更新記憶體**：`saveAnalysis()` 失敗後不再把未落盤結果放入記憶體。若有其他呼叫端依賴失敗後的記憶體記錄，需改用回傳的 `record`；本次指定回歸與額外 import 測試均未發現依賴。
5. **續作最終保存失敗**：會復位 `finalizing` 並保留先前的 running／cancelled 進度 checkpoint；不會自動產生 `complete`，需使用者重試或續作。
6. **i18n 稽核既有輸出**：`audit-i18n.mjs` 仍列出專案既有的未引用鍵與 `phonetic-chart` 硬寫死中文；本次未新增鍵，亦未修改該範圍。
