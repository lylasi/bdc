## 二、測試方式（真元件，不鏡像實作）

### 1. `tests/extension-workspace-client-deepseek.test.mjs`（前端待傳 client）

受測主體是**真的** `shared/workspace-client.mjs`，只注入三種 adapter（交辦允許的注入點）：

1. **storage**：模擬 `chrome.storage.local`——JSON 往返、**回傳時把頂層與巢狀物件鍵重排**（重現先前修正過的 canonical 比較場景）、可阻塞單一 `get`/`set`/`remove`（製造真實 await 時間窗）、可注入失敗。
2. **session**：以 `generation + token + userId + endpoint` 四項比對，語意同 `sync-cloudflare.js` 的 `captureAuthSession` / `isAuthSessionCurrent`。（真實模組會連帶載入 `ai-config.js` 等私有檔，本輪不得讀取，故以同語意 adapter 取代。）
3. **request**：真的呼叫 `cloudflare-worker/src/worker.js`，接 `node:sqlite` + `selfhost/d1-adapter.js` + `cloudflare-worker/schema.sql`；和 `apiRequest` 一樣「**以目前設定的 endpoint 發送、token 取自呼叫端捕捉的 session**」，所以「舊 token 送到新 endpoint」是可觀測的（兩個 endpoint 各自一套資料庫與 token）。可模擬「伺服器已套用但回應遺失」與「伺服器回畸形回執」。

除 AI 外，client、Worker 路由、`page-links`、`capture-books`、`articles`、SQLite 全是產品程式碼；SQL 只用於「事前 fixture」與「事後事實核對」。

### 2. `tests/extension-inline-security-deepseek.cjs`（真 MV3 邊界）

真 Chromium 載入 `extension/`，真 Worker + SQLite（`tests/helpers/extension-mv3.cjs`），**只有 AI transport 是 mock**。網頁端使用嚴格 CSP 頁面（`default-src 'self'; frame-src 'none'; script-src 'none'`）。「回應遺失」用 Playwright route 先 `route.fetch()` 讓伺服器真的套用、再回 503，等同「雲端已寫入但用戶端看到失敗」。

## 四、確定缺陷

### F1（嚴重度：中／P2）有待傳工作時，重開面板後的預覽沒有鎖定，使用者的編輯會被「沿用」吞掉

- 測試：`tests/extension-inline-security-deepseek.cjs` → `重開面板後，仍有待傳時預覽是否鎖定（需求要求鎖定）`（失敗）
- 具體可重現步驟（真 MV3、真 Worker/SQLite，AI 為 mock）：
  1. 面板連上帳戶 → 對本頁按「AI 提取本頁文章」→ 修改正文 → 勾「保存前同時逐段 AI 分析」→ 按「儲存到文章詳解」。
  2. 讓 `POST /articles` 的回應失敗（測試用 route 先 `fetch` 讓 Worker 真的建立文章，再回 503；實機等同斷線／Worker 5xx）。此時介面出現「本機待傳（1）」，輸入框與分析勾選**已被鎖定**（正確）。
  3. 重新整理／重開面板（同時擋住 `POST /vocabulary/page-link`，讓自動重試失敗）→ 待傳仍在清單。
  4. 再按「AI 提取本頁文章」→ 標題、正文、逐段分析、「儲存到文章詳解」**全部可用**；在正文輸入時沒有任何提示。
  5. 改寫正文再儲存 → 用戶端只發 `GET /vocabulary/books?sourceUrl=…` 與 `POST /vocabulary/page-link`，回執 `reused:true`，介面顯示「這篇網頁已有文章，已沿用原記錄並保留原內容。」；**雲端文章仍是第一次的正文，第二次編輯的內容沒有送出**。
- 實測輸出（artifact `results.json`）：`{"titleDisabled":false,"bodyDisabled":false,"analyzeDisabled":false,"saveDisabled":false,"pendingItems":1}`。同一輪也驗證 `第二次保存沿用既有文章`、`第二次保存沒有多建一篇文章`、`沿用時介面有提示` 三項成立——所以不是資料被覆蓋，而是**新編輯被靜默丟棄**。
- 根因（對照 `extension/workspace-ui.js` @ `b089d232`）：
  - `:35` `for (const input of [articleTitle, articleBody, articleAnalyze]) input.disabled = busy || !!currentJob;` —— 只看記憶體中的 `currentJob`；`:51` `showPending()` 讀到的 storage 待傳**沒有寫回 state**，重開面板後 `currentJob` 恆為 `null`。
  - `:183` 的 `pagePendingLocked` 提示只在 `currentJob` 存在時觸發，而該狀態下輸入框已被 `disabled`，不會產生 `input` 事件 → 提示實際不可達（MV3 `現況：有待傳時修改預覽沒有任何提示` 已斷言）。
  - `shared/workspace-client.mjs` 的 `send()` 對「同網址已有文章」一律回 `reused:true` 且不送 payload，第二次儲存沒有任何落庫路徑。
- 建議修法（任一）：
  1. `showPending()`/`syncWorkspace()` 把「本頁文章（比對 `payload.sourceUrl` 與目前 source）的待傳 job」存進 state，`render()` 以它鎖定輸入與儲存（與 `currentJob` 同等對待）。
  2. 或在 `saveArticle()` 發現同網址已有待傳時，先提示「請先重試或取消該筆待傳」，不建立新 job。
  3. 若產品要支援「同網址再次保存＝更新既有文章」，`send()` 應改走 `PUT /articles/:id`（帶 `expectedRevision`）；否則至少要在儲存前明確告知「本次內容不會保存」。

## 五、疑點（已在測試中斷言「現況」，需產品決策，不算失敗）

1. **重試佇列會被「沒有 HTTP status」的失敗整條卡住（建議：低／P3）** — `C4`。`retry()`（`shared/workspace-client.mjs:100` 附近）在 `!error.status` 時 `break`；`capture_invalid_record`、`capture_invalid_response`、`capture_invalid_input` 都沒有 status。實測：一筆「結構合法但 `sourceUrl` 非法」的舊版／損壞待傳排在最前面時，後面健康的建書待傳完全不會送出，必須手動取消那一筆。`enqueue` 在 14:13:55 之後已會先驗證，所以這種記錄只能來自舊版或外部竄改；但舊版升級上來時仍會遇到。有 status 的失敗（404/409）則會繼續（`C3` 通過）。
2. **待傳清單與重試次序不保證先入先出（建議：低／P3）** — `E3`。`pending()` 沒有像 `capture-client.mjs` 那樣依 `createdAt` 排序，次序等於 `chrome.storage.local` 的鍵序（測試中反轉鍵序即可看到倒序）。目前詞書與文章工作彼此獨立，影響有限；若要「先建書再存文章」的語意保證，建議補排序。
3. **同一網址再存一次＝沿用舊文章（文件化行為，建議：低／P3）** — `D5`、MV3。新 requestId、新內容都會被丟棄，只回 `reused:true` 並顯示「保留原內容」。這是目前文案已說明的設計，但與 F1 疊加時會讓使用者以為存了。
4. **`page-link` 回執的 `articleId` 未與先前的 `GET ?sourceUrl` 值比對（建議：極低／P4）** — `books.articleId` 分支用 `GET` 的值當回執，只驗證 page-link 的 `articleId` 格式。兩者都走同一個 `findPageArticle`，實務風險極低，但並行時理論上可能不一致，建議加一行相等檢查。
5. **`cancel()` 需要已登入（建議：極低／P4）** — `cancel()` 內 `assertSession`，登出後無法從 UI 清掉本機待傳；切換 endpoint 後，舊 endpoint 的待傳在 UI 完全看不到也無法清理（只能靠 storage 手動清）。目前不影響資料正確性。
6. **封面已修正的項目（供對照）** — 「登出／切帳後輸入框殘留前一帳戶文章」在 14:13:55 版本已清空，本輪已改為斷言「已清空」；「同網址文章被刪後重建卡住」在 14:13:55 版本已加入槽位重配置，`D10` 驗證通過。

## 六、已驗證為正確的重點（可作為回歸依據）

- **先落盤後發送**：`enqueue` 只寫 storage，第一個網路請求一定在落盤之後；`storage.set` 失敗回 `capture_storage_failed` 且完全不發請求（`A1`、`A3`）。
- **canonical 比較**：Chrome 重排頂層與巢狀鍵後，重送仍視為同一筆 payload 並成功（`A2`）；落盤後被竄改的 payload 一律 `capture_invalid_record` 且不送出（`A4`）。
- **入列驗證**：非法 `sourceUrl`（含 `javascript:`）一律 `capture_invalid_input`、空正文 `invalid_article`（status 422），都不落盤、不發請求（`D6`）。
- **帳戶／endpoint 隔離**：`pending()` 只看得到自己 scope；切帳戶或切 endpoint 後重送舊工作一律 `stale_session`，且**沒有任何請求**離開（`B1`–`B3`）。
- **await 時間窗**：`storage.get`（pending／send）被阻塞期間切帳戶 → 不寫入、不發送（`B4`、`B5`）；`GET ?sourceUrl` 之後、`pageStableId` 的 hash 等待中切帳戶 → 不會 `POST /articles`、不會把新帳戶 token 用在舊工作上（`B6`）。
- **回執驗證**：requestId 不符、bookId 非法、401、page-link articleId 非法都不清 pending（`C5`–`C7`、`D7`）；只有有效回執才清（`C8`）。
- **畸形／外帳戶待傳**：標成 `invalid`、payload 一律 `{}`（不外洩外來內容）、可單獨取消、健康項照常送出（`C1`）；上限 20 筆含損壞項（`C2`）。
- **文章路徑**：首次保存的請求序列固定為 `GET /vocabulary/books?sourceUrl` → `POST /articles` → `POST /vocabulary/page-link`，頁書被關聯（`D1`）；既有文章時**不再** `POST /articles`，由 page-link 補關聯（`D2`）；本次建立成功但 link 失敗（500）→ pending 保留，重試時補關聯且文章仍只有一篇（`D3`）；回應遺失後重試不重複建立、不覆蓋主站已編輯的內容（`D4`）；`#comments` 片段不另建文章、不同網址建不同文章（`D8`、`D9`）；文章被刪後重建不卡墓碑（`D10`）；舊後端 404 會轉成可辨識的 `capture_server_update_required`（`D11`）。
- **取消**：只刪本機那一筆，雲端文章／詞書與關聯都保留（`E2`、MV3 UI 取消）。
- **真 MV3 邊界**：偽造／空白／缺 ticket、同 tab 重播、跨 tab 重播、關閉後重播、換頁後重播、頂層分頁帶真 ticket 進 `embedded=1`——全部顯示「無法在此頁面開啟查詞」，**不初始化帳戶、不呼叫 AI、不寫入任何資料**；同 tab 重播不會頂替原有浮窗。
- **偽造訊息**：把 `BDC_OPEN_INLINE`／`BDC_READ_PAGE`／`BDC_INLINE_CONTEXT`／`BDC_CLOSE_INLINE`／`BDC_INLINE_LABELS`／`BDC_ENABLE_INLINE` 送到 `window` 與每個子框，再補合成 `mouseup`/`click` 事件——浮窗仍存活、結果不變、沒有新浮窗、AI 呼叫數不變、雲端沒有新寫入；網頁仍看不到浮窗（closed shadow root），也列不出浮窗網址。
- **可信／不可信上下文**：擴充頁面可讀 `chrome.storage`；內容腳本世界（isolated world）讀 `chrome.storage` 被拒（`TRUSTED_CONTEXTS` 生效）；網頁世界沒有 `chrome.runtime`，localStorage／sessionStorage 沒有 token 或 ticket。
