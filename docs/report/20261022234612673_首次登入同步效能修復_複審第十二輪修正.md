## 二、R1（High）`applied:false` 後不得再 `markOpFailed`

### 根因

`pushRestoreUpdate()` 在 `advanceOperationBase()` 回 `applied:false` 時仍呼叫
`store.markOpFailed(articleId, 'revision_base_superseded', { ctx })`
（舊 `modules/article-sync.js:321-326`）。

- `applied:false` 的語意是「這筆 outbox 操作已被新的本機修改取代、已被另一個分頁完成或移除、或代際已不符」，`article-store.js:advanceOperationBase()` 已經在原狀完全不動的情況下回報。
- `markOpFailed()`（`modules/article-store.js:3036`）會用**本分頁記憶體**建立
  `{ ...record, dirty:true, pending:true }`，再走 `persistDocWithMeta()`（`:2969`）。
- `persistDocWithMeta()` 在後備／IndexedDB 兩條路徑都只用
  `adoptStoredGeneration()`（`:785`）合併**代際**；代際相同時它不會採用持久化文件的
  `revision`。因此同代際下會發生：
  - (a) 持久化文件被寫成 `dirty:true, pending:true`，但 outbox 已無對應操作 →
    內部 outbox 讀取（`:1044`、`:1052`）／`listPending()`（`:1638`）讀不到任何操作，下載又跳過 dirty 文件
    → 永久 pending 但永不上傳的孤兒狀態；
  - (b) 持久化文件較新的 `revision`（另一個分頁已完成 PUT）被記憶體裡的舊 revision 覆蓋
    → 版本倒退，之後的 PUT 必定 409 假衝突。
- 唯一可接受的做法是：**不改寫任何持久化狀態**，把「已被取代／延後」明確回報給
  `pushOutbox()`，下一輪由新的操作自然接手。

### 修正

`modules/article-sync.js:330-338`

```js
if (advanced.applied !== true) {
    // 等待期間這筆操作已被新的本機修改取代，或已被另一個分頁完成／移除：
    // 不能用舊正文繼續 PUT，也**不可** markOpFailed ...
    // 原狀完全不動（文件、outbox 都不寫），只回報「已被取代」。
    return { ok: false, error: 'revision_base_superseded', superseded: true };
}
```

`modules/article-sync.js:553-563`（`pushOutbox`）

```js
if (result.ok) pushed += 1;
else if (result.conflict) conflicts += 1;
else if (result.superseded) {
    // 這筆操作已被新的本機修改取代／別的分頁完成：不是使用者衝突，
    // 也不該重試同一筆（outbox 已不是它了），不計失敗、不動任何資料。
} else { failed += 1; ... }
```

確認事項：

1. **不記成使用者衝突**：`superseded` 分支在 `conflict` 之後、`failed` 之前被攔下，
   不會觸及 `markOpFailed(..., { conflict })`，`getConflicts()` 維持 0。
2. **不會清 op**：`confirmReceipt()`／`markOpDone()` 完全沒有被呼叫。
3. **下一輪由新操作接手**：outbox 沒有被本輪改動；若別的分頁已清空 outbox，下一輪
   `listPending()` 自然回空集合（測試斷言第二輪 `pushed === 0 && failed === 0`）。
4. **記憶體不寫回持久化**：superseded 分支不呼叫任何 store 寫入 API；需要新狀態時
   只能由 `reloadScope()`／重新讀取持久化資料取得（測試以此驗證）。

### 測試設計（`tests/article-rebuild-generation.test.mjs`，「跨分頁：A 的 restore 回應遲到…」）

1. `seedRestoreUpdate()` 建立「遠端墓碑 rev4 + 本機 outbox `restore_update`（正文 a-v7）」。
2. 在 `tests/helpers/article-sync-server.mjs` 的 `/restore` 成功路徑新增
   `state.hooks.afterRestore`，讓 A 的 restore **已在伺服器提交、回應暫扣**。
3. A 的 `syncArticles()` 卡在等待；此時 B（重新載入後看到同一筆 outbox）完成
   restore（冪等）+ PUT → 遠端 rev6／body `a-v7`，並清掉 outbox。
4. 放行 A 的回應 → `advanceOperationBase()` 因 outbox 已消失回 `applied:false`。
5. 斷言：持久化文件 `revision === 6`、`body === 'a-v7'`、`dirty === false`、
   `pending === false`、`generation === 1`、outbox 為 `null`、摘要 revision 6、
   `conflicts === 0`、本輪 `pushed.failed === 0`；`reloadScope()` 後記憶體為 clean rev6；
   下一輪 `pushed === 0 && failed === 0 && conflicts === 0`。

## 三、R2（High）所有後備桶「讀改寫」入口都要用嚴格讀取

### 根因

`fallbackRead()`（`modules/article-store.js:282`）為了讓「第一次啟動、尚無資料」的
一般讀取可用，會把**任何例外或解析失敗都當成空桶** `{ docs:[], outbox:[], state:{} }`。
只要「讀桶 → 改 → 寫回」的入口誤用它，一次 `SecurityError`／損壞 JSON／非物件桶就會
被寫成空桶，其他文件與待同步操作全部消失，而該輪還可能被回報成成功。

`fallbackReadStrict()`（`:299`）已存在並能區分「合法空桶（`null`／`''`）」與
「`storage_read_failed`／`storage_corrupt`」，但當時只有回執、state 寫入、
`markOpFailed`（`persistDocWithMeta`）、`advanceOperationBase` 採用。

### 修正（全部站點）

| 用途 | 函式 | 位置（修正後） |
| --- | --- | --- |
| 文件寫入 + outbox 合併 | `fallbackDocWrite()` | `:468`（嚴格讀取 `:471-476`） |
| `persistDoc()` 後備分支 | `persistDoc()` | `:494`（`:500-505`） |
| 單篇移除 | `fallbackRemoveDoc()` | `:567`（`:571-576`） |
| 遠端墓碑 | `fallbackApplyTombstones()` | `:603`（`:605-607`） |
| 文件 + outbox 交易 | `persistDocWithOp()` | `:850`（`:862-867`） |
| 寫／移除 outbox 操作（含 `idb_unavailable` 分支） | `writeOutboxOp()` | `:1058`（`:1063`、`:1074`） |
| 同上 | `removeOutboxOp()` | `:1084`（`:1088`、`:1098`） |
| import 送出快照 | `recordImportSubmission()` | `:1142`（`:1154-1156`） |
| 清除 import 快照 | `clearImportSnapshots()` | `:1215`（`:1231-1233`） |
| 刪除建立失敗文章（撤掉 create） | `deleteArticle()` → `applyFallback()` | `:1835`（`:1837-1839`） |
| 草稿儲存（含 `idb_unavailable`） | `saveDraft()` | `:1976`（`:1991`、`:2001`） |

保留寬鬆讀取（純讀取，不寫回）：內部 outbox 讀取（`:1044`、`:1052`）與 `listPending`（`:1638`）、
`loadAllRecords`（`:1398`）、`loadSummaries`（`:1417`）、`readState`（`:1429`）、
`ensureArticleLoaded`（`:1545`）、`readDraft`（`:2013`）。

共同語意：

1. **不得把「讀不到」當成空桶覆寫**：每個入口在嚴格讀取失敗時直接
   `{ ok:false, error:'storage_read_failed'|'storage_corrupt' }` 且不寫入。
2. **`null`／`''` 仍是合法空桶**：`fallbackReadStrict()` 的既有行為未改，首次啟動
   仍可正常建立資料（既有測試 `markOpDone`／`markOpsDone` 的空桶案例持續通過）。
3. 既有嚴格語意沒有回退：`markOpFailed` → `persistDocWithMeta`（`:2976`）、
   `fallbackWriteState`（`:989`）、`persistMeta`、`fallbackApplyReceipts`（`:2646`）、
   `advanceOperationBase`（`:2099`）皆維持原本的嚴格讀取。

## 四、R3（Medium）介面不得吞掉文章同步失敗

### 根因

- `features/sync/sync.js:runArticleSyncPhase()`（舊 `:314-327`）永遠 `return { ok:true, info }`；
  `syncArticles()` 的失敗是以 `{ ok:false, error }` 回傳、**不拋出**，所以只有例外才會
  走 `ok:false`。
- 因此手動路徑 `handleSync()` 的 `else if (!articlePhase.ok)`（舊 `:400`）是死碼，
  自動路徑 `doAutoSync()`（舊 `:2136`）完全沒檢查 → 文章同步失敗時仍顯示
  `sync.syncDone`／彈出「同步完成」成功提示。

### 修正

1. **包裝層**（`features/sync/sync.js:315-330`）

```js
const info = await syncArticles();
if (info && info.ok === false) {
    updateStatus(t('sync.articleSyncFailed'));
    return { ok: false, error: (info && info.error) || 'article_sync_failed', info };
}
```

   `stale_session`／`unauthorized` 仍維持 `throw`（catch 區塊未改）。

2. **完成狀態抽成可測純函式**：新增 `features/sync/sync-status.js`
   `resolveSyncCompletion({ manual, restoredFromRemote, articleOk, readingUnsupported })`，
   回傳 `{ statusKey, toastKey, toastLevel, toastMs }`；`articleOk === true` 才可能回
   `sync.syncDone`。手動與自動同步共用同一套判斷：
   - 手動：`features/sync/sync.js:404-413`（失敗 → `sync.articleSyncFailed` 狀態 +
     error 提示；成功 → `sync.syncDone` 狀態 + success 提示）。
   - 自動：`features/sync/sync.js:2153-2162`（失敗 → 狀態列
     `sync.articleSyncFailed`，**不再**顯示 `sync.syncDone`、不彈成功提示）。
3. **文案**：沿用既有鍵 `sync.articleSyncFailed`／`sync.syncDone`／
   `sync.readingServerUpdateRequired`／`sync.restoredEmpty`／`sync.restoredAutomatic`
   （`locales/zh-CN.js:1280`、`locales/zh-HK.js:1280`），**未新增任何鍵**，因此鍵集與
   插值參數完全一致（`node tests/audit-i18n.mjs` 回報鍵數 2022/2022、差異 0、插值不一致 0）。

### 測試設計（新增 `tests/sync-status.test.mjs`，node:test）

覆蓋方式（無需瀏覽器）：把判斷抽成零依賴模組後，用 `node:test` 直接列舉覆蓋，
再用原始碼接線斷言守住 `sync.js` 的包裝層。

7. 接線斷言（讀取 `features/sync/sync.js` 原始碼）：
   - `runArticleSyncPhase` 內含 `info.ok === false` 與 `article_sync_failed`、仍保留
     `stale_session`；
   - `articleOk: articlePhase.ok === true` 恰好出現 2 次（手動 + 自動）；
   - `t('sync.syncDone')` 出現 0 次（不再有寫死的完成分支）；
   - `resolveSyncCompletion(` 恰好 2 次呼叫。

## 八、剩餘風險

1. **R1 之後的分頁記憶體短暫不一致（低）**：superseded 分頁的記憶體仍保留
   `dirty/pending` 與舊 revision，直到 `reloadScope()` 或下一次保存
   （`mergeStoredRevision()` 會以 `max(記憶體, 持久化)` 取 revision，不會倒退）。
   本輪刻意**不**由記憶體回寫持久化（那正是 R1 的病灶），也未強制重載整份 scope 以免
   干擾使用者正在編輯的畫面；UI 的 pending 標記可能短暫殘留，屬顯示層問題，無資料風險。
2. **`syncArticles()` 的 `pushed.failed` 語意（低）**：「被取代」不再計入 `failed`，
   因此 `sync.articleSyncPending`（`failed || conflicts`）不會因它亮起；這是刻意的
   （被取代不是待處理狀態）。若日後要觀測此狀態，需另加計數欄位。
3. **`reconcileFullList` 回傳形狀變更（低）**：由 `string[]` 改為
   `{ ok, removed, error }`。已同步更新專案內唯一呼叫端（`pullFull`）與既有的兩處測試
   呼叫端；若有第三方腳本直接呼叫此 API 需一併調整。
4. **R2 嚴格化後的錯誤可視性（低）**：後備桶讀取失敗現在會讓整輪同步
   `ok:false`（而不是靜默成功），使用者會看到「文章同步失敗」；這是預期行為，
   但若儲存長期不可用（例如 Safari 私密模式配額為 0），會每輪重試失敗並留下錯誤訊息。
5. **R3 只用 node 覆蓋（中低）**：`features/sync/sync.js` 依賴 DOM／Supabase 用戶端，
   無法在 node 直接 import，因此改用「純函式模組測試 + 原始碼接線斷言」。真實瀏覽器
   的狀態列文字（`updateStatus`）與 toast 尚未以 Playwright 驗證；建議在
   `tests/audit-flows.cjs` 後續補一條「文章同步失敗時狀態列不是同步完成」的 E2E。
6. **`tests/phonetics.test.mjs:47`** 仍為既有失敗（`node:vm` 無法執行含 `import` 的
   字串），與本輪無關，未處理。
