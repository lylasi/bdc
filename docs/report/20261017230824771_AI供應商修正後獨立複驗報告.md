## 結論

上次 F1–F6 的具體重現案例已通過，管理員簡化新增與模型白名單流程亦通過雙語功能測試。惟補充檢查仍確認 **2 項憑證資料處理問題及 1 項部署檢查問題**，尚不宜視為整個方案驗收完成。

## R1／P1：移除雲端副本會清空本機 Key

- 位置：`modules/ai-credential-sync.js:538`；相同清空行為亦見 `:525` 的 delete-not-found 和 `:438` 的 confirm-pending 分支。
- 原方案第 9 節明確規定：「移除雲端副本，保留此裝置」，成功後本機轉 local-only，不能被自己的刪除標記清掉。
- 重現：新增並成功同步一個供應商至 version 1 → 執行 `removeCloudKey()` → 完成同步。
- 實際：`cloudDeleted=true, localHasKey=false, mode=local-only`。正常 DELETE 成功就會遺失本機 Key，並非只有網路競態才發生。原本可在本機使用的供應商因此失效。
- 原因：成功刪除雲端憑證時，無條件執行 `credential.apiKey = ''`，未區分「刪除供應商／本機憑證」與「只移除雲端副本」。
- 修正要求：保存並遵守此次操作的本機保留意圖；涵蓋正常成功、404、回應遺失後的 mutation 確認及後續 tombstone。不要影響真正刪除供應商或採用遠端刪除的語義。

## R2／P1：手動採用雲端衝突版本會覆蓋較新的 Key，亦未檢查工作階段

- 位置：`modules/ai-credential-sync.js:949` 至寫回入口 `:955`，函式 `resolveCredentialConflict()`。
- 原方案第 8 節要求每個異步工作在回應及寫入前檢查 endpoint、userId、sessionGeneration；新修正的一般同步亦以憑證指紋避免覆蓋使用者最新編輯。
- 重現 A：供應商處於衝突 → 點「使用雲端版本」並延遲 GET → 使用者保存新的本機 Key → 放行舊下載。
- 實際 A：新 Key 被舊雲端 Key 覆蓋，新的 pending 操作被清除。
- 重現 B：同樣延遲衝突下載 → 明確登出 → 重新登入同一帳戶並保存該供應商的新 Key → 放行先前登入工作階段的下載。
- 實際 B：先前工作階段的 Key 覆蓋重新登入後的新 Key；新的 pending 亦消失。此案例已啟用 `initAICredentialSync()`，不是因為測試漏掉登出清理事件。
- 原因：函式在 await 後直接對捕獲的 scope 寫入，只檢查憑證列仍存在；未校驗工作階段、憑證指紋、當前衝突版本或操作是否已被新的使用者修改取代。
- 修正要求：捕獲並在下載完成後檢查會話及操作基準，再有條件提交；過期結果不能清除新 pending、改寫新 Key 或重建舊 scope。採用雲端版本亦應按原方案核對 binding。

## R3／P2：部署指南的線上設定檢查命令會誤報通過

- 位置：`docs/release/20261017174843744_AI供應商設定同步部署與遷移指南.md:149`；`scripts/check-ai-static-config.mjs:93`、`:119`。
- 指南命令把 curl 的回應接到 `node scripts/check-ai-static-config.mjs --dir /dev/stdin`。
- 重現：以不含真實秘密的 `export const API_KEY = "test-placeholder-only";` 作 stdin，執行相同檢查參數。
- 實際：`exitCode=0, ok=true, findings=[]`，沒有檢查輸入內容。
- 原因：`--dir` 只支援目錄；對 `/dev/stdin` 呼叫 readdir 失敗後靜默 return，最後把「沒有掃到檔案」當成「沒有問題」。
- 修正要求：指南提供實際可執行的命令，例如先下載至暫存目錄內的 `ai-config.js` 再檢查該目錄，或實作明確 stdin 模式。工具應拒絕非目錄、不可讀目標及掃描失敗，避免以成功碼掩蓋未檢查。命令還需處理 HTTP 失敗，不能把錯誤頁當作設定檢查通過。
