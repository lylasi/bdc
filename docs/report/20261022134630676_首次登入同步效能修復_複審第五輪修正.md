## 摘要

Codex 第五輪複審提出的 4 項 Medium 全部完成，且每一項都做了「暫時還原錯誤實作 → 新測試必須失敗」的反向驗證（見各節）：

1. **相同內容、不同 mutation ID 持續 deferred**：`snapshotNeedsVerification()` 現在只要快照的 mutation ID 與目前操作不同就先核對，不再單憑內容相同跳過。
2. **第三輪等待期間新增刪除會漏標 deferred 並提前 final**：建立匯入清單時改成「先檢查所有操作是否仍有未核對快照，再按操作類型分流」，delete 不再在檢查前被略過。
3. **舊 missing 結果會誤刪另一分頁的新快照**：missing 結果改為攜帶「查詢當時」的快照身分（mutation ID + `submittedAt`），清除時只用該身分；快照已被替換時儲存層回報 deferred，本輪延後重新核對。
4. **revision 取最大值破壞遠端 404 後的重建**：新增明確的「重建重設」路徑，在文章文件的同一個交易內核對目前操作後，原子重設文章／摘要／outbox 的版本基準為 0；並以 `supersededMutations` 保護舊回執不再把版本推回。

## 逐項修改

### 1. Medium — 相同內容、不同 mutation ID 會持續 deferred

**問題**
匯入已提交但回應遺失後，使用者再保存一次完全相同內容（或內容 A→B→A）會產生新的 mutation ID；`snapshotNeedsVerification()` 只比內容就跳過核對，寫入快照時卻被 `importSnapshotMatches()`（要求 mutation ID 相等）拒絕。結果每一輪都 `deferred=true`、沒有 batch 核對、outbox 保留、gate 未清，且 `syncArticles()` 提前返回，其他操作也無法推送。

**根因**
「快照是否需要核對」用內容判斷，但「快照是否可被替換」用身分（mutation ID）判斷。兩者不一致時，preflight 不會清掉舊快照，`recordImportSubmission()` 永遠回報 `deferred`，形成永久延後。

**修改**
- `modules/article-sync.js:446`：`snapshotNeedsVerification()` 在 delete 之後新增 `snapshot.clientMutationId !== op.clientMutationId → true`。內容相同但身分不同時一律先核對舊快照；核對成功後由 `markOpsDone()`／`rebasePendingOutbox()` 清掉舊快照、把 revision 推進到伺服器版本，操作自然轉成逐篇 update。
- 既有保證不變：mutation ID 與內容都相同時仍不核對（重送只會被伺服器 skip）；delete 一律核對。

**驗收測試**（`tests/article-import-progress.test.mjs`）
- `:828`「回應遺失後保存相同內容（新 mutation）」：兩篇回應遺失，其中一篇同值保存、另一篇真的改內容；斷言本輪 `deferred` 為 undefined、outbox 清空、gate 關閉、`createCalls=0`、文章數不變、`importPayloads` 仍只有原本那 1 次匯入、兩篇 revision 與遠端一致。
- `:875`「內容 A→B→A 且快照停在 A」：斷言只走一次 update、不重新匯入、`articles.size=1`、遠端 revision 2。

**反向驗證**
暫時移除 `if (snapshot.clientMutationId !== op.clientMutationId) return true;`（改回只比內容）→ 兩個測試都失敗：
`✖ 回應遺失後保存相同內容（新 mutation）…`、`✖ 內容 A→B→A 且快照停在 A…`；失敗原因為 `deferred` 仍為 true、outbox 未清。

### 2. Medium — 第三輪等待期間新增刪除，會漏標 deferred 並提前 final

**問題**
四篇已提交但回應遺失；核對 A 時修改 B、核對 B 時修改 C、核對 C 時刪除 D。三輪 preflight 耗盡後，D 的 delete 操作仍帶著未核對快照，但建立匯入清單的迴圈先把非 create／update 的操作 `continue` 掉，因此 `deferred` 是空的 → 送出 `final`、清掉 gate，接著逐篇送出 `expectedRevision: 0` 的 DELETE（真實 Worker 回 400 `expected_revision_required`，遠端文章仍存在）。

**根因**
「未核對快照」的檢查放在「操作類型分流」之後，delete 永遠走不到檢查。

**修改**
- `modules/article-sync.js:739`：`pushLegacyMigration()` 建立匯入清單時改成先檢查 `snapshotNeedsVerification(op)`（`:742`），任何仍有未核對快照的操作（含 delete）都進入 `deferred`；之後才做 create／update 分流。`finalize` 仍只在 `!deferred.length` 時存在，因此本輪不會送 final、不會清 gate，`syncArticles()` 也會提前返回而不推送 outbox。
- 下一輪 preflight 會以 delete 的快照核對伺服器版本，`markOpsDone()` 把 delete 的 `expectedRevision` 推進到伺服器 revision，再以正確 revision 完成刪除。

**驗收測試**
- `tests/article-import-progress.test.mjs:912`「三輪核對期間修改 B／修改 C／刪除 D」：以三次 batch 屏障串起連鎖修改（每輪斷言 batch ids 分別是 `chain-a`、`chain-b`、`chain-c`）。第一輪斷言 `deferred=true`、`legacy.deferred=true`、`finalCalls=0`、`gatePending=true`、`deleteCalls=0`、D 未被刪除、outbox 仍有帶快照且 `expectedRevision=0` 的 delete。第二輪斷言 `finalCalls=1`、gate 關閉、只發 1 次 DELETE 且 `expectedRevision=1`、D 已刪除、文章數仍 4、`createCalls=0`、outbox 清空、A／B／C 最新內容都到遠端。
- 測試 mock 的 DELETE 分支同步補上真實 Worker 語意（`tests/article-import-progress.test.mjs:220`）：`expectedRevision < 1` 回 400 `expected_revision_required`，讓原錯誤能被真實重現。

**反向驗證**
暫時把檢查移回「操作類型分流之後」（即原實作）→ `✖ 三輪核對期間修改 B／修改 C／刪除 D…`，失敗於 `actual: undefined, expected: true`（「未核對的 delete 沒有讓本輪 deferred」）。

### 3. Medium — 舊 missing 結果會誤刪另一分頁的新快照

**問題**
暫扣 S1 的 missing 回應；期間另一分頁清除 S1、提交 S2，本機再修改成 S3。放行舊回應後，清除步驟從「重新讀取的 outbox」取得 mutation ID／`submittedAt`（其實是 S2 的身分），於是 S2 被當成 S1 刪掉；流程再重匯 S3、產生假 `legacy_differs`，最後仍清掉 gate。

**根因**
`verifySubmittedSnapshots()` 的 missing 結果只保存 `articleId`，身分在很久之後才由呼叫端重新讀取；查詢與清除之間 outbox 可能已被另一個分頁換成新快照。

**修改**
- `modules/article-sync.js:531`／`:546`：`verifySubmittedSnapshots()` 的 `missing` 改為 `Map<articleId, { clientMutationId, submittedAt }>`，記下「查詢當時」的快照身分（含失敗提前返回的路徑）。
- `modules/article-sync.js:681`：`pushLegacyMigration()` 合併 preflight 的 missing 時保留該身分。
- `modules/article-sync.js:709`：清除時只用查詢當下的身分建立 `clearImportSnapshots()` 參數，不再讀目前 outbox 的快照。
- `modules/article-store.js`（第四輪已加入的 `clearImportSnapshots()`）：交易內比對 mutation ID（與 `submittedAt`）不符就回報 `deferred`；`pushLegacyMigration()` 收到 `deferred` 立即回報本輪延後、不清 gate、不送 final，下一輪重新核對真正存在的新快照。

**驗收測試**
- `tests/article-import-progress.test.mjs:1003`「舊 missing 回應不得刪掉另一個分頁的新快照」：以 batch 屏障暫扣 missing 回應（mock 在 `:158` 改成「請求當下就決定查詢結果、hook 只延後送達」，與真實 Worker 一致），等待期間清 S1、寫入 S2、提交遠端 B2、本機改成 S3後才放行。斷言第一輪 `deferred=true`、`finalCalls=0`、gate 保留、outbox 快照仍是 S2、遠端仍是 B2、無衝突；第二輪先核對 S2 再推送 S3，斷言無衝突、outbox 清空、gate 關閉、`articles.size=1`、遠端 `v3`／revision 2、沒有重新 import、沒有 DELETE。

**反向驗證**
暫時改回「從重讀的 outbox 取得快照身分」→ `✖ 舊 missing 回應不得刪掉另一個分頁的新快照…`，失敗於 `first.deferred` 為 undefined（S2 被誤刪後走成 import + 假 `legacy_differs`）。

### 4. Medium — revision 取最大值破壞遠端 404 後的重建

**問題**
原文章 revision 3，遠端不存在後更新收到 404；`requeueAsCreate()` 雖然把記憶體 record 設成 revision 0，但 `mergeStoredRevision()` 無條件取 `max(record.revision, storedDoc.revision)`，`createOutboxOp()` 的 `expectedRevision` 也取最大值，於是本機仍是 3。重建（POST）成功時遠端是 revision 1、本機仍是 3，下一次修改送出 `expectedRevision: 3` 收到 409 衝突。

**根因**
「一般保存只能讓 revision 前進」的安全下限被套用到「伺服器確認 404 後重建」這種必須重設基準的路徑，且重設只寫在記憶體、沒有和文章／摘要／outbox 一起原子提交，也沒有在交易內核對目前操作。

**修改**
- `modules/article-store.js:497`：`mergeStoredRevision(record, storedDoc, options)` 新增 `resetRevision`；重建時直接回傳 `revision: 0`，其餘路徑仍取最大值。
- `modules/article-store.js:529`：`persistDocWithOp()` 讀取 `resetRevision`／`resetFromMutationId`；IndexedDB 交易內先核對「目前 outbox 操作仍是呼叫端看到的那一個 mutation」，不是就回報 `{ deferred: true }`（`:565`），是才同時寫入文件、摘要與歸零後的新 outbox 操作；localStorage 後備在同一段無 `await` 的同步區塊做同樣核對。
- `modules/article-store.js:900`：`createOutboxOp()` 在 `resetRevision` 時把 `type` 固定為 `create`、`expectedRevision` 歸零、丟棄舊 `importSnapshot`（伺服器已沒有這篇，該快照不可能再核對為完成），並把被取代的操作 mutation 記到 `supersededMutations`。
- `modules/article-store.js:508`：新增 `ignoresRebuiltReceipt()`。`rebasePendingOutbox()`（`:1862`）、`markOpDone()`（`:1911`）與 `markOpsDone()`（`:2006`）對 `supersededMutations` 內的舊回執不再推進 revision／`updatedAt`，避免重建前那一次更新的回執（例如另一個分頁的延遲回應）把版本推回 3。
- `modules/article-sync.js:301`：`pushOne()` 的 404 分支改為 `store.requeueAsCreate(articleId, ctx, { fromMutationId: mutationId })`，並回報 `requeued`／`deferred`。
- `modules/article-store.js:2140`：`requeueAsCreate()` 改為帶 `resetRevision + resetFromMutationId` 的寫入；只有寫入成功才用持久化後的文件回填記憶體（revision 0），交易內發現操作已被新修改取代時回報 `deferred`，下一輪重新處理。

**驗收測試**
- `tests/article-import-progress.test.mjs:1104`「revision 3 遠端 404：重建後版本基準歸零」：先同步到遠端 revision 3，再刪除遠端文章並本機修改；第一輪斷言本機 revision 0、outbox 是 `create` 且 `expectedRevision=0`；接著模擬重建前更新的遲到回執（`markOpsDone` 帶舊 mutation、revision 3）斷言本機仍為 0；第二輪建立成功斷言本機與遠端都是 revision 1；第三次修改斷言 PUT 以 `expectedRevision 1` 成功（revision 2）、無衝突。
- 既有回執競態測試（同檔 `:245` 的舊回執不覆蓋等待期間的新修改、`:411` 的重複舊回執、`:712` 的儲存／快照交錯、`:78` 的內容指紋）全數仍通過。

**反向驗證**
暫時讓 `mergeStoredRevision()` 恢復無條件取最大值、`createOutboxOp()` 的 `expectedRevision` 也取最大值 → `✖ revision 3 遠端 404…`，失敗於「404 重建後本機仍停在舊 revision」（actual 3 / expected 0）。進一步放寬該斷言後以 debug 版本重跑，觀察到原症狀：重建後本機 3、遠端 1，下一次更新產生 `kind: "revision"`、`remoteRevision: 1` 的 409 衝突，遠端內容停留在 `v4`。

## 仍存風險與限制

1. **跨分頁重複推送 + 極晚的舊回執**：`supersededMutations` 只存在於 outbox 操作上；若重建後的 create 已確認、操作被清除，之後才送達「重建前更新」的回執，仍可能把本機 revision 推回舊值。此情境需要同一操作在兩個分頁同時推送且回應延遲極久，正常 HTTP 不會重送同一回應；未新增跨分頁鎖。
2. **preflight 仍是最多 3 輪**：使用者若在三輪核對期間持續修改不同文章，本輪會回報 `deferred` 並在下一輪重試；不丟資料，但該輪不推送 legacy 變更（刻意維持第四輪的有界策略）。
3. **清除 missing 快照時若身分已消失**：另一個分頁可能剛好已確認／清除同一份快照；此時 `clearImportSnapshots()` 回報 `cleared:0` 且沒有 deferred，本輪會用目前內容走匯入。這是既有行為（沒有可核對的證據），未在本輪擴大處理。
4. **`requeueAsCreate()` 交易內發現操作已被取代**：本輪回報 `deferred` 並視為推送失敗，下一輪會再以新操作收到 404 後重建；不會丟資料，但會多一輪同步。
5. **PostgreSQL 交易語意未重新實測**：本輪未設定 `BDC_TEST_PG_URL`，`articles-quota-postgres.test.mjs` 6 項仍 skip；本輪沒有改動 Worker 的配額路徑。
6. **測試替身語意變更**：`tests/article-import-progress.test.mjs` 的 `/articles/batch` 改為「請求當下決定查詢結果、hook 只延後送達」。這比原本「hook 之後才查詢」更貼近真實 Worker，且既有使用該 hook 的測試（驗證期間只改本機狀態）不受影響；`tests/fake-indexeddb.test.mjs` 未修改。
