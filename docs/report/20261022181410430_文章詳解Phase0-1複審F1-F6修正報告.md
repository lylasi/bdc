## 二、逐項根因、修法與測試

### F1｜P1：不同段落同時重試會丟失其中一段持久化結果

**根因**

- `persistParagraphResult` 先同步讀取目前記錄、複製整份 `paragraph_analysis`，再呼叫 `articleStore.saveAnalysis` 寫入整份結果。
- 兩個不同段落同時重試時，兩邊都先拿到同一份舊快照；`paragraphClaims` 只保證同段所有權，不能防止不同段之間的 lost update。
- 真實 IndexedDB 交易排隊後，後提交者用自己的舊快照覆蓋先提交者。

**修法**

- `features/article/article.js` 新增 `analysisSaveQueues`：
  - key 為 `articleId + contentVersion`，同一篇同版本序列化保存；不同文章／版本不互相阻塞。
  - `queueAnalysisSave()` 讓下一個任務在前一個完成（含失敗）後才開始，最後一個任務完成後清掉 queue。
- `persistParagraphResult` 改為進入 queue 後才：
  1. 再次檢查 `canCommit()`（job／claim 所有權）。
  2. 重新讀取最新記錄。
  3. 只把本次 index 的 patch 合併到最新 `paragraph_analysis`，保留其他段最新結果。
  4. 呼叫 `articleStore.saveAnalysis`。
- 批次重試最後保存也走同一 queue；提交前重讀最新記錄，只合併仍由該 batch 擁有的段落。
- 完整分析最後保存也走同一 queue，避免等待中的段落重試用舊快照蓋掉完整結果。

**測試**

- `tests/article-reliability.cjs` 情境 16：
  - 先用真實 `docs` readwrite transaction 佔住 IndexedDB。
  - 同時重試 `art_race` 第 1、2 段；確認交易釋放前兩段仍在等待保存。
  - 釋放後檢查 DOM 兩段都 `done`、記錄同時有兩段譯文、整頁重載後仍存在。

**紅燈證據（暫時停用 queue 序列化，之後已還原）**

### F2｜P1：批次保存 await 時切 A→B，A 失敗回調污染 B 畫面

**根因**

- 批次重試在所有請求完成後才保存；保存期間切到 B 時，舊 job 已被取消，但 `saveAnalysis` await 後的失敗分支仍直接 `renderParagraph()`、顯示摘要與操作目前 DOM。
- `finally` 也會無條件刷新目前畫面的按鈕／版本狀態，沒有區分工作是否還持有目前畫面。

**修法**

- 批次保存後先重驗 `isJobWriteTarget(job)`（文章、版本、action context、job 活躍、claim）：
  - 不再是目前畫面：只保留 A 的內部未保存標記，直接結束；不 render、不摘要、不按鈕、不 history。
  - 仍是目前畫面：才更新失敗段、toast、摘要與按鈕。
- 批次 `runNext` 的進度更新改為 `if (!job.cancelled)` 才執行。
- 單段重試 `persistParagraphResult` 增加 `canCommit`，排隊等待期間失去 claim 就不提交；保存後仍以 `isJobWriteTarget(job, idx)` 守門。
- 單段重試 `finally` 只在 `isCurrentArticle(targetArticleId)` 時刷新版本／按鈕狀態。
- 完整分析最後保存後也以 `isRunActive(run) + isCurrentArticle + contentVersion` 判斷是否可更新 UI／歷史。

**測試**

- `tests/article-reliability.cjs` 情境 17：
  - A（`art_race`）批次重試，使用真實 readwrite transaction 佔住 `docs`。
  - 等待 A 的最後保存交易建立（被 hold 擋住）後，透過正式閱讀記錄流程切到 B（`art_f2_b`）。
  - 以 `IDBObjectStore.prototype.put` 對 A 的 docs 寫入執行真正 `transaction.abort()`。
  - 比對切換前後 B 的原文、段落英文／譯文／status／原因、批次按鈕、摘要、history state。

**紅燈證據（暫時移除保存後守門，之後已還原）**

```text

before: F2-B 第一段譯文。/ done
after : RACE first paragraph... / 分析失败 / failed /
        失败原因：分析已显示，但未能保存；请重试
=== 結果：1 項失敗 ===
```

**綠燈**

### F3｜P1：整篇分析最後保存失敗仍顯示「已存入閱讀記錄」

**根因**

- `analyzeArticle` 最後 `saveArticle` 失敗時只顯示 toast 與一次性 history status，但隨後 `await updateHistoryIndicators()` 又以目前記憶體中的記錄重算，覆蓋成「已存入閱讀記錄」。
- 記憶體中的記錄在交易失敗後仍有完整結果，因此「有記錄」被誤當成「這次已成功保存」。
- 沒有可操作的「只重試保存」入口，重載後結果遺失。

**修法**

- 新增 `analysisSaveFailures`（以 articleId 為 key）保存完整分析最後保存失敗的明確狀態：
  - `contentVersion`、正文、完整結果、標題／來源、錯誤。
- 最後保存失敗時：
  - 保留目前完整分析畫面與譯文。
  - 在分析區頂部插入 `.analysis-save-failure` 提示列，含 `article.analysisSavePendingTitle`、`article.analysisSavePendingHint` 與 `article.retrySaveAnalysis` 按鈕。
  - `updateHistoryIndicators()` 對目前文章／版本優先顯示 `article.historyStatusSaveFailed`，不得被「已載入記錄」覆蓋。
  - 歷史清單狀態 `recordStatusText()` 也顯示未保存。
- `retryPendingAnalysisSave()` 只重試保存，不重新呼叫 AI：
  - 走同一保存 queue；再次核對目前文章與版本。
  - 成功後清除失敗狀態、清除同版本未保存標記、移除提示列、顯示已保存；重載以磁碟為準。
- `applyRecordToView()` 切回該篇時會依記憶體失敗狀態重畫提示列。
- 語言切換時 `refreshAnalysisSaveFailureTexts()` 重套提示文案。

**測試**

- `tests/article-reliability.cjs` 情境 18：
  - 舊記錄有失敗段；修改正文後完整分析。
  - 只 abort 最後一次包含完整譯文的 docs 交易；先前正文保存成功。
  - 檢查：確實 abort、history state failed、沒有「已存入阅读记录」、段落仍 done 且譯文可見、提示列與重試按鈕存在。
  - 再觸發一次 input → `updateHistoryIndicators`，確認失敗狀態不被覆蓋。
  - 恢復寫入後按「重試保存」，確認不重新呼叫 AI、提示消失、顯示已保存；重載後譯文仍在。

**紅燈證據（暫時讓歷史指示器忽略保存失敗，之後已還原）**


### F4｜P2：成功完整重分析未清舊 `unsavedParagraphs`

**根因**

- `clearParagraphsUnsaved` 的 bucket key 是 `articleId + contentVersion`。
- 完整分析成功路徑只傳 `articleId`，實際 key 變成 `articleId + 空版本`，舊版本的未保存標記沒有被清掉。
- 同頁重開時 `applyRecordToView` 依殘留標記把段落重畫成 `save_failed`，造成假失敗；整頁重載後才恢復。

**修法**

- 完整分析成功後以 `saveVersion = contentVersionOfText(articleText)` 呼叫 `clearParagraphsUnsaved(articleId, saveVersion)`。
- 同時清除 `analysisSaveFailures`；成功保存仍保留「一次寫入整份記錄」的語義。

**測試**

- `tests/article-reliability.cjs` 情境 19：
  - 單段重試成功但 docs 交易 abort，產生未保存標記。
  - 恢復寫入後，用相同正文完整重分析並成功保存。
  - 檢查段落全部 done、失敗數 0、批次按鈕隱藏。
  - 同頁重新開啟該記錄，再整頁 reload 後重新開啟，均保持成功。

**紅燈證據（暫時改回無版本 key，之後已還原）**

### F6｜P2：回答中新增助手會話會刪 stop UI 但 `activeAsk` 仍封鎖

**根因**

- `newConversation` 直接建立會話並清空 `#assistant-messages`，連同 `.assistant-stop` 一起移除。
- 舊 `activeAsk` 仍存在，第二題被忙碌鎖拒絕，但使用者已失去停止入口。
- 會話歷史的切換／刪除也有相同風險。

**修法（採「回答中禁止會話操作」策略）**

- `activeAsk` 存在時：
  - `newConversation()` 直接提示 `assistant.sessionBusy` 並返回；不建立、不清空目前訊息。
  - 歷史面板的 `open`／`delete` 操作被拒絕並提示；目前會話不變、stop 保留。
  - `deleteAssistantConversation()` 與對外 API `remove`／`create`／`switch` 也加守門。
  - `restoreConversation()` 在回答中直接返回，避免重新開啟面板或文章事件清掉 stop UI。
- 完成或停止後 `activeAsk` 由持有 token 的 `finally` 解除；舊 token 不影響下一請求，`cancelled` 語義不變。
- 新增 `assistant.sessionBusy` 的 zh-CN／zh-HK 文案。

**測試**

- `tests/assistant-state.cjs` 情境 6：
  - 建立兩個同文章會話，送出 Q6 並保持 SSE pending。
  - 點「新增會話」：stop 數量仍 1、目前會話不變、會話數不增、Q6 訊息保留、顯示忙碌提示。
  - 開歷史面板點另一會話：目前會話不變、stop 保留、訊息不清空。
  - 點目前會話刪除：不進確認、會話仍存在、stop 保留。
  - 停止後：Q6 半段保存在原會話；可建立並切到新會話；新會話不含 Q6，舊會話仍有半段。

## 五、殘留風險與邊界

1. **保存佇列只在單一頁面記憶體**：同一頁內序列化；多分頁同時保存同一篇仍依賴 `article-store` 既有的 revision／generation／outbox 機制，本次未做跨分頁交易鎖測試。
2. **`analysisSaveFailures` 只在記憶體**：整頁重載後以磁碟為準，會回到舊的失敗段狀態；這是刻意的「不誤報已保存」。若使用者未按「重試保存」就重載，畫面結果會消失，符合目前設計與測試。
3. **完整保存失敗的「重試保存」使用失敗當下的正文與結果快照**：若使用者在按重試前又修改輸入框，仍可能保存舊快照；目前只以 articleId／版本守門，沒有把輸入框最新值納入。這是保守選擇，避免把未分析的新正文寫成已分析。
4. **F6 採禁止策略**：回答中不能新增、切換、刪除會話；locale 切換會重建面板的行為仍沿用既有邏輯，本次沒有在串流中切換 locale 的專項測試。
5. **未驗證真實 AI／TTS／IME／螢幕閱讀器／真機**；所有驗證為本機 mock 與靜音替身。
6. **未修改共享 store**：`saveAnalysis` 交易失敗時仍會更新記憶體記錄（既有行為），本次在 feature 層以「未保存標記／保存失敗狀態／保存佇列」補償；若未來 store 改為失敗即回滾，這些 UI 狀態仍應保留（最壞是多顯示可重試入口，不會寫錯資料）。
7. 工作區仍有其他會話 WIP；本次只改上述檔案，沒有 commit／push／部署。
