## 1. 實際變更摘要

### 1.1 文章獨立儲存（伺服器）

- `articles`：每篇一列。`id`、`owner_user_id`（關聯 `users.user_id`）、`title`、`body`、`analysis_json`、
  `source_type`、`source_url`、遞增 `revision`、`created_at`、`updated_at`、`deleted_at`（tombstone）、
  `legacy_article_id`（舊資料冪等映射）、`last_mutation_id`、`size_bytes`。
  主鍵 `(owner_user_id, id)`：舊資料的 `url:` / `local:` ID 由來源推導，跨帳戶可能重複，因此文章身份
  以「擁有人＋ID」為準（規格要求的「穩定、與標題／網址／內容無關」用於新建文章；舊 ID 保留是為了
  不讓生詞本連結斷掉）。
- `article_changes`：每位使用者單調遞增的 `seq`（游標就是最後看到的 seq）。文章寫入、變更記錄與
  游標前進在**同一個交易／D1 batch** 內完成，條件不成立時三者都不生效。
- `article_state`：`next_seq`、`pruned_before`、`legacy_write_blocked`、`migrated_at`。
- 兩個後端共用同一份實作：`cloudflare-worker/src/articles.js` 是唯一路由實作，selfhost 透過
  `selfhost/d1-adapter.js` 把 Node SQLite／PostgreSQL 介面轉成 D1 形狀後直接重用；協議驗證放在
  `shared/article-protocol.mjs`（前端也匯入同一份）。

接口：

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| GET | `/articles?cursor=N&limit=` | 增量同步；`resetRequired` 表示游標無效或已過期 |
| GET | `/articles?full=1&includeDeleted=1` | 完整清單（metadata，不含正文） |
| POST | `/articles/batch` | 批次取完整文件（≤50） |
| GET/POST | `/articles` | 讀取單篇／新增（`clientMutationId` 冪等） |
| PUT/DELETE | `/articles/:id` | `expectedRevision` 原子版本檢查／軟刪除 |
| POST | `/articles/:id/restore` | 復原（同樣帶 `expectedRevision`） |
| POST | `/articles/import` | 舊快照文章匯入（冪等、保留原 ID）；`{final:true}` 開啟舊寫入閘門 |
| GET | `/articles/usage` | 筆數、位元組用量、產品限制 |

安全性與配額（`shared/article-protocol.mjs`）：

- 所有查詢／寫入都帶 `owner_user_id = 登入者`；別人的文章一律 404（不洩漏存在性）。`label`、`token_hash` 不參與身份。
- 單篇 800 KB（原文＋分析 JSON 的 UTF-8 位元組；明確以位元組計算，不用 D1 1 MB 的錯誤說法）、
  每人 50 MB、400 篇提示／1,000 篇上限、原文 20k 提示／100k 上限。超限回 413／409，**不刪除既有資料**。
- 舊客戶端閘門：帳戶遷移完成後，`POST /snapshot` 若仍帶非空 `articles` 群組回
  `409 articles_legacy_write_blocked`（`upgradeRequired:true`）；`GET /snapshot` 也會隱藏該群組。
  其他群組完全照常。
- selfhost 的 CORS 補上 `PUT`／`DELETE`（原本只允許 GET/POST，瀏覽器預檢會擋下更新與刪除；這是
  端到端測試抓到的實際缺陷）。

### 1.2 本機儲存（IndexedDB，local-first）

新增 `modules/article-store.js`：

- DB `bdc-articles`，object stores：`docs`（逐篇文件）、`outbox`（待同步操作）、`state`（游標、
  衝突、閘門狀態）、`drafts`（切換／刪除前的草稿）。
- 範圍（scope）＝ `同步端點 + user_id`，訪客用 `guest`；**換帳戶不會把前一個帳戶的文章或待同步
  操作帶給新帳戶**。登入後若訪客範圍有文章，會**明確詢問**是否帶入目前帳戶（不隱式歸屬）。
- 每篇文章最多保留一個待同步操作（建立後再改仍是一次建立），寫入失敗回報 `{ok:false}` 並保留記憶體
  內容（可匯出），不假裝成功；IndexedDB 不可用時退回 localStorage 後備並提示容量有限。
- `state.analyzedArticles` 仍是功能模組唯一讀取的清單（沿用 `articleId`／`article`／`result` 欄位），
  啟動時由 store 一次 hydrate，因此既有渲染／朗讀／助手流程不用改寫。
- 最近閱讀 `lastOpenedAt` 只寫本機、不動文章 `revision`、不觸發同步。

### 1.3 文章身份與非同步工作歸屬（資料安全）

`features/article/article.js`：

- 明確區分「編輯已載入的記錄」與「匯入另一篇」：文章庫、網址、新聞、檔案、OCR、問答集等**所有**
  匯入入口都經過 `applyImportedArticle()`，先清掉編輯上下文再決定是否命中既有來源；只有載入記錄／
  重新分析才沿用 `articleContext.recordId`（同篇不換 ID、不裂出生詞本；生詞本 id 仍等於文章 id）。
- 主分析、單段重試、單字／句子／片語詳解都在**啟動時**固定 `{runId, articleId, controller}`：
  - 回應回來時只寫回 `run.articleId` 那一篇；
  - 只有該篇仍是目前文章時才更新 DOM；
  - 目標文章已刪除就丟棄，不復活；
  - 取消舊工作時會還原分析按鈕狀態（原實作在切換後會卡在「分析中…」，本次修正）。
- 頂層 `detailed_analysis` 保留（按需取得的單字詳解只存在這裡），本次不做任何有損 compact；
  已移除 `sync-core.js` 原本的 `compactAnalyzedArticles`。
- 分析成功但寫入失敗會分開呈現（畫面保留結果、狀態列顯示寫入失敗），不再先宣告已儲存。

### 1.4 同步

- `modules/article-sync.js`：先上傳舊資料（`/articles/import`）→ 拉增量（`/articles?cursor=`，
  `resetRequired` 時改走完整重同步）→ 推送 outbox。快照同步與文章同步**完全分開**：
  其他群組沒有變更時仍會跑文章同步，文章同步失敗也不阻斷其他群組。
- `modules/sync-core.js`：快照不再包含 `articles`；遠端舊快照的文章群組只當成**一次性匯入來源**
  （`applyArticlesPayload` → `articleStore.importLegacyArticles`）。文章尚未遷移完成前，快照推送會
  保留遠端文章群組，避免第一次推快照就把它刪掉。
- `modules/sync-cloudflare.js`：`pushSnapshot` 會讀 409 的錯誤碼，區分版本衝突與
  `articles_legacy_write_blocked`（不再把所有 409 都當一般重試衝突）。
- 衝突處理：409 `article_revision_conflict` 時保留本機內容、暫停該篇上傳並記錄衝突；使用者可選
  「保留本機修改」「另存為副本」「使用雲端版本」。刪除遇到衝突也走同一流程。
- 刪除／復原以 tombstone 同步；伺服器 404（文章已不存在）時更新會改成重新建立，避免永久卡住。

### 1.6 遷移與備份

新增於 `modules/article-store.js`：

1. **先備份**：把原始 `analyzedArticles` + `articleMetas` 完整寫入 `bdc:articles:migration-backup:v1`
   並回讀驗證筆數，失敗就中止（原資料不動）。
2. 逐篇寫入 IndexedDB 並記錄 `legacy` 標記的待同步操作；保留原文章 ID（生詞本 id = 文章 id）。
3. **回讀驗證**：原文、分析結果（含頂層 `detailed_analysis`）、來源類型逐篇比對，不一致就中止且不標記成功。
4. 驗證通過才寫入遷移標記、清除舊 localStorage 鍵（備份仍保留）；中斷或 IDB 失敗不刪原資料、不提前標記。
5. 若遷移失敗，`main.js` 會用舊清單撐住畫面並明確提示（可重試，原資料仍在）。
   「目前沒有舊資料」時**不**寫入成功標記，避免舊分頁稍後寫入的資料永遠不被遷移（本次測試抓到的缺陷）。

備份／匯出（`modules/local-backup.js`、`modules/sync-core.js`）：備份 payload 追加
`articleDocuments`（原文、分析、來源、時間），還原時寫回逐篇儲存；仍可讀取舊備份格式。

## 3. 遷移／部署步驟（未執行，交由部署方）

### 3.1 前端

1. 直接部署靜態檔案（無 build 步驟）。瀏覽器首次啟動會自動：
   備份舊 localStorage 文章 → 逐篇寫入 IndexedDB → 回讀驗證 → 標記完成 → 清除舊鍵。
2. 登入後第一次同步會把本機與雲端快照中的舊文章以 `/articles/import` 上傳（保留原文章 ID，
   重試不會重複），最後以 `{final:true}` 開啟閘門。
3. 建議先在一台測試帳戶完成一次「備份 → 清空 → 還原」再對使用者發布。

### 3.2 Cloudflare Worker + D1（已於 2026-10-18 20:05 實際執行）

```bash
cd cloudflare-worker
npx wrangler d1 export bdc-sync --remote --output backup-<date>.sql   # 先備份
npx wrangler d1 execute bdc-sync --remote --file ./migrations/004_article_storage.sql
npx wrangler deploy
```

- `004` 只新增 `articles`、`article_changes`、`article_state` 與索引，不改既有資料、可重複執行。
- **必須先套用 migration 再部署新 Worker**，否則 `/articles` 會因缺表回 500。
- 舊版前端仍可同步其他群組；它若推送文章群組會收到 409（顯示一般衝突，屬預期）。

### 3.3 selfhost（SQLite／PostgreSQL，本次未部署）

```bash
# 備份
sqlite3 data/bdc-sync.sqlite ".backup 'bdc-sync-backup.sqlite'"   # SQLite
pg_dump "$DATABASE_URL" > bdc-sync-backup.sql                     # PostgreSQL
# 啟動新版即會以 IF NOT EXISTS 建立文章表；也可先手動套用：
sqlite3 data/bdc-sync.sqlite < migrations/001_article_storage.sql
psql "$DATABASE_URL" -f migrations/001_article_storage.sql
```

- 反向代理需放行 `PUT`／`DELETE`（CORS 已允許，代理層若有限制要一併調整）。
- PostgreSQL 模式的交易批次使用單一連線（`BEGIN/COMMIT/ROLLBACK`），不需要額外設定。

### 3.4 回滾政策

- 不建議把 `legacy_write_blocked` 關掉當回滾：那會讓舊快照重新覆蓋新資料。
- 需要回滾時：先暫停寫入 → 備份最新 `articles` 全表 → 再決定向前修復或反向轉換；已遷移後新增的
  文章必須保全。

4. **`/articles` 的寫入失敗（例如磁碟滿）在 selfhost／D1 端只回 500**，沒有更細的分類；前端視為一般失敗

5. **記憶體 hydrate**：目前啟動時把所有文章的原文與分析載入 `state.analyzedArticles`（與舊 localStorage

## 7. 已知取捨

- 文章 ID 的「全域唯一」以**(擁有人, ID)** 實作：舊 `url:`／`local:` ID 保留下來才不會拆散生詞本，
  而這些 ID 在不同帳戶可能相同。新建文章使用 `art_<時間>_<隨機>`。
- 標題權威欄位是文章記錄本身；`articleMetas` 只保留生詞本需要的來源資訊，不再用來顯示清單標題。
- 刪除文章不會刪除其專屬生詞本（沿用既有語意），文案已說明。
- 舊 localStorage 鍵在遷移驗證後才清除，且保留 `bdc:articles:migration-backup:v1` 供救援。
