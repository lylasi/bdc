# 閱讀筆記同步失敗修復報告

日期：2026-11-02，Asia/Shanghai。

狀態：本機修復及回歸驗證完成；後續已提交、推送並部署至 149，見[部署記錄](../release/20261102183612017_閱讀筆記同步修復149部署記錄.md)。以下是以合成資料重現的程式問題，未取得使用者實際失敗請求或正式環境日誌，因此不能斷言涵蓋正式環境的所有失敗原因。

## 重現原因

1. **每批固定上傳 100 項，超出後端呼叫預算。** `/reading/mutations` 逐項執行交易及回執核對，100 項需要超過 50 次 D1 API 呼叫。以真實 Worker 路由、SQLite 及每次請求 50 次呼叫的限制測試，原程式留下 100 項待同步資料，兩輪推送均失敗。部分資料雖已提交，整個 HTTP 回應仍失敗，前端無法確認回執；直接重送同一大批次仍可能失敗。Cloudflare 官方目前列出的 D1 Free 上限為每次 Worker invocation 50 次呼叫，`DB.batch()` 整批計一次：[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)。本次測試也按每個 batch 計一次，沒有把交易內 SQL 誤算為多次 API 呼叫。
2. **沒有按 UTF-8 大小分批。** 十份各 20 萬中文字的筆記約 6 MB，單篇仍在閱讀文件容量內，但一批合起來超過閱讀 API 的 4 MiB 請求上限，原程式反覆收到 413。
3. **閱讀失敗可能被誤報為成功。** 原 `syncReading()` 在推送失敗後仍回傳 `ok:true` 並清除 `lastError`；主同步完成狀態亦忽略閱讀階段的一般錯誤及 pending／衝突。
4. **手動與自動同步的鎖不一致。** 手動同步沒有設定自動同步使用的 `syncInFlight`，兩輪可能重疊。原有最短間隔亦沒有涵蓋其他裝置通知及失敗嘗試。
5. **現行齒輪選單讀不到同步狀態。** 靜態骨架沒有舊版的 `#sync-status`，原狀態更新直接跳過，選單無法顯示最近結果。

## 已完成修正

- `modules/reading-sync.js`：每批最多 10 項，按 512 KiB 的 UTF-8 目標大小拆分；較大的合法單篇文件獨立傳送。每個推送階段最多 40 批，保留原先的小型資料吞吐上限及整輪逾時保護。沒有裁切筆記內容或改動儲存格式。
- 上傳 HTTP 錯誤、缺少回執及本機確認失敗會保留 outbox；尚有失敗項目時回傳 `ok:false` 並保留錯誤原因。帳戶切換後，舊請求的錯誤不會寫入新帳戶狀態。
- `features/sync/sync.js`：手動及自動同步共用一把鎖；在途變更保留到下一輪，自動排程遵守至少 20 秒間隔。閱讀失敗、待同步及衝突均交給完成狀態判斷。
- `features/sync/sync-status.js`：閱讀階段沒有完成時，不顯示「同步完成」，包括快照還原的情況。手動失敗提示包含錯誤碼，自動同步更新狀態。
- `modules/dom.js` 與齒輪選單：補上選單狀態參照；最近狀態保存在記憶體，重新開啟選單仍可查看，開着的選單會即時更新。輸出經文字轉義，切換語言會重新翻譯狀態而保留錯誤碼。
- `locales/zh-CN.js`、`locales/zh-HK.js`：同步完成失敗／待處理文案同步更新。
- `index.html`：依專案既有腳本更新靜態資源 import map。

## 實際使用與部署邊界

修復使用既有 Worker／selfhost 路由，不需要資料庫遷移。更新前端後，既有 outbox 可按小批次繼續傳送。這次驗證使用隔離瀏覽器、合成資料及本機臨時 SQLite，沒有核對或修改正式帳戶的筆記。此修復處理單次請求容量及排程問題；網絡中斷、登入失效或整個帳戶的服務配額不足仍可能需要按實際錯誤碼排查。

工作區原有 AI 設定等未提交內容另行保留；本報告所列為本次閱讀同步修復範圍。
