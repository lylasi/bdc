## 4. 新發現（需明確重現與行號）

### N1 · 面板 Tab 陷阱在「更多」選單收起時不完整（可選，建議修）

**重現（390 或 1024，面板模態）**

1. 開面板 → 焦點移到最後一個可見控件「更多」（summary）。
2. 按 Tab → 焦點落到 `document.body`（`activeElement = BODY`），再按一次 Tab 才回到面板第一項（`×`）。
3. 焦點在第一項（`×`）時按 Shift+Tab → **沒有任何回繞**（焦點停在 `×`）。

**量測**：面板內符合 `button, input, textarea, select, summary, a[href]` 且 `!disabled && getClientRects().length` 的目標共 55 個，最後一個是 `#reading-ai-notes`（位於**收起的** `<details class="reading-tools">` 內）；其 `getClientRects().length` 為 1、`offsetParent` 有值、`visibility: visible`，只有 `checkVisibility({checkVisibilityCSS:true, contentVisibilityAuto:true})` 回 `false`。選單**展開**時，從 `#reading-ai-notes` 按 Tab 可正常回繞到 `×`。

**原因行號**：`features/article/reading-panel.js:211-212`

```js
const targets = Array.from(panel.querySelectorAll('button, input, textarea, select, summary, a[href]'))
    .filter(element => !element.disabled && element.getClientRects().length);
```

Chrome 對 `details` 收起內容仍保留 layout box，`getClientRects().length` 不能區分；`last = targets.at(-1)` 因此指向隱藏按鈕，`:215-219` 的回繞判斷（`document.activeElement === last`）永遠不成立。

**影響**：焦點陷阱漏 1 步（落到 `body`），Shift+Tab 回繞失效；背景控件仍不可達（≤1199 背景為 inert），無資料或安全風險。屬本次新增程式碼（`git diff` 顯示此段為新增）。

**最小建議**：把過濾條件改為同時要求 `element.checkVisibility?.({ checkVisibilityCSS: true, contentVisibilityAuto: true }) !== false`（或不把 `details:not([open])` 後代算進 targets）。實測 `checkVisibility` 對這三個隱藏按鈕正確回 `false`。

**證據**：[recheck2-observations.json](assets/20261028072437416_deepseek-sidebar-recheck/recheck2-observations.json) 的 `NEW-tabtrap-390`／`NEW-tabtrap-1024`。

### N2 · 滑鼠點「重試」時焦點落到 body（可選）

**重現（1440 或 390）**

1. 展開卡片 → 注入保存失敗 → 輸入文字 → 出現「保存失败，请重试 重试」。
2. 解除注入，**用滑鼠**點「重試」。
3. 結果：資料與狀態正確（store 有新筆記、狀態為「已保存」），但 `document.activeElement` 是 `BODY`，不是 textarea。
4. 同一流程改用程式觸發 `button.click()`：狀態「已保存」且焦點回到 textarea。

**原因**：`features/article/reading-panel.js:864` 的 `blur` → `persistNoteDraft` 在 mousedown 時就保存成功並觸發 `bdc:reading-change` 重繪（`renderPanel` 於 `:1114-1118` 只在 `activeElement` 是 `.reading-note` 時跳過重繪，此刻焦點已在按鈕上），重試按鈕在 mouseup 前被替換，`click` 沒有送到 `:617-625` 的 handler，被移除的按鈕使焦點回落到 body。

**影響**：僅焦點位置；資料、狀態與重試語意都正確。鍵盤使用者靠 blur 自動保存即完成保存（等同不必再按重試）。若要修，可在 `blur` 保存成功後把焦點交還同一 textarea（重整後重新查詢節點），或在 `renderPanel` 重繪後還原焦點。

**證據**：[recheck2-observations.json](assets/20261028072437416_deepseek-sidebar-recheck/recheck2-observations.json) 的 `O1-zh-CN`／`O1-zh-HK`（`focusAfterMouseClick: BODY`）與 `O1-*-keyboard`（`focusTag: TEXTAREA`）。

## 7. 未覆蓋與限制

- **未測 AI 生成本身**：「生成」按鈕只驗證可命中，未點擊（不呼叫任何供應商）；`ai_not_configured` 之後的分支沿用既有邏輯，未重測。
- **未測真實雲端同步**：`SYNC.endpoint` 為空字串，合成端點被 route 阻擋；同步競態與墓碑保護由主代理另行驗證。
- zh-HK 只重跑 390 的關鍵流程（選單、匯出對話框、全篇筆記、保存失敗／重試），1440 的 zh-HK 沿用上一輪結果。
- 模態焦點以 headless Chrome 鍵盤事件量測；未使用螢幕閱讀器，未在真機驗證軟鍵盤。
- 未重跑 `tests/reading-panel-improvements.cjs` 等全部 Node 套件（主代理職責），本輪只做針對性獨立瀏覽器檢查。
- `#app-gear-btn` 在目前版本開啟的是齒輪選單（`features/sync/sync.js:104-105`），不是 `#app-modal`；因此「全站模態」回歸以同一個 `#app-modal` 的全篇筆記／AI 範圍對話框（含全域 Escape／Tab／焦點還原）作為樣本，另加 options 對話框與刪除確認。
