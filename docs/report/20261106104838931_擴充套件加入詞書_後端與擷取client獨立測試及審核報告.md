## 2. 測試方法（為何這些測試有鑑別力）

1. **真資料庫、真路徑**：後端測試一律使用 `node:sqlite` 的 `DatabaseSync` ＋ `selfhost/d1-adapter.js`（`createD1Adapter(createSqliteDatabase(db))`）＋ `cloudflare-worker/src/worker.js` 的真實路由與認證，沒有用假的 SQL 或假的 DB。
2. **真 HTTP 的 selfhost**：`tests/vocabulary-captures-deepseek.test.mjs` 最後一項會以子行程啟動 `selfhost/server.mjs`（`PORT=0`、`HOST=127.0.0.1`、`SQLITE_PATH` 指向暫存檔），用真 `fetch` 驗證「同一份 handler 在自建服務上」的接線、401/403、重播與 `/reading/changes` 可見性；結束時只終止自己建立的子行程並刪除自己的暫存目錄。
3. **不重跑既有斷言**：新測試針對既有檔未覆蓋的面向——回執寫入失敗的回滾、同 payload 併發三連送、四個不同詞的 seq 連續性、讀取後被編輯／被刪除的中間狀態、legacy 120 筆不得被寫回裁切、已刪除詞書不得靜默成功、migration 冪等、selfhost 真 HTTP。
4. **UI 測的是產品檔本身**：`tests/capture-ui-deepseek.test.mjs` 把 `extension/capture-ui.js` 與它真正相依的 `shared/*.mjs` **逐位元組複製**到暫存目錄（並斷言複本與 repo 內容相同，`Buffer.compare === 0`），只把網路／儲存／session／i18n 換成可控 stub，用最小 DOM shim 驅動；不是複刻一份邏輯。
5. **突變驗證**：另外在 `/tmp` 的一次性複本上對產品碼做 6 個定向突變，確認測試會失敗（或在修正後轉綠），見第 5 節。
6. **限流隔離**：`http.js` 的限流桶是模組層級 Map，因此每個後端測試都建立自己的使用者與 `:memory:` DB，避免互相污染（`node --test` 每個檔案也是獨立行程）。

## 3. 缺陷與風險清單

### P2-1｜收藏途中切換目標詞書：`busy` 永不解除，成功結果被吞掉（UI 競態）

- 位置：`extension/capture-ui.js:210`
  ```js
  } finally {
      if (isAuthSessionCurrent(session) && key === currentKey()) busy = false;   // ← 210
  ```
  搭配 `extension/capture-ui.js:259-265`（`change` 監聽只重設 `savedKey`／`lastAttempt`，沒有處理 `busy`）。
- 重現（已固定成測試）：
  ```bash
  node --test --test-name-pattern='切換目標詞書' tests/capture-ui-deepseek.test.mjs
  ```
  步驟：有查詞結果 → 按「加入詞書」→ 伺服器回應前把下拉改成另一個詞書 → 等收藏完成。
- 實際結果：`captureSave.disabled === true`、文案一直停在「正在加入…」、`captureNotice` 沒有任何訊息（本測試額外驗證了「成功但沒有提示」的現況）。`key`（`displayVersion:bookId`）已改變，於是 `busy` 不會被重設，而唯一會重設 `busy` 的其他地方是 `clearResult()`（`:235`）與 `showResult()`（`:275`）。
- 影響：該次查詞結果的主要動作永久不可用，且**後端其實已收藏成功卻沒有任何回饋**；使用者可能重新查詞再收藏（雖然伺服器端會因來源去重不會產生第二筆來源，但體驗與可觀測性都不對）。重新查詞或收到帳戶事件觸發 `sync()` 才會恢復。
- 建議修法：`finally` 內無條件 `busy = false`（突變 D 證實：只改這一行，重現測試即轉綠），或把 `busy` 綁在 `displayKey` 上並在 `change` 時一併解除。

### P2-2｜單筆損壞的待傳記錄會毒化整個 outbox（無法新增、無法重試、無法從 UI 取消）

- 位置：`shared/capture-client.mjs:33-44`（`pending()` 只要有一筆記錄驗證失敗就 `throw error('capture_storage_failed')`，第 36、41 行），而 `enqueue`（`:58` 先 `pending()` 檢查 200 筆上限）與 `retry`（`:93` 先 `pending()`）都依賴它。
- 重現：
  ```bash
  node --test --test-name-pattern='單筆損壞記錄' tests/capture-client-deepseek.test.mjs
  ```
  在同一 scope 放一筆 `word: ''` 的記錄後：`pending()` → `capture_storage_failed`；`enqueue()` 新收藏也 →`capture_storage_failed`；`retry()` →`capture_storage_failed`；良好的那筆仍躺在 storage 但永遠傳不出去。其他帳戶 scope 不受影響（已測）。
- 影響：只要出現一筆不合規記錄（版本落差、寫入被截斷、storage 損壞），該帳戶的所有收藏與重試都失效；`capture-ui.js` 的待傳清單靠 `client.pending()` 渲染，因此**連「取消本機待傳」的按鈕都不會出現**，使用者只能清 storage。
- 建議：`pending()` 改成「逐筆容錯」——回傳 `{ operations, invalid }` 或直接略過壞記錄並回報數量；UI 對 `invalid` 提供「清除失效記錄」。

### P2-3｜同錨點但不同「當次意思」→ 回執成功但什麼都沒存

- 位置：`cloudflare-worker/src/captures.js:82-86`（來源只在 `sourceUrl | sentence | context` 有值時才建立）與 `:84`（去重鍵）、`:100`（`changed` 判斷）；去重鍵 `shared/vocabulary-source.mjs:20-26` 只比較 `sourceUrl／articleId／sentence／anchor`，**不含 `meaning`、`pageTitle`、`context`**。
- 重現：
  ```bash
  node --test --test-name-pattern='同錨點不同意思' tests/vocabulary-captures-deepseek.test.mjs
  ```
  同一句、同一 anchor 先用「暴跌」收藏，再用「另一義」收藏 → 第二次回 `{ok:true, sourceAdded:false, revision:1}`；詞條釋義仍是「暴跌」、`sources` 仍只有 1 筆且 `meaning` 仍是「暴跌」，但擴充套件顯示「已加入詞書」。
- 影響：使用者以為新意思已收藏，實際沒有；屬於「誤報成功」家族，但因詞已存在且舊意思可見，嚴重度列 P2。
- 建議：把 `meaning` 納入來源鍵（同位置不同意思視為不同來源），或同錨點不同意思時更新該來源的 `meaning` 並推進 revision；或回執帶 `sourceAdded:false` 的具體原因讓 UI 顯示「已存在相同來源」。

### P2-4｜預設詞書是「中文名稱猜測」且面板會自動預選

- 位置：`cloudflare-worker/src/captures.js:41-42`（`['单词本','生詞本','生字簿'].includes(name)`，否則 `books[0]`，而 `books` 是按 `entity_id` 字典序）；`extension/capture-ui.js:110`（`restoreChoice` 首次就選 `defaultBookId`）。
- 影響：使用者若把詞書命名為英文／自訂名稱，預設值等於「entity_id 最小的那本」；面板又會自動預選，使用者按一下就把詞存進可能不是他想要的詞書。**這是 UX 風險而非資料錯誤**，但因為「加入詞書」是本輪唯一動作，誤存成本不低。
- 建議：伺服器回傳真正的 `defaultBookId`（由主站的最後選取詞書或明確標記決定）；在沒有可信預設時面板保持 placeholder「請選擇詞書」，讓使用者顯式選擇。

### P2-5｜主站路徑仍會靜默裁切到 100 筆來源（計劃「不能靜默裁切」只達成一半）

- 位置：`shared/reading-protocol.mjs:213`（`value.filter(isPlainObject).slice(0, MAX_VOCABULARY_SOURCES)`，靜默截斷）；主站 `modules/vocab.js:205-215` 的 `appendSource` 沒有上限檢查。
- 現況：
  - **收藏路徑正確**：`cloudflare-worker/src/captures.js:85` 在 100 筆時回 `422 capture_sources_full`，且不留回執（已測 99→100 成功、100→101 拒絕）。
  - **legacy 超量資料正確**：既有 120 筆的詞條不會被寫回成 100 筆（已測）。
  - **但主站自己做第 101 筆追加時**：本機會先存 101 筆，伺服器寫入時被 `.slice(0,100)` 截掉，下一次同步第 101 筆無聲消失，沒有任何提示。
- 建議：`normalizeReadingPatch` 不要靜默截斷（超量時報錯或回傳 `truncated:true`），或在 `appendSource` 先檢查並提示。

## 6. 已驗證成立的重點（避免只列問題）

- 收藏的 entity／`reading_changes`／`reading_state.next_seq`／回執四者在同一個 `DB.batch()` 交易內；任一環節失敗都回 500 且**零殘留**（兩種注入方向都測過），重試後 revision 只前進一版。
- 同 requestId 重播（含併發三連送、跨刪除、跨復活）始終回**逐欄相同**的原始回執；改內容回 409 且不新增寫入。
- 收藏完全不動 snapshot：`snapshots.version` 與 payload 不變，主站改由 `GET /reading/capabilities.cursor` 與 `GET /reading/changes` 發現（`modules/sync-cloudflare.js:946-953` 的 poll 已接上 `readingStore.getReadingCursor()` 比較，並有 `isAuthSessionCurrent` 守衛）。
- 100 筆上限在收藏路徑是**明確 422 且不留回執**，且不會把 legacy 超量資料寫回被裁切的陣列（符合「不能靜默裁切」的收藏面）。
- 共用 client 的四個核心不可回退性質成立：保存先於網路、重開可續傳、取消與 scope 隔離、遲到回應不誤傷新帳戶。
- 兩語 i18n：擴充套件 `extension.*` 鍵集合 zh-CN／zh-HK 完全一致，`lookup.html` 的 `data-i18n` 鍵都存在；主站 `vocabulary.savedSources／sourceSentence／sourceMeaning／sourceContext／openOriginalSource` 兩語齊備。
