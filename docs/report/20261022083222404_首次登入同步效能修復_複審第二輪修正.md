## 摘要

本輪完成 4 項必要修正與 3 個測試缺口：

1. **舊回執誤清新修改**：匯入核對改成攜帶實際送出的 `clientMutationId`，`markOpDone`／`markOpsDone` 在交易內比對最新 outbox；舊回執只確認同一個 mutation，新的修改／刪除會保留，並把基準 revision 推進到伺服器版本。尚未上傳的 create 在伺服器已有文件後會 rebase 成 update，下一輪才能正常收斂。legacy create 在核對期間被刪除時不再直接撤掉 outbox。
2. **閱讀衝突 metadata 非原子**：`applyRemoteEntitiesInTransaction()` 把 `reading_state` 納入同一個 readwrite 交易，交易內讀取最新 state、合併衝突、與 entity／outbox 一起寫入；提交成功後才更新記憶體。fallback 也改成 entity／outbox／state 一次寫入完整 bucket，失敗直接回報。
3. **匯入進度失敗仍關閘／重傳**：`verifyLegacyRecords()` 有明確 `{ ok:true }` 契約，檢查 `markOpsDone`／`markOpFailed` 的持久化結果；缺少遠端文件不算確認。runner 遇到核對失敗立即停止，不送 `final`、不清 `gatePending`、不改走逐篇補送；`syncArticles()` 收到 `legacy.error` 也停止本輪。
4. **並行匯入突破配額**：import 的 insert 改為交易內原子配額條件（count／bytes），change／advance 用每次 insert 的唯一 token 綁定，避免替別人的文章記變更；重試前重新讀取已提交用量，並把被擋下的重複 ID 正確計入 `skipped`。回應的 `imported`／`ids`、change log、`next_seq` 都對應實際提交。

測試缺口：`tests/article-import-progress.test.mjs` 改為真實 `article-store` 持久化路徑（fake IndexedDB 跨交易／重新載入保留資料），覆蓋舊回執修改／分析／刪除、第二個 50 篇核對失敗續傳、import 回應遺失；`tests/reading-remote-apply.cjs` 補 `reading_outbox` 與 `reading_state` 寫入失敗；`tests/articles-import-race.test.mjs` 修正 barrier 讀取 `__args`，並新增 992 篇與 50 MiB 配額競態。

## 逐項修改

### 1. High — 匯入舊回執會誤清新的文章修改

- `modules/article-sync.js:374`：`verifyLegacyRecords()` 的輸入改為「實際送出的紀錄」`{ articleId, clientMutationId, title, body }`；內容與 mutation ID 都在 import 送出時捕捉，核對時不再比較「現在的本機內容」。
- `modules/article-sync.js:379`：核對缺少 `clientMutationId` 直接失敗，不允許無 ID 的回執被視為匹配。
- `modules/article-sync.js:412`：只在整批核對成功後呼叫 `store.markOpsDone(done, ctx)`，並檢查回傳 `ok`。
- `modules/article-sync.js:418`：遠端缺少文件回傳 `legacy_verify_missing`，不得視為已確認。
- `modules/article-sync.js:524`：`pushLegacyMigration()` 以 `opById` 取得每個 outbox 操作的 mutation ID，import 與核對共用同一份 `importArticleOf()` 內容。
- `modules/article-store.js:1594`：新增 `rebasePendingOutbox()`。舊回執與目前 outbox 的 mutation ID 不同時，保留新操作，`expectedRevision` 推进到伺服器 revision；`create` 在 revision > 0 時改成 `update`。
- `modules/article-store.js:1624`、`:1696`：`markOpDone`／`markOpsDone` 的 `matches` 改為必須有 ID 且與 outbox 的 `clientMutationId` 相同；不匹配時在交易內寫回 rebase 後的 outbox，而不是刪除。
- `modules/article-store.js:1103`：`deleteArticle()` 的「未上傳 create 直接撤掉 outbox」分支排除 `legacy` create。核對期間刪除 legacy 文章會留下 delete outbox，舊 create 回執回來後只推進 revision，下一輪送 delete。

驗收：
- `tests/article-import-progress.test.mjs:209`：延遲 `/articles/batch`，期間修改正文、分析、刪除；舊回執不清理 3 個新操作，types 為 update／update／delete，revision 由 0 推進到 1；重新載入後 outbox 仍在；下一輪同步後伺服器正文／分析／刪除狀態都收斂，無衝突。

### 2. High — 閱讀衝突紀錄沒有與 entity／outbox 原子提交

- `modules/reading-store.js:2040`：`applyRemoteEntitiesInTransaction()` 的交易 store 加入 `READING_STATE`。
- `modules/reading-store.js:2052`：交易內先讀取最新 state。
- `modules/reading-store.js:2106`：交易內合併新舊衝突，`reading_state.put` 與 entity／outbox 的寫入放在同一批 operations。
- `modules/reading-store.js:2140`：交易成功後才把 `value.committedConflicts` 寫回記憶體 `meta.conflicts`；交易失敗直接回 `ok:false`，不更新任何記憶體。
- `modules/reading-store.js:2150`：fallback 改成在本地 bucket 內合并 state，entity／outbox／state 一次 `writeBucket`；寫入失敗回 `storage_full`，成功後才更新 `meta.conflicts` 與 remembered entities。
- `modules/reading-store.js:2213`：抽出 `mergeConflictUpdates()`；`modules/reading-store.js:2227`：抽出 `buildStatePayload()`，`persistMeta()` 也共用同一份完整 state payload（`:2397`）。

驗收：
- `tests/reading-remote-apply.cjs:206`：注入 `reading_outbox.put` 失敗；entity revision、outbox mutation ID、記憶體、衝突與 state 都維持原值。
- `tests/reading-remote-apply.cjs:287`：注入 `reading_state.put` 失敗；entity／outbox／state／記憶體零部分更新，函式回 `ok:false`。移除注入後重試成功合併，衝突寫入持久層；重新載入後衝突仍在；再次套用同一遠端 revision 2 不會清掉衝突。

### 3. Medium — 匯入進度未持久化成功，仍關閘並重傳

- `modules/article-sync.js:374`：核對有明確成功契約；`markOpsDone`／`markOpFailed` 失敗會回傳錯誤。
- `modules/article-sync.js:458`：`runLegacyImportBatches()` 檢查每個 `verifyChunk` 的結果；失敗立即回傳錯誤，不再處理後續 import 批次，也不執行 `finalize`。
- `modules/article-sync.js:592`：`syncArticles()` 在 `pushLegacyMigration()` 回傳 `legacy.error` 時立即回 `{ ok:false, error }`，不執行 `pullDelta`／`pushOutbox`，避免逐篇補送。
- 缺少遠端文件（`:418`）與 mutation ID 缺失（`:379`）都不算核對成功；只有已持久化的批次會保留進度。

驗收：
- `tests/article-import-progress.test.mjs:287`：120 篇，第二個 50 篇核對注入 `docs.put` 失敗；第一個 50 篇進度保留（outbox 70），`finalCalls` 0、`gatePending` true、沒有逐篇 create。重新載入後 outbox 仍是 70；第二輪 import 只送 70 篇（伺服器 skip 已存在的 50 篇），完成核對與持久化後才 final，最後 outbox 0、gate false、伺服器 120 篇。
- `tests/article-import-progress.test.mjs:328`：伺服器已提交但 import 回應遺失；第一輪失敗且 outbox 60 保留，第二輪重新 import 60 篇（全部 skipped）、核對、final，伺服器仍 60 篇且沒有逐篇 create。

### 4. Medium — 並行匯入重試可突破文章配額

- `cloudflare-worker/src/articles.js:200`：新增 `insertQuotaStatement()`。`INSERT ... SELECT ... WHERE` 在同一個 statement／交易內檢查當下已提交的 count 與 `SUM(size_bytes)`；配額不足時 insert 影響 0 列。
- `cloudflare-worker/src/articles.js:150`、`:163`：`writeStatements()`／`advanceStatements()` 支援 `matchToken`；import 的 change／advance 只對本次 insert 寫入的唯一 `last_mutation_id` token 生效，不會替另一個請求已建立的文章記 change 或前進序號。
- `cloudflare-worker/src/articles.js:661`：`flush()` 重試前（`:690`）重新以 `readUsage()` 讀取已提交用量，不再用本請求的暫記值扣重複項目。
- `cloudflare-worker/src/articles.js:743`：被原子條件擋下的項目重新讀取既有 ID／legacy ID；已由其他請求建立者計入 `skipped`，其餘才是真正的配額阻擋。
- `cloudflare-worker/src/articles.js:739`、`:761`：insert 後重新讀取實際用量，依 `checkQuota()` 回傳正確的 `article_count_exceeded`／`article_quota_exceeded`；`imported`／`ids` 只累計實際 insert 成功的項目。

驗收：
- `tests/articles-import-race.test.mjs:203`：初始 992 篇，A 匯入 8 篇、B 匯入 16 篇且前 8 篇同 ID 但大小不同。屏障強制兩者先讀舊用量、A 先提交；B 在重試後不能再插入，回應 409 `article_count_exceeded`、imported 0、skipped 8；最終 1,000 篇、8 筆 create change、`next_seq` 9；重送不改資料與 change log。
- `tests/articles-import-race.test.mjs:284`：seed 一篇 `maxUserBytes - 100`，強制第一次 `readUsage` 回過期值；匯入 100／200 bytes 兩篇。原子條件只允許第一篇，總量正好 50 MiB；回應 409 `article_quota_exceeded`、imported 1、ids 只有第一篇；change 1 筆、`next_seq` 2；重送 imported 0、skipped 1，資料與序號不變。

## 未完成事項與風險

1. **單篇 create／update／restore 的配額仍是先讀後寫**：本輪依複審要求把 `/articles/import` 的 insert 做成交易內原子配額；`POST /articles`、`PUT /articles/:id`、`POST /articles/:id/restore` 仍使用原本的 `readUsage()` + `checkQuota()` 前置檢查。若 direct create／update 與 import 同時發生，理論上仍可能由單篇寫入突破配額；這是既有路徑，不在本輪 4 個問題與驗收案例內。若要完全消除，應把同一原子條件套到 create／update／restore 並補並行測試。
2. **PostgreSQL 未在本輪重跑**：Worker 與 selfhost 共用 `articles.js`，本輪 SQL 只在 SQLite（D1 adapter）與既有 selfhost 測試驗證；使用 `INSERT ... SELECT ... WHERE`／相關子查詢與 `crypto.randomUUID()` 屬標準語法，但部署前仍建議在 PostgreSQL 實測 992 篇與 50 MiB 邊界。
3. **`tests/article-import-progress.test.mjs` 使用測試用 fake IndexedDB**：實作了本專案實際使用的 open／upgrade／transaction／get／put／delete／getAll／index 子集，資料跨交易與 reload 保留；不是完整 IndexedDB 規範。真實 Chromium + IndexedDB 的 120 篇匯入與 `reading-remote-apply.cjs` 已另外覆蓋主要瀏覽器路徑。
4. **閱讀 fallback 的 state 原子寫入沒有獨立瀏覽器測試**：本輪已把 fallback 改成 entity／outbox／state 一次 `writeBucket`，但現有 `reading-remote-apply.cjs` 只注入 IndexedDB 失敗。fallback 需要 IndexedDB 完全不可用，本輪沒有另建專用測試。
5. **既有 phonetics 測試失敗**：全量 Node 測試的唯一失敗是 `tests/phonetics.test.mjs` 的 vm import 語法問題，與本輪修改檔案無關；未擅自修改其他 session 的 phonetics 模組。
