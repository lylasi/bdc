## 摘要

本輪完成 5 項必要修正：

1. **回應遺失後修改分析會誤清 outbox（High）**：送出 `/articles/import` 前先把「實際送出的內容＋mutation ID」持久化成 `importSnapshot`，跟著後續修改／刪除的操作保留；重載重試時先核對這份快照（analysis／source 等全部同步欄位），確認原操作後再保留新操作並 rebase 到伺服器 revision。舊回執只確認同一個 mutation ID，重複回執不會重建已確認操作。
2. **衝突 metadata 寫入失敗仍回報成功（Medium）**：`markOpFailed()` 改成文章文件、摘要與 `state`（lastError／衝突）在同一個 IndexedDB 交易提交，成功才更新記憶體；`markOpDone()`／`markOpsDone()` 的衝突移除也放進同一交易，不再忽略 `persistMeta()` 結果。
3. **單篇寫入與 PostgreSQL 的配額保護（Medium）**：建立、更新（放大內容）、還原全部改用交易內原子配額條件；PostgreSQL 在每個配額交易的第一條語句對 `article_state` 做使用者範圍的 `SELECT … FOR UPDATE` 列鎖，READ COMMITTED 下也能序列化。selfhost 轉接層補上 `driver` 讓共用路由判斷方言。
4. **整批 skipped 後用量未重算（Medium）**：import 的重試路徑在所有「只剩重複項目」與「全部被擋下的都是重複項目」返回前，都重新以已提交資料讀取用量，清掉被跳過項目的預占額度。
5. **fake IndexedDB 缺乏交易語意（Medium）**：替身改為「交易快照＋提交／回滾」、重疊交易依建立順序序列化、交易內可讀自己的未提交寫入；新增 request 執行期失敗注入。文章測試改在批次「後段」非同步失敗，驗證整批回滾與先前 50 篇進度保留。

## 逐項修改

### 1. High — 回應遺失後修改分析，重試不得靜默清掉操作

- `modules/article-store.js:661`：新增 `recordImportSubmission()`。在送出 import 前，把 `{ clientMutationId, title, body, analysis, sourceType, sourceUrl, submittedAt }` 寫進 outbox 操作的 `importSnapshot`；IndexedDB／localStorage 後備都支援。操作已不存在時不重建。
- `modules/article-store.js:717`：`buildOutboxOp()` 產生新的 update／delete 操作時保留既有 `importSnapshot`，等待期間的修改不會失去「真正送出過什麼」的資訊。
- `modules/article-store.js:1660`：`rebasePendingOutbox()` 增加 `confirmedMutationId`。確認的是舊快照時清掉 `importSnapshot`，但保留目前操作並把 `expectedRevision` 推進到伺服器 revision；`create` 在 revision > 0 時改成 `update`。
- `modules/article-sync.js:376`：新增 `sortedJson()`；`modules/article-sync.js:390`：新增 `contentKey()`／`docContentKey()`，核對涵蓋 title／body／analysis／sourceType／sourceUrl（analysis 以排序鍵的 JSON 比較，忽略鍵序與 `undefined`）。
- `modules/article-sync.js:484`：新增 `verifySubmittedSnapshots()`。重新載入後若操作帶著未確認的 `importSnapshot`，先用 `/articles/batch` 核對伺服器內容：
  - 與快照一致 → 以快照的 mutation ID 確認，`markOpsDone()` 保留新操作並 rebase。
  - 伺服器沒有這篇 → 快照當初未提交，下一階段重送目前內容。
  - 兩者都不同 → 真正衝突，`markOpFailed()` 記錄 `legacy_differs`。
  - `delete` 操作也適用，因此「匯入成功但回應遺失後立刻刪除」會保留 delete 並推進 revision。
- `modules/article-sync.js:606`：`pushLegacyMigration()` 先跑 preflight，再重新讀取 outbox，只匯入「尚未確認、且不是已 rebase 的 update」的 create／update；`modules/article-sync.js:659` 在每個 import 批次送出前持久化快照，持久化失敗就停止本輪、不送 final。
- `modules/article-sync.js:426`：`verifyLegacyRecords()` 改比對完整內容指紋，不再只比 title／body；沒有 mutation ID、沒有遠端文件或持久化失敗都不算核對成功。
- `modules/article-sync.js:701`：沒有要匯入且閘門已關閉時不再多送 `final`。

驗收測試：

### 2. Medium — 文章衝突 metadata 寫入失敗不得當成成功

- `modules/article-store.js:1866`：新增 `persistDocWithMeta()`。文章文件、摘要與完整 `state`（含 `lastError`、`conflicts`）在同一個 IndexedDB 交易提交；IndexedDB 不可用時退回單一 localStorage 桶一次寫入。任何一部分失敗都回 `ok:false`，不更新記憶體。
- `modules/article-store.js:1907`：`markOpFailed()` 改用上述交易，成功提交後才設定 `meta.lastError`／`meta.conflicts`、更新記錄；失敗直接回傳錯誤。原本忽略的 `markSyncError()`／`setConflict()` 兩段寫入已合併。
- `modules/article-store.js:1683`：`markOpDone()` 的交易加入 `state` store；完成確認與衝突移除同交易提交，失敗整批回滾。
- `modules/article-store.js:1770`：`markOpsDone()` 同理；批次確認的衝突移除不再另開 `persistMeta()` 並忽略結果。

驗收測試：`tests/article-import-progress.test.mjs:461`。注入 `state` 寫入失敗時同步回 `ok:false`、`final` 0 次、gate 保持 pending、逐篇 create 0 次、記憶體沒有未持久化的衝突；移除注入後重試成功，衝突寫入持久層，重新載入後仍保留。
- 反證：把 `markOpFailed()` 還原成忽略 metadata 失敗的舊寫法，測試失敗（同步回報成功）。

### 3. Medium — 配額保護涵蓋單篇寫入與 PostgreSQL 並行

- `cloudflare-worker/src/articles.js:147`：新增 `quotaLockStatements()`。PostgreSQL 在每個配額敏感 batch 的第一條語句執行 `SELECT 1 FROM article_state WHERE owner_user_id = ? FOR UPDATE`；SQLite／D1 回空陣列（寫入本身序列化）。
- `cloudflare-worker/src/articles.js:47`／`:56`：`ensureState()` 先讀取狀態列，已存在就不再 upsert；並行序列化交給上述明確列鎖，不再依賴 `INSERT … ON CONFLICT` 偶然擋住別的交易（也少一次寫入）。
- `cloudflare-worker/src/articles.js:200`：`insertQuotaStatement()` 的 `token` 寫入 `last_mutation_id`；匯入、建立共用同一條 `INSERT … SELECT … WHERE` 原子配額。
- `cloudflare-worker/src/articles.js:386`（建立，batch `:426`）：改用 `insertQuotaStatement()`，並以 `locks.length` 取得 insert 結果；被擋下時重讀該 ID 判斷冪等或配額錯誤。change／advance 以本次 token 綁定，只對實際插入的列生效。
- `cloudflare-worker/src/articles.js:465`（更新，batch `:510`）：`UPDATE … WHERE revision = ? AND (SELECT SUM(size_bytes) … AND id <> ?) + ? <= ?`，把「其他人的已提交用量＋本篇新大小」放在同一個 statement；`revision` 相符卻 0 列時回配額錯誤而不是版本衝突。
- `cloudflare-worker/src/articles.js:555`（刪除）：補 `ensureState()` 與 token，change／advance 只對這次真正更新的列生效。
- `cloudflare-worker/src/articles.js:600`（還原，batch `:633`）：`UPDATE … WHERE … AND (SELECT COUNT(*) …) < 1000 AND (SELECT SUM(size_bytes) …) + ? <= 50 MiB`；0 列時區分版本衝突與配額。
- `selfhost/d1-adapter.js:62`：`createD1Adapter()` 暴露 `driver`，讓共用路由判斷是否需要 PostgreSQL 列鎖。

## 未完成事項與風險

1. **舊版已存在、沒有 `importSnapshot` 的 legacy outbox**：若使用者升級前就已經歷「匯入回應遺失＋修改」，升級後第一次同步沒有快照可核對，會以目前內容比對遠端；不同時記錄 `legacy_differs` 衝突讓使用者選擇，而不是靜默清掉。這是刻意保守的降級行為，不會再誤清操作，但需要使用者處理一次。
2. **PostgreSQL 常駐測試仍需環境**：repo 內沒有 `pg` 依賴與 CI PostgreSQL；本輪以臨時容器實測，測試檔在未設定 `BDC_TEST_PG_URL` 時 skip。部署前若 CI 有 PostgreSQL，建議把這個檔案接進去。
3. **D1／SQLite 的並行保護依賴寫入序列化與原子條件**：D1 的 batch 寫入本身序列化；selfhost SQLite 使用 `BEGIN IMMEDIATE`。若未來改成允許 SQLite 並行寫入的 driver，仍需確認交易隔離。
4. **`ensureState()` 改為先讀後寫**：這是本輪為了讓 PostgreSQL 列鎖成為唯一序列化機制、並減少每次請求 upsert 的寫入。並行首次建立狀態列時仍靠 `ON CONFLICT DO NOTHING` 與唯一鍵，行為與原本一致；已由既有 Worker／selfhost 測試覆蓋。
5. **fake IndexedDB 不是完整規範實作**：只支援本專案使用的 store／index／count 子集與交易語意；真實 Chromium IndexedDB 的回應遺失與衝突流程已由 `tests/article-import-lost-response.cjs` 另外覆蓋。
6. **既有 phonetics 測試失敗**：全量 Node 測試唯一失敗是 `tests/phonetics.test.mjs` 的 vm import 語法問題，與本輪修改檔案無關；未擅自修改其他 session 的 phonetics 模組。
7. **UI 驗收**：本輪沒有新增或修改使用者可見文字，`zh-CN`／`zh-HK` 鍵集合仍一致（各 1987 鍵）；沒有新增 locale key。
