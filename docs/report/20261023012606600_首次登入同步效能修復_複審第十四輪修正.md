## 二、逐項根因與修改

### P1（High）後備匯出仍會「假成功」

**根因**

1. `modules/article-store.js` 的 `readDocsDetailed()` 在 localStorage 後備分支直接回
   `{ ok: true, docs: fallbackRead(scope).docs || [] }`。`fallbackRead()` 會把
   `localStorage.getItem` 例外與 `JSON.parse` 失敗吞成空桶，於是
   `exportDocumentsResult()` → `loadAllRecordsDetailed()` → `readDocsDetailed()`
   這條備份鏈在桶損壞時得到「0 篇文章、成功」。
2. `modules/reading-store.js` 的 `exportAll()` 後備分支使用寬鬆的 `readBucket()`，
   同樣把例外／損壞轉成空桶，回 `ok:true` 的空快照。
3. `modules/local-backup.js` 的檢查本身是正確的（`articleExport.ok !== true` 即
   回錯、`readingExport.ok !== true` 即回錯），但在上游永遠拿到 `ok:true` 時，
   便會 `saveBackupPayload()`、裁剪舊自動備份、寫入自動備份簽章；同一簽章讓
   下一次自動備份跳過重建，等於用殘缺備份永久覆蓋可用備份。

**修改（file:line 為修改後位置）**

1. `modules/article-store.js:1397-1422`
   - 新增 `fallbackDocsDetailed(scope)`：改用既有的 `fallbackReadStrict(scope)`；
     失敗時寫入 `meta.persistenceError` 並回 `{ ok:false, error }`（`storage_read_failed`／
     `storage_corrupt`），成功才回文件清單。桶不存在（`null`／`''`）在
     `fallbackReadStrict()` 內仍視為合法空桶。
   - `readDocsDetailed()` 的後備分支與 `idb_unavailable` 轉後備分支都改走
     `fallbackDocsDetailed()`。`readDocs()` 仍是「失敗回 `[]`」的相容包裝，
     一般讀取路徑行為不變。
2. `modules/reading-store.js:185-221` 新增 `readBucketStrict(recordScope)`：
   - `getItem` 例外 → `{ ok:false, error:'storage_read_failed' }`
   - `JSON.parse` 例外／非物件／陣列 → `{ ok:false, error:'storage_corrupt' }`
   - 桶內已知清單欄位（`items`、`documents`、`books`、`entries`、`links`、
     `conversations`、`messages`、`outbox`、`versions`）存在卻不是陣列 → `storage_corrupt`；
     `state` 存在卻不是物件 → `storage_corrupt`
   - 桶不存在（`null`／`''`）→ `{ ok:true, bucket: emptyBucket() }`
   - `readBucket()` 保留原樣給一般讀取路徑（裝置無備份時仍可正常啟動）。
3. `modules/reading-store.js:2660-2667` `exportAll()` 後備分支改用
   `readBucketStrict()`，失敗回 `{ ok:false, error }` 並寫 `meta.persistenceError`。
4. `modules/local-backup.js` **無需修改**（既有 `ok !== true` 檢查已足夠），
   因此不保存、不裁剪、不寫簽章；本次以測試固定此契約。

**測試設計**

新增 `tests/local-backup-fallback-export.test.mjs`（`globalThis.indexedDB = undefined`，
讓 article-store 與 reading-store 都走 localStorage 後備）：

1. 桶不存在＝合法空桶：`exportDocumentsResult()`／`exportAll()` 都回 `ok:true` 空資料。
2. 文章桶無效 JSON → `exportDocumentsResult().error === 'storage_corrupt'`；
   `createBackup('auto sync')` 回 `error`（`article_export_failed:storage_corrupt`），
   備份檔清單、索引、中繼資料與自動備份簽章全部不變，損壞桶內容未被覆寫。
3. 文章桶 `docs` 不是陣列 → 同樣 `storage_corrupt`。
4. 閱讀桶無效 JSON（文章桶先放合法空桶，確保失敗來源是閱讀）→
   `exportAll().ok === false`；備份不保存、不裁剪、不改簽章，損壞桶未被覆寫。
5. 閱讀桶 `messages` 不是陣列 → `storage_corrupt`。
6. 反向驗證：桶恢復正常（含一篇文章）→ 備份建立成功、簽章更新、
   `payload.articleDocuments[0].body` 正確、`payload.reading.ok === true`。

### P2（Medium）閱讀還原部分寫入失敗仍回成功

**根因**

`modules/reading-store.js` 的 `restoreAll()` 逐一呼叫 `writeEntity()`／
`saveArticleVersion()`，但只做 `if (result.ok) counts.X += 1;`，`!ok` 直接忽略；
且 `verifyErrors` 只在 `allowPartial !== true` 時使用，`allowPartial:true` 時整批丟棄，
最後一律 `return { ok:true, counts, verifyErrors }`。備份還原
（`sync-core.applySnapshotPayload()`）與 `adoptGuestReadingData()` 都使用
`allowPartial:true`，因此資料缺一半仍被當成成功。

**修改**

- `modules/reading-store.js:2758-2764` 新增 `failures` 與 `recordFailure(entity, id, result)`，
  統一記錄 `{ entity, id, error }`（`error` 取 `result.error`，缺省為 `write_failed`）。
- 七個 `writeEntity()` 迴圈（vocabularyBook / vocabularyEntry / learningItem /
  vocabularyLink / articleDocument / conversation / message）與
  `saveArticleVersion()` 迴圈，改為成功累計 counts、失敗 `recordFailure()`；
  **仍繼續處理其餘項目**（保留 partial 語意）。
  - 文章版本以 `articleId:version` 作為 `id`（版本鍵）。
- `modules/reading-store.js:2884-2890` 完成後：
  - `allowPartial:false` + `verifyErrors` → 維持既有 `{ ok:false, error:'verify_failed', details, counts }`。
  - 其他情況若有任何 `failures` 或 `verifyErrors` → 回
    `{ ok:false, error:'partial_restore_failed', failures, verifyErrors, counts }`。
  - 都沒有才回 `{ ok:true, counts, verifyErrors }`。
- `adoptGuestReadingData()` 未改動：`{ ...result, imported: total }` 會正確帶出
  `ok:false`，`features/sync/sync.js:301-308` 既有的 `if (result && result.ok)` 分支
  因此顯示錯誤訊息，不再誤報「已併入」。
- `sync-core.applySnapshotPayload()` 已檢查 `result.ok !== true`，現在會把
  `reading` 群組錯誤往上報，`restoreSnapshotLocally()` 拋
  `snapshot_restore_failed`。

**測試設計**

新增 `tests/reading-restore-partial.test.mjs`（fake IndexedDB；以 monkey-patch
`FakeObjectStore.prototype.put` 對指定 store／id 注入同步例外，等同配額或
DataClone 失敗）：

1. 兩則 learningItem，對第一則的 `reading_items` put 注入失敗：
   - `restoreAll(..., { allowPartial:true })` → `ok:false`、
     `error:'partial_restore_failed'`、`counts.learningItems === 1`（其餘項目仍寫入）、
     `failures[0] === { entity:'learningItem', id, error:'idb_work_failed' }`、
     `verifyErrors` 含 `missing_item:<id>`；成功項目真的存在、失敗項目不存在。
2. `allowPartial:false` 同一情境 → 維持 `{ ok:false, error:'verify_failed', details }`。
3. `restoreSnapshotLocally({ reading: payload })` → 拋
   `snapshot_restore_failed`，訊息含 `reading:partial_restore_failed`，
   `error.errors` 有 `{ group:'reading', error:'partial_restore_failed' }`。
4. `adoptGuestReadingData()`：訪客 scope 先寫入一本詞書，切回目前 scope 後對
   `vocab_books` put 注入失敗 → 回 `ok:false`、`partial_restore_failed`、
   `failures[0].entity === 'vocabularyBook'`、`imported === 1`（不再被丟棄）。
5. 反向驗證：移除注入後 `restoreAll` 與 `restoreSnapshotLocally` 都成功，
   兩則條目內容正確。

### P3（Medium）還原提示仍掩蓋文章「未完成」

**根因**

`features/sync/sync-status.js` 的 `resolveSyncCompletion()` 在
`restoredFromRemote` 成立的區塊只有兩個分支：`!articleOk` 的組合訊息與「純還原」
提示。當 `restoredFromRemote === true && articleOk === true && articlePending === true`
（單篇推送失敗／衝突）時會落到純還原提示，手動同步顯示
`sync.restoredEmpty`／`sync.restoredAutomatic`，完全看不到「文章同步未完成」，
自動同步也只更新狀態列而不提示。

**修改**

- `features/sync/sync-status.js:31-42`：在 `!articleOk` 分支之後、純還原分支之前，
  新增 `restoredFromRemote && articlePending` 組合狀態：
  - 手動：`{ statusKey:'sync.restoredArticleSyncPending',
    toastKey:'sync.restoredArticleSyncPending', toastLevel:'warning', toastMs:5000 }`
  - 自動：`{ statusKey:'sync.restoredArticleSyncPending', toastKey:'', toastLevel:'' }`
    （只更新狀態列，不彈提示）
- `locales/zh-CN.js:1282`：`restoredArticleSyncPending: '已从云端恢复，但仍有文章未同步完成；稍后会自动重试'`
- `locales/zh-HK.js:1282`：`restoredArticleSyncPending: '已從雲端還原，但仍有文章未同步完成；稍後會自動重試'`
  （香港書面中文、無插值、沿用既有 `articleSyncPending` 用詞）

**測試設計**

`tests/sync-status.test.mjs` 新增「雲端還原與文章未完成同時發生」測試：

- 手動：`statusKey === 'sync.restoredArticleSyncPending'`、
  `toastKey` 相同、`toastLevel === 'warning'`，且 `statusKey` 不得為
  `sync.syncDone`／`sync.restoredEmpty`／`sync.restoredAutomatic`／`sync.articleSyncPending`。
- 自動：`statusKey === 'sync.restoredArticleSyncPending'`、`toastKey === ''`，
  且不得為 `sync.syncDone`／`sync.restoredAutomatic`。
- 對照：`restoredFromRemote && articleOk && !articlePending` 仍是純還原提示
  （`sync.restoredEmpty`），確保新分支不搶先。
- 既有「所有可能回傳的鍵都有 zh-CN 與 zh-HK 文案」列舉測試會自動涵蓋新鍵。

## 六、剩餘風險

1. **一般讀取仍寬鬆**：`readSummaries()`／`readState()`（文章）與 `readBucket()`
   （閱讀）仍是寬鬆讀取，這是刻意的（讓沒有備份的裝置可啟動），但後備桶損壞時
   一般畫面會顯示空清單，只有 `meta.persistenceError` 與匯出路徑會反映錯誤。
   本次只把「匯出／備份」鏈改嚴格，未擴大影響面。
2. **`partial_restore_failed` 的 UI 粒度**：`restoreSnapshotLocally()` 只要有一個
   群組失敗就整體拋 `snapshot_restore_failed`，使用者看到的是「還原失敗」，
   不會看到「已還原 N 項、M 項失敗」。`failures`／`counts` 已帶在回傳值與
   `sync-core` 的錯誤明細中，後續若要顯示部分成功摘要可直接使用。
3. **`allowPartial:false` 的版本寫入失敗**：若只有 `saveArticleVersion()` 失敗而
   核對（`verifyErrors`）沒有涵蓋到，現在會落到 `partial_restore_failed`（舊行為
   是 `ok:true`）。語意上更正確，但屬於行為變更，已由第 2 個測試確認
   `verify_failed` 優先順序未變。
4. **`storage_read_failed` 分支未直接測試**：Node 的 localStorage shim 不會在
   `getItem` 拋錯，現有測試只覆蓋 `storage_corrupt`；真實瀏覽器的
   SecurityError／配額情境仍需手動或 Playwright 驗證。
5. **嚴格讀取的欄位白名單**：`readBucketStrict()` 只驗證已知清單欄位與 `state`，
   不會逐筆驗證每個實體；未來新增桶內欄位時要同步加入白名單，否則新欄位損壞
   不會被偵測（但也不會被當成清單誤讀）。
6. **locale 稽核仍有既有噪音**：`audit-i18n.mjs` 仍回報 643 處既有硬編碼中文與
   `phonetics.` 缺鍵，皆非本次引入；本次新增鍵已在兩份字典同步且鍵集合一致
   （2024 / 2024）。
