## 1. 必修 1：delta 墓碑必須結束上一條生命週期

### 1.1 根因

`applyRemoteTombstones()` 只把 `deletedAt` 寫進文件，代際（`generation`）與
`article_generations` ledger 都停在原值：代表「上一條生命週期」沒有被結束。
於是 B 在墓碑前送出的 gen1 PUT（伺服器已提交 rev2、回應暫扣）在 A 收到墓碑、
匯入同 ID 備份、再保存新正文之後仍屬「同代際」，`markOpDone`／`markOpsDone`
的 `sameGeneration` 判定成立（`rebuilt` 僅取決於代際與 `supersededMutations`），
舊回執把新文件的 `updatedAt` 覆回舊回應、把 revision 推高，後續更新便 409。

第八輪的 ledger 前進只覆蓋 **完整 pull 移除**（`deleteDoc` 的 `retireGeneration`），
delta 墓碑（`pullDelta` → `applyRemoteTombstones`、以及 full pull 內
`item.deletedAt` 的墓碑清單）沒有走到那條路徑。

### 1.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:2196-2256` `applyRemoteTombstones()` | 交易內改成三態：`missing`（本機沒有文件，不動 ledger）／`skippedLocalPending`（dirty／pending／outbox，完全不動）／`alreadyDeleted`（本地已是 tombstone，只補齊 ledger，不再 +1）／套用墓碑 |
| `:2232` | 套用時 `generation = effectiveStoredGeneration(localDoc, ledgerRow) + 1`：代際只前進、仍以交易內最高值為基準 |
| `:2233-2241` | 文件、摘要、outbox、ledger 在同一個 IndexedDB 交易內一起寫；ledger 一律寫入新代際（不再只在「大於」時才寫） |
| `:2168-2194` `finishRemoteTombstones()` | IDB／後備共用的記憶體同步：更新記憶體記錄的 `deletedAt`、`generation`、`revision`、`dirty`、`pending`，`dataEpoch += 1`、`emitChange()` |
| `:542-587` `fallbackApplyTombstones()` | localStorage 後備的同一套規則：讀 bucket → 判斷 → 一次寫回，中間沒有 `await`；文件、`generations` ledger、outbox 同步維護 |
| `:2201`、`:2247-2250` | 後備模式直接走 `fallbackApplyTombstones()`；IDB 回 `idb_unavailable` 時切換後備同一條路徑 |
| `:2258-2272` `applyRemoteTombstone()` | 回傳值語意不變（`applied` / `skippedLocalPending`），另可取得 `generation` |

設計取捨：

- **只有遠端墓碑退休代際**。使用者主動刪除仍走 `deleteArticle()` →
  `persistDocWithOp(tombstone, 'delete')`：tombstone、delete outbox、ledger
  同一個代際，`DELETE` 回執仍能匹配（新增測試固定這條路徑）。
- 遠端墓碑遇到 `dirty`／`pending`／outbox 直接跳過（既有語意），因此
  「本機還有未上傳的刪除／正文」不會被遠端墓碑改寫，也不會被退休。
- 已同步完成的 tombstone 再收到同一個遠端墓碑（delta 重送、`includeDeleted`
  的完整清單）走 `alreadyDeleted`：只補 ledger 不 +1，避免同一生命週期被
  反覆推進。文件被永久清除後由完整 pull 移除（`deleteDoc(..., retireGeneration)`）
  時仍會再 +1 一次，這是上一輪已記錄的行為。
- `missing`（本機完全沒有這份文件）不推進 ledger：本機沒有可結束的生命週期，
  而文件之所以消失必定是先前某個分頁走過完整 pull 移除／墓碑退休，ledger
  已經領先；在這裡再 +1 會讓每一次 delta 重送都灌高 ledger。
- 墓碑後收到同 ID 的新遠端文件（`applyRemoteDocs`／`applyRemoteDoc`）本來就採
  `max(文件, ledger)`，現在 ledger 已前進，新文件直接沿用更高代際。

## 2. 必修 2：後備模式的回執必須真的落地

### 2.1 根因

`markOpDone()`／`markOpsDone()` 只有 IndexedDB 實作：IndexedDB 不可用時
`idbRequest` 回 `idb_unavailable`，兩個函式都直接回 `{ ok:false, error:'idb_unavailable' }`。
`pushOne()` 又忽略 `markOpDone` 的回傳值，於是出現：

1. `POST /articles` 成功（遠端 rev1）；
2. 回執寫不進本機 → 文件仍 rev0、`dirty` 仍 true、outbox 沒清；
3. `pushOutbox` 仍回 `{ pushed:1, conflicts:0, failed:0 }`；
4. 下一次保存送出 `expectedRevision 0` → 409 → `{ pushed:0, conflicts:1 }`，遠端永遠停在第一次正文。

### 2.2 修正

`modules/article-store.js`

| 位置 | 內容 |
| --- | --- |
| `:2357-2433` `fallbackApplyReceipts()` | 後備桶內的單筆／批次回執：一次讀出 docs／outbox／`generations`／state，用與交易內完全相同的規則（`effectiveStoredGeneration`、`matches`、`rebuilt`、`rebasePendingOutbox`、衝突清除），最後一次 `fallbackWrite()` 寫回；整段沒有 `await` |
| `:2435-2453` `applyFallbackReceipts()` | 寫入成功後才更新記憶體（`cacheDoc`、`loadedDocs`、`mergeRecordsIntoMemory`）、`meta.conflicts`、`dataEpoch`、`emitChange`；單筆回 `{ ok, stale }`，批次回 `{ ok, results }` |
| `:2456-2463` `markOpDone()` | `fallbackMode` 時走 `applyFallbackReceipts(..., { single:true })` |
| `:2571-2572` `markOpsDone()` | `fallbackMode` 時走 `applyFallbackReceipts(scope, list)` |
| `:2538-2540`、`:2648-2650` | 交易本身失敗時**不改寫**後備桶（文件與 outbox 都在 IndexedDB），直接回報錯誤讓呼叫端保留 outbox 重試，避免「找不到文件 → 誤判完成」 |

設計取捨：

- 確認失敗**不得**計為成功、也不記成衝突：`syncArticles` 仍回 `ok:true`，
  但 `pushed.failed` 增加、outbox 與 `dirty` 保留；下一輪 `POST` 會拿到
  `409 article_id_exists` 走冪等分支（內容相同）或 `PUT` 的同 mutation 冪等回應。
- 後備回執不會在「IDB 交易失敗」時偷寫後備桶：那會讓 IndexedDB 裡真正的
  outbox 永遠無法確認，卻回報成功。

## 6. 未完成項與仍存風險

1. **（既有缺口，未修）** `markOpFailed()` 經 `persistDocWithMeta()` 仍以呼叫端記憶體
   內容寫文件；上傳失敗若發生在本機剛保存新正文之後，正文可能被覆回舊內容
   （代際／版本不倒退，但正文可能是舊的）。本輪未動這條路徑。
2. **（既有缺口，未修）** 開庫失敗仍會鎖住後備模式的部分路徑：`applyRemoteDocs()`
   遇到 `idb_unavailable` 直接回錯（不切後備），因此若首次開庫失敗但
   `fallbackMode` 尚未成立，下載／核對可能整輪失敗；`markOpDone`／`markOpsDone`
   本輪刻意**不**在交易失敗時改寫後備桶（避免「後備桶沒有文件 → 誤判完成」），
   而是回報失敗保留 outbox。
3. **（既有行為，未擴大處理）** `restoreArticle()` 在遠端已不存在時仍送 `/restore`，
   伺服器 404 會變成衝突（`pushOne()` 只對 `update` 的 404 走重建）。本輪只保證
   還原後的代際屏障正確；墓碑後用備份「覆蓋還原」（`importDocuments(..., {replace:true})`）
   仍以 `update` 送出，遠端是 tombstone 時會走既有衝突流程。
4. **ledger 長期容量**：`article_generations` 每篇「曾被重建／被遠端移除／被遠端墓碑」
   的 ID 留一列，不會回收。本輪只保證同一墓碑重複送達不推進（`alreadyDeleted`）；
   已同步 tombstone 被永久清除後再由完整 pull 移除時仍會 +1，長期仍隨文章 ID 數成長。
5. **`missing` 墓碑不推進代際**：本機完全沒有該文件時不寫 ledger（避免 delta 重送
   灌高代際）。若某個分頁在「文件已被移除但 ledger 尚未推進」的極端時序下收到
   delta 墓碑，屏障仍由先前的完整 pull 移除負責；這是刻意的取捨。
6. **localStorage 後備的跨分頁原子性**：`fallbackApplyTombstones()`、
   `fallbackApplyReceipts()` 的讀改寫中間沒有 `await`，屬既有後備模型限制；
   兩個分頁在同一個事件迴圈切片外的極端交錯仍可能覆蓋，與其他後備寫入
   （`fallbackDocWrite`、outbox）風險相同。
7. **未跑 Playwright 巡檢**：本輪改動集中在 IndexedDB 交易、後備桶與同步回執，
   已用 fake IndexedDB＋雙實例＋真實 mock Worker 流程覆蓋；依約束只執行 node
   測試與 i18n 檢查。
