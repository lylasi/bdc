## 八、發現的問題（分級）

### P2（需在後續工作中處理，非本次阻斷）

1. **`ALLOW_ORIGIN=*` 仍是萬用字元**：本次只證明「沒有放寬」（前後逐欄相同），並沒有收緊。配合擴充套件的 `host_permissions`，CORS 在擴充套件情境下不構成來源邊界（本代理實測 4 個請求皆無 `Origin` 標頭）。建議後續文件／驗收不要把「擴充套件來源 200」寫成 CORS 驗證通過；若日後把 `ALLOW_ORIGIN` 收緊為具體清單，必須同時把 `chrome-extension://<id>` 納入（或改走 Worker 代理），否則擴充套件會即時失效——此風險尚未驗證。
2. **`--keep-vars` 只有間接證據**：`deploy-worker.txt` 未記錄命令列與旗標。目前靠「3 個 `secret_text` 綁定保留」＋「`passwordLogin: true`」實質證明密鑰未掉，建議把部署命令（或 `wrangler deploy --keep-vars --dry-run` 摘要）一併落盤。
3. **寫入路徑完全未測**：帳戶 E2E 全程只發 GET／OPTIONS。同步寫入（`POST /snapshot`、`/ai-credentials`、文章與閱讀資料）在正式服務上仍屬未驗證區。
4. **清理腳本的自檢只看 `users`**：子表殘留要另行查詢才發現（我已補做，結果為 0）。建議 `run-live-smoke.py` 的 `verify-cleanup` 改成同時計數子表，並把計數寫進 `fixture-cleanup.json`。
5. **清理失敗時 token 檔會殘留**：`temp` 目錄只在 `cleanupOk` 為真時刪除，`fixture.json`（內含 token，權限 600）在清理失敗情境下會留在暫存目錄。建議改為 `finally` 內無條件刪除檔案，僅把清理成敗另存紀錄。
