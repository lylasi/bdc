## 二、測試方式（真元件，無 SQL 鏡像）

每個測試各自建立 `node:sqlite` `:memory:` 資料庫、載入 `cloudflare-worker/schema.sql`（含 `vocabulary_capture_settings`）、以 `selfhost/d1-adapter.js` 接上**真正的** `worker.fetch`。請求一律走公開 HTTP 介面（`POST/GET /vocabulary/books`、`PUT /vocabulary/default`、`POST /captures`、`POST /articles`、`PUT/DELETE /articles/:id`、`POST /articles/import`、`POST /reading/mutations`、`GET /reading/changes`），只用 SQL 做「事前 fixture」與「事後事實核對」。

已覆蓋（對應使用者交辦清單）：

1. 授權與帳戶隔離（401／403、清單與預設互不洩漏、不能設定他人書為預設）
2. 建書／換 default／刪 default 後無預選；`makeDefault` 只在要求時改動
3. page 與 custom 差異（URL 穩定 ID、沿用本頁既有書不覆寫名稱、custom 由 requestId 派生）
4. 重播逐欄回原回執、改 body 409、刪書重播不復活、並行同 URL 冪等（恰好一筆 created）
5. 無效字串長度／requestId 字元／網址（`javascript:`、含帳密、`file:`、`ftp:`、相對路徑、>2048）皆於寫入前拒絕，邊界值可接受

## 三、確定的失敗（4 項）

### F1（嚴重度：中）舊版「網址文章」關聯會寫入儲存 ID，不是公開 ID

- 測試：`tests/extension-page-workspace-deepseek.test.mjs:575`「舊版網址文章（url: 公開 ID）關聯時應使用公開 ID，而不是產生的儲存 ID」
- 重現：`POST /articles/import` 匯入 `legacyId = 'url:https%3A%2F%2F…'`（舊網址文章，`isValidArticleReference` 允許的公開身份）→ 再建同頁詞書 → 書上的 `articleId` 是 `art_mw4…`（`articles.id`），而 `GET /articles` 對外id 是 `url:https%3A…`，另有 `storageId`。
- 影響：`shared/article-protocol.mjs:273-279` 已明寫「舊 ID 是閱讀條目、詞書與會話的外鍵，匯入時產生的新 ID 只用於 SQL 儲存，不可取代公開身份，否則原本的關聯失效」；`docs/plan/20261106133310562…` 第 18 行也要求「以有效文章身份建立關聯」。目前所有以 `url:` 為公開 ID 的既有文章，其「同頁自動關聯」在主站查表時都會對不上（前端文章清單以公開 `id` 為鍵）。
- 根因：`cloudflare-worker/src/page-links.js:7-8` 只 `SELECT id, source_url, title` 並回傳 `row.id`；`captures.js:44-47` 與 `capture-books.js:39-42` 都直接沿用這個 `id`。
- 建議修法：`findPageArticle` 改回傳 `legacy_article_id || id`（與 `toArticleMeta` 一致），或在呼叫端以 `toArticleMeta` 取值。

### F2（嚴重度：中）文章關聯失敗時 `worker.fetch` 直接 reject，沒有 JSON 500

- 測試：`…:767`「關聯失敗時應回 JSON 500，不得讓 worker.fetch 直接 reject」
- 重現：建頁書 → 對 `reading_changes` 建 trigger `RAISE(ABORT)` → `POST /articles`（帶 `clientMutationId`）→ 測試端 `await worker.fetch(...)` **拋出 `Error: test link failure`**，而不是 `{status:500, code:'internal_error'}`。
- 影響：正式環境會變成沒有 JSON 封套的 500，`console.error('[bdc-sync] route failed')` 也不會執行（可觀測性同時失效）；客戶端無法依 `code` 判斷可否重試。
- 根因：`cloudflare-worker/src/worker.js:512`（同型：`/reading`、`/ai-credentials`、`/admin`、`/ai-catalog`）在 `try` 內 **`return handleArticlesRoute({…})` 但沒有 `await`**，async 例外不會被同層 `catch` 接住。既有 `POST /articles` 送壞 JSON 也會直接 reject（已另外實測），本次關聯掛鉤讓「成功建立文章」也能走到這條路徑。
- 另一併發事實（測試 `…:779` 通過）：關聯失敗不會留下半套資料，文章交易已提交、書的 revision 未動、`reading_changes` 只有建書那一筆；移除 trigger 後同 `clientMutationId` 重試會回 200 idempotent 並補上關聯。

### F3（嚴重度：中低）非法 `sourceUrl` 查詢會把「沒有網址的書」誤報成本頁書

- 測試：`…:831`「非法 sourceUrl 查詢不得把無網址的書當成本頁書」
- 重現：建一本 custom 書（無 `sourceUrl`）→ `GET /vocabulary/books?sourceUrl=not%20a%20url`（或 `javascript:alert(1)`、` /relative`、含帳密 URL）→ 回 `pageBookId = webbook_f0a7…`（那本 custom 書），`articleId = ''`。
- 影響：只要呼叫端傳入非絕對 http(s) 網址，伺服器就會把「任一本無網址的書」指定為本頁書；擴充套件若信任此欄位就會把詞收藏到錯誤的書。目前 `shared/workspace-client.mjs` 會先自行 `pageUrlKey` 驗證才呼叫，所以現階段尚未爆，但這是伺服器契約層的錯誤預選。
- 根因：`cloudflare-worker/src/captures.js:46` 對兩側都呼叫 `pageUrlKey`，非法值一律變成 `''`，於是 `'' === ''` 成立。
- 建議修法：`pageUrlKey(sourceUrl)` 為空時直接回 `pageBookId: ''`。

### F4（嚴重度：低）`GET /vocabulary/default` 回 400 `bad_json`，而非 405

- 測試：`…:506`
- 重現：帶 Bearer 的 `GET /vocabulary/default`（無 body）→ `400 {"code":"bad_json"}`。
- 根因：`cloudflare-worker/src/capture-books.js:84` 先 `readJsonBody`（空 body 即 `bad_json`）才在 `:85-96` 判斷 method/path；`POST /vocabulary/default`（帶 `{}`）仍是 405，只有無 body 的請求會誤報「JSON 壞掉」。
- 影響：僅錯誤碼語意與除錯噪音，不影響資料。

## 四、疑點（已在測試中斷言「現況」，需產品決策，不算失敗）

1. **刪除頁書後無法重建（`…:370`，建議嚴重度：中）**：頁書 ID 由正規化網址決定，軟刪除留下墓碑後，新的 requestId 再建同 URL 頁書會得到 `404 capture_target_missing`（`capture-books.js:32-37`）。使用者在主站刪掉本頁詞書後，再從擴充套件收藏會直接失敗；custom 書換新 requestId 則可重建。若要支援「重新建立本頁詞書」，需明確定義是復活墓碑（帶現行 revision 的 upsert）或改 ID 策略。
2. **custom 書帶同網址時會被當成頁書沿用（`…:231`）**：`kind:'custom'` + `sourceUrl` 之後，`pageBookId` 會指向它，且 page 建書沿用（名稱保持 custom 的命名）。若產品希望「頁書」是獨立類別，需在資料模型補 `kind` 欄位。
3. **`makeDefault:false` 時回執的 `defaultBookId` 是 `''`（`…:273`）**：不是目前實際預設；客戶端若把回執當成「現在預設」會誤清。建議回傳實際生效值。
4. **`kind` 未知值一律當 custom、`makeDefault` 非 `true` 一律 false（`…:487`）**：缺少嚴格枚舉／型別檢查，錯誤請求會靜默降級成 custom。
5. **文章刪除後書上的 `articleId` 不清除（`…:699`）**：`GET ?sourceUrl` 的 `articleId` 已是 `''`（正確），但 `books[].articleId` 仍指向已刪文章；前端若用書上的值顯示「已關聯文章」會導向 404。`POST /articles/:id/restore` 亦不會補回關聯（若當初未關聯）。
6. **`/vocabulary/books` 無速率限制、書的數量無上限**：`/captures` 有 120/分鐘，建書端點沒有；reading 層也沒有實體數量上限，`custom` 書可用新 requestId 無限建立（每本一列 + 一筆 change）。
