## 四、C4／E3：已修正（node 套件）

### 1. C4（改寫）本機錯誤跳過、續送健康項

以**明確不同**的 `createdAt`（`2026-11-01T00:00:00`～`00:00:04`）排出「三筆壞記錄在前、兩筆健康項在後」，不依賴同一毫秒內的 UUID 次序：

| 記錄 | 觸發 | 預期 |
| --- | --- | --- |
| 結構損壞（缺 `requestId`／`endpoint`／`userId`） | `pending()` 標 invalid | `capture_invalid_record`，略過 |
| 舊版壞網址 `javascript:alert(1)`（結構合法） | `send()` 的 `pageUrlKey` 為空 | `capture_invalid_input`，略過、不發請求 |
| 詞書回執 `requestId` 不符 | 回執驗證 | `capture_invalid_response`，略過 |
| 兩筆健康頁書（不同網址） | 正常建書 | 都成功、都清待傳 |

斷言：`retry()` 依序處理 5 筆、三筆壞記錄全部保留（只能手動取消）、兩本健康書都建立、壞網址沒有被送到伺服器。

### 2. C4b（新增）網路中斷與 429／5xx 仍會停止

交辦要求「網路／401／429／5xx 仍停止」必須同時守住，否則就成了無條件續送。以三個獨立世界驗證 `network`（連線就失敗、無 status）、`429`、`503` 都在第一筆停住：只處理 1 筆、兩筆待傳都保留、第二筆完全沒有送出。（401 由既有 `C7` 覆蓋。）

### 3. E3（改寫）pending 依 createdAt 排序

- 兩筆入列次序與時間次序刻意相反、時間明確不同 → `pending()` 回 `[較早, 較晚]`，證明不是 storage 鍵序／入列次序；
- 另兩筆同 `createdAt` → 依 key 排序，且同一份 storage 連讀兩次結果一致（穩定）；
- `retry()` 用同一順序送出：時間最早的文章先送（`GET ?sourceUrl` → `POST /articles` → `page-link`），再依 key 送三筆同時間的頁書；同頁詞書在文章建立後被關聯到該文章。

### 4. 其餘 node 測試

原有 34 項全部保留（A1–A4、B1–B6、C1–C3、C5–C8、D1–D11、E1、E2、E4、E5），加上 1 項新回歸 `C4b` → **35 項**。其中包含文章入列驗證（`D6`）、墓碑 slot 重建（`D10`）、有效回執才清 pending（`C5`–`C8`）、回應遺失後不覆蓋（`D4`）、取消不刪雲端（`E2`）、ledger 冪等（`E5`）。
