# AI 供應商設定同步 — 部署與遷移指南

首次上線請依序使用 [逐步部署手冊](20261018025155000_AI供應商逐步部署與維護手冊.md)，該手冊補充帳戶 SQL 實際套用、全新／既有資料庫分支、發布副本與首次管理介面的啟用順序。

- 方案：`docs/plan/20261017130932086_D1按使用者同步AI供應商設定完整方案.md`
- 實作報告：`docs/report/20261017174843744_按使用者同步AI供應商設定實作報告.md`
- 適用版本：本次工作區變更（前端 + `cloudflare-worker/`）

> 本次只交付可部署程式、migration 與設定範例；**沒有**部署正式 Worker、修改正式 D1、建立真實共享 Key 或撤銷任何供應商 Key。以下步驟需由部署者執行。

## 1. 部署前檢查

1. 確認 `cloudflare-worker/wrangler.toml` 指向正確的 D1（此檔已被 `.gitignore` 忽略）。
2. 確認前端 `ai-config.js` 的 `SYNC.endpoint` 指向同一個 Worker。
3. 準備兩個獨立隨機秘密（不要寫進 Git 或前端）：
   - `AI_CREDENTIAL_KEY_V1`：AES-256-GCM 主密鑰（32 bytes）。
   - `AI_CATALOG_DIGEST_KEY`：發布請求 HMAC 秘密，與主密鑰分開保管。
4. 選定前端 origin 清單（例如 `https://bdc.example.com`）。

## 2. 備份 D1

```bash
cd cloudflare-worker
mkdir -p ~/bdc-d1-backups
npx wrangler d1 export bdc-sync --remote \
  --output ~/bdc-d1-backups/bdc-sync-$(date +%Y%m%d%H%M%S).sql
```

同時把目前使用中的 Worker Secret 版本清單記錄在安全位置。**只有密文備份無法還原 Key**。

## 3. 套用 migration

```bash
npx wrangler d1 execute bdc-sync --remote \
  --file ./migrations/001_ai_provider_sync.sql
```

- 新增 `users.role`、`user_ai_credentials`、`ai_default_catalog_releases`。
- 這個 migration 只執行一次；重跑會因 `role` 欄位已存在而失敗，屬預期行為。
- 全新資料庫可直接用 `schema.sql`。

## 4. 設定秘密與第一個管理員

先用 `npx wrangler secret list` 核對。以下只適用於尚未設定的秘密：分別產生兩個不同的 32-byte 隨機值，保存到密碼管理器，再輸入提示框。已有秘密與使用中的版本必須保留，不可為重跑部署覆蓋主密鑰。

```bash
npx wrangler secret put AI_CREDENTIAL_KEY_V1
npx wrangler secret put AI_CATALOG_DIGEST_KEY
```

可用 `openssl rand -base64 32` 產生每個隨機值。`secret put` 會部署 Worker 版本；完整備份及環境選擇見逐步部署手冊。

在 `wrangler.toml` 設定：

```toml
[vars]
ALLOWED_ORIGINS = "https://bdc.example.com"
AI_CREDENTIAL_KEY_VERSION = "1"
```

> `ALLOWED_ORIGINS` 可用逗號分隔多個完整 origin。舊的 `ALLOW_ORIGIN` 只在未設定 `ALLOWED_ORIGINS` 時使用；正式環境不要用 `*`。

指定首名管理員（先確認 `user_id`）：

```bash
npx wrangler d1 execute bdc-sync --remote \
  --command "UPDATE users SET role='admin' WHERE user_id='<confirmed-user-id>';"
```

後續角色調整同樣由部署者執行 SQL；沒有公開升級角色的 API。

### 既有帳戶的通行碼

- 憑證與預設 Key 介面要求通行碼至少 32 字元；舊通行碼會收到 `403 passcode_upgrade_required`。
- 學習資料同步仍接受舊通行碼，讓使用者先登入後自行更新。
- 重設／建立使用者：

```bash
node add-user.mjs <user_id> [label]
node add-user.mjs --admin <user_id> [label]
```

工具會自動產生 43 字元隨機通行碼；`ON CONFLICT` 不會提升或清除既有角色。它只輸出 SQL，還須將 SQL 保存到網站外的私密檔案並以 `wrangler d1 execute --remote --file` 套用，詳見逐步部署手冊第 4 節。

## 5. 部署 Worker

```bash
npx wrangler deploy
```

部署後快速檢查（需要一個 ≥32 字元測試通行碼）：

```bash
curl -s https://<worker>/me -H "Authorization: Bearer <passcode>"
# → {"user_id":"...","label":"...","role":"user"|"admin"}
```

未登入存取 `/ai-catalog` 應回 401；管理員以外存取 `/admin/ai-catalog` 應回 403。

## 6. 發布第一版預設供應商列表

本節需要新版管理介面。首次上線先完成第 7 節的配置整理、掃描與前端部署，再回到本節；或先在允許的測試 origin 使用新版前端發布列表。

1. 管理員登入 BDC → 設定 →「管理預設供應商」。
2. 按「新增預設供應商」：只需填「服務地址 + API Key」（無需金鑰的局域網服務可留空），按「連接」。系統會用已實作的適配器自動辨識協議並取得模型；也可在「進階設定」手動覆寫協議／端點／認證方式，或直接手動加入模型名稱（辨識失敗不等於服務不可用）。
3. 連接成功後，模型只是**候選**，全部預設不勾選。逐個勾選要對全站開放的模型（不要一次開放全部），再按「加入草稿」。
4. 為各任務選擇模型；已開放的模型會保留其能力標記，重新「取得模型」不會清空或自動擴大已開放清單。
5. 需要測試時，在該供應商的「進階設定」填「臨時測試密鑰」（只留在本頁記憶體，不會發布），再按「測試模型」；這會產生一次供應商費用。保留的舊 Key 不會回顯，需重新輸入才能測試。
6. 按「發布更改」，伺服器建立不可變版本 1。單一供應商測試或取得模型失敗只顯示該供應商的錯誤，不影響其他供應商與發布。
7. 用一般使用者帳號登入，確認可選擇預設供應商；未登入時應顯示登入提示且無法取得共享 Key。

## 7. 前端靜態設定整理與部署（順序已修正）

> 這一節的順序是強制性的：**先確認要發布的靜態產物已不含任何預設供應商網址／模型／共享 Key，才部署前端。** 先部署前端再遷移，會讓舊的靜態共享 Key 繼續對外提供（CDN 與瀏覽器快取亦會保留），與「移除靜態 AI 預設」的目標相反。

### 7.1 在受控環境完成靜態設定整理（尚未對外發布）

1. 備份目前網站根目錄（含 `ai-config.js`）到網站根目錄之外的安全位置。
2. 先看差異，不寫入任何檔案：

```bash
node scripts/migrate-ai-config.mjs --dry-run
```

3. 確認 TTS／`SYNC.endpoint`／限流／文章抓取／QA-OCR 參數仍正確後，在**要發布的副本**上執行：

```bash
node scripts/migrate-ai-config.mjs
```

    腳本會：
    - 在**網站根目錄之外**產生私密匯入檔 `../bdc-ai-config-import-<timestamp>.json`（0600）。
    - 在網站根目錄之外備份原始 `ai-config.js`（0600）。
    - 把 `ai-config.js` 改寫成只含 TTS、同步端點、限流、文章抓取與 QA/OCR 參數的版本。
    - 不把任何 Key 印到終端機。

4. 執行靜態產物檢查（不會印出任何金鑰內容，只報檔名、行號與問題類型）：

```bash
# 檢查專案根目錄的 ai-config.js 與根目錄 HTML
node scripts/check-ai-static-config.mjs

# 建議：直接檢查真正要上傳的發布目錄
node scripts/check-ai-static-config.mjs --dir ../dist --deep
```

    必須得到「沒有發現靜態 AI 供應商網址、模型映射或金鑰」（exit 0）才可繼續。若仍列出 `legacy-ai-export:*`、`inline-api-key-literal` 或 `provider-key-prefix`，表示遷移尚未完成，**不要部署**。

    結束碼語意（exit 2 一律視為「沒有檢查完成」，不可當作通過）：

    | 結束碼 | 意義 |
    | --- | --- |
    | 0 | 實際掃描過，沒有發現問題 |
    | 1 | 有發現項目，列出檔名、行號與類型（不印出任何值） |
    | 2 | 掃描失敗：目錄不存在／不可讀、目標不是目錄、stdin 為空、目錄內沒有符合條件的檔案，或讀檔、列目錄失敗 |

5. 保存第 3 步的私密 JSON。新版前端可用後，到「管理預設供應商」→「匯入舊版 ai-config.js」選擇該 JSON；逐項核對端點與模型後才發布（見第 6 節）。

### 7.2 部署不含靜態 AI 預設的前端

1. 只上傳通過 7.1 第 4 步檢查的產物（含 `modules/ai-profile-storage.js`、`ai-catalog.js`、`ai-credential-sync.js`、`ai-protocols/`、`features/ai-admin/`）。
2. 清理 CDN 與瀏覽器快取，確認線上 `ai-config.js` 已是不含 AI 網址／Key 的版本：

```bash
# 建議：先下載到暫存目錄，再用 --dir 檢查該目錄（保留檔名 ai-config.js，
# 才會套用 legacy AI 匯出檢查）。curl -f 讓 4xx/5xx 直接失敗，避免把錯誤頁當成設定檔。
(
  bdc_check_dir="$(mktemp -d)" || exit "$?"
  trap 'bdc_check_status=$?; trap - EXIT; rm -rf -- "$bdc_check_dir"; exit "$bdc_check_status"' EXIT
  curl -fsS "https://<site>/ai-config.js" -o "$bdc_check_dir/ai-config.js" || exit "$?"
  test -s "$bdc_check_dir/ai-config.js" || exit 2
  node scripts/check-ai-static-config.mjs --dir "$bdc_check_dir"
)
```

```bash
# 或用 stdin 管道（--stdin 與 --dir - / --dir /dev/stdin 等價，--name 只影響報告顯示）
(
  set -o pipefail
  curl -fsS "https://<site>/ai-config.js" \
    | node scripts/check-ai-static-config.mjs --stdin --name ai-config.js
)
```

    請在專案根目錄以 Bash 或 Zsh 執行，整段退出碼為 0 才算通過。暫存版保留下載／掃描退出碼，清理不會覆蓋它；管道版以 pipefail 保留下載失敗。掃描器的 1／2 及 curl 的其他非零碼都代表未通過。這是靜態文字檢查，不能判斷所有 HTTP 200 錯誤頁；另須確認網址回傳真正的 JavaScript 設定，且瀏覽器可載入該模組。

3. **不要直接封鎖 `/ai-config.js`。** 前端仍以 ESM 靜態匯入它（`modules/ai-profile-storage.js`、`modules/sync-cloudflare.js` 等 `import { ... } from '../ai-config.js'`）；整檔封鎖會讓模組載入失敗，整個應用（含 TTS、學習資料同步）都無法啟動。可行做法：
   - **建議**：保留 `/ai-config.js`，但確保它只含非 AI 設定（7.1 已產生），並用第 4 步的檢查持續把關。
   - 若資安政策要求不可公開該檔：改成在部署流程以樣板產生 `ai-config.js`（內容仍是非秘密設定），或改為伺服器注入 `window.__BDC_CONFIG__` 再由載入器讀取——後者需要程式修改與回歸驗收，不能只加一條封鎖規則。
   - 其他路徑（`/cloudflare-worker/`、`/docs/`、`.git`、`.env` 等）可直接封鎖，前端不依賴它們。
4. 到供應商控制台**撤銷／更換舊的共享 Key**；只刪除檔案不能收回已下載到瀏覽器的 Key。此步驟完成後，第 9 節的驗收才算具備條件。


## 8. 使用者遷移

- 第一次載入新版前端時，`pen_global_settings.ai`／`pen_global_secrets.aiProviders` 會一次性遷移到「此裝置」AI profile：
  - 只遷移非 `default`、有使用者 Key 的供應商。
  - 遷移後的供應商預設**停用**，需使用者確認後啟用。
  - 遷移的 Key 標記為 `local-only`，不會自動上傳。
  - 舊 `default`／`aiApiKey` 只留下隔離紀錄，不複製 Key，亦不恢復共享 Key 回退。
  - 只有新 profile 寫入並讀回成功後，才刪除舊 AI 秘密；失敗時保留舊資料並提示。
- 已登入使用者可在「我的供應商」→「從此裝置匯入供應商」明確匯入，並可勾選「同時同步金鑰到我的帳號」。

## 9. 上線驗收（最少）

| 項目 | 預期 |
| --- | --- |
| 未登入 | 預設供應商鎖定；可新增／使用自己的「此裝置」供應商；無共享 Key |
| 已登入一般使用者 | 可選用已發布模型；不能修改預設列表；可同步自己的 Key |
| 管理員 | 可發布／還原；一般使用者呼叫管理接口回 403 |
| 兩台裝置同時改同一 Key | 一台成功、另一台 409；UI 顯示衝突選項 |
| 上傳後回應遺失 | 同 mutationId 重試不增加版本 |
| 退出 | 清除該帳戶本機 AI profile／共享 Key／管理草稿；其他分頁同步失效 |
| 401 | 保留個人 Key；清除共享 Key；停止同步並要求重新登入 |
| 列表更新 | 舊 Key 被丟棄；版本不符回 409 並重取 |
| 45–60 分鐘後 | 共享 Key 清理，預設請求被阻止；個人供應商不受影響 |
| 全新裝置首次登入 | 套用快照後會下載已同步的個人 Key（憑證清單有列、本地沒有列時），狀態顯示已同步；binding 不符則不下載、不改用他人 Key |
| 網路等待期間保存供應商／換 Key／刪除／改任務模型 | 同步完成後都不會被舊的整份 profile 覆寫；新草稿保留，換 Key 會接續成新的上傳 |
| 舊帳戶延遲 401（含跨分頁、直接換帳戶） | 不會登出目前帳戶；只有屬於目前工作階段的 401 才結束登入 |
| 直接切換帳戶（未先登出） | 立即鎖定預設供應商、清除共享 Key 與有效期；新帳戶驗證成功前不可用，舊請求結果被丟棄 |
| 管理員取得模型 | 只更新候選清單，不擴大已開放模型；新模型預設不勾選；發布只含明確勾選的集合，能力標記保留 |
| 管理員新增供應商 | 只有服務地址與 API Key 兩欄；協議自動辨識（可用進階覆寫）；模型需明確勾選才加入草稿；無 Key 的局域網服務可用 |
| 舊版任務模型映射 | 遷移後 profile.taskModels 保留指向已遷移個人供應商的選擇；managed／`default` 引用不匯入；確認寫入後才移除舊欄位 |
| zh-CN / zh-HK | 草稿、測試、發布、衝突、錯誤狀態都有翻譯（含新增供應商表單與候選模型清單） |

## 10. 回退與輪換

- 前端可回退到「含新儲存與登入門檻」的相容版本；**不得**恢復含靜態共享 Key 的舊部署。
- 預設列表可從歷史版本載入後重新發布；歷史 Key 不可下載，需要重新輸入。
- 主密鑰輪換：
  1. 新增 `AI_CREDENTIAL_KEY_V2`，保留 V1。
  2. 把 `AI_CREDENTIAL_KEY_VERSION` 改為 `2`（新寫入用 V2）。
  3. 以舊 key version 解密、V2 重新加密，更新時保留業務 version 條件。
  4. 核對仍需 V1 的記錄與備份後，再按政策淘汰 V1。
- 摘要密鑰可獨立輪換；`request_digest` 以 `v1:` 前綴記錄格式。
- 若 D1 還原到舊備份，本機偵測版本倒退會停止自動覆寫（`remote_version_rollback`），核對來源後再重建基準。

## 11. 已知限制（必須向使用者說明）

- 瀏覽器直連供應商：已登入使用者取得共享 Key 後可以複製；本方案**不提供**供應商端強制登入或逐人限額。緊急撤銷必須到供應商控制台換 Key。
- 共享 Key 只在頁面記憶體，最長 60 分鐘；過期後需重新驗證。
- 個人供應商在登入失效（401）後仍可使用本機 Key；共享預設會鎖定。
- Worker 限流是單一 isolate 的盡力而為，不是全域配額；供應商端限額仍應在控制台設定。
- 靜態主機仍會提供 `ai-config.js` 的 TTS／同步設定；不要把任何 AI Key 留在這個檔案。
- 本機 8414 的 `python3 -m http.server` 在大量並行模組請求下會出現連線重置；請用 `scripts/serve.py` 做瀏覽器巡檢。
