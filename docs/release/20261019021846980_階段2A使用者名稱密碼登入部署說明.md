## 2. 部署前準備

1. 確認 `cloudflare-worker/wrangler.toml` 的 `database_id`、`ALLOWED_ORIGINS` 正確。
2. 備份 D1：

   ```bash
   cd cloudflare-worker
   npx wrangler d1 export bdc-sync --remote --output backup-$(date +%Y%m%d-%H%M).sql
   ```

3. 確認 Wrangler 已登入，且目前操作的是正式帳號：

   ```bash
   npx wrangler whoami
   ```

4. 產生 `PASSWORD_PEPPER`（至少 32 字元），先保存到密碼管理器：

   ```bash
   openssl rand -base64 48
   ```

   > 這個值只存在 Worker secret，**不要**寫入 `wrangler.toml`、`ai-config.js`、D1 或任何提交檔案。遺失 pepper 後，所有已設定密碼都無法驗證，只能由管理員逐一重設。

## 3. 部署順序

先套用 migration，再設定 secret，最後才部署 Worker 與前端。舊 Worker 會忽略新欄位，因此 migration 可安全先行。

### 3.1 套用 D1 migration

```bash
cd cloudflare-worker

# 若正式資料庫尚未套用 004，先補上
npx wrangler d1 execute bdc-sync --remote --file ./migrations/004_article_storage.sql

npx wrangler d1 execute bdc-sync --remote --file ./migrations/005_username_password.sql
```

驗證欄位：

```bash
npx wrangler d1 execute bdc-sync --remote \
  --command "PRAGMA table_info(users);"
npx wrangler d1 execute bdc-sync --remote \
  --command "PRAGMA table_info(user_sessions);"
```

預期 `users` 含 `username`、`username_normalized`、`password_hash`、`password_updated_at`、`auth_version`、`is_active`；`user_sessions` 含 `auth_version`。

### 3.2 設定 Worker secret

```bash
npx wrangler secret list
npx wrangler secret put PASSWORD_PEPPER
```

`PASSWORD_PEPPER` 少於 32 字元時，`/auth-capabilities` 會回報 `passwordLogin: false`，前端不會顯示密碼登入分頁。

### 3.3 部署 Worker

```bash
npx wrangler deploy
```

### 3.4 部署前端

依現有流程發布靜態檔案（`git push` 後由正式站 pull，或既有部署方式）。前端先上線不會壞：舊 Worker 的 `/auth-capabilities` 沒有 `passwordLogin` 時，前端會自動隱藏密碼分頁。

## 4. 部署後驗證清單

### 4.1 能力與舊登入回歸

- [ ] `GET https://<worker>/auth-capabilities` 回傳 `passwordLogin: true`、`passwordMinLength: 10`、`adminPasswordMinLength: 12`。
- [ ] 既有通行碼登入仍可取得 `/me`。
- [ ] 既有一次性登入碼（`#login=CODE`）仍可自動登入，且 fragment 會被清除。
- [ ] 既有已配對裝置未被登出（migration 後 `auth_version` 預設同為 1）。

### 4.2 管理員設定憑證

- [ ] 管理員 → 設定 → 工具 → 用戶管理 → 編輯使用者，填入使用者名稱與新密碼。
- [ ] 列表顯示 `@username` 與「已設密碼」。
- [ ] 管理員可為自己設定使用者名稱與 12 字元以上的密碼；原本 32 字元通行碼仍可使用。

### 4.3 使用者名稱＋密碼登入

- [ ] 主站登入彈窗預設顯示「使用者名稱密碼」分頁。
- [ ] 正確帳密可登入並保存 session。
- [ ] 錯誤帳密顯示「使用者名稱或密碼不正確」，不泄露帳戶是否存在。
- [ ] 停用帳戶的正確密碼回 `account_disabled`。
- [ ] 連續錯誤達到限流後顯示「嘗試次數過多」，`Retry-After` 有值。

### 4.4 修改密碼與撤銷

- [ ] 使用者登入後，齒輪選單可看到「修改密碼」。
- [ ] 修改成功後，目前裝置仍保持登入。
- [ ] 同一帳戶的其他裝置在下一次請求時被登出。
- [ ] 管理員重設該使用者密碼後，該使用者所有 session 立即失效。
- [ ] 重設通行碼後，密碼登入仍可用，但舊 session 全部失效。

### 4.5 雙語

- [ ] `zh-CN` 與 `zh-HK` 下登入分頁、錯誤訊息、管理員表單、修改密碼彈窗文案完整。
- [ ] 切換語言不影響使用者名稱、密碼輸入或既有資料。

## 5. 回復方式

- **只回復 Worker**：重新部署上一版 Worker。migration 新增欄位不影響舊程式。
- **回復 migration**：D1 不支援直接刪除欄位；如需完全回到舊 schema，使用部署前備份還原整個資料庫。
- **pepper 遺失**：無法回復舊密碼雜湊。處理方式是由管理員為每個帳戶重新設定密碼；通行碼與一次性登入碼不受影響。

## 6. Workers Free 注意事項

- PBKDF2 50,000 次＋HMAC pepper 的目標是控制在 Free 方案每個請求 10 ms CPU 之內；實際用量請在 Cloudflare 儀表板的 Worker 指標觀察 `CPU time`。
- 若登入請求出現 CPU 超限，先確認是否為冷啟動或大量併發；不要直接降低迭代次數，應改為評估 Workers Paid 或改用其他 KDF 方案。
- 限流是 isolate 記憶體內的最佳努力煞車，跨 isolate 不精確；家庭規模可接受，不作為安全邊界。

## 7. 已知限制

- 自助「忘記密碼」未實作；忘記密碼需由管理員在用戶管理重設。
- 使用者名稱一旦設定，只能由管理員修改。
- `selfhost/` 後端沒有 `/auth-capabilities` 與 `/login`；前端會自動隱藏密碼登入，僅保留該後端支援的登入方式。
- 本次未部署，也未變更任何正式環境設定。
