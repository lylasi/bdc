# AI 供應商逐步部署與維護手冊

日期：2026-10-18。適用於本次 BDC 原生 ES Modules 前端、Cloudflare Worker 與 D1。以下是部署者操作步驟；本輪只完成本機修正及驗證，尚未替你執行正式環境操作。

## 1. 部署順序與準備資料

按此順序操作：備份 → D1 結構 → 管理員與 Worker secrets → Worker → 整理前端發布副本 → 新版前端 → 管理員發布預設列表 → 一般使用者驗收 → 撤銷舊共享 Key。

首次上線時，舊前端未必有管理介面，因此本手冊先上新版前端，再由管理員發布第一版列表。此期間學習與個人供應商仍可用，預設列表尚未可用。若不接受這個短暫空窗，可在已加入 Worker origin 清單的測試站先開新版管理介面、發布列表，再切換正式前端。

準備下列資料（本手冊沒有假定你使用哪一間前端主機）：

| 項目 | 用途／範例 |
| --- | --- |
| 正式前端 origin | 例如 `https://bdc.example.com`，只有協議、域名與連接埠，不含路徑 |
| Worker 網址 | 例如 `https://bdc-sync-api.example.workers.dev`；部署結果為準 |
| D1 名稱與 ID | 範例名稱為 `bdc-sync`，既有服務沿用原資料庫 |
| Worker 名稱 | 既有服務沿用原名稱，不要意外建立第二個 Worker |
| 管理員 user_id | 已有帳戶可提升角色；新帳戶需真正套用產生的 SQL |
| 供應商 URL、Key、模型 | 首次發布用；支援協議為 OpenAI Chat Completions、Anthropic Messages、Gemini |

以下命令以同一個 **Bash** 終端逐段執行，每段成功再繼續。專案沒有 `npm run build`。先進入 Bash 並設定路徑：

```bash
bash
cd /Users/linus/CODE/bdc
bdc_repo="$PWD"
bdc_release_work="$HOME/bdc-release-work/$(date +%Y%m%d%H%M%S)"
bdc_private="$bdc_release_work/private"
umask 077
mkdir -p "$bdc_private"
```

`bdc_release_work` 必須位於網站公開根目錄之外。此目錄會保存資料庫備份、遷移備份及私密匯入檔；最後只發布其 `public` 子目錄。

## 2. 核對 Cloudflare 與本機設定

```bash
cd "$bdc_repo/cloudflare-worker"
npx wrangler --version
npx wrangler login
npx wrangler whoami
# 只有尚未存在設定檔時才複製，已有的不要覆蓋
test -f wrangler.toml || cp wrangler.toml.example wrangler.toml
```

編輯 `cloudflare-worker/wrangler.toml`，保留既有 routes／帳戶設定，核對以下欄位：

```toml
name = "bdc-sync-api"
main = "src/worker.js"
compatibility_date = "2026-01-01"

[vars]
ALLOWED_ORIGINS = "https://bdc.example.com"
AI_CREDENTIAL_KEY_VERSION = "1"

[[d1_databases]]
binding = "DB"
database_name = "bdc-sync"
database_id = "實際的資料庫 ID"
```

多個 origin 用逗號分隔；包括實際使用的自訂域名及測試 origin。不要填頁面路徑。若已有金鑰版本不是 1，保留現有版本，不照範例改回 1。此處假設未使用 Wrangler named environment；若有，所有遠端命令要一致指定同一個 `--env`，並核對該環境的 D1 綁定與 vars。

## 3. 備份及更新 D1（二選一）

**A：已有同步服務／已有使用者資料**

```bash
npx wrangler d1 info bdc-sync
npx wrangler d1 export bdc-sync --remote \
  --output "$bdc_private/bdc-sync-before-ai.sql"
npx wrangler d1 execute bdc-sync --remote \
  --command "PRAGMA table_info(users);"
npx wrangler d1 execute bdc-sync --remote \
  --command "SELECT name FROM sqlite_master WHERE type='table' ORDER BY name;"
```

確認備份成功。若 `users` 尚無 `role`，執行一次：

```bash
npx wrangler d1 execute bdc-sync --remote \
  --file ./migrations/001_ai_provider_sync.sql
```

若已有 `role`，而 `user_ai_credentials`、`ai_default_catalog_releases` 也存在，代表此結構已套用，跳過 migration。若只有部分結構存在，先按 `schema.sql` 核對缺項並處理中斷狀態；不要重跑含 `ALTER TABLE ... ADD COLUMN role` 的整份 migration。

**B：全新安裝，尚未有資料庫**

```bash
npx wrangler d1 create bdc-sync
# 將上一步回傳的 database_id 填入 wrangler.toml，再執行：
npx wrangler d1 execute bdc-sync --remote --file ./schema.sql
```

全新資料庫使用 `schema.sql` 後，不再執行 `001_ai_provider_sync.sql`。命令使用方式依 [Cloudflare D1 Wrangler 文件](https://developers.cloudflare.com/d1/wrangler-commands/) 核對。

## 4. 建立／提升管理員

**已有帳戶：只提升權限，不重設通行碼**

```bash
npx wrangler d1 execute bdc-sync --remote \
  --command "SELECT user_id, label, role FROM users;"
# 將下列 admin_user_id 換成剛核對的 user_id
npx wrangler d1 execute bdc-sync --remote \
  --command "UPDATE users SET role='admin' WHERE user_id='admin_user_id';"
npx wrangler d1 execute bdc-sync --remote \
  --command "SELECT user_id, role FROM users WHERE user_id='admin_user_id';"
```

最後必須得到正確的一列且 `role=admin`；UPDATE 沒有匹配帳戶並不會幫你建立帳戶。

**新帳戶，或舊通行碼不足 32 字元**

```bash
node add-user.mjs --admin admin_user_id '網站管理員' > "$bdc_private/admin-user.sql"
# 先將終端顯示的通行碼與恢復碼存入密碼管理器
npx wrangler d1 execute bdc-sync --remote --file "$bdc_private/admin-user.sql"
```

`add-user.mjs` 只產生 SQL，直到第二條命令成功才建立／更新遠端帳戶。通行碼是 43 字元隨機值。對既有 user_id 執行會重設通行碼與恢復碼，但不改 role；既有帳戶仍須用上面的 UPDATE 提升角色。一般使用者同樣可執行 `node add-user.mjs user_id '名稱'` 產生 SQL，再套用。AI 憑證介面要求至少 32 字元通行碼。

## 5. 設定 Worker secrets 並部署

```bash
npx wrangler secret list
```

需要 `AI_CREDENTIAL_KEY_V1`（或目前版本對應名稱）及 `AI_CATALOG_DIGEST_KEY`。已有並正在使用的值要保留；**不要為重跑部署而重新隨機生成同名主密鑰**，否則舊密文無法解開。

首次設定時，分別執行兩次 `openssl rand -base64 32`，將兩個不同結果存入密碼管理器，然後逐一輸入到提示框：

```bash
npx wrangler secret put AI_CREDENTIAL_KEY_V1
npx wrangler secret put AI_CATALOG_DIGEST_KEY
npx wrangler secret list
npx wrangler deploy
```

確認兩個 secret 名稱存在，記錄 Worker 部署版本與回傳網址。D1 備份還原需要保留對應版本主密鑰，不能只備份 SQL。`secret put` 本身也會建立並部署 Worker 版本；它已屬正式環境操作，詳見 [Cloudflare Secrets 文件](https://developers.cloudflare.com/workers/configuration/secrets/)。

設定實際網址後檢查未登入的回應及 CORS：

```bash
bdc_worker_url='https://實際的-worker-網址'
bdc_site_origin='https://實際的網站域名'
curl -sS -o /dev/null -w '%{http_code}\n' "$bdc_worker_url/ai-catalog"
# 預期 401
curl -sS -i -X OPTIONS "$bdc_worker_url/ai-catalog" \
  -H "Origin: $bdc_site_origin" \
  -H 'Access-Control-Request-Method: GET' \
  -H 'Access-Control-Request-Headers: Authorization'
```

預檢應成功，`Access-Control-Allow-Origin` 應等於前端 origin。登入後的角色與列表檢查在第 8、9 節完成。

## 6. 在私密副本整理前端，產生發布目錄

不直接改正在服務的網站目錄。從目前工作區複製完整開發副本（包含未提交但要發布的改動），排除工具及版本控制目錄：

```bash
mkdir -p "$bdc_release_work/source"
rsync -a --exclude='.git/' --exclude='node_modules/' --exclude='.wrangler/' \
  --exclude='.playwright-cli/' --exclude='.agents/' --exclude='.codex/' \
  --exclude='.aws/' "$bdc_repo/" "$bdc_release_work/source/"
cd "$bdc_release_work/source"
```

此開發副本及其父目錄都不能作為公開網站根目錄。如果尚無 `ai-config.js`，先從 `ai-config.example.js` 複製，再填非 AI 設定。有舊配置時，按順序執行：

```bash
node scripts/migrate-ai-config.mjs --dry-run
node scripts/migrate-ai-config.mjs
```

腳本依其自身位置處理副本內的 `ai-config.js`，保留 TTS／SYNC／非 AI 參數，產生私密匯入 JSON 與原始備份於 `bdc_release_work`。保存輸出的路徑，不把這些檔案放進 `public`。

編輯副本的 `ai-config.js`：確認 `SYNC.endpoint` 是第 5 節的 Worker URL，保留其餘 SYNC poll 參數及原本需要的非 AI 設定。AI 的 URL、Key、模型與任務映射改由管理介面維護。

接著只打包執行前端所需的檔案：

```bash
bdc_public="$bdc_release_work/public"
mkdir -p "$bdc_public"
cp index.html main.js styles.css phonetics.html ai-config.js \
  voices.json voices.min.json voices.fallback.json "$bdc_public/"
for bdc_asset_dir in modules features locales wordlists articles qa-sets phonetic-chart; do
  cp -R "$bdc_asset_dir" "$bdc_public/"
done
node scripts/check-ai-static-config.mjs --dir "$bdc_public" --deep
```

最後一條命令必須 exit 0。此清單已以公開設定樣板驗證，可掃描 186 個文字檔案而不誤攔協議辨識域名。**這不是對你真實發布配置的通過保證**；仍須對實際副本執行。若網站另有教材引用的自訂圖片、主機 `_headers`／`_redirects` 等檔案，將已核對的公開資源加入 `public` 後重掃。不要把 docs、tests、scripts、後端、SQL 備份、私密匯入 JSON 或整個專案直接發布。

檢查器是靜態文字檢查，不能替代確認非 AI 服務設定是否適合公開。

## 7. 上傳前端與核對線上設定

**使用現有靜態主機**：把 `public` 目錄內的檔案部署到原網站根目錄，保留所有子目錄結構。主機需支援 ES Modules 的 JavaScript MIME；`/ai-config.js` 必須仍可讀取。將不存在的 `.js` 路徑回傳首頁會導致模組載入失敗。

**若選用 Cloudflare Pages Direct Upload**：首次建立專案執行 `npx wrangler pages project create`；已有專案略過。由前端開發副本所在目錄部署：

```bash
npx wrangler pages deploy "$bdc_public" --project-name '實際的-Pages-專案名稱' --branch '實際的正式分支'
```

這是可選的前端託管方式，無需因後端使用 Cloudflare 就遷移既有網站。部署方式及分支規則見 [Cloudflare Pages Direct Upload 文件](https://developers.cloudflare.com/pages/get-started/direct-upload/)。

更新／清理主機 CDN 快取，再回到原專案根目錄，執行 [原指南第 7.2 節](20261017174843744_AI供應商設定同步部署與遷移指南.md#72-部署不含靜態-ai-預設的前端) 已修正的任一線上檢查命令，把 `https://<site>` 換成正式 origin。整段退出碼必須是 0；非零立即處理，不繼續當作已驗收。

另外用瀏覽器重新整理，確認 index、main、AI 模組及 `ai-config.js` 均正確載入，沒有 JavaScript MIME 或匯入錯誤。文字掃描不會判定所有 HTTP 200 錯誤頁，不能只看掃描 exit 0。

## 8. 發布第一版預設供應商列表

1. 以管理員新通行碼登入新版 BDC，開啟「設定 → 管理預設供應商」。若沒有入口，核對 `/me` 的 `role`、目前登入 user_id 及前端版本。
2. 可選「匯入舊版 ai-config.js」，讀取第 6 節在本機產生的私密 JSON，核對 URL、模型及任務選擇。也可直接新增供應商，只填服務地址與 API Key。
3. 按「連接」辨識協議及取得模型；手動協議／端點／認證方式位於進階設定。無 Key 的局域網服務選相應認證方式。
4. 模型候選預設不勾選。只勾選你要開放的模型並加入草稿，為各 AI 任務選擇模型。
5. 用測試功能確認服務與模型可用；測試請求可能產生供應商費用。辨識或測試失敗僅影響該供應商，先處理它即可。
6. 按「發布更改」，確認版本號增加。首次空列表應成為版本 1；已有版本則在其上發布，不強行重設版本。
7. 以一般使用者及未登入視窗分別驗證。一般使用者可用已發布模型；未登入預設供應商被鎖定，但仍能新增自己的個人供應商。

為舊版曾公開的共享 Key 準備替代 Key，測試及發布新 Key 成功後，到供應商控制台撤銷舊 Key。只改 D1 或刪掉舊配置不能使已被複製的 Key 失效。

## 9. 上線驗收與常見問題

| 操作 | 通過條件 |
| --- | --- |
| 未登入開頁面 | 核心學習正常；預設 AI 提示登入；仍可新增個人供應商 |
| 一般使用者登入 | 預設模型可用；沒有管理權限；管理 API 返回 403 |
| 管理員新增／編輯／發布 | 新列表版本成功；重新載入可看到設定 |
| 新增個人供應商 | URL＋Key → 連接 → 選模型 → 保存，可發出 AI 請求 |
| 同帳戶第二個瀏覽器／裝置 | 同步非秘密設定後，已選雲端同步的 Key 可下載使用 |
| 移除雲端副本 | 當前裝置 Key 保留，轉為僅本機；雲端副本已移除 |
| 衝突下載期間換 Key／重新登入 | 新 Key 與新工作階段不被舊回應覆蓋 |
| 退出／換帳戶 | 預設共享 Key 失效，其他分頁同步更新狀態 |
| zh-CN／zh-HK | 新增、保存、錯誤及管理發布流程的文字正確 |
| 非 AI 功能 | 詞書、文章、聽寫、TTS、學習資料同步仍正常 |

常見錯誤：`passcode_upgrade_required` 代表通行碼不足 32 字元；`credential_unavailable` 優先核對主密鑰版本、secret 名稱和值；`origin_not_allowed` 核對 origin 是否精確匹配；`admin_required` 核對 DB role；`old_worker`／表不存在則核對 Worker 部署及 D1 綁定／migration。

預設供應商採瀏覽器直連，使用者的瀏覽器必須能到達供應商並通過其 CORS。局域網地址是從使用者裝置連線，還受 HTTPS／HTTP 混合內容與瀏覽器本地網絡政策限制；把設定放 D1 不會讓 Cloudflare 代理局域網請求。

## 10. 日常維護、備份與回退

- 列表、模型、任務預設、供應商 Key：在「管理預設供應商」改草稿並發布，不必修改 ai-config.js 或重新部署前端。
- 單一供應商故障：停用該供應商、把其任務改選其他模型後發布。不要為修一個供應商刪掉整份列表。
- 增加全新協議：需要程式適配器與部署；已有協議的另一家相容供應商通常只需設定 URL＋Key。
- 撤回誤改：從歷史列表載入後重新發布。歷史 Key 不提供下載，要重新輸入有效 Key。
- 管理員角色與帳戶重設：維持第 4 節的受控 SQL 操作，不由一般前端自行提升角色。
- 定期備份 D1，並另外保管各版本主密鑰。此輪沒有新增背景備份或自動輪換服務。
- 主密鑰輪換需保留舊版本及完成密文重加密；目前沒有一鍵完成整批重加密的部署命令，不要直接覆蓋 V1。
- 前端故障可回退到仍保留登入門檻與新儲存模型的相容版本；不可重新公開含靜態共享 Key 的舊版本。不要為前端問題直接還原整個 D1，以免丟失新學習資料。

目前方案限制：登入後共享 Key 會交給瀏覽器，因此已登入者可以複製；它不是服務端 AI 請求代理，也不提供供應商端逐人強制配額。若日後要求 Key 永不下發或逐人計費，需另行實作服務端代理。
