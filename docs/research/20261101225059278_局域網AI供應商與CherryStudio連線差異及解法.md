# 局域網 AI 供應商與 Cherry Studio 連線差異及解法

日期：2026-11-01（Asia/Shanghai）。範圍：核對 BDC 現行程式、Cherry Studio／Magpie 公開實作與瀏覽器限制，提供可直接採用的設定方式；本次沒有修改應用程式碼或部署服務。

## 結論

BDC 可以保存及呼叫 HTTP 局域網供應商，沒有禁止 `192.168.*`、`10.*` 等私人位址。關鍵差異是由誰發出供應商請求：BDC 目前由瀏覽器直接發出；Magpie 有本機網關；Cherry Studio 能使用桌面程序的網絡能力，亦能自行配置 Electron 的網頁限制。單純以「桌面應用程式與網頁」區分並不充分，有本機後端的網頁同樣可以支援本地供應商。

因此，同一個 API 在 Cherry Studio 可用，並不代表它已符合網頁的跨域、混合內容及本地網絡權限要求。若是在同一台裝置、使用相同完整網址及認證方式，Cherry Studio 已能連接，應優先排查瀏覽器這幾層限制。

目前未取得實際使用的 BDC 網址、供應商網址、瀏覽器版本及控制台錯誤，不能判定這一次失敗究竟由哪一層造成。下文區分已確認的程式行為與需要依現場錯誤判斷的原因。

## 已確認的程式依據

| 位置 | 現行行為 | 影響 |
| --- | --- | --- |
| `modules/ai-protocols/index.js:101` | 服務網址接受完整 `http:`／`https:` URL，沒有私人 IP 黑名單 | 不是表單一律拒絕局域網供應商 |
| `modules/ai-profile-storage.js:115` | 保存網址時接受 HTTP／HTTPS，拒絕內嵌憑證等不合規輸入 | 不會僅因私人 IP 而清空網址 |
| `modules/ai-protocols/index.js:183` | 模型列表經瀏覽器 `fetch()` 請求 | 模型探索也受瀏覽器限制 |
| `modules/api.js:441`、`:572` | 普通與串流推理均直接 `fetch(request.url)` | 沒有自動轉送到本機或 Cloudflare 的 AI 代理 |
| `modules/ai-protocols/chat-completions.js:39` | 對話使用 JSON，按設定加入認證標頭 | 跨域 POST 即使無 Key，通常仍須 CORS 預檢 |
| `scripts/serve.py:581` | 可由 Python 代理固定上游，轉發 `/v1/*` | 在本機提供網頁與同源 API，是現成可用的替代路徑 |

供應商設定／Key 保存到 D1，並不會改變上述資料通道。一般公網 Worker 沒有通往使用者家中私人 IP 的路由；要由雲端回源，必須另建 Tunnel、VPN 或其他可達的網絡通道。

## Cherry Studio 為何不同

核對到的 Cherry Studio **v1.6.5** 主視窗設定含 `webSecurity: false` 與 `allowRunningInsecureContent: true`。Electron 官方文件說明，前者可以停用同源政策。這是已核實的一個版本實作，不代表每個版本都採相同配置，也不表示所有請求必定由 Node.js 發出。

Cherry Studio 現行主分支的 API Gateway 文件也展示主程序 `AiStreamManager` 的推理通道。桌面應用程式能選擇的網絡通道與權限設定，與普通網站不同。

普通網站的 JavaScript 無法自行把瀏覽器的 `webSecurity` 關閉。安裝成 PWA 也仍使用網頁的安全模型。

來源：[Cherry Studio v1.6.5 視窗原始碼](https://github.com/CherryHQ/cherry-studio/blob/v1.6.5/src/main/services/WindowService.ts)、[Electron WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences)、[Cherry Studio API Gateway 文件](https://github.com/CherryHQ/cherry-studio/blob/main/docs/references/api-gateway/README.md)。

## Magpie 補充：本機網關與 127.0.0.1 的含義

使用者補充 Magpie 畫面：供應商 `grok2api`，地址 `127.0.0.1:8000`，顯示 2 個模型。這與上述限制並不矛盾，也說明 BDC 可以採用同類架構提供本地供應商接入。

Magpie 官方文件說明，它自帶預設 `127.0.0.1:3425` 的本機網關，負責路由到供應商；桌面介面使用 Wails，其 Web 版亦由實際運行的 Magpie 服務提供，並可在網頁入口提供網關 `/v1` 路徑。因此，看見網頁樣式的管理介面，不代表瀏覽器直接向供應商送出請求。

| 情況 | 請求路徑 | 本地 API 請求的執行者 |
| --- | --- | --- |
| Magpie 的本機網關轉送 | 介面／客戶端 → Magpie → grok2api | Magpie 程序 |
| 現行 BDC 直接接 grok2api | BDC 網頁 → grok2api | 瀏覽器 |
| BDC 使用本機同源代理 | BDC 網頁 → BDC 本機服務 → grok2api | 本機服務程序 |

`127.0.0.1` 是本機回環地址，指向**發出該段請求的程序所在環境**。Magpie 在 Mac A 原生運行時，它轉送到 `127.0.0.1:8000` 會連 Mac A；若 BDC 後端在 Mac B，後端相同地址會連 Mac B；若後端在容器裡，通常是容器本身。要連另一台裝置上的 grok2api，應填該裝置可達的區網地址。不能透過同步同一個 loopback 網址，讓各裝置自動連回同一台服務主機。

BDC 若要提供與 Magpie 相近的接入體驗，可讓模型探索、連線測試與推理統一經過能到達供應商的本機服務；同時支援所需認證標頭、協議及 SSE。現成 `--ai-proxy` 已有基本路徑，限制見下文。僅把 BDC 供應商改指 Magpie 的 HTTP 網關，仍須處理「瀏覽器 → Magpie」這一段的來源及本地網絡權限。

截圖本身不能判定使用者採用的是 Magpie 原生視窗還是 Web 版；上述架構依據來自官方文件，沒有讀取使用者的 Magpie 私人設定或抓取實際網絡流量。

來源：[Magpie 入門與網關說明](https://usemagpie.ai/docs/start)、[Magpie 參考手冊](https://github.com/yetone/magpie/blob/main/docs/reference.md)、[Magpie Web／Docker 說明](https://usemagpie.ai/docs/docker)。

## 常見失敗原因

### 1. CORS／OPTIONS 預檢

網頁位於 `https://bdc.example.com`，AI 位於 `http://192.168.1.100:11434`，兩者是不同來源；即使同一 IP，只要埠不同亦屬跨域。API 必須允許 BDC 實際網頁來源，以及所用方法、標頭，並正確處理 `OPTIONS`。只允許 Cherry 的來源、只支援命令列或只在 GET 回應加入標頭，均可能不足。

在網址列開到模型列表，或 `curl` 呼叫成功，只證明相應連線可達，沒有驗證網頁跨域 POST 的預檢。模型列表成功，也不能推論對話、圖片或串流都成功。

來源：[MDN CORS 與預檢說明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)。

### 2. HTTPS 與 HTTP 混合內容、本地網絡權限

HTTPS 網頁向 HTTP 服務發出請求，可能被混合內容規則攔截；連接私人 IP 亦可能需要本地網絡存取授權。

這裡不能簡化成「HTTPS 網頁永遠不能呼叫 HTTP 局域網」。Chrome 官方說明，從 Chrome 142 起推出 Local Network Access 權限；在符合條件並獲授權後，可放寬本地請求的混合內容限制。私人 IP 字面值及 `.local` 名稱有相應識別；一般網域即使解析到私人 IP，也可能需要額外的 `targetAddressSpace` 標註。BDC 現行 `fetch()` 沒有加入這個標註。

本地網絡授權不會自動修復 API 的 CORS。不同瀏覽器、版本及作業系統權限亦有差異。

來源：[Chrome 本地網絡權限說明](https://developer.chrome.com/blog/local-network-access)、[Chrome 142 發佈說明](https://developer.chrome.com/release-notes/142)。

### 3. 裝置與 API 設定差異

若 Cherry Studio 在電腦上，而 BDC 在手機上，兩者的網絡路徑並不相同。手機的 `localhost`／`127.0.0.1` 指手機本身；要連電腦上的服務，須使用電腦區網 IP，且服務監聽區網介面、防火牆放行。

此外仍須核對協議、完整路徑、模型名稱及認證方式。無 Key 服務在 BDC 應選「無需金鑰」；僅能處理 Ollama 原生端點的服務，不能直接視為 OpenAI 相容服務。

## 解法一：保留現行網頁，調整權限與 CORS

適合希望繼續從公網 BDC 網頁直接連家中 API，且所用瀏覽器支援相應本地網絡權限的情況。

1. 在 BDC 網站的瀏覽器權限設定允許本地網絡存取；如作業系統另有本地網絡權限，也要允許瀏覽器。
2. API 服務端允許 BDC 的實際 origin，包含正確的 scheme、host 及 port；支援 GET、POST、OPTIONS 與實際使用的認證／JSON 標頭。
3. API 地址填可由目前裝置到達的區網 IP，並核對完整端點。
4. 重新測試模型列表及實際對話，分別觀察控制台和 Network 的錯誤。

若使用 Ollama，可依官方文件設定 `OLLAMA_HOST` 控制監聽介面、`OLLAMA_ORIGINS` 允許網頁來源，設定後重啟服務。這些設定各自處理監聽與跨域，不能取代瀏覽器本地網絡授權。

來源：[Ollama FAQ](https://docs.ollama.com/faq)。

## 解法二：本機運行 BDC，使用現成同源代理

這是目前最直接、可控制的本機方案，適用於 OpenAI 相容 API。

假設 AI 服務是 `http://192.168.1.100:11434`，運行 BDC 的電腦 IP 是 `192.168.1.20`，在專案根目錄執行：

```bash
python3 scripts/serve.py --lan --ai-proxy http://192.168.1.100:11434
```

接著：

| 項目 | 填寫／開啟內容 |
| --- | --- |
| 瀏覽器網頁 | `http://192.168.1.20:8313/` |
| BDC 供應商服務網址 | `http://192.168.1.20:8313/v1` |
| 協議 | OpenAI Chat Completions 相容 |
| 認證 | 上游無 Key 就選「無需金鑰」；Bearer 上游填其 Key |

資料路徑為：`瀏覽器 → BDC 同源 /v1 → Python → 局域網 AI`。

此時瀏覽器只連網頁自己的來源，上游請求由 Python 發出，API 不必為這段 Python 請求提供瀏覽器 CORS 標頭。**網頁與供應商網址必須使用完全相同的 scheme、host 及 port**。如果在電腦上用 `http://127.0.0.1:8313/` 開啟網頁，供應商便應填 `http://127.0.0.1:8313/v1`；手機則使用電腦 IP。

注意兩項設定：

- `--ai-proxy` 上游不要再加 `/v1`，程式會把瀏覽器請求的 `/v1/...` 接上去，否則容易得到 `/v1/v1/...`。
- 新版供應商須填完整絕對網址，不能只填 `/v1`。`scripts/serve.py` 檔首仍有相對 provider 的歷史說明，應以現行 README 與供應商設定行為為準。

**現成代理的實際限制：**它只接 `/v1/*`、只轉發 `Content-Type`／`Authorization`／`Accept`，不轉發 `x-api-key`、`x-goog-api-key` 等標頭；而且使用 `response.read()` 完整讀取回應後才返回，會失去 SSE 逐段輸出，較長推理也可能先碰到前端逾時。它適合先打通 OpenAI 相容的一般請求；要全面支援多協議與串流，應完善代理或換成支援串流的反向代理。

`--lan` 單獨使用只讓其他裝置載入網頁，不會自動代理 AI。仍留在公網 BDC 網頁、僅把 API 改填本機 Python 的 HTTP 網址，也不等於同源，仍需處理相同的跨域／本地網絡限制。

## 解法三：保留公網 HTTPS 入口，建立可回源的 HTTPS 通道

若主要需求是繼續使用公網 BDC、跨瀏覽器或離家使用，可讓區網內服務主機建立 Tunnel 等回源通道，將 API 提供為具認證的 HTTPS 端點；亦可在同一 HTTPS 入口提供網頁與 API 路徑。

獨立的 HTTPS API 網域可以解決 HTTP 混合內容與私人 IP 可達性問題，但若與 BDC 網域不同，仍須配置 CORS。同一入口代理網頁與 API 則可同時消除跨域問題。對外提供 API 時需保留適當認證。

單純在公網 Worker 中 `fetch('http://192.168.1.100:11434')` 無法連到使用者家中電腦；必須先有上述通道。

## 依錯誤快速判斷

| 瀏覽器觀察 | 優先檢查 |
| --- | --- |
| `CORS policy`、預檢未通過 | API 的 origin 白名單、OPTIONS、方法與標頭 |
| `Mixed Content` | HTTPS → HTTP，及本地網絡例外是否適用 |
| `ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`／本地網絡權限拒絕 | 網站本地網絡權限、瀏覽器與系統權限 |
| `ERR_CONNECTION_REFUSED`／連線逾時 | IP、埠、監聽介面、防火牆、目前裝置的路由 |
| 401／403 | Key、認證模式、來源白名單；依回應內容判斷 |
| 404／405 | 路徑、重複 `/v1`、協議或方法不符 |
| 只有 `Failed to fetch` | 這是統稱，不能單憑它斷言是 CORS；需看控制台及 Network |

## 本次驗證與限制

已直接載入現有 `scripts/serve.py`，用 Python 標準庫建立兩個暫時的 loopback HTTP 服務；上游模擬 API 不提供 CORS 標頭。驗證結果：

- `/v1/models` 與 `/v1/chat/completions` 正確轉發，JSON 回應成功。
- Bearer 認證正常轉發，無 Key 請求亦可轉發。
- 上游未收到 `Origin`；確認此段由伺服器請求，不需上游的瀏覽器 CORS 許可。
- 確認 `x-api-key` 不會轉發；串流緩衝限制由程式碼核對。

這些是本機模擬的代理傳輸驗證，沒有實測使用者實際 AI 服務，亦沒有在各款瀏覽器執行完整端到端測試。沒有新增測試檔、修改 AI 邏輯或進行部署。
