## 一、現況摘要與證據邊界

本專案是離線優先的純前端靜態 SPA，以原生 ES Modules 組織功能，無 bundler。文章詳解的定位是先完成可閱讀的逐段翻譯，再按需要取得詞、句、片語詳解，並銜接朗讀、閱讀記錄和 AI 助手；不是按一次分析就預先產生全文所有詞語的深度解析。依據：`README.md:3`、`README.md:39`、`README.md:42`、`README.md:48`、`index.html:1143`、`modules/prompts/article.js:14`。

**主要判斷：最值得先改善的是閱讀狀態與資料可靠性。** 現有功能已相當完整，但分析失敗、重試、原文修改、助手上下文和音訊中斷各自使用不同狀態來源，容易出現「畫面看似完成，實際沒有保存」「目前看到的文章與 AI 使用的文章不一致」等問題。應先讓現有流程可信，再增加功能入口。

- 分析已有逐段呈現、進度、最多兩個併發請求及啟動間隔；已有單段與批次重試（`features/article/article.js:2098`、`features/article/article.js:4232`、`features/article/article.js:4577`）。
- 閱讀已有查詞、句／片語解析、發音、加入詞書、標記、筆記、迷霧與朗讀控制；閱讀檔案可依詞、句、標記、筆記、AI 文件篩選（`features/article/article.js:3994`、`features/article/reading-panel.js:16`）。
- 閱讀面板已適配桌面側欄與手機底部面板；已有 Markdown 筆記匯出、完整 JSON 備份、AI 難點分析／整理，不應另建一套平行系統（`styles.css:6293`、`features/article/reading-panel.js:66`、`modules/reading-actions.js:303`）。

- 已有防止查詞晚回應覆蓋其他選詞／文章／帳戶／版本的檢查；筆記關閉前也會等待保存，失敗時保留草稿（`features/article/article.js:3978`、`features/article/reading-panel.js:153`、`features/article/phrase-picker.js:435`）。這些保護應擴充到其他路徑，不能全面推倒重寫。

## 二、使用者流程與痛點（按嚴重度排序）

### F01｜P1：分析失敗沒有一致的狀態，重試可能不見、失效或不能保存

**流程：分析 → 失敗 → 重試 → 重開文章。**

**事實與證據：**

1. `analyzeParagraph` 在候選模型與 fallback 均失敗後回傳空翻譯物件，沒有拋錯或 `failed: true`（`modules/api.js:813`、`modules/api.js:829`）。主分析卻只在 catch 時把段號加入 `lastFailedIndices`；正常回傳的空結果仍會進入頁內 `paragraphCache`（`features/article/article.js:2150`、`features/article/article.js:2158`）。
2. 段落畫面依「非中文原文且沒有譯文」判定失敗，但批次重試按鈕依 `lastFailedIndices` 顯示，兩者來源不同（`features/article/article.js:4549`、`features/article/article.js:2223`）。
3. 開啟歷史記錄時，按鈕根據 `recordFailedParagraphs(record)` 顯示；此路徑沒有重建 `lastFailedIndices`，而批次重試在陣列為空時直接返回（`features/article/article.js:2671`、`features/article/article.js:2683`、`features/article/article.js:4577`）。全檔該陣列的初始化／寫入亦沒有從歷史記錄還原的路徑（`features/article/article.js:1436`、`features/article/article.js:2106`）。
4. 單段重試會寫回 `saveAnalysis`，但同樣沒有先判斷空翻譯是否有效，仍移除失敗段號並閃示成功（`features/article/article.js:4284`、`features/article/article.js:4292`）。批次重試只更新 DOM 與 dataset，函式內沒有寫回文章記錄，也沒有像單段重試般固定目標文章 ID 後驗證（`features/article/article.js:4577`、`features/article/article.js:4625`、`features/article/article.js:4644`）。

**影響推論：** 可能出現段落顯示失敗但沒有批次重試、歷史文章的重試按鈕可見卻無動作、空結果被當作重試成功、重開後退回重試前狀態。批次重試期間切換文章亦有晚回應更新目前畫面的風險，需實測。

**建議：** 使用共同的段落狀態模型 `pending/success/failed/cancelled`，區分跳過圖片、原文已是中文、空回應及真實失敗；保留可重試錯誤原因。批次按鈕從目前文章的段落狀態推導；單段與批次共用同一條請求、有效性檢查、歸屬驗證及保存流程。失敗不得進入成功快取。

### F02｜P1：修改／匯入原文後，閱讀、朗讀與助手可能各用不同內容

**流程：閱讀 A → 修改文字或導入 B → 朗讀／提問。**

**事實與證據：** 原文 input 事件只更新歷史指示；`applyImportedArticle` 更新 context、輸入框及來源，未在此處清除舊分析畫面、取消分析或停止朗讀（`features/article/article.js:298`、`features/article/article.js:56`）。朗讀只要找到已渲染的 `.paragraph-pair`，就從該 DOM 建立 chunks，沒有時才讀輸入框（`features/article/article.js:3110`、`features/article/article.js:3150`）。助手則每次從目前輸入框建立上下文（`features/assistant/assistant.js:370`）。

**影響推論：** 畫面及朗讀仍是 A，但助手回答 B；使用者可能誤以為正在問畫面中那篇文章。匯入期間若仍有舊工作回應，也需要核對 run 與版本的歸屬。

**建議：** 建立明確的「原文已修改，分析待更新」狀態。閱讀、朗讀、助手共同使用固定的 `articleId + contentVersion`；切換文章時處理舊工作與音訊。編輯草稿、目前閱讀版本、已保存版本應可辨認，重新分析前說明既有標記及筆記如何保留，不要靜默混用內容。

### F03｜P1：助手的錯誤、停止與重試語義不可靠

**流程：問 AI → 串流失敗／停止 → 切文章 → 重試。**

**事實與證據：**

- 串流失敗時 catch 寫入錯誤提示，finally 又用 `buffer` 重畫，會覆蓋該提示；重試按鈕另外加入（`features/assistant/assistant.js:499`、`features/assistant/assistant.js:504`、`features/assistant/assistant.js:539`）。
- `AbortError` 不設 `hadError`，因此停止後的半段或空回答仍走保存路徑，狀態是 `complete`（`features/assistant/assistant.js:500`、`features/assistant/assistant.js:510`）。
- 重試固定原會話 ID，但再次從當前輸入框建立正文及優先文章 ID，未固定原正文快照／版本（`features/assistant/assistant.js:431`、`features/assistant/assistant.js:440`、`features/assistant/assistant.js:544`）。
- 每輪取最後八則歷史，再加入目前問題；重試不新增使用者記錄，但原問題可能已在這八則中（`features/assistant/assistant.js:456`、`features/assistant/assistant.js:465`）。

**影響推論：** 使用者只見回答突然結束卻不知原因；停止的內容被當作完整答案。切換文章後重試，可能把原會話配上另一篇正文；原問題也可能重複送出。

**建議：** 先修正 `streaming/complete/cancelled/failed` 與畫面提示，保留已收到內容並明示不完整。重試使用原請求的文章版本、上下文範圍及訊息快照，明確替換失敗輪次，避免重複問題；若要改問目前文章，另作新提問。

### F04｜P1：查詞發音會中斷文章音訊，暫停後實際從句首重播

**流程：朗讀 → 點詞發音 → 繼續閱讀。**

**事實與證據：** 點詞發音直接呼叫共用 `speakText`；每次 `speakText` 都先 `stopCurrentAudio`，後者清掉原 `onended`、重設時間並取消本機語音（`features/article/article.js:3825`、`modules/audio.js:199`、`modules/audio.js:44`）。文章朗讀依賴原 `onEnd` 推進 chunk（`features/article/article.js:3373`）。文章 pause 也是 stop，resume 再呼叫 `playCurrentChunk`（`features/article/article.js:3420`）。遠端音訊把 `onloadstart` 當成 `onStart`（`modules/audio.js:225`）。

**影響推論：** 單字發音可能打斷文章且沒有完成回呼，文章播放狀態與實際音訊脫節；「繼續」實際重播目前句／段，而非從停止時間續播。載入時間也可能被誤當播放時間。

**建議：** 由共用音訊層管理播放擁有者及中斷通知，明確選擇「發音後回到原句」或「暫停文章等待操作」。支援的後端提供真正 pause/resume；不能支援時明示「重播本句／本段」。區分載入、播放、暫停、失敗，讓圖示、文字及無障礙名稱同步。

### F05｜P2：分析已有進度，但中途重整沒有逐段永久 checkpoint

**流程：長文分析 → 已完成部分段落 → 重整／關頁。**

**事實與證據：** 開始分析時先保存原文與原有結果；每段完成後更新記憶體陣列及 DOM，待全部工作完成才組合並保存新結果（`features/article/article.js:2047`、`features/article/article.js:2151`、`features/article/article.js:2183`）。API 有持久快取，因此不能說重整後所有 AI 成果一定丟失（`modules/api.js:745`）。

**影響推論：** 使用者看到部分完成，不代表文章記錄已保存相同進度；重開後需重新進入分析流程。若快取未命中、已過期或儲存失敗，重做成本更高。現有進度按段數顯示，亦不代表可靠的剩餘時間。

**建議：** 每段成功建立可續作 checkpoint，包含文章版本、段落狀態及 run ID；取消只停止剩餘工作，不撤銷已完成項。UI 分清「分析中／已完成／已保存／保存失敗」，重開時提供繼續未完成段落，避免虛構精準倒數。

### F06｜P2：點詞詳解的入口與彈窗，對鍵盤及小螢幕仍有缺口

**流程：閱讀 → 點詞 → 看解釋／發音／收藏 → 返回原文。**

**事實與證據：**

- 正文詞語由正則包成 `span`，沒有 role／tabindex；目前入口綁 click，未提供相應正文詞語鍵盤操作（`features/article/article.js:1859`、`features/article/article.js:3644`、`features/article/article.js:5671`）。
- 詳解容器是空 div，沒有內建 dialog 語義與關閉按鈕；共用 tooltip 以外部 click 關閉，定位只處理左右及上下選邊，未處理視窗可用高度（`index.html:1555`、`modules/ui.js:207`、`modules/ui.js:241`）。CSS 有寬度限制，但未提供最大高度與內容內捲（`styles.css:1411`）。
- 句解析圖示的寬高為 16px、透明度 0.3（`styles.css:3409`）。詳解在同層提供多項操作，詞義之前先顯示句中角色；未命中詳解時，載入畫面沒有同等的即時發音入口（`features/article/article.js:4006`、`features/article/article.js:4026`、`features/article/article.js:4094`）。
- 片語選取器已有真正 button、Escape 與焦點返回；閱讀面板也已有手機底部排版，不能泛稱全部不支援鍵盤或手機（`features/article/phrase-picker.js:39`、`features/article/phrase-picker.js:428`、`styles.css:6293`）。

**影響推論：** 只用鍵盤的人難以進入正文查詞；手機軟鍵盤、橫屏或縮放時，較長詳解可能越界。多個同級操作及低可見度的句解析入口增加發現與選擇成本。實際溢出和誤觸率尚未量測。

**建議：** 優先呈現「句中意思 → 發音 → 收藏」，其他動作收進更多選單。桌面維持輕量浮層，手機可沿用既有底部面板模式，加入高度限制、內捲、明確關閉、Escape、焦點返回及必要的焦點管理。提供句級進入後選詞的鍵盤方式，避免把長文每個詞都加入 Tab 順序；擴大句解析點擊區。載入中仍應可發音、取消及返回。

### F07｜P2：詞語切分偏 ASCII，可能降低命中率或干擾原文連結

**事實與證據：** 詞語切分使用 `[A-Za-z][A-Za-z'’-]*`；DOM 包裝只跳過句解析按鈕及已包裝詞，沒有一併跳過連結、程式碼等語義節點（`features/article/article.js:1859`、`features/article/article.js:5671`）。點詞事件會進入自訂詳解處理（`features/article/article.js:3644`）。

**影響推論：** 如帶重音字母的 `café`、混合字母數字詞及專有名詞，切分可能與使用者預期不同；連結中的可點詞可能與原連結行為競爭。這是切分規則與事件路徑推論，尚未做跨瀏覽器命中率測試。

**建議：** 先建立教材樣本與分詞期望，採語言感知分詞配合例外規則；原文連結、code 等保留本來行為，以明確操作另行查詞。維持正文 offset／occurrence 錨點，支援片語選取作補救，避免只改正則而破壞歷史記錄。

### F08｜P2：多層快取的語言、失敗與生命週期不一致

**事實與證據：** API 段落持久快取已納入 locale、promptVersion、model、level；但頁內 `paragraphCache` 僅以文字為鍵，也會放入空結果（`modules/api.js:745`、`features/article/article.js:1435`、`features/article/article.js:2122`、`features/article/article.js:2150`）。查詞 `_lazyCache` 以句子與詞為鍵，儲存完成結果，未包含 locale／模型／promptVersion，也未儲存 in-flight Promise（`features/article/article.js:4068`）。相較之下，句解析已有進行中請求去重（`features/article/article.js:1499`）。快取過期讀取路徑會刪除 localStorage 後備，但未同步刪除過期 IndexedDB 記錄；未見容量淘汰機制（`modules/cache.js:101`）。

**影響推論：** 同一頁面切換語言／模型後，可能先命中舊頁內結果；連點同詞可能重複請求，雖有晚回應保護，仍消耗等待時間與供應商額度。長期使用可能累積已過期 IDB 記錄；尚無容量量測。

**建議：** 統一可再生快取的 identity，至少涵蓋 locale、任務／提示版本、模型及內容；評估是否納入 provider 以區分同名模型。失敗不當成功快取、同鍵請求去重，清楚定義 TTL／容量清理。永久閱讀文件與可再生快取分開；切換介面語言不應轉寫教材或歷史詳解，可另提供「按目前語言重新生成」。

### F09｜P2：長文的 DOM、單段輸出及助手全文上下文缺少成本界線

**事實與證據：** 分析一次建立全部段落 placeholder，閱讀將詞逐一包成 DOM；查詞錨點定位還需掃描句子／原文（`features/article/article.js:2084`、`features/article/article.js:5671`、`features/article/article.js:1456`）。段落 token budget 依模式設定上限，未按任意長段落先分塊；共用請求已有 length 類重試，不能說完全沒有截斷補救（`modules/api.js:770`、`modules/api.js:497`）。助手每輪附全文及最後八則訊息，未見依可用 context budget 選段的流程（`features/assistant/assistant.js:455`）。

**影響推論：** 多段長文可能增加 DOM 數量與點詞延遲；極長單段／表格可能輸出不足。助手問題很短也重送全文，增加成本、延遲及超出模型上下文的風險。這些均為待量測風險，本次沒有測得實際瓶頸或支援上限。

**建議：** 先量測 DOM 數、long task、點詞延遲、請求輸入／輸出量，再決定懶渲染／虛擬化。預先計算句子 offset，對極長段落按結構拆分並重組。助手提供「選句／本段／全文」範圍提示、token 預算及必要的歷史摘要；範圍縮減應可見，避免靜默截斷重要前文。

### F10｜P2：助手輸入、捲動及「刷新上下文」增加操作摩擦

**事實與證據：** 助手使用單行 input；送出立即清空輸入，Enter 路徑未檢查 `isComposing`，未見全會話 busy／排隊控制（`features/assistant/assistant.js:150`、`features/assistant/assistant.js:203`）。串流每收到 delta 都捲到底部（`features/assistant/assistant.js:489`）。「刷新上下文」按鈕只新增提示；實際每次 `ask` 本來就重新 `buildContext`（`features/assistant/assistant.js:169`、`features/assistant/assistant.js:431`）。

**影響推論：** 中文輸入法按 Enter 選字時可能誤送；連續提問可能產生順序難理解的回答。使用者向上看舊訊息時，串流可能把畫面拉回底部。上下文按鈕未讓人知道目前究竟用了哪篇、哪個版本及多大範圍。

**建議：** 支援多行及 IME 保護，清楚定義 Enter／Shift+Enter；提供失敗草稿與重送。單會話採序列或明確顯示並行輪次。只有使用者接近底部才自動跟隨，否則顯示新回答提示。把冗餘刷新提示改成可核對的文章標題、版本與上下文範圍。

### F11｜P2：播放可離線後備，但音訊下載能力與範圍不透明

**事實與證據：** 朗讀未設定遠端服務時可使用本機語音；下載則直接建立遠端 TTS 連結並開新分頁，未做同等能力判斷或 HTTP 成功檢查（`modules/audio.js:202`、`modules/audio.js:162`）。URL 以 GET 包含完整文字及 `api_key`（`modules/audio.js:149`）。全文模式合併全文，句／段模式使用目前 chunk；此流程未提供下載工作進度（`features/article/article.js:3495`）。播放按鈕狀態更新主要改 title，而初始 aria-label 為固定朗讀文章（`features/article/article.js:3445`、`index.html:1148`）。

**影響推論：** 有聲音不代表能下載；下載可能開到錯誤頁、範圍也可能與使用者理解不同。長文 GET URL 的長度限制、服務端或代理日誌記錄文字／Key 屬條件風險，不能據此宣稱已發生外洩。

**建議：** 分開顯示播放與下載能力；下載前明示全文／本段／本句與所需遠端服務。可監測的後端提供工作狀態／錯誤；若需 POST、分段合併或避免 Key 進 URL，應先確認 TTS 協議與服務端支援，不能假設只改純前端即可完成。

### F12｜P2：切換介面語言時重建動態 UI，可能丟失當前操作狀態

**事實與證據：** 助手 locale 變更直接 remove 再 mount，未先保存輸入框草稿或管理舊請求；setup 會重新建立 observer 及 hash／nav listener（`features/assistant/assistant.js:53`、`features/assistant/assistant.js:101`）。閱讀面板 locale 變更也重建 DOM，沒有保留開啟狀態的流程；片語選取器則移除 sheet 再建立，未先 flush 當前輸入（`features/article/reading-panel.js:940`、`features/article/phrase-picker.js:463`）。全域 i18n 更新靜態標記後發事件，但已開啟的詞語 tooltip 未見對應重畫機制（`modules/i18n.js:78`、`features/article/article.js:3994`）。

**影響推論：** 切換 zh-CN／zh-HK 時，輸入中的問題、選詞筆記或面板位置可能消失；部分已開啟控制文字可能維持原語言。閱讀面板的草稿 Map 仍存在，不能宣稱已保存筆記全部丟失。重複 listener 的實際使用影響需實測。

**已驗證範圍：** 執行 `node tests/audit-i18n.mjs --json` 並讀取摘要，兩語各 1969 鍵，鍵集合及插值參數一致；本次文章／learning／assistant 的疑似硬編碼候選為空。腳本另報 `phonetics.` 動態鍵候選，未在本次確認；不能稱全站所有 i18n 檢查通過。這也不等於已做雙語瀏覽器驗收。

**建議：** 優先原位更新 UI 文字；必須重建時先保存草稿、選取／開關／焦點狀態，完整 teardown 舊監聽。歷史 AI 內容與教材維持原文，只有控制文字及後續生成採目前 locale。

### F13｜P2：加入詞書後，例句的點詞承諾未完成

**流程：文章收藏詞語 → 單字學習 → 生成例句 → 點另一個生詞。**

**事實與證據：** learning 的 `handleWordAnalysisClick` 對 `.interactive-word` 只輸出 `console.log`，沒有顯示詳解（`features/learning/learning.js:349`）。生成例句 await 後直接 `displayExamples(word)`，該路徑未先核對是否仍是目前選詞（`features/learning/learning.js:188`、`features/learning/learning.js:209`）。

**影響推論：** 文章與例句中看似相同的可點詞，回應卻不同；快速換詞時也可能看到上一個詞較晚返回的例句。

**建議：** 共用具句境的查詞動作與顯示模型，先補齊例句可點詞行為或移除誤導樣式。為例句請求加入詞 ID／請求序號檢查，延遲結果可保存到原詞，但不得覆蓋新選詞畫面。

### F14｜P3：複習與匯出已有基礎，仍可降低「讀完之後」的決策成本

**事實與證據：** 閱讀檔案已整合查詞、標記、筆記、AI 文件，且 AI 整理會使用選中的學習記錄／筆記，保留來源與版本（`features/article/reading-panel.js:16`、`modules/reading-actions.js:303`）。頁面頂部匯出直接使用預設值；Markdown 預設不含全文及 chat，面板內才有相應範圍選項（`features/article/reading-panel.js:898`、`modules/reading-export.js:66`、`features/article/reading-panel.js:66`）。完整 JSON 則包含目前 scope 的文章、閱讀檔案、詞書、所有訊息及原文版本，與單篇 Markdown 不同（`modules/reading-export.js:318`）。走查未找到文章直接建立 QA 訓練集的入口；已有的是 QA → 文章（`features/article/article.js:1389`）。

**影響推論：** 兩個匯出入口可能讓人對全文／對話是否包含產生不同期待。查過、標記過、真正需要複習也不是同一狀態；讀完後仍需自行挑選內容。文章 → QA 屬產品機會，不能列成既有功能故障。

**建議：** 匯出先給統一的範圍摘要／預覽，區分「本篇閱讀筆記」與「目前帳戶／端點完整備份」。先從已標記詞句產生可確認的複習清單，再評估轉成 QA；保留原句與版本來源，不把查閱次數等同掌握程度。可重用 QA 的解析／保存、訓練、AI 校對及 PDF 路徑，避免新增平行資料系統；現有入口分別見 `features/qa/qa-creator.js:22`、`features/qa/qa-creator.js:248`、`features/qa/qa-trainer.js:22`、`features/qa/qa-checker.js:78`、`features/qa/qa-pdf.js:64`。這些入口的存在不代表已具備文章轉 QA 的編排、題目審核及來源關聯，後續仍需補產品設計。

## 四、風險與取捨

1. **版本一致性與使用自由。** 綁定文章版本可防混用，但不能強迫每次改字都重新分析。應允許「繼續閱讀舊版」與「分析新版本」，並標示助手使用哪一版。
2. **永久學習記錄與可再生快取。** TTL／LRU 只能清理可再生內容；不能把已收藏詳解、筆記、chat 或舊原文版本當快取刪除。現有 IndexedDB 交易、scope、outbox 及保存失敗處理需保留。
3. **checkpoint 寫入頻率。** 每段保存提升恢復能力，也增加儲存與同步工作；可合併短時間寫入，但 UI 必須如實標示尚未保存狀態，且切帳戶／版本時不能跨 scope 合併。
4. **長文優化與來源定位。** 虛擬化會影響瀏覽器搜尋、選取、標記、朗讀跟隨、鍵盤與螢幕閱讀器。優先量測、預計算 offset，再考慮僅對遠離視窗的重型內容懶載，避免以降低 DOM 為唯一目標。
5. **音訊後端能力不同。** HTMLAudio、系統 SpeechSynthesis、第三方 TTS 對暫停、事件、下載的支援不一致；需按能力設計一致承諾，而非假定相同 API 即有相同行為。
6. **上下文縮減與回答品質。** 限制全文可減少請求成本及暴露範圍，但可能丟失代詞、人物、論證背景；提供選句／段／全文並顯示實際範圍，必要時讓使用者擴大。
7. **雙語介面與教材完整性。** 切 locale 應更新操作文案及後續 AI 語言；不得轉換文章、OCR、QA、使用者輸入或歷史回答。已保存詳解若需要重生，應保留來源／版本關係。
8. **離線優先的邊界。** 已保存的文章／筆記與命中快取可離線使用，不表示首次 AI 分析可離線完成；本機語音可播放亦不表示可生成可下載音檔。錯誤提示應清楚區分。
9. **安全結論不能超出證據。** Markdown 已有 escaping 與 URL scheme 白名單（`modules/markdown.js:3`）；本次沒有發現足以宣稱 XSS 的證據。TTS URL 與助手全文風險應以實際部署及傳輸紀錄驗證，不應稱已外洩。

## 六、尚待確認的問題

1. 真實使用者文章長度、手機比例、常見語言／教材格式，以及最常用的是查詞、翻譯還是助手？需要使用觀察，才能調整 F06／F09 的投入順序。
2. F01 的歷史批次重試、F02 的輸入／舊閱讀混用、F03 的跨文章重試、F04 的音訊狀態，實際瀏覽器如何重現？靜態證據足以安排優先驗證，但不是執行結果。
3. 真實 TTS 部署是否支援 POST、分段音檔、可驗證的下載結果及真正續播？不同瀏覽器／voice 的事件行為是否一致？
4. 手機長詳解的實際越界程度、IME 誤送、locale 切換草稿狀態及 listener 累積影響，仍需真機及重複切換測試。
5. 長文延遲主要來自 DOM、錨點掃描、網路還是供應商？模型的實際 context 與輸出上限、每輪成本尚未量測，不能先承諾虛擬化或換模型一定改善。
6. 產品希望「文章詳解」預設保持精簡按需，還是提供可選深讀工作流？目前程式明確採精簡翻譯＋按需詳解，建議在可靠性修復後再作產品決策。
7. 缺失的 storage architecture 文件是否有外部版本？若有，應核對與目前 IndexedDB／outbox／版本保存設計是否一致。
