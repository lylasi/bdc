**建議落地順序（可各自回滾）**：

| 順序 | 改動 | 目前實測 | 風險 |
|---|---|---|---|
| 1 | 清洗 chunk 受控並行（2）＋保序＋部分失敗提示 | 2 塊 5.97s→~3.5s；6 塊 ~2× | 低中 |

## 3. 主要發現與建議（依優先級）

### P0-1　正文清洗逐塊序列化（尚未改，長頁預覽主成本）

**證據**

- `modules/api.js:2100-2114`：`for (i…) { await cleanMarkdownChunk(chunks[i]) }`，一次只有 1 塊 in-flight。
- `modules/api.js:2015-2036`（`splitMarkdownForCleanup`）以 3500 字切塊；長文 2–N 塊。
- 實測 S2（2 塊、AI 2.5s）：預覽 5966ms；what-if 3 塊：序列 **7512ms**、並行 **5010ms**（1.5×）；6 塊時會接近 2×。
- 第 2 塊以後失敗會靜默保留原文（`:2110-2112`）；`finish_reason=length` 會讓 `extractPageArticle` 丟 `page_extraction_truncated`（`modules/api.js:2178`），整個預覽消失。

**建議**

- 與段落分析相同的 worker pool（2），`cleaned[i]` 保序，最後 join；`onProgress` 改完成數。
- `catch` 最前面先判斷 `ctx.signal?.aborted || err?.name === 'AbortError'`，直接 throw（不要吞）。
- 部分失敗：保留原文 + 蒐集 `{index, code}`，最後以新 notice（如 `pageExtractionPartial`）提示「N 塊未整理，已保留原文」，不要靜默。
- 截斷：不建議直接丟棄全部結果；較安全的折衷是「回傳已清洗內容 + 明確警告，使用者可檢查後再確認」，或提供「使用目前已提取內容」。需要產品決策與新 i18n 文案。
- 併發上限維持 2（`AI_LIMITS.default.maxConcurrency`）。

**風險**：順序務必用 index；供應商 TPM 壓力（429 會退避重試，可能反而拉長）；部分失敗文案要雙語。

**驗證**

- 長頁 3 塊，route 讓第 2 塊最快回、第 1 塊最慢；斷言預覽拼接順序 A、B、C，且 in-flight ≤ 2。
- 第 2 塊持續失敗：預覽仍出現、第 2 塊為原文、notice 顯示「1 塊未整理」、DB 尚無文章。
- 清洗中途按停止：notice = 已停止、無預覽、無寫入。

**預期收益**：本次 mock 2 塊 5.97s→~3.5s；3 塊 7.5s→5.0s；6 塊 ~2×。

### P0-2　文章視窗冷啟動重複同步（尚未改）

**證據**

- `extension/lookup.js:809-818`：`await workspaceStartup` → `await syncExtensionAccountAI()` → 才 `setReady(true)`。
- `modules/extension-ai-runtime.js:191-205`：每次 `force:true` 刷新 catalog，再 `syncCredentials`。
- `modules/ai-catalog.js:548-577`：`initAICatalog()` 已 `/me` + `refreshAICatalog`（非強制，但 `lastRefreshAt` 是 per-document，新視窗必打）+ 排程刷新；`modules/ai-credential-sync.js:1227` 登入後 +1s 再排一次 credential sync。
- 實測 8 個 Worker 請求、`/ai-catalog` 與 `/ai-credentials` 各兩次。

**建議**

- 文章視窗改成「已 ready 就不做強制 sync」：

```js
// extension/lookup.js, isWorkspaceWindow branch
await workspaceStartup;
if (getExtensionReadiness().loggedIn) {
    const ready = getExtensionReadiness();
    if (ready.taskResolution.status !== 'ready' || !ready.catalog.usable) {
        try { await syncExtensionAccountAI(); }
        catch (error) { workspaceUI.setReady(true, error); return; }
    }
    workspaceUI.setReady(true);
    if (pageParameters.has('import')) await workspaceUI.importPage();
}
```

- 更完整版：把 `lastRefreshAt`、`lastCredentialSyncAt`、`lastSnapshotPullAt` 以 scope key 持久化到 localStorage（TTL 5–10 分鐘），`syncExtensionAccountAI` 增加 `maxAgeMs`；登入／手動同步仍 `force`。同一帳號連開多個文章視窗只會有第一次完整同步。
- 文章視窗的 `captureUI.sync()`（書單）與 `workspaceUI.sync()`（outbox）可延後到預覽後（`requestIdleCallback`）；文章路徑不需要書單，outbox 重試不該擋預覽。
- `findExistingPageArticle` 的 GET 可用 ticket 的 `pageUrl` 與 `readPage()` 並行，`readPage()` 回來後比對 URL 再採用。

**風險**：遠端設定／catalog 最多延遲 TTL；`SIGNED_IN`／`ACCOUNT_CHANGED` 必須維持強制同步；既有測試若在開窗後立刻斷言 catalog 狀態可能需要調整等待條件（本次兩個基線測試不受影響）。

**驗證**

- route 記錄請求：文章視窗「文件建立→第一個 AI」的請求集合不含重複 `/ai-catalog`、`/ai-credentials`、`/snapshot`（或 TTL 內跳過）。
- 冷啟仍完整同步一次；登入後立刻開窗 → 跳過；手動同步 → 仍強制。
- 清掉本地 meta（模擬 TTL 過期）→ 自動回退完整 sync。

**預期收益**：少 3 個往返（本次 mock ~0.4s；真實 300ms RTT ~0.9s），降低 Worker 壓力。

### P0-3　保存尾段往返與「確認前寫入」（尚未改）

**證據**

- `shared/workspace-client.mjs:65`：POST `/articles` 前先 GET `/vocabulary/books?sourceUrl`；但 POST 已帶 `clientMutationId`，且 409 `article_id_exists`（同 URL）會 reuse（`:78-90`），GET 幾乎只是多一個往返（同時也是 `findExistingPageArticle` 已查過的同一件事）。
- `modules/extension-workspace.js:31-49`：查重後直接 `POST /vocabulary/page-link`（`:46`），發生在使用者按確認之前（實測 S7：`linkWrites: 1`、`articlesUnchanged`）。
- `extension/workspace-ui.js:115`：保存成功後 `await captureUI.refreshBooks()`（多一個 GET）。
- 實測 S3 尾段：GET books?sourceUrl → POST /articles → POST page-link → GET books，4 個連續往返。

**建議**

- `workspace-client.send`：移除第一個 GET；直接 POST，保留 409 同 URL reuse／deletedAt 重試分支。先加回歸測試再移除。
- `findExistingPageArticle` 改成只查不寫；`page-link` 移到 `openArticle()`（按「在 BDC 打開」時）或保存確認後（`send` 內已有 page-link）。若產品要求「提取即關聯同頁詞書」，至少做成使用者可見的明確動作。
- `applyReceipt` 的 `refreshBooks()` 改成背景（不 await）或延後到開啟「詞書設定」dialog 時。
- 查重 GET 與 `readPage()` 並行（見 P0-2）。

**風險**：舊 Worker 對 POST 同 URL 的行為要先確認；page-link 延後會讓「已存在文章」暫時沒有同頁詞書關聯（需產品確認或改成開啟時關聯）；書單延後只影響 capture UI。

**驗證**

- 保存請求集合：只允許 POST /articles、POST page-link，不得再有 GET books?sourceUrl；尾段 4→2 RTT。
- 已存在頁面按提取：**沒有任何 POST**（含 page-link）、沒有文章新增、顯示沿用與「在 BDC 打開」。
- 遺失回覆：讓 POST /articles 第一次回 503（helper 可擴充 `loseNextReply` 到 `/articles`），確認 outbox 保留、重試只送一次、DB 只有一篇、analysis 不重送。

### P0-4　剛實作的並行分析：兩個必須補的點

#### 4a. 失敗仍會 abort 兄弟 worker、沒有失敗清單

目前 `modules/extension-ai-runtime.js:636-639`：

```js
} catch (error) {
    if (!failure) failure = error;
    controller.abort(error);   // ← 把另一個 in-flight 請求也砍掉
}
```

- 任一段失敗就停止所有 worker，後面的段落不會跑；另一個已送出的請求被 abort，token 白花。
- 沒有 `failedIndexes`／`causeCode`；重試只能整批重來（成功段落靠快取省請求）。
- 實測 S5（6 段、第 2 段失敗）：首輪送 6 個請求（含被 abort 的），重試 3 個請求、5858ms。改前 fail-fast 是首輪 4 個、重試 4 個、10887ms；目前總時間有改善，但第一輪仍會丟掉正在跑的段落。
- 失敗段落仍會送 2 個請求（候選 + plain fallback，`modules/api.js:1149-1225`）；若是 401／金鑰錯誤，因為 fail-fast 只會打到第一段的 2 個請求（候選 + fallback）就停，不會每段都打；但 notice 是泛用「段落分析未完成」，看不到真正原因。

**建議**

- 內容層失敗（`empty_translation`、`provider_error`、timeout 等）→ **不要 abort 兄弟**；跑完所有 job，記 `failed = [{index, code}]`，最後 throw `page_analysis_failed` 並帶 `failedIndexes`、`causeCode`。成功段落已在快取，重試只會對失敗段發請求。
- 設定／認證類（`unauthorized`、`ai_key_missing`、`ai_key_binding_mismatch`、`invalid_response`）→ 立刻 abort 整批，帶 `causeCode`，讓 `getAIErrorTranslationKey` 顯示正確提示。
- 使用者停止／換帳戶／locale 變更 → 維持 abort（現行正確）。
- UI：notice 顯示「{count} 段失敗，可重試」；主按鈕直接重試（見 P1-3）。

**風險**：跑完所有段會讓使用者在「確定失敗」時多等一點（但可拿回其他段成果）；429 時可能多花請求。可用「連續 2 段失敗就停」的折衷。

**驗證**

- 只讓第 3 段失敗：第一次跑完 0/1/2/4/5（成功段落各 1 請求，失敗段 2 請求），DB 無文章；重試只對第 3 段發請求；最後 analysis 7 段齊全且順序正確。
- 401：只打第一段的 2 個請求，notice 顯示登入／金鑰錯誤。

#### 4b. `catalogGeneration` 造成「設定已更改」假中止（新 bug）

- `modules/extension-ai-runtime.js:582` 把 `catalogGeneration` 放進 context snapshot；`modules/ai-catalog.js:410` 在**每次成功刷新** catalog 時 `state.generation += 1`（即使版本、任務映射都沒變）。
- `contextChanged` 監聽 `bdc:ai-catalog-change`（`:600-601`），refresh 完成 → 事件 → `assertCurrent()` 發現 generation 變了 → abort 分析。
- 實測 `bdc-catalog-abort.cjs`：分析中觸發一次 `refreshAICatalog({force:true})`，catalog `version 1→1`、`generation 2→3`，2 個 in-flight 段落被 abort，文章 0，notice「语言或 AI 设置已更改，正文预览已保留…」。這不是使用者改了設定，是背景刷新。
- 生產環境 5 分鐘前景刷新（`CATALOG_REFRESH_INTERVAL_MS = 5 * 60 * 1000`）與 focus／visibility 刷新（60 秒間隔）都可能觸發；長文章分析有機會被打斷。

**建議**

- 從 context snapshot 移除 `catalogGeneration`；保留 `catalogVersion` 與**有效的** `tasks`／provider 映射（必要時只比較 `getCatalogState().tasks` 與實際使用的 provider 條目）。
- 若要偵測「managed key 被清空」，監聽 `AUTH_EVENT`／scope 變更即可（已有），不要用 generation。
- 只有「choice、實際任務模型／thinking、provider 設定、locale」變了才 abort；refresh 但版本／任務不變 → 不 abort。
- 文案：若真的是設定變更，再顯示 `pageAnalysisSettingsChanged`；catalog 刷新不該用這句。

**風險**：如果 catalog 真的換了版本但任務映射剛好沒變，理論上 provider 可能被替換（apiUrl/key）；以 version 有變時仍可 abort（版本號是更精準的訊號）。

**驗證**

- 新測試：分析中呼叫 `refreshAICatalog({force:true,reason:'test'})`，catalog 內容不變 → 分析應完成並保存。
- 另一個測試：真的改 `articleParagraphTranslation` 的模型（寫入 profile 並觸發事件）→ 應 abort 並顯示「設定已更改」。
- 既有 article-confirm / compact 測試保持通過。

#### 4c. 微觀成本（可選）

- `assertCurrent()` 每次呼叫都 `loadAIProfile(scope)` + `JSON.stringify(contextSnapshot())`（`:585-596`），在每個段落前後、`analyzeParagraph` 內外都會跑；長文章會多幾十次 localStorage 解析。可在 operation 開始時快照一次，之後只在事件發生時重算（`contextChanged` 已經是事件驅動）。
- `cacheContext` 把整個 profile（含所有 provider 的 `updatedAt`）塞進快取 key（`:587`），任何無關 provider 的儲存都會讓段落快取失效；可只取實際使用到的 provider/task 條目。

## 5. 測試補強設計（確保六件事）

以下測試可加在 `tests/extension-article-confirm.cjs` 或新的 `tests/extension-article-parallel.cjs`，沿用 `tests/helpers/extension-mv3.cjs`（真 MV3／Worker／SQLite，只 mock AI transport）。

### 5.1 並行後原文順序

- AI route 依 prompt 中的段落標記回傳不同譯文；**故意讓第 3 段最快、第 1 段最慢**。
- 斷言：
  - `analysis.paragraph_analysis[i].chinese_translation` 對應正文第 i 個 block（不是完成順序）。
  - `analysis.chinese_translation` 以 `\n\n` join 後順序正確。
  - DB `body` 與 analysis 的段落索引一致。
- 同時在 route 記錄 start/end，斷言 in-flight 最大值 = 2（或設定值），且至少一次 ≥2。

### 5.2 編輯後正文

- 既有測試已覆蓋「編輯後分析使用新正文」；補「只改一段」：
  1. 先讓分析在第 2 段失敗。
  2. 修改第 1 段文字，重試。
  3. 斷言送出的 prompt 只包含修改後的第 1 段與第 2 段，其他段 0 請求（快取命中）。
  4. 斷言 DB 保存修改後正文、analysis 順序完整。

### 5.3 零確認前請求／寫入

- 在 context 層記錄所有請求；定義白名單：
  - 允許：`GET /me`、`GET /ai-catalog`、`GET /ai-credentials`、`GET /snapshot`、`GET /vocabulary/books*`、managed credential、`articleCleanup`（若保留 AI 清洗）。
  - 禁止：任何 `articleParagraphTranslation`／`articleAnalysis`／`articleWordTranslation`、`POST /articles`、`POST /vocabulary/page-link`、`POST /captures`、任何 outbox key。
- 特別加「已匯入過的頁面再提取」：現況會出現 `POST /vocabulary/page-link`，改完 P0-3 後應為 0；防回歸。
- 既有測試只檢查 translations/writes/pending，建議擴充成完整白名單。

### 5.4 abort／換帳戶不串資料

- **分析中按停止**：等第一個段落請求發出後按停止；斷言 `requestfailed` 有 abort、DB 文章 0、outbox 0、notice = 已停止、預覽保留、再按確認可成功。（目前工作區已符合，見 `abort-extract.json`／S6。）
- **多 chunk 清洗中按停止**：斷言沒有預覽、notice = 已停止。
- **分析中切 Bob**：沿用 `bdc-account-switch.cjs`；斷言 Alice/Bob 都沒有該 URL 文章、outbox 0、預覽／標題／正文清空；切回 Alice 再提取正常。目前重測：2 個 in-flight abort、0 文章、0 outbox。
- **切回後舊請求回覆不得寫入**：route 延遲回覆，切換後才 fulfill，驗證 epoch／session guard。
- **送出行程中切帳戶**：目前 send 不受 signal 影響；切換後 job 屬於舊 scope，`pending()` 會視為 invalid 或不同 scope。斷言新帳戶看不到、也不會被自動送出。

### 5.5 失敗不存半成品

- 已有：分析失敗保留修改後正文、無文章、無 outbox。
- 補：部分段落失敗（只第 3 段）→ 文章仍未寫入；成功段已在快取；重試只送失敗段；最後 analysis 含全部段落且順序正確。
- 補：`POST /articles` 失敗（503）→ outbox 保留含 analysis 的 job；重試成功；DB 只有一篇；段落翻譯請求不因重試而增加。
- 補：`POST /articles` 成功但 `POST page-link` 失敗 → job 保留；重試 GET 看到 articleId → reuse，不重複建立；outbox 清空。
- 補：提取 truncation／chunk failure 的文案與「不半成品」策略（依產品決策）。

### 5.6 重試只重做失敗段

- AI route 以段落文字計數：
  - 第一次：失敗段（假設第 3 段）2 個請求（候選 + fallback），其他段各 1。
  - 重試：只有第 3 段有請求（2 個），其他段 0。
- 再加「改模型後重試」：cache key 含 model/thinking/context，應全部重送（避免跨模型錯誤重用）。

### 5.7 新增：背景 catalog 刷新不得中止分析

- 分析進行中，從文章頁呼叫 `refreshAICatalog({force:true,reason:'test'})`，catalog 版本與任務映射不變。
- 斷言：分析完成、文章保存、沒有 `article_context_changed` notice。
- 反向測試：真的改 `articleParagraphTranslation` 模型 → 應 abort、notice = 設定已更改、DB 無文章、預覽保留。

### 5.8 其他

- **雙擊確認**：連續兩次點 `#ext-article-save` → 只有 1 個 outbox job、1 次 POST /articles。
- **多視窗同 URL**：同時確認 → 只建立 1 篇（第二個 409 reuse）、無重複 outbox。
- **i18n**：新增文案跑 `node tests/audit-i18n.mjs`（只看 `extension/`；此腳本會掃到 `.claude/worktrees` 的雜訊），人工切 `zh-CN`／`zh-HK`。
- **效能護欄**：用 route 的 start/end 斷言「清洗 chunk 有重疊」「段落分析有重疊」，不要用絕對秒數。

## 7. 實測限制

1. **AI 是 mock**：固定 2.5s 延遲，沒有真實 TTFT、排隊、rate limit、thinking token 差異；比例可參考，絕對秒數不可對外承諾。

3. **Headless Chromium**、無 CPU/網路 throttle；每個 extension 視窗是獨立 document（module state 不共享），這是冷啟重複同步的根因之一。
4. **快取影響**：段落快取（IndexedDB）跨情境保留；S6 必須用不同段落文字才能觀察完整序列。真實使用者第二次匯入同一頁會很快，不代表第一次也快。
5. **what-if**：在文章視窗內直接呼叫生產 `analyzeParagraph`／`aiCleanArticleMarkdown`（同一 module instance、同一佇列與快取），只差呼叫端併發；不是 UI 全鏈路，但足以代表 P0-1／4a 的上限。
6. **未測**：Service Worker 被回收後重啟、MV3 event page 冷啟、個人供應商 vs managed catalog、TTS／朗讀、正式站同步延遲。
7. **未測**：真實 provider 的 429 行為；並行後若碰到 429，`requestAI` 退避會拉長總時間，需在正式 provider 實測再決定上限。
