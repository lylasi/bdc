# 文章詳解「本文學習記錄」側欄優化整合評估報告

- 評估日期：2026-10-28
- 整合者：主代理；獨立評估協作者：使用者指定的 DeepSeek Harness
- 範圍：文章詳解內的「本文學習記錄」面板，包含桌面側欄、手機底部面板、詞句記錄、全篇筆記、保留的 AI 資料及相關操作。
- 依據：目前工作區程式碼、現有測試、兩個獨立瀏覽器評估及主代理交叉複核。未修改業務程式碼。
- DeepSeek 原始報告：[獨立評估](20261028014059796_DeepSeek文章學習記錄側欄獨立評估.md)。本報告已去重、調整優先級，並區分已確認行為與產品建議。

## 1. 核心結論

這個側欄的功能基礎已完整，最值得優化的是「快速找到記錄、對照原文、繼續學習」這條路徑。現在每張卡片預設呈現編輯表單和多項工具，瀏覽密度低；同時存在刪除、狀態提示、篩選計數及平板版面等實際問題。

**建議方向：以緊湊的記錄清單作主體，選中記錄才展開詳情與筆記；桌面可以並排對照原文，手機可以方便返回同一條記錄。** 現階段優先修正記錄可靠性和布局，再擴充搜尋、排序及 AI 資料追溯。

最優先處理五件事：

1. 文件刪除缺乏確認／復原；詞句記錄刪除後再查同一處，仍可能不出現在清單。
2. 本機讀取失敗會顯示「還沒有學習記錄」，與真正沒有資料混淆。
3. 1024px 同時展開左右兩側時正文只剩約 44px；768–899px 的側欄會覆蓋正文。
4. 篩選列把「AI 資料」「只看已收藏」放到預設視野之外；數字與實際內容不完全一致。
5. 手機每張卡片約 344px 高，390×844 畫面的清單區僅約 453px，首屏只能完整看一張。

## 3. 實測方式與關鍵數據

主代理使用獨立 Chrome context、合成文章及合成學習資料：11 條詞句記錄、1 份全篇筆記、1 份 AI 資料、1 個有效詞書關聯。攔截私有設定為合成設定，阻斷外部請求；沒有使用正式帳戶或既有瀏覽器資料。

檢查包含 1440／1024／834／768／767／390／320px 寬度、390px 觸控 context、zh-CN／zh-HK、篩選與空結果、定位、刪除、重查，以及模擬 IndexedDB 讀取失敗。主代理保存了 22 組觀察；這是定向 UX 核驗，不代表整個應用測試全部通過。

## 4. 整合後的優化建議

優先級：**P1**＝影響資料可信度或基本可用性，第一批處理；**P2**＝改善主要閱讀／複習路徑；**P3**＝延後擴充，先確認使用需要。這裡是產品排程優先級，並非安全漏洞分級。

### U1 · P1：統一刪除、復原與「重新查閱」語意

**已確認：** 詞句刪除有確認；AI／全篇筆記刪除直接生效。兩類都沒有使用者可見的復原入口。學習項目採穩定 ID，資料層會保留已刪除實體的 `deletedAt`；經實際 `recordExplanation()` 入口重查同一處，保存成功但記錄仍隱藏。

**影響：** 誤刪筆記缺乏挽回途徑；使用者以為重新查詞已保存，列表卻找不到該項，削弱對學習記錄的信任。

**建議：**

- AI／全篇筆記刪除加入確認，清楚顯示所刪內容的標題及範圍。
- 兩種刪除都提供短時間「復原」，並處理保存失敗提示。資料雖然是軟刪除，復原仍需走正式寫入及同步流程，不可只讓卡片重新顯示。
- 明確把「使用者主動重新查閱」設計成重新記錄／恢復入口；背景預取或舊同步回應不得自行復活已刪資料。同步刪除衝突規則需一起驗證。
- 說清楚刪除學習記錄、刪除記錄內筆記、保留詞書條目各自的影響，避免把目前確認文字中的「筆記會保留」理解為所有筆記都能在側欄找回。

證據：[刪除 handler](../../features/article/reading-panel.js:722)、[文件刪除](../../features/article/reading-panel.js:751)、[穩定 ID](../../modules/reading-store.js:790)、[保留 deletedAt](../../modules/reading-store.js:805)、[重查保存入口](../../modules/reading-actions.js:138)。主代理與 DeepSeek 交叉確認。

### U2 · P1：區分載入、真正空白、篩選無結果及讀取失敗

**已確認：** 面板打開時等待資料但沒有明確載入狀態；載入結果沒有依 `ok:false` 分支處理。空列表只有同一句文案。兩方均以讀取失敗注入確認，錯誤沒有變成可見的錯誤提示或重試。

**建議：**

- 載入中：顯示短提示及 `aria-busy`，保留正在讀取的文章身份。
- 全篇真的沒有資料：說明查詞、標記或筆記會建立記錄，提供可執行入口。
- 篩選無結果：顯示目前條件及「清除篩選／顯示全部」。
- 讀取失敗：明確告知未能讀取本機記錄，提供重試；不要顯示資料為零。
- 同步失敗與本機讀取／保存失敗分開表達，沿用既有狀態區與筆記重試能力。

證據：[開啟載入](../../features/article/reading-panel.js:136)、[唯一空態](../../features/article/reading-panel.js:463)、[換文章載入](../../features/article/reading-panel.js:1064)、[資料層錯誤回傳](../../modules/reading-store.js:280)。主代理與 DeepSeek 交叉確認。

### U3 · P1：按正文可用寬度協調兩個側欄，補齊平板斷點

**已確認：** 底部面板從 ≤767px 生效，正文讓位從 ≥900px 開始，768–899px 形成覆蓋區間。900–1199px 雖有讓位，仍可能同時容納全站導航、輸入欄、正文、學習記錄欄，導致正文過窄。

**建議：**

- 設定正文最小可讀寬度；空間不足時，打開學習記錄先暫時收起輸入／設定區，保留原先偏好，關閉時按情境恢復。
- 平板寬度採明確的抽屜／底部模態，或重新分配版面；不要在沒有遮罩提示時直接壓住正文。
- 桌面讓記錄欄寬度在合理範圍內調整，優先確保文章閱讀區；不以固定 900px 作為唯一判斷。
- 驗收必須同時覆蓋「輸入欄開／關」「記錄欄開／關」，不能只驗證其中一個側欄。

證據：[手機模式](../../styles.css:6995)、[桌面讓位與窄桌面欄寬](../../styles.css:7036)。由主代理跨尺寸實測補充，DeepSeek 確認兩種面板模式的基本行為。

### U4 · P1：讓既有篩選看得見，統一篩選與計數

**已確認：** 篩選列 `overflow-x:auto` 且隱藏捲軸。本次主代理量到內容寬 618px，而面板篩選可視區只有 320–439px。AI 資料及收藏條件通常不在初始視野，雖可橫捲操作，但沒有明確提示。「全部」「有筆記」漏計全篇筆記；收藏條件不約束文件。

**建議：**

- 桌面可容許兩行篩選；手機用清楚的「更多篩選」入口並顯示生效條件。避免新增搜尋後又堆出過高的固定工具區。
- 「只看已收藏」改用更準確的「已加入詞書」，與內容類型分開；在 AI／全篇筆記視圖停用不適用條件，或清楚限定為詞句範圍。
- 由同一個可見資料集合計算計數、列表及結果摘要。此合成案例「全部」應可對應 13 張卡；「有筆記」應可對應 3 張卡，或明確拆分成詞句筆記與全篇筆記。
- 全篇筆記卡的類型標籤使用「全篇筆記」，不要借用篩選文字「有筆記」。
- 副標顯示「11 條詞句 · 1 份全篇筆記 · 1 份 AI 資料」一類清楚的組成，並補充目前顯示數。

證據：[篩選與計數](../../features/article/reading-panel.js:299)、[文件篩選](../../features/article/reading-panel.js:463)、[副標與徽章](../../features/article/reading-panel.js:928)、[橫捲樣式](../../styles.css:6745)。雙方確認可見性和計數；主代理補充收藏條件的實際範圍。

### U5 · P2：卡片改為摘要瀏覽，筆記及次要操作按需展開

**已確認：** 所有項目無條件渲染 textarea；「標記／取消標記」旁又顯示「未標記／已標記」；每卡再列加入詞書、回原文、問 AI、刪除等操作。句子卡還會同時顯示引用與相同的原句文字。

**建議：**

- 摘要顯示：引用文字、簡短詞義／譯文、類型、標記／詞書／筆記提示，以及必要時間。
- 無筆記顯示「寫筆記」；有筆記先顯示一至兩行預覽。選中／編輯才展開輸入框。
- 常用動作保留「回原文」「標記」；問 AI、加入詞書、刪除等視狀態收進更多選單，危險操作與常用操作分開。
- 句子卡避免重複呈現相同英文句子；完整上下文按需展開。
- 從詞卡「寫筆記」進入時，自動展開並聚焦目標項，保留既有自動儲存、錯誤重試與草稿機制。

**設計目標，尚非完成數據：** 390×844 首屏可掃描至少 3 個一般短詞條摘要；卡片高度依內容而非固定表單決定。此項在 DeepSeek 報告屬較後順位，本報告因手機實測密度偏低而提升至 P2，建議與工具區簡化一起做。

證據：[卡片模板](../../features/article/reading-panel.js:408)、[固定筆記區](../../styles.css:6824)。雙方確認，主代理補充具體卡高。

### U6 · P2：收斂底部工具區，釐清匯出範圍

**已確認：** 固定底部包含兩個全文／聊天選項及五個操作；Markdown 匯出打開後，對話框又提供同類選項及完整 JSON 備份。JSON 備份的範圍是目前帳戶／端點，超出單篇文章側欄的直覺範圍。

**建議：**

- 底部保留「全篇筆記」「匯出／更多」等少量入口；AI 難點分析與筆記整理放入同一個「AI 整理」選單。
- 全文／對話選項只在匯出範圍對話框出現，繼續記住上次選擇；不在側欄長期佔位。
- 明確標示「匯出本篇」與「備份目前帳戶」，避免完整備份與本篇內容混淆。
- 先利用既有範圍對話框整合入口，不新增另一套匯出流程。

證據：[底部工具](../../features/article/reading-panel.js:72)、[匯出範圍對話框](../../features/article/reading-panel.js:602)、[手機底部樣式](../../styles.css:6995)。主代理整合建議，DeepSeek 也提出工具區簡化。

### U7 · P2：增加搜尋與少量排序，改善長記錄清單

**已確認：** 有分類篩選，但沒有文字搜尋或排序控制。詞句按原文位置排序，文件按更新時間排序後接在後面；時間欄位存在，但詞句卡只顯示已查閱。位置未知（`start=-1`）自然排到正常原文位置之前。

**建議：**

- 搜尋涵蓋引用、詞義／譯文、原句、個人筆記及文件標題；搜尋文件正文可按需載入，不擴大整站啟動讀取量。
- 排序先提供「原文順序」「最近查閱」「最近修改」，預設仍可沿用原文順序，不強制改成時間軸。
- 記錄顯示簡短時間及完整日期提示，避免把查閱時間誤作已掌握程度。
- 位置待確認獨立成組，提供「重新定位」；不得猜測貼到第一個同字。
- 搜尋與篩選條件應可見；切文章時重置或按文章保留，避免沿用舊條件造成假空態。

證據：[條目排序](../../modules/reading-store.js:718)、[文件排序](../../modules/reading-store.js:1554)、[現有定位更新接口](../../modules/reading-store.js:1101)。雙方確認。優先使用既有欄位，首批搜尋排序無須新增同步 schema。

### U8 · P2：讓「記錄 → 原文 → 記錄」形成連續路徑

**已確認：** 點「回原文」會保存草稿、關面板、捲動到句子並閃爍；焦點回到面板開啟按鈕。使用者仍可重開面板，但沒有回到原項目的專用入口。普通重繪不保證恢復先前卡片焦點及展開狀態。

**建議：**

- 桌面確保正文可讀後，定位時保留側欄及當前項目，讓使用者邊讀邊對照。
- 手機可暫時收起面板，提供「返回這條記錄」入口，恢復原篩選、捲動、選中項與草稿。
- 定位時提示具體詞語或短語；有精確錨點時突出該範圍，句子作上下文。
- 位置失效提供重新選取定位及複製引用；錯誤提示後仍保留原記錄。
- 記錄級 URL 可後續評估，不是改善這個互動的前置要求，也不等於開放分享。

證據：[定位行為](../../features/article/reading-panel.js:761)、[特定項筆記入口](../../features/article/reading-panel.js:1043)。雙方確認；本報告避免把「沒有專用返回」誇大成完全無法重開。

### U9 · P2：AI 資料顯示可讀內容與來源，銜接既有助手

**已確認：** AI 文件已保存 `sourceItemIds`、`sourceMessageIds`、`contentVersion`，但卡片只顯示標題、日期、收起的純文字 `<pre>` 和刪除。Markdown 原文中的標題、粗體、清單不會被呈現成格式。生成整理會建立新文件，固定標題可能重複。對話本身由助手管理，側欄「AI 資料」不等同聊天歷史。

**建議：**

- 預覽 AI 資料摘要，展開時延用既有安全 Markdown 渲染能力。
- 顯示「來源 N 個詞句／來自某次對話」；點擊可回到相關記錄或助手會話。若來源已刪／尚未載入，給明確狀態。
- 新舊整理用生成時間、範圍及版本區分，提供明確的「建立新版／取代這份」動作，避免靜默覆寫舊內容。
- 優先在匯出對話框提供將附帶的對話摘要與查看入口；是否把聊天歷史搬入側欄，列 P3 決策，避免重複建造助手管理介面。
- 模型與生成設定未完整保存到現有文件實體；若日後要展示，需補來源資料，不可把當前設定推算成歷史模型。

證據：[文件模板](../../features/article/reading-panel.js:445)、[保存 AI 回覆](../../modules/reading-actions.js:261)、[生成資料](../../modules/reading-actions.js:303)、[文件欄位](../../modules/reading-store.js:1567)。雙方確認現狀；主代理將 DeepSeek 的「新增完整 AI 對話分組」收斂為先銜接既有助手。

### U10 · P2：保留焦點，讓手機模態及輔助功能一致

**已確認：** 篩選及卡片重建會令焦點掉到 `body`；本次標記操作的列表捲動位置保持，沒有證據表明每次都跳回頂部。手機有遮罩，面板卻始終 `aria-modal=false`，Tab 可離開面板。多個刪除按鈕沒有帶記錄引用的名稱。

**建議：**

- 更新篩選選中狀態和受影響卡片，或按項目 ID 還原焦點；不把整區 HTML 重建當作每次操作的唯一方法。
- 手機模式同步設定模態語意、背景不可操作及焦點循環；桌面非模態保留原文可操作性。
- 刪除等重複操作加上引用／文件標題的 `aria-label`；清單和卡片提供適當語意及標題。
- 操作後播報「顯示 X 項」；不要把整份長清單設成即時播報區。
- 手機軟鍵盤遮擋需實機驗證，必要時沿用專案已有的可視視窗處理；本次不把未實測情況列為已發生缺陷。

證據：[面板語意](../../features/article/reading-panel.js:51)、[篩選重建](../../features/article/reading-panel.js:322)、[列表重建](../../features/article/reading-panel.js:463)、[筆記編輯保護](../../features/article/reading-panel.js:892)。雙方確認焦點問題；保留既有輸入草稿保護與切語言恢復能力。

## 6. 推薦實施順序與驗收

### 第一批：可信度與可用性修正

涵蓋 U1、U2、U3、U4，以及 U10 的焦點與危險操作標籤。先把現有功能修準。

驗收要求：

- 文件刪除可取消、可復原；保存／刪除失敗有明確反饋。
- 主動重查已刪項的產品行為明確且可測；背景回應不自行復活刪除記錄。這部分要與同步資料層一起處理。
- 真空態、篩選空結果、讀取失敗、載入中各自正確顯示；失敗後可重試。
- 相同合成資料下，「全部」13 張卡、「有筆記」3 張卡，徽章／副標／篩選數字符合定義；收藏條件的適用範圍可理解。
- 320／390／768／834／1024／1440px，輸入欄與記錄欄所有開關組合都可讀，沒有未提示的覆蓋或極窄正文。
- 篩選／標記後焦點保留，筆記草稿不丟失；兩種語言都走一次成功、失敗、重試流程。

### 第二批：提升瀏覽與複習效率

涵蓋 U5、U6、U7、U8；補完手機模態行為。這批最能改善「側欄用起來累」的感受。

驗收要求：

- 短詞條摘要在 390×844 首屏可掃描至少 3 項；長句依內容換行，不以硬截斷犧牲必要資訊。
- 筆記可從詞卡直接開啟目標編輯；自動儲存、關閉前 flush、匯出前 flush、重試均保留。
- 搜尋與排序之後編輯不失焦；清除條件可回全部。
- 桌面可對照原文；手機「回原文 → 返回記錄」恢復同一項及原位置。
- 匯出只在一處決定全文／對話選項；本篇匯出與帳戶備份界線清楚。

### 第三批：資料追溯與延伸複習

涵蓋 U9；再評估跨文章筆記索引、批次整理及複習模式。完整聊天分組、間隔複習、新的理解程度狀態及記錄分享都不是首批必要範圍。

若新增持久化欄位，需一起核對 reading protocol、store、雲端／selfhost 同步及備份還原。復原與重查涉及刪除實體、outbox 及跨裝置衝突，不能只修改面板 DOM。

本次沒有修改產品，因此未重跑整站測試。實施時優先沿用：
