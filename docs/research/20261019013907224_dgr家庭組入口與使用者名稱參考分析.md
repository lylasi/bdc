# dgr 家庭組入口與使用者名稱參考分析

- 日期：2026-10-19
- 參考專案：`/Users/linus/CODE/dgr`
- 目的：評估 dgr 的「家庭組入口」與「使用者名稱」設計，是否可套用到 BDC 目前的登入碼／階段 2 帳號密碼方案。

## 1. dgr 的家庭組入口

### 1.1 資料模型

`src/lib/db.ts`：

```sql
CREATE TABLE families (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  timezone TEXT NOT NULL,
  status TEXT NOT NULL,              -- active / inactive
  entry_code TEXT NOT NULL UNIQUE,   -- 16~100 字元
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

另有 `family_bosses(family_id, boss_id, display_name_override)` 與 `workers(family_id, ...)`，所有業務資料都帶 `family_id`。

### 1.2 入口碼的產生與生命週期

`src/lib/account-service.ts`：

- 建立家庭：`randomBytes(18).toString("base64url")`，即 24 個 URL-safe 字元。
- 輪換入口：`rotateFamilyEntryCode()` 重新產生 24 字元入口碼，舊連結立即失效。
- 查詢入口：`getActiveFamilyByEntryCode()` 只接受 16~100 字元，且家庭必須是 `active`。

入口碼的性質：

- **長期有效**，不是一次性。
- **不是登入憑證**，本身不能取得任何角色權限。
- **可輪換撤銷**：輪換後舊連結與舊 QR 立即失效。
- 用於識別「哪一個家庭（tenant）」，不是「哪一個人」。

### 1.3 前端入口流程

- 路由：`/family/{entryCode}`（`src/app/family/[entryCode]/page.tsx`）。
- 根首頁 `/`：
  - 可設定是否公開家庭目錄（`public_family_directory_enabled`）。
  - 公開時列出所有啟用中家庭，點擊進入 `/family/{code}`。
  - 無論是否公開，都提供「已有家庭入口」輸入框，可貼完整網址或直接輸入入口碼（`familyEntryPathFromInput()`）。
- `GET /api/bootstrap?entryCode=...`：
  - 驗證入口碼；無效回 `FAMILY_ENTRY_NOT_FOUND`。
  - 只回傳該家庭的公開角色（小朋友）與老闆清單。
  - 若入口家庭與目前 session 的作用中家庭衝突，會抑制 `activeIdentity`，避免跨家庭操作。
- 進入家庭後，畫面是角色選擇：小朋友需要 PIN，老闆需要帳號密碼。
- QR code 只編碼家庭入口 URL；UI 明確提示「進入具體角色仍需 PIN 或老闆帳號」（`src/components/family-entry-qr.tsx`）。
- 老闆設定頁與系統管理員家庭編輯頁都提供「複製入口／顯示 QR／輪換入口」（`admin-app.tsx`、`system-admin-app.tsx`）。

### 1.4 安全邊界

- 入口碼外洩只會暴露該家庭的公開角色名稱／頭像，以及「這個家庭存在」；不會直接取得資料或管理權。
- 關閉公開目錄不會讓已知入口失效；要撤銷必須輪換入口碼。
- 家庭隔離由伺服器端每個 API 的 `family_id` 檢查保證，不是只靠前端路由。

## 2. dgr 的使用者名稱設計

### 2.1 資料模型

`boss_accounts`：

```sql
username TEXT NOT NULL COLLATE NOCASE UNIQUE
  CHECK(length(trim(username)) BETWEEN 3 AND 50),
display_name TEXT NOT NULL,
password_hash TEXT NOT NULL,
auth_version INTEGER NOT NULL DEFAULT 1,
is_active INTEGER NOT NULL DEFAULT 1
```

- 使用者名稱與顯示名稱分離。
- `username` 全域唯一、**大小寫不敏感**（`COLLATE NOCASE`）。
- 同一帳號可透過 `family_bosses` 加入多個家庭；每個家庭可有不同的 `display_name_override`。

### 2.2 使用者名稱規則

`src/lib/account-service.ts`：

```js
const USERNAME_PATTERN = /^[\p{L}\p{N}][\p{L}\p{N}._-]*$/u;
```

- 3~50 字元。
- 必須以文字或數字開頭。
- 允許文字、數字、點、底線、橫線（支援 Unicode）。
- 查詢時 `WHERE username = ? COLLATE NOCASE`。

### 2.3 登入與 session

- 登入：`POST /api/auth`，`action: "boss_login"`，使用者名稱＋密碼。
- 密碼：`src/lib/password.ts` 使用 Node `scrypt`（salt + 64 bytes），最低 8 字元。
- `auth_version`：
  - 登入成功後把 `bossId -> authVersion` 寫入 session。
  - 修改密碼會遞增 `auth_version`，其他裝置的舊 session 立即失效。
- 多家庭：
  - 只有一個家庭 → 自動進入。
  - 多個家庭 → 回傳 `familySelectionRequired: true` 與家庭清單，前端顯示家庭選擇。
- 已記住的裝置可直接點老闆帳號切換，不需要重新輸入密碼（session 內已保存授權版本）。
- 登入限流：以 `client + username` 為 key，5 次失敗後指數退避，最長 60 秒（`src/lib/rate-limit.ts`）。
- Session 是 HMAC 簽章的 httpOnly cookie，預設 180 天。

## 3. 與 BDC 目前階段的差異

| 項目 | dgr | BDC 階段 1 |
| --- | --- | --- |
| 入口碼用途 | 選擇家庭（tenant） | 登入單一使用者 |
| 入口碼壽命 | 長期，可輪換 | 10 分鐘 / 24 小時 / 7 天 / 30 天 |
| 是否一次性 | 否 | 是 |
| 是否為登入憑證 | 否 | 是 |
| 登入方式 | 使用者名稱＋密碼、小朋友 PIN | 一次性登入碼／既有通行碼 |
| 多使用者歸屬 | 一個老闆可屬多個家庭 | 每個使用者獨立，無群組 |
| 資料隔離 | `family_id` | `user_id` |
| 顯示名稱 | 與 username 分離，可按家庭覆寫 | `label`，無 username |

關鍵差異：

- dgr 的入口碼解決「進入哪個家庭」，dgr 的帳號密碼解決「你是誰」。
- BDC 的登入碼同時解決「你是誰」與「證明身份」，所以必須一次性、短效、可撤銷。
- BDC 目前沒有群組層；若直接引入家庭入口，必須先決定群組要解決什麼問題。

## 4. 可參考的部分

### 4.1 可直接參考：使用者名稱與帳號模型（階段 2）

若日後要做使用者名稱＋密碼：

1. `users` 增加 `username`（`COLLATE NOCASE UNIQUE`）與 `auth_version`。
2. `user_id` 保持不可變；`label` 作為顯示名稱，不作為登入識別。
3. 使用者名稱規則沿用 dgr：3~50 字元、Unicode 文字／數字＋`._-`、必須以文字或數字開頭。
4. 大小寫不敏感查詢與唯一性。
5. 密碼變更／管理員重設時遞增 `auth_version`，session 記錄版本，讓舊裝置失效。
6. 登入限流以 `client + username` 為 key，而不是只按 IP。
7. 密碼雜湊在 Cloudflare Workers 上用 WebCrypto PBKDF2（Workers 沒有 Node scrypt）；selfhost 可考慮 scrypt。
8. 登入成功後回傳帳號可存取的家庭／群組清單；單一歸屬直接進入，多個歸屬顯示選擇。

這一部分與先前討論的階段 2 相容，且不需要改動 BDC 現有資料隔離。

### 4.2 有條件參考：家庭組入口

先釐清「家庭組」在 BDC 要解決哪一種需求：

**方案 A：家庭入口＋成員選擇（資料仍按使用者隔離）**

- 新增 `groups` 與 `group_members`。
- 家庭入口碼長期有效、可輪換、可關閉公開目錄。
- `#group=CODE` 進入家庭頁，列出成員；點成員後仍使用該成員自己的登入碼或密碼。
- 家長（owner）可代成員產生一次性登入碼。
- 優點：改動相對小，重用 BDC 現有登入碼；家庭成員仍保有各自資料。
- 缺點：如果沒有共享資料，家庭頁的價值主要是「一個連結找到全家人」與「家長代發登入碼」。

**方案 B：家庭共享學習資料**

- 所有詞書、文章、QA 需要增加 `group_id` 或共享層。
- 需要處理：資料擁有者、多人同時編輯、刪除／合併衝突、成員退出後資料歸屬、AI 快取與同步範圍。
- 這是資料模型與同步協議的大型改造，不建議與登入改造混在一起。

**方案 C：家長管理帳號**

- 家庭 owner 可在家庭內建立成員、重設登入碼、停用成員。
- 需要把目前的全域管理員權限拆成「系統管理員」與「家庭 owner」兩層。
- 與 dgr 的 `system_admin` / `boss` 分層最接近，但 BDC 目前只有 `admin` / `user`。

### 4.3 不建議直接照搬的部分

- **入口碼路徑**：BDC 是純靜態 SPA，沒有 Next.js 動態路由；應改用 `#group=CODE` 或由 Worker 處理路徑，並在啟動最早期捕捉、清除 fragment（與目前 `#login=CODE` 相同模式）。
- **入口碼公開成員目錄**：BDC 的成員名稱可能包含兒童個資；預設應關閉公開目錄，只允許持連結者查看，且提供輪換。
- **scrypt**：Cloudflare Workers Free 沒有 Node `scrypt`；若走 Workers，使用 PBKDF2。若主要部署在 selfhost，才考慮 scrypt。
- **一次入口碼同時登入**：dgr 明確實作「入口只選家庭、角色仍需登入」。BDC 若讓家庭入口直接登入某個成員，會把 tenant token 變成 authentication token，不建議。

## 5. 建議

1. 若目前目標只是「家庭成員各自登入 BDC」：先做 **方案 A**，並把家庭入口定位為「選擇家庭與成員的導覽入口」，不是登入憑證。成員登入沿用現有一次性登入碼；家長可代發登入碼。
2. 若目標是「一家人共用同一份詞書／文章」：先做資料共享的決策與規格（方案 B），不要先做入口。
3. 若目標只是「不用登入碼，改用使用者名稱＋密碼」：這就是階段 2；可直接採用 dgr 的 username 規則與 `auth_version`，但把雜湊換成 Workers 可用的 PBKDF2。
4. 不論哪一種，家庭入口碼都應：高熵（至少 18 bytes）、長期有效、可輪換、可停用、預設不公開目錄、不作為登入憑證。

## 6. 待確認問題

1. BDC 的「家庭組」是「一個連結進入家庭、成員各自登入」，還是「家庭成員共享同一份學習資料」？
2. 家長是否需要管理成員帳號（建立、停用、代發登入碼、重設）？
3. 是否仍維持 Cloudflare Workers Free、暫時不做使用者名稱＋密碼？若是，家庭組入口＋成員一次性登入碼即可成立。
4. 家庭入口是否需要在首頁公開列出家庭，或只允許持連結進入？
