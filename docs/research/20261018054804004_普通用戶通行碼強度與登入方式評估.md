# 普通用戶通行碼強度與登入方式評估

- 時間：2026-10-18 05:48:04 CST
- 狀態：評估完成；已採用方案 A（2026-10-18，見 `docs/plan/20261018055618504_裝置配對碼登入v1實施計劃.md`）
- 關聯：`cloudflare-worker/src/worker.js`、`modules/sync-cloudflare.js`、`features/sync/sync.js`
- 相關文件：`docs/research/20261018053635730_電郵OAuth登入適用性評估.md`

## 1. 問題

目前建立、修改或重設通行碼都要求至少 32 個字元。普通用戶是否需要這麼複雜？
能否讓普通用戶使用較短、較好記的通行碼？

## 2. 目前實際規則

- `MIN_AI_PASSCODE_LENGTH = 32`，主要用於：
  - `/ai-credentials`、`/ai-catalog`、`/admin/*` 的強通行碼檢查。
  - `/change-token`、`/reset-token` 的新通行碼長度。
  - `add-user.mjs` 與管理員用戶管理 v1 產生 43 字元隨機通行碼。
- `/me`、`/version`、`/snapshot` 不檢查長度；既有短通行碼仍可登入及同步學習資料。
- 因此「一定要 32 位」並非所有接口的絕對規則，而是**支援的建立／修改流程與 AI／管理接口**的要求。

## 3. 為何不能只把 32 改成 6 或 8

目前通行碼同時是**長期 Bearer token**，不是一般密碼：

- D1 只存未加鹽的 SHA-256；短密碼一旦資料庫洩漏，可快速離線破解。
- Token 存在 localStorage，沒有到期、裝置綁定或撤銷機制。
- 登入限流是 Worker isolate 內的盡力而為，沒有全域鎖定或失敗次數上限。
- 已登入用戶可透過 `/ai-credentials/:id` 取得解密後的個人 AI Key；短通行碼被猜到不只暴露學習資料，還可能暴露 API Key。
- 管理員帳戶目前靠同一套 token；若放寬普通用戶長度，日後角色提升時會出現弱憑證保護管理接口的風險。現有 32 位門檻正好阻止這種情況。

## 4. 可選方案

### 方案 A：保留高強度通行碼，改善輸入體驗（風險最低）

- 通行碼仍為 43 字元隨機值，但每個瀏覽器只需首次輸入；localStorage 會保留登入狀態。
- 管理員建立用戶時已可複製通行碼與恢復碼。
- 可再加「裝置配對碼」：管理員產生短效一次性配對碼，新裝置用它換取長期 token，避免手動輸入 43 字元。
- 不改認證模型，安全性不下降。

### 方案 B：密碼 + 工作階段（若要讓用戶自訂簡單密碼，建議此方案）

把「人類密碼」與「API 工作階段 token」分開：

1. `POST /login` 接受 `user_id + password`。
2. 密碼以 PBKDF2-SHA256 + 隨機 salt 儲存（或改用受管理的認證服務）。
3. 驗證成功後簽發高熵 session token，存入 `user_sessions`，設定到期與撤銷。
4. 所有 API 只驗證 session token，不再每次驗證密碼。
5. 加入 D1 或 Cloudflare 層級的登入失敗限流／鎖定。
6. 管理員帳戶維持高強度憑證；普通用戶可設 10–12 字元以上的密碼或密語。
7. 管理員重設改為簽發臨時密碼，首次登入強制修改。

需要新增 migration（`password_hash`、`password_salt`、`password_iterations`、
`user_sessions`、登入失敗記錄）與前端登入流程；工作量明顯大於調整常數。

注意：Workers 的 CPU 限制可能影響 PBKDF2 迭代次數，需先實測；若成本過高，
可考慮 Cloudflare Access、Supabase Auth 等受管理方案。

### 方案 C：只降低 32 位門檻（不建議）

- 改動最小，但同時削弱學習資料、個人 AI Key 與管理接口的保護。
- 不解決未加鹽 SHA-256、無 session 到期、無限流等根本問題。
- 若只對「非 AI 的普通用戶」放寬，會出現同一帳戶在不同功能間憑證強度不一致的產品分裂。

### 方案 D：本機 PIN 解鎖（只解決共用裝置的日常解鎖）

- 用 6 位 PIN 在本機加密保存的 token，PIN 不送往伺服器。
- 只適合「同一台已登入裝置的快速解鎖」，不能當成遠端帳戶密碼。
- 初次配對仍需要高強度通行碼或配對碼。

## 5. 建議

- 若使用者只是不想每次在新裝置輸入 43 字元：先做方案 A（記住登入狀態、複製憑證、裝置配對碼），不要降低憑證強度。
- 若使用者明確要求自訂簡單密碼：做方案 B，最低建議 10–12 字元或密語，並保留高強度恢復碼；不要只改 `MIN_AI_PASSCODE_LENGTH`。
- 若普通用戶不使用 AI、只同步學習資料，且接受較低風險，可考慮方案 B 的簡化版；但仍應使用 PBKDF2 與 session，而不是短 SHA-256 token。
- 6 位 PIN 僅可作本機解鎖，不可作為唯一遠端憑證。

## 6. 待決定問題

1. 「簡單」是指 8–10 字元密碼、12 字元密語，還是 6 位 PIN？
2. 普通用戶是否使用 AI 功能、是否保存個人 AI Key？
3. 是否有多人共用同一台裝置的情境？
4. 是否接受新增 `/login`、`user_sessions` 與密碼重設流程？
5. 管理員帳戶是否維持 32 位以上隨機通行碼或其他更強方式？
