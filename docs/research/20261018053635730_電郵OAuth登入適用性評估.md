# 電郵 OAuth 登入適用性評估

- 時間：2026-10-18 05:36:35 CST
- 狀態：評估完成，待決定是否立項
- 關聯：`cloudflare-worker/`、`modules/sync-cloudflare.js`、`features/sync/`
- 相關計劃：`docs/plan/20261018052824133_管理員用戶管理v1實施計劃.md`

## 1. 結論摘要

技術上可行，但**不是**在現有通行碼登入上直接加一個 OAuth 按鈕即可。現有架構以
`user_id + 通行碼` 為身分，D1 每人只有一組 `token_hash`，沒有電郵、供應商身分
映射或多裝置工作階段。要正確支援電郵 OAuth，至少需要新增身分表、工作階段表、
OAuth callback 與一次性授權碼交換。

是否「合適」主要取決於兩件事：

1. 使用者主要所在地區。
2. 產品是公開註冊，還是管理員邀請的小範圍使用。

現階段建議：**保留通行碼登入與剛完成的管理員用戶管理 v1，OAuth 另立階段評估**。
v1 已預留可空 `users.email` 欄位，日後可作邀請與身分映射，不影響目前流程。

## 2. 現況與缺口

| 項目 | 現況 | OAuth 需要 |
| --- | --- | --- |
| 身分 | `users.user_id`，沒有電郵 | `email`、`user_identities(provider, subject)` |
| 工作階段 | 每人一組 `users.token_hash`，Bearer 存在 localStorage | `user_sessions` 多裝置、到期與撤銷 |
| 登入流程 | 使用者輸入 43 字元通行碼 | OAuth start／callback、state／PKCE、nonce |
| 前端交換 | 直接 Bearer 呼叫 Worker | callback 後一次性授權碼交換或同站 Cookie |
| 帳戶建立 | 部署者 CLI／管理員 v1 建立 | 邀請制白名單或已驗證電郵自動建立 |
| 地區 | 介面預設 `zh-CN`，另有 `zh-HK` | 大陸不可依賴 Google OAuth |

`users.token_hash` 是主鍵且每人只有一列。若 OAuth 每次登入都產生新 token 並覆寫，
會讓其他裝置立即失效；因此多裝置 OAuth 必須先拆出 `user_sessions`。

## 3. 可選方案

| 方案 | 適合場景 | 優點 | 限制 |
| --- | --- | --- | --- |
| Cloudflare Access | 私人／小團隊、已有自訂網域 | 幾乎不用寫 OAuth；可用 Google、Microsoft 或一次性電郵 PIN | 不支援 `workers.dev`；跨來源 Cookie／CORS 限制；免費方案人數有限；不適合公開註冊 |
| Worker 內實作 OAuth | 公開或邀請制產品、國際使用者 | 完全控制流程、可維持 Bearer；可只允許白名單 | 需自行實作 state／PKCE、callback、session、撤銷與审计；Google 在大陸不可用 |
| 電郵一次性驗證碼／魔法連結 | 大陸或不想綁定第三方 | 不依賴 Google；對非技術使用者較直觀 | 不是 OAuth；需外發郵件服務、投遞率與防濫用；QQ／163 等信箱投遞需實測 |
| Supabase Auth／Auth0／Clerk | 想快速取得多供應商登入 | 現成 session、電郵驗證、OAuth | 增加外部依賴與費用；Worker 需驗證 JWT；與現有 D1 資料仍是兩套身分 |

## 4. 地區與合規注意

- **中國大陸**：Google OAuth 不可用；WeChat／QQ 登入通常需要中國主體、認證與
  ICP 備案。Cloudflare 自訂網域在大陸的連線品質亦不穩定。若主要使用者在
  大陸，建議優先評估電郵驗證碼，或維持通行碼。
- **香港／海外**：Google 或 Microsoft OAuth 可行，實作成本主要在 session 與
  邀請流程，而非供應商本身。
- **公開註冊 vs 邀請制**：本專案目前是管理員建立帳戶。OAuth 若採邀請制，管理員
  先建立電郵白名單，首次 OAuth 登入只綁定该電郵；若採公開註冊，則需處理濫用、
  配額與帳戶清理。

## 5. 若立項的建議順序

1. `user_sessions`：先讓通行碼登入也改用多裝置 session，補上到期與撤銷。
2. `user_identities`：保存 provider + subject，電郵只作邀請與顯示，不作唯一身分。
3. OAuth start／callback：state、PKCE、nonce、`email_verified` 檢查與精確 redirect URI。
4. 一次性授權碼交換：callback 不把長期 token 放在 URL；前端用短效碼換 Bearer。
5. 邀請制白名單與管理員介面：管理員可預先建立電郵，OAuth 首次登入完成綁定。
6. 保留通行碼與恢復碼作為後備；管理員重設流程維持 v1 邊界。
7. 审计與監控：登入成功／失敗、綁定、撤銷、管理員操作。

## 6. 待決定問題

1. 使用者主要在中國大陸、香港，還是海外？
2. 目標是公開註冊，還是管理員邀請的小範圍使用？
3. 偏好 Google／Microsoft，還是電郵驗證碼？
4. 是否接受新增外部認證服務（Supabase Auth／Auth0／Clerk）？
5. 是否需要在同一帳戶保留通行碼登入作為後備？

在上述問題有答案前，不建議改動現有登入流程；v1 的 `email` 欄位已足夠作為
日後邀請與映射的起點。
