# AI 查詞、文章翻譯與助手的思考強度核對

核對時間：2026-11-02。本文件記錄目前程式行為及調整建議；本次只新增調研記錄，沒有修改 AI 請求或帳戶設定。

## 結論

目前應用程式沒有為查詞、文章翻譯、句子分析或 AI 助手明確指定思考強度。各任務均使用所選模型與服務端的預設行為，不能將目前狀態直接稱為「低」、「中」或「高」，也不能將未傳參數理解為一律關閉思考。

應用程式已支援按功能選擇不同模型；獨立的思考強度設定尚未實作。建議按任務區分速度與推理需求：簡單查詞優先關閉或使用最低強度，普通翻譯使用低強度，複雜句法分析使用中等強度，助手以中等為預設、複雜問題再選高強度。這些是產品策略建議，實際可用檔位須按供應商與模型能力對應。

## 哪些設定容易混淆

- 查詞、文章翻譯與助手多使用 `temperature: 0.2`。Temperature 控制生成的隨機程度，並非思考強度；它與推理參數的相容性也須按模型確認。
- 段落的 `quick`／`standard`／`deep` 是應用程式的處理級別，會影響逾時等設定，並未轉換為模型的 reasoning／thinking 參數（`features/article/paragraph-pipeline.js:32`、`modules/api.js:750`）。
- `maxTokens` 是生成預算，不是跨供應商通用的思考強度旋鈕。有些推理模型會把思考 token 計入生成上限；一味壓低上限可能讓正文或 JSON 不完整。共用入口目前遇到 `finishReason === 'length'` 時還會嘗試增加預算重發，可能增加等待與用量（`modules/api.js:399`、`:501`）。
- 關閉思考仍然是在使用 AI 模型，只是對支援的模型關閉額外推理；不代表查詞或翻譯功能失效。

## 現在可採用的調整方式

在 AI 供應商設定中展開「按功能指定模型」，可以分別選擇「查詞 / 單詞分析」、「文章詳解」和「AI 助手」的模型（`features/sync/ai-provider-settings.js:49`、`:506`）。因此已可將查詞指派給反應較快的非推理模型，讓助手使用推理能力較強的模型。實際可選型號取決於目前供應商提供及允許的模型列表。

一般任務的模型來源優先次序為明確任務選擇、個人預設、管理員預設。文章細分任務另外會依各函數列出的候選任務尋找設定；例如文章單詞查詢可沿用 `wordAnalysis`，段落與句子分析可沿用 `articleAnalysis`。相關解析在 `modules/ai-models.js:315`、`:331`。

目前設定面板沒有獨立列出文章段落翻譯、片語及句子分析的思考強度。AI profile 的任務資料主要儲存模型規格，不會保留附在任務模型物件上的任意 reasoning 欄位；僅手動加入一個 JSON 欄位並不能讓它生效（`modules/ai-profile-storage.js:193`）。

本次未讀取使用者瀏覽器的帳戶 profile、實際請求紀錄或代理服務設定。倉庫也沒有固定的 AI 模型預設，因此不能據此報出目前帳戶使用的具體型號，或服務端省略參數時採用的確切檔位。

## 建議的任務策略

| 任務 | 建議預設 | 調整理由 |
| --- | --- | --- |
| 常用單詞意思、詞性、一般音標 | 關閉思考；模型不支援關閉時使用最低可用強度或快速模型 | 優先回應速度；高強度不保證詞典資訊更準確 |
| 文章中單詞／一般片語釋義 | 關閉或低 | 保留句子上下文，通常足以判斷句中義；歧義較大時再升級 |
| 普通文章翻譯 | 低，或品質已驗證的非推理模型 | 大量段落不宜全部使用高強度；需保留語境和翻譯品質 |
| 長難句、語法結構及細緻比較 | 中 | 多步分析比直接翻譯更需要推理 |
| AI 助手的一般教學與追問 | 中 | 兼顧解釋品質與等待時間 |
| 助手的複雜推導、多段比較及有歧義問題 | 按需高 | 將較高成本用在需要額外推理的問題 |

建議讓助手具備每次提問可切換的強度選項，並讓查詞與普通翻譯沿用任務預設。不要把所有助手提問一律設為最高檔。

若實作統一介面，可提供「跟隨模型／關閉／低／中／高」這類使用者選項，再由協議適配器按模型能力對應。OpenAI 相容服務可能支援 `reasoning_effort`；Anthropic 使用其 `thinking`／預算或自適應機制；Gemini 使用 `thinkingConfig`；部分相容服務另有自己的開關或以模型名稱區分模式。這些只是常見介面形式，不能假設同協議的所有模型都支援相同參數、值或關閉方式。本次沒有查證特定供應商的最新能力清單。

新增設定時，應讓流式與非流式請求使用同一套解析，兼顧帳戶設定及同步，並在需要辨識不同生成策略的快取鍵中納入相關選項。修改 UI 文案須同時支援 `zh-CN`、`zh-HK`。

## 驗證與限制

已用 Node 直接呼叫三套適配器的 `buildRequest()`，分別構造流式及非流式請求，共 6 種組合。使用虛構模型及 `example.invalid`，沒有發送網絡請求，也沒有讀取或輸出金鑰。

全部 6 種組合均通過斷言：請求物件沒有 `reasoning_effort`、`reasoning`、`thinking`、`thinkingConfig`、`thinking_config`、`thinkingBudget`、`thinkingLevel`、`budget_tokens` 或 `enable_thinking` 控制欄位。

本次沒有量測實際推理時間、回應品質或用量，不能承諾具體加速比例。是否值得優先調整，應以同一批查詞／翻譯／助手問題，比較快取未命中時的首字時間、總耗時、輸出完整性及內容正確性；等待也可能來自服務端排隊、網絡、較長上下文或重試。
