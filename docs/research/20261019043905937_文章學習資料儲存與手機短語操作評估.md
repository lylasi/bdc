# 文章學習資料儲存與手機短語操作評估

日期：2026-10-19  
範圍：依目前程式碼核對文章、查詞、查句、短語、詞書及文章 AI 對話的儲存、同步、備份與手機操作；提出改善建議。本次未修改應用程式。

這次是原始碼審查，沒有讀取使用者瀏覽器中的私人學習資料，也沒有進行 iPhone／Android 真機操作。下文「已確認」指可由現行程式碼直接判斷的行為；涉及觸控事件時序、並行操作與瀏覽器容量的項目另列為待驗證風險。

## 1. 判斷與優先次序

文章已完成逐篇儲存，但文章內的學習資料仍分散在三條路徑：文章的分析 JSON、整體詞書資料、助手會話與通用快取。**逐篇存文章，尚未等於逐項保存及同步學習記錄。**

建議先修復可遺失或無法重新讀取的資料，再增加獨立學習資料層。手機短語操作可先改善，不必等待整套儲存重構，但選取來源與保存介面應使用一致的資料契約。

最值得先處理的問題：

1. 助手聊天正文存在 `bdc-cache`，而「清除快取」會嘗試刪除整個資料庫。
2. 助手同步快照每段會話只保留最後 **50 條消息**；本地備份沿用同一快照，也有這個截斷。
3. 全篇重新分析沒有帶回既有 `sentence_analysis` 與 `phrase_analysis`。
4. 句子／短語解析雖有寫入文章，重新打開的主要入口沒有優先讀取這些陣列。
5. 有解析不代表確實查閱過；目前缺少可靠的查閱記錄。
6. 短語保存入口不一致，同句短語解析只保留最新三筆。
7. 同步粒度仍不一致：文章逐篇；詞書與聊天則各自整組比較時間，沒有逐詞／逐消息合併。

## 2. 現在各種內容存在哪裏

| 內容 | 本機主要位置 | 雲端路徑 | 目前保存語義 |
| --- | --- | --- | --- |
| 文章原文、翻譯、段落分析 | IndexedDB `bdc-articles` → `docs`，一篇一筆 | 獨立 `/articles`，D1 `articles.body`、`analysis_json` | 穩定文章 ID，具版本、待同步、衝突與軟刪除狀態 |
| 按需查出的單詞詳解 | 該篇 `result.detailed_analysis[]`；另有通用 API 快取 | 隨該篇完整 `analysis` 同步 | 保存解釋，沒有首次／最近查閱時間或精確出現位置 |
| 查過的句子解析 | 該篇 `result.sentence_analysis[]`；另有 API 快取 | 隨文章同步 | 以句子＋上下文去重、更新；重開入口未優先復用這些持久化資料 |
| 查過的短語解析 | 部分入口存 `result.phrase_analysis[]`；部分僅進 API 快取 | 寫入文章的部分才隨文章同步 | 同句＋上下文最多三筆；不是完整短語歷史 |
| 加入詞書的單詞／短語 | localStorage `vocabularyBooks` → 某詞書的 `words[]` | 一般快照中的 `vocabulary` 整組 | 獨立於文章解析；短語也存於 `word` 欄位 |
| 向文章 AI 提出的問題與回答 | localStorage `assistantConvIndex` 索引；IndexedDB `bdc-cache/kv` 中 `assistant:conv:<id>` 正文 | 一般快照中的 `assistant` 整組，每會話最後 50 條消息 | 本機追加時沒有同樣的 50 條限制，但同步／備份有 |
| AI 可重建的結果快取 | IndexedDB `bdc-cache/kv`，失敗時回退 localStorage | 不單獨同步 | 標準成功路徑：單詞 30 日、句子 21 日、短語 30 日 |

以上 TTL 只適用於通用解析快取，不代表已加入詞書的內容會在 30 日後刪除。文章內已寫入的解析也不按這些 TTL 自動過期。

### 2.1 文章本體的實際結構

介面使用的物件大致是：

```js
{
    articleId,
    article,                // 原文
    result: {
        chinese_translation,
        word_alignment,
        detailed_analysis: [],
        paragraph_analysis: [],
        sentence_analysis: [], // 按需新增，未必存在
        phrase_analysis: []    // 按需新增，未必存在
    },
    title, sourceType, sourceUrl,
    revision, createdAt, updatedAt, lastOpenedAt,
    deletedAt, dirty, pending, conflict
}
```

寫入 IndexedDB 後，`articleId/article/result` 對應為 `id/body/analysis`。鍵由帳戶範圍與文章 ID 組成；範圍包含同步端點和使用者，訪客亦有自己的範圍。另有 `outbox`、`state`、`drafts` 三個 store。

正常 IndexedDB 路徑是一篇一筆；回退 localStorage 時，`bdc:articles:fallback:v1:<scope>` 仍以整個範圍的文件、佇列及狀態集合保存。舊 `analyzedArticles` 是遷移來源，不能再當成現行文章主儲存。

查一個詞後，程式會重寫這一篇的分析文件；下一次上傳仍傳送該篇原文和完整分析。待同步操作可合併，因此不代表每一次點擊都立即產生網絡請求。也沒有每查一次就永久保存一份完整原文歷史副本。

當前專案限制為每篇原文＋分析 JSON 共 800 KiB、每位使用者文章合計 50 MiB。這是專案的產品限制，並非引用 Cloudflare 平台的通用上限。若把所有學習活動繼續塞進單篇分析，文章內容沒變，分析增長仍會消耗這個額度。`saveArticle()` 有本機大小檢查，`saveAnalysis()` 目前沒有同樣的明確檢查，需補齊一致的錯誤回報。

來源：`modules/article-store.js:24,67,215,524,569`、`modules/article-sync.js:140`、`shared/article-protocol.mjs:7`、`cloudflare-worker/migrations/004_article_storage.sql`。

### 2.2 「查過的詞」實際上主要保存了甚麼

按需分析大致為 `{ word, sentence, analysis: { phonetic, pos, meaning, role } }`，合併至文章頂層 `detailed_analysis`。匹配時會同時考慮單詞與句子，避免直接把其他句境的詞義拿過來。

但這裏混合了整篇／段落分析產生的資料和使用者點詞取得的資料，沒有統一的 `viewedAt` 或查閱事件。打開既有解釋會直接顯示，也不額外留下查閱時間。因此無法從陣列還原「我實際查過哪些詞、何時查過、查過幾次」。

此外，同一頁執行期間還有 `_lazyCache`。命中它時只更新畫面使用的分析陣列，沒有在該分支再次保存到目標文章；同一個句子／詞出現在另一篇文章時，畫面可顯示，但第二篇未必得到獨立持久化記錄。

來源：`features/article/article.js:1471,3712`、`modules/api.js:838`。

### 2.3 查句與短語解析的保存缺口

`sentence_analysis` 按句子＋上下文匹配，保存結果與 `updatedAt`；`phrase_analysis` 多一個 `selection`，並對每個句子＋上下文只保留最新三筆。

已確認的不一致：

- 句子彈窗重新打開會走 API 分析入口；可以命中通用快取，但沒有先讀文章內已同步的 `sentence_analysis`。換裝置後文章有解析，通用快取卻未必存在，仍可能要求 AI 或在離線時無法重開。
- 全篇重新分析重建 `finalResult`，明確合併單詞詳解，但沒有合併句子、短語兩個陣列。成功保存新結果後，舊的這兩類文章內資料會被替換掉。
- 句子卡片的部分短語入口會持久化；單詞浮框的短語分析入口只呼叫 API 並顯示，沒有呼叫 `persistPhraseAnalysis()`。
- 句子卡片「分析選中短語」在非同步返回後，呼叫持久化時沒有傳入捕捉好的文章 ID，仍可能取當時的目前文章。這是可見的歸屬風險，尚未以切換文章的操作重現。
- 保存失敗部分只記錄在 console；有些呼叫只捕捉 exception，沒有處理 `{ ok: false }`，畫面呈現與已寫入磁碟可能不同。

三筆限制只會裁剪文章內的短語解析，**不會因此刪除已經加入詞書的短語**。

來源：`features/article/article.js:1493,1509,2048,3640,4526,4740`。

### 2.4 加入單詞表後的資料

本文詞書一般以 `articleId` 作詞書 ID，帶 `sourceType: 'article'`、`articleId`。加入詞條時主要保存：

```js
{
    id, word, meaning, phonetic,
    examples: [], addedAt,
    source: 'article',
    context,               // 優先原句，其次較大上下文
    sourceArticleId,
    wordbookId,
    pos                    // 有提供才有
}
```

目前沒有獨立「短語表」；`look forward to` 可作為 `word` 的值加入。詞書入口優先目前綁定詞書，必要時建立文章詞書或回退預設詞書。

同一本詞書按整理後文字去重：大小寫、空白、首尾標點會規範化。已存在就返回已有詞條，不會追加第二個來源句子或獨立詞義。同一個 `bank` 在兩句有不同意思，第二次加入可能只看到「已存在」，新的語境沒有保留下來。

詞書資料獨立於文章分析，文章刪除流程不連帶刪詞書。但有關聯 ID 不代表能精確跳回原文；現有詞條沒有文字範圍和原文版本。

若缺少釋義／音標，現有加入流程可能先等待補全，再存詞條。手機離線或慢網時，應改成先存選詞和來源，釋義稍後補全；不能把收藏成功綁在 AI 請求完成上。

來源：`modules/vocab.js:35,173,227`、`modules/storage.js:180,314,368`、`modules/article-store.js:599`。

### 2.5 向文章 AI 提問後的資料

會話索引為 `[{ id, articleKey, title, updatedAt }]`；正文是 `assistant:conv:<id>` 對應的 `{ messages: [{ role, content, ts }] }`。`assistantCurrentMap` 記住每篇文章目前選中的會話，一篇可有多個會話。

此處的 `articleKey` 是**文章輸入框原文計算出的雜湊鍵**，不是現在的穩定 `articleId`。因此：

- 修改原文，甚至空白改變，可能進入另一個會話分組，舊對話未必自動顯示。
- 兩篇不同 ID 的文章若原文完全相同，會落入相同的會話分組。
- 只改文章標題、不改輸入框原文，不應直接推論一定會分開會話。

需要分清三個不同限制：

| 層次 | 現行行為 |
| --- | --- |
| 本機追加聊天 | 保存整段消息陣列，沒有這裏所述的 50 條上限；TTL 預設 0，即不按時間過期 |
| 給 AI 的上下文 | 使用最近 8 條歷史消息，再附本輪問題及文章內容；這不是聊天保存上限 |
| 同步和本地備份 | `buildAssistantSnapshotPayload()` 只取每會話最後 50 條消息；通常約 25 輪一問一答，但實際依消息結構而定 |

「清除快取」會嘗試 `deleteDatabase('bdc-cache')`。若刪除成功，聊天正文也會被刪，localStorage 的會話索引仍在。瀏覽器可能因開啟中的連線阻擋刪除；當前程式把成功、錯誤及被阻擋都當作完成，因此既有誤刪風險，也有誤報清除成功的風險。回退 localStorage 的 `assistant:conv:` 又不符合清理前綴，兩條儲存路徑的結果並不一致。

詞書和聊天的本機鍵不像文章一樣帶帳戶範圍；所查登出處理移除登入資訊，沒有一併清除上述資料。這應列為帳戶切換設計待統一的範圍；不能僅因文章已按帳戶分隔，就假設所有學習資料也有同等隔離。登入時已有本機資料合併流程，需配合檢視，不能直接以清空資料解決。

來源：`features/assistant/assistant.js:21,249,328,404,475,675`、`modules/sync-core.js:100`、`features/sync/sync.js:1751,2235`、`modules/local-backup.js:109`。

## 3. 同步、備份與並行操作的影響

目前文章獨立同步，是已經完成的重要基礎；但文章內查詢仍共用一個完整分析物件。兩部裝置分別在同篇查不同詞，仍可能產生文章版本衝突，不能自動按詞合併。現有文章衝突有保留及處理流程，不應說成直接靜默覆蓋所有文章。

詞書與助手走 `lwwMerge()` 的整組時間比較。例如手機新增詞書 A 的詞、電腦新增詞書 B 的詞，仍可能由較新的整組內容取代另一組，因為合併單位不是詞書 A／B 或各詞條。助手的兩個不同會話亦有相同問題。

同頁內同時完成多個解析時，各處先讀取 `record.result`、組新物件、再非同步寫回；沒有統一的逐篇修改佇列，存在讀到相同舊值後互相覆蓋的風險。後續應以並行回應測試驗證。短期可序列化同篇更新，在真正寫入時讀最新值；長期分項記錄可減少衝突範圍。

本地備份會額外附上完整文章文件，包含當時仍在文章中的解析；詞書也進快照。但助手消息有最後 50 條的截斷，不能把現有備份稱為完整聊天封存。備份本身存在 localStorage，文章越多越大，還會面臨額外複製帶來的容量壓力。

## 4. 建議的資料邊界

### 4.1 分開四種語義

1. **文章及解析**：教材原文、來源、翻譯與 AI 解釋。
2. **查閱與筆記**：使用者實際打開過甚麼、何時打開、自己寫了甚麼；不能靠 AI 解析陣列推導。
3. **收藏與詞書**：準備學習的詞條、詞義、來源例句及複習資料。
4. **對話與消息**：使用者問題、AI 回答、當時引用的原文；屬長期資料。

通用快取另外存在，只保存可以重新取得的結果。清快取必須保留文章、查閱、收藏、筆記和聊天。

### 4.2 可逐步落地的結構

以下是建議契約，並非已存在的資料表，也不要求一次建立所有表：

| 實體 | 建議最小欄位 | 目的 |
| --- | --- | --- |
| `articles` | 現有 ID、來源、目前原文版本、標題 | 延續既有逐篇文章儲存 |
| `articleContents` | `articleId, contentHash, body, createdAt` | 原文真的變更且有記錄引用時，保留必要舊版本 |
| `studyRecords` | `id, scope, articleId, contentHash, kind, anchor, firstViewedAt, lastViewedAt` | 單詞／短語／句子的查閱事實 |
| `analysisRecords` | 目標記錄、結果、語言、模型／供應商識別、提示詞及 schema 版本 | 可重開的解釋，避免混入查閱狀態；不存 Key |
| `notes` | 目標／原文定位、正文、時間、修訂及刪除標記 | 個人內容獨立保存，AI 刷新不能覆蓋 |
| `vocabularyEntries` 與來源關聯 | 詞書、文字、詞義；多個 `source`／例句關聯 | 同詞可保留多個語境，不重複塞一條相同例句 |
| `conversations` | `id, scope, articleId, title` | 用穩定文章 ID 關聯 |
| `messages` | `id, conversationId, role, content, status, contentHash, quotedAnchor?, createdAt` | 逐條存消息、分頁讀取、增量同步 |

共用範圍用 `endpoint + userId`；訪客資料有獨立歸屬，登入後明確執行接管／合併。不能把舊的無範圍資料默認歸給下一個登入者。

`revision` 表示同步修訂，`contentHash` 表示教材原文版本，兩者用途不同。查一個詞可以更新學習記錄修訂，不必生成新的原文版本。同一原文重分析亦不應移除查閱和筆記。

### 4.3 文字定位與同詞多義

建議每次收藏、查閱或提問引用都捕捉：

```js
{
    articleId,
    contentHash,
    anchor: {
        paragraphId,
        start,
        end,
        exact: 'look forward to',
        prefix: 'We ',
        suffix: ' meeting you.'
    },
    sentence: 'We look forward to meeting you.'
}
```

文字範圍應以同一套原文標準化及字元計數規則建立，不依賴會隨重新渲染改變的 DOM 路徑。可結合位置與原文摘錄、前後文，參考 W3C 的 [Text Quote Selector 與 Text Position Selector](https://www.w3.org/TR/annotation-model/#selectors)；本專案未必需要實作整套標準。

相同句子可能在一篇重複出現，單靠句子字串不足以定位。原文編輯後先匹配版本及位置，再以摘錄和前後文嘗試重新定位；不確定就保留原引用並標示位置待確認，不能默默跳到另一處同詞。

同詞去重應分層處理：詞書內可共用一個詞條，但來源例句要分開；不同詞義可以讓使用者選擇保留為獨立義項。不要用全站小寫文字鍵把 `bank` 的所有語境合成一筆解釋。

查閱狀態首版建議只記首次及最近查閱時間。若日後需要準確次數，應有可去重的事件 ID，或明確的裝置計數合併規則，不能把各裝置的總數直接相加。

### 4.4 永久資料的同步與保留

- 按學習記錄、詞條來源、會話消息的 ID 同步，不再把全部學習資料重新包進一個大 JSON。
- 新增消息／不同查閱項可按 ID 合併；同一筆筆記並行修改則保留衝突內容，不做無提示覆蓋。
- 用刪除標記防止離線裝置把已刪內容帶回來；保留期與裝置游標確認後再清理。
- 本機永久記錄與其 outbox 操作放同一資料庫交易；以交易完成作為寫入成功，而非只看單個 request 的成功回呼。
- 全部非同步操作在開始時固定 `scope/articleId/contentHash/conversationId/selection`，回應返回後按原目標保存，不再讀「目前畫面」決定歸屬。
- AI 請求只送最近若干消息，是成本策略；聊天保存及備份的完整性應獨立設定。長會話用分頁和摘要降低載入／上下文成本。
- 文章刪除預設保留已收藏詞條與其原句；聊天、筆記保留可回顧的引用。若提供連帶刪除，必須清楚列出範圍。
- 永久保存的解釋要保留原來語言；切換介面語言不改寫歷史消息及原文。需要另一語言解釋時另建變體或明確刷新。

## 5. 手機加短語的建議操作

### 5.1 現在的困難

現行正文先讓使用者原生選字，再依 `mouseup/touchend` 顯示浮動「加入生詞本」按鈕；點擊按鈕時重新讀取 `window.getSelection()`。句子卡片亦有讀目前選區的按鈕。

程式碼可確認沒有在這個流程監聽 `selectionchange`，沒有固定選取快照，也沒有浮動按鈕的視窗邊界／安全區校正。上下文由選區起點推斷，範圍只檢查是否在整個分析區內，未明確限制英文原文及同句。

實機需驗證的結果包括：長按系統選單遮住按鈕、調整選取手柄後位置沒更新、點按鈕導致選區消失、短語跨行難以拖準，以及正文單詞點擊與選字互相干擾。不能只以桌面模擬手機寬度判定 iOS／Android 均正常。

來源：`features/article/article.js:3490,4458,4764`。

### 5.2 主流程：點起詞、點末詞

例句：`We look forward to meeting you.`

1. 使用者點 `look`，在現有詞義面板選「選短語」。句子詳解亦提供同一入口。
2. 顯示底部選詞面板，重現該句，`look` 已作為起點。句子中的詞作為有足夠間距的可點按項目，避免直接要求手指精準拖選正文小字。
3. 點 `to` 作末詞，自動選中中間整段 `look forward to`；跨畫面換行仍視為同一段原文。
4. 面板顯示所選短語、原句和目的詞書。主要按鈕為「加入本文生詞本」，另可切換詞書；提供「調整起詞／末詞」、重新選及取消。
5. 點加入即完成本機保存，顯示成功與撤銷。已有釋義直接帶入；需要 AI 補全時在保存後進行，離線也能收藏。

在點了某詞後進入模式，起點已預填，因此通常只需再點末詞和加入。不要求每次重新選兩個端點。反向點選可取兩端之間的範圍，並在預覽中確認。點末詞後仍可繼續調整，不自動收藏。

底部面板建議只有一個主要動作；「解析」「寫筆記」「問 AI」放次要操作。尤其不要一選中短語就必須先等 AI 解釋。

### 5.3 保留兩個快捷入口

**已有 AI 短語區塊**：在句子詳解的每個短語旁加「加入」。直接使用已有短語文字、釋義和原句，但只有在能可靠定位原文時才自動回填位置；AI 生成但原文不存在的片語，可作為一般詞條保存，不能偽造原文選區。

**原生長按選字**：保留給熟悉手機選字的人。監聽 `selectionchange`、節流更新預覽，先保存文字和來源範圍再處理按鈕點擊；手機可用穩定的底部操作列，減少選區旁小浮鈕與系統選單爭位置。`selectionchange` 的用途可參考 [MDN 官方說明](https://developer.mozilla.org/en-US/docs/Web/API/Document/selectionchange_event)。

「手動輸入短語」留作編輯／特殊需求的後備入口，可用正常表單取代瀏覽器 `prompt`；不作手機收藏的主要路徑。

### 5.4 需要先定義的細節

| 情境 | 建議處理 |
| --- | --- |
| 同句連續短語 | 首版主要支援；跨行不增加操作難度 |
| 撇號、連字號、標點 | 保留原文 token 邊界；去掉句尾標點不應改壞 `don't` 或 `well-known` |
| 整句／跨句 | 整句另提供句子收藏或筆記；跨句選取提示為摘錄，不勉強作短語入詞書 |
| 不連續片語 `pick … up` | 首版可保存連續原句引用，另編輯詞條顯示文字；後續用多段範圍支援。不能把刪去中間詞的結果偽裝成連續原文 |
| 相同短語已在詞書 | 顯示已有狀態；新語境可追加為來源例句，已有同一來源則不重複；修改舊釋義需明確操作 |
| 一句同詞出現兩次 | 以起訖位置區分，不能僅用文字定位 |
| 切換文章／帳戶 | 畫面結束原選取模式；已開始的保存按固定的原 scope／文章處理 |
| AI 未設定／離線／超時 | 先存文字與原句，提示釋義待補全；重試不重複新增詞條 |
| 容量不足 | 保留選取與輸入，明確顯示未保存，提供重試／匯出；不可先顯示成功 |
| 誤觸或重複點加入 | 冪等保存，短暫停用按鈕；撤銷只還原本次新增／新增來源，不刪既有詞條 |
| 朗讀、換字體、翻譯區展開 | 選取依原文索引保存，不能因 DOM 重繪失去目標；操作期間避免自動滾動搶走位置 |

主要按鈕及面板內詞項可把 44–48 CSS px 作為可點按高度的設計目標，兼顧間距、長詞換行、螢幕安全區和軟鍵盤。這是本方案的舒適度目標；WCAG 2.2 AA 的最低目標尺寸規則是 24×24 CSS px 並有例外，不能混為同一硬性標準。參考 [W3C 目標尺寸說明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。

選詞模式需有清楚的選中狀態、取消與返回、焦點管理和讀屏提示；不能只靠顏色。鍵盤可操作起點、終點及加入按鈕。手機測試涵蓋 iOS Safari、Android Chrome、窄螢幕、橫向、放大字體及系統選字選單。

## 6. 保存後怎樣方便回顧

建議文章提供「本文學習記錄」入口，分別查看查過的詞／短語、查過的句子、已加入詞書、筆記和 AI 對話；顯示最近操作，可跳回原文，並搜尋引用及釋義。

「已有解釋」「已查過」「已收藏」「有筆記」是不同狀態，可同時成立。已查過用低干擾標記，收藏和筆記用不同圖示或底線；不要把正文塗成大量重疊色塊。首版短語重疊標記可放到選取面板和記錄列表，不必立即完成任意多層正文高亮。

查閱狀態的顯示範圍可沿用既有評審方向：同一文章版本、同一句中的相同詞形共用「已查過」；收藏按本文詞書推導；個別語境、筆記和回跳位置仍精確保存。若將來要改為逐次出現的查閱標記，只調整顯示規則，底層來源位置仍可沿用。

只有主動打開且有效結果確實呈現才算查閱。預取、載入失敗、背景 AI 回應、使用者已切換畫面時，不應自動新增「已查過」。命中既有解析或快取並成功顯示，則應記錄。

## 7. 分階段落地及舊資料遷移

### 第一階段：先修復現有資料可靠性

- 把聊天永久正文移出通用快取；過渡期清快取只刪明確的可重建解析項，不能整庫刪除。
- 移除備份的 50 條靜默截斷；同步改為完整可恢復或分頁／逐條消息協議，不能單純擴大一個數字而不驗證容量。
- 同原文重分析保留句子／短語結果；原文改變時按舊版本保留，避免把舊解析當成新原文的結果。
- 打開解析先讀持久化結果，再查通用快取，最後才請求 AI；刷新操作明確更新解釋。
- 統一所有短語入口的保存、文章歸屬和錯誤回報；取消「永久記錄只留三筆」，顯示層可以只展示最近三筆。
- 統一同篇更新流程，防止並行解析覆蓋；補齊大小檢查與保存失敗提示。

### 第二階段：查閱記錄與手機選短語

- 建立最小 `studyRecords`、來源定位和範圍契約；新增功能寫入獨立永久記錄。
- 對單詞／短語／句子採用同一套查閱語義；收藏保留多來源。
- 完成底部短語選取面板、快捷加入、離線保存、重複詞和撤銷。
- 所有新增文案、載入／錯誤／完成狀態及無障礙標籤，同時提供 `zh-CN`、`zh-HK`，不複製兩套功能邏輯。

### 第三階段：按記錄同步與容量優化

- 學習記錄、詞條來源和消息逐項增量同步，補上軟刪除、衝突、重試及帳戶範圍。
- 文章列表先載摘要及計數，需要閱讀才載全文；現有初始化仍載入文章全文與分析，可在文章增多後改善。
- 聊天分頁讀取、完整匯出；備份與同步採不同傳輸策略，但都可恢復全部永久資料。
- 通用快取做實際過期清理、容量控制；目前讀到過期 IndexedDB 記錄會返回空，但沒有在該處刪除過期 IDB 列，邏輯過期不等於釋放空間。

遷移須先備份，再批次轉換、核對數量／內容，成功後才停用舊讀取；有遷移標記且可重試。讀新寫新，過渡期讀舊補遷移，避免長期雙寫成為兩份主資料。

舊資料的處理原則：

- `detailed_analysis` 保留為已有解析，不偽造首次查閱時間／次數；使用者下次主動打開才新增可靠查閱記錄。
- `sentence_analysis/phrase_analysis` 保留解析及原有時間，但不能宣稱包含所有曾經查詢；被三筆限制或重分析移除的部分，需有舊備份／其他裝置副本才可能恢復。
- 舊聊天 hash 能唯一對應文章時關聯文章 ID；對應多篇或找不到原文時保留為未關聯會話，不能擅自合併或刪除。
- 舊詞條缺少精確位置時保留原句並標記來源位置未知；不要以第一個同文字出現位置冒充確定定位。
- 切換帳戶、訪客接管、不同同步端點均需獨立遷移狀態；升級舊客戶端的寫入協議亦要有保護，避免舊快照覆蓋新資料。
