# BDC 接入 magpie 的 AI 方案評估

- 時間：2026-10-17 02:24
- 背景：BDC 是純靜態 SPA，AI 走多 provider（`ai-config.js` 兜底 + 瀏覽器 settings/secrets 覆蓋）。magpie 已成為統一模型網關，需要決定「前端要怎麼接它」才長期站得住。
- 本文所有結論都來自實測（curl / 瀏覽器行為），不是推測。

---

## 一、現況與硬約束

### 1. 部署現況

| 項目 | 現況 |
| --- | --- |
| 應用託管 | 149（macmini）上的 **qinglong 容器**：`python -m http.server 8000 -d /ql/data/scripts/bdc`；檔案在宿主機 `~/Documents/code/qinglong/ql/data/scripts/bdc`（活的 git 工作區，remote = github.com/lylasi/bdc） |
| 公網入口 1 | 路由器（iStoreOS）`https://bdc.eigui.cn:5000` → 149:8000；**自簽憑證**（issuer CN=iStoreOS） |
| 公網入口 2 | Cloudflare 隧道 `https://bdc.a4a4.qzz.io` → 149:8000；**有效憑證**（Google Trust Services）；與入口 1 內容相同（md5 一致） |
| 存取控制 | 兩條入口**都沒有**任何身分驗證 |
| magpie | mac5:3425，明文 http；`*:3425` 綁所有網卡；**未對公網暴露**（實測公網 IP 該埠不通） |

### 2. magpie 網關的三個實測行為

1. **來源白名單**：請求帶 `Origin` 且該來源在 `~/.config/magpie/settings.json` 的 `corsOrigins` 內 → 回 `Access-Control-Allow-Origin`；不在名單 → `403 permission_error`（訊息會要你去 Settings → Network and sharing → Web pages 加上）。
2. **預檢要靠 URL 裡的 key**：`OPTIONS` 預檢本身不帶 `Authorization`（瀏覽器規範如此），所以只有把 key 放進 URL（`?key=sk-magpie-…`）時，預檢才會被授權：實測 `204 + Access-Control-Allow-Headers: authorization, x-api-key`。純 header 認證在瀏覽器裡過不了預檢。
3. **gateway key 可限定模型與額度**：`magpie gateway-key list` 可看到每把 key 的可用模型；`magpie gateway-key limit <id> month --tokens N --cost USD` 可加月度上限。

### 3. 瀏覽器的三條硬規則（所有方案的邊界）

| 規則 | 觸發條件 | 後果 |
| --- | --- | --- |
| 混合內容 | https 頁面 → http 目標 | 直接攔，無法繞過 |
| Local Network Access | 公網來源頁面 → 私網位址（含 10.x、100.64/10 尾網段） | 需要使用者授權；**http 頁面連授權入口都沒有**（Chromium 153/155 實測） |
| 跨域 CORS | scheme/host/port 任一不同 | 需要伺服器回 CORS 頭；預檢由伺服器授權 |

**關鍵推論：只要頁面與網關不同源，就會掉進上面某一條；唯一能同時避開三條的形態是「同源」。**

## 二、風險現狀（依嚴重度排序）

1. **新的 HAPI key 在公網可下載的檔案裡** ⚠️ 最高
   `https://bdc.eigui.cn:5000/ai-config.js` 與 `https://bdc.a4a4.qzz.io/ai-config.js` 皆 `200`，內容含 `HAPI.apiKey` 明文。任何人都能抄走這把 key 直接消耗額度；且因為它是隨站點發布的，**任何訪客的瀏覽器都會拿它去呼叫 AI**，等於開了一個免費端點。
2. **兩條公網入口都無身分驗證**，且 `.git/config`、`docs/`、`scripts/`、`tests/` 皆可下載（實測 200）。因為倉庫在 GitHub 上本來就是 public，這條性質偏「原始碼公開」，危害低於第 1 條，但仍應收斂。
3. **路由器那條是自簽憑證**：每台裝置首次都要手動信任，長期會養成「看到警告照樣點繼續」的習慣；若 AI 憑證會經過這條通道，中間人風險變實質。
4. ✅ 已無明文 AI key 的其他副本（本次已清理），magpie 3425 未對公網暴露，http:5000 已關閉。

## 三、三個方案

| | 方案 A：瀏覽器直連 | 方案 B：同源 `/v1` 反代 | 方案 C：憑證留在服務端 |
| --- | --- | --- | --- |
| gateway key 在哪 | 每個瀏覽器 localStorage（+ 表單裡的 `?key=`） | 同方案 A | **只在服務端**（Worker secret） |
| 需要什麼 | 給 magpie 套一層 https（Tailscale Serve 或隧道 hostname） | 隧道加一條 `path: /v1/*` 規則（或路由器 nginx `location /v1/`） | Cloudflare Worker + Supabase JWT 驗證 + 隧道 Access service token |
| CORS / 混合內容 / LNA | 全部要處理（來源白名單、https、可能彈權限） | **全部消失**（同源） | **全部消失**（同源） |
| 換裝置 | 每台都要重填 key | 每台都要重填 key | 零設定 |
| key 洩漏後果 | 額度被盜用 | 額度被盜用 | 換 secret 即可（不落地） |
| 工作量 | 10 分鐘 | 10 分鐘 | 約半天 |
| 適合 | 只有自己幾台裝置、圖快 | 個人＋家人，長期自用 | 有別人用、要能管權限與額度 |

### 方案 A 的具體做法（二選一）

- Tailscale：`tailscale serve --bg --https=443 --set-path /v1 http://127.0.0.1:3425`，管道 URL 用 `https://<tailnet 名>/v1/chat/completions?key=…`。**但每台裝置都要裝 Tailscale**，且公網頁面連 100.64/10 位址會觸發 LNA 權限提示。
- Cloudflare 隧道：加一條 `magpie.<網域> → http://127.0.0.1:3425`，管道 URL 用 `https://magpie.<網域>/v1/…?key=…`。憑證有效、無混合內容；**網關就對公網開放了，只靠 gateway key 保護**（建議同時加 Access 或給 key 加額度上限）。

### 方案 B 的具體做法

Cloudflare 隧道的 ingress 支援 `path`，同一 hostname 下分流即可（不需要新進程、不需要 Caddy/serve.py）：

```yaml
ingress:
  - hostname: bdc.<網域>
    path: /v1/*
    service: http://10.10.10.5:3425
  - hostname: bdc.<網域>
    service: http://10.10.10.149:8000
  - service: http_status:404
```

前端只要把 provider 的 URL 寫成**相對路徑** `/v1`（`/v1/chat/completions`、`/v1/models`），頁面在內網、4G、任何地方都同源可用。
注意：同源 POST 仍會帶 `Origin`，而 magpie 的來源閘門不看同源與否 → **仍要把頁面來源加進 `corsOrigins`**，或由反代剝掉 `Origin` 頭。

### 方案 C 的具體做法

1. 隧道加一條只給 Worker 用的 hostname（例如 `magpie-internal.<網域> → http://127.0.0.1:3425`），並加 **Cloudflare Access Service Token** 策略，只允許該 token。
2. Worker 掛在 `bdc.<網域>/api/ai/*`（與頁面同源），職責：驗 Supabase JWT → 轉發到 magpie-internal → 注入 `Authorization: Bearer <gateway key>`（key 只存在 Worker secret）。
3. 前端 provider 寫相對路徑 `/api/ai/*`，**不需要任何 key**；`ai-config.js` 可以永久保持無憑證。
4. 順帶得到：按使用者限流、用量統計、以後要開放給別人用也不必改架構。

## 四、建議路線

| 步驟 | 內容 | 成本 | 解決什麼 |
| --- | --- | --- | --- |
| **Step 0（立刻）** | 把 HAPI key 從公開檔案移除（key 只留瀏覽器設定）；`corsOrigins` 補上實際頁面來源 | 5 分鐘 | 停止「免費端點」與憑證外洩 |
| **Step 1（今天）** | 用 Cloudflare 隧道做方案 B（同源 `/v1`），並**收斂成單一公網入口**（關掉路由器 5000 那條），順手拿到有效憑證 | 15 分鐘 | 同源＝CORS／混合內容／LNA 全部消失；告別自簽證書 |
| **Step 2（本週）** | 升級到方案 C（Worker 持 key + Supabase JWT + Access service token） | 半天 | 換裝置零設定、key 不落地、可管權限與額度 |
| **Step 3（可選）** | `magpie gateway-key limit <id> month --tokens N --cost USD`；對公開站點加 Access；再做「乾淨根目錄」 | 各 10 分鐘 | 縱深防禦 |

## 五、明確不要做

1. **不要把 gateway key 寫進任何隨站點發布的檔案**（`ai-config.js`、HTML、任何 docs）——公開站點等於把額度送人。
2. **不要讓同一份內容掛兩條公網入口**（自簽那條＋隧道那條）——維護加倍、風險加倍，且容易忘記關其中一條。
3. **不要用自簽憑證跑要傳遞憑證的通道**——會訓練使用者忽略警告。
4. **不要依賴「http 頁面 + 內網 IP」當長期方案**——只要換成 https 或從 4G 打開就失效。

## 六、附錄：本次實測指令（可重跑）

```bash
# magpie 的 CORS 與預檢行為（來源需先在 corsOrigins 內）
curl -sS -D - -o /dev/null -X OPTIONS \
  "http://10.10.10.5:3425/v1/chat/completions?key=<gateway key>" \
  -H "Origin: <頁面來源>" -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: authorization,content-type"

# 模型清單（gateway key 限定）
curl -sS "http://10.10.10.5:3425/v1/models?key=<gateway key>" -H "Origin: <頁面來源>"

# 公網入口暴露面自檢
for p in /ai-config.js /.git/config /docs/prd.md /scripts/serve.py /tests/; do
  printf '%-18s ' "$p"; curl -sSk -o /dev/null -w 'HTTP %{http_code}\n' "https://<入口>$p"
done
```
