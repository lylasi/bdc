# 管理員用戶管理 v1 實施計劃

- 時間：2026-10-18 05:28:24 CST
- 狀態：已完成（2026-10-18）
- 關聯：`cloudflare-worker/`、`features/ai-admin/`、`features/sync/`

## 1. 背景與目標

目前帳戶由部署者以 `cloudflare-worker/add-user.mjs` 產生 SQL，再透過
`wrangler d1 execute` 寫入 D1。日常新增用戶、修改備註、重設通行碼都需要
部署者介入，不利於多用戶維運。

本階段在既有管理員權限模型上增加「用戶管理」介面與 Worker 路由，覆蓋日常
維運所需的最小集合，同時保留「角色調整與帳戶刪除由部署者維護」的安全邊界。

## 2. v1 範圍

1. 管理員查看用戶列表：用戶代號、備註、角色、可選電郵、建立時間。
2. 新增用戶：Worker 產生 43 字元通行碼與恢復碼，只回傳一次；資料庫只存
   SHA-256 雜湊。
3. 編輯用戶：只允許修改備註名稱與可選電郵；用戶代號建立後不可修改。
4. 重設通行碼／恢復碼：僅限非管理員帳戶；重設後該用戶舊通行碼立即失效。
5. 管理操作寫入 `admin_audit_log`，不記錄通行碼、恢復碼或明文電郵。
6. 前端入口位於「設定 → 工具」，僅管理員可見；所有文案支援 `zh-CN` 與
   `zh-HK`。

## 3. 非範圍（本階段不做）

- 角色調整（`user` / `admin`）：仍由部署者在 D1 維護。
- 刪除用戶、停用帳戶：尚未提供；避免誤刪 `snapshots` 與
  `user_ai_credentials`。
- 管理員帳戶通行碼重設：仍由部署者以 CLI 或使用者自助恢復碼處理。
- 電郵 OAuth／魔法連結登入：本階段只新增可選 `email` 欄位，為日後登入方式
  預留映射，不改變目前通行碼登入流程。
- 首名管理員建立：仍必須由 CLI／D1 初始化，管理介面無法解決冷啟動。

## 4. 資料模型

新增 migration `cloudflare-worker/migrations/002_admin_user_management.sql`：

- `users.email TEXT`：可空；寫入前統一轉小寫；非空時唯一。
- `users.created_at TEXT`：ISO 時間；既有用戶為 `NULL`。
- `admin_audit_log`：
  - `id`、`actor_user_id`、`action`、`target_user_id`、`detail_json`、`created_at`
  - 動作：`user_create`、`user_update`、`user_reset_passcode`
  - 不記錄任何憑證或明文個人資料。

同時更新 `cloudflare-worker/schema.sql`，讓全新安裝直接具備相同結構。

## 5. Worker API

全部路由先經既有 `authenticate()`、`requireStrongPasscode()`，再檢查
`user.role === 'admin'`。

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| GET | `/admin/users` | 用戶列表；不回傳任何雜湊 |
| POST | `/admin/users` | 建立 `role=user` 帳戶，回傳一次性通行碼／恢復碼 |
| PUT | `/admin/users/:id` | 修改 `label`／`email` |
| POST | `/admin/users/:id/reset-passcode` | 重設非管理員帳戶的通行碼／恢復碼 |

錯誤碼：`admin_required`、`invalid_user_id`、`invalid_label`、`invalid_email`、
`user_exists`、`email_exists`、`user_not_found`、`admin_account_protected`、
`rate_limited`、`method_not_allowed`。

寫入與審計使用 `env.DB.batch()`，避免操作成功但審計缺失。

## 6. 前端

新增 `features/admin-users/admin-users.js`：

- `initAdminUsers()`：監聽登出／帳戶切換／工作階段失效並關閉面板。
- `openAdminUsersPanel()`：獨立覆蓋層，沿用 `ai-admin-overlay` 視覺外殼。
- 列表、建立表單、編輯表單、一次性憑證卡片、面板內重設確認。
- 憑證提供複製按鈕與「只顯示一次」警告；關閉面板即清除記憶體中的憑證。
- 管理員帳戶不顯示重設按鈕，改顯示由部署者維護的提示。

入口：`features/sync/sync.js` 的「設定 → 工具」加入僅管理員可見的卡片，
由 `main.js` 呼叫 `initAdminUsers()`。

## 7. 安全邊界

- 前端隱藏按鈕不構成授權；Worker 每次請求重新檢查角色。
- 通行碼與恢復碼只在建立／重設回應中出現一次，不寫入日誌、審計或快照。
- 重設管理員帳戶被拒絕，避免管理員互相接管或誤將自己登出。
- 用戶代號限制為 `[A-Za-z0-9_-]{1,64}`，避免路徑與 SQL 注入風險。
- 列表與變更操作都有獨立速率限制。
- 不新增刪除或角色升級接口，維持既有部署者邊界。

## 8. OAuth 相容性

本階段僅新增可空 `email` 欄位。若日後採用電郵 OAuth，還需要：

- `user_sessions`：支援多裝置工作階段與撤銷；目前 `users.token_hash` 每人只有
  一組，OAuth 每次登入若覆寫會讓其他裝置失效。
- `user_identities`：保存 provider + subject 映射，避免只依賴可變更的電郵。
- OAuth start／callback／一次性授權碼交換、state／PKCE、`email_verified` 檢查、
  邀請制白名單與工作階段撤銷。
- 若使用 Cloudflare Access，Worker 需自訂網域、驗證 `Cf-Access-Jwt-Assertion`，
  並處理跨來源 Cookie 限制；不適合直接套在 `workers.dev`。

## 9. 驗證

```bash
node --test tests/ai-worker.test.mjs tests/ai-units.test.mjs tests/ai-sync-regressions.test.mjs
node tests/audit-i18n.mjs
PORT=8313 PLAYWRIGHT_MODULE=<path-to-playwright> node tests/audit-flows.cjs
PORT=8313 PLAYWRIGHT_MODULE=<path-to-playwright> node tests/admin-users.cjs
```

另需手動驗證：

1. 管理員可在「設定 → 工具」開啟用戶管理。
2. 建立用戶後通行碼／恢復碼只顯示一次，複製可用。
3. 新用戶以新通行碼登入，舊用戶不受影響。
4. 編輯備註／電郵後列表即時更新。
5. 重設非管理員通行碼後，該用戶舊工作階段失效。
6. 普通用戶直接呼叫 `/admin/users` 取得 403。
7. `zh-CN` 與 `zh-HK` 完整流程文案一致。

## 10. 部署順序

1. 備份 D1。
2. 套用 `migrations/002_admin_user_management.sql`。
3. 部署 Worker。
4. 部署前端。
5. 以管理員登入驗證列表、建立、編輯與重設流程。
