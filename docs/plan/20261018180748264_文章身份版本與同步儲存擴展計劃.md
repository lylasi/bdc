## 0. 摘要

這次一併處理兩個相連的問題：

1. **文章身份（identity）**：目前「重新分析」會建立新的 `articleId`，「改一小段再貼上」會被當成新文章；同一篇文在閱讀記錄裡長出多筆，文章專屬生詞本也跟著分裂。
2. **儲存與同步**：一份分析結果在 JSON 裡重複存了 2–3 份；每次自動同步會下載全量、上傳全量，還在 localStorage 再存兩份全量備份；雲端單次快照上限 2 MB，文章一多就撞牆。

建議路線：

| 階段 | 內容 | 效果 |
| --- | --- | --- |
| Phase 0 | 沿用現有 `articleId`，修正重新分析流程 | 根治「改一小段變新文章」的主路徑 |
| Phase 1 | 分析結果 schema v2 去重、備份移到 IndexedDB、容量治理、413 處理 | 文章資料體積約減半；localStorage 不再被備份撐爆 |
| Phase 2 | 指紋／SimHash 相似提示、重複整理、版本 metadata | 貼上修改版也能辨識為同一篇，且不自動刪資料 |
| Phase 3 | 文章索引 + 內容 blob（內容尋址）同步 | 快照只放索引；每次同步只傳變更的文章 |
| Phase 4 | 索引層 per-article LWW + tombstone + blob GC | 多裝置同時新增／刪除不互相覆蓋 |

Phase 0–1 建議與閱讀記錄 UI 優化同批上線；Phase 3 是較大的前後端工程，先立計劃再動工。

## 1. 問題重現與根因

### 1.1 同一篇文章變成多筆記錄

| 情境 | 目前行為 | 根因 |
| --- | --- | --- |
| 從閱讀記錄載入 → 改一段 → 按分析 | 新增一筆記錄、新的文章生詞本 | `buildArticleMetaInput()` 不帶 `id`（`article.js:115-137`）；非 URL 來源一律生成新的 `local:` id（`storage.js:401-408`）；`saveAnalysisResult` 用新 id 找不到，再用完整內文比對也因內容已改而找不到（`storage.js:595-618`） |
| 同一篇不改直接重新分析 | 記錄的 `articleId` 被換掉，舊 meta／生詞本變孤兒 | 先產生新 id，`saveAnalysisResult` 才用內文完全相符找到舊記錄並覆寫 `articleId` |
| 貼上修改後的全文 | 必然新增一筆 | 沒有 `currentArticleId`、沒有 URL，只能靠完整內文比對 |
| 從 URL 重新匯入 | 正確更新原記錄 | `findArticleMetaByUrl()` 會重用 meta（`storage.js:167-172`、`387-394`） |
| 從文章庫重新載入同一篇 | 每分析一次就多一筆 | `sourceType=file` 只帶路徑，沒有重用既有 id |

結論：身份目前綁在「這次分析所建立的 meta id」，而不是「這篇文章本身」；也沒有內容指紋可以做二次判定。

### 1.2 儲存與同步的實際成本

以 `articles/manifest.json` 第一篇（1,832 字元）模擬目前結果結構（中文長度約英文 55%）：

| 模式 | 目前 v1 | 精簡 v2 | 節省 |
| --- | ---: | ---: | ---: |
| 標準（無 `sentences`） | 4,746 字元 | 3,187 字元 | **33%** |
| 逐句（`sentences.en/zh`） | 8,268 字元 | 4,424 字元 | **46%** |

| 項目 | 目前 v1 | 精簡 v2 | 說明 |
| --- | --- | --- | --- |
| 單筆記錄 JSON | 4.7–8.3k 字元 | 3.2–4.4k 字元 | 視模式而定，約 **-33~46%** |
| 100 筆（localStorage，UTF-16） | 約 0.95–1.65 MB | 約 0.64–0.88 MB | 未計備份 |
| 100 筆 + 2 份自動備份 | 約 2.9–5.0 MB | — | 逐句模式接近 5 MB 配額；長文章會直接爆 |
| 100 筆快照（UTF-8） | 約 0.5–0.8 MB | — | 長文章（6k 字）約 1.6–2.7 MB，超過 2 MB 上限 |

其他放大器：

- **重複儲存**：`finalResult` 同時存了 `chinese_translation`、`word_alignment`、`detailed_analysis` 的聚合版，以及逐段的 `paragraph_analysis`（`article.js:1904-1910`）。逐句模式還在 `paragraph_analysis[].sentences` 裡再存一次英文與中文。
- **自動備份**：`local-backup.js` 把完整 payload 再寫進 localStorage，自動備份保留 2 份（`MAX_AUTO_BACKUPS = 2`）；`sync.js:1595` 每次自動同步都呼叫 `createBackup()`，等於即時資料的 3 倍。
- **全量同步**：`syncNow()` 無條件 `pullSnapshot()`（整包）→ `buildLocalSnapshot()`（整包 stringify）→ `pushSnapshot()`（整包）→ `applyMergedSnapshot()`（整包 parse）→ `createBackup()`（再整包一次）。
- **沒有條件請求**：`/snapshot` 不支援 ETag／304；本機改了資料但雲端沒變，仍下載整包。
- **群組級 LWW**：`articles` 整包比 `updatedAt`，兩台裝置各新增文章時，後同步者會蓋掉前者。
- **詛咒性成長**：孤兒 meta、重複記錄、無限備份都只增不減；2 MB 上限（Worker `SNAPSHOT_MAX_BYTES`、selfhost 同名常數）遲早會撞到。

## 2. 文章身份模型（Phase 0 + 2）

### 2.1 身份解析順序

分析前先決定「這篇要更新哪一筆」：

```text
resolveArticleIdentity({ text, sourceType, sourceUrl, currentId })
1. currentId 存在且記錄還在            → 沿用（載入歷史後編輯的主路徑）
2. sourceUrl 正規化後命中既有 meta      → 沿用（同一網址更新）
3. fingerprint(text) 命中既有記錄       → 沿用（空白／換行差異、完全相同的貼上）
4. simhash 相近且段落重疊達門檻         → 詢問使用者（更新原記錄／另存新篇／取消）
5. 以上皆無                            → 建立新 local id
```

實作要點：

- `buildArticleMetaInput()` 接受 `id`（來自步驟 1–3），讓 `getOrCreateArticleWordbook()` 走既有「有 id 就沿用」分支（`storage.js:381-388`），不需要改 storage 介面。
- URL 正規化：`new URL()`、host 小寫、移除 `utm_*`／`fbclid`／`gclid`／`spm` 等追蹤參數、移除 hash、去除尾斜線；保留其餘 query（有些站用 query 當文章 id）。
- 完整內文比對仍保留作為 fingerprint 的二次確認；兩者都命中才視為同一篇。

### 2.2 fingerprint 與 simhash

| 項目 | 做法 |
| --- | --- |
| 正規化 | Unicode NFC、CRLF→LF、逐行 trim、合併水平空白、去 BOM／零寬字元；**不**移除標點或 Markdown 符號（避免把不同文章誤判成同一篇） |
| fingerprint | 64-bit FNV-1a（同步、無需 Web Crypto）轉 hex；命中後再比對 `chars` 與頭尾各 80 字 |
| simhash | 正規化後取 3-gram token，64-bit SimHash 轉 hex；只用來快速篩候選 |
| 候選條件 | 最近 50 筆、`popcount(a XOR b) ≤ 6`、字數比在 0.7–1.4 |
| 二次確認 | **逐句** hash 的 Jaccard ≥ 0.6 才顯示「可能是同一篇」（用逐句而非逐段，容忍段落合併／拆分） |
| 短文章 | 少於 5 句或 300 字元時改用：距離 ≤ 3、長度比 0.8–1.25、Jaccard ≥ 0.8；否則不提示 |
| 成本 | 只在按下分析時計算一次；O(50) 的 popcount 與句子比對，可忽略 |

> 不做「自動合併」。相似度誤判的代價（譯文、生詞本被換掉）遠高於多問一次。

### 2.3 更新流程與版本

沿用既有記錄時：

- 更新 `article`、`result`、`fingerprint`、`simhash`、`chars`、`updatedAt`；
- `createdAt` 保持第一次建立時間；
- `analysisCount += 1`；
- 選配 `revisions: [{ at, fingerprint, chars }]`，最多 5 筆，**只存 metadata**，不存舊譯文；
- 依決策 1：**預設不保留**完整舊結果；Phase 3 之後才提供 `reading.keepArticlePreviousResult`，開啟時以獨立 blob 保留 **1 份**上一版，並在容量面板顯示額外佔用；
- 文章專屬生詞本 id 不變，選字加入生詞本仍然正確。

UI 影響：

- 閱讀記錄清單一篇文章只有一列，副標顯示「更新於 2 小時前 · 分析 3 次」；
- 分析完成提示由「已存入閱讀記錄」改為「已更新《X》 · 第 3 次分析」；
- 需要保留兩個分支時提供「另存新篇」：複製記錄與 meta，新的 `local:` id，標題加「（副本）」。

### 2.4 相似文章提示

當步驟 4 命中時，用既有 `app-modal` 顯示（不用原生 confirm，因為需要三個選項）：

```
┌ 可能是同一篇文章                                 × ┐
│ 這次輸入與《The Future of Work》相似度 92%。        │
│ 要更新原記錄，還是另存為新的一篇？                   │
│                                                    │
│ [更新原記錄]  [另存新篇]  [取消分析]                │
└────────────────────────────────────────────────────┘
```

- 「更新原記錄」→ 沿用候選 id，進入正常分析流程；
- 「另存新篇」→ 新 id，並記住這個文字指紋的選擇（同一 session 不再問）；
- 「取消分析」→ 不呼叫 AI、不改任何資料。

### 2.5 重複整理（非破壞性）

- 閱讀記錄管理新增「整理重複」：
  - **完全相同**（fingerprint 相同）：可一鍵合併；
  - **可能重複**（simhash 相近 + 段落重疊）：列出成對候選，逐一確認。
- 合併規則：
  - 保留較新的 `result` 與 `article`；
  - `createdAt` 取最早、`analysisCount` 取最大、`revisions` 聯集；
  - 刪除被合併那筆的記錄與 meta；
  - **不刪除**它的文章專屬生詞本（可能已有使用者單字），在確認文案說明「生詞本會保留在詞書列表」。
- 升級後第一次載入若偵測到完全相同的重複，提示一次「發現 N 筆重複記錄，要合併嗎？」可選「稍後」。

### 2.6 記錄欄位（schema v2）

```js
{
  articleId,        // 穩定身份，不再隨分析變動
  article,          // 目前內文
  result,           // 最新分析結果（見 3.1）
  title,            // 選配：使用者重新命名；優先用 meta.title
  createdAt,        // ms
  updatedAt,        // ISO
  fingerprint,      // 64-bit hex
  simhash,          // 64-bit hex
  chars,            // 內文字數
  analysisCount,    // 分析次數
  sourceType,       // 選配：meta 缺失時的後備
  sourceUrl,        // 選配
  revisions?        // [{ at, fingerprint, chars }]，最多 5
}
```

單筆增加約 100–200 bytes，相對節省下來的體積可忽略；同步快照向後相容（舊版忽略未知欄位）。

## 3. 儲存精簡（Phase 1）

### 3.1 分析結果 schema v2

改成「逐段為唯一來源」，其餘在載入時推導：

```js
result: {
  v: 2,
  paragraph_analysis: [
    {
      chinese_translation: '...',
      word_alignment: [],          // 空陣列直接省略
      detailed_analysis: [],       // 空陣列直接省略
      sentences: ['譯句 1', '譯句 2'] // 只留中文；英文由本地分句器重建
    }
  ],
  sentence_analysis: [...],        // 保留（使用者逐句點開的結果）
  phrase_analysis: [...]           // 保留（最多 3/句）
}
```

- 移除 top-level 的 `chinese_translation`、`word_alignment`、`detailed_analysis`（渲染前由段落推導，`displayArticleAnalysis` 目前本來就以 `paragraph_analysis` 為主）。
- `sentences` 移除 `en`：`alignedZhSentences()` 已允許 `p.en` 不存在（`article.js:3781-3793`），本地分句順序一致時仍能逐句對齊。
- 省略空字串／空陣列；`failed` 段落保留標記，但不要寫入假的翻譯。
- 提供兩個純函式：
  - `compactArticleResult(result)`：寫入 storage／push 前使用；
  - `hydrateArticleResult(result)`：載入／套用快照後還原成現有渲染程式期待的形狀。
- 實測樣本：標準模式 4,746 → 3,187 字元（-33%）；逐句模式 8,268 → 4,424 字元（-46%）。
- **標註資料必須另設全域上限**：`sentence_analysis` 與 `phrase_analysis` 目前沒有全域上限，長文大量點開可累積數 MB。
  - `sentence_analysis` 最多 300 筆；
  - `phrase_analysis` 最多 300 筆；
  - 兩者序列化合計 ≤ 256 KB；
  - 超過時淘汰最舊並提示；
  - 單篇文件（article + result）硬上限 800 KB。
- 相容：若結果沒有 `paragraph_analysis`（更舊的資料），`compactArticleResult()` 直接回傳原物件，不強行拆解；`hydrateArticleResult()` 兩種形狀都要能吃。
- `sentences` 只留中文後，`alignedZhSentences()` 需要接受字串陣列（目前讀 `p.zh`），hydration 時轉回 `[{ zh }]` 或調整函式。

### 3.2 備份搬離 localStorage

這是目前最容易忽略的配額殺手（即時資料 + 2 份完整備份 ≈ 3 倍）。

- 新增 IndexedDB `bdc-backup`（store `backups`，key `ts`），把 `bdc:backup:v1:*` 逐筆遷移後刪除舊 key；索引可留在 localStorage。
- 保留策略：自動備份 2 份、手動備份 3 份；超過就淘汰最舊（目前手動備份無上限）。
- 自動備份降頻：
  - 只在 `articlesUpdatedAt` 或其他群組時間戳真的變了才備份；
  - 自動備份最短間隔 30 分鐘；
  - 自動備份只存「索引 + 非文章群組」，文章本文與結果交給 IDB 的正式資料（或一併存 IDB，反正不佔 localStorage）。
- `syncNow` 完成後直接把已建好的 payload 傳給備份，避免再 `buildLocalSnapshot()` 一次（`local-backup.js:106-113`）。
- 備份失敗（quota）要回報，不要靜默吞掉。

**Phase 3 的索引化會讓備份／還原／匯出失效，必須同步改：**

- 備份格式升版為 `{ format: 2, payload, docs: { [hash]: { article, result } } }`；舊格式仍可讀。
- 自動備份可只存索引；**手動備份與匯出必須包含 docs**，否則還原後只有清單、沒有內容。
- 匯出改用 `CompressionStream('gzip')` 產生 `.json.gz`（或把上限提高到 100 MB 並警告）；匯入同時支援舊 JSON 與新 gzip。
- `listBackups()`／`loadBackupPayload()` 改成 async（IndexedDB）；`showBackupRestoreModal()` 一併調整。
- `restoreSnapshotLocally()` 遇到 schema 2：先把 docs 寫入 IndexedDB，再寫索引；缺 docs 的索引標記「只有索引，需重新同步」，不要假裝成功。
- 補測試：備份 → 清空 → 還原 → 每篇文章可開啟；無網路時也能還原。

### 3.3 容量治理

- 在閱讀記錄 footer 與同步設定顯示：
  - 文章筆數、估算大小（`JSON.stringify(state.analyzedArticles).length * 2` bytes）；
  - 備份份數與 IndexedDB 估算用量；
  - localStorage 其他 key 的粗略佔用（可選）。
- 閾值：
  - 3 MB：黃色提示「建議清理較舊的文章」；
  - 4 MB：分析前提示，仍允許（不阻止使用者）；
  - 篇數 400：軟警示；1,000：硬上限（需先清理才能新增分析）；
  - 單篇 20k 字元：提示分析時間；100k 字元：硬上限（提示分段）。
- 任何寫入失敗都要有明確文案（`article.historySaveFailed`），不能讓 `analyzeArticle` 的大 `try` 把畫面覆寫成「分析失敗」。

### 3.4 孤兒 meta 清理

- 分析流程不再產生新 id 後，孤兒主要來自舊資料。
- 載入後掃描 `articleMetas`：若某 id 既沒有對應記錄、也沒有對應生詞本（`getWordbookById(id)`），視為孤兒。
- 可選：自動刪除並更新 `articlesUpdatedAt`；或只在容量面板顯示「N 筆可清理」讓使用者手動清理。
- 文章專屬生詞本仍在時**不要**刪 meta，否則詞書的「回到文章」會失去來源資訊。

### 3.5 清單效能與搜尋範圍

- 目前 `buildArticleHistoryRecords()` 每筆都重新 `parseTitleAndParagraphs()` 解析全文（`article.js:2096-2121`）；1,000 篇時每次開啟清單都要解析數 MB 字串。
- 儲存時就把 `title`、`summary`（前 200 字）、`chars` 寫進記錄／索引，清單只讀這些欄位，不再解析全文。
- 搜尋範圍：
  - 索引只放標題與 excerpt，因此同步完成前只搜尋「標題＋摘要」；
  - 全文搜尋只在已載入 IndexedDB 的文件上做，UI 顯示「尚有 N 篇未下載」；
  - 背景下載完成後再自動擴大到全文；不要為了搜尋在啟動時阻塞下載全部文章。
- 超過 200 列使用虛擬列表或分批渲染，避免一次建立上千個 DOM。

### 3.6 重新分析與既有標註

- 目前 `finalResult` 只由 `paragraphAnalyses` 組成（`article.js:1904-1910`），重新分析會丟掉舊的 `sentence_analysis`／`phrase_analysis`。
- 建議：
  - 內文未變：合併舊的句子／片語分析；
  - 內文有變：只保留 sentence/context 仍能對上的項目，其餘丟棄並提示；
  - 或在重新分析前明確警告「會清除逐句筆記」。
- 這與決策 1 無關：`previousResult` 預設關閉，但「目前的逐句筆記」不應該無聲消失。

## 4. 同步擴展（Phase 3–4）

### 4.1 現況成本

一次本機改動（例如新增一個單字）目前會：

```text
touch → 6s debounce（最短 20s 間隔）
  → syncNow()
    → GET  /snapshot          全量下載
    → buildLocalSnapshot()    全量 stringify（含全部文章）
    → lwwMerge()              全量 stringify 比對
    → POST /snapshot          全量上傳（上限 2 MB）
    → applyMergedSnapshot()   全量 parse + 套用
    → createBackup()          再建一次全量 payload → localStorage
```

100 篇短文約 0.8 MB：一次小改動 ≈ 1.6 MB 網路 + 1.6 MB 本機寫入；300 篇或長文章直接超過 2 MB 而同步失敗。

### 4.2 方案比較

| 方案 | 做法 | 每次同步傳輸 | 本機配額 | 跨裝置完整度 | 工程 | 風險 |
| --- | --- | --- | --- | --- | --- | --- |
| A. 就地精簡 | result v2、備份搬家、容量治理 | 仍全量，但約 -33~46% | 大幅改善 | 完整 | 小 | 低 |
| B. 壓縮 | `CompressionStream` + base64 放入快照 | 全量，約 -60~75% | 改善 | 完整 | 中 | 除錯、舊客戶端、伺服器大小檢查 |
| C. 索引 + 內容 blob（推薦） | 快照只放索引；文章本文／結果用內容尋址 blob 按需同步 | **O(變更)** | 本文移到 IndexedDB，幾乎不佔 localStorage | 完整 | 大 | 兩階段一致性、GC |
| D. 每篇一列 + 增量 API | D1/自建庫 `article_docs`，`/articles?since=` 增量 | O(變更) | 同上 | 完整 | 大 | 遷移、per-article 衝突、selfhost 同步維護 |
| E. 雲端只留最近 N 篇 | 舊文只在本機 | 小 | 改善 | 舊文跨裝置看不到 | 小 | 不建議 |

**推薦 C**：

- 對現有「一個使用者一列快照」的架構改動最小，其他群組（詞書、問答、助手）完全不用動；
- 文章內容是 opaque JSON，伺服器不需要解析或清洗；
- 內容尋址天然去重，也為後續「保留上一版結果」鋪路；
- 每次同步只傳新文章／改過的文章，索引本身只有幾十 KB。

D 的 per-article API 更標準，但需要改寫群組合併語義、增加伺服器端查詢與衝突處理；等 C 落地後如果需要在伺服器端搜尋／排序，再升級。

### 4.3 目標架構

#### 本機

```text
localStorage
  analyzedArticles = [ index entry, ... ]        // 不含 article / result
  articleMetas     = { id: meta }
  articlesUpdatedAt, lastSnapshotVersion, ...

IndexedDB  bdc-articles
  docs      key = docHash   → { article, result, bytes }
  byArticle key = articleId → { docHash, updatedAt }
  syncState key = 'state'   → { pushed: { articleId: docHash }, cursor }

IndexedDB  bdc-backup
  backups   key = ts        → { note, payload, ts }
```

- **索引常駐、文件快取**，不要在啟動時下載全部文章：
  - `state.analyzedArticles` 只放索引；
  - 啟動時只載入 IndexedDB 已有的 docs（快、離線可用）；
  - 背景下載缺少的 docs，分批、可續傳、顯示「已同步 N/M」；
  - 開啟文章時若 doc 不在記憶體／IDB，顯示「正在下載分析結果」並單篇 fetch；
  - 目前文章與最近開啟優先預取。
- 所有讀取改走 `getArticleDoc(articleId)`（async）；`showCurrentArticleIfAvailable()` 改成 async，導航用 `await` 或 fire-and-forget。歷史清單只用索引欄位，不需要 docs。
- 若不想全面改成 async getter，退而求其次：啟動只載入本機 docs，缺少的條目在清單顯示「同步中」，點擊時才下載。**不要**在啟動時阻塞下載全部文章。
- 1,000 篇的索引約 250 KB；記憶體中的 docs 依實際開啟／預取數量增長，不需要一次全載。
- 請求 `navigator.storage.persist()`，降低瀏覽器自動回收 IndexedDB 的機率。

#### 快照

```js
articles: {
  updatedAt,
  schema: 2,
  index: [
    {
      articleId, title, sourceType, sourceUrl,
      createdAt, updatedAt, fingerprint, simhash,
      chars, analysisCount, docHash
    }
  ],
  tombstones: { [articleId]: '2026-10-18T...' }, // Phase 3
  metas: [ ... ]                                  // 保持現狀
}
```

- 每篇索引約 200–300 bytes；500 篇約 125 KB，1,000 篇約 250 KB。
- 不再有 `analyzedArticles` 全文陣列。
- `docHash` 在安全上下文用 SHA-256（`crypto.subtle`）；LAN HTTP 沒有 `crypto.subtle` 時，改用同步的 **128-bit fallback**（例如兩組 FNV-1a 64-bit），不可退回現有 32-bit 快取雜湊。
- 若啟用「保留上一版」，索引額外帶 `previousDocHash`（預設不寫）。

#### Blob API（Worker / selfhost 同一套）

```text
POST /blobs
  { items: [{ hash, data }] }        // 單個 ≤ 900 KB，單批 ≤ 10 個、總量 ≤ 4 MB
  → { stored: [hash], rejected: [{ hash, reason }] }

GET /blobs/:hash                     → 200 JSON | 404
POST /blobs/missing                  { hashes: [] } → { missing: [] }
POST /blobs/fetch                    { hashes: [] } → { docs: { [hash]: data } }
                                     // 批次下載，單批 ≤ 10 篇 / 2 MB
```

資料表：

```sql
CREATE TABLE article_blobs (
  user_id    TEXT NOT NULL,
  hash       TEXT NOT NULL,
  payload    TEXT NOT NULL,
  bytes      INTEGER NOT NULL,
  created_at TEXT NOT NULL,
  PRIMARY KEY (user_id, hash)
);
CREATE INDEX idx_article_blobs_created ON article_blobs(created_at);
```

- 認證沿用現有 session；速率限制沿用 `rateLimit()`。
- 伺服器不解析文章內容，但需驗證：hash 格式、單篇／單批大小、index 筆數上限（2,000）、payload 可解析為 JSON。
- 配額：單 blob **900 KB**、單使用者 50 MB（`MAX_ARTICLE_BYTES_PER_USER` 可調）；超額回 `413 quota_exceeded` 並附 `{ used, limit }`。
  - 900 KB 是為了避開 D1 單列 1 MB 的 overhead；若實測 D1 上限更高，再調回 1 MB。
  - 單篇文件（article + result，含標註）硬上限 800 KB，超過時阻止新增標註並提示清理或分段。
- 快照 push 時驗證索引：若引用了不存在的 blob，回 `409 missing_blobs` 並附 hash 清單，要求先上傳；避免「索引有、內容沒有」。
- 刪除與 GC：
  - **不要**在每次 push 更新所有 index hash 的 `last_seen_at`（500 篇 = 500 次 UPDATE，會撞 D1 寫入限制）。
  - GC 直接讀目前快照 index，刪除「`created_at < now - 30d` 且不在 index」的 blob；被 index 引用的 blob 永遠保留。
  - 每日 cron（Worker `scheduled`／selfhost `setInterval`）執行；`IN (...)` 要分批，避免參數上限。
  - 提供「立即清理未引用」動作（未引用且建立超過 24 小時），讓使用者主動釋放配額。

#### 同步流程

```text
1. GET /version
   ├─ 與 lastSnapshotVersion 相同且本機沒有 dirty → 結束（零下載）
   └─ 有變化 → 2
2. GET /snapshot（只有索引，幾十 KB）
3. 合併索引（Phase 3：per-article LWW + tombstones）
4. 找出遠端有、本機 IDB 沒有的 docHash → POST /blobs/missing → POST /blobs/fetch 批次下載
5. 寫入 IDB；本機已有的 docs 先 hydrate，缺少的顯示「同步中」，不阻塞啟動
6. 找出本機 dirty 的 docHash → POST /blobs（先上傳內容）
7. POST /snapshot（只推索引）→ 成功後清除 dirty 標記
8. 視需要備份（IndexedDB，且只在內容真的變了時）
```

順序很重要：**先上傳 blob、再推索引**。若 blob 上傳失敗就中止該次 push，索引仍指向上一版，雲端不會出現「索引有、內容沒有」的斷鏈。失敗的 blob 放進重試佇列，下次同步先補。

### 4.4 衝突與刪除

目前 `articles` 是整包 LWW，兩台裝置各新增文章會互相覆蓋。索引化之後可以順手改成 per-article：

- `mergeArticleIndex(local, remote)`：
  - 以 `articleId` 為 key；
  - 同一 id 取 `updatedAt` 較新者；相同時取 `docHash` 字典序較大者（決定性）；
  - `tombstones[id] > entry.updatedAt` 時視為已刪除。
- 刪除文章時寫入 `tombstones[id] = now`，保留 **180 天**後清除；避免離線裝置把舊文章復活。
- tombstone 與 per-article merge **提前到 Phase 3**，不要等 Phase 4；Phase 4 只做 GC 加固、usage、監控。
- 刪除時保留本機 doc 至少到 undo 視窗結束（8 秒）；雲端 blob 由 GC 在 30 天後回收。
- 詞書、問答、助手仍維持現有群組 LWW，不在這次範圍。

### 4.5 遷移與相容

**本機遷移**（第一次載入新版）：

1. 讀取舊 `analyzedArticles`（v1）；
2. `compactArticleResult()` → v2；
3. 計算 `fingerprint`／`simhash`／`docHash`；
4. 文件寫入 `bdc-articles.docs`，`byArticle` 建索引；
5. 驗證文件數與原文筆數一致後，才把 localStorage 改寫成索引陣列，寫入 `articleDataVersion = 2`；
6. 全部文章標記 dirty，第一次同步時分批上傳（顯示進度、可續傳）；
7. 遷移前先建立一份 IndexedDB 備份或匯出檔案（localStorage 可能已滿，不要依賴它）。

**遷移邊界（必須處理）**：

- 沒有 `articleId` 的舊記錄：用 `local:legacy-<fingerprint>` 補一個，並建立 meta。
- 沒有 `paragraph_analysis` 的舊結果：保留 v1 形狀，`compactArticleResult()` 直接回傳原物件，不要硬拆。
- `url:` id 的網址未正規化：查詢時先比對原始 URL，再比對「正規化後」的 `sourceUrl`，找到就沿用舊 id；不要批次改 id。
- `sourceType === 'file'` 的 `sourceUrl` 是檔案路徑，不要丟進 `new URL()`；只做斜線與大小寫正規化。
- IndexedDB 寫入失敗（配額、私密模式）：保留 v1 資料，不寫 `articleDataVersion`，提示使用者清理或改用支援 IndexedDB 的瀏覽器。
- 遷移可重入：已寫入 docs 的 hash 不重寫；中斷後從 dirty 清單續傳。
- 舊快照 pull 到一半失敗：不要覆寫本機索引，等下次同步重試。

**雲端遷移**：

- 新客戶端 pull 到舊快照（有 `analyzedArticles`、沒有 `schema: 2`）時，走同一套本機遷移，然後上傳 blob、推送新索引。
- 舊客戶端 pull 到新快照時會看不到 `analyzedArticles`；必須擋住降級：
  - push 時帶 `X-BDC-Sync-Schema: 2`；
  - 伺服器若已存 schema 2，收到 schema 1 且帶 `payload.articles.analyzedArticles` 的 push → `409 client_upgrade_required`；
  - 舊客戶端顯示「此裝置的版本過舊，請重新載入／更新後再同步」。
- **部署順序**：伺服器只有在收到第一個 schema 2 push 後才會進入閘門；在那之前舊裝置仍可 push。發布時要同時要求所有裝置重新載入，並在 release note 寫明；若擔心這個空窗，先做一次全量本機／雲端備份。
- 由於是個人專案，接受「所有裝置需更新到新版前端」的發布要求，並在 release note 寫明。
- 回滾：保留遷移前的快照（可在伺服器加一次性 `snapshot_before_articles_v2` 欄位或由本地備份匯出），出問題可整包還原。

### 4.6 不必等 Phase 3 的快贏

即使暫不做 blob，以下措施可以先做（Phase 1）：

1. **先問版本再拉全量**：`syncNow` 先 `GET /version`；若遠端版本等於 `lastSnapshotVersion` 且本機有變更，直接帶 `expected_version` push；衝突才回頭 pull。
2. **條件請求**：`GET /snapshot` 支援 `If-None-Match: <version>`，相同回 `304`（Worker/selfhost 各幾行）。
3. **413 可行動化**：`payload_too_large` 時顯示「文章資料過大，請清理或等同步升級」，附上容量面板入口；不要把錯誤吞成「同步失敗」。
4. **停止每次同步的完整備份**（見 3.2）。
5. **避免重複 compact**：`compactAnalyzedArticles` 以 `articlesUpdatedAt` 做快取，不要每次 build 都跑。
6. **助手會話上限**：`buildAssistantSnapshotPayload` 每段會話只留最近 50 則（`sync-core.js:111`）；若會話含長文章上下文，再加單則長度上限。
7. **壓縮（選配）**：若 Phase 3 延期，可用 `CompressionStream('gzip')` 把 `articles` 群組壓成 base64 字串（新舊客戶端需協商），作為過渡。

### 4.7 可觀測性與限額

- 同步面板顯示：
  - 快照大小、索引篇數、blob 數量／位元組、最後同步時間與錯誤；
  - 本機文章篇數、估算大小、備份份數。
- 伺服器可選 `GET /usage` 回傳 `{ snapshotBytes, blobCount, blobBytes, limitBytes }`，前端在容量面板顯示。
- 日誌只記 hash 與大小，不記文章內容。

## 5. 路線圖

| 階段 | 內容 | 交付 | 估時 | 依賴 |
| --- | --- | --- | --- | --- |
| **Phase 0** | 沿用 `articleId`；重新分析更新原記錄；URL 正規化；沿用原 meta／生詞本 | 無重複記錄、生詞本不再分裂 | 1 天 | 無 |
| **Phase 1** | result v2、hydrate/compact、標註上限、備份搬 IndexedDB、容量面板、413 與存檔失敗處理、版本預檢 | 100 篇短文穩定；同步 payload 減 33–46% | 1.5–2 天 | Phase 0 |
| **Phase 2** | fingerprint／simhash、相似提示、重複整理（保留生詞本連結）、`analysisCount`／`revisions`、另存新篇 | 貼上修改版也能辨識；重複可整理 | 1–1.5 天 | Phase 0 |
| **Phase 3** | 索引 + blob：IDB 文件庫、lazy hydration、快照索引、`/blobs` API、批次／續傳、**tombstone + per-article merge**、**備份／還原／匯出含 docs**、Worker + selfhost、遷移、版本閘門 | 同步只傳變更；啟動不阻塞；刪除不復活 | 5–8 天 | Phase 1 |

## 6. 驗收清單

1. 載入舊記錄 → 改一段 → 分析：仍是同一列，`analysisCount` +1，文章生詞本不變。
2. 同一篇不改重新分析：不新增記錄、`articleId` 不變、meta 不新增。
3. 貼上修改版全文：出現相似提示；選「更新」後同一列；選「另存」後兩列都在。
4. 合併兩筆完全相同的記錄：變一列；被合併的生詞本仍在詞書列表；若該生詞本有「回到文章」，連結仍可用（或已改指向 canonical id）。
5. 100 篇短文：localStorage 不含備份時 < 1.5 MB；Phase 1 快照 < 1 MB，Phase 3 快照索引 < 200 KB；自動同步不再因備份爆配額。
   - 手動備份／匯出後清空本機 → 還原 → 每篇文章可開啟；無網路也能還原。
   - 新裝置首次啟動：其他模組可用，文章清單先顯示索引，缺少的結果背景下載，不阻塞 UI。
6. 8,000 字長文章：分析結果可儲存、可同步，不出現 413。
7. 本機改一個單字、雲端沒變：同步不下載整包（Network 面板確認只打 `/version` + push）。
8. 模擬 413：顯示可清理的錯誤提示，文章內容與畫面不丟失。
9. 兩台裝置離線各新增一篇 → 同步後兩篇都在（Phase 3，per-article merge）。
10. A 刪除、B 離線後上線：B 不會把文章復活；tombstone 過期後才可清理。
11. blob 上傳失敗：索引不推進、重試成功後才可見；不出現「索引有內容沒有」。
12. 舊快照遷移：所有文章可開啟、無重複；遷移前的備份可匯出。
13. selfhost 與 Worker 行為一致（blob、配額、GC、schema 閘門）。
14. `zh-CN`／`zh-HK` 所有新增文案、錯誤、容量提示、相似提示正確。
15. 100k 文章 + 300 句 + 300 片語標註：序列化 < 800 KB，可上傳／下載。
16. LAN HTTP（無 `crypto.subtle`）：仍可建立、上傳、下載 blob（128-bit fallback）。

## 8. 風險與取捨

| 風險 | 處理 |
| --- | --- |
| v2 結果格式讓舊版前端讀不到 | 發布前確認所有裝置更新；伺服器 schema 閘門；必要時 dual-write 一個版本週期 |
| 相似度誤判導致覆蓋 | 永不自動合併；三重門檻（simhash + 字數比 + 逐句 Jaccard）；預設「另存新篇」安全選項 |
| 合併刪掉使用者的生詞本 | 合併只刪記錄與 meta，不刪生詞本；若生詞本仍存在則保留 meta 或改指向 canonical id；文案明示 |
| IndexedDB 被瀏覽器回收 | `navigator.storage.persist()`；localStorage 保留索引；必要時從 blob 重新下載 |
| Blob 遺失／上傳中斷 | 先上傳內容再推索引；重試佇列；GC 有 30 天寬限且只刪未引用 |
| 同步邏輯變複雜、難回滾 | 用 `articles.schema` + 伺服器 feature flag 控制；保留遷移前備份；必要時退回整包快照 |
| D1／自建庫容量與費用 | 單 blob 900 KB、單篇文件 800 KB、單使用者 50 MB、每日 GC；容量面板提前預警 |
| 指紋碰撞 | 64-bit 指紋命中後再比字數與頭尾字串；`docHash` 安全上下文用 SHA-256，HTTP 用 128-bit fallback |
| selfhost 與 Worker 行為漂移 | 共用同一份 API 測試案例；兩邊都實作 `/blobs`、GC、schema 閘門 |

## 9. 不在這次範圍

- 完整的版本歷史／任意版本還原（Phase 5，且預設關閉）。
- 伺服器端全文搜尋、文章分享連結。
- 詞書、問答、助手群組的增量同步改造。
- 文章內容的端到端加密或靜態加密。

## 10. 已定案

決策 1–5 已於 2026-10-18 確認；詳細推導見 `docs/decision/20261018181402724_文章同步配額與相容決策記錄.md`，評審修正見 `docs/report/20261018182830456_文章身份與同步方案評審.md`。

1. **已定案**：不保留「上一版分析結果」；只存版本 metadata。Phase 3 後提供可選開關，最多保留 1 份完整舊結果（獨立 blob）。
2. **已定案**：SimHash 距離 ≤ 6、長度比 0.7–1.4、**逐句** Jaccard ≥ 0.6；短文章另訂嚴格門檻；用 fixture 校準。

4. **已定案並修正**：篇數軟警示 400、硬上限 1,000；單篇警示 20k 字元、硬上限 100k；標註另受全域上限約束。
5. **已定案**：舊客戶端採硬性 `409 client_upgrade_required` + 7 天回滾開關。
6. Phase 3 直接做 C（索引 + blob）；不等文章數超過 100，因為備份／還原與刪除復活問題必須一起修。
