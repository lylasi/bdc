# 文章詳解單詞標記與筆記功能實施計劃

日期：2026-10-15

狀態：評審版

交付範圍：功能與工程實施計劃

2026-10-15 補充評估：[文章與筆記儲存粒度及版本策略評估](../decision/20261015140740572_文章與筆記儲存粒度及版本策略評估.md)。核對到 D1 單列容量上限後，本版第 6 節「新增學習資料持續放進單列 JSON、預計無需新資料表」的假設須修訂；建議改為按需原文版本及分項雲端同步。下文保留原評審方案供對照，相關同步設計與 10–15 日工期須重新拆解，不能直接視為修訂版承諾。

使用者已確認採用三項建議：分別顯示「已查過／已收藏」；首版提供單詞、短語和句子筆記；支援本機離線保存、跨裝置同步及備份恢復。本計劃為其餘細節提出可直接實施的預設方案，供整體評審。

建議依序完成文章身分與查詢歸屬修正、學習資料層、正文標記、筆記介面、同步備份及回歸驗收。按一名熟悉專案的開發者估算，完整版本約需 **10–15 個工程工作日**；標記可以先形成第一個交付。估算包含雙語與手機驗收，主要不確定性是舊文章 ID 修復和跨裝置衝突處理。

## 1 使用者會得到甚麼

閱讀文章時，可以看出某個詞在這一句是否查過、是否已加入本文生詞本，以及哪個位置有自己的筆記。點詞或打開句子解析後，可以直接寫筆記；下次開啟文章，標記和筆記仍在。手機與電腦使用同一同步帳戶時，可以取得這些學習記錄。

典型例子：

1. 文章第一句出現兩次 `bank`，第二句也出現一次。
2. 在第一句點開 `bank` 並成功顯示詞義，第一句的兩個 `bank` 都顯示「已查過」，第二句維持原狀。
3. 將 `bank` 加入本文生詞本，本文所有相同詞形都顯示「已收藏」。
4. 為第一句第一個 `bank` 寫下「這裏指河岸」，筆記只關聯這個位置；同句第二個 `bank` 可以有另一則筆記。
5. 清理 AI 快取或重新分析相同原文後，查閱記錄與筆記仍保留。

### 首版範圍

| 功能 | 評審版方案 |
| --- | --- |
| 已查過 | 主動打開詞義且有效結果已呈現後記錄；包括命中既有詳解／快取 |
| 已收藏 | 由本文生詞本實際成員推導，加詞／刪詞後即時更新 |
| 筆記類型 | 英文原文中的單詞、同一句內短語、整句 |
| 筆記格式 | 純文字，每則最多 5,000 個 Unicode 字元，介面顯示字數；超限提示且保留輸入 |
| 筆記數量 | 每個精確原文範圍一則主要筆記；並發建立或編輯時允許衝突副本 |
| 保存 | 輸入停止 500ms 後自動存本機草稿；完成、切換文章／筆記時立即保存 |
| 回顧 | 本文筆記列表，可搜尋引用原文與筆記內容、返回原文位置 |
| 顯示控制 | 「顯示學習標記」開關，預設開啟；隱藏不改變保存的資料 |
| 同步 | 沿用目前 Cloudflare 同步登入與排程，學習資料逐項合併 |
| 匯出 | 完整 JSON 備份及本文筆記 Markdown 匯出 |
| 刪除與恢復 | 筆記刪除可撤銷、可從已刪除列表恢復；保留同步所需刪除記錄 |

後續擴充：整篇心得、跨句／跨段劃選、富文字及圖片附件、全站筆記搜尋、跨文章生詞掌握度、AI 整理筆記。首版以本文閱讀與回顧為核心。

## 2 標記規則

### 2.1 已查過

查閱記錄的範圍是「文章 ID＋原文版本＋句子位置＋規範化詞形」。同句相同詞形共用查閱狀態，不擴散到其他句子或文章。

- 詞形統一大小寫、首尾標點及空白處理，重用現有詞彙規範化規則；`run`、`runs`、`running` 視為不同詞形。
- 只有主動開啟且有效詞義實際呈現才記錄。載入中、失敗、空結果、hover、背景預取均不記錄。
- 請求完成時若使用者已關閉浮框、改點別詞或換文章，可將解釋保存回原文章，但不新增本次「已查過」。
- 保存記錄失敗時，詞義仍可閱讀，介面提示記錄未保存並可重試，不能顯示永久保存成功。
- 清理 AI 快取、相同原文重分析、切換 UI 語言不清除查閱記錄。
- 舊 `detailed_analysis` 無法可靠區分主動查閱與批次生成，升級時保留解釋；使用者再次打開後才建立新查閱記錄。
- 首版記錄首次／最近查閱時間，不記精確查閱次數，避免多端重複計數。

### 2.2 已收藏

以目前文章詞書的規範化單詞集合判斷，本文所有相同詞形顯示收藏狀態。收藏指詞書成員，與某次出現的具體詞義分開。

同一詞加入其他文章的生詞本，不會令本篇自動顯示已收藏。從本文詞書刪除後取消收藏標記，既有查閱記錄及筆記保留。短語收藏先在選字操作／浮框顯示，正文任意短語重疊高亮留待後續擴充。

### 2.3 有筆記及視覺層次

| 狀態 | 建議正文呈現 | 補充說明 |
| --- | --- | --- |
| 尚未查閱 | 沿用目前可點詞的虛線提示 | 保持現有操作習慣 |
| 已查過 | 較低干擾的實線底線 | 浮框顯示狀態文字 |
| 已收藏 | 收藏樣式底線，浮框顯示星形標記及文字 | 同時查過時，浮框顯示兩種狀態 |
| 有筆記 | 原文範圍的細點線／旁邊小型筆記入口 | 列表可直接返回此位置 |

顏色須配合線型、圖示或文字，不作唯一識別方式。朗讀中的句子、滑鼠配對和中英聯動沿用既有背景高亮；新標記避免與之競爭。

正文標記由保存資料推導。全篇渲染、歷史載入、段落重試、同步套用後均呼叫同一個恢復入口，不能依賴點擊後臨時加上的 class。

## 3 筆記操作流程

### 3.1 入口與面板

- 單詞浮框增加「新增筆記／編輯筆記」。
- 選取同一句英文中的短語，既有選字工具列增加「寫筆記」。選區兩端須在同一英文句內；跨句、譯文選區給出明確提示。
- 句子解析增加「句子筆記」，同一整句範圍再次點擊直接開啟既有筆記。
- 文章工具列增加「本文筆記（數量）」及「顯示學習標記」。
- 桌面使用獨立右側筆記面板；與 AI 助手切換顯示，兩邊內容保留。
- 手機使用可展開的底部面板，輸入時可佔滿可視高度，確保鍵盤不遮住內容及完成按鈕。

筆記使用獨立 DOM 容器。現有句子解析會清空共用 Modal，不能把尚未保存的編輯器放在同一容器。從句卡進入筆記時，先保存選區／句子資訊，再切換到筆記面板。

筆記入口須在詞義／句子分析載入中、失敗及沒有 AI 設定時仍可操作。來源快照的原文閱讀也提供相同入口；寫筆記不依賴 AI 回覆成功，也不因此記作已查過。

同範圍按 `sourceId + start + end` 找既有筆記，kind 不參與唯一性：點詞與選取同一詞、句卡與選取整句都開啟同一則。不同範圍的單詞、短語與句子筆記可重疊；相交位置的入口列出相關筆記供選擇。跨裝置各自建立的同範圍筆記按衝突規則保留，不能直接去掉其中一份。

### 3.2 編輯與保存

編輯器包含引用原文、純文字輸入、字數、本機保存狀態、同步狀態，以及「完成」「刪除」操作。第一個非空內容才建立筆記；將既有筆記改成空白時提示填寫或使用刪除，不把空白默認當作刪除。

1. 在入口觸發時快照文章、原文版本及範圍，之後不依賴仍存在的 `window.getSelection()`。
2. 輸入後立即顯示「儲存中」，停止 500ms 後寫入持久草稿。
3. 等資料庫交易完成才顯示「已儲存在本機」。
4. 完成、切換筆記、切換文章及切換助手面板時，立即保存最後輸入並封存版本。
5. 保存失敗時保留編輯器文字，提供重試及複製／下載草稿。會丟失未保存輸入的切換須先處理失敗。
6. 頁面重新開啟時恢復未完成草稿；多分頁草稿按編輯者識別分開保存。

關閉頁面、背景切換會嘗試提前保存，但瀏覽器崩潰或突然斷電可能丟失最後尚未完成寫入的輸入。500ms 是草稿保存間隔，不是零資料損失保證。

### 3.3 列表與重新定位

「本文筆記」按原文順序排列，可切換最近更新、搜尋引用／筆記、篩選待定位／衝突／已刪除。每項顯示引用、筆記摘要及狀態；點選「返回原文」後捲動並短暫提示目標範圍。

原文修改後，筆記保留在原來的版本。引用文字及前後文能在新版唯一匹配時，顯示建議位置，由使用者確認後建立重新連結的修訂；無法唯一匹配就顯示「原文位置待確認」。使用者也可在新版重新選取範圍後連結，舊來源及舊修訂仍保留。查閱記錄按原文版本保存，不自動搬到新版。

## 4 必須先修正的文章基礎

以下為目前程式碼已發現的問題，應與新功能一起處理，避免標記或筆記落到錯誤文章。

| 問題 | 目前位置 | 處理方案 |
| --- | --- | --- |
| 從歷史開啟文章未恢復目前文章／詞書 ID | `features/article/article.js:2095` | 由統一入口同時恢復文章、詞書、來源及版本；無綁定時清除舊上下文 |
| 非 URL 文章重分析可能產生新 ID | `article.js:1769`、`modules/storage.js:367` | 重分析傳回原 ID；清空或導入另一篇文章才建立新上下文 |
| 查詞完成後才讀目前文章，存在串文風險 | `article.js:3069` | 請求開始固定文章／版本／句子；回覆檢查 UI 請求識別，資料寫回發起時的文章 |
| 整篇重分析重建 result，可能抹掉詞句詳解 | `article.js:1882`、`storage.js:595` | 僅在原文版本與語境相容時合併可重用詳解；學習資料獨立保存 |
| 詞元素只有詞形，缺乏精確位置 | `article.js:4207` | 由統一原文文字映射產生範圍資訊；支持同句重複詞的獨立筆記 |
| 多個渲染出口替換詞句 DOM | 歷史載入、段落更新與重試 | 統一重掛標記及筆記入口，不複製多套狀態邏輯 |

正文須保存其已渲染的文章／來源版本上下文。修改上方文字框但尚未重新分析時，點擊舊正文仍使用舊正文的來源版本；重新分析或載入完成後才切換正文上下文。查閱、收藏及筆記均不能直接以當時文字框內容推斷歸屬。

處理 ID 時遵守以下規則：同篇重分析沿用 ID；同一已知 URL 內容更新沿用 ID 並增加原文版本；不同來源即使全文相同也不盲目合併。舊文章缺 ID 時分配一次穩定 ID 並落盤。舊 metadata／詞書如存在多個候選，只在關聯唯一時修復，保留不能確定的記錄。

## 5 資料架構

### 5.1 儲存位置

新增獨立 IndexedDB **`bdc-study`** 保存學習資料，與可清除的 **`bdc-cache`** 分開。現有文章、詞書等仍經既有 storage 入口存取；新資料透過集中封裝的非同步 API 存取。

採用獨立資料庫的原因是：原文版本、筆記修訂及草稿會持續增長；交易可讓來源與筆記一起寫入，也能避免多分頁整份 localStorage 互相覆蓋。IndexedDB 不可用時，保留輸入並顯示保存失敗，提供匯出；不默默降級成僅存在記憶體卻顯示已保存。

建議 object stores：

| Store | 主鍵／主要內容 | 用途 |
| --- | --- | --- |
| `sources` | `sourceId = articleId + contentVersion`；精確原文、標題、來源、雜湊、規範化英文純文字、mapping version 及句界 | 即使分析歷史被覆蓋，仍能閱讀筆記依附的原文並還原範圍 |
| `lookups` | 文章／版本／句子位置／詞形；首次與最近查閱時間 | 持久查閱標記 |
| `notes` | noteId、文章歸屬及目前版本索引 | 筆記查詢入口；目前版本索引可重建 |
| `revisions` | revisionId、noteId、父版本、文字、錨點、刪除狀態 | 逐筆合併、衝突、刪除與恢復 |
| `drafts` | noteId＋writerId；seq、文字、錨點、baseHeads | 本機持久草稿，獨立於雲端確認狀態 |
| `meta` | schema、遷移記錄及編輯者已封存游標 | 版本相容及原子封存 |

目前版本 heads 是尚未被任何後代取代的修訂。通常只有一個；多個並存代表需要處理的衝突。它由父子關係計算，不能以裝置時間決定。

### 5.2 原文版本及範圍

`contentVersion` 由原文內容生成穩定雜湊；統一 CRLF／LF 後保留其餘內容，版本不包含譯文、AI 模型或介面語言。重新分析相同原文不增加版本。

錨點保存以下資訊：

```js
{
    version: 1,
    sourceId: 'articleId + contentVersion',
    kind: 'word | phrase | sentence',
    sentenceStart: 120,
    start: 136,
    end: 140,
    quote: 'bank',
    prefix: '前方最多 32 字元的原文',
    suffix: '後方最多 32 字元的原文'
}
```

範圍採 `[start, end)`，偏移以 JavaScript／DOM 一致的 UTF-16 單位計算。錨點範例為欄位示意；實際 prefix／suffix 保存英文原文。

正文位置基於同一套英文純文字映射，處理 Markdown 標題、清單、強調及換行，排除中文譯文、按鈕與裝飾內容。儲存與渲染使用相同 mapping version；精確偏移必須再次核對 quote，避免渲染器調整後誤貼位置。

首版固定映射及分句規則，來源快照保存計算後的英文純文字與句界，正文依該結果渲染。不能讓各瀏覽器的 `Intl.Segmenter` 與後備規則分別決定持久鍵；同一原文須產生一致的句界和偏移。未來調整映射版本時保留舊版讀取能力，不能覆寫既有來源的定位基準。

首次查閱／寫筆記時保存對應原文版本；每版本只存一份，筆記用 sourceId 引用。建立記錄與原文保存須在同一交易完成。

### 5.3 筆記版本與持久草稿

每筆修訂有全域唯一 revisionId、noteId、`parentRevisionIds`、文字、錨點、刪除狀態和時間。父版本可以有多個，供解決衝突時合併分支。首版保留修訂及祖先關係，不自動清理刪除記錄。

500ms 保存的是可合併的持久草稿；完成操作或建立同步／備份快照前才封存不可變修訂，避免每次按鍵都增加完整版本。僅在文字、錨點、刪除狀態及因果關係都沒有改變時略過重複修訂。刪除、恢復及解決衝突仍須建立修訂；即使選擇保留其中一份原有文字，也要用新修訂引用全部已處理 heads。

必須遵守的交易規則：

- 每個分頁使用獨立 writerId；草稿 key 為 noteId＋writerId，seq 單調增加，交易內拒絕過期寫入。
- 草稿保存及封存都以 `transaction.oncomplete` 為成功點。
- 封存以單一交易完成：讀目前草稿、建立修訂、更新索引、記錄已封存 seq／revisionId，再消費該 seq。
- 封存期間繼續輸入的較新 seq 必須保留，並接續該 writer 剛封存的修訂；不能因 UI 尚未收到通知而接錯父版本。
- baseHeads 代表編輯開始時看過的版本。遠端同步不會默默把新分支算作已讀，否則會錯誤消除衝突。
- 恢復草稿採交易取得接管權，避免兩分頁同時自動提交同一草稿。
- 雜湊等非資料庫非同步工作在開啟交易前完成，避免交易等待外部 Promise 而提前結束。

## 6 同步與衝突

### 6.1 同步方式

快照新增 `payload.articleStudy`，包含獨立 `schemaVersion`、來源版本、查閱記錄、筆記及修訂。建立同步／備份快照前以交易封存所有分頁已持久的 drafts，再讀取一致快照；保留每個 writer 的封存游標，較新 seq 接續其封存修訂。writer 游標等本機控制資料不送雲端。

```mermaid
flowchart LR
    A[點詞或寫筆記] --> B[本機 bdc-study 交易]
    B --> C[更新正文與本機保存狀態]
    B --> D[既有資料變更事件]
    D --> E[封存草稿及建立快照]
    E --> F[拉取遠端並逐項合併]
    F --> G[帶版本條件推送]
    G --> H[與最新本機資料再次合併]
    H --> C
```

目前以通行碼登入後自動同步。沿用停止修改約 6 秒及兩次同步至少間隔 20 秒的排程；本次新增恢復連線事件的重試處理，離線時先保存在本機，連線恢復後按既有排程重試。手動同步入口仍可使用。筆記面板顯示「已儲存在本機／待同步／同步中／已同步／同步失敗」，雲端未成功確認前不顯示已同步。

同步狀態按本次雲端確認的修訂集合及查閱記錄版本判斷。等待推送期間產生的新修訂、較新查閱時間或草稿仍顯示待同步，不能因上一份快照成功而一律標為已同步。

### 6.2 合併規則

| 情境 | 處理 |
| --- | --- |
| 同一來源版本 | 按 sourceId 合併，校驗原文雜湊；同 ID 不同內容視為資料異常，保留本機並報錯 |
| 同一詞句兩端查閱 | 查閱集合聯集；首次時間取較早，最近時間取較晚；時間只作顯示 |
| 兩端修改不同筆記 | 各自保留並合併 |
| 同一筆記連續修改 | 根據完整祖先關係，使用後代作目前版本 |
| 同一筆記兩端離線修改 | 非祖先版本並存，提示「發現不同版本，已保留 {count} 份筆記」 |
| 同位置兩端各建立新筆記 | 按範圍顯示為可合併的多份筆記，不按位置鍵直接覆蓋 |
| 刪除後收到舊版本 | 刪除修訂支配其祖先，不復活 |
| 一端刪除、一端同時修改 | 保留修改分支及刪除分支，交由使用者選擇 |
| 使用者解決衝突 | 可選一份或合併文字，產生引用所有已處理 heads 的新修訂 |
| 同步等待時繼續輸入 | 套用前再讀本機最新資料，交易合併；各 writer 草稿保留 |

合併函式必須滿足重複套用不增加副本，以及不同同步順序最終得到相同結果。版本分歧以因果關係判斷，不依賴手機與電腦的時鐘一致。

完整版本鏈及原文快照會增加容量；首版先保留資料並測量容量與快照大小，容量失敗明確提示。歷史壓縮與永久抹除需要另外設計，不能直接裁掉祖先鏈或刪除標記。

### 6.3 相容與後端保護

- `buildLocalSnapshot`、合併、套用、還原、空本機判斷及匯入識別名單都加入 articleStudy。
- 舊備份缺少 articleStudy 表示該版沒有此功能，保留目前學習資料。
- 此版舊客戶端的 `lwwMerge` 會從遠端 payload 保留未知頂層欄位，需以相容案例驗證正常同步。
- 建議 Cloudflare POST `/snapshot` 加入小型保護：在同一樂觀鎖版本條件下，請求缺少 articleStudy 時保留服務端既有資料區；傳入無效／不支援的 schema 時拒絕降級改寫。
- 後端仍使用既有 JSON payload，預計無需新資料表。改動位置是 `cloudflare-worker/src/worker.js`；發布順序為保護邏輯先上線，再更新前端。
- Supabase adapter 仍存在，應維持共用快照契約及空本機判斷相容；本次跨裝置主驗收以目前使用的 Cloudflare 為準。

## 7 文章與筆記的生命週期

| 操作 | 結果 |

| 相同原文重新分析 | 保留文章 ID、原文版本、查閱記錄及筆記 |
| 編輯目前文章原文 | 保留文章 ID，建立新原文版本；舊筆記保留，提供唯一匹配或手動重新連結 |

| 刪除詞書／移除單詞 | 更新收藏狀態，查閱及筆記保留 |

既有「已收藏」仍由詞書資料導出。詞書目前採整組同步，這次不將其改為逐詞衝突合併；收藏顯示會如實反映同步後詞書。筆記及查閱記錄則依上述獨立策略保存。

## 8 備份與匯出

### 完整 JSON

將 articleStudy 納入現有完整備份，並提供學習資料專用下載。內容含原文版本、筆記修訂、查閱記錄及 schema。建立備份前立即保存呼叫分頁的最新輸入，再封存所有分頁已持久的草稿並讀取一致快照。其他分頁仍在 500ms 等待期間、尚未完成寫入的輸入不保證包含；備份須涵蓋當時已顯示儲存成功的資料。

匯入先驗證 schema、ID、來源雜湊、引用及修訂父鏈，確認可讀後再交易合併；失敗不先清空本機資料。對超出長度限制的匯入內容提示處理，不截斷文字。舊備份中曾存在而目前已刪除的內容可供明確恢復。

既有本機快照保存在 localStorage。新增版本資料後須檢查大小並回報寫入失敗；無法存本機快照時，仍可直接下載 JSON。既有備份匯入檔案大小限制也要一併檢查，確保應用匯出的檔案能被其匯入流程接受，較大資料改用學習資料專用匯入。

### 本文筆記 Markdown

輸出文章標題、來源、引用原文、筆記內容及修改時間，按原文順序排列。Markdown 用於閱讀與分享，完整恢復使用 JSON。備份不包含私有 API 設定；筆記始終作純文字安全呈現。

清除整個網站資料會清除本機資料庫和本機快照；可下載備份或已完成同步的雲端副本負責跨清除恢復。

## 13 發布與主要風險

1. 升級前先建立可下載的完整備份；ID 遷移採可重入流程，成功後記錄 schema／遷移版本。
2. 先完成 Cloudflare 缺欄位保留保護，再發布前端學習資料 schema；兩裝置完成往返驗收後視為同步可用。
3. 標記可先交付；筆記對使用者開放跨裝置能力時，衝突、刪除與備份必須已通過驗收。
4. 如需暫停新介面，可隱藏入口並保留資料庫與遠端資料區；回退版本不得清除新資料。

主要工程風險是舊文章 ID 歧義、原文位置映射、多分頁草稿封存及修訂資料增長。計劃用穩定文章身分、原文版本快照、交易與因果版本關係逐一處理。第一階段程式調研已確認相關風險；上述功能與修正仍待實作及瀏覽器驗證。
