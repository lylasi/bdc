## 1. 現況

文章詳解頁的「歷史文章」目前由三件元件組成（`index.html:1013-1025`）：

1. `#article-history-select` 原生下拉，列出所有已分析文章；
2. `#manage-history-btn` 開啟「閱讀記錄管理」彈窗；
3. `#delete-history-btn` 刪除下拉中選中的那一筆。

資料層是 `state.analyzedArticles`：每次分析成功以 `storage.saveAnalysisResult()` 寫入（`modules/storage.js:595`），陣列順序是最舊在前，記錄本身只存 `{ article, result, articleId? }`，標題、來源、時間放在 `articleMetas`（`modules/storage.js:102`）。

也就是說：**資料足夠，問題主要在呈現與操作流程，另外藏了幾個會弄壞資料／畫面的缺陷。**

## 2. 現況問題

### 2.1 會破壞資料或畫面的缺陷（P0）

| 編號 | 問題 | 位置 | 影響 |
| --- | --- | --- | --- |
| A1 | 下拉選回空白項（「讀取歷史記錄」）會直接呼叫 `clearArticleInput()` | `article.js:2259-2266` | 誤觸即清空輸入框、分析結果與目前文章／生詞本上下文，且無確認、無法復原 |
| A2 | 刪除**任何**一筆記錄後都呼叫 `clearArticleInput()` | `article.js:2153-2158` | 刪掉無關的舊記錄，正在讀的文章也一併消失 |
| A3 | 載入歷史只設定來源列，沒有設定 `state.currentArticleId` / `state.currentWordbookId` | `article.js:2123-2151` | 之後選字「加入生詞本」會加到**上一篇**文章的生詞本（`modules/vocab.js:244-251`）；助手雖然用文字快取不受影響，但生詞本語境是錯的 |
| A4 | 重新分析已載入的歷史文章會產生新的 `articleId` | `article.js:115-137`（`buildArticleMetaInput` 不帶 `id`）、`storage.js:367-408`（非 URL 一律生成 `local:` 新 id） | 舊 `articleMeta` 與文章生詞本變成孤兒；同一篇文章在記錄裡換 id、時間被重置，同步後在別的裝置看起來像新文章（身份與版本設計見延伸計劃第 2 節） |
| A5 | 分析進行中切換歷史／清空，前景分析仍會把段落寫進容器 | `article.js:1914`、`1922-1930`、`2085-2088` | 已經換成另一篇文章，舊分析的非同步回呼仍逐段覆寫畫面，最後還可能把舊結果存回記錄；`clearArticleInput()` 的 abort 也會在稍後被寫上「已取消此次分析」，蓋掉初始提示 |
| A6 | localStorage 寫滿時 `saveAnalyzedArticles` 直接拋錯，被分析流程的大 `try` 接住 | `storage.js:492-496`、`article.js:1914`、`1922-1930` | 翻譯其實已成功，畫面卻被替換成「分析失敗！」；使用者重試只會再失敗一次 |
| A7 | 刪除與載入都用陣列索引當識別碼（`data-index`） | `article.js:2123-2158`、`2186` | 彈窗開著時若同步套用了遠端快照，索引已位移，可能刪錯筆 |

### 2.2 互動效率與可辨識性（P1）

| 編號 | 問題 | 說明 |
| --- | --- | --- |
| B1 | 排序是「最舊 → 最新」 | `saveAnalysisResult` 用 `push` 加到陣列尾端，下拉照陣列順序排；最新文章永遠在最底，記錄一多就要一路往下找 |
| B2 | 選項只有被截到 40 字的標題 | 沒有時間、來源、段落數、分析狀態；同名文章或「未命名文章」無法分辨 |
| B3 | 入口佔掉三行 | `styles.css:2809-2811`：下拉獨佔整列、兩顆按鈕各半列；桌面輸入欄只有 320–380px 寬（`styles.css:3556`），文字輸入區被壓縮 |
| B4 | 管理彈窗每刪一筆就整個重建 | `article.js:2242-2244` 刪除後再次 `openArticleHistoryManager()`：清單閃動、捲動位置回到頂端，連續清理多筆很痛苦 |
| B5 | 沒有搜尋、排序、分組、釘選、重新命名 | 只能靠肉眼在長下拉裡找 |
| B6 | 分析完成或切換語言後，下拉被重建、選中值被清空 | `article.js:263`、`1919`、`2250`；畫面明明有文章，下拉卻顯示「讀取歷史記錄」（巡檢報告 M12 已記錄同類問題） |
| B7 | 沒有「已存入閱讀記錄」回饋、容量提示與筆數上限 | 使用者不知道有沒有存、還剩多少空間；`analyzedArticles` 無上限成長，同步快照也一併變大 |
| B8 | 刪除當前文章時不會提示「這就是你正在看的這篇」 | 刪完畫面空白，只能自己意識到 |

### 2.3 期望與現實的落差

使用者打開文章頁的實際需求順序是：

1. **回到剛才那篇**（最高頻）；
2. 找一篇較舊的文章；
3. 清理不要的記錄。

現在的設計把 1 和 2 都塞進原生下拉，把 3 拆成「先選再按刪除」與「管理彈窗」兩條路，還讓 1 有機會毀掉目前內容。這才是「交互不好」的根因，而不是單純樣式問題。

## 3. 目標體驗原則

1. **一個入口**：所有歷史相關操作從同一個「閱讀記錄」入口進入，不再有「下拉＋管理＋刪除」三顆控制項。
2. **瀏覽不破壞現況**：切換、刪除、取消都不得默默清掉目前輸入；真會覆蓋時提供復原。
3. **一眼可辨識**：標題＋相對時間＋來源＋狀態，同名文章也分得出來。
4. **目前文章永遠有標示**，且與生詞本／助手上下文一致。
5. **大量記錄仍可快速找到**：搜尋、排序、日期分組。
6. **破壞性操作可逆或需確認**：單筆刪除可復原；清空全部需明確確認。

| 方案 | 內容 | 優點 | 缺點 | 結論 |

## 5. 目標互動設計（方案 B）

### 5.1 入口

- `index.html` 的 `.analysis-input` 標題列改為：左邊「輸入文章」，右邊一顆輕量按鈕 `閱讀記錄`＋數量徽章。
- 移除整個 `.history-controls`（下拉＋兩顆按鈕）。
- 在結果區來源列（`#article-source-bar`）旁新增 `#article-history-status`：
  - 已存入：`已存入閱讀記錄 · 7 分鐘前`，可點擊開啟清單；
  - 尚未存入：`尚未存入閱讀記錄`（輸入框有內容但未分析）；
  - 空白：隱藏。
- 這樣「有沒有存」與「這篇多久了」在閱讀區就看得到，不必回頭看下拉。

```
┌ 輸入文章 ──────────────────────── [🕘 閱讀記錄 12] ┐
│ ┌───────────────────────────────────────────────┐ │
│ │ 貼上或輸入文章…                                │ │
│ └───────────────────────────────────────────────┘ │
│ [分析文章] [匯入…] [清除重寫] [從文章庫選取]        │
│ 已存入閱讀記錄 · 7 分鐘前                  ← 狀態列 │
└───────────────────────────────────────────────────┘
```

### 5.2 清單彈窗

```
┌ 閱讀記錄 12                                         × ┐
│ [🔍 搜尋標題或內文        ] [最近更新 ▾]             │
│ [全部] [網頁] [文章庫] [OCR] [貼上]                  │
│ ── 今天 ─────────────────────────────────────────── │
│ ▌目前  The Future of Work                  ⋯        │
│        2 小時前 · 網頁 · 12 段 · 1,842 字            │
│ ── 昨天 ─────────────────────────────────────────── │
│        How Language Shapes Thought          ⋯        │
│        昨天 21:04 · 文章庫 · 部分失敗 2 段           │
│ ── 更早 ─────────────────────────────────────────── │
│        …                                            │
│ ─────────────────────────────────────────────────── │
│ 共 12 篇 · 約 1.8 MB               [清空全部]        │
└─────────────────────────────────────────────────────┘
```

要點：

- **搜尋**：比對「標題＋正文」，首次開啟時建立一次小寫索引（`Map<key, haystack>`），記錄變動時重算；輸入即時過濾，不需按 Enter。
- **排序**：最近更新（預設）／最近加入／標題 A→Z；以 `result.updatedAt || meta.updatedAt || meta.createdAt` 為時間來源。
- **來源篩選**：全部／網頁／文章庫／OCR／貼上，沿用 `article.source*` 文案。
- **日期分組**：今天／昨天／本週／更早（以本地時區 00:00 切）。
- **列**：標題（單行省略）＋中繼資料＋狀態；`⋯` 選單提供「重新命名／刪除」；點列任一處＝開啟。
- **目前文章**：加「目前」徽章與底色；點它只關閉彈窗，不重新載入。
- **使用者可見的狀態**：`已分析`／`部分失敗 N 段`／`未分析`（沿用 `article.analyzed` / `article.notAnalyzed`，新增 `article.historyPartial`）。

### 5.3 關鍵流程

| 操作 | 行為 |
| --- | --- |
| 開啟一筆 | 設定 `currentArticleId`／`currentWordbookId` → 填入輸入框 → 渲染分析 → 更新來源列與助手上下文 → 關閉彈窗 → 桌面聚焦結果區、手機捲到結果區 |
| 目前有未分析草稿 | **不阻擋**；切換前把草稿暫存，顯示可復原提示（「復原目前輸入」），避免像現在一樣默默丟失 |
| 單筆刪除 | 立即從清單移除（不重建整個彈窗、不跳捲動位置）→ 底部顯示 8 秒「已刪除《X》 復原」；只有刪到**目前文章**時才清空畫面，並明確提示 |
| 清空全部 | 確認彈窗，文案補充「清空後文章專屬生詞本仍會保留」；完成後清單顯示空狀態 |
| 重新命名 | 更新該筆記錄的 `title` 覆寫值並持久化；不影響文章內文與來源 |
| 分析完成 | 該筆移到「今天」最上方；狀態列更新；若清單開著則就地更新（實務上清單通常關著） |
| 分析中切換 | 先中止目前分析（帶明確原因），不讓舊回呼覆寫新畫面 |

### 5.4 鍵盤與無障礙

- 開啟後聚焦搜尋框（桌面）／第一列（手機）；`Esc` 關閉並把焦點還給入口按鈕。
- `↑`／`↓` 移動列焦點，`Enter` 開啟，`Delete` 刪除（可復原）。
- 清單使用 `role="list"` + `<button>` 列，狀態徽章有 `aria-label`；`⋯` 選單用 `aria-haspopup="menu"`。
- 全部新文案同時補 `zh-CN` / `zh-HK`，動態文字一律走 `t()`。

## 6. 資料與程式改動

### 6.1 穩定識別碼（取代索引）

```js
// 顯示與操作都用 key，實際索引在動作發生時才解析
function getHistoryRecordKey(item) {
    return item?.articleId || `t:${hashString(item?.article || '')}`;
}
```

- DOM 以 `data-key` 標記，刪除／載入時 `findIndex` 回推；避免同步快照套用後索引位移。
- `storage` 既有 API 不改；需要時在 feature 層以 key 找 index 再呼叫 `deleteAnalyzedArticleByIndex`。

### 6.2 排序只在呈現層

- `buildArticleHistoryRecords()` 回傳**依時間降冪**的新陣列，不改動 `state.analyzedArticles` 順序（同步快照與索引穩定性不受影響）。
- 時間相同時以原索引降冪為 tie-breaker。

### 6.3 時間欄位

- 分析完成寫入時補 `finalResult.updatedAt = new Date().toISOString()`（目前只有逐句／片語更新會寫）。
- 顯示優先用 `result.updatedAt`，其次 `meta.updatedAt`、`meta.createdAt`，都沒有才顯示「未記錄時間」。
- 相對時間用 `Intl.RelativeTimeFormat`（跟隨目前 locale），tooltip 顯示 `formatDateTime` 絕對時間。

### 6.4 重新分析沿用原記錄

- `analyzeArticle` 取得文章文字後，先找 `state.currentArticleId` 或完全相同的內文對應記錄；找到就把 `id` 帶進 `buildArticleMetaInput()`。
- `getOrCreateArticleWordbook` 已有「有 `id` 就沿用」的分支（`storage.js:381-388`），因此不需要改 storage。
- 這樣「重新分析」＝更新原記錄，不會製造孤兒 meta／生詞本。
- 完整的身份解析優先序（current id → 正規化 URL → 內容指紋 → 相似度詢問 → 新 id）見延伸計劃 2.1；P0 先落實前三步與更新流程。

### 6.5 容量與失敗處理

- `saveAnalyzedArticles` 失敗時單獨 `try/catch`，回傳布林值或拋出可辨識錯誤；`analyzeArticle` 不因存檔失敗而覆寫已渲染結果，改顯示 `article.historySaveFailed` 提示。
- 彈窗 footer 顯示筆數與估算容量（`JSON.stringify(state.analyzedArticles).length * 2` bytes，約略值即可）。
- 超過 3 MB 時在 footer 顯示警示色與「建議清理」提示；**不自動刪除**使用者資料。
- 筆數上限（P2 再定，建議 100）只在超過時提示，不靜默淘汰。

### 6.6 刪除與 meta

- 單筆刪除沿用 `deleteAnalyzedArticleByIndex`（會一併刪 `articleMeta`）。
- 復原時需同時還原記錄與 `articleMeta` 快照；實作時在刪除前保存 `{ item, index, meta }`。
- 清空全部維持現行語意：刪記錄與文章 meta，但**不刪文章專屬生詞本**（`clearAnalyzedArticles` 目前即如此），文案要說清楚。

### 6.7 渲染競態

- 新增 `let articleRenderToken = 0;`：
  - 載入歷史、清空、開始新分析時 `articleRenderToken += 1`；
  - 分析流程與逐段回呼在每次寫 DOM 前比對 token，不符就跳過；
  - abort 的 reason 區分 `article-switched` / `cancelled-by-clear`，catch 不再無條件寫「已取消此次分析」。

## 9. 驗收清單

1. 空白下拉情境不存在（UI 已移除）；舊資料仍能載入。
2. 新增文章分析完成 → 清單最上方出現、顯示「已存入閱讀記錄 · 剛剛」。
3. 開啟任一舊記錄 → 輸入框、結果、來源列、助手上下文一致；選字加入生詞本會進**該文章**的生詞本。
4. 重新分析已載入的文章 → 記錄數目不變、時間更新、生詞本不變。
5. 刪除非目前文章 → 目前文章與分析結果不受影響。
6. 刪除目前文章 → 畫面清空並提示；復原可還原記錄與文章 meta。
7. 連續刪除 5 筆 → 清單不閃動、捲動位置不跳、每筆一次點擊。
8. 清空全部 → 需確認；完成後為空狀態；文章生詞本仍在詞書列表。
9. 分析中切換歷史 → 舊分析停止，新文章畫面不被舊回呼覆寫。
10. 儲存空間不足（可用 DevTools 塞滿 localStorage 模擬）→ 顯示「未能存入閱讀記錄」，翻譯結果仍在。
11. 搜尋標題與內文皆可命中；排序、來源篩選、日期分組正確。
12. `zh-CN` 與 `zh-HK` 所有新文案、相對時間、aria-label 正確；`node tests/audit-i18n.mjs` 通過。
13. 手機 390px、桌面 1280px 各走一次；鍵盤操作（Tab／↑↓／Enter／Esc）可用。
14. 同步：A 機重新命名／刪除 → 同步 → B 機清單一致；B 機重新分析同一篇不會長出重複記錄。
