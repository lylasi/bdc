## 1. 需求理解

管理員在「管理用戶」面板可以：

1. 為用戶產生**登入碼**。
2. 把登入碼包成**一次性登入連結**，用戶直接開啟即登入。
3. 把同一條連結顯示成**二維碼**，用戶用手機相機掃碼即登入。
4. 不使用登入碼時，用戶可以改用**用戶名 + 密碼**登入。

本計劃把需求拆成兩層：

- **A. 登入碼 / 連結 / 二維碼**：沿用現有 `pairing_codes` 一次性配對碼，主要改前端與管理面板，後端只做少量兼容。
- **B. 用戶名 + 密碼**：新增真正的密碼憑證（PBKDF2 + 隨機 salt）、`POST /login` 與可撤銷 session。**不要**把現有 43 字元通行碼直接改名成密碼。

### 1.1 已確認決策（2026-10-18）

1. 用戶名**不區分大小寫**；顯示時保留原本大小寫。
2. 普通用戶密碼最短 **8 字元**；管理員密碼最短 **12 字元**。
3. 開啟登入連結時**自動登入**；已登入其他帳戶時先確認切換。
4. 登入碼不再固定 10 分鐘。改為：
   - 新代碼 **16 字元**（約 80 bits）。
   - 有效期可選 **10 分鐘 / 24 小時 / 7 天 / 30 天**，預設 **7 天**。
   - **仍然單次使用**；管理員可撤銷該用戶所有未使用登入碼。
   - 不提供永不過期登入碼；永久登入請用「用戶名 + 密碼」。
5. 前端沿用**現有 BDC SPA 與現有管理用戶面板**，不另做獨立管理前端。登入連結開啟的也是同一個 SPA。

## 2. 現況與限制

### 2.1 已具備的能力

- `POST /admin/users/:id/pairing-code` 已可產生 12 字元、10 分鐘有效、單次使用的配對碼，只存 SHA-256 雜湊。
- `POST /pair` 可用 `{ userId, code }` 換取 180 天 session token。
- `user_sessions` 已支援可撤銷 session；重設通行碼會撤銷 session 與未使用配對碼。
- `authenticate()` 同時接受 `users.token_hash`（43 字元通行碼）與 `user_sessions.token_hash`。

### 2.2 目前缺口

- 管理面板只顯示配對碼文字，沒有連結、沒有二維碼。
- 登入彈窗的配對表單要求用戶手動輸入「用戶代號 + 配對碼」。
- 沒有一般「用戶名 + 密碼」概念；通行碼是 43 字元隨機 token，不適合人類記憶或輸入。
- `main.js` 把 hash 當成模組路由，新增 `#login=...` 前必須先攔截，否則會被當成未知模組。
- 專案沒有 QR 產生程式庫，也沒有 bundler。

### 2.3 不能直接做的事

- **不可**把登入連結或二維碼做成含長期 token 的 URL。長期 token 一旦經聊天軟件、瀏覽器歷史或截圖洩漏，等於永久帳戶憑證。
- **不可**只把 `MIN_AI_PASSCODE_LENGTH` 由 32 降到 8 或 10 就當成密碼登入。`users.token_hash` 是無 salt 的 SHA-256，且同時是長期 Bearer token；短密碼會令資料庫洩漏後可快速離線破解，也會削弱 AI Key 與管理接口的保護。
- **不可**把密碼明文或可逆加密存入 D1，也不可寫入日誌或審計詳情。

## 3. 方案總覽

實施後提供三種登入方式，按使用者情境區分：

| 方式 | 適用情境 | 憑證 | 有效期 |
| --- | --- | --- | --- |
| 登入連結 / 二維碼 | 管理員當面或遠程派發；新裝置 | 16 字元一次性登入碼 | 可選 10 分鐘 / 24 小時 / 7 天 / 30 天，單次 |
| 手動輸入登入碼 | 用戶只收到登入碼 | 同上 | 同上 |
| 用戶名 + 密碼 | 日常登入、用戶自選密碼 | PBKDF2 密碼 → 30 天 session | 密碼長期；session 30 天 |
| 通行碼（保留） | 舊帳戶、管理員、備援 | 43 字元高強度 token | 長期，重設前有效 |

登入碼與密碼登入成功後都簽發同一種 `user_sessions` token，後續 API 流程不變。

## 4. 使用者流程

### 4.1 管理員產生登入碼 / 連結 / 二維碼

1. 管理員開啟「設定 → 工具 → 管理用戶」。
2. 在非管理員用戶列按「登入碼」。
3. 選擇有效期：10 分鐘 / 24 小時 / 7 天（預設）/ 30 天。
4. 前端呼叫 `POST /admin/users/:id/pairing-code`，body 可帶 `{ ttlSeconds }`。
5. 管理面板顯示：
   - 用戶名與備註名稱。
   - 16 字元登入碼（可用 `XXXX-XXXX-XXXX-XXXX` 分組顯示，複製時去掉連字號）。
   - 一次性登入連結（可複製）。
   - 二維碼（可掃描）。
   - 到期時間與剩餘時間提示。
   - 「複製連結」「複製登入碼」「重新產生」「撤銷未使用登入碼」。
6. 管理員把連結或二維碼交給用戶。代碼只顯示一次，關閉面板後不可再查看。

有效期較長時的產品說明：

- 登入碼仍然是**一次性邀請憑證**，不是永久密碼；有效期越長，連結在未被使用前被轉發的風險窗口越大。
- **有效期只影響「首次使用」**；成功登入後的 session 仍為 180 天。因此不需要把登入碼設為永久。
- 管理員應把連結單獨發給指定用戶，不要發到群組。
- 若需要「同一組憑證可重複登入、換裝置再用」，應使用「用戶名 + 密碼」，不要使用登入連結。

### 4.2 用戶開啟登入連結

1. 用戶在手機或電腦開啟 `https://<app>/<path>#login=<CODE>`。
2. SPA 啟動時讀取 hash，立即用 `history.replaceState` 把登入碼由網址移除。
3. 未登入：自動呼叫 `/pair`（只帶 `code`）換取 session，成功後顯示「已登入」。
4. 已登入：
   - 先顯示確認：「目前以 X 登入，開啟此連結會切換帳戶，是否繼續？」
   - 確認後才消費登入碼；取消則不消費。
5. 失敗（過期、已使用、網絡錯誤）：開啟登入彈窗的「登入碼」頁，預填代碼並顯示錯誤；管理員可重新產生。

### 4.3 用戶掃描二維碼

二維碼內容就是 4.2 的連結。用戶用系統相機或瀏覽器掃碼，開啟後流程相同；不需要在 BDC 內開啟相機權限。

> 若日後要在 App 內建掃碼器，才需要 `getUserMedia` / `BarcodeDetector`，屬另一階段。

### 4.4 用戶手動輸入登入碼

1. 登入彈窗選「使用登入碼」。
2. 只需輸入 16 字元登入碼（不需要用戶代號；後端可由 code 反查用戶）。
3. 成功後與連結登入相同。

現有「用戶代號 + 配對碼」表單保留兼容：`/pair` 同時接受 `{ code }` 與 `{ userId, code }`。

### 4.5 用戶名 + 密碼登入

1. 登入彈窗預設顯示「用戶名 + 密碼」。
2. 用戶名即現有 `user_id`（例如 `alice`），**不區分大小寫**；顯示時保留原本大小寫。
3. 密碼由管理員建立或重設，之後用戶可在設定中更改。
4. 成功後簽發 30 天 session token；本機 localStorage 流程與現有登入完全相同。
5. 忘記密碼：
   - 有恢復碼：用「用戶名 + 恢復碼」重設通行碼，密碼會被清除；之後可用新通行碼登入並設定新密碼。
   - 沒有恢復碼：由管理員重設密碼。

## 5. 技術設計：登入碼 / 連結 / 二維碼

### 5.1 連結格式

採用 fragment，不用 query：

```text
https://<app-host>/<app-path>#login=<16-char-code>
```

原因：

- fragment 不會送到伺服器，不會出現在 HTTP access log。
- fragment 不會出現在 `Referer`，降低外洩風險。
- 不需要新增後端登入頁。

`#login=` 必須在 `main.js` 的模組路由之前攔截。建議在 `features/sync/sync.js` 匯出 `handleLoginLinkFromUrl()`：

- **最早擷取**：在 `main.js` 初始化流程一開始（`setupNavigation()`、`initQA()` 之前）先讀取 `#login=` 並存入記憶體，再 `replaceState` 清除 hash。不能等到 `initSync()` 之後才讀，否則使用者在慢速初始化期間點擊導覽，hash 可能已被模組路由覆蓋。
- 首次載入：認證流程就緒後才兌換代碼。
- 同一個 SPA 已開啟時貼上連結：`hashchange` listener 先呼叫 `handleLoginLinkFromUrl()`，再決定是否做模組路由；不要依賴 `replaceState` 觸發 `hashchange`。
- 函式需可重入保護，避免同時處理兩次。

### 5.2 前端處理

`handleLoginLinkFromUrl()`：

1. 讀取 `location.hash`，匹配 `^#login=([A-Za-z0-9]{12,32})$`（兼容舊 12 字元與新 16 字元）。
2. 正規化代碼（大寫、移除空白／連字號）。
3. 立即 `history.replaceState(null, '', location.pathname + location.search)`，確保代碼不再留在可見網址與歷史記錄。
4. 若已有登入 session，先確認是否切換帳戶；取消則不消費代碼。
5. 呼叫 `auth.signInWithLoginCode(code)`。
6. 成功：顯示提示，觸發 `SIGNED_IN`；是否自動同步依第 5.6 節「本機資料政策」處理。
7. 失敗：開啟登入彈窗，切到「登入碼」頁並預填代碼，顯示「登入碼無效、已過期或已使用」。

注意：

- 代碼在 `history.replaceState` 後只存在記憶體；若重新載入頁面，代碼會消失，需重新產生。
- 若請求已到達伺服器但回應遺失，代碼可能已被消費；重試失敗時提示管理員重新產生。
- 連結消費是 `POST /pair`，一般聊天軟件的連結預覽只做 GET，不會消費代碼。

### 5.3 後端 `/pair` 兼容

`cloudflare-worker/src/device-pairing.js`：

- `userId` 改為可選。
- 若只提供 `code`：用 `code_hash` 查出 `pairing_codes.user_id`，再載入用戶。
- 若同時提供 `userId`：維持比對，但改為**不區分大小寫**（`toLowerCase()` 後比較），避免舊表單因大小寫失敗。
- 代碼長度：新代碼 16 字元；為兼容舊代碼，正規表示式接受 12–32 字元（字母表仍排除易混淆字元）。
- 其餘規則不變：單次、只存 SHA-256、管理員帳戶不可用、失敗一律 `403 pairing_invalid`。
- 回應維持 `{ token, user_id, label, role, expires_at }`。
- 消費代碼後新增 session 時，必須使用**代碼資料列的 canonical `user_id`**，並以 `credential_version` 條件式 INSERT；若管理員在這一步之前重設憑證，簽發失敗。
- 代碼消費的條件式 UPDATE 需同時檢查 `used_at IS NULL` 與 `expires_at > now`。

### 5.4 管理面板建立連結

`features/admin-users/admin-users.js` 的 `generatePairingCode()` 成功後：

```js
const base = new URL(SYNC.publicBaseUrl || window.location.href);
base.hash = '';
if (!SYNC.publicBaseUrl) base.search = '';
const loginUrl = `${base.href.replace(/#.*$/, '')}#login=${encodeURIComponent(code)}`;
```

- 新增可選設定 `SYNC.publicBaseUrl`（`ai-config.example.js`），供管理員由內網或不同網域開啟管理面板時，仍產生正確的對外連結。
- 若 `publicBaseUrl` 為空，使用目前頁面的 origin + pathname，並清除 routing query。
- 若目前頁面是 `http:` 且不是 localhost，顯示「正式環境請使用 HTTPS」提示。

### 5.5 二維碼

- 新增 `modules/qr.js`：對外提供 `renderQrSvg(container, text, options)`。
- 新增 `modules/vendor/qrcode-generator.js`：引入 MIT 授權的 `qrcode-generator`（Kazuhiko Arase），改成 ESM 並保留 `LICENSE`。
- 使用 SVG 輸出，避免 canvas 縮放模糊；建議 cell size 4–6、quiet zone 4 modules、黑白高對比。
- 管理面板在顯示二維碼的同時保留可複製連結，避免用戶裝置無法掃碼時無法登入。
- 二維碼不做長期快取；面板關閉即清除。

### 5.6 自動登入與本機資料政策

現有同步是 local-first：登入後會自動排程同步，把本機資料與雲端快照合併後上傳。若直接讓登入連結自動登入並自動同步，可能出現：

- 使用者 A 的裝置被切到 B 的帳戶，A 的本機詞書／文章／QA 被上傳到 B。
- 攻擊者把自己的登入連結發給受害者，受害者一開連結，本機資料就被上傳到攻擊者帳戶（login CSRF / 資料外洩）。

因此登入連結的自動登入**不等於授權上傳本機資料**：

1. 兌換登入碼、建立 session 後，先檢查本機資料是否為空。
2. 本機資料為空（新裝置）：可自動同步，流程與一般首次登入相同。
3. 本機資料非空：
   - 顯示確認：「此裝置已有本機資料。要合併到 {user} 的帳戶嗎？」
   - 選項：「合併並同步」／「只登入，暫不同步」／「取消並登出」。
   - 「取消並登出」要呼叫伺服器 `POST /logout` 撤銷剛建立的 session，再清除本機登入狀態；不能只清 localStorage。
   - 未確認前不得呼叫 `syncNow` 上傳。
4. 已登入其他帳戶時：
   - 先確認切換。
   - 切換前停止自動同步；不得把原帳戶的本機資料靜默合併到新帳戶。
5. 訪客資料政策：第一版以「使用者明確確認」為準；不做靜默合併。長期可考慮按帳戶隔離本機資料，但不在本次範圍。

驗收必須涵蓋：A → B 切換、訪客 → B、拒絕合併、只登入不同步，以及 AI profile 不跨帳戶泄漏。

## 6. 技術設計：用戶名 + 密碼

### 6.1 資料模型

新增 `cloudflare-worker/migrations/004_password_login.sql`，並同步更新 `schema.sql`：

```sql
CREATE TABLE IF NOT EXISTS user_passwords (
  user_id             TEXT PRIMARY KEY NOT NULL,
  password_hash       TEXT NOT NULL,
  password_salt       TEXT NOT NULL,
  password_iterations INTEGER NOT NULL CHECK (password_iterations > 0),
  password_algorithm  TEXT NOT NULL DEFAULT 'pbkdf2-sha256',
  pepper_version      INTEGER NOT NULL DEFAULT 1,
  password_updated_at TEXT NOT NULL,
  failed_attempts     INTEGER NOT NULL DEFAULT 0 CHECK (failed_attempts >= 0),
  locked_until        TEXT,
  FOREIGN KEY (user_id) REFERENCES users(user_id)
);

-- 用戶名不區分大小寫；套用前先確認沒有大小寫重複的 user_id。
CREATE UNIQUE INDEX IF NOT EXISTS idx_users_user_id_nocase
  ON users(user_id COLLATE NOCASE);

-- 憑證版本：任何通行碼／密碼／恢復碼重設都遞增，讓撤銷與簽發的競態失效。
ALTER TABLE users ADD COLUMN credential_version INTEGER NOT NULL DEFAULT 0;
ALTER TABLE user_sessions ADD COLUMN credential_version INTEGER NOT NULL DEFAULT 0;
ALTER TABLE user_sessions ADD COLUMN auth_method TEXT; -- passcode | pairing | password
```

設計理由：

- `user_passwords` 用 `CREATE TABLE IF NOT EXISTS`；`credential_version` 的 `ALTER TABLE` 與 002 一樣是**只套用一次**，重跑會因 duplicate column 失敗，這是安全的。
- 沒有 `user_passwords` 列的用戶仍可只用通行碼／登入碼，向後兼容。
- `failed_attempts` / `locked_until` 用於持久化的帳戶鎖定，不依賴 Worker isolate 記憶體。
- `credential_version` 讓「管理員重設」與「登入／配對簽發 session」即使交錯，也不會留下有效 session。
- 不再另建 `idx_user_passwords_user`；`user_id` 已是主鍵。

### 6.1.1 用戶名不區分大小寫

- 登入查詢：`SELECT ... FROM users WHERE user_id = ? COLLATE NOCASE`。
- 建立用戶：先以 `COLLATE NOCASE` 檢查重複，並依賴 `idx_users_user_id_nocase` 防止併發建立大小寫變體。
- 舊「用戶代號 + 配對碼」表單：比對時兩邊 `toLowerCase()`。
- 顯示、儲存、審計仍保留原本大小寫。
- 部署前檢查：
  ```sql
  SELECT lower(user_id) AS normalized, count(*) AS n
  FROM users
  GROUP BY lower(user_id)
  HAVING count(*) > 1;
  ```
  若有結果，先由部署者改名其中一個帳戶，再套用 migration。
- 自建 PostgreSQL 版本改用 `CREATE UNIQUE INDEX ... ON users (lower(user_id))`，查詢用 `lower(user_id) = lower($1)`。

### 6.2 密碼雜湊

新增 `cloudflare-worker/src/passwords.js`：

- 演算法：PBKDF2-HMAC-SHA256（WebCrypto `crypto.subtle.deriveBits`）。
- **Pepper**：先以 `HMAC-SHA256(PASSWORD_PEPPER_V1, password)` 得到固定長度輸入，再進行 PBKDF2。Pepper 只存在 Worker secret／selfhost 環境變數，不進 D1。
  - `user_passwords.pepper_version` 記錄版本，方便日後輪換；第一版固定 `1`。
  - 新增 `PASSWORD_PEPPER_V1` secret（`openssl rand -base64 32`），必須備份；遺失時密碼不可驗證，但可用通行碼／恢復碼／管理員重設。
- Salt：16 bytes 隨機值，Base64 儲存。
- 輸出：256 bits，Base64 儲存。
- 迭代次數：每個帳戶獨立儲存。
  - **先做平台 spike**：Codex 指出 workerd 對 PBKDF2 可能有迭代上限；本機 workerd 4.151.1 實測 600,000 次仍可執行，未觸發硬上限，但這不代表 Cloudflare 生產環境。Workers Free 的 HTTP CPU 限額是 10ms，這才是主要限制。先在 staging（與正式相同方案）實測。
  - 本機參考值（2026-10-18，Mac；僅供量級參考，不能代替 staging）：
    | 迭代次數 | Node WebCrypto | 本機 workerd 4.151.1 |
    | --- | --- | --- |
    | 10,000 | 1.4ms | 1ms |
    | 50,000 | 4.9ms | 5ms |
    | 100,000 | 9.1ms | 7ms |
    | 210,000 | 18.3ms | 14ms |
    | 600,000 | 51.3ms | 42ms |
  - **Free 建議起點：50,000 + pepper**。100,000 已接近 Free 的 10ms 總 CPU，還要留給路由、D1、JSON 等處理，風險較高。
  - **Paid 建議：100,000 + pepper**，或依 spike 結果調整。
  - 不建議低於 10,000；若必須更低，應先考慮改用登入碼或受管理認證。
  - 登入成功時若發現 `password_iterations` 低於目前預設，用新 salt 重新雜湊並更新（opportunistic rehash）；更新需以舊 hash 作 CAS 條件，避免覆蓋同時發生的重設。
- 比對：解碼為 byte array 後以固定時間 XOR 比較，不用一般字串相等。
- 長度：一般用戶 **8–128 個 Unicode code points**；管理員 **12–128 個 Unicode code points**。另設輸入 byte 上限（例如 512 bytes）。不做 Unicode 正規化、不 trim。
  - 前後端與 CLI 必須使用同一套長度定義；不能用 UTF-8 bytes 當「字元數」。
- 額外檢查（不增加最小長度，但阻擋最差情況）：
  - 拒絕常見密碼。使用可維護的小型黑名單（至少涵蓋 top 100 常見密碼），不要只硬編碼三個示例。
  - 拒絕與用戶名相同或只差大小寫的密碼。
- 管理員密碼最低 12 字元（伺服器強制），不再只是風險提示。
- 不記錄密碼、不把密碼放入 audit detail。

### 6.2.1 為什麼需要 PBKDF2？Free 方案怎麼辦？

**PBKDF2 是什麼：** 它是一種「故意很慢」的單向密碼雜湊。伺服器不存密碼明文，而是存
`PBKDF2(HMAC(pepper, password), salt, iterations)`。登入時重算一次並比對。因為每次計算都要花時間，資料庫外洩時，攻擊者不能像猜 SHA-256 那樣每秒嘗試數十億次，只能逐個密碼慢慢試。

**為什麼不能只用 SHA-256：** 8 字元人類密碼的組合有限；無 salt、快速雜湊在離線破解下很快。PBKDF2 + 隨機 salt + pepper + 限流，才是「可以接受」的密碼儲存方式。

**這不是使用者看到的複雜度：** 使用者仍然只輸入用戶名和密碼；PBKDF2 只在 Worker 內部執行。

**Workers Free 的限制：** Free 的 HTTP 請求 CPU 限額是 10ms。本機 workerd 4.151.1 量測 50k 約 5ms、100k 約 7ms，但本機 CPU 較快，且未計入 D1、路由與 JSON 成本；100,000 次 + pepper 是否能在正式 Free 的 10ms 內完成，必須在 staging 實測，不能假設。Codex 提到的 workerd 迭代上限在本機版本未觸發，但仍需以正式版本為準。

可選方案：

| 方案 | 做法 | 優點 | 缺點 |
| --- | --- | --- | --- |
| A. 升級 Workers Paid | 100,000 次 + pepper | 安全強度較好、實作簡單 | 每月約 US$5 |
| B. 留在 Free | 50,000 次 + pepper + 嚴格限流 | 不增加成本；本機量測約 5ms，較有機會符合 10ms | 離線破解抵抗力低於 100k，需明確接受風險 |
| C. 受管理認證服務 | Supabase Auth／Auth0 等 | 專業處理密碼、重設、MFA | 增加依賴、帳號與成本，架構改動大 |
| D. 不存人類密碼 | 保留 43 字元通行碼 + 登入碼／QR | 不需要 PBKDF2，安全性最高 | 使用者仍要保存長通行碼；不符合「用戶名＋密碼」需求 |

**建議：**

1. 先用 staging Worker（與正式相同方案）做 spike，量測 50,000 與 100,000 次 + pepper 的 CPU 與失敗率。
2. Free 方案：預設 **50,000 次 + pepper**；這是成本與安全的務實折衷，不需要追求 OWASP 600k。
3. 若 spike 顯示 100,000 在 Free 仍有充足餘量，可用 100,000；否則不要勉強。
4. 若願意升級 Paid：用 100,000 次 + pepper。
5. 若暫時不想承擔密碼儲存風險：先做階段 1（登入碼／QR），密碼登入延後。

### 6.3 新 API

#### `POST /login`（未登入）

Request：

```json
{ "userId": "alice", "password": "...", "deviceLabel": "iPhone" }
```

Response 200：

```json
{
  "token": "<43-char-session-token>",
  "user_id": "alice",
  "label": "Alice",
  "role": "user",
  "expires_at": "2026-11-17T..."
}
```

規則：

- 用戶名查詢使用 `WHERE user_id = ? COLLATE NOCASE`（SQLite），不區分大小寫。
- **一律使用資料庫回傳的 canonical `row.user_id`** 簽發 session、寫入審計及後續關聯；不要使用請求中的大小寫。
- 先做 IP rate limit（例如 20 次／10 分鐘），再做帳戶鎖定檢查。
- 查 `users` + `user_passwords`。
- 用戶不存在時仍執行一次 dummy PBKDF2，降低 timing 泄漏。
- 密碼錯誤：`401 login_invalid`，訊息一律「用戶名或密碼錯誤」。
- 帳戶鎖定：統一回 `401 login_invalid`，不要用特有的 429 泄漏帳戶是否存在；前端顯示「登入失敗，請稍後再試」。
- 連續失敗 10 次：以原子 SQL 設定 `locked_until = now + 15 分鐘`；成功登入時清零。鎖定期間不延長。
- 成功：以**條件式 INSERT** 建立 `user_sessions`，要求 `users.credential_version` 仍等於驗證開始時讀到的版本；若管理員在驗證期間重設憑證，簽發失敗並回 `401 login_invalid`。
- Session TTL 30 天（`PASSWORD_SESSION_TTL_MS`），`auth_method='password'`。
- 管理員帳戶同樣可登入，密碼長度門檻為 12。

#### `POST /change-password`（已登入）

Request：

```json
{ "currentPassword": "...", "newPassword": "..." }
```

規則：

- `newPassword` 長度：一般用戶 8–128、管理員 12–128 個 Unicode code points，並套用常見密碼／與用戶名相同等檢查。
- 若 `user_passwords` 已存在：
  - 請求以 session token 認證（`user.viaSession === true`）時，必須提供並驗證 `currentPassword`。
  - 請求以主通行碼認證（`user.viaSession === false`）時，可不提供 `currentPassword`；因為已持有高強度主憑證。
- 若 `user_passwords` 不存在：
  - 只允許 `viaSession === false`（用通行碼登入）設定初始密碼。
  - 配對 session 不可設定初始密碼，避免被盜 session 永久接管帳戶；前端提示改用通行碼或請管理員設定。
- 成功後：
  - 以舊 hash 作 CAS 條件更新 `user_passwords`（避免覆蓋同時發生的重設）。
  - `users.credential_version += 1`。
  - 若目前是 session 認證，把**目前 session** 的 `credential_version` 更新為新版本；刪除其他 session。
  - 若目前是通行碼認證，刪除該用戶所有 session。
- 回傳 `{ ok: true }`。

### 6.3.1 憑證變更入口與撤銷規則

Codex review 指出：現有 `/change-token` 允許任何有效 session 把主通行碼改成自選值；攻擊者取得配對 session 後，可先用 `/change-token` 取得主通行碼，再以「通行碼認證」身份設定密碼，繞過「配對 session 不可設定密碼」的限制。

因此必須同步收緊所有入口：

| 入口 | 允許的認證 | 動作 |
| --- | --- | --- |
| `/change-password` | 主通行碼；或 session + 目前密碼 | 更新密碼、遞增 credential_version、撤銷其他 session |
| `/change-token` | **只允許主通行碼**（`viaSession === false`）或有效恢復碼 | 更新主通行碼、遞增 credential_version、撤銷所有 session 與未使用登入碼 |
| `/reset-token` | 恢復碼 | 設定新通行碼、刪除密碼、遞增 credential_version、撤銷所有 session 與未使用登入碼 |
| 管理員 `reset-passcode` | 管理員 session | 同上，並清除密碼 |
| 管理員 `reset-password` | 管理員 session | 更新密碼、遞增 credential_version、撤銷所有 session 與未使用登入碼 |
| 配對 session | 登入碼 | 只能一般 API；**不可**輪換主通行碼或設定初始密碼 |

若产品希望配對使用者仍可自行輪換通行碼，必須要求輸入目前通行碼或恢復碼；不能只憑 session。

#### `/me` 擴充

回傳增加：

- `has_password` boolean
- `via_session` boolean（目前 bearer 是 session token 還是主通行碼）
- `auth_method`：`passcode` / `pairing` / `password` / `legacy_session`
- `expires_at`（session 認證時）

前端據此決定「更改密碼」表單是否顯示目前密碼欄位；不要用「使用者從哪個表單登入」推斷。舊後端未回傳欄位時視為未知，不要當成未設密碼。

### 6.4 管理員 API

`cloudflare-worker/src/admin-users.js`：

1. `GET /admin/users`
   - 每列增加 `hasPassword`（只回 boolean，不回雜湊）。

2. `POST /admin/users`
   - 建立用戶時同時產生 12 字元初始密碼，寫入 `user_passwords`（PBKDF2 + pepper）。
   - 回應增加 `password` 欄位；這是**只顯示一次的初始密碼**，不是一次性使用。
   - 保留現有 `passcode`、`recoveryCode`。
   - 建立操作與 audit 同一批次；若密碼寫入失敗，整個建立失敗。

3. `POST /admin/users/:id/reset-password`
   - 產生新 12 字元初始密碼，或接受 `{ password }` 自訂密碼（依政策驗證）。
   - 更新 `user_passwords`，清除失敗次數與鎖定。
   - `users.credential_version += 1`，撤銷該用戶所有 `user_sessions` 與未使用 `pairing_codes`。
   - 回傳 `{ user, password }`，只顯示一次。
   - 管理員帳戶仍由部署者維護，端點拒絕 `role=admin`（與現有 reset-passcode 一致）。

4. `POST /admin/users/:id/reset-passcode`（既有）
   - 追加刪除該用戶 `user_passwords` 列。
   - `users.credential_version += 1`，撤銷 session 與未使用登入碼。
   - 前端提示「密碼已清除」。

5. `POST /admin/users/:id/pairing-code`（既有）
   - 接受可選 `{ ttlSeconds }`；只允許 600 / 86400 / 604800 / 2592000，預設 604800（7 天）。
   - **空 body 必須視為預設值**：舊前端呼叫此端點時不帶 body，不能因 `readJsonBody()` 對空 body 拋錯而回 400。
   - 產生 16 字元代碼；回應 `{ userId, code, expiresAt }`。
   - 前端負責組連結與二維碼。
   - 仍禁止管理員帳戶。

6. `DELETE /admin/users/:id/pairing-codes`（新增）
   - 刪除該用戶所有未使用登入碼，回 `{ revoked: n }`。
   - 用於連結外洩或派發錯誤時的補救。
   - 寫入 audit log（不含代碼）。

7. `POST /admin/users/:id/revoke-sessions`（新增）
   - 刪除該用戶所有 `user_sessions`；可選 `{ keepCurrent: true }`。
   - 用於登入碼已被兌換、裝置遺失或帳戶外洩。
   - 與「撤銷未使用登入碼」分開，管理面板需明確區分「撤銷連結」與「登出所有裝置」。

8. `POST /logout`（新增，已登入）
   - 刪除目前 bearer 對應的 session；若 bearer 是主通行碼，則不做事。
   - 現有前端 `signOut()` 只清 localStorage，伺服器端 session 仍有效；新增此端點可真正登出。

### 6.4.1 簽發與撤銷的競態

- 所有 session 簽發（`/pair`、`/login`）使用條件式 INSERT，要求 `users.credential_version` 等於驗證開始時的版本。
- 所有憑證重設先遞增 `credential_version`，再刪除 session／代碼；即使簽發請求在刪除後才插入，版本不符也會被 `authenticate()` 拒絕。
- `authenticate()` 的 session 查詢必須同時比對 `s.credential_version = u.credential_version`。
- 舊 session（migration 前建立）沒有版本欄位，`ALTER TABLE` 預設 0；`users.credential_version` 也預設 0，因此舊 session 仍有效，直到下一次重設。
- 單獨把多條 SQL 放入 D1 batch 不足以保證原子性；條件式 INSERT 或憑證版本是必要條件。

### 6.4.2 登入碼產生與有效期

- `randomPairingCode()` 改為 16 字元；字母表維持 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`。
- `PAIRING_CODE_TTL_MS` 改為預設 7 天；新增 `ALLOWED_PAIRING_TTLS`。
- `pairing_codes.expires_at` 已有欄位，不需要 migration。
- 舊 12 字元代碼仍可兌換；`normalizePairingCode()` 與查詢邏輯不依賴長度。
- 建議在 `pairing-code` handler 順便清理已過期且未使用的舊代碼，避免表無限增長；保留最近 30 天作審計即可。

### 6.5 恢復碼流程

`POST /reset-token` 追加：

- 刪除該用戶 `user_passwords` 列（密碼失效）。
- `users.credential_version += 1`。
- 保留現有撤銷 `user_sessions` 與未使用 `pairing_codes`。
- 可選：接受 `new_password`，在同一請求中設定新密碼；第一版可先不做，讓用戶用新通行碼登入後在設定中補設。

### 6.6 Session 與認證來源

- 登入碼／配對：維持 180 天（不變），`auth_method='pairing'`。
- 用戶名 + 密碼：30 天（`PASSWORD_SESSION_TTL_MS`），`auth_method='password'`。
- 主通行碼登入不建立 session；`/me` 以 `via_session=false` 表示。
- `authenticate()` 需回傳 `authMethod`、`expiresAt`、`credentialVersion`；session 查詢同時比對 `s.credential_version = u.credential_version`。
- 重設密碼、重設通行碼、恢復碼重設都會遞增 `credential_version` 並撤銷 session。
- 舊 session 的 `auth_method` 為 NULL，視為 `legacy_session`；第一版保留有效，不強制登出。

## 8. 安全設計

1. **登入碼**
   - 新代碼 16 字元、32 字元字母表、約 80 bits，排除易混淆字元；舊 12 字元代碼仍可兌換。
   - 可選 10 分鐘 / 24 小時 / 7 天 / 30 天 TTL，單次使用、只存 SHA-256。
   - `/pair` 維持 IP rate limit；所有失敗回同一個 `pairing_invalid`。
   - 管理員帳戶不可產生登入碼。
   - 連結用 fragment，不進 server log / Referer；讀取後立即 `replaceState`。
   - 不在前端 localStorage 保存登入碼或登入連結。

2. **密碼**
   - PBKDF2-HMAC-SHA256 + 16-byte salt + pepper + 每帳戶迭代次數。
   - 固定時間比較。
   - **跨 isolate 限流**：現有 `http.js` 的 `Map` 只在單一 isolate 內有效；正式環境需用 Cloudflare Rate Limiting 或 D1 計數器。`/login`、`/change-password`、`/pair` 都要限流。
   - D1 帳戶失敗計數／短期鎖定使用原子 SQL；鎖定期間不延長，成功登入清零。
   - 用戶不存在也執行 dummy hash；錯誤訊息不區分「用戶不存在」與「密碼錯誤」。
   - 密碼不寫入日誌、審計、localStorage 或 URL。
   - 普通用戶最低 8 字元；管理員最低 12 字元（伺服器強制）；管理員登入碼維持禁止。
   - **管理員 12 字元仍低於原本 43 字元通行碼**：43 字元 session 只代表 token 隨機度，不代表登入憑證強度。階段 2 建議加至少一個服務端控制：
     - 管理員敏感操作（建立／重設用戶、發布 AI catalog）要求 15 分鐘內重新驗證；或
     - 管理員只能以主通行碼執行管理操作。
     預設建議採用「15 分鐘內重新驗證」，對日常使用影響較小。

3. **Session**
   - 沿用 43 字元隨機 token、只存 SHA-256。
   - 密碼登入 session 30 天；登入碼 session 180 天。
   - `user_sessions` 記錄 `auth_method`、`credential_version`。
   - `authenticate()` 必須比對 `s.credential_version = u.credential_version`。
   - 重設密碼／通行碼／恢復碼會遞增 `credential_version` 並撤銷 session。
   - `change-password` 撤銷其他 session，保留目前 session 並更新其版本。
   - 新增伺服器端 `POST /logout` 與管理員 `revoke-sessions`；只清 localStorage 不等於撤銷 token。

4. **兼容**
   - 舊通行碼與舊配對碼繼續有效。
   - 新密碼表沒有資料的用戶不受影響；管理員可逐步為用戶設定密碼。
   - 不降低 `MIN_AI_PASSCODE_LENGTH`；AI／管理接口仍要求 bearer token 長度 ≥ 32（session token 為 43 字元，符合）。

## 10. 遷移與部署順序

0. **平台 spike（階段 2 開始前）**：
   - 在目標 Worker 方案實測 PBKDF2 50,000（Free）與 100,000（Paid）次 + pepper 的登入／rehash CPU。
   - 確認 workerd 迭代上限與 Free／Paid CPU 限額；若不可行，先決定升級方案或替代認證方案，不要先產生正式密碼資料。
   - 檢查現有 `user_id` 大小寫重複：
     ```sql
     SELECT lower(user_id), count(*) FROM users GROUP BY lower(user_id) HAVING count(*) > 1;
     ```
     有結果即停止部署，先處理帳戶改名（不可直接合併）。
1. 備份 D1：
   ```bash
   cd cloudflare-worker
   npx wrangler d1 export bdc-sync --remote --output backup-$(date +%Y%m%d).sql
   ```
2. 設定 pepper secret（保存到密碼管理器）：
   ```bash
   npx wrangler secret put PASSWORD_PEPPER_V1
   # 值用 openssl rand -base64 32 產生
   ```
3. 套用 migration：
   ```bash
   npx wrangler d1 execute bdc-sync --remote --file ./migrations/004_password_login.sql
   ```
4. 部署 Worker。
5. 部署前端（含 QR vendor 與新 locales）。
6. 驗證：
   - 管理員為測試用戶產生登入碼 → 開連結 → 成功登入。
   - 同一連結第二次開啟 → 失敗。
   - 掃二維碼 → 成功登入。
   - 用戶名 + 密碼登入 → 成功；錯誤密碼 → 失敗。
   - 重設密碼 → 舊密碼失效、舊 session 失效。
   - 重設通行碼 → 密碼被清除。
   - 管理員 revoke-sessions → 該用戶所有裝置失效。
7. 回滾：前端可先回舊版；migration 不回滾（新增欄位向後兼容）。若 pepper 遺失，密碼全部失效，需用通行碼／恢復碼／管理員重設。

## 12. 決策記錄

| # | 問題 | 決定 |
| --- | --- | --- |
| 1 | 「用戶名」是否就是現有 `user_id`？ | 是。`user_id` 同時作為登入用戶名，不新增欄位；**不區分大小寫**。 |
| 2 | 一般用戶與管理員密碼最短長度？ | 普通用戶 8 字元；管理員 12 字元（伺服器強制）。 |

| 5 | 登入碼 TTL？ | 可選 10 分鐘 / 24 小時 / 7 天 / 30 天，預設 7 天；仍然單次使用，可撤銷。 |

## 15. 風險與緩解

| 風險 | 緩解 |
| --- | --- |
| 登入連結被聊天軟件預覽消費 | 消費需要 JS 執行 `POST /pair`；一般預覽只 GET。若仍發生，改為一鍵確認頁。 |
| 連結經截圖／轉發外洩 | 可選 TTL（預設 7 天，最長 30 天）、單次使用、管理員可撤銷未使用代碼；不把長期 token 放進 URL。 |
| PBKDF2 在 Worker CPU 超時或被 workerd 上限拒絕 | 階段 2 前先 spike；Free 以 50k + pepper 為起點，Paid 用 100k；不可行時在升級方案／受管理認證／更低迭代之間明確決策，不靜默降級。 |
| 登入連結造成本機資料外洩（login CSRF） | 自動登入不等於授權上傳；本機資料非空時必須明確確認合併（第 5.6 節）。 |
| 撤銷與簽發競態 | `credential_version` + 條件式 session 簽發 + `authenticate()` 版本比對（第 6.4.2 節）。 |
| 帳戶鎖定被用作 DoS | 只鎖 15 分鐘、跨 isolate 限流、成功登入清零；不因鎖定泄漏帳戶是否存在。 |
| 8 字元普通用戶密碼強度不足 | 以 PBKDF2 + pepper、跨 isolate 限流、失敗鎖定、常見密碼黑名單緩解；管理員維持 12 字元；日後可調高常數而不改資料格式。 |
| 現有用戶名有大小寫重複 | migration 前先執行檢查 SQL；有重複則由部署者改名，否則 unique index 會阻止套用。 |
| 用戶忘記密碼 | 管理員重設；有恢復碼者可自行重設通行碼後補設密碼。 |
| 舊帳戶不願使用密碼 | 保留通行碼與登入碼；密碼是可選增強，不強制遷移。 |
| 管理員用內網位址產生連結 | 新增 `SYNC.publicBaseUrl`，文件說明要填對外網址。 |
| QR 程式庫供應鏈風險 | 只引入 MIT、無網絡依賴的 QR 編碼器，保留 LICENSE，不引入遠程 QR 服務。 |

## 16. 驗收標準

1. 管理員可為非管理員用戶產生 16 字元登入碼，選擇 10 分鐘／24 小時／7 天／30 天有效期，並在面板看到可複製連結與可掃描二維碼。
2. 用戶開啟連結或掃碼後，無需輸入任何憑證即可登入；URL 不再保留登入碼。
3. 同一登入碼只能成功使用一次；過期、已用、無效均顯示一致錯誤；管理員可撤銷未使用代碼。
4. 本機資料非空時，登入連結不會靜默上傳；使用者必須明確選擇合併或只登入。
5. 管理員可為用戶建立／重設密碼（普通用戶 ≥8、管理員 ≥12）；用戶可用「用戶名 + 密碼」登入，用戶名不區分大小寫。
6. 用戶可在已登入狀態更改密碼；錯誤的目前密碼被拒絕；配對 session 不可直接輪換主通行碼。
7. 重設密碼／通行碼後，相關舊 session 與舊憑證按設計失效；`credential_version` 能攔截撤銷／簽發競態。
8. 管理員可撤銷未使用登入碼與登出所有裝置；舊 session 立即失效。
9. 舊通行碼登入、舊 12 字元配對碼登入、舊 session 仍可運作。

12. Worker 測試、真實 SQLite／D1 測試、管理面板 Playwright、登入連結 Playwright 全部通過。

### 17.4 決策狀態

1. **管理員密碼長度**：已決定提升至 **12 字元**（2026-10-18）。敏感操作建議採用「15 分鐘內重新驗證」，待實作前最終確認。
2. **PBKDF2 平台 spike**：仍待 staging 量測。使用者目前是 Workers Free；本機 workerd 4.151.1 量測 50k 約 5ms、100k 約 7ms（未計 D1／路由成本），100k 已接近 Free 10ms 總 CPU，建議 Free 以 **50k + pepper** 為起點。若 staging 不可行，再在「升級 Paid／受管理認證／更低迭代」之間決策。
3. **大小寫重複帳戶**：已確認目前沒有重複（2026-10-18）；部署時仍保留檢查 SQL 作為 gate。

## 18. 階段 1 實施結果（2026-10-18）
