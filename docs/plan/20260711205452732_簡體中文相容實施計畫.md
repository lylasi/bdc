# 簡體中文相容實施計畫

## 1. 文件目的

本計畫用於在保留現有繁體中文體驗的前提下，為 BDC 靜態 SPA 增加簡體中文相容能力。改造範圍包括介面文案、AI 提示詞、AI 回覆、語音選擇、快取、搜尋、靜態教材與同步設定。

本階段只制定實施計畫，不修改產品程式碼。

## 2. 建設目標

第一版建議支援以下語言模式：

- `zh-Hant`：繁體中文，維持現有預設體驗。
- `zh-Hans`：簡體中文，提供簡體介面與對應的 AI 回覆。
- `auto`：根據瀏覽器語言自動選擇，允許使用者手動覆蓋。

相容能力分為三個彼此獨立的維度：

1. **介面語言**：導航、按鈕、表單、提示、錯誤訊息與設定說明。
2. **AI 回覆語言**：單字解析、文章分析、OCR 後處理、QA 校對與 AI 助手回覆。
3. **內容語言**：詞書、文章、QA、OCR 原文及使用者自行輸入或匯入的資料。

切換介面語言不得自動改寫使用者原始資料。

## 3. 核心設計原則

### 3.1 語言與內容分離

介面文案應集中到語系資源，功能模組只使用翻譯鍵，不直接依賴繁體或簡體字串。建議新增：

```text
modules/i18n.js
locales/zh-Hant.js
locales/zh-Hans.js
```

兩個語系檔必須使用完全相同的鍵結構，例如：

```js
export default {
    common: {
        confirm: '確認',
        cancel: '取消'
    },
    learning: {
        analyzeWord: '解析單字'
    }
};
```

簡體版本只替換值，不改變鍵名：

```js
export default {
    common: {
        confirm: '确认',
        cancel: '取消'
    },
    learning: {
        analyzeWord: '解析单词'
    }
};
```

### 3.2 不以全頁機械轉換取代 i18n

不建議將整個 DOM 交給 OpenCC 或類似工具即時轉換，原因包括：

- 簡繁差異包含地區用詞，不只是字形轉換。
- 全頁轉換可能污染輸入框、英文教材、程式碼與使用者資料。
- 動態文案與 AI 提示詞容易遺漏或重複轉換。
- 繁簡轉換不一定完全可逆。

OpenCC 可用於大量既有教材的初稿生成或搜尋正規化，但 UI 正式文案應人工維護。

### 3.3 保留原始內容

下列資料預設保持原樣：

- 使用者輸入或匯入的文章、詞書與 QA 資料。
- OCR 原始辨識結果。
- 已儲存的 AI 對話。
- 已同步至 Supabase 的內容。
- 備份檔中的既有資料。

若使用者需要轉換內容，應提供獨立且可確認的「轉為簡體／轉為繁體」功能，並避免直接覆寫原始資料。

## 4. i18n 基礎架構

### 4.1 `modules/i18n.js` 職責

建議集中處理：

- 瀏覽器語言偵測與 locale 正規化。
- 讀取及保存使用者語言偏好。
- 提供 `t(key, params)` 翻譯函式。
- 支援參數插值與繁體回退。
- 更新 `document.documentElement.lang`。
- 發出語言變更事件。
- 在開發階段警告缺少或多餘的翻譯鍵。

語言判定建議如下：

```text
zh-CN、zh-SG、zh-Hans       → zh-Hans
zh-TW、zh-HK、zh-MO、zh-Hant → zh-Hant
其他語言                    → zh-Hant
```

第一版不必拆分 `zh-Hant-TW` 與 `zh-Hant-HK`，但資料結構應允許未來增加地區變體。

### 4.2 靜態 DOM 文案

`index.html` 可使用明確的翻譯標記：

```html
<button data-i18n="common.confirm">確認</button>
<input data-i18n-placeholder="vocabulary.searchPlaceholder">
```

語言切換時只更新已標記節點，不掃描並轉換整個 DOM。DOM 存取仍應遵守現有架構，優先透過 `modules/dom.js` 管理。

### 4.3 動態文案

下列動態內容必須改用翻譯鍵：

- Toast、訊息條、模態框及確認提示。
- 表單驗證與 API 錯誤訊息。
- Quiz、Dictation 的倒數、分數及流程狀態。
- 空狀態、載入中、同步中與離線狀態。
- OCR、QA、AI 助手與文章分析提示。
- 音訊播放與權限說明。

包含數字或名稱的句子應使用參數插值，不應拼接固定中文字串：

```js
t('quiz.score', {
    correct: 8,
    total: 10
});
```

## 5. AI 提示詞相容方案

### 5.1 分離任務規則與語言規則

不要維護兩套完整提示詞。現有繁體提示詞應拆成：

1. 語言無關的任務、格式、安全與評分規則。
2. 可依 locale 注入的輸出語言規則。
3. 與 system prompt 明確隔離的使用者內容。

建議建立共用規則：

```js
const outputLanguageRules = {
    'zh-Hant': '請一律使用繁體中文回答，採用臺灣常用詞彙。',
    'zh-Hans': '请一律使用简体中文回答，采用中国大陆常用词汇。'
};
```

提示詞組裝順序建議為：

```text
基礎 system prompt
→ 任務與輸出格式規則
→ locale 對應的語言規則
→ 使用者內容
```

### 5.2 結構化輸出保持穩定

AI 回傳 JSON 時，程式欄位應固定使用英文鍵名，只翻譯欄位值：

```json
{
  "definition": "...",
  "examples": [],
  "notes": "..."
}
```

不得因語言切換而將鍵名改成「釋義」或「释义」，以免破壞解析、快取、同步及舊資料相容性。

### 5.3 各 AI 功能的處理重點

- **Learning**：解釋、例句說明與備註跟隨 AI 回覆語言。
- **Article**：原文保持不變；摘要、分析及問答依語言設定生成。
- **OCR**：區分來源語言、介面語言及後處理輸出語言。
- **QA**：校對原文時保留原簡繁；解釋和建議依回覆語言生成。
- **Assistant**：可提供跟隨介面或跟隨使用者輸入兩種模式。

## 6. 設定與資料模型

建議將介面語言與 AI 回覆語言分開保存：

```js
{
    interfaceLanguage: 'auto',
    aiResponseLanguage: 'follow-interface'
}
```

建議值：

```text
interfaceLanguage:
- auto
- zh-Hant
- zh-Hans

aiResponseLanguage:
- follow-interface
- follow-input
- zh-Hant
- zh-Hans
```

相容規則：

- 舊使用者沒有語言欄位時回退 `zh-Hant`，避免既有體驗突然改變。
- 未登入使用者將偏好保存在 localStorage。
- 已登入使用者可將偏好同步至 Supabase，但需定義本地與遠端衝突優先級。
- 語言設定新增時需同步檢查 `modules/settings.js`、`modules/storage.js`、`modules/sync-core.js` 與 `modules/sync-supabase.js`。

## 7. 快取、搜尋與語音

### 7.1 AI 快取隔離

AI 快取鍵必須包含：

- locale 或 AI 回覆語言。
- 任務類型。
- 模型名稱。
- 提示詞版本。
- 會影響輸出的重要設定。

例如：

```text
learning:v3:model-name:zh-Hans:word
```

切換語言時不必清空全部快取；繁體與簡體結果可並存，由既有 TTL 與容量策略淘汰。

### 7.2 簡繁搜尋相容

搜尋功能應保留原始資料，同時建立可比較的正規化形式：

- 英文字母統一大小寫。
- 視需要移除不影響搜尋的空白與標點。
- 建立簡繁字形正規化索引。
- 不直接覆寫詞書或文章原文。
- 地區詞彙同義搜尋可列為第二階段能力。

### 7.3 TTS 與聲音選擇

介面語言不能直接決定所有朗讀 voice。建議依序考慮：

1. 被朗讀文字的實際語言。
2. 使用者明確選擇的 voice。
3. locale 對應的地區偏好。
4. 瀏覽器可用 voice。
5. 安全回退 voice。

中文回退建議：

```text
zh-Hant → 優先 zh-TW，必要時回退 zh-HK
zh-Hans → 優先 zh-CN，必要時回退 zh-SG
```

英文單字及文章仍使用英文 voice。

## 8. 靜態教材策略

可選方案如下：

### 方案 A：只翻譯 UI 與動態 AI 回覆

- 開發成本最低。
- 既有靜態教材仍可能顯示繁體。
- 適合第一版快速驗證。

### 方案 B：教材維護簡繁雙版本

```json
{
  "definition": {
    "zh-Hant": "繁體解釋",
    "zh-Hans": "简体解释"
  }
}
```

- 可離線使用，內容品質穩定。
- 資料量及維護成本較高。

### 方案 C：顯示時機械轉換

- 適合快速覆蓋大量舊資料。
- 地區詞彙品質有限，搜尋、匯出及同步處理較複雜。

### 建議選擇

採用混合方案：

- UI 文案人工維護雙語。
- 高頻與核心教材人工維護雙語。
- 大量舊教材可由 OpenCC 生成草稿，再人工抽查。
- 使用者資料永遠保留原樣。
- AI 動態內容直接按目標語言生成，不做二次機械轉換。

## 9. 分階段實施計畫

### 第一階段：盤點與規格

預估 1～2 個工作日。

- 搜尋 `index.html`、`main.js`、`modules/` 與 `features/` 中的硬編碼中文。
- 盤點 `modules/api.js` 及各功能模組使用的 AI 提示詞。
- 盤點 `wordlists/`、`articles/`、`qa-sets/` 的中文欄位。
- 定義語言判定、回退、同步和內容保留規則。
- 建立繁簡術語表及不應轉換的專有名詞清單。

交付物：字串清單、提示詞清單、翻譯鍵規範、術語表與資料相容清單。

### 第二階段：建立 i18n 基礎

預估 2～4 個工作日。

- 新增語系資源與 `modules/i18n.js`。
- 實作 `t()`、參數插值、繁體回退及缺鍵警告。
- 實作瀏覽器語言偵測與 localStorage 持久化。
- 更新 `<html lang>`。
- 在設定頁增加語言選項。
- 建立語言變更事件與翻譯鍵一致性檢查。

驗收：切換語言不需重新整理；舊使用者仍預設繁體；缺少翻譯不會使應用崩潰。

### 第三階段：介面文案遷移

預估 4～8 個工作日。

建議依序遷移：

1. 共用 UI、主導航與設定。
2. Vocabulary、Learning。
3. Quiz、Dictation。
4. Article、OCR。
5. QA、Sync、Assistant。
6. 錯誤訊息、空狀態與邊界流程。

每完成一個模組即進行繁簡雙模式巡檢，避免最後一次性驗證。

### 第四階段：AI 提示詞語言化

預估 3～5 個工作日。

- 抽離共用輸出語言規則。
- 將任務提示詞與語言要求分離。
- 透過 `modules/api.js` 為所有 AI 任務傳入 locale。
- 將語言及提示詞版本納入快取鍵。
- 固定結構化輸出的英文 schema。
- 建立繁簡回覆測試樣本。
- 驗證自訂提示詞不會覆蓋必要的 system 規則。

### 第五階段：教材、搜尋與輸出

預估 3～10 個工作日，視資料量調整。

- 決定需要人工雙語維護的核心教材。
- 為大量舊教材生成簡體草稿並抽查。
- 建立簡繁搜尋正規化。
- 明確定義匯入、匯出、備份及 PDF 的語言行為。
- 確保顯示語言切換不會產生同步寫入。

### 第六階段：全面驗證與發布

預估 2～4 個工作日。

- 巡檢九大功能模組的繁簡模式。
- 測試瀏覽器自動偵測、手動覆蓋與重新整理持久化。
- 測試離線、備份、還原、登入與跨裝置同步。
- 測試 TTS voice 選擇及回退。
- 抽查所有 AI 任務及快取隔離。
- 第一版先提供手動切換，再視回饋啟用自動選擇。

## 10. 驗證清單

### 10.1 翻譯完整性

- `zh-Hant` 與 `zh-Hans` 的鍵集合完全一致。
- 正式畫面不顯示原始翻譯鍵。
- 缺少簡體翻譯時安全回退繁體。
- 建立硬編碼中文掃描及必要的例外清單。

### 10.2 UI 與資料相容

- 九大模組的導航、按鈕、提示及錯誤均可切換。
- 語言切換不會重複綁定事件。
- 使用者輸入中的中文不被自動轉換。
- 舊設定缺少語言欄位時可正常啟動。
- 備份還原與同步不會改寫內容簡繁。

### 10.3 AI 與快取

- `zh-Hant` 任務回傳繁體中文。
- `zh-Hans` 任務回傳簡體中文。
- JSON 鍵名及解析格式保持一致。
- 不同語言的 AI 結果不共用同一快取項。
- OCR 原文不因介面語言而被自動轉換。
- QA 校對能區分「保留原文」與「轉換語言」。

### 10.4 手動巡檢重點

- 詞書 CRUD、匯入、匯出及搜尋。
- Learning 單字分析、例句及朗讀。
- Dictation 暫停、恢復與評分。
- Quiz 計分、倒數與離開保護。
- Article 分析、朗讀與 Assistant。
- OCR 拖放、後處理與 Markdown 預覽。
- QA 訓練、校對、進度恢復及 PDF。
- Supabase 登入、同步與本地備援。
- 語言設定若影響持久化 UI，額外驗證 `test-floating-statusbar.html`。

## 11. 優先級

### P0：簡體版本發布前必須完成

- 明確分離介面語言、AI 回覆語言與內容語言。
- 所有 AI 任務都能取得 locale。
- AI 快取鍵包含語言與提示詞版本。
- 結構化回應 schema 不隨語言變更。
- 切換語言不改寫使用者資料。
- 舊設定安全回退繁體中文。

### P1：第一版建議完成

- 共用 UI 與九大模組主要文案完成雙語。
- 提示詞統一注入語言規則。
- 支援瀏覽器偵測與使用者手動覆蓋。
- 建立翻譯鍵完整性檢查。
- 支援基本簡繁搜尋。
- 支援 TTS 地區 voice 選擇。

### P2：後續優化

- 靜態教材完整雙語。
- 中國大陸、臺灣及香港地區術語精細化。
- 增加 `zh-Hant-HK` 等地區變體。
- 建立自動化 UI 與 AI 輸出測試。
- 導入翻譯管理或內容審校流程。

## 12. 主要風險與對策

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| 只做字形轉換 | 用詞不自然且容易污染內容 | UI 人工翻譯，OpenCC 僅作輔助 |
| 維護兩套完整提示詞 | 規則逐漸不一致 | 共用任務模板，僅注入語言規則 |
| 語言切換觸發資料改寫 | 同步衝突及不可逆資料變更 | 顯示語言與原始內容完全分離 |
| AI 快取混用 | 簡體介面顯示繁體結果 | locale 納入快取鍵 |
| JSON 鍵名本地化 | 解析及舊資料相容失敗 | 程式欄位固定英文，只翻譯值 |
| 一次改造範圍過大 | 回歸問題難以定位 | 按模組遷移並保留繁體回退 |
| 簡體術語不符合習慣 | 使用者理解成本增加 | 先建立術語表並進行人工審校 |

## 13. 預估投入與里程碑

總投入預估為 15～33 個工作日，實際時間取決於硬編碼文案數量與教材翻譯範圍。

建議里程碑：

1. **M1：規格完成**——字串、提示詞、術語與資料相容規則確認。
2. **M2：i18n 可用**——設定頁可切換語言，共用 UI 完成雙語。
3. **M3：主要功能雙語**——九大功能的核心流程完成遷移。
4. **M4：AI 雙語穩定**——提示詞、快取與結構化回應完成改造。
5. **M5：發布準備完成**——教材、搜尋、同步與手動巡檢通過。

## 14. 建議結論

最穩妥的方向不是直接將整個繁體專案轉成簡體，而是建立輕量 i18n 層，分開管理介面語言、AI 回覆語言與內容語言。

第一版應優先完成 UI 雙語、提示詞語言注入、AI 快取隔離及舊資料相容；大量教材翻譯與地區術語優化可放在後續階段。這種做法能保留現有繁體使用者體驗，也能降低未來增加英文或其他語言時的改造成本。
