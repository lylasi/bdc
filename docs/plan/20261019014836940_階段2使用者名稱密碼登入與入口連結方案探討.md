# 階段 2：使用者名稱／密碼登入與入口連結方案探討

- 日期：2026-10-19
- 狀態：階段 2A 已實作並通過本機測試，待部署驗證；2B／2C 不做
- 前置：階段 1 已完成（一次性登入碼、`#login=CODE`、QR、撤銷）
- 參考：`/Users/linus/CODE/dgr` 的家庭入口與老闆帳號設計

> **2026-10-19 範圍更新**：維持 Cloudflare Workers Free；**不做家庭入口**（不新增 `groups`／`group_members`、不做 `#group=`）。階段 2 收窄為 2A 使用者名稱＋密碼，2B 個人入口 `#u=` 可選。決策見 `docs/decision/20261019015618616_階段2維持WorkersFree且不做家庭入口決策.md`。

## 1. 目標與三種入口

目前 BDC 只有一種登入方式：一次性登入碼（`#login=CODE` 自動登入）。階段 2 要加入「使用者名稱＋密碼」，並允许不同入口：

| 入口 | 範例 | 需要什麼 | 用途 |
| --- | --- | --- | --- |
| 一次性登入碼 | `#login=ABCD...` | 不需要密碼 | 小孩、臨時裝置、家長代發 |
| 個人入口連結 | `#u=alice` | 只需輸入密碼 | 常用裝置、書籤 |
| 家庭入口連結 | `#group=<entryCode>` | 選成員後輸入密碼，或改用登入碼 | 一家人共用一個入口 |
| 主站登入 | 無連結 | 使用者名稱＋密碼 | 一般登入 |

三者最後都換成同一種 `user_sessions` token（180 天），不需要三套 session 機制。

重要邊界：

- **入口連結只負責「選擇身分／預填使用者名稱」，不是登入憑證。**
- 一次性登入碼是例外：它本身就是 bearer credential，所以必須一次性、短效、可撤銷（階段 1 已符合）。
- 不要把長期有效的「記住我」token 放在 URL；URL 會進入瀏覽歷史、截圖、Referer。入口連結只放公開識別碼（username 或 group entry code）。

## 2. 階段 2A：使用者名稱＋密碼

### 2.1 資料模型

在 `users` 增加：

```sql
ALTER TABLE users ADD COLUMN username TEXT;
ALTER TABLE users ADD COLUMN username_normalized TEXT;
ALTER TABLE users ADD COLUMN password_hash TEXT;
ALTER TABLE users ADD COLUMN password_salt TEXT;
ALTER TABLE users ADD COLUMN password_iterations INTEGER;
ALTER TABLE users ADD COLUMN auth_version INTEGER NOT NULL DEFAULT 1;
ALTER TABLE users ADD COLUMN password_updated_at TEXT;
ALTER TABLE users ADD COLUMN is_active INTEGER NOT NULL DEFAULT 1;

CREATE UNIQUE INDEX idx_users_username_normalized
  ON users(username_normalized) WHERE username_normalized IS NOT NULL;
```

在 `user_sessions` 增加：

```sql
ALTER TABLE user_sessions ADD COLUMN auth_version INTEGER NOT NULL DEFAULT 1;
```

說明：

- `user_id` 仍是不可變主鍵；`username` 只作為登入識別。
- `username_normalized` 由 Worker 以 `NFKC + toLowerCase()` 產生，避免 SQLite 與 PostgreSQL 的 collation 差異。若只允許 ASCII 使用者名稱，可直接存小寫。
- `label` 繼續作為顯示名稱，可包含中文；`username` 建議只允許 ASCII，避免 Unicode 大小寫與正規化問題。
- `auth_version` 用於改密／重設後即時失效舊 session。
- `is_active` 可讓管理員停用帳號；`authenticate()` 需檢查。

### 2.2 使用者名稱規則

建議：

- 3～32 字元。
- `^[a-z0-9][a-z0-9._-]*$`（存小寫；輸入時自動轉小寫）。
- 大小寫不敏感唯一。
- 顯示名稱（`label`）另設，可中文、可空白。
- 保留字避開：`admin`、`system`、`root`、`api` 等。

若一定要支援中文使用者名稱，改用 `NFKC + toLowerCase()` 正規化並存 `username_normalized`，但需接受不同 Unicode 組合可能碰撞的風險。

### 2.3 密碼雜湊

格式：

```text
pbkdf2-sha256$<iterations>$<salt-base64url>$<hash-base64url>
```

- 每位使用者獨立隨機 salt（16 bytes）。
- Workers 使用 WebCrypto `PBKDF2`；Workers 沒有原生 scrypt／Argon2。
- Workers Paid：建議 600,000 iterations（OWASP 對 PBKDF2-HMAC-SHA256 的建議值）。
- Workers Free：見第 4 節，需要取捨。
- 密碼長度：一般使用者至少 8 字元；管理員至少 12 字元（先前決議）。上限 200。
- 不改寫密碼內容（不 trim），允許空白片語。

### 2.4 API

**`POST /login`**（免認證）

```json
{ "username": "alice", "password": "...", "deviceLabel": "iPad" }
```

成功：

```json
{
  "token": "<43-char session token>",
  "user_id": "alice",
  "label": "Alice",
  "role": "user",
  "expires_at": "2027-04-17T..."
}
```

失敗：

- `401 invalid_credentials`（不區分帳號不存在或密碼錯誤）
- `403 account_disabled`
- `429 rate_limited` + `Retry-After`

流程：

1. 正規化 username。
2. 限流檢查（見 2.6）。
3. 查 `users`；不存在時仍執行一次固定 dummy 雜湊，降低時間側信道（Free 方案可視 CPU 預算省略）。
4. 驗證 PBKDF2。
5. 檢查 `is_active`。
6. 建立 `user_sessions`（`auth_version` 寫入目前版本）。
7. 回傳 token。

**`POST /change-password`**（需登入）

```json
{ "currentPassword": "...", "newPassword": "..." }
```

流程：

1. 驗證目前密碼。
2. 更新 hash／salt／iterations／`password_updated_at`。
3. `auth_version += 1`。
4. 刪除該使用者其他 session；目前 session 更新為新 `auth_version`（讓目前裝置保持登入）。
5. 清除未使用的登入碼。

**`POST /reset-password`**（管理員）

- 管理員可為非管理員使用者產生一次性臨時密碼，或直接設定新密碼。
- 建議：管理員產生「設定密碼用的一次性登入碼」，使用者登入後強制設定新密碼；避免管理員知道使用者密碼。
- 重設後 `auth_version += 1`、刪除所有 session、刪除未使用登入碼。

**`POST /change-token`**（既有）

- 保留作 32 字元通行碼變更；若使用者已有密碼，可選擇是否停用通行碼登入。
- 若停用，將 `token_hash` 設為隨機不可用值，或新增 `passcode_login_enabled` 旗標。

**`GET /auth-capabilities`**

- 部署後回傳 `passwordLogin: true`；前端據此顯示「使用者名稱密碼」頁籤。
- 舊 Worker／selfhost 回 404 時前端自動隱藏。

### 2.5 登入 UI

登入彈窗改為兩個頁籤：

1. **使用者名稱密碼**（預設，若 capability 支援）
   - 使用者名稱、密碼、顯示／隱藏密碼。
   - 「忘記密碼」提示聯絡管理員，或使用復原碼重置通行碼。
2. **登入碼**
   - 沿用階段 1 的單一輸入框。

其他狀態：

- 已登入其他帳號時，密碼登入成功後仍需確認是否切換（與階段 1 相同）。
- 登入後若 `username` 為空，顯示「設定使用者名稱與密碼」引導（既有使用者認領）。
- 管理員使用者建立／編輯表單增加 username、重設密碼、停用帳號。

### 2.6 限流與列舉防護

- `login:<clientKey>:<username>`：10 次／10 分鐘。
- `login:<clientKey>`：30 次／10 分鐘（防止換 username 掃描）。
- 成功後可清除該 key 的失敗計數（目前的 `rateLimit` 需要增加 clear）。
- 所有失敗回同一錯誤碼；避免在訊息中區分「帳號不存在」與「密碼錯誤」。
- 目前 `rateLimit` 是 isolate 內記憶體，屬 best-effort；家庭規模足夠。若要多 isolate 精確限流，需 D1 計數表或 Durable Object（付費）。

### 2.7 與既有通行碼的關係

目前 `authenticate()` 同時接受：

1. `users.token_hash`（32 字元通行碼的 SHA-256）
2. `user_sessions.token_hash`（裝置 session）

加入密碼登入後，密碼登入產生的 token 走第 2 條，因此 `requireStrongPasscode`（AI 路由要求 token 長度 ≥ 32）仍會通過（session token 為 43 字元）。

需要決定：

- **方案 P1**：密碼與通行碼並存。通行碼作為備用／復原憑證，保留 `authenticate()` 第 1 條。
- **方案 P2**：設定密碼後停用通行碼登入。攻擊面較小，但管理員重設流程要更完整。
- **建議**：階段 2 先採 P1，保留 32 字元通行碼作 break-glass；等密碼流程穩定後再考慮停用。

### 2.8 遷移

- 既有使用者沒有 username／password。
- 管理員可在使用者管理面板逐一設定 username，或使用者用既有登入碼／通行碼登入後自行認領。
- 未設定 username 的使用者仍可用登入碼／通行碼登入。
- `auth_version` 預設 1；既有 `user_sessions` 一併預設 1，不影響現有登入。

## 3. 階段 2B：入口連結

### 3.1 個人入口 `#u=<username>`

- 前端在啟動最早期捕捉 `#u=`，立即 `history.replaceState` 清除。
- 打開登入彈窗，username 預填並隱藏或唯讀，焦點在密碼框。
- 不自動送出；密碼仍由 `POST /login` 驗證。
- 若目前已登入同一帳號，可直接進 app；若已登入其他帳號，密碼驗證後詢問是否切換。
- 不改後端，成本最低。

### 3.2 家庭入口 `#group=<entryCode>`

若要像 dgr 一樣「一個家庭連結 → 選成員 → 輸入密碼」：

新增：

```sql
CREATE TABLE groups (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  entry_code TEXT NOT NULL UNIQUE,
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE group_members (
  group_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('owner', 'member')),
  created_at TEXT NOT NULL,
  PRIMARY KEY (group_id, user_id)
);
```

- `entry_code`：`randomBytes(18).toString('base64url')`，24 字元，長期有效、可輪換。
- `GET /groups/by-entry/:code`（免認證）：回傳 group 名稱與成員的 `userId`、`username`、`label`；不吐 email、角色以外的敏感資料。
- 管理員／group owner 可輪換入口、管理成員、代發一次性登入碼。
- 入口連結只選家庭與成員；選成員後仍需密碼或登入碼。
- 預設不公開家庭目錄；只有持連結者能看到成員名單。成員名單可能是兒童個資，應可關閉、可輪換。
- 資料仍按 `user_id` 隔離；若要做「共享詞書／文章」，那是另一個資料模型專案（見第 6 節）。

### 3.3 連結類型總結

| 連結 | 是否含秘密 | 是否自動登入 | 後端需求 |
| --- | --- | --- | --- |
| `#login=<one-time code>` | 是（一次性） | 是 | 階段 1 已有 |
| `#u=<username>` | 否 | 否，只需密碼 | 無 |
| `#group=<entryCode>` | 入口碼（可輪換，非登入憑證） | 否，選成員後輸入密碼／登入碼 | groups 表與成員 API |

## 4. Cloudflare 限制與取捨

### 4.1 真正的限制

Cloudflare Workers 官方限制（2026-10 查閱）：

| 項目 | Workers Free | Workers Paid |
| --- | --- | --- |
| CPU time／HTTP 請求 | 10 ms | 5 分鐘（預設 30 秒） |
| 每日請求 | 100,000 | 無上限 |
| 記憶體 | 128 MB | 128 MB |
| D1 免費額度 | 5M rows read/day、100k rows written/day、5 GB | 依方案 |

官方文件也說明：一般 Worker 約 2.2 ms；認證、SSR、較大 payload 常見 10–20 ms。也就是說，**密碼雜湊很可能超過 Free 的 10 ms**。

Workers 的 WebCrypto 支援 PBKDF2，但沒有原生 scrypt／Argon2。純 JS／WASM 的 Argon2 在 Free 的 10 ms 內不現實。

Node WebCrypto 基準（僅供數量級參考，非 Workers 實測）：

| PBKDF2-SHA256 iterations | 約略耗時 |
| --- | --- |
| 10,000 | 1.5 ms |
| 50,000 | 5 ms |
| 100,000 | 9 ms |
| 210,000 | 18 ms |
| 600,000（OWASP 建議） | 52 ms |

### 4.2 五個選項

**選項 1：升級 Workers Paid（建議）**

- $5/月起，CPU 上限 5 分鐘（預設 30 秒）。
- PBKDF2 600k 約 50 ms，完全不是問題；也可考慮 Argon2 WASM。
- 安全性與標準做法一致，程式不複雜。
- 這是「要不要花 $5」的產品決定，不是技術難題。

**選項 2：Free + PBKDF2 100k + pepper**

- 約 9 ms，貼近 10 ms 上限；偶爾可能 1102。
- 加上 Worker secret pepper（HMAC）後，D1 單獨外洩無法離線破解；但 pepper 與 D1 同時外洩仍弱。
- 建議密碼至少 12 字元，並嚴格限流。
- 需要實測 Workers 上的 CPU；若超限，降到 50k。

**選項 3：Free + 快速 HMAC + pepper**

- `HMAC-SHA256(pepper, salt || password)`，<1 ms，完全不會撞 CPU。
- 不是 memory-hard；安全性依賴 pepper 保密與線上 rate limit。
- 若 D1 外洩但 Worker secret 未外洩，攻擊者無法離線破解。
- 若兩者同時外洩，弱密碼可被快速破解。
- 對家庭規模、強制 12+ 密碼、嚴格限流的情況，是可接受的務實折衷；但不建議當成通用做法。

**選項 4：Cloudflare Access / Zero Trust**

- Free 方案支援最多 50 位使用者（依 Cloudflare 方案）。
- 由 Cloudflare 處理登入（Email OTP、Google 等），Worker 驗證 Access JWT。
- 不需要自己存密碼，也沒有 KDF CPU 問題。
- 缺點：登录體驗變成 Cloudflare 頁面；需要網域與 Access 設定；不是「站內使用者名稱＋密碼」。
- 若目標是「安全、Free、少量家庭成員」，這是很乾淨的替代方案。

**選項 5：維持一次性登入碼**

- 階段 1 已是 80-bit 一次性碼、可撤銷、可設 TTL，對小孩與家庭裝置其實很好用。
- 缺點：成人每次新裝置要請管理員發碼；沒有「自己記得密碼」的體驗。
- 最省事、Free 完全沒問題。

### 4.3 其他限制

- **D1 Free**：登入會寫 `user_sessions`，每次登入一筆；家庭規模遠低於 100k writes/day。不是瓶頸。
- **Worker 請求數**：100k/day；家庭規模足夠。
- **限流**：目前是 isolate 記憶體內，跨 isolate 不精確；家庭規模可接受。要精確需 D1 計數或 Durable Object（付費）。
- **Worker 大小**：WebCrypto 不增加 bundle；WASM Argon2 才需要考慮。

## 5. 複雜度評估

| 工作 | 內容 | 粗估 |
| --- | --- | --- |
| 2A 使用者名稱＋密碼 | schema、`/login`、PBKDF2、限流、登入 UI、改密、管理員重設、測試 | 3–5 個工作日 |
| 2B 個人入口 `#u=` | 捕捉、清除、預填、雙語文案 | 0.5–1 個工作日 |
| 2C 家庭入口 `#group=` | groups／members、入口碼輪換、成員 API、家庭頁、owner 權限 | 3–5 個工作日 |
| 2D 共享學習資料 | group_id、權限、衝突、同步協議 | 以週計，獨立專案 |

「複雜很多」主要不是程式量，而是：

1. Free 的 KDF 取捨（選項 1–4）。
2. 家庭入口的產品決策（誰是 owner、成員名單是否公開、是否共享資料）。

如果選 Workers Paid + PBKDF2 600k，2A 的技術風險很低；如果堅持 Free，2A 也能做，但要接受選項 2 或 3 的安全折衷。

## 6. 建議路線

1. **先做 2A + 2B（個人入口）**：使用者名稱＋密碼、`#u=` 預填。這已能滿足「主站用户名+密碼」與「獨立入口只需密碼」。
2. **再決定要不要 2C 家庭入口**：若家庭成員需要「一個連結看到全家人」，再做 groups；若只是個人書籤，`#u=` 已足夠。
3. **2D 共享資料不要與登入混在一起**：先定資料擁有者、衝突與退出規則。
4. **KDF 決策**：
   - 願意付 $5/月 → Workers Paid + PBKDF2 600k（建議）。
   - 堅持 Free → 選項 3（HMAC + pepper）或選項 4（Cloudflare Access）；若選選項 2，先做 Worker CPU 實測。
5. **保留一次性登入碼**：小孩、臨時裝置、家長代發都很好用；不要用密碼取代它。

## 7. 待確認

1. 是否願意升級 Workers Paid（$5/月）？這是影響最大的決定。
2. 「獨立入口」是個人 `#u=username`，還是家庭 `#group=code`？還是兩者都要？
3. 家庭入口是否需要家長管理成員（建立、停用、代發登入碼、重設密碼）？
4. 家庭成員是否需要共享詞書／文章／QA？若是，另立資料共享專案。
5. 管理員是否也改用使用者名稱＋密碼，還是保留 32 字元通行碼？
6. 現有使用者要由管理員設定 username，還是登入後自行認領？

## 8. 最終決策（2026-10-19）

1. 維持 Cloudflare Workers Free，不升級 Paid。
2. 不做家庭／群組入口，也不做個人 `#u=username` 入口；只做「主站使用者名稱＋密碼」。
3. 一般使用者密碼最短 **10** 字元；管理員密碼最短 **12** 字元。
4. 管理員保留 32 字元通行碼作為緊急入口，同時可為自己設定使用者名稱＋密碼。
5. 既有使用者由管理員在「用戶管理」設定使用者名稱與初始密碼；使用者登入後可自行修改密碼。
6. 一次性登入碼（`#login=CODE`）與通行碼登入維持不變。

## 9. 實作結果

### 後端（Cloudflare Worker + D1）

- 新增 `cloudflare-worker/migrations/005_username_password.sql`：`users` 增加 `username`、`username_normalized`、`password_hash`、`password_updated_at`、`auth_version`、`is_active`；`user_sessions` 增加 `auth_version`。
- 新增 `cloudflare-worker/src/password.js`：PBKDF2-HMAC-SHA256 50,000 次＋伺服器端 pepper（`PASSWORD_PEPPER`，至少 32 字元），格式 `pbkdf2-sha256$<iterations>$<salt>$<peppered-hash>`。
- `POST /login`：使用者名稱不分大小寫（NFKC＋lowercase），錯帳密統一 401 `invalid_credentials`；停用帳戶 403 `account_disabled`；未設定 pepper 時 503 `password_not_configured`；限流為每 client 30 次／10 分鐘、每 client＋使用者名稱 10 次／10 分鐘。
- `POST /change-password`：驗證目前密碼，遞增 `auth_version`，保留目前 session、撤銷其他 session 與未使用登入碼。
