# AI 供應商金鑰「跟隨帳號」體驗改造方案

- 時間：2026-10-19 04:35:11
- 狀態：提案（待確認）
- 觸發案例：舊裝置設定好的個人供應商，換到新裝置（`http://10.10.10.149:8000`）登入後，供應商與模型仍在，但連線顯示「認證失敗，請檢查 API Key 或認證方式」。
- 相關檔案：`modules/ai-credential-sync.js`、`modules/ai-profile-storage.js`、`modules/sync-core.js`、`modules/ai-settings-sanitize.js`、`features/sync/ai-provider-settings.js`、`cloudflare-worker/src/ai-credentials.js`

## 1. 現況機制

1. **兩條同步通道**
   - 供應商定義（label、baseUrl、apiUrl、modelsUrl、format、authMode、allowedModels、discoveredModels、任務模型、個人預設）走一般 snapshot；`sanitizeAISettings` 會剝離金鑰（`modules/ai-settings-sanitize.js`）。
   - 金鑰只透過 `/ai-credentials` 同步，且必須 `syncMode === 'cloud'`（`modules/ai-credential-sync.js`）。
2. **本機儲存**
   - Profile 鍵名：`bdc_ai_profile_v1:<encoded-endpoint>:<encoded-user>`，另有 `bdc_ai_profile_v1:device:guest`（`modules/ai-profile-storage.js:80-99`）。
   - `localStorage` 按裝置與 origin 隔離；換裝置或換 `protocol://host:port` 都是全新的本機儲存。
3. **預設值**
   - 新增個人供應商預設 `syncMode: 'local-only'`（`features/sync/ai-provider-settings.js:598-628`）。
   - 未登入時儲存一律降為 `local-only`（`features/sync/ai-provider-settings.js:789`）。
4. **伺服器保護**
   - 金鑰以 AES-256-GCM 加密，AAD 綁定 user/provider/binding/version。
   - PUT/DELETE 採 `expectedVersion + mutationId` CAS；版本不符回 409，不會盲目覆蓋（`cloudflare-worker/src/ai-credentials.js`）。
5. **狀態顯示**
   - 全域「已同步」只代表 `/ai-credentials` 清單請求成功，不代表每個供應商金鑰都已下載（`features/sync/ai-provider-settings.js:262-281`）。
   - 本機完全沒有 credential 列時，`mode: 'none'` 會被顯示成「僅保存在此設備」（`features/sync/ai-provider-settings.js:351`）。

## 2. 問題判定

### 2.1 屬於設計選擇（非 bug）

- 金鑰不進 snapshot、預設 local-only、雲端金鑰需明確切換：都是隱私／安全設計。
- 真正的問題是：這些設計沒有被清楚地表達，且預設值與使用者「跟帳號走」的期待相反。

### 2.2 確認的實作缺陷

#### B1 冷裝置金鑰下載競態（高）

- 登入後 snapshot 自動同步與 credential sync 並行；credential sync 在登入事件後約 400ms 啟動（`modules/ai-credential-sync.js:1154-1168`），或啟動時已登入則約 1000ms 後啟動（`modules/ai-credential-sync.js:1188-1199`）。
- `runCredentialSync` 先 GET `/ai-credentials`，再讀本機 profile；`addDownloadTargets` 只會為「本機已存在 provider 定義」的遠端金鑰建立下載目標（`modules/ai-credential-sync.js:203-223, 584-660`）。
- 新裝置的 provider 定義要等 snapshot 的 `applyAISettingsPayload` 才寫入（`modules/sync-core.js:305-335`）；AI 群組又排在 dictation、vocabulary、articles、QA 之後，snapshot 較大時可能明顯較慢。
- 若 credential sync 先讀到空 profile，它會回報 `synced`；`applyRemoteAISettings` 之後沒有任何 `scheduleCredentialSync` 觸發。結果是：定義出現了、金鑰永遠不自動下載，直到使用者手動按「立即同步」、切回前景或下次登入。
- 這正是「我記得選了同步到帳號，但新裝置沒帶過來」最可能的成因。

#### B2 AI 定義群組可能被其他裝置覆蓋（高）

- snapshot 的 `aiSettings` 是 whole-group LWW（`modules/sync-core.js:470-477`）。
- `getAIProfileUpdatedAt()` 回傳整個 profile 的 `updatedAt`（`modules/ai-profile-storage.js:397-399`）；而 `updateAIProfile` 在任何寫入（包含 credential sync 的下載、版本確認、衝突狀態變更）都會把 `updatedAt` 更新為現在時間（`modules/ai-profile-storage.js:345-353`）。
- 因此一台只是「下載金鑰」的裝置，會讓自己的 AI 群組時間戳變成最新；下一次推送時，它手上可能較舊或不完整的 provider 定義會成為遠端版本，覆蓋其他裝置剛新增或修改的定義。
- 金鑰本身有 CAS，不會被靜默覆蓋；但**供應商定義**確實可能被另一台裝置覆蓋，這就是「多部機器互相覆蓋」的真實風險。

#### B3 狀態文案誤導（中）

- `mode: 'none'`（本機完全沒有金鑰列）顯示「僅保存在此設備」，使用者無法區分「本機有金鑰」與「本機根本沒有金鑰」。
- 全域「已同步」與 per-provider 狀態混在一起，使用者會以為金鑰已同步。
- 缺少「等待下載」「本機無金鑰」「上傳中」「綁定不一致」等狀態。

#### B4 帳號級策略缺失（中）

- 每個供應商都要單獨切換，沒有「跟隨帳號」的帳號級預設。
- 已在本機的 local-only 金鑰沒有主動提示可上傳，使用者只能自己發現下拉選單。
- 切換到「僅保存在此設備」不會移除雲端副本；「從帳號移除」是另一個選項，語義容易誤解。

## 3. 設計目標

1. **帳號優先**：登入狀態下，新供應商預設「跟隨帳號」；金鑰在明確同意後自動上傳。
2. **可預期**：每個供應商都有獨立、清楚的狀態；全域狀態不得掩蓋個別失敗。
3. **不靜默上傳、不靜默覆蓋**：首次上傳既有本機金鑰要提示；跨裝置定義衝突要可見。
4. **新裝置零操作**：登入後自動恢復供應商與金鑰，不需要手動按「立即同步」。
5. **離線可用**：未登入或網路失敗時本機金鑰仍可使用，恢復後自動補同步。
6. **安全**：沿用 AES-256-GCM 與 CAS；local-only 仍是明確 opt-out。

## 4. 方案

### 4.1 帳號級「AI 金鑰同步」設定（新增）

位置：全域設定 → AI 供應商 → 我的供應商區塊頂部。

- 選項：
  - `跟隨帳號（建議）`：新供應商預設 cloud；金鑰加密上傳；其他裝置自動下載。
  - `僅保存在本機`：所有新供應商預設 local-only；不自動上傳。
- 每個供應商仍保留 per-provider override：`同步到我的帳號` / `僅保存在本機` / `從帳號移除`。
- 首次從 local-only 切換到跟隨帳號，或登入後發現在本機有 local-only 金鑰時，顯示一次性確認：
  - 標題：「有 N 個供應商的金鑰僅保存在本機」
  - 說明：金鑰會以 AES-256-GCM 加密存放於同步伺服器。
  - 按鈕：`上傳到帳號` / `稍後` / `不要再問`
- 未登入時顯示：「未登入：金鑰只會保存在本機。登入後可跟隨帳號。」

### 4.2 新增／編輯供應商流程

- 登入且帳號設定為「跟隨帳號」時，表單的「金鑰同步」預設選 `同步到我的帳號`，並顯示一行說明。
- 未登入時隱藏雲端選項（現況已如此）；若之後登入，在供應商列顯示「可上傳到帳號」提示。
- 儲存成功後立即顯示 per-provider 狀態，不要只顯示全域 toast。

### 4.3 新裝置恢復與競態修復

- `applyAISettingsPayload` 成功寫入後呼叫 `scheduleCredentialSync(...)`，或 dispatch `bdc:ai-settings-applied` 由 credential sync 監聽。
- `runCredentialSync` 若發現「遠端有金鑰列、本機沒有對應 provider 定義」，記錄 `orphanRemote`；等 snapshot 套用後自動重跑一次（設上限，避免迴圈）。
- 登入後顯示 per-provider「正在從帳號恢復金鑰…」，完成後變「已同步」。
- 失敗（401/403/網路/綁定不一致）顯示具體原因與「重試」。

### 4.4 狀態模型與文案

每個供應商顯示以下狀態之一：

| 狀態 | 條件 | zh-CN | zh-HK |
|---|---|---|---|
| synced | cloud + hasKey + version > 0 | 已同步到账号 | 已同步到帳戶 |
| awaiting-download | cloud + !hasKey + 遠端有列 | 等待从账号下载密钥 | 等待從帳戶下載密鑰 |
| local-only | local-only + hasKey | 仅保存在此设备 | 僅保存在此裝置 |
| no-key | 無 credential 且 authMode !== none | 本机未保存密钥 | 本機未保存密鑰 |
| uploading | pending put | 正在上传… | 正在上載… |
| conflict | conflict | 账号与本机版本冲突 | 帳戶與本機版本衝突 |
| binding-mismatch | lastError = binding_mismatch | 地址已变更，需重新输入密钥 | 地址已變更，需重新輸入密鑰 |
| auth-required | 未登入 | 登录后可同步到账号 | 登入後可同步到帳戶 |

- 全域同步狀態改為彙總：`全部已同步` / `N 个供应商待处理` / `同步失败`。
- 不再用「僅保存在此設備」表示「本機沒有金鑰」。

### 4.5 多裝置定義覆蓋修復

- **拆分時間戳**：`aiProfile.updatedAt` 僅代表「定義／任務映射」變更；credential sync 的寫入不要更新它。
  - 新增 `credentialsUpdatedAt`（或 sync 寫入時保留原 `updatedAt`）。
  - `getAIProfileUpdatedAt()` 只回傳定義時間。
- **定義合併改為 per-provider LWW**：
  - `applyRemoteAISettings` 以每個 provider 的 `updatedAt` 比較，而不是整個 map 替換。
  - 刪除需要 tombstone（或保留目前「遠端沒有就刪除」但加上版本／時間），避免舊裝置把已刪除的供應商復活。
- 保留現有 credential CAS 與衝突 UI。
- snapshot schema 增加 `aiSettings.schemaVersion`；新舊客戶端並存時採保守合併（保留本機 local-only、僅覆蓋較新的 provider）。

### 4.6 安全與隱私

- 沿用 `/ai-credentials` 的 AES-256-GCM、AAD 綁定 user/provider/binding/version。
- 首次上傳既有金鑰需明確確認；不因登入而自動上傳。
- `僅保存在本機` 與 `從帳號移除` 的差異要在 UI 明示；切到 local-only 時提示「雲端副本仍保留，如需刪除請選『從帳號移除』」。
- 登出（SIGNED_OUT）仍清除本機帳號 profile；SESSION_INVALID 保留本機金鑰、只停止同步（現況正確）。

## 7. 驗收

1. 裝置 A 新建供應商（跟隨帳號）→ 裝置 B 登入 → 不按任何按鈕，供應商與金鑰自動可用；Network 顯示 `/ai-credentials/:id` 下載。
2. 裝置 A 在 snapshot 尚未套用時就觸發 credential sync（模擬慢網路）→ 套用後自動重試並下載成功。
3. 兩台裝置同時修改不同供應商 → 兩邊定義都保留；同一供應商衝突時可見並可選擇。
4. 未登入時新建供應商 → 顯示正確的「本機未保存／僅本機」狀態；登入後提示上傳，不自動上傳。
5. 切換到「僅保存在本機」→ 雲端副本仍在且 UI 明示；選「從帳號移除」才刪除。
6. zh-CN / zh-HK 新增文案鍵集合與插值參數一致，無硬編碼。
7. `node --test tests/ai-worker.test.mjs tests/ai-units.test.mjs tests/ai-sync-regressions.test.mjs` 全綠；新增競態與雙裝置測試。

## 8. 風險

- 預設改為 cloud 屬隱私敏感變更，需明確告知與一次性確認。
- per-provider LWW 需要 tombstone，否則已刪除的供應商可能被舊裝置復活。
- 舊客戶端仍可能以 whole-group 推送；需以 schema/版本協商或保守合併降低覆蓋。
- 金鑰下載仍受 binding 限制；URL 變更時必須引導重新輸入，不能放寬。

## 9. 實作結果

- 實作日期：2026-10-19
- 實際範圍：P0 + P1 + P2 的安全子集（時間戳拆分）。per-provider LWW／tombstone 未實作，留待後續（見 §9.3）。

### 9.1 已實作

**P0（bugfix）**

- **B1 冷啟動競態**：`modules/sync-core.js` 的 `applyAISettingsPayload` 在遠端 AI 設定成功寫入後 dispatch `window` CustomEvent `bdc:ai-settings-applied`；`modules/ai-credential-sync.js` 的 `initAICredentialSync` 監聽該事件，登入狀態下呼叫 `scheduleCredentialSync(300)`。`sync-core` 沒有 import `ai-credential-sync`（避免循環依賴），事件只會安排一次同步、不會寫入供應商定義，因此不會自我觸發。
- **B3 逐供應商狀態**：`features/sync/ai-provider-settings.js` 新增 `providerKeyStatusLabel`，依序為 pending put → 移除雲端 → binding_mismatch → conflict → 無 credential → cloud → local-only。`mode: none` 且 `authMode !== 'none'` 改顯示「本机未保存密钥 / 本機未儲存密鑰」，不再誤用「仅保存在此设备」。
- **全域同步狀態改為彙總**：錯誤狀態保留原文案；同步中顯示「正在同步密钥…」；有 conflicts 或 pending 顯示「N 个供应商待处理 / N 個供應商待處理」；所有（非 `authMode:none`）供應商都有 Key 時，若仍有僅保存在本機的 Key，顯示「N 个供应商仅保存在本机 / N 個供應商僅儲存在此裝置」，否則顯示「全部已同步 / 全部已同步」；其餘回到「密钥同步待命」。
- 無 credential 列的供應商，其同步方式下拉選單改為停用（顯示帳號政策），避免選了之後才跳出 `credential_missing`。
- `binding_mismatch` 不再重複印出原始錯誤碼那一行（狀態標籤與「服務地址已變更」提示已表達）。

**P1（體驗）**

- **帳號級金鑰同步政策**：`aiProfile.keySyncDefault: 'cloud' | 'local-only'`（預設 `cloud`），已加入 `emptyProfile`、`normalizeProfile`（`normalizeKeySyncDefault`）、`applyRemoteAISettings`、`sanitizeAISettings`、`getAIViewFromProfile`，並同步更新 Cloudflare Worker 與 selfhost 的 `snapshot-sanitize.js`，否則伺服器會在清洗時把欄位丟掉。舊 snapshot 沒有此欄位時，`applyRemoteAISettings` 保留本機政策，不會被重設為預設值。新增 `setAIKeySyncDefault(mode, scope)` 寫入 profile。
- **UI 政策下拉選單**：登入後在「我的供應商」區頂部（說明文字之後）新增 `settings.aiKeySyncPolicy` 下拉選單（`data-ai-key-sync-policy`，選項為「跟隨帳號」與既有的「僅保存在此設備」），變更時 `setAIKeySyncDefault` + `syncTouch('aiSettings')`。未登入時不顯示（該設定是帳號範圍）。
- **新增供應商表單**：登入時 `form.syncMode` 預設取 `profile.keySyncDefault`，未登入仍強制 `local-only`（`saveForm` 的既有保護未動）。
- **本機金鑰上傳提示**：登入後若存在「有 Key 且 `syncMode === 'local-only'`」且未被忽略的 credential，顯示可關閉橫幅（標題／說明／上載到帳戶／稍後／不再提醒）。
  - 上載：逐個 `setProviderKeySyncMode(id, 'cloud')`（單一失敗以 try/catch 跳過），再 `await syncCredentials({ reason: 'upload-prompt' })`；完成後逐個覆核，仍有殘留則顯示「有 N 个供应商上传失败」。
  - 「稍後」只在本次登入的有效期間隱藏（換帳號／登出會重置）；「不再提醒」以 `localStorage: bdc_ai_key_upload_prompt_dismissed_v1:<userId>` 按帳號持久化。
  - 位址已變更（`bindingVerified === false`）的本機金鑰不列入提示，需使用者重新輸入金鑰。
- **新裝置恢復狀態**：`cloud + !hasKey` 且 credential sync 正在同步時顯示「正在从账号恢复密钥… / 正在從帳戶恢復密鑰…」，其餘情況顯示「等待从账号下载密钥」；失敗時保留具體狀態（錯誤碼／綁定不一致）與既有的「立即同步」按鈕。

**P2a（時間戳拆分）**

- `updateAIProfile(mutator, scope, options = {})` 新增 `touchUpdatedAt`（預設 `true`）；`false` 時保留原 `updatedAt`。
- `commitCredentialChanges`（下載、版本確認、衝突狀態、錯誤碼）與 `setProviderKeySyncMode` 傳 `{ touchUpdatedAt: false }`；`savePersonalProvider`、`deletePersonalProvider`、`importGuestProviders`、`applyAISettingsPatch` 維持預設 `true`。
- 效果：只下載金鑰的裝置不再把自己的 AI 定義群組時間戳推成最新，降低 B2 描述的全群組覆蓋風險。

### 9.5 偏差與已知取捨

1. **`keySyncDefault` 是 AI 定義群組的一部分**，會隨整組 LWW 被覆蓋。伺服器清洗器已保留合法值；舊客戶端推送的 `aiSettings` 沒有這個欄位時，新客戶端會保留本機政策，不會重設為 `cloud`。影響仍僅限「新供應商的預設值」，不會自動上載既有金鑰。
2. **per-provider 同步下拉選單在「沒有 credential 列」時改顯示帳號政策**（原本固定顯示 `local-only`），與逐供應商狀態一致。
3. `binding_mismatch` 的原始錯誤碼行不再重複顯示（狀態標籤＋位址變更提示已表達）。
4. 彙總狀態保留既有的最後同步時間與「{count} 项等待同步」（僅計 pending）；`sync.aiKeyPendingProviders` 的計數為 conflicts ∪ pending。
5. `tests/ai-sync-regressions.test.mjs` 檔尾新增 `after()` 清理（`stopCredentialSync` + `destroyAICatalog`）：管理目錄的測試會安裝 catalog 的驗證監聽器，本次新增的測試再次登入時會重新啟動其 5 分鐘刷新計時器，否則測試程序無法結束。這是測試環境現象，不是產品行為改變。
